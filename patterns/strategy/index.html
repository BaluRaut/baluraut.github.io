Behavioral Pattern

The Strategy pattern - swap algorithms without touching the caller

Some code has to do the same job several ways: pay by card or PayPal, sort by price or rating, compress with zip or gzip. Strategy captures each way as a separate object behind a common interface, then lets you choose one at runtime. The client keeps working the same, while the behavior it uses becomes a plug-in you can add, replace, or test in isolation.

01 - What

What is the Strategy pattern?

Strategy defines a family of algorithms, encapsulates each one in its own class, and makes them interchangeable behind a shared interface. The object that needs the work (the context) holds a reference to a strategy and delegates to it, so the algorithm can vary independently from the code that uses it. Instead of a growing chain of if/else deciding how to do something, you hand the context an object that already knows how.

🧩 Strategy interface

A single method (or small set) that every algorithm implements. This is the contract the context depends on, never the concrete classes.

⚙️ Concrete strategies

Interchangeable implementations - card payment, gzip compression, price sort. Each is self-contained and testable on its own.

📦 Context

Holds a strategy and delegates to it. It exposes a setter or takes the strategy in its constructor, then never cares which one it has.

Key mental model: Strategy turns a verb into a noun. "How should I sort/pay/compress?" stops being a branch inside one method and becomes an object you can pass around, swap, and unit test. The context asks what, the strategy owns how.
02 - Why

Why the Strategy pattern exists

The alternative is one method that grows a new if branch every time a variant appears. That method violates the open/closed principle, mixes unrelated logic, and becomes impossible to test in pieces. Strategy pulls each variant out into its own object so behavior can change without editing the caller.

🚫 Kills conditional sprawl

Replaces a fat switch on "type" with polymorphism. Adding a variant means adding a class, not editing a branch that every other variant shares.

🔓 Open for extension

New algorithms plug in without modifying the context or existing strategies. Closed for modification, open for extension - the open/closed principle in practice.

🔁 Swappable at runtime

Change behavior while the program runs: pick a compression level from config, choose a routing algorithm based on load, switch pricing rules per customer.

🧪 Isolated and testable

Each strategy is a small unit with one job, so you test algorithms independently and mock them out when testing the context.

In Plain Terms

Strategy explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is like choosing a route home. Walking, bus, or bike all get you there; you pick one based on the weather and time. The destination (the interface) is fixed; the method (the strategy) is interchangeable.

👩‍💻 For a developer

It is a function passed as an argument. Instead of hardcoding how to sort, you hand the sorter a comparator. Same call site, different behavior, decided by whoever supplies the object.

🏢 For a professional

Think of a payment terminal that accepts card, contactless, or wallet. The cashier runs the same "take payment" step; the customer chooses the method. The till does not need a branch per payment type.

🧳 Everyday version

A power adapter for travel. Your laptop plugs in the same way; you swap the wall prong for the country you are in. The device stays identical; only the plug strategy changes.

03 - How

How it works under the hood

Strategy is built on composition and delegation. The context has a strategy rather than being a subclass of one, so the algorithm lives in a separate object the client can inject and replace at will.

🔗 Composition, not inheritance

The context holds a strategy field and delegates the varying step to it. Behavior is assembled at runtime by wiring objects, not fixed at compile time by a class hierarchy.

🎯 Program to an interface

The context depends only on the strategy interface. Concrete algorithms are invisible to it, which is what makes them swappable and independently testable.

A realistic example in Java

// 1. The strategy interface - the common contract
interface PaymentStrategy {
    void pay(int amountCents);
}

// 2. Interchangeable concrete strategies
class CreditCardPayment implements PaymentStrategy {
    private final String number;
    CreditCardPayment(String number) { this.number = number; }
    public void pay(int amountCents) {
        System.out.printf("Charged %d to card %s%n", amountCents, mask(number));
    }
    private String mask(String n) { return "****" + n.substring(n.length() - 4); }
}

class PayPalPayment implements PaymentStrategy {
    private final String email;
    PayPalPayment(String email) { this.email = email; }
    public void pay(int amountCents) {
        System.out.printf("Charged %d via PayPal (%s)%n", amountCents, email);
    }
}

// 3. The context - delegates, never branches on payment type
class Checkout {
    private PaymentStrategy strategy;
    void setStrategy(PaymentStrategy s) { this.strategy = s; }
    void checkout(int amountCents) {
        if (strategy == null) throw new IllegalStateException("No payment method");
        strategy.pay(amountCents);   // the varying step, delegated
    }
}

// 4. The client selects a strategy at runtime
Checkout checkout = new Checkout();
checkout.setStrategy(new CreditCardPayment("4242424242424242"));
checkout.checkout(1999);

checkout.setStrategy(new PayPalPayment("buyer@example.com")); // swap, same call
checkout.checkout(1999);

Notice the context has no conditional on payment type. Adding CryptoPayment means writing one new class - Checkout never changes. That is composition doing the work a switch statement used to do.

Functional strategies with lambdas (TypeScript)

// When a strategy is a single method, it is just a function type.
type SortStrategy<T> = (a: T, b: T) => number;

class ProductList {
  constructor(private items: Product[]) {}
  sortBy(strategy: SortStrategy<Product>): Product[] {
    return [...this.items].sort(strategy);
  }
}

// Strategies as plain lambdas - no class boilerplate needed
const byPriceAsc:  SortStrategy<Product> = (a, b) => a.price - b.price;
const byRatingDesc: SortStrategy<Product> = (a, b) => b.rating - a.rating;

const list = new ProductList(catalog);
list.sortBy(byPriceAsc);    // choose an algorithm at the call site
list.sortBy(byRatingDesc);  // swap it freely

// A registry makes runtime selection data-driven
const sorters: Record<string, SortStrategy<Product>> = {
  price:  byPriceAsc,
  rating: byRatingDesc,
};
list.sortBy(sorters[userChoice] ?? byPriceAsc);

In modern languages a strategy with one method collapses into a lambda. The pattern is identical - interface, interchangeable implementations, runtime selection - but a functional interface (Comparator, Runnable, a function type) removes the class ceremony.

05 - Step by Step

The 0 → 100 flow

From spotting a fat conditional to shipping interchangeable, testable algorithms - the whole journey in order.

00
Spot

Notice the varying behavior

You find a method doing one job several ways, branching on a "type" or "mode" flag. That branch is the algorithm family Strategy will extract.

10
Define

Declare the strategy interface

Name the single operation the algorithms share, like pay(amount) or compress(data). Keep it minimal and free of any concrete detail.

20
Extract

Pull each branch into a class

Move each arm of the conditional into its own concrete strategy implementing the interface. One algorithm, one class, one responsibility.

30
Compose

Give the context a strategy field

Add a field of the interface type plus a constructor or setter. The context now has a strategy instead of hardcoding the algorithm.

40
Delegate

Replace the branch with a call

Swap the old switch for strategy.execute(...). The context stops knowing which algorithm runs; it just delegates.

50
Inject

Wire the strategy from the client

The client, factory, or DI container chooses a concrete strategy and passes it in. Selection logic lives at the edge, not inside the context.

60
Select

Map runtime input to a strategy

A registry or factory keyed by user choice or config picks the algorithm at runtime, keeping the mapping in one small, obvious place.

70
Simplify

Collapse tiny strategies to lambdas

If the interface has one method, express simple strategies as lambdas or function references and drop the class boilerplate.

80
Test

Unit test each algorithm alone

Each strategy is isolated, so test it directly. Test the context with a stub strategy to prove it delegates correctly.

90
Extend

Add variants without edits

A new algorithm is a new class or lambda registered in the selector. The context and existing strategies stay untouched - open/closed in action.

100
Ship

Swap behavior in production

Change algorithms via config or feature flags with zero redeploy of the context, and roll out new variants safely behind selection logic.

Common Pitfalls

Pitfalls & anti-patterns

Strategy is simple, which makes it easy to over-apply or wire up badly. Watch for these.

🪆 Strategy explosion

Creating a class for behavior that never varies, or for a one-off, adds indirection without payoff. Reach for Strategy when there are real, multiple interchangeable algorithms - not just one.

🔀 Leaking the choice back in

If the context still switches to decide which strategy to build, you moved the conditional, not removed it. Put selection in a factory or registry, not inside the context.

🧷 Fat interface

Cramming many unrelated methods into the strategy interface forces every algorithm to implement things it does not need. Keep the contract to the one operation that actually varies.

📤 Passing too much context

Handing the strategy the entire context object couples them tightly. Pass just the data the algorithm needs as parameters so strategies stay independent and reusable.

🌀 Confusing it with State

Using Strategy where the object should transition between behaviors on its own leads to awkward external switching. If the behavior change is internal and self-driven, you want State.

🧊 Stateful shared strategies

Giving a shared strategy instance mutable per-call state causes race conditions when it is reused across threads or requests. Keep strategies stateless or create one per use.

Trade-offs

Trade-offs & when to use

Strategy trades a little indirection for a lot of flexibility. Use it when variants are real and likely to grow.

AspectDetail
ProsRemoves conditional sprawl, honors open/closed, enables runtime swapping, isolates and simplifies testing of each algorithm.
ConsMore classes and indirection, clients must know the strategies exist to choose one, overkill when behavior never varies.
Use whenYou have multiple interchangeable ways to do one job, the set is likely to grow, or you need to select behavior at runtime by config or input.
Avoid whenThere is only one algorithm, variants never change, or the behavior transitions are internal and self-driven (that is State).
ComplexityLow. One interface, N implementations, one delegating field. Lambdas cut it further for single-method strategies.
RelatedState (self-driven transitions), Template Method (fixed skeleton, inheritance), Decorator (wrap to add behavior), Factory Method (create the strategy).
Rule of thumb: if you are writing a switch on a "type" to decide how to do something, and that switch keeps gaining cases, reach for Strategy. If the object should decide its own next behavior, reach for State instead.
06 - Case Studies

Real-world case studies

Three representative uses showing Strategy in production-style code.

💳

1 · Payment processing at checkout

Pattern: interchangeable payment algorithms

An e-commerce checkout must accept card, PayPal, wallet, and later buy-now-pay-later, without the order flow branching on each.

  • Each provider implements a PaymentStrategy with a single pay(amount) method.
  • A registry maps the user's selected method to the right strategy at runtime.
  • Adding a new provider is one new class plus a registry entry, with the checkout untouched.
✅ Outcome: New payment methods ship without changing or re-testing the checkout flow, and each provider is tested in isolation.
🗜️

2 · Pluggable compression in a storage layer

Pattern: algorithm chosen by config or content

A file service compresses uploads, but the best codec depends on file type and a tunable speed-versus-ratio setting.

  • A Compressor interface is implemented by gzip, zstd, and a no-op strategy.
  • The chosen strategy comes from configuration, so operators tune it without a redeploy.
  • Benchmarks run each strategy independently since none depend on the storage context.
✅ Outcome: The team switches codecs per bucket via config and adds zstd with zero changes to the upload pipeline.
🔢

3 · Sorting and ranking in a product catalog

Pattern: functional strategies as comparators

A catalog page lets shoppers sort by price, rating, relevance, or newest, with new orderings added often.

  • Each ordering is a comparator lambda, no class boilerplate required.
  • A map from the UI choice to a comparator selects the strategy per request.
  • Composite strategies combine comparators (rating then price) by chaining.
✅ Outcome: Product managers add sort options as small, pure functions, each trivially unit tested, with no risk to the page logic.
07 - Relevance

Modern relevance

Strategy is one of the most enduring patterns because modern languages make it nearly free and dependency injection makes it the default way to vary behavior.

🧬 Lambdas made it trivial

Functional interfaces and function types let a single-method strategy become a one-line lambda, so the pattern shows up everywhere without the old class overhead.

💉 It powers dependency injection

Injecting an interface implementation is Strategy by another name. DI containers wire concrete strategies into contexts as a matter of course.

🎚️ Behavior behind feature flags

Selecting a strategy by flag or config lets teams roll out and A/B test algorithm variants in production without redeploying the caller.

🔌 Plugin architectures

Extensible systems expose a strategy interface so third parties can drop in new algorithms - payment providers, exporters, validators - safely.

⚡ Testable by design

Isolated strategies fit unit testing and mocking perfectly, which is why they are favored in codebases that prize fast, focused tests.

🧠 Policy objects in ML and pricing

Ranking, routing, and pricing "policies" are Strategy objects swapped as models and rules evolve, keeping the surrounding system stable.

Bottom line: Strategy is how you make behavior a first-class, swappable thing. Whenever a piece of logic has several interchangeable implementations, capturing them behind one interface keeps your code open to new variants and closed to breaking the ones that already work.
