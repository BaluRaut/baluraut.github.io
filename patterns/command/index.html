Behavioral Pattern

The Command pattern - turning actions into objects

The Command pattern wraps a request as a standalone object with an execute() method, decoupling the thing that triggers an action from the thing that performs it. Because each action is now a first-class object, you can queue it, log it, replay it, batch it into a macro, and above all undo it. It is the backbone of every editor, task queue, and transactional UI you have ever used.

01 - What

What is the Command pattern?

Command is a behavioral design pattern that turns a request into a self-contained object. That object carries everything needed to perform the action later: the receiver to act on, the method to call, and the arguments to pass. The caller no longer says "do this now"; it holds an object and says "run this when you are ready." That small shift is what unlocks undo, queuing, logging, and macros.

📦 Request as object

An action becomes a value you can store in a variable, pass around, and put in a list, rather than a method call that runs and vanishes.

▶️ A uniform execute()

Every command exposes the same tiny interface, so the invoker treats "delete text" and "send email" identically without knowing the details.

↩️ Reversible by design

Pair execute() with undo() and each command knows how to reverse itself, giving you history, redo, and transactional rollback for free.

Key mental model: the Command pattern separates what to do (the command object) from when and how often to do it (the invoker). Once an action is an object, time and repetition become things you control.
02 - Why

Why the Command pattern exists

Calling a method directly is fine until you need to defer it, repeat it, record it, or take it back. A raw method call has no memory and no reverse gear. Wrapping the call in an object gives the action an identity you can manage.

↩️ Undo and redo

If each command can reverse itself, a stack of executed commands becomes an undo history and a stack of undone ones becomes redo. This is the single biggest reason the pattern exists.

⏳ Queue and schedule

Because a command is just data, you can push it onto a queue, run it on a worker thread, retry it, or delay it, all without the caller knowing when it runs.

🧾 Log and replay

Serialize commands to a log and you can audit every change, replay them to rebuild state, or ship them across a network as an event stream.

🔗 Decouple caller from worker

A button, a menu item, and a keyboard shortcut can all fire the same command object. The invoker never learns what the receiver is or how it works.

In Plain Terms

Command explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

A command is a written homework instruction on an index card. The teacher (invoker) hands you a stack of cards; each card knows exactly what task to do. You can reorder the stack, redo a card, or tear one up to undo it, without the teacher knowing the details of any task.

👩‍💻 For a developer

It is a closure with a name and a reverse. Instead of doc.insert("hi") running now, you build an object holding the receiver, the args, and an undo(). The invoker calls cmd.execute() and can push it onto a history stack.

🏢 For a professional

Think of a restaurant order ticket. The waiter (invoker) writes the order and clips it to the rail; the kitchen (receiver) cooks it. The ticket queues, gets logged, and can be voided. The waiter never touches a stove.

🔌 Everyday version

A remote control button. Each button holds one command bound to a device. Press it to run the action, and a well-designed remote has an undo or "last channel" that reverses what you just did.

03 - How

How it works under the hood

A command binds a receiver plus arguments behind a uniform execute(). An invoker runs commands and keeps two stacks, one for undo and one for redo, so history becomes a simple push and pop.

🧱 Building a command

The client constructs a concrete command, capturing the receiver and the arguments it needs. For undo, the command also records the state it will overwrite, so it can restore it later.

🗂️ Running the history

The invoker calls execute(), pushes the command onto the undo stack, and clears redo. Undo pops the top command and calls undo(); redo pops from the redo stack and re-executes.

A realistic text-editor example (Java)

// Command interface: every action is execute + undo
interface Command {
    void execute();
    void undo();
}

// Receiver: knows how to actually mutate text
class Document {
    private final StringBuilder buf = new StringBuilder();
    void insert(int pos, String text) { buf.insert(pos, text); }
    void delete(int from, int len)    { buf.delete(from, from + len); }
    String read(int from, int len)    { return buf.substring(from, from + len); }
    @Override public String toString() { return buf.toString(); }
}

// Concrete command: insert, and remember how to reverse it
class InsertTextCommand implements Command {
    private final Document doc;
    private final int pos;
    private final String text;
    InsertTextCommand(Document doc, int pos, String text) {
        this.doc = doc; this.pos = pos; this.text = text;
    }
    public void execute() { doc.insert(pos, text); }
    public void undo()    { doc.delete(pos, text.length()); }
}

// Concrete command: delete captures what it removed so undo can restore it
class DeleteTextCommand implements Command {
    private final Document doc;
    private final int from, len;
    private String removed;               // state saved during execute()
    DeleteTextCommand(Document doc, int from, int len) {
        this.doc = doc; this.from = from; this.len = len;
    }
    public void execute() {
        removed = doc.read(from, len);    // snapshot before destroying it
        doc.delete(from, len);
    }
    public void undo() { doc.insert(from, removed); }
}

// Invoker: runs commands and maintains undo/redo history
class CommandStack {
    private final Deque<Command> undo = new ArrayDeque<>();
    private final Deque<Command> redo = new ArrayDeque<>();
    void run(Command c) { c.execute(); undo.push(c); redo.clear(); }
    void undo() { if (!undo.isEmpty()) { Command c = undo.pop(); c.undo(); redo.push(c); } }
    void redo() { if (!redo.isEmpty()) { Command c = redo.pop(); c.execute(); undo.push(c); } }
}

// Client wiring it together
Document doc = new Document();
CommandStack editor = new CommandStack();
editor.run(new InsertTextCommand(doc, 0, "Hello world"));
editor.run(new DeleteTextCommand(doc, 5, 6));   // "Hello"
editor.undo();                                  // back to "Hello world"
editor.redo();                                  // "Hello" again

Notice that DeleteTextCommand snapshots the removed text during execute(), not in its constructor, because the correct value only exists at run time. That captured state is exactly what makes undo() possible, and it is the detail most naive implementations get wrong.

05 - Step by Step

The 0 → 100 flow

From defining the interface to shipping full undo, redo, and macros, the whole journey in order.

00
Define

Declare the Command interface

Start with the smallest contract: execute(), and undo() if reversibility matters. Every action in the system will implement it.

10
Receiver

Identify who does the work

Find the objects that already know how to perform the operations, the document, the light, the account. Commands delegate to them; they hold the real logic.

20
Wrap

Create concrete commands

For each action, build a class that captures a receiver plus its arguments and calls the receiver inside execute().

30
Reverse

Make each command undoable

Implement undo() so a command reverses its own effect. Snapshot any state you will overwrite during execute(), not before.

40
Invoker

Build the invoker

Add a component that receives command objects and calls execute() on them, staying ignorant of what each command actually does.

50
History

Add the undo stack

Every executed command is pushed onto a stack. Undo pops the top and calls its undo(). Now you have single-level and multi-level undo.

60
Redo

Add the redo stack

When you undo, move the command to a redo stack. Redo pops it and re-executes. Any fresh command clears redo to keep history linear.

70
Bind

Wire triggers to commands

Point buttons, menu items, and shortcuts at the same command objects. The UI fires commands; it never calls receivers directly.

80
Macro

Compose commands into macros

A macro command holds a list of commands and runs them in order, undoing them in reverse. One user gesture becomes many atomic steps.

90
Queue

Queue, log, or persist

Because commands are objects, enqueue them for a worker, write them to an audit log, or serialize them to replay and rebuild state later.

100
Ship

Robust, reversible actions

You now have a system where every action is testable, queueable, loggable, and reversible, all behind one tiny interface.

Common Pitfalls

Pitfalls & anti-patterns

The pattern is simple, but undo and state capture are where most implementations quietly break.

📸 Capturing state too early

Recording the value to restore in the constructor instead of during execute() means undo restores a stale or wrong value. Snapshot at execution time.

🫥 Half-undoable macros

A macro that fails midway but does not roll back the steps it already applied leaves state inconsistent. Undo applied sub-commands in reverse on failure.

🧨 God commands

Cramming real business logic into the command instead of delegating to a receiver turns commands into a dumping ground and defeats the decoupling.

♾️ Unbounded history

Keeping every command forever grows memory without limit, especially when commands hold large snapshots. Cap the stack or use lighter deltas.

🔗 Leaky references in undo

Undo that reverses by re-running forward logic, rather than restoring saved state, drifts when other commands ran in between. Reverse from captured data.

🏗️ Over-engineering trivial actions

Wrapping a single fire-and-forget call that never needs undo, queuing, or logging in a command class adds ceremony with no payoff. Use it where it earns its keep.

Trade-offs

Trade-offs & when to use

Command buys you flexibility around time, repetition, and reversal, at the cost of more classes and indirection.

AspectDetail
ProsDecouples invoker from receiver; enables undo/redo, queuing, logging, and macros; each command is easy to test in isolation; satisfies open/closed - add actions without touching the invoker.
ConsIntroduces many small classes; adds a layer of indirection; robust undo and state capture require care; can feel heavy for simple actions.
Use whenYou need undo/redo, want to queue or schedule work, must log or replay actions, need macros, or want one action reachable from many triggers.
Avoid whenThe action is a one-off call that never needs to be deferred, repeated, logged, or reversed. A plain method or lambda is enough.
ComplexityLow to moderate for basic execute; moderate once you add reliable undo, redo, and transactional macros.
RelatedMemento (stores the state a command restores), Observer (fires commands on events), Strategy (swaps an algorithm), Chain of Responsibility (routes a request through handlers).
Rule of thumb: reach for Command the moment an action needs a life beyond "run now" - if you must undo it, queue it, log it, or batch it, wrap it in a command; otherwise call the method directly.
06 - Case Studies

Real-world case studies

Three representative systems where the Command pattern is the load-bearing structure.

📝

1 · Text and graphics editor undo history

Pattern: reversible edits on a document

A word processor or design tool needs unlimited undo and redo across every kind of edit, from typing to moving shapes.

  • Every edit - insert, delete, format, move - is a command with execute() and undo().
  • An undo stack and redo stack turn Ctrl+Z and Ctrl+Y into simple push and pop.
  • Grouped edits become a macro command so one gesture undoes as a single unit.
✅ Outcome: users edit fearlessly because any action can be reversed, and the editor code stays uniform since the invoker treats all edits alike.
📥

2 · Background task queue and job workers

Pattern: deferred, retryable, logged execution

A system needs to run work asynchronously - send emails, process images, sync data - reliably and with an audit trail.

  • Each job is a serialized command placed on a durable queue for a worker to run.
  • Failed commands are retried or moved to a dead-letter queue without touching callers.
  • The command log doubles as an audit trail and a way to replay work after an outage.
✅ Outcome: producers stay fast and decoupled while workers execute, retry, and log commands independently, giving durability and observability for free.
🏠

3 · Smart-home and remote-control automation

Pattern: one interface over many devices

A universal remote or home hub must control lights, blinds, and media from many vendors through a single UI.

  • Each button or scene holds a command bound to a specific device receiver.
  • A "movie night" scene is a macro command that runs several device commands at once.
  • An undo or "all off" command reverses the last scene using stored prior states.
✅ Outcome: the hub adds new devices without changing its UI, since every control is just another command behind the same execute() call.
07 - Relevance

Modern relevance

Command is far from a museum piece; its shape underpins some of the most active ideas in modern software architecture.

🧩 CQRS command handlers

Command Query Responsibility Segregation models every write as a command object dispatched to a handler, a direct descendant of this pattern.

📜 Event sourcing

Storing an append-only log of commands or events lets you rebuild state by replaying history, exactly the log-and-replay use case.

⚛️ Redux and reducers

Front-end state stores dispatch action objects to reducers; time-travel debugging is undo/redo over a command history in disguise.

🌐 Distributed task queues

Systems like Celery and Sidekiq serialize commands onto brokers so workers execute, retry, and schedule them across machines.

🔄 Sagas and rollbacks

Long-running distributed transactions use compensating commands to undo prior steps, the macro rollback idea at cloud scale.

🤖 Agent tool calls

An LLM agent emitting structured tool invocations that a runtime executes and logs is the Command pattern applied to AI actions.

Bottom line: the Command pattern is how you give an action an identity so you can control its timing, repetition, and reversal. From editors to event sourcing to agent tool use, that idea only grows more central.
