OOP Concept

Liskov Substitution Principle - subtypes you can trust anywhere the base type is expected

The Liskov Substitution Principle says a program using a base type must keep working correctly when you hand it any subtype, with no special casing and no surprises. That promise only holds when the subtype honors the base contract: it cannot demand more from callers, cannot deliver less than they were told to expect, and cannot quietly break the guarantees the base type made. When a subtype cheats on that contract, code that looked polymorphic starts failing in production.

01 - What

What is the Liskov Substitution Principle?

LSP is the "L" in SOLID. Barbara Liskov's original phrasing is that if S is a subtype of T, then objects of type T can be replaced with objects of type S without altering any of the desirable properties of the program. In plain terms: a subtype must behave like its base type, not just share its shape. Inheritance gives you the method signatures for free; LSP is about honoring the behavior those signatures promised.

🔁 Substitutability

Any code written against the base type keeps working when a subtype is passed in. The caller should never need to check the concrete class.

📜 Behavioral subtyping

It is not enough to inherit or implement an interface. The subtype must respect the meaning of every method, not just match its parameters and return type.

🤝 Contract, not shape

Each method carries a contract of what it needs and what it guarantees. The subtype is bound by that same contract, no tighter, no weaker.

The three contract rules

RuleWhat it meansViolation looks like
Preconditions cannot strengthenThe subtype cannot demand more of callers than the base type didA subtype rejects inputs the base accepted, or requires extra setup
Postconditions cannot weakenThe subtype must guarantee at least what the base promised on returnA subtype returns null, a partial result, or skips a promised side effect
Invariants preservedTruths that always hold on the base must still hold on the subtypeA subtype leaves an object in a state the base type forbids
History constraintThe subtype cannot allow state changes the base type disallowedA mutable subtype of an immutable base lets callers mutate hidden state
Exception compatibilityThe subtype should not throw new checked exceptions the base did notA subtype throws NotSupported for a method the base said always works
Key mental model: inheritance answers "is this the same shape?" LSP answers "can I trust this thing to behave like the promise on the label?" A subtype that throws where the base returned, or that only accepts half the inputs, is a subtype in the type checker but a liar at runtime.
02 - Why

Why LSP matters

LSP is what makes polymorphism safe. Without it, every call site has to know which concrete subtype it received, and the abstraction you built collapses into a pile of type checks.

🧱 Polymorphism you can rely on

When subtypes are honest, one line of code works for every implementation. A checkout flow can accept any PaymentGateway and never branch on the vendor.

🚫 Kills defensive type checks

Code littered with if (repo instanceof ReadOnlyRepo) is the smell of a broken subtype. Honor the contract and those branches disappear.

🔌 Safe extension points

New subtypes can be added without touching the callers. That is the whole promise of the Open-Closed Principle, and LSP is what keeps it true.

🐞 Fewer runtime surprises

Violations surface as production incidents: a save that throws, a queue that silently drops, a null where a value was promised. LSP catches the design error before it ships.

In Plain Terms

Liskov Substitution explained with analogies

Same principle, four ways to picture it, so it clicks whoever you are.

🎓 For a student

A substitute teacher must be able to run the class from the same lesson plan. If the substitute refuses to teach half the syllabus or demands a permission slip the regular teacher never needed, students are worse off. A good substitute is indistinguishable for the plan's purpose.

👩‍💻 For a developer

If a function takes a Repository and calls save(), every repository you pass must actually save. A read-only repository that throws on save compiles fine and blows up at runtime. It fits the interface but breaks the contract.

🏢 For a professional

A vendor who signs your standard contract must meet its terms. If a new supplier accepts fewer order types or ships partial pallets while claiming to fulfill the same agreement, your operations break even though the paperwork matched.

🔑 Everyday version

A duplicate key should open the same lock the original did. A key that fits the keyhole but only turns halfway, or one that jams unless you push a hidden button first, is not a real substitute even though it looks identical.

03 - How

How it works under the hood

LSP shows up the moment you have a base type with a real contract and more than one implementation. The classic trap is modeling with the "is-a" test alone: an archived, read-only order repository "is a" repository in English, so people extend the writable one and override save() to throw. It typechecks. It violates LSP.

🧨 The violation

A ReadOnlyOrderRepository extends a writable base and overrides save() to throw UnsupportedOperation. Callers holding a base reference call save() and crash. The subtype strengthened the precondition to "never call save," which no caller can honor.

🛠️ The fix

Split the contract. A narrow ReadableOrders base only promises reads; a WritableOrders subtype adds save(). The archive is read-only, so it never claims to write, and no caller can ever call a method the object cannot support.

Below is the fix: separate the readable contract from the writable one. Now the archive only implements what it can honor, the live repository implements both, and reconcile asks for exactly the capability it uses. Every subtype is fully substitutable for the interface it declares.

// FIX: split the contract so no subtype has to lie.
interface ReadableOrders {
  findById(id: string): Order | null;
}
interface WritableOrders extends ReadableOrders {
  save(order: Order): void;
}

class LiveOrderRepository implements WritableOrders {
  findById(id: string): Order | null { /* ... */ return null; }
  save(order: Order): void { /* writes to the primary DB */ }
}

class ArchiveOrderRepository implements ReadableOrders {
  findById(id: string): Order | null { /* reads cold storage */ return null; }
  // No save() - it never claims a capability it cannot deliver.
}

// The caller asks only for what it uses, so substitution is always safe:
function reconcile(repo: WritableOrders, order: Order) {
  order.status = "reconciled";
  repo.save(order);
}

const live = new LiveOrderRepository();
reconcile(live, someOrder);         // works for every WritableOrders
// reconcile(new ArchiveOrderRepository(), ...) // won't even compile
# FIX: split the contract so no subtype has to lie.
from abc import ABC, abstractmethod

class ReadableOrders(ABC):
    @abstractmethod
    def find_by_id(self, order_id): ...

class WritableOrders(ReadableOrders):
    @abstractmethod
    def save(self, order): ...

class LiveOrderRepository(WritableOrders):
    def find_by_id(self, order_id):
        ...                           # reads from the primary DB
    def save(self, order):
        ...                           # writes to the primary DB

class ArchiveOrderRepository(ReadableOrders):
    def find_by_id(self, order_id):
        ...                           # reads cold storage
    # No save() - it never claims a capability it cannot deliver.

    repo.save(order)

reconcile(LiveOrderRepository(), some_order)   # works for every WritableOrders
# ArchiveOrderRepository() is not a WritableOrders, so it can't be passed
# FIX: split the contract into role modules so no subtype has to lie.
module ReadableOrders
  def find_by_id(id)
    raise NotImplementedError
  end
end

module WritableOrders
  include ReadableOrders
  def save(order)
    raise NotImplementedError
  end
end

class LiveOrderRepository
  include WritableOrders
  def find_by_id(id); end            # reads from the primary DB
  def save(order); end               # writes to the primary DB
end

class ArchiveOrderRepository
  include ReadableOrders
  def find_by_id(id); end            # reads cold storage
  # No save - it never claims a capability it cannot deliver.
end

# The caller asks only for what it uses, so substitution is always safe:

  order.status = "reconciled"
  repo.save(order)
end

reconcile(LiveOrderRepository.new, some_order) # any WritableOrders works
# ArchiveOrderRepository has no save, so passing it fails fast and loud

The lesson: the "is-a" relationship in English lied to you. An archive "is a kind of" order store, but it is not a writable one. Modeling the capability, not the noun, is what makes every subtype substitutable and keeps callers free of type checks.

05 - Step by Step

The 0 -> 100 flow

From spotting a shaky "is-a" to a set of subtypes that are fully substitutable, in order.

00
Model

Name the base type and its job

Write down what the base type promises. An OrderRepository promises "you can read and save orders." That sentence is the contract.

10
Contract

State pre and postconditions per method

For save(order): precondition is a valid order; postcondition is the order is durably persisted. Make the promise explicit.

20
Invariants

List truths that always hold

An invariant might be "a saved order always has an id." Every subtype must keep it true, before and after every call.

30
Subtype

Propose a candidate subtype

Someone wants an ArchiveOrderRepository for cold storage. Ask: can it honor every method's contract, unchanged?

40
Check

Test preconditions - are they weaker or equal?

The subtype must not demand more of callers. If the archive needs a special flag to read, it strengthened a precondition. Red flag.

50
Check

Test postconditions - are they stronger or equal?

The subtype must deliver at least what was promised. If save() throws instead of persisting, it weakened the postcondition to nothing.

60
Check

Test invariants and history

Confirm the subtype never leaves state the base forbids and never allows mutations the base disallowed. Immutable stays immutable.

70
Detect

Spot the violation

The archive cannot honor save(). Forcing it to throw is the violation. The "is-a" was really "is a read-only kind of."

80
Refactor

Split the contract by capability

Extract ReadableOrders and WritableOrders. The archive implements only what it can honor; the live repo implements both.

90
Depend

Point callers at the narrowest contract

Rewrite reconcile to take WritableOrders. Now the compiler refuses any subtype that cannot save. Substitution is guaranteed.

100
Verify

Run the same tests against every subtype

A shared contract test suite runs against all implementations. If any subtype fails a base-level test, you have found an LSP break before shipping.

Common Pitfalls

Pitfalls & anti-patterns

Most LSP breaks come from inheriting for code reuse when the behavior does not actually match. These are the usual culprits.

🚫 Throwing "not supported"

Overriding a base method to throw UnsupportedOperation is the loudest LSP violation. If a subtype cannot do it, it should not inherit the promise that it can.

🔒 Strengthening preconditions

A subtype that rejects inputs the base accepted, like a region-locked PaymentGateway refusing currencies, breaks callers who relied on the wider contract.

📉 Weakening postconditions

Returning null, a partial list, or skipping a promised side effect leaves callers holding less than the base guaranteed. Silent data loss follows.

🕵️ instanceof in the caller

if (repo instanceof ArchiveRepo) skip() is the caller compensating for a broken subtype. Every type check is a symptom, not a fix.

🧊 Mutable subtype of immutable base

Adding setters to a value type that callers assumed was frozen violates the history constraint and corrupts shared state in ways that are brutal to debug.

🎣 Fat base interface

One giant interface forces every subtype to implement methods it cannot honor. This pushes teams toward stub-and-throw, which is exactly the LSP trap.

Signals & Metrics

Signals & how to measure

You cannot put a single number on LSP, but these signals reliably tell you whether your subtypes are honest.

SignalWhat it tells you
Overrides that throw NotSupportedA direct count of LSP violations - each one is a subtype refusing part of its contract
instanceof / type-check density in callersHow often calling code special-cases concrete subtypes, the fingerprint of a broken abstraction
Shared contract tests passing on all subtypesWhether every implementation satisfies the base test suite - a red subtype is a confirmed violation
Empty or stubbed override bodiesMethods overridden to do nothing signal a subtype that cannot honor the promise but pretends to
Runtime errors on polymorphic call sitesExceptions thrown only for certain concrete types point straight at a substitutability break
Precondition drift in overridesExtra null checks or narrower input validation in a subtype reveals a strengthened precondition
Rule of thumb: if you ever need to know the concrete class to call a method safely, the subtype is not truly substitutable. Write one contract test suite and run it against every implementation; the first subtype that fails is your violation.
06 - Case Studies

Real-world case studies

Three production-style systems where LSP decided whether the design held up.

💳

1 · Payment gateway abstraction over multiple processors

Pattern: honest subtypes behind one charge contract

A checkout system routes charges through several processors behind a single PaymentGateway interface with a charge(amount, currency) contract.

  • One processor supported only domestic currency and threw on everything else, strengthening the precondition and crashing international checkout.
  • The fix declared the supported currencies as capability metadata and routed by it, so every gateway honored the full contract for the traffic it received.
  • A shared contract test ran the same charge, refund, and idempotency cases against every processor adapter.
✅ Outcome: Checkout branched on capability instead of catching processor-specific exceptions, and adding a new processor stopped requiring changes in the caller.
🗄️

2 · Repository layer with a read-only archive

Pattern: split read and write contracts

An orders service kept recent orders in a primary database and older ones in a read-only archive, both behind one repository interface.

  • The archive repository inherited save() and threw, so background reconciliation jobs failed whenever they touched an archived order.
  • Splitting into ReadableOrders and WritableOrders let the archive implement only reads, and the compiler blocked any write path from reaching it.
  • Callers were rewritten to depend on the narrowest interface they actually used.
✅ Outcome: The class of "cannot save archived order" runtime errors disappeared entirely, and write jobs became provably safe at compile time.
📨

3 · Notification senders behind one delivery interface

Pattern: uniform postconditions across channels

A platform sent email, SMS, and push through a shared NotificationSender with a send(message) contract that promised a delivery receipt.

  • The push sender returned early without a receipt when a device token was missing, weakening the postcondition and leaving audit logs incomplete.
  • The contract was tightened so every sender returned an explicit delivered or failed result, never a silent no-op.
  • A shared suite asserted the postcondition, that a receipt is always returned, for all three channels.
✅ Outcome: Downstream retry and audit logic worked identically for every channel, because each sender delivered exactly the guarantee the base type promised.
07 - Relevance

Modern relevance

LSP predates today's languages, but its core idea, behavioral substitutability, is more relevant than ever as systems lean on interfaces and plugins.

🧩 Interface segregation partners

Splitting fat interfaces into role-based ones is often the cleanest way to satisfy LSP. The two SOLID principles reinforce each other directly.

🔗 Plugin and adapter ecosystems

Every plugin API is an LSP contract. A plugin that half-implements the interface breaks the host, so honest subtyping is a platform survival trait.

🦆 Structural and duck typing

In TypeScript structural types and Python protocols, the compiler checks shape but not behavior. LSP is the discipline that fills that gap by hand.

🧪 Contract and property-based tests

Running one shared suite against every implementation, or generating inputs to probe postconditions, turns LSP from a principle into an automated gate.

🏗️ Composition over inheritance

Modern designs favor composing behavior, which sidesteps many LSP traps by never claiming an "is-a" the subtype cannot back up.

🤖 Typed API and RPC schemas

Versioned service contracts are LSP at the network boundary: a new server version must remain substitutable for clients built against the old one.

Bottom line: LSP is the rule that keeps polymorphism trustworthy. Design subtypes around the behavior they can truly honor, not the noun that sounds right, and your abstractions stay clean, your callers stay free of type checks, and your extensions stay safe.
