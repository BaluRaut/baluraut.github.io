Composition over inheritance - build behavior by assembling, not extending

Inheritance couples a subclass to every detail of its parent, so a change high in the tree ripples down and breaks classes nobody remembers. Composition flips this: instead of being a base class, an object has collaborators it delegates to. You wire behavior together at runtime, swap pieces freely, and keep each part small and testable.

01 - What

What is composition over inheritance?

Composition over inheritance is a design guideline that says: prefer to build a type out of smaller objects it holds and delegates to (a has-a relationship) rather than out of a base class it extends (an is-a relationship). Both reuse code, but inheritance reuses by inheriting a whole implementation, while composition reuses by wiring independent pieces together. The guideline exists because deep inheritance trees turn out to be rigid, while assembled objects stay flexible.

🧬 Inheritance (is-a)

A subclass extends a base class and inherits its fields and methods. Strong, static coupling: the child depends on the parent's internals and is fixed at compile time.

🧩 Composition (has-a)

An object holds references to collaborator objects and forwards work to them. Loose coupling through interfaces: pieces can be swapped, even at runtime.

🔀 Delegation

The mechanism that makes composition work: a method calls the same method on a held collaborator, so the outer object exposes behavior it did not implement itself.

The core vocabulary

TermWhat it meansRelationship
is-aA subtype that can stand in for its base typeInheritance / subtyping
has-aAn object that owns and uses another objectComposition / aggregation
DelegationForwarding a call to a held collaboratorRuntime behavior sharing
Mixin / traitA reusable slice of behavior mixed into a classHorizontal reuse
InterfaceA contract a collaborator promises to satisfyDecoupling seam
Key mental model: ask "is X truly a kind of Y, forever?" If yes, inheritance may fit. If X merely uses or can do Y, or the answer changes over time, model it as has-a and delegate. Inheritance is for identity, composition is for capability.
02 - Why

Why prefer composition

Inheritance is the tightest coupling in object-oriented programming: a subclass sees protected members, depends on call order, and inherits everything whether it wants it or not. That is exactly what makes deep hierarchies fragile. Composition trades that rigidity for flexibility.

🧱 Escapes the fragile base class

When behavior lives in collaborators behind interfaces, editing one does not silently break subclasses. A change is contained to the piece that owns it instead of rippling down a tree.

🔧 Flexible at runtime

You can swap a collaborator, or stack several, while the program runs. Inheritance is fixed the moment you compile; composition lets configuration and dependency injection decide behavior.

🚫 Sidesteps the diamond problem

Single inheritance forces awkward hierarchies and multiple inheritance creates ambiguous method resolution. Holding several collaborators gives you many behaviors with zero ambiguity.

🧪 Easier to test

Each collaborator is small and mockable through its interface. You test a unit in isolation instead of dragging in a five-level base class with hidden state and setup.

In Plain Terms

Composition over inheritance explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Inheritance is copying a whole essay and tweaking a few lines - if the original had a mistake, so does yours. Composition is citing sources: you pull in exactly the paragraphs you need and swap a source without rewriting the paper.

👩‍💻 For a developer

Inheritance is extends BaseController and hoping the base does what you expect. Composition is injecting a Logger, a Validator, and a Repository - each an interface you can mock, replace, or reorder without touching the rest.

🏢 For a professional

Inheritance is a rigid org chart where everyone reports up a fixed chain. Composition is a project team assembled from specialists: you bring in the right people for the job and disband when done.

🔌 Everyday version

A phone with a soldered-in battery is inheritance: cheap until something needs to change, then you replace the whole device. A phone with plug-in accessories is composition: click in a new charger, case, or lens whenever you like.

03 - How

How it works under the hood

The move is mechanical: take the behavior that used to live in a base class, put it behind an interface, implement it in small classes, and have the outer object hold and delegate to one of them instead of extending a parent.

🧬 The inheritance design

A Bird base class defines fly(). Then a penguin arrives that cannot fly, an ostrich that runs, a bird that swims. The hierarchy fractures into special cases and overrides that throw exceptions.

🧩 The composition design

Define FlyBehavior, SwimBehavior interfaces. A bird has a fly strategy and a swim strategy. A penguin gets NoFly and StrongSwim - no exceptions, no broken contracts.

The same problem, two designs in TypeScript

// INHERITANCE: rigid, and Penguin is forced to lie about fly()
abstract class Bird {
  eat(): string { return "peck peck"; }
  fly(): string { return "flap and take off"; }
}
class Duck extends Bird {}
class Penguin extends Bird {
  // A penguin is-a Bird, but cannot fly -> the contract breaks
  override fly(): string { throw new Error("penguins can't fly"); }
}

// COMPOSITION: behavior is injected, so no class ever lies
interface FlyBehavior { fly(): string; }
class WingFly  implements FlyBehavior { fly() { return "flap and take off"; } }
class NoFly    implements FlyBehavior { fly() { return "stays grounded"; } }

class Animal {
  // has-a, not is-a: the fly behavior is a collaborator
  constructor(private readonly flyer: FlyBehavior) {}
  move(): string { return this.flyer.fly(); }   // delegation
  setFlyer(f: FlyBehavior) { /* swap at runtime */ }
}

const duck    = new Animal(new WingFly());   // "flap and take off"
const penguin = new Animal(new NoFly());     // "stays grounded" - honest, no throw

Notice that the composed Animal never overrides anything and never throws. Behavior is supplied through the constructor and can be swapped with setFlyer - the exact flexibility a fixed extends relationship cannot offer.

05 - Step by Step

The 0 → 100 flow

From a fragile inheritance tree to a clean composed design - the refactor in order.

00
Spot

Notice the smell

A base class keeps growing, subclasses override methods to throw or no-op, and a small parent change breaks distant children. That is fragile-base-class pain asking for composition.

10
Question

Test the is-a claim

Ask whether the subclass truly is a kind of its parent in every context, permanently. If it only uses or can do some of the behavior, it is a has-a in disguise.

20
Isolate

Find the varying behavior

Identify the parts that differ across subclasses - the fly, the pay, the render. Those variations are the pieces to pull out of the hierarchy.

30
Interface

Define a contract

Create an interface for each varying behavior, for example FlyBehavior. This becomes the decoupling seam the outer object depends on.

40
Implement

Write small strategies

Provide concrete classes per variation: WingFly, NoFly, JetFly. Each is tiny, single-purpose, and independently testable.

50
Hold

Add a field, not a parent

Give the outer class a field of the interface type instead of extending a base. The object now has-a behavior rather than is-a subclass.

60
Delegate

Forward the call

In the outer method, call the collaborator: move() simply invokes flyer.fly(). The class exposes behavior it does not implement itself.

70
Inject

Wire it from outside

Pass collaborators through the constructor or a DI container. Now configuration, not a class name, decides behavior.

80
Swap

Change behavior at runtime

Expose a setter so a running object can trade one strategy for another. This is the flexibility inheritance can never give you.

90
Combine

Layer with mixins or decorators

Stack multiple capabilities by holding several collaborators or wrapping with decorators, gaining rich behavior without a combinatorial class explosion.

100
Judge

Keep inheritance where it fits

Retain inheritance for genuine, stable is-a subtyping and template methods. The goal is the right tool, not zero inheritance.

Common Pitfalls

Pitfalls & anti-patterns

Both inheritance and composition can be misused. These are the traps that show up most in real code.

🕳️ Deep inheritance hierarchies

Five or six levels of extends mean a single method call runs code scattered across the tree. Nobody can reason about it, and any base edit is a landmine. Flatten it with composition.

🧱 Fragile base class

Changing a base method or its call order silently breaks subclasses that relied on the old behavior. The parent cannot evolve safely because it is coupled to every child.

💎 Reaching for the diamond

Multiple inheritance where two paths reach the same ancestor creates ambiguous method and state resolution. Languages ban or complicate it for good reason - compose instead.

🎭 Inheritance for code reuse only

Extending a class just to grab a helper method forces an is-a claim you do not mean. You inherit its whole surface and coupling. Prefer holding it as a collaborator.

🧨 Liskov violations

Overriding a method to throw or weaken the contract, like Penguin.fly() throwing, breaks substitutability. Callers of the base type get surprises. That is a sign the is-a was wrong.

🍝 Delegation boilerplate

Composition can drift the other way: dozens of one-line pass-through methods just to forward calls. Use language delegation features, interfaces, or a decorator base to keep it lean.

Trade-offs

Trade-offs & when to use

Composition is a default, not a law. Weigh these before you refactor a hierarchy or reach for a base class.

AspectDetail
ProsLoose coupling, runtime flexibility, small testable units, no fragile base class, sidesteps the diamond problem, honors the open-closed principle.
ConsMore classes and interfaces up front, delegation boilerplate, indirection can obscure a simple flow, wiring moves to constructors or a DI container.
Use whenBehavior varies across cases, needs to change at runtime, would create a deep or fragile tree, or the relationship is really has-a or can-do.
Avoid whenThe subtype is a genuine, stable is-a, you need real polymorphic substitutability, or a template-method framework expects you to extend a base class.
ComplexityLow conceptually, moderate in wiring. Trades a few extra types for far easier change later - usually a good bargain past trivial cases.
RelatedStrategy, Decorator, Bridge, and Adapter are all composition in action; SOLID's dependency-inversion and open-closed principles motivate it.
Rule of thumb: reach for inheritance only when the subtype is a true, permanent is-a that you would substitute for its base without surprise. For everything that merely reuses or varies behavior, compose and delegate. Favor composition by default, allow inheritance by justification.
06 - Case Studies

Real-world case studies

Three places where choosing composition over inheritance changed the outcome.

🎮

1 · Game entities via component systems

Pattern: entity-component composition

Early game engines used deep class trees like Enemy extends Character extends GameObject, then broke when a crate needed physics but not AI.

  • Behavior split into components: Position, Render, Physics, AI, each held by an entity.
  • A new entity type is a new bag of components, not a new subclass in a rigid tree.
  • Designers mix capabilities at runtime without a programmer editing the hierarchy.
✅ Outcome: Entity-component-system architecture became the industry norm because composition scaled where inheritance combinatorially exploded.
☕

2 · Java I/O streams

Pattern: Decorator, composition by wrapping

Java needed buffering, compression, and encryption over any stream without a class per combination.

  • BufferedInputStream wraps another InputStream and delegates to it.
  • You stack wrappers: buffer around gzip around a file stream, composed at runtime.
  • Adding a capability is a new decorator, not a subclass of every stream type.
✅ Outcome: A handful of composable decorators cover every combination, avoiding a huge inheritance matrix of stream subclasses.
🛒

3 · Payment and pricing strategies

Pattern: Strategy, injected behavior

A checkout service started with CreditCardOrder extends Order and gained a subclass per payment and discount rule until the tree was unmanageable.

  • PaymentMethod and DiscountPolicy became interfaces the order holds.
  • An order is configured with a payment strategy and a discount strategy at creation.
  • New promotions and providers are new strategy classes, injected without touching Order.
✅ Outcome: The order class stopped changing, tests mocked each strategy in isolation, and new payment options shipped without regression risk.
07 - Relevance

Modern relevance

Far from dated, composition over inheritance underpins how modern languages, frameworks, and paradigms are designed.

🧵 Traits and mixins mainstream

Rust traits, Scala traits, and TypeScript mixins let you compose horizontal behavior without a base class, making composition the ergonomic default.

🚫 Go and Rust drop inheritance

Go has struct embedding and interfaces, Rust has traits, and neither offers class inheritance at all - a deliberate bet on composition.

⚛️ React chose composition

React explicitly recommends composition over inheritance for reuse, using hooks and child components instead of extending base components.

💉 Dependency injection everywhere

Spring, Angular, and NestJS wire collaborators through constructors, making has-a design the default way frameworks assemble apps.

🧩 Patterns are composition

Strategy, Decorator, Bridge, and Adapter, the workhorses of the Gang of Four, are all composition dressed for a specific job.

🔬 Testability demands it

Modern testing culture rewards small, mockable units behind interfaces, which is exactly what composition produces and inheritance resists.

Bottom line: inheritance still earns its place for true, stable is-a subtyping and template methods, but composition is the default that keeps systems flexible, testable, and safe to change. Reach for has-a first, and let inheritance prove it belongs.
