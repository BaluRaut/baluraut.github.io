OOP Concept

Composition over inheritance - build behavior from collaborators

Inheritance says an object is-a kind of its parent and copies the parent's guts into every subclass. Composition says an object has-a set of collaborators it delegates to. Favoring composition keeps behavior swappable at runtime, keeps base classes from becoming brittle, and lets you assemble features like an HTTP client from retry, auth, and logging parts instead of a deep class tree.

01 - What

What is composition over inheritance?

Composition over inheritance is a design guideline: prefer assembling an object from smaller collaborators it holds and delegates to, rather than deriving it from a base class to reuse code. Instead of a RetryingAuthenticatedHttpClient that extends a chain of base classes, you build one HttpClient that has a retry policy, has an auth provider, and has a logger, each an independent object you can swap.

🧩 Has-a (composition)

An object holds references to collaborators and forwards work to them. Behavior is the sum of parts you can replace one at a time.

🌳 Is-a (inheritance)

A subclass extends a base and inherits its fields and methods. Reuse is real but rigid: it is fixed at compile time and cuts across the whole hierarchy.

🔁 Delegation

The mechanism that makes composition work: a method on the host calls the same or a related method on a held collaborator, passing the result back out.

Key mental model: inheritance couples you to how a parent is built; composition couples you only to what a collaborator promises. Program to the interface a collaborator exposes and you can reshape behavior by swapping parts, not by rewriting a class tree.
02 - Why

Why favor composition

Inheritance is the tightest coupling in object orientation: a subclass depends on the base's public API, its protected members, and often its private call order. Composition trades that hidden coupling for explicit, swappable collaborators.

🔧 Swappable at runtime

Give an HttpClient a NoRetry policy in tests and an ExponentialBackoff policy in production without touching the client. Inheritance would force a new subclass per combination.

🧱 No combinatorial explosion

Retry, auth, and logging as three collaborators compose into any mix. As subclasses they multiply: authenticated-retrying, logged-retrying, logged-authenticated, and so on.

🛡️ Avoids the fragile base class

Collaborators only see each other's public contract, so an internal refactor of one cannot silently break another the way a base class change breaks its subclasses.

🧪 Easy to test in isolation

Pass a fake auth provider or a recording logger straight into the constructor. No subclassing the unit under test, no overriding protected hooks just to observe it.

In Plain Terms

Composition over inheritance explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Inheritance is inheriting a family recipe you cannot change without affecting every cousin who also inherited it. Composition is keeping separate spice jars: you pick which ones go in this dish and can swap salt for pepper any time.

👩‍💻 For a developer

An HttpClient that extends a retry base is welded to it. An HttpClient that takes a RetryPolicy in its constructor is wired, not welded: you rewire it per environment.

🏢 For a professional

Inheritance is a rigid org chart where every team must do what the parent department dictates. Composition is hiring specialist contractors: the project holds a security firm, an auditor, and a courier, and can replace any one without reorganizing the company.

🔌 Everyday version

A power strip does not inherit from a lamp. It plugs devices in. Composition is the socket: whatever you plug in provides the behavior, and unplugging one thing never breaks the others.

03 - How

How it works under the hood

The core move is to name each cross-cutting concern as its own small interface, then hold instances of those interfaces inside the host and delegate to them. The host orchestrates; the collaborators do the specialized work.

📇 Define collaborator contracts

Each concern gets a narrow interface: RetryPolicy.run(op), AuthProvider.authorize(req), RequestLogger.log(req, res). The host depends on these, not on concrete classes.

🔗 Inject and delegate

The host receives collaborators through its constructor and calls them in send(). Swapping behavior means passing a different implementation, never editing the host.

// Collaborator contracts
interface AuthProvider { authorize(req: Request): Request; }
interface RetryPolicy { run<T>(op: () => Promise<T>): Promise<T>; }
interface RequestLogger { log(req: Request, res: Response): void; }

class BearerTokenAuth implements AuthProvider {
  constructor(private token: string) {}
  authorize(req: Request): Request {
    req.headers.set("Authorization", `Bearer ${this.token}`);
    return req;
  }
}

class ExponentialBackoff implements RetryPolicy {
  constructor(private tries = 3, private baseMs = 100) {}
  async run<T>(op: () => Promise<T>): Promise<T> {
    for (let attempt = 1; ; attempt++) {
      try { return await op(); }
      catch (err) {
        if (attempt >= this.tries) throw err;
        await new Promise(r => setTimeout(r, this.baseMs * 2 ** attempt));
      }
    }
  }
}

class ConsoleLogger implements RequestLogger {
  log(req: Request, res: Response): void {
    console.log(`${req.method} ${req.url} -> ${res.status}`);
  }
}

// The host HAS-A each collaborator and delegates to it.
class HttpClient {
  constructor(
    private auth: AuthProvider,
    private retry: RetryPolicy,
    private logger: RequestLogger,
  ) {}

  async send(req: Request): Promise<Response> {
    const authed = this.auth.authorize(req);              // delegate auth
    const res = await this.retry.run(() => fetch(authed)); // delegate retry
    this.logger.log(authed, res);                         // delegate logging
    return res;
  }
}

// Assemble by wiring parts; swap any part without a new subclass.
const client = new HttpClient(
  new BearerTokenAuth(process.env.API_TOKEN!),
  new ExponentialBackoff(4, 200),
  new ConsoleLogger(),
);
const res = await client.send(new Request("https://api.example.com/v1/orders"));

from __future__ import annotations
from typing import Protocol, Callable, TypeVar
import os, time

T = TypeVar("T")

# Collaborator contracts
class AuthProvider(Protocol):
    def authorize(self, req: Request) -> Request: ...

class RetryPolicy(Protocol):
    def run(self, op: Callable[[], T]) -> T: ...

class RequestLogger(Protocol):
    def log(self, req: Request, res: Response) -> None: ...

class BearerTokenAuth:
    def __init__(self, token: str) -> None:
        self._token = token
    def authorize(self, req: Request) -> Request:
        req.headers["Authorization"] = f"Bearer {self._token}"
        return req

class ExponentialBackoff:
    def __init__(self, tries: int = 3, base_ms: int = 100) -> None:
        self._tries, self._base_ms = tries, base_ms
    def run(self, op: Callable[[], T]) -> T:
        attempt = 1
        while True:
            try:
                return op()
            except Exception:
                if attempt >= self._tries:
                    raise
                time.sleep(self._base_ms * 2 ** attempt / 1000)
                attempt += 1

class ConsoleLogger:
    def log(self, req: Request, res: Response) -> None:
        print(f"{req.method} {req.url} -> {res.status}")

# The host HAS-A each collaborator and delegates to it.
class HttpClient:
    def __init__(self, auth: AuthProvider, retry: RetryPolicy, logger: RequestLogger) -> None:
        self._auth, self._retry, self._logger = auth, retry, logger

    def send(self, req: Request) -> Response:
        authed = self._auth.authorize(req)                 # delegate auth
        res = self._retry.run(lambda: do_fetch(authed))    # delegate retry
        self._logger.log(authed, res)                      # delegate logging
        return res

# Assemble by wiring parts; swap any part without a new subclass.
client = HttpClient(
    BearerTokenAuth(os.environ["API_TOKEN"]),
    ExponentialBackoff(tries=4, base_ms=200),
    ConsoleLogger(),
)
res = client.send(Request("GET", "https://api.example.com/v1/orders"))

# Contrast: inheritance would force AuthedRetryingClient(RetryingClient(BaseClient))

# Collaborator contracts are duck-typed: any object answering the
# right message plays the role. No base class needed.

class BearerTokenAuth
  def initialize(token) = @token = token
  def authorize(req)
    req.headers["Authorization"] = "Bearer #{@token}"
    req
  end
end

class ExponentialBackoff
  def initialize(tries: 3, base_ms: 100)
    @tries, @base_ms = tries, base_ms
  end

  def run
    attempt = 1
    begin
      yield
    rescue => e
      raise e if attempt >= @tries
      sleep(@base_ms * 2**attempt / 1000.0)
      attempt += 1
      retry
    end
  end
end

class ConsoleLogger
  def log(req, res) = puts("#{req.method} #{req.url} -> #{res.status}")
end

# The host HAS-A each collaborator and delegates to it.
class HttpClient
  def initialize(auth:, retry:, logger:)
    @auth, @retry, @logger = auth, retry, logger
  end

  def send(req)
    authed = @auth.authorize(req)            # delegate auth
    res = @retry.run { do_fetch(authed) }    # delegate retry
    @logger.log(authed, res)                 # delegate logging
    res
  end
end

# Assemble by wiring parts; swap any part without a new subclass.
client = HttpClient.new(
  auth:   BearerTokenAuth.new(ENV.fetch("API_TOKEN")),
  retry:  ExponentialBackoff.new(tries: 4, base_ms: 200),
  logger: ConsoleLogger.new,
)
res = client.send(Request.new(:get, "https://api.example.com/v1/orders"))

# Ruby also offers mixins for shared behavior without an is-a tree:
# module Instrumented; def timed(&blk) = ...; end
# class HttpClient; include Instrumented; end

The host send() never knows which retry or auth strategy it holds; it only knows the message to send. That is delegation: behavior is chosen by wiring, so the same class covers test, staging, and production by swapping constructor arguments rather than growing a subclass for each combination.

05 - Step by Step

The 0 → 100 flow

From a tangled class tree to a cleanly composed client, the whole refactor in order.

00
Smell

Spot the growing hierarchy

You notice classes like AuthedRetryingLoggingClient extending three levels deep, with each new mix demanding another subclass.

10
Name concerns

Separate the cross-cutting jobs

List what the tree conflates: authentication, retry, and logging are three independent responsibilities, not one lineage.

20
Define contracts

Write a narrow interface per concern

AuthProvider.authorize, RetryPolicy.run, RequestLogger.log. Each promises one small behavior.

30
Extract

Move behavior into collaborators

Pull the auth logic out of the base and into BearerTokenAuth; do the same for retry and logging. Each becomes a standalone class.

40
Hold

Give the host has-a fields

HttpClient now stores an auth, a retry, and a logger field typed to the interfaces, not concretes.

50
Inject

Accept collaborators in the constructor

The host takes its parts as arguments, so the caller decides which implementations to wire in.

60
Delegate

Forward work in send()

send() calls auth.authorize, then retry.run, then logger.log. The host orchestrates; parts do the work.

70
Delete

Collapse the subclass tree

The special-case subclasses vanish. One HttpClient now covers every combination via wiring.

80
Swap

Reconfigure per environment

Wire NoRetry and a NullLogger in tests, ExponentialBackoff and a structured logger in production. Same class throughout.

90
Test

Inject fakes and assert

Pass a recording logger and a stub auth to verify the client without subclassing or touching the network.

100
Judge

Keep inheritance where it earns it

For genuine is-a subtypes with a stable, thin base and true substitutability, inheritance still fits. Reach for it deliberately, not by default.

Common Pitfalls

Pitfalls & anti-patterns

Composition is not free; done carelessly it swaps one mess for another. Watch for these.

🏗️ Inheritance for reuse only

Subclassing just to borrow a few methods, with no real is-a relationship, is the classic misuse. If the child is not substitutable for the parent, it should hold the behavior, not inherit it.

🧨 The fragile base class

A base that calls its own overridable methods internally lets a private refactor break every subclass silently. The more subclasses reach into protected internals, the worse it gets.

🪆 Deep hierarchies

Four or five levels of extends make behavior impossible to trace: you must read the whole chain to know what one call does. Flatten into collaborators.

🕸️ God object via composition

Composition can hide a monolith too: a host holding fifteen collaborators and coordinating them all is just a big ball of mud with extra indirection. Keep hosts focused.

🔁 Boilerplate delegation

Forwarding twenty methods by hand to a held object is tedious and error prone. Use language delegation features (Ruby Forwardable, Kotlin by) or a thin facade instead.

🧬 Mixin collisions

Two mixins that both define save or both touch the same state create surprising method resolution order bugs. Keep mixins small, orthogonal, and namespaced.

Signals & Metrics

Signals & how to measure

You cannot unit-test a design guideline, but these signals tell you whether a hierarchy has gone wrong and composition would help.

SignalWhat it tells you
Inheritance depth (DIT)Deep trees are hard to reason about; a jump past three or four levels often signals reuse-by-inheritance that composition would flatten.
Subclass count for combinationsIf N features produce roughly 2^N subclasses, you are paying the combinatorial tax that composition removes.
Overrides that call super in a fixed orderSubclasses depending on the base's internal call sequence are fragile-base-class risk waiting to fire.
Protected member surfaceA wide protected API means subclasses reach into internals; the base cannot evolve safely. Narrow it and prefer composition.
Test setup complexityIf testing a class requires subclassing it or overriding protected hooks, its behavior is not injectable and composition would simplify it.
Change ripple across the treeOne base edit forcing edits in many subclasses shows tight structural coupling that swappable collaborators avoid.
Rule of thumb: if a proposed subclass would fail the Liskov test (it cannot be used everywhere the base is expected), or exists only to reuse code, model it as a has-a collaborator instead. Keep inheritance for true, thin, stable is-a subtypes.
06 - Case Studies

Real-world case studies

Three production-style systems where composition beat a class hierarchy.

🔌

1 · An HTTP API client SDK

Pattern: assemble the client from retry, auth, and logging collaborators

A payments SDK started with BaseClient subclassed for every combination of auth scheme and retry behavior, and the tree became unmaintainable.

  • Auth, retry, and instrumentation were extracted into injectable interfaces the client holds.
  • Sandbox and live modes became two wirings of one HttpClient, not two subclasses.
  • New auth schemes shipped as new AuthProvider implementations with zero client changes.
✅ Outcome: The subclass tree collapsed to a single client class, and adding features became wiring rather than inheritance surgery.
📊

2 · A reporting and export engine

Pattern: a Report has-a datasource and a formatter

An analytics platform first modeled reports as PdfSalesReport extending SalesReport extending Report, exploding as formats and sources multiplied.

  • A Report now holds a DataSource and an OutputFormatter, delegating fetch and render to them.
  • CSV, PDF, and XLSX became three formatters; warehouse and API became two datasources.
  • Any source pairs with any format at runtime, no new class per pairing.
✅ Outcome: Format-times-source combinations became a small set of parts, and a new export format was one class instead of a new branch of the tree.
🔔

3 · A notification service

Pattern: mixins and channel collaborators over a channel hierarchy

A messaging system had an EmailNotification extending Notification tree, with retry and templating duplicated or awkwardly pushed into the base.

  • Channels (email, SMS, push) became interchangeable Channel collaborators the sender holds.
  • Cross-cutting concerns like timestamping and rate limiting became small mixins, not base methods.
  • A digest sender simply held several channels and fanned out, no new subclass required.
✅ Outcome: Adding a Slack channel was one new Channel class, and shared behavior lived in focused mixins instead of a swelling base.
07 - Relevance

Modern relevance

Composition over inheritance is older than most frameworks, yet modern language and platform design keeps pushing it further into the mainstream.

🧵 Traits and protocols

Rust traits, Swift protocol extensions, and Go's interface embedding give composition-style reuse without a class hierarchy at all, making has-a the default.

💉 Dependency injection everywhere

DI containers in Spring, NestJS, and .NET exist precisely to wire collaborators into hosts, industrializing the composition pattern across whole codebases.

🎛️ Delegation as a keyword

Kotlin's by and Ruby's Forwardable make delegation first class, removing the boilerplate that once made composition feel heavier than inheritance.

⚛️ Composition in UI frameworks

React and modern component systems replaced inheritance-based UI with composed components and hooks, a large-scale endorsement of has-a over is-a.

🧩 Entity-component systems

Game and simulation engines build entities from attached components rather than deep class trees, the purest form of composition at runtime.

🌳 Inheritance, kept deliberate

Sealed classes and interfaces keep a place for true is-a modeling, so the future is not zero inheritance but inheritance used on purpose.

Bottom line: favor composition to keep behavior swappable, testable, and safe from fragile-base-class breakage, and reserve inheritance for genuine, thin, substitutable is-a relationships. Assemble objects from collaborators first; extend a base only when the subtype relationship is real.
