OOP Foundation

SOLID principles - design classes that survive change

SOLID is five design principles that keep object-oriented code flexible and easy to change. Each one attacks a specific way that classes grow rigid, fragile, or tangled. Together they push you toward small responsibilities, stable abstractions, and dependencies that point at interfaces instead of concrete details.

01 - What

What is SOLID?

SOLID is an acronym for five object-oriented design principles popularized by Robert C. Martin. They are not rules for correctness; they are heuristics for changeability. Code that follows them tends to have small, focused classes that you can extend without editing, and modules that depend on abstractions rather than on each other's internals.

🧩 One reason to change

SRP and ISP split fat classes and interfaces into cohesive pieces, so a change in one concern does not ripple into unrelated code.

🔌 Extend, do not edit

OCP asks you to add behavior by plugging in new types, not by rewriting tested code with more if/else branches.

🔗 Depend on abstractions

LSP and DIP make subtypes honor their contracts and route dependencies through interfaces, so pieces swap freely.

The five principles at a glance

PrincipleWhat it saysThe smell it kills
S - Single ResponsibilityA class should have one reason to change, one owner of its behaviorGod classes that mix persistence, formatting, and business rules
O - Open/ClosedOpen for extension, closed for modificationGrowing switch statements you edit for every new case
L - Liskov SubstitutionSubtypes must be usable anywhere their base type is expectedSubclasses that throw, weaken, or break inherited contracts
I - Interface SegregationPrefer many small interfaces over one fat oneClients forced to implement methods they never call
D - Dependency InversionDepend on abstractions, not concretionsHigh-level policy welded to low-level libraries
Key mental model: SOLID is about the direction and shape of dependencies. Make responsibilities small, make contracts trustworthy, and make the arrows point at stable abstractions. Do that and change stays local instead of spreading through the codebase.
02 - Why

Why SOLID exists

Software does not fail because it was written wrong once; it decays because every change is harder than the last. SOLID targets that decay directly, so a codebase stays cheap to modify as it grows.

🛡️ Change stays local

When each class owns one concern, a new requirement touches one place. Ripple edits across unrelated files, the classic sign of rot, mostly disappear.

🧪 Testable by design

Depending on abstractions lets you inject fakes and mocks. Units test in isolation instead of dragging a database or network into every test.

🔧 Safe extension

Adding a payment method or export format becomes a new class you plug in, not a risky edit to code that already works in production.

🤝 Parallel teamwork

Small interfaces and clear contracts mean teams build against a stable boundary, integrating without stepping on each other's implementations.

In Plain Terms

SOLID explained with analogies

Same five ideas, four ways to picture them, so they click whoever you are.

🎓 For a student

SOLID is like a well-organized ring binder. Each subject has its own tab (single responsibility), you add new pages without rewriting old ones (open/closed), and any tab you pull out still fits the same rings (substitution).

👩‍💻 For a developer

Think of a USB port. The laptop depends on the USB contract, not on a specific device (dependency inversion). Any compliant device works (Liskov), and the port exposes only what a device needs (interface segregation).

🏢 For a professional

It is a company org chart. Each role has one clear remit (SRP), you onboard new specialists instead of overloading one person (OCP), and managers depend on job descriptions, not on specific individuals (DIP).

🔌 Everyday version

Household wall sockets. Every appliance that fits the socket just works, the kettle can replace the toaster with no rewiring, and you never call an electrician to add one more lamp.

03 - How

How the five principles work together

Each principle handles one axis of change, but they reinforce each other. SRP and ISP decide where the seams go; OCP and DIP decide how you cross them; LSP guarantees the pieces on either side are actually interchangeable.

🧭 Seams: SRP and ISP

Split a class by reason-to-change (SRP) and split its interface by the client that uses it (ISP). You end up with small, cohesive units and narrow contracts that no one implements by force.

🚪 Doors: OCP and DIP

DIP puts an abstraction at the seam so high-level policy never names a concrete detail. OCP then lets you add new implementations behind that abstraction without editing the policy. LSP keeps every implementation honest.

A dependency-inversion refactor in TypeScript

// BEFORE - high-level policy welded to a concrete detail (violates DIP + OCP)
class StripeGateway {
  charge(amount: number) { /* call Stripe */ }
}

class OrderService {
  private gateway = new StripeGateway();   // hard dependency
  checkout(total: number) {
    this.gateway.charge(total);            // to add PayPal, you must edit this class
  }
}

// AFTER - depend on an abstraction; add providers without touching OrderService
interface PaymentGateway {
  charge(amount: number): Receipt;
}

class StripeGateway implements PaymentGateway {
  charge(amount: number): Receipt { /* call Stripe */ return new Receipt(); }
}

class PaypalGateway implements PaymentGateway {   // new type, zero edits to policy (OCP)
  charge(amount: number): Receipt { /* call PayPal */ return new Receipt(); }
}

class OrderService {
  constructor(private readonly gateway: PaymentGateway) {}  // injected abstraction (DIP)
  checkout(total: number): Receipt {
    return this.gateway.charge(total);   // works with any conforming gateway (LSP)
  }
}

// wiring happens at the edge, not inside the policy
const service = new OrderService(new PaypalGateway());

The high-level OrderService now names only the PaymentGateway abstraction. Adding a provider is a new class (open for extension), the service never changes (closed for modification), and any gateway substitutes cleanly because they all honor the same contract.

05 - Step by Step

The 0 → 100 flow

From a tangled god class to a SOLID design you can extend safely, the whole refactor in order.

00
Spot

Find the reasons to change

Look at a class and list why it might change - new report format, new payment provider, new storage. Multiple reasons means multiple responsibilities hiding inside.

10
SRP

Split by responsibility

Extract each concern into its own class. Persistence, formatting, and business rules become separate collaborators with one owner each.

20
ISP

Narrow the interfaces

Break fat interfaces so each client depends only on the methods it actually calls. No class is forced to stub out methods it will never use.

30
Abstract

Name the abstraction at the seam

Where high-level code meets a low-level detail, define an interface that captures only what the policy needs, phrased in the policy's language.

40
DIP

Invert the dependency

Make the high-level class depend on that interface and receive the implementation by injection, so it never news up a concrete detail itself.

50
Implement

Write the concrete providers

Each low-level detail implements the abstraction. The Stripe gateway, the file store, the CSV formatter all live behind their contract.

60
LSP

Honor the contract

Ensure every implementation keeps the base type's promises - same preconditions or weaker, same postconditions or stronger, no surprise exceptions.

70
OCP

Extend without editing

Add the next provider or format as a brand new class implementing the abstraction. Tested policy code stays closed to modification.

80
Wire

Compose at the edge

Choose concrete types in one composition root - a main method or DI container - so all the concrete decisions sit at the outer boundary.

90
Test

Inject fakes and verify

Unit test the policy against a mock implementation. Because dependencies are abstractions, tests run fast with no database or network.

100
Evolve

Change stays local

New requirements land as new small classes. The core policy is stable, the design flexes at its seams, and each principle reinforces the others.

Common Pitfalls

Pitfalls & anti-patterns

SOLID misapplied is as damaging as no design at all. These are the usual traps.

🌫️ Abstraction for its own sake

Wrapping every class in an interface it will only ever have one implementation of adds indirection with no payoff. Introduce a seam when a second implementation is real or clearly coming.

🪓 SRP taken to shards

Splitting until every method is its own class scatters cohesive logic across dozens of files. One reason to change means one concern, not one line.

🧬 Inheritance where composition fits

Forcing an is-a hierarchy to reuse code breeds Liskov violations. Favor composition and small interfaces when behavior, not identity, is what varies.

🕳️ Leaky abstractions

An interface that exposes SQL fragments or HTTP details drags the concrete implementation back into the policy, quietly undoing dependency inversion.

🐦 Contract-breaking subtypes

Overriding a method to throw, to tighten a precondition, or to return null violates LSP. The subtype must be usable anywhere the base type is.

📚 Fat interfaces by default

One giant service interface forces every client and mock to depend on methods they never touch. Segregate by the consumer, not by the implementer.

Trade-offs

Trade-offs & when to use

SOLID buys flexibility at the cost of indirection. Apply it where change is likely, not everywhere by reflex.

AspectDetail
ProsLocalized change, isolated testing, safe extension, parallel teamwork, and clear module boundaries that survive years of edits.
ConsMore types and files, extra indirection to follow, and up-front design effort that can slow the first version.
Use whenThe code has volatile requirements, multiple implementations of a concept, a long lifespan, or a team that needs stable seams to work in parallel.
Avoid whenShort-lived scripts, one-off prototypes, or stable code with a single implementation where extra abstraction only adds friction.
ComplexityLow per principle, but the count of interfaces and injected dependencies grows. Manage it with a DI container and clear naming.
RelatedDesign patterns (strategy, factory), composition over inheritance, dependency injection, and clean/hexagonal architecture.
Rule of thumb: introduce an abstraction the moment you have a real second reason to change or a real second implementation, not before. SOLID rewards code that must evolve; it taxes code that never will.
06 - Case Studies

Real-world case studies

Three representative refactors showing SOLID applied under production pressure.

💳

1 · Payment provider expansion

Principles: DIP + OCP + LSP

A checkout service hardcoded a single card processor; every new market needed a new provider and edits to the core order flow.

  • A PaymentGateway interface was defined in the language of the order domain.
  • Stripe, PayPal, and a local wallet each became an implementation injected at startup.
  • The order service stopped changing entirely; new providers shipped as new classes.
✅ Outcome: Launching a new market became a plug-in task instead of a risky edit to battle-tested checkout code.
🧾

2 · The invoice god class

Principles: SRP + ISP

A single Invoice class calculated totals, rendered PDFs, and persisted to the database, so any format tweak risked the tax math.

  • Calculation, rendering, and persistence were split into three cohesive collaborators.
  • Narrow interfaces let the renderer depend only on read methods it needed.
  • Changing the PDF layout no longer touched code that computed money.
✅ Outcome: Formatting changes shipped without regression risk to financial logic, and each concern got focused unit tests.
🗄️

3 · Swapping the storage backend

Principles: DIP + LSP

Business logic called a concrete file store directly, making a move to cloud object storage a codebase-wide search-and-replace.

  • A DocumentStore abstraction captured save, load, and delete in domain terms.
  • Local disk and cloud implementations honored the exact same contract.
  • Tests ran against an in-memory store, cutting suite time dramatically.
✅ Outcome: The backend migration became a one-line wiring change, and the policy code never knew storage moved to the cloud.
07 - Relevance

Modern relevance

SOLID predates microservices and functional-leaning codebases, yet its core idea, aim your dependencies at stable abstractions, only grew more important.

🧱 Clean & hexagonal architecture

Ports-and-adapters is dependency inversion at the system scale: the domain depends on ports, infrastructure implements them at the edge.

🧪 Testability everywhere

Injected abstractions remain the simplest path to fast, isolated tests, which is why DIP is baked into every modern framework's DI container.

🔀 Functional crossover

Passing a function is dependency inversion without a named interface; higher-order functions deliver OCP and DIP with less ceremony.

🌐 Microservice contracts

Service boundaries are interface segregation writ large - narrow, versioned APIs that let teams deploy independently behind stable contracts.

🤖 AI-assisted refactoring

Tools now flag SRP and DIP violations and suggest extractions, but naming the right abstraction still needs human judgment about change.

📦 Plugin ecosystems

Every extensible platform, from editors to CI, is open/closed by design: third parties add behavior through a fixed extension contract.

Bottom line: SOLID is not five rules to obey but one instinct to build - keep responsibilities small and point every dependency at a stable abstraction. Do that and your code bends with new requirements instead of breaking under them.
