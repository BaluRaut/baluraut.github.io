Value Objects vs Entities - modeling identity and equality

In a payments and orders system, some things are what they contain, and some things are who they are. A value object like Money or Email is defined entirely by its attributes and never changes. An entity like an Order or Customer has a stable identity and a lifecycle that outlives any single set of field values.

01 - What

What are value objects and entities?

This is the most consequential modeling decision in domain design. An entity is a thing with a distinct identity that persists through change: an Order is the same order whether it is pending, paid, or shipped. A value object is a thing defined only by its attributes: two Money instances of 25.00 USD are interchangeable, and neither has a life story worth tracking.

🆔 Entity

Has an identity (an id) that stays fixed while its attributes mutate over time. Order, Customer, and Payment each have a lifecycle worth tracking.

💠 Value object

Has no id. It is fully described by its fields and is immutable. Money, Email, and Address are compared by content, not reference.

⚖️ Equality split

Entities are equal when their ids match. Value objects are equal when every attribute matches. Getting this wrong corrupts caches, sets, and lookups.

Entity vs value object at a glance

TraitEntityValue object
IdentityDistinct id, assigned onceNone; the content is the identity
EqualitySame id means same entitySame attributes mean equal
MutabilityAttributes change over the lifecycleImmutable; changes produce a new instance
LifecycleCreated, tracked, archived, deletedCreated and discarded freely, no tracking
ExamplesOrder, Customer, Payment, ShipmentMoney, Email, Address, DateRange
Key mental model: ask "if two of these had all the same fields, would I still care which is which?" If yes, it is an entity and needs an id. If no, it is a value object and should be immutable and compared by content.
02 - Why

Why the distinction matters

Blurring these two categories is the root of a whole class of bugs: mutable amounts that drift, entities compared by fields that silently duplicate, and equality that behaves differently in a set than in an if. Naming the category up front makes correctness the default.

🛡️ Immutability removes shared-state bugs

A Money that cannot change cannot be mutated by one part of the checkout while another reads it. You pass value objects around freely without defensive copies.

🎯 Correct equality powers collections

Value objects that are equal by content deduplicate correctly in sets, act as reliable map keys, and let caches hit instead of leaking duplicates.

🧭 Identity tracks the real thing

An Order keeps one id from cart to delivery. Every state transition, event, and audit row hangs off that stable identity, not off a snapshot of its fields.

🧱 Rich types replace primitive soup

An Email or Money type validates once at construction, so the rest of the system trusts the value instead of re-checking raw strings and floats everywhere.

In Plain Terms

Value objects vs entities explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

A student id number is an entity: it is still you after you change your name, address, or major. A ten dollar bill is a value object: any ten dollar bill spends exactly the same, so nobody tracks which one you hold.

👩‍💻 For a developer

A database row with a primary key is an entity; you update its columns but the key never moves. A Color(255, 0, 0) or Money(25, "USD") is a value object: equal by fields, replaced rather than edited.

🏢 For a professional

A customer account is an entity your business tracks for years across every order. The shipping address printed on one order is a value object: a snapshot of fields, valid on its own, not something with a life of its own.

🏦 Everyday version

Your bank account is an entity: same account number as the balance rises and falls. A banknote is a value object: two twenties of the same currency are interchangeable, defined only by their denomination.

03 - How

How to model each one

A value object validates in its constructor, exposes read-only fields, and returns new instances from any operation. An entity carries an id, guards its own state transitions, and defines equality on the id alone.

💠 Building a value object

Freeze the fields, validate once, and compare by content. Arithmetic like adding two Money values returns a fresh Money rather than mutating either operand.

🆔 Building an entity

Assign an id at creation, keep it constant, and let methods drive the lifecycle. An Order holds value objects for its total and address while its status evolves.

// Money: a value object - immutable, equal by attributes
class Money {
  constructor(
    readonly amountCents: number,
    readonly currency: string,
  ) {
    if (!Number.isInteger(amountCents)) throw new Error("amount must be whole cents");
    Object.freeze(this);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("currency mismatch");
    return new Money(this.amountCents + other.amountCents, this.currency);
  }

  equals(other: Money): boolean {
    return this.amountCents === other.amountCents && this.currency === other.currency;
  }
}

// Order: an entity - equal by identity, mutable lifecycle
class Order {
  private lines: Money[] = [];
  status: "pending" | "paid" = "pending";

  constructor(readonly id: string, readonly customerId: string) {}

  addLine(price: Money): void {
    this.lines.push(price); // attributes change; id does not
  }

  total(): Money {
    return this.lines.reduce((sum, m) => sum.add(m), new Money(0, "USD"));
  }

  pay(): void {
    this.status = "paid";
  }

  equals(other: Order): boolean {
    return this.id === other.id; // identity, not fields
  }
}

const order = new Order("ord_1001", "cus_42");
order.addLine(new Money(1999, "USD"));
order.addLine(new Money(500, "USD"));
console.log(order.total().equals(new Money(2499, "USD"))); // true
order.pay();
console.log(order.status); // "paid"
from dataclasses import dataclass, field

# Money: a value object - frozen and equal by attributes
@dataclass(frozen=True)
class Money:
    amount_cents: int
    currency: str

    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError("currency mismatch")
        return Money(self.amount_cents + other.amount_cents, self.currency)

# frozen dataclass gives __eq__ by fields and __hash__ for free

# Order: an entity - equal by identity, mutable lifecycle
class Order:
    def __init__(self, id: str, customer_id: str):
        self.id = id
        self.customer_id = customer_id
        self._lines: list[Money] = []
        self.status = "pending"

    def add_line(self, price: Money) -> None:
        self._lines.append(price)  # attributes change; id does not

    def total(self) -> Money:
        total = Money(0, "USD")
        for line in self._lines:
            total = total.add(line)
        return total

    def pay(self) -> None:
        self.status = "paid"

    def __eq__(self, other: object) -> bool:
        return isinstance(other, Order) and self.id == other.id  # identity

    def __hash__(self) -> int:
        return hash(self.id)

order = Order("ord_1001", "cus_42")
order.add_line(Money(1999, "USD"))
order.add_line(Money(500, "USD"))
print(order.total() == Money(2499, "USD"))  # True
order.pay()
print(order.status)  # "paid"
# Money: a value object - immutable and equal by attributes
class Money
  attr_reader :amount_cents, :currency

  def initialize(amount_cents, currency)
    raise ArgumentError, "amount must be whole cents" unless amount_cents.is_a?(Integer)
    @amount_cents = amount_cents
    @currency = currency
    freeze
  end

  def add(other)
    raise ArgumentError, "currency mismatch" unless other.currency == currency
    Money.new(amount_cents + other.amount_cents, currency)
  end

  def ==(other)
    other.is_a?(Money) && amount_cents == other.amount_cents && currency == other.currency
  end
  alias eql? ==

  def hash
    [amount_cents, currency].hash
  end
end

# Order: an entity - equal by identity, mutable lifecycle
class Order
  attr_reader :id, :customer_id
  attr_accessor :status

  def initialize(id, customer_id)
    @id = id
    @customer_id = customer_id
    @lines = []
    @status = :pending
  end

  def add_line(price)
    @lines << price # attributes change; id does not
  end

  def total
    @lines.reduce(Money.new(0, "USD")) { |sum, m| sum.add(m) }
  end

  def pay
    @status = :paid
  end

  def ==(other)
    other.is_a?(Order) && id == other.id # identity, not fields
  end
end

order = Order.new("ord_1001", "cus_42")
order.add_line(Money.new(1999, "USD"))
order.add_line(Money.new(500, "USD"))
puts order.total == Money.new(2499, "USD") # true
order.pay
puts order.status # paid

Notice the split: Money is frozen and defines equality over its fields, so 2499 cents equals 2499 cents no matter which instance you hold. Order keeps a fixed id, mutates its lines and status, and compares only by id, so a paid order still equals the pending order it once was.

05 - Step by Step

The 0 → 100 flow

From an unmodeled concept to a clean split of entities and value objects across the orders domain, in order.

00
Spot

List the domain nouns

Write down every concept in the checkout: order, customer, money, email, address, payment, line item. These are your candidates.

10
Ask

Does it need an identity?

For each noun ask whether two of them with identical fields are still distinct things you must track. If yes, it is an entity.

20
Classify

Split the two groups

Order, Customer, and Payment become entities. Money, Email, and Address become value objects defined by their attributes.

30
Freeze

Make value objects immutable

Give value objects read-only fields so no caller can mutate a shared amount or address after it is created.

40
Validate

Guard invariants in the constructor

Reject a negative fractional cent, a malformed email, or an empty currency at construction so every existing value is already valid.

50
Equality

Define value equality by fields

Implement equals and hash over all attributes so two equal Money values behave identically in sets and as map keys.

60
Identity

Assign entity ids

Give each entity an id at creation and compare entities only by that id, never by their current field values.

70
Compose

Embed values inside entities

Let the Order hold a Money total and an Address, and the Customer hold an Email. Entities own value objects, not the reverse.

80
Transition

Drive the lifecycle with methods

Move the Order from pending to paid to shipped through methods that enforce rules, while the id stays fixed throughout.

90
Persist

Store entities by id, values inline

Save entities keyed on their id and inline their value objects as columns or embedded documents, since values have no identity to store.

100
Trust

Reason with confidence

The rest of the system now trusts that values are valid and immutable and that entities are tracked by stable identity, killing a whole class of bugs.

Common Pitfalls

Pitfalls & anti-patterns

Most identity bugs trace back to mixing the two categories. These are the usual culprits.

🧨 Mutable value objects

Adding a setter to Money or Address means one caller can mutate a shared instance and silently change an order total elsewhere. Value objects must be frozen and replaced, not edited.

🪞 Comparing entities by fields

Overriding entity equality to compare all attributes makes two customers with the same name look equal, duplicating records and breaking lookups. Entities compare by id only.

🆔 Identity on a value object

Slapping a database id on Money or Email turns a simple value into a tracked row nobody needs, cluttering the schema and inviting accidental duplicates that should have been equal.

💵 Floats for money

Storing amounts as floating point invites rounding drift where 0.1 plus 0.2 is not 0.3. Model Money over integer cents or a decimal type inside the value object.

🧵 Primitive obsession

Passing raw strings for email and raw numbers for amounts scatters validation everywhere and lets a currency string land in an email field. Wrap them in typed value objects.

♻️ Forgetting hash with equals

Defining value equality but not a matching hash means equal Money values land in different set buckets, so deduplication and caching quietly fail.

Signals & Metrics

Signals & how to measure

You can feel the split in the shape of the code. These signals tell you whether the boundary is drawn correctly.

SignalWhat it tells you
Setters on a value typeA leaking abstraction; the value object is mutable and will cause shared-state bugs
Entity equals reads fieldsIdentity is being confused with content, so distinct records can compare as equal
Duplicate rows for equal valuesA value object was given an id it does not need, breaking natural deduplication
Validation repeated at call sitesA missing value object; the same check lives in many places instead of one constructor
Set or map keys behaving oddlyequals and hash are out of sync on a value object
id changes during a lifecycleThe entity boundary is wrong; identity must be stable from creation to deletion
Rule of thumb: if a type has a setter, it should have no id; if a type has an id, its equality should read only that id. When both halves of that rule hold across the model, the entity and value boundary is clean.
06 - Case Studies

Real-world case studies

Three production-style systems where the entity and value object split is load-bearing.

💳

1 · Payments ledger with a Money value object

Pattern: immutable amounts, tracked transactions

A payments platform must add, split, and convert amounts without ever losing a cent or mutating shared state.

  • Money is a frozen value object over integer minor units plus a currency code, equal by content.
  • Every Transaction is an entity with a stable id, an immutable Money amount, and a status lifecycle.
  • Arithmetic returns new Money instances, so ledger entries never drift when reused across reports.
✅ Outcome: Reconciliation matches to the cent because amounts are immutable values while each transaction stays independently tracked by id.
📦

2 · E-commerce orders and addresses

Pattern: entity lifecycle over value snapshots

An online store needs an order to survive edits and shipping while preserving the exact address it was placed with.

  • Order and Customer are entities; the shipping Address and line prices are value objects.
  • The Address captured at checkout is a frozen snapshot, so later profile edits never rewrite past orders.
  • The Order id stays fixed from cart through delivery while its status and lines evolve.
✅ Outcome: Historical orders keep their original addresses and totals, while the live customer entity keeps evolving under one identity.
📧

3 · Accounts and auth with an Email value object

Pattern: validated values guarding an entity

A user-accounts service must treat an email as a validated, comparable value while the account itself is a long-lived entity.

  • Email is a value object that normalizes and validates its address once at construction.
  • Customer is an entity keyed on a user id, so changing an email never changes who the customer is.
  • Equal Email values compare and hash identically, powering uniqueness checks and lookups.
✅ Outcome: Duplicate-email checks are reliable and account identity is stable, because the value is validated and the entity is tracked by id.
07 - Relevance

Modern relevance

The entity and value object split predates modern frameworks and keeps getting more useful as languages add first-class support for immutable data.

🧊 Records and frozen data

TypeScript readonly, Python frozen dataclasses, Kotlin data classes, and Java records make value objects a one-liner, so there is no excuse for mutable value types.

🏗️ Domain-driven design

DDD builds aggregates from exactly this split: entities with identity anchor an aggregate while value objects express its measurements and descriptions.

🔗 Event sourcing

Events are immutable value objects; the entity is the aggregate reconstructed by replaying them, making the identity-versus-content line explicit.

🧪 Easier testing

Immutable value objects need no setup or teardown and compare by content, so assertions read cleanly and tests do not leak state between cases.

🧵 Concurrency safety

Immutable values are safe to share across threads and async tasks without locks, which matters as services get more concurrent.

🗃️ ORM mapping

Modern ORMs map value objects as embedded or owned types and entities to tables with keys, encoding the distinction right in the persistence layer.

Bottom line: deciding entity versus value object is the first real modeling call you make, and it pays off everywhere: correct equality, safe sharing, clean persistence, and code that says what it means.
