OOP Concept

Polymorphism - one call, many behaviors

Polymorphism lets a single call site work with objects of many types, each responding in its own way. A checkout service calls charge() once; a card gateway, a wallet, and a bank transfer each run their own logic. The caller stays ignorant of the concrete type, and the runtime picks the right method by dynamic dispatch.

01 - What

What is polymorphism?

Polymorphism means "many forms": one interface, many implementations. You program against an abstract contract, such as a PaymentMethod with a charge() method, and at runtime any concrete method that honors that contract can be substituted in. The caller sends one message; the receiving object decides how to respond. This is the mechanism that lets you add a new payment provider without editing the code that triggers payments.

🧬 Subtype polymorphism

A StripeCard is-a PaymentMethod. Wherever the base type is expected, any subtype works. The classic OO form, resolved by dynamic dispatch.

🔀 Ad-hoc (overloading)

The same operation name handles different argument types with distinct code, like format(amount) versus format(amount, currency). Resolved per signature.

📦 Parametric (generics)

One implementation works for any type, like a Repository<T> or a generic Cache. Type-agnostic code, no branching on type.

Key mental model: polymorphism moves the decision "which behavior runs" out of a switch statement and into the type system. You stop asking "what kind of thing is this?" and instead tell the thing "do your job."
02 - Why

Why polymorphism matters

Systems grow by adding cases: a new payment provider, a new export format, a new notification channel. Without polymorphism, every new case edits every conditional that already exists. With it, new behavior arrives as a new class the old code never sees.

➕ Extensible by addition

Add a ApplePayMethod class and register it. The checkout service, invoices, and receipts keep working untouched. New behavior does not mean new branches.

🧹 Kills conditional sprawl

A giant if method == "card" ... elif method == "wallet" spread across the codebase collapses into a single method.charge(). The type carries the decision.

🧪 Trivially testable

Because callers depend on an interface, tests inject a fake PaymentMethod that records calls. No network, no real gateway, no monkey-patched globals.

🔗 Decoupled layers

The order service knows the contract, not the vendor. Swap Stripe for Adyen behind the same interface and nothing upstream changes. Dependencies point at abstractions.

In Plain Terms

Polymorphism explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is a universal remote. You press "power" once; the TV, the soundbar, and the projector each interpret that same signal in their own way. One button, many devices, correct behavior everywhere.

👩‍💻 For a developer

You call paymentMethod.charge(amount) against an interface. The concrete object, injected at runtime, decides whether that means a card authorization, a wallet debit, or a bank transfer. The call site never branches on type.

🏢 For a professional

Think of an invoice that renders to PDF, HTML, or CSV. Accounting asks the invoice to "render"; the format object handles the details. Add a new format and the billing screen does not change.

🔌 Everyday version

A wall socket accepts any appliance that fits the plug. The socket does not care if it powers a lamp or a laptop charger; it just delivers, and each device does its own thing.

03 - How

How it works under the hood

Polymorphism rests on two pieces: a shared contract (an interface or base class declaring a method), and dynamic dispatch, the runtime lookup that routes a call to the concrete object's own override rather than the base version.

📜 The contract

An abstract PaymentMethod declares charge(amount): Receipt. It says what, never how. Every concrete method promises to fulfill it, so callers can hold the base type safely.

🎯 Dynamic dispatch

When you call m.charge(amount), the runtime inspects the actual object behind m and jumps to that class's charge. This late binding is what makes overriding take effect.

// Shared contract: every payment method honors charge()
interface Receipt { method: string; amount: number; reference: string; }

abstract class PaymentMethod {
  abstract charge(amount: number): Receipt;
  abstract label(): string;
}

class CardGateway extends PaymentMethod {
  constructor(private last4: string) { super(); }
  charge(amount: number): Receipt {
    // authorize + capture against the card network
    return { method: this.label(), amount, reference: `auth_${this.last4}` };
  }
  label() { return `Card ****${this.last4}`; }
}

class DigitalWallet extends PaymentMethod {
  constructor(private walletId: string) { super(); }
  charge(amount: number): Receipt {
    // debit the stored wallet balance
    return { method: this.label(), amount, reference: `wlt_${this.walletId}` };
  }
  label() { return `Wallet ${this.walletId}`; }
}

class BankTransfer extends PaymentMethod {
  constructor(private iban: string) { super(); }
  charge(amount: number): Receipt {
    // initiate an ACH / SEPA pull
    return { method: this.label(), amount, reference: `sepa_${this.iban.slice(-4)}` };
  }
  label() { return `Bank ${this.iban.slice(-4)}`; }
}

// The caller branches on nothing. Dynamic dispatch does the routing.
class CheckoutService {
  settle(method: PaymentMethod, amount: number): Receipt {
    const receipt = method.charge(amount);
    console.log(`Settled ${amount} via ${receipt.method} -> ${receipt.reference}`);
    return receipt;
  }
}

const checkout = new CheckoutService();
const methods: PaymentMethod[] = [
  new CardGateway("4242"),
  new DigitalWallet("acct_9f2"),
  new BankTransfer("DE89370400440532013000"),
];
for (const m of methods) checkout.settle(m, 4999);
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class Receipt:
    method: str
    amount: int
    reference: str

class PaymentMethod(ABC):
    @abstractmethod
    def charge(self, amount: int) -> Receipt: ...
    @abstractmethod
    def label(self) -> str: ...

class CardGateway(PaymentMethod):
    def __init__(self, last4: str):
        self.last4 = last4
    def charge(self, amount: int) -> Receipt:
        # authorize + capture against the card network
        return Receipt(self.label(), amount, f"auth_{self.last4}")
    def label(self) -> str:
        return f"Card ****{self.last4}"

class DigitalWallet(PaymentMethod):
    def __init__(self, wallet_id: str):
        self.wallet_id = wallet_id
    def charge(self, amount: int) -> Receipt:
        # debit the stored wallet balance
        return Receipt(self.label(), amount, f"wlt_{self.wallet_id}")
    def label(self) -> str:
        return f"Wallet {self.wallet_id}"

class BankTransfer(PaymentMethod):
    def __init__(self, iban: str):
        self.iban = iban
    def charge(self, amount: int) -> Receipt:
        # initiate an ACH / SEPA pull
        return Receipt(self.label(), amount, f"sepa_{self.iban[-4:]}")
    def label(self) -> str:
        return f"Bank {self.iban[-4:]}"

class CheckoutService:
    def settle(self, method: PaymentMethod, amount: int) -> Receipt:
        receipt = method.charge(amount)  # dynamic dispatch, no isinstance checks
        print(f"Settled {amount} via {receipt.method} -> {receipt.reference}")
        return receipt

The three snippets are behaviorally identical. Note the difference in binding style: TypeScript and Python declare an explicit base contract, while Ruby leans on duck typing - settle accepts any object that responds to charge, no shared ancestor required. In every case the caller has zero branches on payment type.

Before and after - dispatch replaces the conditional

// BEFORE: the caller owns every case. Each new method edits this switch.
function settle(kind: string, amount: number) {
  if (kind === "card") {
    return authorizeCard(amount);
  } else if (kind === "wallet") {
    return debitWallet(amount);
  } else if (kind === "bank") {
    return initiateTransfer(amount);
  }
  throw new Error(`Unknown method ${kind}`);
}

// AFTER: the object owns its case. New method = new class, caller untouched.
function settle(method: PaymentMethod, amount: number) {
  return method.charge(amount);
}
# BEFORE: the caller owns every case. Each new method edits this branch.
def settle(kind: str, amount: int):
    if kind == "card":
        return authorize_card(amount)
    elif kind == "wallet":
        return debit_wallet(amount)
    elif kind == "bank":
        return initiate_transfer(amount)
    raise ValueError(f"Unknown method {kind}")

# AFTER: the object owns its case. New method = new class, caller untouched.
def settle(method: PaymentMethod, amount: int):
    return method.charge(amount)
# BEFORE: the caller owns every case. Each new method edits this case.
def settle(kind, amount)
  case kind
  when "card"   then authorize_card(amount)
  when "wallet" then debit_wallet(amount)
  when "bank"   then initiate_transfer(amount)
  else raise "Unknown method #{kind}"
  end
end

# AFTER: the object owns its case. New method = new class, caller untouched.
def settle(method, amount)
  method.charge(amount)
end

This is the payoff. The conditional did not vanish; it moved. Each concrete class holds exactly one branch of the old switch, and the runtime's dispatch table replaces the manual dispatch you used to write by hand.

05 - Step by Step

The 0 → 100 flow

From a hardcoded conditional to clean polymorphic dispatch, and adding a brand new payment method without touching the caller.

00
Smell

Spot the growing switch

Payments run through a sprawling if kind == "card" ... elif "wallet". Every provider added means editing this block plus the receipt and refund paths.

10
Contract

Name the shared behavior

List what all methods must do: charge(amount) and label(). Declare it as an abstract base class or interface, the PaymentMethod contract.

20
Model

Give each case a class

Create CardGateway, DigitalWallet, and BankTransfer, each implementing the contract. One branch of the old switch moves into each class.

30
Override

Implement charge() per class

Each subtype overrides charge() with its own logic: authorize a card, debit a wallet, pull a transfer. Same signature, different bodies.

40
Depend

Type the caller to the base

CheckoutService.settle now accepts a PaymentMethod, not a string. It depends on the abstraction, never the concrete provider.

50
Dispatch

Replace the switch with one call

Delete the conditional. The body becomes method.charge(amount). Dynamic dispatch routes to the right override at runtime.

60
Construct

Pick the type at the edge

Something must still choose the concrete class, usually a factory reading the checkout request. That choice lives at one boundary, not scattered everywhere.

70
Iterate

Process mixed collections uniformly

A list of assorted PaymentMethod objects loops through one call site. Retries, split payments, and receipts treat them identically.

80
Extend

Add ApplePay with zero edits upstream

Write ApplePayMethod implementing the contract and register it in the factory. Checkout, refunds, and reporting compile and run unchanged.

90
Test

Inject a fake method

Tests pass a stub PaymentMethod that records the amount. The polymorphic seam makes the service testable without any real gateway.

100
Ship

Behavior scales by classes, not branches

The codebase now grows by adding types, not by widening conditionals. New behavior is additive, isolated, and safe to deploy.

Common Pitfalls

Pitfalls & anti-patterns

Polymorphism done carelessly recreates the very coupling it was meant to remove. Watch for these.

🔎 Type-checking the abstraction

Writing if (method instanceof CardGateway) inside the caller defeats the point. If you must ask an object its concrete type, the behavior belongs on the object as another method.

⚠️ Violating Liskov substitution

A BankTransfer.charge() that throws where the base promised a receipt breaks callers that trusted the contract. Subtypes must honor the base's guarantees, not weaken them.

🧩 Fat interfaces

A contract with charge, refund, tokenize, and threeDSecure forces every method to stub out what it cannot do. Split into focused roles instead.

🪜 Deep inheritance chains

Five levels of PaymentMethod subclasses to share code makes overrides impossible to trace. Prefer composition and small mixins over tall hierarchies.

🕳️ Silent default cases

An overridden method that quietly returns null or an empty receipt for the case it does not handle hides bugs. Fail loudly or make the missing behavior explicit in the type.

🎭 Duck typing without a check

In dynamic languages, passing an object that lacks charge fails deep in production, not at the boundary. Validate the required methods at the edge, or use protocols.

Signals & Metrics

Signals & how to measure

You cannot put polymorphism on a dashboard, but these code signals tell you whether it is helping or missing.

SignalWhat it tells you
Type-switch countRepeated switch or instanceof on the same set of kinds signals a missing polymorphic hierarchy. Each duplicate is a place a new case will be forgotten.
Shotgun surgery per featureIf adding one payment method touches many files, dispatch is still manual. Good polymorphism makes it a single new class.
Cyclomatic complexity of callersHigh branching in the service layer often means logic that belongs on the objects. Dispatch should flatten these numbers.
Override consistencyDo all subtypes accept the same inputs and return the same shape? Divergent signatures warn of a leaky contract and Liskov risk.
Test double easeIf faking a dependency requires patching internals rather than passing an implementation, your seams are not polymorphic enough.
Open-closed adherenceTrack whether new behavior arrives as added classes versus modified conditionals in existing files. The former is the healthy pattern.
Rule of thumb: if you find yourself writing the same if-ladder on the same set of types in more than two places, that is the type system asking for a polymorphic method. Move the branch onto the object.
06 - Case Studies

Real-world case studies

Three production-style systems where polymorphism carries the weight.

💳

1 · Payment orchestration across providers

Pattern: one charge() call, many gateways

A marketplace routes payments through Stripe, Adyen, and local bank rails depending on the buyer's region and method.

  • Every provider implements a common PaymentMethod.charge(), so the checkout flow is provider-agnostic.
  • A factory at the request boundary picks the concrete gateway; nothing downstream branches on it.
  • Adding a new regional provider ships as one class plus a factory entry, with refunds and receipts untouched.
✅ Outcome: New markets launch by adding classes, and the core settlement path stays stable and heavily tested.
📣

2 · Multi-channel notification service

Pattern: one send() across email, SMS, push

A platform sends transactional alerts over email, SMS, push, and in-app channels from a single dispatch loop.

  • Each channel is a Notifier that overrides send(message, recipient) with its own transport.
  • User preferences yield a list of channel objects; the dispatcher iterates and calls send uniformly.
  • A new WhatsApp channel drops in as a class implementing the same contract, no dispatcher changes.
✅ Outcome: Channels evolve independently and the fan-out engine never learns a new if branch.
🧾

3 · Report and invoice export pipeline

Pattern: one render() to PDF, HTML, CSV

A billing system exports the same invoice to PDF for customers, HTML for the web view, and CSV for accounting imports.

  • Each format is a Renderer overriding render(invoice); the invoice holds the data, the renderer the form.
  • The export endpoint resolves the requested format to a renderer object and calls one method.
  • A new XLSX export is added without editing the invoice model or the endpoint's dispatch code.
✅ Outcome: Output formats multiply freely while the invoice domain model stays clean and single-purpose.
07 - Relevance

Modern relevance

Polymorphism is not a relic of classic OO; it underpins how modern typed and dynamic languages compose behavior.

🧱 Protocols and traits

Swift protocols, Rust traits, and Go interfaces are polymorphism without inheritance: behavior is bound by capability, echoing structural and duck typing at compile time.

🔤 Structural typing

TypeScript matches shapes, not names. Anything with the right methods satisfies an interface, blending static safety with duck-typed flexibility.

🧬 Bounded generics

Parametric polymorphism with constraints, like <T extends PaymentMethod>, gives one implementation that works for many types while keeping guarantees.

🧩 Sum types and pattern match

Functional languages and modern Rust and Scala pair closed sum types with exhaustive matching, an intentional alternative to open subtype dispatch.

🔌 Plugin architectures

Extensions, adapters, and drivers all lean on a shared interface so third parties add behavior without forking the core, the same open-closed payoff.

🌐 Polyglot service contracts

gRPC and OpenAPI define a contract many language implementations satisfy, subtype substitution stretched across process and network boundaries.

Bottom line: polymorphism is how you make code open to new cases and closed to change. Whether by class, interface, protocol, or generic, the goal is constant: call one thing, let the type decide the behavior, and grow by adding rather than editing.
