OOP Concept

Dependency Injection - hand a class its collaborators instead of building them

A class that reaches out and constructs its own database client, mailer, and clock is welded to those exact implementations forever. Dependency Injection flips that: collaborators are passed in from outside, so the same OrderService can run against a real Postgres repository in production and a fast in-memory fake in tests, with zero code changes.

01 - What

What is Dependency Injection?

Dependency Injection (DI) is the practice of giving an object the collaborators it needs from the outside rather than letting it create or locate them itself. Instead of an OrderService calling new PostgresOrderRepository(), new SmtpMailer(), and new SystemClock() in its own body, those three objects are handed to it, usually through its constructor. The service depends on what they do, expressed as interfaces, not on which concrete class provides it.

🏗️ Constructor injection

Required collaborators arrive as constructor arguments. The object is never valid without them, so there is no half-built state. This is the default and preferred form.

🔧 Setter injection

An optional collaborator is supplied after construction through a setter or property. Useful for genuinely optional behavior like a metrics sink, but it allows an object to exist before it is fully wired.

📨 Method injection

A collaborator is passed as an argument to the single method that needs it, rather than stored on the object. Good when the dependency is per-call, like a request-scoped clock or user context.

The moving parts

TermWhat it isIn the OrderService example
Dependent / clientThe class that needs collaboratorsOrderService

Injection pointWhere the collaborator entersThe constructor parameters
Injector / composition rootThe place that builds and wires the graphmain() or an IoC container

Key mental model: DI does not remove the new keyword from your program, it relocates it. Objects still get constructed, but the construction moves out of business logic and up into a single wiring layer at the edge of the app, the composition root.
02 - Why

Why Dependency Injection exists

When a class builds its own collaborators, it hard-codes decisions that belong to the caller: which database, which mail provider, which clock. That coupling makes the class impossible to reuse, hard to configure per environment, and painful to test. DI pulls those decisions out to where they can vary.

🧪 Testability without the world

Pass a fake repository and a stub clock and you can assert that placing an order saves the right row and emails the customer, all in memory, in milliseconds, with no network or database.

🔁 Swap implementations freely

Move from SMTP to a transactional email API, or from Postgres to an in-memory store for a demo, by changing one line in the composition root. The service body never changes.

🔍 Honest, visible dependencies

A constructor that lists a repository, a mailer, and a clock tells you exactly what the class touches. Hidden new calls and global singletons hide that surface and surprise the next reader.

⚙️ Configuration lives at the edge

Connection strings, API keys, and retry policies are decided once where objects are wired, not scattered through business logic. Each environment builds its own graph.

In Plain Terms

Dependency Injection explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is the difference between an exam that hands you a calculator and one that makes you build a calculator from scratch first. You focus on the problem because the tool is provided; a different exam could hand you a different tool.

👩‍💻 For a developer

Instead of your OrderService writing new SmtpMailer() deep inside placeOrder, the mailer is a constructor argument. Production passes the real one, tests pass a recording fake, and the method under test never knows the difference.

🏢 For a professional

A well-run team does not let each new hire procure their own laptop and vendor accounts. IT provisions the standard tools centrally. The employee does the job; the organization decides which tools back it.

🔌 Everyday version

Your kettle has a plug, not hard-wired mains cabling. The socket supplies power however the building sources it. Swap the building's supply and the kettle keeps working, because it depends on the socket, not the power plant.

03 - How

How it works under the hood

The client class declares interfaces for what it needs and stores whatever it is given. Something else, a composition root or an IoC container, decides the concrete classes and wires the object graph together at startup.

📐 Depend on contracts

OrderService holds a Repository, a Mailer, and a Clock, all interfaces. It calls save, send, and now without knowing whether those talk to Postgres, an email API, or the system clock.

🧬 Wire at the composition root

A single startup location builds SmtpMailer, PostgresOrderRepository, and SystemClock, then passes them into OrderService. Tests build a different graph with fakes and stubs instead.

// Contracts the service depends on, not concrete classes
interface Clock { now(): Date; }
interface Mailer { send(to: string, subject: string, body: string): void; }
interface Repository {
  nextId(): string;
  save(order: Order): void;
}

interface Order { id: string; customerId: string; total: number; placedAt: Date; }

class OrderService {
  // Collaborators are injected, never constructed inside
  constructor(
    private readonly repo: Repository,
    private readonly mailer: Mailer,
    private readonly clock: Clock,
  ) {}

  placeOrder(customerId: string, total: number): Order {
    const order: Order = {
      id: this.repo.nextId(),
      customerId,
      total,
      placedAt: this.clock.now(),
    };
    this.repo.save(order);
    this.mailer.send(customerId, "Order confirmed", `Total ${order.total}`);
    return order;
  }
}

The service body is identical in production and in tests. Only the composition root differs: production hands it a Postgres repository, an SMTP mailer, and the system clock, while the test hands it a fake, a spy, and a frozen clock. That interchangeable seam is the entire payoff of injecting collaborators instead of newing them up.

05 - Step by Step

The 0 → 100 flow

From a class that news up its own collaborators to a fully injected, testable service wired at the composition root.

00
Smell

Spot the hidden new

You find new SmtpMailer() and new PostgresOrderRepository() buried inside placeOrder. The method cannot be tested without a real mail server and database.

10
Name

Identify the collaborators

List what the class truly depends on: a repository to persist orders, a mailer to notify the customer, and a clock to timestamp. Three real dependencies, three responsibilities to inject.

20
Contract

Define interfaces

Write a Repository, Mailer, and Clock interface capturing only the methods the service calls, such as save, send, and now.

30
Depend

Point the service at contracts

Change field types from concrete classes to interfaces. The service now speaks to abstractions, satisfying the Dependency Inversion Principle.

40
Inject

Add constructor parameters

Accept the three collaborators as constructor arguments and store them. Delete every new for a collaborator from the method bodies.

50
Adapt

Write concrete implementations

Implement PostgresOrderRepository, SmtpMailer, and SystemClock against the interfaces. These are the production adapters.

60
Wire

Build the composition root

In main() construct each concrete collaborator and pass them into new OrderService(...). This is now the only place that knows the concrete types.

70
Fake

Create test doubles

Write a FakeRepository that stores orders in a list, a SpyMailer that records recipients, and a FixedClock that returns a constant time.

80
Test

Inject the doubles

Construct the service with the fakes and call placeOrder. Assert the order was saved, the customer was emailed, and the timestamp is deterministic.

90
Scale

Introduce an IoC container

As the graph grows, register bindings such as Mailer to SmtpMailer in a container that resolves and constructs the whole tree, so you stop wiring by hand.

100
Vary

Swap per environment

Bind a fake mailer in staging, a real one in production, and an in-memory repository in a demo, all without touching OrderService. The seam pays off forever.

Common Pitfalls

Pitfalls & anti-patterns

DI is easy to overdo and easy to fake. These are the mistakes that turn a clean seam into a mess.

🕳️ Service locator in disguise

Passing a container into the class and calling container.resolve(Mailer) inside a method hides dependencies again. The constructor should list them; do not smuggle a global lookup back in.

🧨 Constructor over-injection

A constructor taking ten collaborators is not a DI win, it is a Single Responsibility failure. The class is doing too much. Split it before you inject the crowd.

🔓 Setter injection for required deps

Using a setter for a mandatory repository lets the object exist half-wired, so a forgotten call crashes at runtime. Required collaborators belong in the constructor.

🎯 Injecting concretes, not contracts

Declaring the parameter as SmtpMailer instead of Mailer re-welds the class to one implementation. You get the ceremony of DI with none of the swappability.

🏭 Newing up inside anyway

Accepting a mailer but still writing new SystemClock() for the timestamp leaves an untestable seam. Every non-trivial collaborator, including the clock, should be injected.

🎭 Mocking everything

Replacing every collaborator with an auto-mock that returns nulls tests the wiring, not the behavior. Prefer simple hand-written fakes and stubs that model real responses.

Signals & Metrics

Signals & how to measure

You cannot count DI directly, but a healthy injection culture leaves fingerprints in the code and the test suite.

SignalWhat it tells you
Count of new in business classesNear zero for collaborators means construction has moved to the composition root; a rising count means hidden coupling is creeping back.
Tests needing no I/OIf unit tests hit no real database, network, or mail server, the dependencies are genuinely injected and faked.
Test setup line countIf wiring a class under test takes twenty lines of mocks, the class likely has too many dependencies or leaks concretes.
Constructor parameter countTwo to four collaborators is healthy; consistently high counts flag a Single Responsibility problem, not a DI success.
Time to add an implementationSwapping SMTP for an email API by editing one wiring line signals a clean seam; edits scattered across the codebase signal leaky abstractions.
Non-determinism in testsFlaky time or random-id assertions reveal an un-injected clock or id source that should have been passed in.
Rule of thumb: if you cannot instantiate a class in a test without starting a server, it is not injecting its dependencies, no matter how many interfaces it declares. The test harness is the honest judge of your DI.
06 - Case Studies

Real-world case studies

Three production-shaped systems where injecting collaborators is the load-bearing decision.

🛒

1 · Checkout service in an e-commerce backend

Pattern: constructor injection across a payment, inventory, and notification graph

A checkout flow must charge a card, reserve inventory, and email a receipt, all of which are external systems that must be faked in tests.

  • The CheckoutService takes a payment gateway, an inventory repository, and a mailer as constructor arguments.
  • Integration tests inject a sandbox gateway and an in-memory inventory store so the full flow runs without real charges.
  • A frozen clock makes receipt timestamps and idempotency keys deterministic under test.
✅ Outcome: The entire purchase path is exercised in unit tests with no live payment provider, so regressions are caught before deploy.
🏦

2 · Ledger posting in a banking core

Pattern: injected clock and repository for auditable, testable transactions

A ledger must post debit and credit entries atomically and stamp each with an exact posting time that auditors can reproduce.

  • The posting engine depends on an injected Clock so tests can assert entries land on a precise business date.
  • A repository interface lets the same engine run against Postgres in production and an in-memory double in property-based tests.
  • Swapping the clock lets the team replay end-of-day batches for any historical date without changing engine code.
✅ Outcome: Time and storage are controllable seams, so audit scenarios and edge-of-day boundaries are tested exhaustively and reproducibly.
🚚

3 · Shipping label generation in logistics

Pattern: IoC container binding one carrier client per region

A fulfillment service generates labels through several carrier APIs, and the right carrier depends on destination and contract.

  • Each carrier client implements a common CarrierGateway interface, injected into the LabelService.
  • An IoC container binds the concrete carrier based on configuration, so new carriers are added without touching the service.
  • A fake carrier gateway returns canned tracking numbers so the label workflow is tested offline.
✅ Outcome: Onboarding a new carrier is a container binding plus one adapter class, with the core label logic untouched and fully tested.
07 - Relevance

Modern relevance

Dependency Injection is decades old, but the shape it takes keeps shifting with frameworks, languages, and testing culture.

🧰 Framework-native containers

Spring, NestJS, ASP.NET Core, and Angular ship IoC containers as the default composition mechanism, making constructor injection the standard way to assemble apps.

🪶 Container-free by hand

Many teams push back on magic and wire graphs in plain code at the composition root, keeping DI the pattern while dropping the heavyweight container.

🧩 Functional injection

Passing collaborators as function arguments or partial applications brings the same substitutability to code that is not built from classes.

⏱️ Deterministic testing

Injecting clocks, id generators, and random sources is now table stakes for reproducible tests and stable snapshots in CI.

🔒 Boundaries for security

Injecting a permission-aware repository or scoped credential provider keeps authorization decisions at the edges and testable in isolation.

🤖 Testing agentic and LLM code

Injecting the model client and tool gateways lets teams stub responses, so pipelines that call language models stay fast and deterministic under test.

Bottom line: whether you use a full container or wire three objects in main(), the discipline is the same: keep new out of business logic and hand classes their collaborators. That single habit is what makes large object-oriented systems configurable, swappable, and testable.
