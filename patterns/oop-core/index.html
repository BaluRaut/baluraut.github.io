OOP Foundation

The four pillars of OOP - the complete picture

Object-oriented programming rests on four ideas that work together: encapsulation guards state behind a clean interface, inheritance models shared behavior, polymorphism lets one call take many forms, and abstraction hides complexity behind simple contracts. Master how they combine and you design systems that stay flexible as they grow.

01 - What

What are the four pillars?

The four pillars of OOP are the core principles that turn "code that groups data and functions" into a discipline for managing complexity. Each pillar answers a different question: how do I protect state, how do I reuse behavior, how do I vary behavior, and how do I hide detail? Used together they let you model a domain in objects that are safe to change.

🔒 Encapsulation

Bundle data with the methods that operate on it and hide the internals. Callers touch a public interface, never the raw fields, so the object protects its own invariants.

🧬 Inheritance

Define a type in terms of another, modeling an is-a relationship. A subclass reuses and extends a base class, sharing structure and behavior.

🎭 Polymorphism

One interface, many implementations. The same call resolves to different behavior at runtime depending on the actual object's type.

The four pillars at a glance

Key mental model: the pillars are not four unrelated tricks. Abstraction decides what a type promises, encapsulation protects how it keeps that promise, inheritance and polymorphism let many types honor the same promise in different ways. They only pay off together.
02 - Why

Why the pillars exist

Software changes constantly, and unmanaged complexity is what kills a codebase. The pillars exist to localize change: keep data safe, isolate what varies, and let callers depend on stable contracts rather than volatile detail.

🛡️ Protect invariants

Encapsulation stops outside code from putting an object into an illegal state. A BankAccount can guarantee its balance never goes negative because only its own methods touch the field.

♻️ Reuse without copy-paste

Inheritance and composition let shared behavior live in one place. Fix a bug in the base type and every specialization benefits, instead of hunting duplicated logic.

🔌 Swap implementations freely

Polymorphism and abstraction let you add a new payment method or storage backend without touching the code that uses it. New behavior plugs in behind the same interface.

🧠 Tame complexity

Abstraction hides irrelevant detail so you reason about one layer at a time. You call list.sort() without knowing which algorithm runs underneath.

In Plain Terms

The four pillars explained with analogies

Same four ideas, four ways to picture them, so they click whoever you are.

🎓 For a student

Think of a vending machine. Encapsulation is the locked case around the coins and snacks; inheritance is that a snack machine and a drink machine are both vending machines; polymorphism is pressing "buy" and getting whatever that slot holds; abstraction is the button panel that hides all the motors inside.

👩‍💻 For a developer

An interface like List is the contract; ArrayList and LinkedList are implementations. You code against List (abstraction), the classes hide their arrays and nodes (encapsulation), share a parent contract (inheritance), and add() dispatches to the real type at runtime (polymorphism).

🏢 For a professional

A company org chart. Every Employee is a type; a Manager is-a Employee (inheritance). You ask any employee to "report status" and each does it their own way (polymorphism). Their private notes stay private (encapsulation), and you deal with them through a job title, not their inner workings (abstraction).

🚗 Everyday version

Driving a car. The steering wheel and pedals are the abstraction; the engine is sealed under the hood (encapsulation); a car is-a vehicle like a truck (inheritance); pressing the accelerator works on any car though each responds differently (polymorphism).

03 - How

How the pillars work under the hood

Structurally, the pillars show up as a hierarchy: an abstraction at the top (an interface or abstract class), concrete subclasses that encapsulate their own state, and callers that invoke them polymorphically through the shared type.

📐 Contracts and hierarchy

An interface declares what without any how. An abstract class can supply shared code plus abstract holes subclasses must fill. Concrete classes complete the contract and keep their fields private.

⚙️ Dynamic dispatch

When you call an overridden method through a base reference, the JVM looks up the actual object's method at runtime via its vtable. Overriding is resolved late; overloading is resolved at compile time by argument types.

A realistic example in Java

// Abstraction: the contract, no implementation
interface Shape {
    double area();
    String name();
}

// Inheritance + partial abstraction: shared code, one abstract hole
abstract class AbstractShape implements Shape {
    private final String label;          // encapsulated state

    protected AbstractShape(String label) {
        this.label = label;
    }

    @Override public String name() {     // reused by every subclass
        return label;
    }

    @Override public abstract double area();  // subclasses must fill this
}

final class Circle extends AbstractShape {
    private final double radius;         // hidden, validated in constructor

    Circle(double radius) {
        super("Circle");
        if (radius <= 0) throw new IllegalArgumentException("radius > 0");
        this.radius = radius;            // invariant: always positive
    }

    @Override public double area() {     // overriding = polymorphism
        return Math.PI * radius * radius;
    }
}

final class Rectangle extends AbstractShape {
    private final double width, height;

    Rectangle(double width, double height) {
        super("Rectangle");
        this.width = width;
        this.height = height;
    }

    @Override public double area() {
        return width * height;
    }
}

// Polymorphism in action: one loop, many concrete types
List<Shape> shapes = List.of(new Circle(2), new Rectangle(3, 4));
for (Shape s : shapes) {
    // dynamic dispatch picks the right area() at runtime
    System.out.printf("%s -> %.2f%n", s.name(), s.area());
}

Notice all four pillars in one snippet: Shape is the abstraction, the radius field is encapsulated behind a validating constructor, Circle extends AbstractShape is inheritance, and the loop calls area() polymorphically without knowing the concrete type.

05 - Step by Step

The 0 → 100 flow

From a raw requirement to a polymorphic, well-encapsulated design - the whole journey in order.

00
Model

Find the objects

Read the domain and name the nouns that own behavior: Account, Order, Shape. Each becomes a candidate class with responsibilities, not just a bag of data.

10
Abstract

Define the contract

Write the interface first: the methods callers need, with no implementation. This is the abstraction that hides every future how behind a stable what.

20
Encapsulate

Hide the state

Make fields private and expose behavior instead of raw data. Decide what invariants the object must always keep true.

30
Guard

Validate in the constructor

Reject illegal arguments up front so an object is never born in a broken state. A constructed object is a valid object.

40
Reuse

Lift shared code to a base

If several types share logic, put it in an abstract class with abstract holes for what varies. Prefer this only for a true is-a relationship.

50
Specialize

Implement concrete subclasses

Each subclass fills the abstract methods and keeps its own private fields. It honors the contract in its own way.

60
Override

Provide varying behavior

Override the base methods with @Override so the compiler checks the signature. This is where polymorphism gets its many forms.

70
Dispatch

Call through the abstraction

Client code holds a reference to the interface, not the concrete class. At runtime dynamic dispatch routes each call to the real type.

80
Substitute

Check Liskov safety

Any subclass must be usable wherever the base is expected without surprises. If a subclass breaks the base's promises, the hierarchy is wrong.

90
Extend

Add a new type, touch nothing

A new requirement becomes a new class implementing the interface. Existing callers keep working, proving the design is open for extension.

100
Combine

Four pillars, one flexible system

Abstraction sets the contract, encapsulation protects it, inheritance shares it, polymorphism varies it. Together they localize change to one place.

Common Pitfalls

Pitfalls & anti-patterns

The pillars are easy to misuse. These are the traps that turn OOP into a tangle instead of a tool.

🕳️ Leaky encapsulation

Getters and setters for every field, or returning a mutable internal list, expose state you meant to hide. Callers then depend on internals and invariants quietly break.

🏗️ Deep inheritance towers

Five-level class hierarchies become fragile: a change in a middle class ripples unpredictably. If you cannot say "X is-a Y" out loud, do not inherit.

🧨 Inheriting for reuse only

Extending a class just to grab its methods creates an is-a lie. A Stack extends Vector leaks Vector operations that violate stack behavior. Prefer composition.

🔀 Overriding vs overloading confusion

Same name, different parameters is overloading (compile-time, not polymorphism). Forgetting @Override can silently create an overload that never dispatches.

🎪 Anemic domain model

Classes that are pure data holders with all logic elsewhere throw away encapsulation. Behavior belongs with the data it protects, not in a distant service.

🧩 Over-abstraction

An interface with a single implementation, wrapped in factories you will never swap, adds indirection with no payoff. Abstract the variation you actually have.

Trade-offs

Trade-offs & when to use

The pillars are powerful but not free. Reach for them where variation and change are real, and keep it flat where they are not.

AspectDetail
ProsLocalizes change, protects invariants, enables reuse, and lets you add behavior by adding types instead of editing callers.
ConsIndirection can obscure control flow, deep hierarchies get fragile, and dynamic dispatch adds a small runtime cost and harder-to-trace stacks.
Use whenYou have genuine variation behind a common contract, invariants worth protecting, or types that truly share an is-a relationship.
Avoid whenThe problem is a simple script or data transform, there is only one implementation, or you are inheriting purely to reuse code.
ComplexityLow to add one interface and a class; grows fast with hierarchy depth. Favor shallow trees and composition to keep it manageable.
RelatedSOLID principles, composition over inheritance, UML relationships, and the Strategy pattern all build directly on these pillars.
Rule of thumb: favor composition over inheritance, program to interfaces not implementations, and only inherit for a real is-a. If a pillar is not solving a concrete change or variation problem, you are adding ceremony, not design.
06 - Case Studies

Real-world case studies

Three places the four pillars quietly hold up software you use every day.

🗂️

1 · The Java Collections Framework

Pattern: abstraction plus polymorphism at scale

The standard library exposes List, Set, and Map as interfaces with many implementations behind them.

  • You code against List, so swapping ArrayList for LinkedList changes nothing for callers.
  • Each class encapsulates its own storage - an array, a node chain, a hash table - fully hidden.
  • Collections.sort(list) dispatches polymorphically to whatever list you pass in.
✅ Outcome: Millions of programs share one stable interface while implementations evolve, because abstraction and polymorphism decouple use from detail.
💳

2 · A payment gateway integration

Pattern: encapsulation plus the Strategy pattern

A checkout service must support cards, wallets, and bank transfers without branching logic spreading everywhere.

  • A PaymentMethod interface defines authorize() and capture(); each provider implements it.
  • Provider classes encapsulate their own API keys and retry rules behind the interface.
  • Adding a new provider is a new class, so the order flow never changes.
✅ Outcome: New payment types ship without touching checkout, because variation is encapsulated behind one polymorphic contract.
🎮

3 · A game entity hierarchy

Pattern: inheritance with a template method

A game engine has many entities - players, enemies, projectiles - that share an update-and-render loop.

  • An abstract Entity fixes the tick skeleton and leaves update() and render() abstract.
  • Each subclass overrides only the behavior that differs, reusing the shared loop.
  • The engine iterates a List<Entity> and calls tick() polymorphically on every object.
✅ Outcome: One loop drives hundreds of entity types, because inheritance shares the skeleton and polymorphism fills in the specifics.
07 - Relevance

Modern relevance

The pillars are decades old, but modern languages and styles refine rather than replace them - and often lean harder on the ideas underneath.

🧱 Composition over inheritance

Modern guidance favors assembling behavior from small parts over deep class trees. The pillar that survives is encapsulation, wired together by composition.

🔗 Interfaces as the primary tool

Go, Rust traits, and TypeScript push interface-based polymorphism without classical inheritance, showing abstraction is the durable idea.

🧾 Records and immutability

Java records and data classes make encapsulated, immutable values cheap, so invariants hold by construction and never mutate into a bad state.

🎯 Sealed types and pattern matching

Sealed hierarchies plus switch patterns give exhaustive, type-safe polymorphism, a modern complement to virtual dispatch.

🧩 Functional and OO blend

Higher-order functions are polymorphism by another name. Mixing lambdas with objects is now idiomatic, not a contradiction.

🏛️ Domain-driven design

DDD leans on rich, encapsulated aggregates that protect invariants - the first pillar, elevated to an architectural principle.

Bottom line: the four pillars are not a style you can outgrow, they are the vocabulary of managing change. Newer tools shift the emphasis toward encapsulation, abstraction, and composition, but the core insight - hide detail, isolate variation, program to contracts - is more relevant than ever.
