Law of Demeter - फक्त आपल्या थेट सहकाऱ्यांशीच बोला

Law of Demeter सांगते की एखाद्या object ने फक्त स्वतःवर, स्वतःच्या fields वर, त्याला दिलेल्या arguments वर, आणि तो स्वतः तयार करतो त्या objects वरच methods कॉल कराव्यात. एका object मधून आरपार पोहोचून दुसऱ्या object ला खटकावणे यावर ती बंदी घालते, त्यामुळे तुम्ही order.getCustomer().getAddress().getCity() सारख्या train wreck साखळ्या लिहिणे थांबवता. त्याऐवजी तुम्ही ती फेरी लपवणारी एक method जोडता, जी Tell Don't Ask मागची तीच प्रेरणा आहे.

01 - काय

Law of Demeter म्हणजे काय?

Law of Demeter (LoD), ज्याला principle of least knowledge असेही म्हणतात, हे objects मधील coupling कमी करण्यासाठीचे एक design मार्गदर्शक तत्त्व आहे. एका method ने फक्त जवळच्या मोजक्या objects लाच संदेश पाठवावेत: स्वतःला, स्वतःच्या fields ला, तिला दिलेल्या arguments ला, आणि ती स्थानिकरित्या तयार करते त्या objects ला. जिच्याशी तिची कधी ओळखच करून दिली नाही अशा अनोळखी object ला आदेश देण्यासाठी तिने getters च्या साखळीतून आरपार पोहोचू नये.

🤝 मित्रांशी बोला

स्वतःच्या fields वर आणि आपल्या arguments वर methods कॉल करा. हे तेच सहकारी आहेत जे तुम्हाला स्पष्टपणे दिले गेले, त्यामुळे त्यांच्यावर अवलंबून राहणे योग्य आहे.

🚫 अनोळखींशी नको

आपल्या मित्रांनी परत केलेल्या objects वर methods कॉल करू नका. एका customer च्या address आतील city हा तुम्हाला कधीही न दिलेला अनोळखी आहे.

🧱 फेरी लपवा

जेव्हा तुम्हाला graph मध्ये खोलवरचे काहीतरी हवे असते, तेव्हा जवळच्या object वर ते तुमच्यासाठी आणून देणारी method जोडा, जेणेकरून navigation एकाच ठिकाणी राहील.

एका method ला काय कॉल करण्याची परवानगी आहे

परवानगी असलेले लक्ष्यते का योग्य आहेE-commerce उदाहरण
स्वतःत्याच object वरील private helpers हे अंतर्गत तपशील असतातthis.calculateSubtotal()
स्वतःच्या fieldsobject धरून ठेवतो आणि मालकी असलेले थेट सहकारीthis.customer.notify(...)
Method argumentsदिलेले objects हे घोषित dependencies असतातgateway.charge(amount)
तो तयार करतो ते objectsस्थानिकरित्या बनवलेले instances पूर्णपणे ज्ञात असतातnew Receipt(order).render()
Return values नाहीgetter ने परत केलेला अनोळखी internals बाहेर काढतोorder.getCustomer().getAddress()
मुख्य मानसिक प्रतिमा: object च्या सीमा ओलांडणारे dots मोजा, स्वतःच्या object वरील dots नाही. this.a.b.c() तुम्हाला हे माहीत असणे भाग पाडते की a ला एक b आहे आणि b ला एक c आहे. Law of Demeter सांगते: a ला अंतिम निकाल विचारा आणि त्याला स्वतःचा आकार private ठेवू द्या.
02 - का

Law of Demeter का अस्तित्वात आहे

object च्या सीमा ओलांडणारा प्रत्येक dot हा एक असा तथ्य आहे ज्यावर आता तुमचा कोड अवलंबून आहे. train-wreck साखळी object graph चा संपूर्ण आकार अशा caller मध्ये कायमचा जोडून टाकते ज्याला त्याची पर्वा असू नये, त्यामुळे एका class मधील छोटासा refactor तीन class दूर असलेल्या callers ना तोडतो.

🔗 coupling कमी करते

फक्त आपल्या थेट सहकाऱ्यांशी संपर्क करणारा caller Customer किंवा Address च्या अंतर्गत रचनेवर अवलंबून नसतो. त्यांच्यातून चालणारी प्रत्येक साखळी शोधल्याशिवाय तुम्ही त्यांची पुनर्रचना करू शकता.

🛡️ बदल स्थानिक ठेवते

जेव्हा shipping चे नियम Address मधून नव्या Region object कडे सरकतात, तेव्हा फक्त navigation लपवणारी method बदलते. ती वापरणारी डझनभर call sites अस्पर्श राहतात.

🔒 encapsulation रक्षण करते

जिवंत अंतर्गत objects परत करणारे getters उघड केल्याने callers ना तुमचे private भाग नियंत्रित करण्याचे आमंत्रण मिळते. navigation लपवल्याने प्रत्येक object स्वतःच्या data आणि invariants चा प्रभारी राहतो.

🧪 testing सोपे करते

दोन थेट सहकारी असलेल्या method ला दोन stubs लागतात. train wreck साठी फक्त एका branch ची चाचणी करण्यासाठी तुम्हाला संपूर्ण graph - customer, address, region - बांधावा लागतो.

सोप्या शब्दांत

उपमांसह समजावलेली Law of Demeter

तीच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असलात तरी ती लक्षात येते.

🎓 विद्यार्थ्यासाठी

हा फक्त आपल्या मित्रांशी बोला हा नियम आहे. तुम्ही आपल्या मित्राला प्रश्न विचारू शकता; पण तुम्ही मित्राच्या पिशवीत हात घालून त्याचा फोन काढून त्याच्या contacts ना message करू नये. मित्राला विचारा, आणि त्याला स्वतःच्या गोष्टी हाताळू द्या.

👩‍💻 developer साठी

object च्या सीमा ओलांडणारे dots मोजा. a.b().c().d() म्हणजे तुमच्या कोडला दुसऱ्याच्या रचनेचे तीन स्तर माहीत आहेत. a वर तुम्हाला जे खरोखर हवे ते परत करणारी एक method जोडा, आणि साखळी a.thing() इतकी कोसळते.

🏢 व्यावसायिकासाठी

एक chain of command ची कल्पना करा. तुम्ही आपल्या थेट अधिकाऱ्याला माहिती देता आणि ते त्यांच्या अधिकाऱ्याला देतात. तुम्ही कधीही न भेटलेल्या कनिष्ठाला आदेश देण्यासाठी तीन managers ला ओलांडून जात नाही; ते जबाबदारी वगळते आणि org chart बदलल्यावर मोडते.

🐶 रोजची आवृत्ती

कुत्र्याला फिरवण्यासाठी तुम्ही कुत्र्याला चालायला सांगता; तुम्ही आत हात घालून त्याचे प्रत्येक पाय हलवत नाही. तुम्ही जवळच्या जबाबदार गोष्टीला आदेश देता आणि आतील गोष्टींचे समन्वय करण्यावर तिच्यावर विश्वास ठेवता.

03 - कसे

आत ते कसे कार्य करते

उपाय जवळजवळ नेहमीच सारख्याच आकाराचा असतो: एक caller getters ची साखळी चालवत होता, म्हणून तुम्ही साखळीच्या सुरुवातीची मालकी असलेल्या object कडे एक method खाली ढकलता. caller अंतिम निकाल विचारतो आणि मधली रचना कधीच शिकत नाही.

🚂 train wreck ओळखा

objects ओलांडणाऱ्या getters च्या साखळ्या शोधा: order.getCustomer().getAddress().getCity(). प्रत्येक getter एक अनोळखी परत करतो, आणि पुढील कॉल त्याच्याशी बोलतो. ते एका ओळीत लपवलेल्या तीन dependencies आहेत.

🔧 navigation लपवा

साखळी आतल्या आत चालवणारी order.shippingCity() जोडा, किंवा त्याहून चांगले, order.ship(courier) ने order ला काम करायला सांगा. caller आता फक्त Order वर अवलंबून असतो.

objects आणि त्यांचे सहकारी

Order ची मालकी एका Customer वर, ज्याची मालकी एका Address वर. caller ला फक्त Order दिसावा.

// TRAIN WRECK: the caller walks the whole object graph.
// It must know Order has a Customer, Customer has an Address,
// and Address has a city. Three couplings in one line.
function labelForShipping(order: Order): string {
  const city = order.getCustomer().getAddress().getCity();
  const zip  = order.getCustomer().getAddress().getPostcode();
  return `${city} ${zip}`;
}

प्रत्येक object फक्त त्याच्याकडे आधीच मालकी असलेल्या field ला delegate करतो, त्यामुळे कोणतीही method कधीही परत केलेल्या अनोळखीमधून कॉल करत नाही. ज्ञानाची साखळी छोट्या, स्थानिक delegations च्या साखळीत मोडली जाते, आणि caller अगदी एकाच type वर अवलंबून राहतो.

आणखी चांगले: Tell, do not Ask

shippingLabel() मागे getter साखळी लपवल्याने coupling दूर होते, पण तुम्ही अजूनही data बाहेर काढून तो दुसरीकडे वापरत असता. अधिक जोरदार चाल म्हणजे object ला संपूर्ण काम करायला सांगणे, जेणेकरून behavior त्याला लागणाऱ्या data सोबतच राहील.

// ASKING: pull data across boundaries, then decide outside.
const city = order.getCustomer().getAddress().getCity();
const fee  = rateTable.lookup(city);
courier.dispatch(order, fee);

// TELLING: hand the order a courier and let it coordinate.
class Order {
  constructor(private readonly customer: Customer,
              private readonly items: LineItem[]) {}

  ship(courier: Courier, rates: RateTable): Shipment {
    const fee = this.customer.shippingFee(rates); // Customer knows its address
    return courier.dispatch(this, fee);           // courier is an argument
  }
}

// Caller: one message, no navigation, no leaked internals.
order.ship(courier, rates);
# ASKING: pull data across boundaries, then decide outside.
city = order.get_customer().get_address().get_city()
fee = rate_table.lookup(city)
courier.dispatch(order, fee)

# TELLING: hand the order a courier and let it coordinate.
class Order:
    def __init__(self, customer, items):
        self._customer = customer
        self._items = items

    def ship(self, courier, rates):
        fee = self._customer.shipping_fee(rates)  # Customer knows its address
        return courier.dispatch(self, fee)        # courier is an argument

  end

  end
end

Law of Demeter आणि Tell Don't Ask एकाच दिशेने ढकलतात: behavior ला ते ज्या data ला स्पर्श करते त्याच्या शेजारी ठेवा. Demeter फेरीवर बंदी घालते; Tell Don't Ask तुम्हाला मुळात फिरायची इच्छा का झाली ते कारणच काढून टाकते.

एका वेळी एक टप्पा delegate करा

Order त्याच्या customer ला विचारतो; Customer त्याच्या address ला विचारतो. प्रत्येक object फक्त त्याच्या मालकीच्या field ला स्पर्श करतो, त्यामुळे कोणत्याही अनोळखीला कधीच कॉल होत नाही.

पूर्ण

सामान्य अडचणी

अडचणी आणि anti-patterns

Law of Demeter सांगायला सोपी आहे आणि अती-लागू करायलाही सोपी आहे. दोन्ही बाजूंच्या या सापळे आहेत.

🚂 train-wreck साखळ्या

नमुनेदार smell: invoice.getAccount().getOwner().getEmail().send(). प्रत्येक dot caller ला रचनेच्या आणखी एका स्तराशी बांधतो, त्यामुळे चारपैकी कोणतीही class ती तोडू शकते.

🕳️ getter चा स्फोट

getCustomerAddressCity(), getCustomerAddressZip() वगैरे जोडून नियमाचे अक्षरशः पालन केल्याने coupling फक्त हलवली जाते आणि जवळचा object दुसऱ्याच्या data ने फुगतो.

📤 internals बाहेर काढणे

getAddress() मधून जिवंत Address परत केल्याने callers ना order ची आतडी बदलण्याची मुभा मिळते. साखळी हे लक्षण आहे; उघड झालेला अंतर्गत object हा आजार आहे.

🧩 मध्यस्थ objects

Demeter अती-लागू केल्याने फक्त कॉल पुढे पाठवण्याखेरीज काहीच न करणाऱ्या classes तयार होऊ शकतात. एखादा object फक्त delegate करत असेल आणि कोणतेही behavior जोडत नसेल, तर त्याला अस्तित्वाचा हक्क नसावा.

🔍 fluent APIs चुकीने मोजणे

query.where(...).order(...).limit(10) हे त्याच builder वर साखळी करतात, this परत करत. ते Demeter उल्लंघन नाही; फक्त वेगवेगळ्या objects वरील साखळ्याच मोजल्या जातात.

📦 नियमात अडकलेल्या data structures

साध्या DTO किंवा parse केलेल्या JSON tree मधून चालणे ठीक आहे; तिथे रक्षण करण्यासारखे behavior किंवा invariant नाही. मूर्ख data bags ला LoD लागू केल्याने काहीही फायदा न होता विधी वाढतात.

संकेत आणि मापके

संकेत आणि कसे मोजावे

coupling वर एकच आकडा लावता येत नाही, पण codebase भर Demeter पाळली जात आहे का हे हे संकेत सांगतात.

संकेततो तुम्हाला काय सांगतो
प्रति method getter साखळ्यादोन किंवा अधिक cross-object getters च्या साखळ्या संभाव्य उल्लंघने दर्शवतात; get नंतर ().get साठी linter किंवा grep त्या पटकन समोर आणतो.
प्रति file import केलेले typesएक काम करण्यासाठी ज्या caller ला Order, Customer, आणि Address import करावे लागतात तो फक्त त्याच्या सहकाऱ्याशी नव्हे तर संपूर्ण graph शी coupled असतो.
rename चा blast radiusएका खोलवरच्या field ला rename करा आणि किती files तुटतात मोजा. जास्त आकडे म्हणजे रचना साखळ्यांतून दूरच्या callers पर्यंत गळली आहे.
test मध्ये बांधलेले objectsएका method ची चाचणी करण्यासाठी stubs चा संपूर्ण graph लागत असेल, तर ती method स्पर्श न करावयाच्या objects मधून आरपार पोहोचत आहे.
tell आणि ask चे गुणोत्तरdata बाहेर काढून दुसरीकडे निर्णय घेणाऱ्या अनेक methods Ask-प्रधान कोड दर्शवतात; behavior data च्या जवळ असले पाहिजे.
pass-through getter ची संख्याफक्त आतल्या object कडे पुढे पाठवणाऱ्या getters मध्ये वाढ हे सूचित करते की तुम्ही एक साखळी पातळ accessors च्या ढिगाशी अदलाबदल केली आहे.
ढोबळ नियम: एखादी एकच ओळ वाचकाला इतर दोन किंवा अधिक classes चा अंतर्गत आकार शिकायला भाग पाडत असेल, तर ते तांत्रिकदृष्ट्या compile आणि run होत असले तरी लपवण्यासारखे Demeter उल्लंघन आहे.
06 - उदाहरण अभ्यास

वास्तविक जगातील उदाहरण अभ्यास

तीन प्रातिनिधिक परिस्थिती जिथे Law of Demeter पाळल्याने एखादी system बदलाला कशी तोंड देते ते बदलले.

🛒

1 · e-commerce platform मधील checkout service

Pattern: order-ते-address navigation लपवा

एका checkout service ने tax आणि rate table निवडण्यासाठी डझनभर ठिकाणी order.getCustomer().getAddress().getCountry() चालवून shipping मोजले.

  • billing आणि shipping addresses वेगळे केल्याने customer कडे एकच address राहिला नाही, आणि प्रत्येक साखळी एकाच वेळी तुटली.
  • उपायाने order.shippingDestination() आणि order.shippingFee(rates) जोडले, फेरी order च्या आत हलवली.
  • country आता order आतल्या आत जुळवणाऱ्या Destination value object मधून येतो, callers ना अदृश्य.
✅ निकाल: address विभाजनाने चाळीस call sites ऐवजी Order वरील तीन methods ना स्पर्श केला, आणि checkout कोड फक्त Order वर अवलंबून आहे.
💳

2 · subscriptions product मधील payments module

Pattern: account ला charge करायला सांगा, त्याचे card मागू नका

एका billing job ने subscription.getAccount().getDefaultCard().getToken() वाचून token gateway ला दिला, त्यामुळे card चे ज्ञान सर्वत्र पसरले.

  • कच्चे token आत जाऊन मिळवल्याने PCI-संवेदनशील तपशील असंबंधित billing कोडमध्ये गळला.
  • team ने साखळी account.charge(amount, gateway) ने बदलली, त्यामुळे account स्वतःची payment पद्धत निवडतो.
  • retry logic आणि card fallback account च्या आत हलले, जिथे ते निर्णय घेण्यासाठीचा data आधीच होता.
✅ निकाल: card तपशील codebase मधून प्रवास करणे थांबले, आणि backup-card fallback जोडणे हा एका class चा बदल होता.
📦

3 · logistics system मधील warehouse fulfillment

Pattern: inventory आणि bins मधून जाणारा train wreck दुरुस्त करा

एका picker screen ने stock दाखवण्यासाठी shipment.getWarehouse().getZone().getBin().getQuantity() कॉल केला, ज्याने UI ला storage पदानुक्रमाशी coupled केले.

  • जेव्हा zones ला dynamic pick paths ने बदलले, तेव्हा संपूर्ण picking UI compile होणे थांबले.
  • refactor ने shipment.availableStock(sku) उघड केले, ज्याने shipment ला location आतल्या आत सोडवू दिले.
  • storage layout हा एक private तपशील बनला जो fulfillment domain आपल्या मर्जीने पुनर्रचित करू शकत होता.
✅ निकाल: zones ला pick paths ने बदलणे UI ला अदृश्य होते, आणि stock lookups एका स्थिर method मधून गेले.
07 - सुसंगतता

आधुनिक सुसंगतता

Law of Demeter आजच्या बहुतांश stacks च्या आधीची आहे, तरीही least-knowledge कल्पना आधुनिक systems जिथे जिथे loosely coupled राहण्याचा प्रयत्न करतात तिथे सर्वत्र दिसते.

🧭 Domain-driven design

Aggregates मोठ्या प्रमाणावर Demeter लागू करतात: बाहेरचा कोड aggregate root शी बोलतो, त्याच्या आत दडलेल्या entities शी कधीच नाही. root स्वतःची navigation लपवतो.

🔌 Microservice सीमा

network पातळीवर तीच प्रेरणा: एक service callers ना त्याच्या अंतर्गत data model मधून wire वरून फिरू देण्याऐवजी हेतू-आकाराचा endpoint उघड करते.

🧱 Hexagonal architecture

Ports behavior उघड करतात, अंतर्गत objects नाही, त्यामुळे adapters domain च्या आकाराबद्दल अनभिज्ञ राहतात. ते संपूर्ण layers ना लागू केलेली Demeter आहे.

⚛️ UIs मधील component props

संपूर्ण model एका component tree मध्ये खोलवर पास केल्याने view मध्ये train wrecks पुन्हा तयार होतात. component ला लागणारी विशिष्ट मूल्ये किंवा callbacks पास केल्याने ते decoupled राहते.

🧪 Test doubles आणि mocks

"तुमच्या मालकीचे नसलेले mock करू नका," आणि खोल stub साखळ्यांचा त्रास, दोन्ही designs ना थेट सहकारी आणि पातळ surfaces कडे ढकलतात.

🤖 GraphQL आणि API design

जिथे clients एका graph मधून फिरतात तिथेही, चांगल्या रचलेल्या resolvers हेतू-पातळीवरील fields उघड करतात जेणेकरून consumers storage आकार कायमचा जोडत नाहीत.

सारांश: Law of Demeter म्हणजे dots मोजणे हा स्वतःसाठीचा हेतू नाही. ती एक आठवण आहे की behavior त्याच्या data सोबत राहावे, आणि तुम्ही ओलांडता ती प्रत्येक सीमा म्हणजे एक coupling आहे जिची किंमत design बदलल्यावर तुम्ही मोजाल.
