Tell, Don't Ask - ऑब्जेक्टना त्यांच्या स्वतःच्या डेटावर कृती करू द्या

एखाद्या ऑब्जेक्टची स्थिती बाहेर काढून, निर्णय घेऊन, आणि बदल परत आत ढकलण्याऐवजी, तुम्ही ऑब्जेक्टला तुम्हाला काय हवे ते सांगता आणि कसे ते त्याला ठरवू देता. वर्तन ज्या डेटाची त्याला गरज असते त्याच्या शेजारी राहते. सार्वजनिक getter वरील एका टिप्पणीऐवजी encapsulation खरे राहते ते हेच.

01 - काय

Tell, Don't Ask म्हणजे काय?

Tell, Don't Ask हे एक डिझाइन मार्गदर्शक तत्त्व आहे: एखाद्या ऑब्जेक्टला त्याची अंतर्गत स्थिती विचारून मग त्याच्यावतीने निर्णय घेण्याऐवजी, तुम्ही ऑब्जेक्टला काय करायचे ते सांगावे आणि त्याला त्याचे स्वतःचे नियम लागू करू द्यावेत. जो caller account.getBalance() वाचतो, तपासतो, आणि मग नवीन balance सेट करतो, त्याने Account च्या आत असावी अशी जबाबदारी घेतली आहे. यावर उपाय म्हणजे एकच command, account.withdraw(amount), जी जिथे डेटा राहतो तिथेच नियम लागू करते.

📤 एक command पाठवा

फील्ड्स आणून ऑब्जेक्टच्या बाहेर निकाल मोजण्याऐवजी हेतू व्यक्त करणारी एखादी method कॉल करा, जसे cart.applyDiscount(code).

🧲 डेटाच्या शेजारी वर्तन

ज्या logic ला एखाद्या फील्डची गरज असते ते त्या फील्डच्या मालक class मध्ये राहावे. निर्णय जिथे स्थिती आधीच आहे तिथे जातात, उलट नाही.

🛡️ Encapsulation, अंमलात

जेव्हा callers आत पोहोचून स्थिती बदलू शकत नाहीत, तेव्हा ऑब्जेक्ट प्रत्येक संक्रमण नियंत्रित करतो. आत जाण्यासाठी फक्त एकच दार असल्याने invariants टिकतात.

02 - का

Tell, Don't Ask का अस्तित्वात आहे

जेव्हा callers ऑब्जेक्टच्या उघड केलेल्या स्थितीवरून निर्णय घेतात, तेव्हा ऑब्जेक्ट फक्त डेटाची पिशवी बनतो आणि खरी logic services व controllers मध्ये गळते. Telling प्रत्येक नियम एकाच ठिकाणी ठेवते, म्हणून प्रणाली वाढत असतानाही सुसंगत राहते.

🔒 Invariants चे रक्षण करते

एक account withdraw मध्ये overdraft नाकारू शकते. जर त्याऐवजी प्रत्येक caller balance वाचून वजा करत असेल, तर एक विसरलेली तपासणी account जास्त काढते.

🧹 डुप्लिकेशन काढून टाकते

Cart ने अंमलात आणलेला एक discount नियम एकदाच दिसतो. तोच नियम checkout, admin, आणि API endpoints मध्ये कॉपी केला तर वेगाने विसंगत होतो.

🧭 बदल स्थानिक करते

जेव्हा withdrawal धोरण बदलते, तेव्हा तुम्ही एकच method संपादित करता. Ask-then-act तुम्हाला balance ला स्पर्श करणारी प्रत्येक शाखा शोधून अद्ययावत करण्यास भाग पाडते.

🧠 हेतू उघड करते

order.markShipped() हे एका व्यावसायिक कृतीसारखे वाचते. Getters आणि setters ची मालिका plumbing सारखी वाचते आणि कोड काय करू पाहत आहे ते लपवते.

सोप्या शब्दांत

उपमांसह समजावलेले Tell, Don't Ask

तीच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

तुम्ही ग्रंथपालाला सांगता "माझ्यासाठी हे पुस्तक चेक आउट करा." तुम्ही शेल्फची स्थिती, कर्जाचे नियम, आणि शिक्का मागत नाही जेणेकरून तुम्ही स्वतः वहीखाते अद्ययावत करू शकाल. ते नियम ग्रंथपालाच्या मालकीचे आहेत.

👩‍💻 डेव्हलपरसाठी

if (account.balance >= amount) account.balance -= amount पेक्षा account.withdraw(amount) पसंत करा. दुसरी आवृत्ती overdraft नियम प्रत्येक call site वर विखुरते आणि encapsulation मोडते.

🏢 व्यावसायिकासाठी

तुम्ही तज्ज्ञाकडे सोपवता: तुम्ही finance ला refund प्रक्रिया करण्यास सांगता. तुम्ही त्यांची spreadsheet मागत नाही, स्वतः धोरण लागू करत नाही, आणि संपादित आकडे परत देत नाही. त्यांच्या डेटाला स्पर्श करणारा निर्णय त्यांच्या मालकीचा आहे.

🍽️ रोजच्या जीवनातील आवृत्ती

रेस्टॉरंटमध्ये तुम्ही पदार्थाची ऑर्डर देता; तुम्ही स्वयंपाकघरात जाऊन, कोठारगृह वाचून, स्वतः शिजवत नाही. तुम्ही हेतू सांगता आणि साहित्याची मालकी असलेले स्वयंपाकघर कसे ते ठरवते.

03 - कसे

ते आत कसे काम करते

ही हालचाल यांत्रिक आहे: जिथे एखादा caller ऑब्जेक्टची स्थिती वाचतो, निर्णय घेतो, मग स्थिती परत लिहितो अशी जागा शोधा. संपूर्ण निर्णय त्या ऑब्जेक्टवरील एका method मध्ये ढकला आणि फक्त हेतू उघड करा.

🔎 Ask-then-act ओळखा

एक getter, त्याच्या निकालावरील एक शाखा, आणि त्यानंतर येणारा setter किंवा फील्ड बदल शोधा. ती त्रयी हा ऑब्जेक्टच्या आत असावा असा निर्णय आहे.

🚚 निर्णय आत हलवा

एक command method जोडा जी हेतू arguments म्हणून घेते, खाजगी स्थितीवर नियम चालवते, आणि एकतर यशस्वी होते किंवा raise करते. फक्त निर्णयाला पुरवणारे getters हटवा.

Ask-then-act विरुद्ध tell, तीन भाषा

// ASK-THEN-ACT: the caller reads state and decides. The overdraft
// rule now lives outside Account and must be repeated everywhere.
if (account.getBalance() >= amount) {
  account.setBalance(account.getBalance() - amount);
} else {
  throw new Error("Insufficient funds");
}

// TELL: send a command; Account owns balance and the rule.
class Account {
  constructor(
    private balance: number,
    private readonly overdraftLimit = 0,
  ) {}

  withdraw(amount: number): void {
    if (amount <= 0) throw new Error("Amount must be positive");
    if (this.balance - amount < -this.overdraftLimit) {
      throw new Error("Insufficient funds");
    }
    this.balance -= amount;
  }

  deposit(amount: number): void {
    if (amount <= 0) throw new Error("Amount must be positive");
    this.balance += amount;
  }

  // A legitimate ASK: a read-only query for reporting, not a decision.
  get available(): number {
    return this.balance + this.overdraftLimit;
  }
}

const account = new Account(100);
account.withdraw(30);   // tell it what to do
account.deposit(50);
console.log(account.available); // 120 - asking is fine for a report

    @balance = balance
    @overdraft_limit = overdraft_limit

    raise ArgumentError, "Amount must be positive" if amount <= 0
    raise "Insufficient funds" if @balance - amount < -@overdraft_limit

लक्षात घ्या की withdrawal नियम अगदी एकदाच, withdraw च्या आत दिसतो, आणि callers कधीही balance ला थेट स्पर्श करत नाहीत. available query अजूनही परवानगी आहे कारण ती फक्त अहवाल देते; account ने स्वतःशी काय करावे हे ती ठरवत नाही.

दुसरे प्रकरण: स्वतःचा discount लागू करणारे cart

// TELL: the cart owns its lines and the discount policy.
class Cart {
  private lines: { price: number; qty: number }[] = [];
  private discountPct = 0;

  add(price: number, qty: number): void {
    this.lines.push({ price, qty });
  }

  applyCoupon(code: string): void {
    // The cart decides whether the coupon is valid for its contents.
    if (code === "SAVE10" && this.subtotal() >= 50) {
      this.discountPct = 10;
    } else {
      throw new Error("Coupon not applicable");
    }
  }

  total(): number {
    return this.subtotal() * (1 - this.discountPct / 100);
  }

  private subtotal(): number {
    return this.lines.reduce((s, l) => s + l.price * l.qty, 0);
  }
}

const cart = new Cart();
cart.add(30, 2);          // tell it to hold items
cart.applyCoupon("SAVE10"); // tell it to apply the coupon
console.log(cart.total());  // 54
# TELL: the cart owns its lines and the discount policy.
class Cart:
    def __init__(self) -> None:
        self._lines: list[tuple[float, int]] = []
        self._discount_pct = 0

    def add(self, price: float, qty: int) -> None:
        self._lines.append((price, qty))

    def apply_coupon(self, code: str) -> None:
        # The cart decides whether the coupon is valid for its contents.
        if code == "SAVE10" and self._subtotal() >= 50:
            self._discount_pct = 10
        else:
            raise ValueError("Coupon not applicable")

    def total(self) -> float:
        return self._subtotal() * (1 - self._discount_pct / 100)

    def _subtotal(self) -> float:
        return sum(price * qty for price, qty in self._lines)

# TELL: the cart owns its lines and the discount policy.
class Cart
  def initialize
    @lines = []
    @discount_pct = 0
  end

  def add(price, qty)
    @lines << [price, qty]
  end

  def apply_coupon(code)
    # The cart decides whether the coupon is valid for its contents.
    if code == "SAVE10" && subtotal >= 50
      @discount_pct = 10
    else
      raise "Coupon not applicable"
    end
  end

  def total
    subtotal * (1 - @discount_pct / 100.0)
  end

  private

  def subtotal
    @lines.sum { |price, qty| price * qty }
  end
end

cart.apply_coupon("SAVE10") # tell it to apply the coupon
puts cart.total           # 54

पात्रता मोजण्यासाठी caller कधीही line items वाचत नाही. तो cart ला coupon लागू करण्यास सांगतो, आणि items व धोरण या दोन्हींची मालकी असलेले cart ठरवते. नियम हलवा आणि कोणतेही call site बदलत नाही.

04 - अनुक्रम आकृत्या

सविस्तर अनुक्रम आकृत्या

तीन दृश्ये: ask-then-act anti-pattern, त्याच withdrawal ची tell आवृत्ती, आणि दोन accounts ना सांगणारा एक transfer.

आकृती 1 - Ask-then-act: caller स्थिती खेचतो आणि ठरवतो (दुर्गंध)
sequenceDiagram
    autonumber
    participant C as 🧾 Caller
    participant A as 🏦 Account

    C->>A: getBalance()
    A-->>C: 100
    C->>C: balance >= amount ?
    alt enough funds
        C->>A: setBalance(70)
        A-->>C: ok
    else not enough
        C->>C: throw Insufficient funds
    end
    Note over C,A: the overdraft rule lives in the caller, not the account
आकृती 2 - Tell: एक command, account त्याचा स्वतःचा नियम अंमलात आणतो
sequenceDiagram
    autonumber
    participant C as 🧾 Caller
    participant A as 🏦 Account

    C->>A: withdraw(30)
    A->>A: check amount and overdraft limit
    alt rule satisfied
        A->>A: balance -= 30
        A-->>C: ok
    else rule violated
        A-->>C: raise InsufficientFundsError
    end
    Note over C,A: balance never leaves the account; the rule lives with the data
आकृती 3 - Transfer: एक service दोन accounts ना सांगते, स्वतः काहीही ठरवत नाही
sequenceDiagram
    autonumber
    participant S as 🔁 TransferService
    participant F as 🏦 From account
    participant T as 🏦 To account

    S->>F: withdraw(amount)
    alt withdrawal allowed
        F-->>S: ok
        S->>T: deposit(amount)
        T-->>S: ok
        S-->>S: commit
    else withdrawal refused
        F-->>S: raise InsufficientFundsError
        S-->>S: abort, nothing moved
    end
    Note over S,T: the service coordinates commands but owns no balance rule

शाखेची अट आणि बदल method मध्ये कॉपी करा, आता getters मार्फत नव्हे तर थेट खाजगी स्थिती वाचून व लिहून.

40
रक्षण

Invariant अंमलात आणा

Method च्या शीर्षस्थानी inputs तपासा आणि बेकायदेशीर संक्रमणे नाकारा, जेणेकरून ऑब्जेक्ट कधीही वाईट स्थितीत राहू शकणार नाही.

50
बदला

Call sites बदला

प्रत्येक caller ला read-decide-write वरून नवीन command च्या एकाच कॉलमध्ये बदला. शाखा caller मधून नाहीशी होते.

60
छाटा

अनावश्यक getters आणि setters काढा

फक्त जुन्या निर्णयाला पुरवण्यासाठी अस्तित्वात असलेले accessors हटवा. स्थिती पुन्हा खाजगी बनते आणि पृष्ठभाग आकुंचन पावतो.

70
ठेवा

योग्य queries ठेवा

फक्त अहवाल देणारी वाचने राखा, जसे statement वर दाखवलेला balance. ही निर्णय न घेता विचारतात, आणि तेवढे परवानगी आहे.

80
तपासा

Command थेट तपासा

Method यश आणि नकार या दोन्हींसाठी unit test करा. नियम एकाच ठिकाणी असल्याने, एकच test suite प्रत्येक caller ला कव्हर करते.

90
समन्वय

Services ना सांगू द्या, ठरवू देऊ नका

जिथे एखादा workflow अनेक ऑब्जेक्ट्सवर पसरतो, तिथे service ने commands पाठवाव्यात आणि अपयश हाताळावे, कोणत्याही ऑब्जेक्टचे नियम पुन्हा अंमलात न आणता.

100
पूर्ण

वर्तन त्याच्या डेटासोबत बसते

आता प्रत्येक निर्णय स्थितीच्या मालक ऑब्जेक्टमध्ये राहतो. नियम बदलल्याने एकच method ला स्पर्श होतो, आणि encapsulation रचनेनुसारच टिकते.

सामान्य अडचणी

अडचणी आणि anti-patterns

Tell, Don't Ask निष्काळजीपणे लागू केल्याने स्वतःच्या गोंधळ निर्माण होतात. या नेहमीच्या सापळ्या आहेत.

🩸 Anemic domain model

ज्या classes फक्त getters आणि setters असतात, आणि सर्व logic services मध्ये असते, त्या मोठ्या प्रमाणावर ask-then-act दुर्गंध असतात. डेटाला वर्तन नसते, म्हणून callers ला त्याच्यासाठी ठरवावे लागते.

🎣 Getter, शाखा, setter

क्लासिक त्रयी: if (x.getState() == READY) x.setState(DONE). State machine ऑब्जेक्टमध्ये complete() command म्हणून असावे.

🚂 Train-wreck साखळ्या

order.getCustomer().getAddress().getCity() अनेक ऑब्जेक्ट्समधून विचारते. ते तुम्हाला त्यांच्या internals शी जोडते आणि Law of Demeter शी वाईट जुळते.

🕳️ बनावट encapsulation

अंतर्गत list संदर्भाने परत करणारा getter callers ना तरीही खाजगी स्थिती बदलू देतो. Telling म्हणजे कोणतेही मागचे दार नाही, म्हणून प्रती परत करा किंवा commands उघड करा.

🔨 हट्टी no-queries

सर्व वाचनांवर बंदी घातल्याने reporting, serialization, आणि UIs मोडतात. Tell, Don't Ask निर्णयांना लक्ष्य करते, प्रामाणिक queries ना नाही. प्रत्येक getter टाळण्यासाठी कोड वाकवू नका.

🧨 अति-command

विचारणे टाळण्यासाठी असंबंधित logic ऑब्जेक्टमध्ये कोंबल्याने तो फुगतो आणि single responsibility चे उल्लंघन होते. जर वर्तनाला ऑब्जेक्टच्या खाजगी स्थितीची गरज नसेल, तर ते अन्यत्र असावे.

संकेत आणि मापके

संकेत आणि कसे मोजावे

यावर तुम्ही एकच आकडा ठेवू शकत नाही, पण हे संकेत तुम्हाला सांगतात की वर्तन त्याच्या डेटासोबत बसते की नाही.

संकेतते तुम्हाला काय सांगते
प्रति class getter-नंतर-setter जोड्याएकाच ऑब्जेक्टवर अनेक read-decide-write क्रम म्हणजे निर्णय त्यातून गळाले आहेत.
Accessors च्या तुलनेत commands चे प्रमाणबहुतांश getters आणि setters असलेला class anemic असतो; हेतू उघड करणाऱ्या methods नी सार्वजनिक पृष्ठभागावर वर्चस्व गाजवावे.
डुप्लिकेट व्यावसायिक नियमतीच अट अनेक callers मध्ये दिसणे म्हणजे मालक ऑब्जेक्टच्या आत एकदाच असावा असा नियम दाखवते.
प्रति नियम बदल Call-site बदलजर एक धोरण बदलल्याने अनेक फाइल्समध्ये संपादने भाग पडत असतील, तर धोरण कधीच encapsulate केले गेले नव्हते.
Method-साखळीची खोलीखोल a.getB().getC() साखळ्या ऑब्जेक्ट्समधून विचारणे आणि त्यांच्या internals शी coupling दर्शवतात.
Test सेटअपची गुंतागुंतजर एखादे वर्तन तपासण्यासाठी ऑब्जेक्टवरील अनेक getters stub करावे लागत असतील, तर ते वर्तन बहुधा त्या ऑब्जेक्टच्या आत असावे.
अनुभवाचा नियम: निर्णय घेण्यासाठी ऑब्जेक्टची स्थिती वाचण्यापूर्वी, ऑब्जेक्ट स्वतः तो निर्णय घेऊ शकतो का ते विचारा. जर होय, तर एक command जोडा आणि getter हटवा. जर तुम्हाला फक्त मूल्य दाखवण्यासाठी किंवा नोंदवण्यासाठी हवे असेल, तर विचारणे ठीक आहे.
06 - प्रकरण अभ्यास

वास्तविक जगातील प्रकरण अभ्यास

तीन production-शैलीच्या प्रणाली जिथे ऑब्जेक्टना विचारण्याऐवजी सांगण्याने नियम सुसंगत राहिले.

🏦

1 · Payments प्रणालीमधील ledger आणि account balances

Pattern: commands आर्थिक invariants अंमलात आणतात

एका payments platform ला डझनभर प्रवेश बिंदूंवर हमी द्यायची होती की कोणतेही account त्याच्या ठरलेल्या मर्यादेपलीकडे overdraw होऊ शकणार नाही.

  • Callers ना balance वाचून वजा करण्यावरून एकाच account.withdraw(amount) command मध्ये पुन्हा लिहिले गेले.
  • Overdraft नियम आणि currency तपासण्या account च्या आत हलवल्या, जेणेकरून प्रत्येक मार्गाने तोच invariant अंमलात आणला.
  • फक्त वाचनाच्या statement queries साध्या accessors म्हणून राहिल्या कारण त्या अहवाल देतात, निर्णय घेत नाहीत.
✅ निकाल: overdraft बगचा एक संपूर्ण वर्ग नाहीसा झाला, कारण नियम आता कोणत्याही caller द्वारे वगळला जाऊ शकत नव्हता.
🛒

2 · स्वतःचे discounts लागू करणारे checkout carts

Pattern: pricing धोरण cart सोबत राहते

एका e-commerce संघाकडे coupon logic web checkout, mobile API, आणि अंतर्गत admin tool मध्ये कॉपी केलेली होती, आणि तिन्ही एकमेकांपासून दूर गेल्या.

  • प्रत्येक client मध्ये line items वाचणाऱ्या पात्रता तपासण्या cart.applyCoupon(code) मध्ये हलवल्या.
  • Cart त्याच्या contents साठी totals, discounts, आणि validity नियमांचा एकमेव मालक बनला.
  • Clients आता cart ला coupon लागू करण्यास सांगतात आणि तो जे परत करतो ते render करतात, काहीही न ठरवता.
✅ निकाल: Coupon वर्तन सर्वत्र सुसंगत बनले, आणि नवीन promotions एकच class संपादित करून पाठवली गेली.
📦

3 · Fulfillment service मधील order state machine

Pattern: setters नव्हे तर commands म्हणून संक्रमणे

एका order fulfillment service मध्ये if (order.getStatus() == PAID) order.setStatus(SHIPPED) तपासण्यांनी भरलेले होते ज्या बेकायदेशीर संक्रमणे निसटू देत होत्या.

  • Status setters ना order.markShipped() आणि order.cancel() सारख्या intent commands नी बदलले.
  • प्रत्येक command सध्याची स्थिती तपासत असे आणि order च्या आतून बेकायदेशीर संक्रमणे नाकारत असे.
  • Status फील्ड खाजगी बनले, त्यामुळे कोणताही caller अवैध उडी सक्तीने करू शकत नव्हता.
✅ निकाल: अवैध स्थिती संक्रमणे रचनेनुसारच अशक्य बनली, आणि order चे जीवनचक्र व्यावसायिक क्रियापदांसारखे वाचले.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Tell, Don't Ask आजच्या बहुतेक frameworks पेक्षा जुने आहे, पण ते जो दबाव कमी करते तो प्रणाली अधिक distributed होत असताना केवळ वाढतच जातो.

🧩 Domain-driven design

स्वतःचे invariants रक्षणारे समृद्ध aggregates हे दुसऱ्या नावाने Tell, Don't Ask च आहेत. DDD ही संकल्पना ज्या anemic model विरुद्ध इशारा देते त्याच्याशी स्पष्टपणे लढते.

📨 CQRS आणि commands

Command-query separation ही विभागणी औपचारिक करते: commands सांगतात आणि स्थिती बदलतात; queries विचारतात आणि फक्त अहवाल देतात. दोघांना वेगळे नागरिक मानले जाते.

🌐 Distributed services

निर्णय घेण्यासाठी service चा डेटा आणण्याऐवजी त्याला काहीतरी करण्यासाठी संदेश पाठवणे, वर्तन आणि स्थिती process सीमांपलीकडेही एकत्र ठेवते.

🧵 Concurrency सुरक्षा

जेव्हा एखादा ऑब्जेक्ट फक्त त्याच्या स्वतःच्या commands मार्फतच बदलतो, तेव्हा तो त्या संक्रमणांचे एकाच ठिकाणी lock ने रक्षण करू शकतो. बाह्य केलेले read-decide-write race करतात.

🎭 Actors आणि messages

Actor model हे runtime पातळीवरील Tell, Don't Ask आहे: तुम्ही actor ला एक message पाठवता आणि तो त्याच्या खाजगी स्थितीवर कृती करतो; तुम्ही आत पोहोचू शकत नाही.

🧪 Testable डिझाइन

त्याच्या डेटासोबत सहस्थित असलेले वर्तन getters च्या विस्तृत stubbing शिवाय स्वतंत्रपणे unit test करणे सोपे असते, जे test suites जलद आणि प्रामाणिक ठेवते.

निष्कर्ष: Tell, Don't Ask हा असा मार्ग आहे ज्याने तुम्ही निर्णयांना ज्या डेटावर ते अवलंबून असतात त्याच्या शेजारी ठेवता, जेणेकरून encapsulation खरे राहते आणि नियम एकाच ठिकाणी राहतात. जेव्हा तुम्हाला फक्त अहवाल द्यायचा असेल तेव्हा मुक्तपणे विचारा; जेव्हा ऑब्जेक्टने स्वतःवर कृती करावी तेव्हा सांगा.
