Creational Pattern

Factory Method - कोणती वस्तू बनवायची हे subclasses ठरवू द्या

एखाद्या class ला अनेकदा माहीत असते की तिला ऑब्जेक्ट केव्हा तयार करायचा आहे, पण कोणती concrete class instantiate करायची हे माहीत नसते. Factory Method ऑब्जेक्ट तयार करण्यासाठी एक interface परिभाषित करते आणि concrete प्रकाराची निवड subclasses वर सोपवते. कॉलर फक्त अ‍ॅब्स्ट्रॅक्शनवर काम करतो, त्यामुळे नवीन product प्रकार त्यांचा वापर करणाऱ्या कोडला स्पर्श न करता आत बसतात.

01 - काय

Factory Method म्हणजे काय?

Factory Method हा एक creational pattern आहे जो ऑब्जेक्ट तयार करण्यासाठी एक method परिभाषित करतो, पण कोणती concrete class instantiate करायची हे ठरवण्यासाठी subclasses ला ती method override करू देतो. पालक class मध्ये workflow असतो आणि तो factory method ला एका placeholder प्रमाणे कॉल करतो; प्रत्येक subclass वेगळा product पुरवतो. याचा परिणाम अशी एक class असते जी कोणत्याही concrete product प्रकाराचे नाव न घेता products वर कार्य करते.

🏭 Creator

ती class जी factory method घोषित करते. त्यात product वापरणारे मुख्य लॉजिक असते, पण प्रत्यक्ष instantiation subclass वर सोडते.

📦 Product

तयार केलेले ऑब्जेक्ट्स ज्या interface मध्ये सामायिक असतात ती. Creator नेहमी फक्त या अ‍ॅब्स्ट्रॅक्शनवर अवलंबून असतो, कधीही concrete अंमलबजावणीवर नाही.

🔧 Concrete Creator

एक subclass जी factory method override करून एक विशिष्ट concrete product परत करते, आणि एक प्रकार सामायिक workflow मध्ये जोडते.

02 - का

Factory Method का अस्तित्वात आहे

संपूर्ण codebase मध्ये new ConcreteThing() विखुरल्याने तो विशिष्ट classes शी घट्ट जोडला जातो. मग प्रत्येक नवीन प्रकार म्हणजे प्रत्येक construction ठिकाण शोधून त्यात बदल करणे. Factory Method तो निर्णय एका override करण्याजोग्या ठिकाणी आणते, त्यामुळे workflow स्थिर राहतो आणि products बदलत राहतात.

🔌 वापर आणि निर्मिती वेगळे करते

क्लायंट कोड product interface वर अवलंबून असतो, concrete classes वर नाही. तुम्ही एक नवीन subclass लिहून नवीन product जोडू शकता, विद्यमान कॉलर्समध्ये बदल न करता.

🧩 विस्तारासाठी खुले

नवीन प्रकार नवीन Concrete Creators म्हणून येतात. विद्यमान कोड बदलासाठी बंद असतो, ज्यामुळे open-closed तत्त्व नैसर्गिकरीत्या पाळले जाते.

♻️ आजूबाजूचा workflow पुनर्वापर करते

Creator सामायिक लॉजिक - logging, validation, orchestration - एकदाच धरून ठेवतो. Subclasses फक्त कोणता ऑब्जेक्ट बनवायचा हे override करतात, संपूर्ण प्रवाह नाही.

🧪 चाचणी करणे सोपे

एका test subclass मध्ये factory method override करून एक fake किंवा stub product इंजेक्ट करा, जेणेकरून आजूबाजूचा अल्गोरिदम स्वतंत्रपणे तपासता येईल.

सोप्या शब्दांत

उपमांसह Factory Method चे स्पष्टीकरण

तीच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती स्पष्ट होते.

🎓 विद्यार्थ्यासाठी

एका रिकाम्या जागा भरण्याच्या निबंध टेम्पलेटचा विचार करा. शिक्षक रचना लिहितात आणि "इथे तुमचे उदाहरण लिहा" असे लेबल असलेली एक रिकामी जागा सोडतात. प्रत्येक विद्यार्थी तीच रचना ठेवतो पण रिकामी जागा वेगळ्या, विशिष्ट उदाहरणाने भरतो.

👩‍💻 डेव्हलपरसाठी

हा एक override करण्याजोगा constructor hook आहे. base class तिच्या अल्गोरिदममध्ये create() कॉल करते; एक subclass तिला हवा तो concrete प्रकार परत करण्यासाठी create() override करते, आणि अल्गोरिदम अबाधित चालू राहतो.

🏢 व्यावसायिकासाठी

भूमिकेनुसार विशिष्ट मुलाखतकार असलेल्या भरती प्रक्रियेसारखे. HR प्रत्येक जागेसाठी तीच प्रक्रिया चालवते, पण प्रत्येक विभाग तांत्रिक फेरी कोण घेणार हे ठरवतो. प्रक्रिया निश्चित असते; आत जोडला जाणारा तज्ज्ञ बदलतो.

🍕 दैनंदिन आवृत्ती

प्रादेशिक स्वयंपाकघरे असलेली पिझ्झा साखळी. मुख्य कार्यालय "ऑर्डर घ्या, पिझ्झा बनवा, बॉक्समध्ये भरा" हे ठरवते. प्रत्येक फ्रँचायझी स्वतःची शैली तयार करण्यासाठी "पिझ्झा बनवा" override करते, तर ऑर्डर आणि बॉक्समध्ये भरण्याचे टप्पे तसेच राहतात.

03 - कसे

ते आतून कसे कार्य करते

Creator एक abstract factory method परिभाषित करतो आणि तिला concrete व्यवसाय लॉजिकमधून कॉल करतो. Subclasses एक विशिष्ट product परत करण्यासाठी factory method override करतात. दोन पदानुक्रम, Creator आणि Product, समांतरपणे विकसित होतात.

🏭 Creator ची बाजू

एक abstract Creator createProduct() घोषित करते आणि plan() सारखी एक खरी method पुरवते जी तिला कॉल करते. Concrete Creators फक्त createProduct() override करतात.

📦 Product ची बाजू

एक Product interface Creator अवलंबून असलेल्या क्रिया घोषित करते. प्रत्येक Concrete Product त्या अंमलात आणतो, आणि सहसा एक Concrete Product एका Concrete Creator शी जोडला जातो.

एका दृष्टिक्षेपात रचना

एक वास्तववादी Java उदाहरण

// Product hierarchy
interface Transport {
    String deliver(String cargo);
}

class Truck implements Transport {
    public String deliver(String cargo) {
        return "Delivering " + cargo + " by road in a box.";
    }
}

class Ship implements Transport {
    public String deliver(String cargo) {
        return "Delivering " + cargo + " by sea in a container.";
    }
}

// Creator hierarchy
abstract class Logistics {

    // The factory method - subclasses decide the concrete Transport.
    protected abstract Transport createTransport();

    // Shared workflow that depends only on the Transport interface.
    public String planDelivery(String cargo) {
        Transport t = createTransport();
        return "Planning route... " + t.deliver(cargo);
    }
}

class RoadLogistics extends Logistics {
    protected Transport createTransport() {
        return new Truck();
    }
}

class SeaLogistics extends Logistics {
    protected Transport createTransport() {
        return new Ship();
    }
}

// Usage: pick the Creator, the workflow stays identical.
Logistics logistics = new SeaLogistics();
System.out.println(logistics.planDelivery("electronics"));
// -> "Planning route... Delivering electronics by sea in a container."

लक्षात घ्या की planDelivery कधीही Truck किंवा Ship चे नाव घेत नाही. हवाई मालवाहतूक जोडणे म्हणजे एक नवीन AirLogistics अधिक एक Plane class, विद्यमान workflow मध्ये शून्य बदल. हाच संपूर्ण फायदा आहे.

सामान्य अडचणी

अडचणी आणि anti-patterns

Factory Method खऱ्या विविधतेने त्याचे मूल्य कमावते. तो खूप लवकर किंवा खूप व्यापकपणे वापरा आणि तुम्ही औपचारिकतेच्या रूपात किंमत मोजता.

🪆 Subclass स्फोट

जिथे कायम फक्त एकच product असतो तिथे तो वापरल्याने विनाकारण संपूर्ण Creator पदानुक्रम भाग पडतो. जर प्रकार कधीच बदलत नसेल, तर फक्त constructor थेट कॉल करा.

🔀 Abstract Factory शी गोंधळ

Factory Method inheritance द्वारे एक product बनवते. Abstract Factory composition द्वारे संबंधित products चे कुटुंब बनवते. या दोन्हीचे मिश्रण दोन्ही अस्पष्ट करते.

🧨 factory मध्ये लॉजिक शिरणे

factory method ने फक्त निर्मिती करून परत करावे. त्यात validation, side effects, किंवा branching टाकल्याने एक स्वच्छ hook एका लपलेल्या god-method मध्ये बदलतो.

🕳️ concrete प्रकार गळणे

जर workflow product ला परत एका concrete class मध्ये cast करत असेल, तर decoupling संपले. काटेकोरपणे product interface वर अवलंबून राहा.

🥶 कठोर one-to-one बंधन

प्रत्येक Creator साठी एक product hard-code करणे तेव्हा प्रतिबंधात्मक वाटू शकते जेव्हा Creator ला runtime वर अनेकांमधून निवडायचे असते. मग एक parameterized factory किंवा Strategy अधिक चांगले बसते.

🌀 static "factory" ला चुकीचे लेबल

switch असलेल्या static method ला "factory method" म्हणणे चुकीच्या अपेक्षा निर्माण करते. हा एक साधा factory idiom आहे आणि subclassing ने विस्तारक्षम नाही.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Factory Method classes च्या एका अतिरिक्त थराने विस्तारक्षमता विकत घेते. तुम्हाला मिळणाऱ्या लवचिकतेचे तुम्ही जोडलेल्या अप्रत्यक्षतेशी वजन करा.

पैलूतपशील
फायदेकॉलर्सना concrete classes पासून वेगळे करते, open-closed चा सन्मान करते, निर्मिती केंद्रित करते, आणि आजूबाजूचा workflow पुनर्वापरयोग्य व चाचणीयोग्य बनवते.
तोटेएक समांतर class पदानुक्रम आणि अधिक अप्रत्यक्षता आणते. जिथे फक्त एकच product प्रकार असतो किंवा प्रकार कधीच बदलत नाहीत तिथे अतिरेक ठरतो.
केव्हा वापरावेजेव्हा एखादी class तिला तयार करावा लागणारा concrete प्रकार अंदाज करू शकत नाही, किंवा तुम्हाला subclasses ने तो निर्दिष्ट करावा असे वाटते, आणि तुम्हाला कालांतराने नवीन प्रकारांची अपेक्षा असते.
केव्हा टाळावेजेव्हा product संच निश्चित आणि लहान असतो, किंवा एक साधा constructor किंवा साधी static factory आधीच स्पष्ट वाचते.
जटिलताकमी ते मध्यम. एक interface अधिक एक Creator base class, नंतर प्रत्येक प्रकारासाठी एक Creator आणि Product जोडी.
संबंधितAbstract Factory (products चे कुटुंब), Builder (टप्प्याटप्प्याने निर्मिती), Prototype (subclass ऐवजी clone), Template Method (hook ला कॉल करणारा workflow).
अंगठ्याचा नियम: Factory Method तेव्हा वापरा जेव्हा आजूबाजूचा अल्गोरिदम स्थिर असतो पण तो जो ऑब्जेक्ट तयार करतो तो subclass नुसार बदलावा. त्याऐवजी जर तुम्हाला संबंधित ऑब्जेक्ट्सची संपूर्ण कुटुंबे हवी असतील, तर Abstract Factory कडे जा. जर प्रकार कधीच बदलत नसेल, तर pattern पूर्णपणे वगळा.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

production frameworks आणि प्रणालींमध्ये Factory Method दिसणारी तीन ठिकाणे.

☕

1 · JDK collection iterators

Pattern: iterator() द्वारे virtual constructor

Java चे Collection.iterator() हे एक पाठ्यपुस्तकातील factory method आहे: प्रत्येक collection concrete iterator class उघड न करता स्वतःचा Iterator परत करते.

  • Iterable Iterator product परत करणारी factory method म्हणून iterator() घोषित करते.
  • ArrayList, LinkedList, आणि HashSet प्रत्येक त्यांच्या रचनेनुसार जुळवलेला एक private concrete iterator परत करतात.
  • for-each loop आणि stream कोड फक्त Iterator वर अवलंबून असतात, त्यामुळे कोणतीही collection एकसमानपणे काम करते.
✅ निकाल: एकच traversal API प्रत्येक collection प्रकारावर पसरतो, आणि नवीन collections क्लायंट loops न बदलता स्वतःचा iterator जोडतात.
🖼️

2 · Cross-platform UI toolkits

Pattern: समांतर Creator आणि Product पदानुक्रम

एका dialog framework ला प्रत्येक ऑपरेटिंग सिस्टमवर तोच interaction प्रवाह हवा असतो, तर प्रत्येकावर native controls render करायचे असतात.

  • एक abstract Dialog Creator render() आणि एक abstract createButton() factory method परिभाषित करते.
  • WindowsDialog एक WindowsButton परत करते, WebDialog एक HtmlButton परत करते, प्रत्येक platform साठी एक Creator.
  • render() workflow सामायिक Button interface द्वारे button च्या click handler ला जोडतो.
✅ निकाल: dialog लॉजिक एकदाच लिहिले जाते, तर प्रत्येक platform जुळणाऱ्या Creator आणि Product subclasses द्वारे native widgets जोडतो.
🔌

3 · Pluggable document parsers

Pattern: subclass concrete parser ठरवते

एक import सेवा अनेक फाइल फॉरमॅट घेते पण त्यांच्याभोवती एक स्थिर ingestion pipeline हवी असते.

  • एक abstract Importer createParser() आणि एक concrete import() घोषित करते जो निकाल validate करून साठवते.
  • CsvImporter, JsonImporter, आणि XmlImporter प्रत्येक त्यांच्या फॉरमॅटसाठी createParser() override करतात.
  • नवीन फॉरमॅट जोडणे म्हणजे एक नवीन Importer अधिक एक नवीन Parser, validation किंवा storage मध्ये कोणताही बदल न करता.
✅ निकाल: ingestion pipeline स्थिर आणि सुव्यवस्थितपणे चाचणी केलेली राहते तर समर्थित फॉरमॅटची यादी पूर्णपणे विस्ताराने वाढते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Factory Method आधुनिक dependency injection च्या आधीचे आहे, पण मूळ कल्पना, concrete प्रकाराची निवड पुढे ढकलणे, ही नेहमीप्रमाणेच केंद्रस्थानी आहे.

💉 DI containers ते शोषून घेतात

Spring सारखे frameworks configuration द्वारे concrete प्रकार सोडवतात, हे Factory Method पुरवत असलेल्या त्याच decoupling चे एक सामान्यीकृत, container-चालित स्वरूप आहे.

🧵 Functional factories

first-class functions असलेल्या भाषांमध्ये, एक supplier किंवा lambda अनेकदा एका Creator subclass ची जागा घेते, कमी औपचारिकतेसह "निवड पुढे ढकला" ही भावना टिकवते.

🧬 Generics करार अधिक तीक्ष्ण करतात

<T extends Product> परत करणाऱ्या typed factory methods compile-time सुरक्षा देतात जी 1994 च्या pattern कडे नव्हती.

🔍 Reflection आणि registries

Plugin प्रणाली Creators ना key ने register करतात आणि त्यांना runtime वर सोडवतात, Factory Method ला products च्या खुल्या संचांपर्यंत वाढवतात.

🧪 चाचणीयोग्यता टिकते

fake इंजेक्ट करण्यासाठी एक factory method override करणे हा एक workflow स्वतंत्रपणे तपासण्याच्या सर्वात सोप्या मार्गांपैकी एक राहतो.

🏗️ अजूनही प्रथम शिकवले जाते

तो creational patterns चा प्रवेशद्वार राहतो कारण तो एक कल्पना वेगळी करतो: जे बदलते (product) ते जे राहते (workflow) पासून वेगळे करा.

सारांश: जिथे एक container किंवा एक lambda जोडणी करते तिथेही, तुम्ही Factory Method चे तत्त्व लागू करत आहात - एका अ‍ॅब्स्ट्रॅक्शनवर अवलंबून राहा आणि concrete प्रकार दुसऱ्या कशाला तरी ठरवू द्या. ते एकदा शिका आणि तुम्हाला ते सर्वत्र दिसते.
