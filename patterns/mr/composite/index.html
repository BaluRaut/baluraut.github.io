Structural Pattern

Composite pattern प्रत्यक्षात कसे काम करते - झाडे जी तुम्ही एकच म्हणून वागवता

काही माहिती स्वाभाविकपणे झाडासारखी असते: फोल्डरांच्या आतले फोल्डर, पॅनेलांच्या आतली पॅनेल, गटांच्या आतले गट. Composite तुम्हाला ती झाडे पाने आणि कंटेनर यांच्यापासून बांधू देते, जे एकच Component interface सामायिक करतात, त्यामुळे client code मुळावर एकच method कॉल करू शकतो आणि बाकीचे काम recursion करू देतो. एक फाइल आणि हजार फायलींचे फोल्डर, दोघेही size() ला एकाच पद्धतीने उत्तर देतात.

01 - काय

Composite pattern म्हणजे काय?

Composite हा एक structural pattern आहे जो वस्तूंना झाडाच्या रचनेत जोडून भाग-आणि-संपूर्ण (part-whole) उतरंडींचे प्रतिनिधित्व करतो. तो clients ना एकट्या वस्तू आणि वस्तूंच्या समूहांना एकसमानपणे वागवू देतो: एक Leaf (एकटी वस्तू) आणि एक Composite (मुलांचा कंटेनर) दोघेही तोच Component interface अंमलात आणतात, त्यामुळे कॉल करणाऱ्याला कधीही विचारावे लागत नाही की "ही एक गोष्ट आहे की अनेक?"

🧩 Component

सामायिक interface किंवा abstract class. तो अशा operations जाहीर करतो ज्यांना पाने आणि कंटेनर दोघांनीही आधार दिला पाहिजे, जसे की render() किंवा size().

🍃 Leaf

मुले नसलेली एकटी वस्तू. ती झाडाचे शेवटचे टोक असते आणि operation थेट, स्वतःच्या वर्तनासाठी अंमलात आणते.

📦 Composite

मुले असलेल्या Components ला धरून ठेवणारा कंटेनर. तो operation आपल्या मुलांकडे सोपवून आणि त्यांचे निकाल एकत्र करून अंमलात आणतो.

02 - का

Composite का अस्तित्वात आहे

त्याशिवाय, भाग-आणि-संपूर्ण उतरंडीवरून चालणारा कोणताही code type checks नी भरलेला असतो: "जर हे फोल्डर असेल तर त्याच्या आतल्या गोष्टींवरून लूप कर, नाहीतर फाइल हाताळ." ती अट प्रत्येक operation आणि प्रत्येक कॉल करणाऱ्यापर्यंत पसरते. Composite ते फांद्यांचे काम वस्तूंच्या आतच ढकलतो.

🎯 Type-checking चा पसारा संपवतो

Clients instanceof च्या शिड्या लिहिणे थांबवतात. एक polymorphic कॉल "हे leaf आहे की container?" ही codebase मध्ये पसरलेली तर्कशक्ती बदलून टाकतो.

🌱 नवीन node प्रकारांसाठी खुला

नवीन प्रकारचे leaf किंवा container जोडा आणि सध्याचा client code चालूच राहतो, कारण तो फक्त Component interface शीच बोलतो. हे प्रत्यक्षातले Open-Closed Principle आहे.

🔁 Recursion फुकट

एकूण आकार, render, किंवा serialize यासारखी एकत्रित operations "प्रत्येक मुलाला विचारा, एकत्र करा" अशी स्वाभाविकपणे व्यक्त होतात. झाडाची खोली कॉल करणाऱ्यासाठी अप्रस्तुत बनते.

🌳 वास्तवाचे थेट प्रतिरूप

File systems, DOM trees, org charts आणि scene graphs हे झाडेच आहेत. Composite त्या आकाराचे code मध्ये प्रतिबिंब करतो, त्याला विचित्र लूपांमध्ये सपाट करण्याऐवजी.

सोप्या शब्दांत

उपमांसह Composite ची उकल

तीच कल्पना, चित्रित करण्याच्या चार पद्धती, म्हणजे तुम्ही कोणीही असलात तरी ती पटते.

🎓 विद्यार्थ्यासाठी

Composite म्हणजे फोल्डरांचे फोल्डर. एका फोल्डरवर right-click करा आणि "Properties" निवडा आणि ते आतल्या सर्व गोष्टींचा एकूण आकार सांगते, कितीही खोल घरटी असोत. तुम्ही फाइल-दर-फाइल तो मोजत नाही; तुम्ही सर्वात वरच्या फोल्डरला विचारता आणि तो खाली विचारतो.

👩‍💻 डेव्हलपरसाठी

हे DOM tree आहे. एक text node आणि मुलांनी भरलेला <div> दोघेही appendChild आणि textContent ला उत्तर देतात. तुम्ही root element वर एक method कॉल करता आणि browser subtree मधून recurse होतो.

🏢 व्यावसायिकासाठी

एका org chart चा विचार करा. कोणत्याही manager ला "तुझ्याखालील एकूण मनुष्यबळ" विचारा आणि ते आपल्या अधीनस्थांची बेरीज करतात, ज्यातील प्रत्येक जण आपल्या अधीनस्थांची बेरीज करतो. एक individual contributor फक्त "एक" असे उत्तर देतो. तोच प्रश्न, संपूर्ण साखळी, कोणतीही विशेष प्रकरणे नाहीत.

📦 रोजच्या जीवनातली आवृत्ती

एक पेटी जी वस्तू किंवा लहान पेट्या धरू शकते. शिपिंगसाठी एकूण वजन शोधण्यासाठी, तुम्ही बाहेरची पेटी वजन करता, म्हणजेच आतली प्रत्येक गोष्ट वजन करता, पेट्यांसह, अगदी शेवटपर्यंत खाली.

03 - कसे

आतल्या बाजूने ते कसे काम करते

तुम्ही एक सामायिक Component प्रकार परिभाषित करता, त्याला एक Leaf अंमलबजावणी देता जी खरे काम करते, आणि एक Composite अंमलबजावणी देता जी मुलांची यादी ठेवते आणि त्यांच्याकडे काम सोपवते. एकत्रित operations recursive बनतात: एक Composite आपल्या मुलांची उत्तरे एकत्र करून आपले उत्तर मोजतो.

🧱 करार परिभाषित करा

Component प्रत्येक node ला आधार देणारी operations जाहीर करतो. पाने ती थेट अंमलात आणतात; Composites ती मुलांवरून लूप करून आणि निकाल एकत्र गुंडाळून अंमलात आणतात.

🪆 मुक्तपणे घरटी करा

कारण Composite Components ला धरून ठेवतो, आणि Composite स्वतः एक Component आहे, त्यामुळे कंटेनर कोणत्याही खोलीपर्यंत कंटेनर धरू शकतात. Client मुळावर तीच method कॉल करत राहतो.

Java मधली एक वास्तववादी अंमलबजावणी

// Component: the shared interface for files and folders
interface FileSystemNode {
    String getName();
    long size();                 // recursive aggregate
    void print(String indent);
}

// Leaf: a single file, does the work itself
final class FileLeaf implements FileSystemNode {
    private final String name;
    private final long bytes;

    FileLeaf(String name, long bytes) {
        this.name = name;
        this.bytes = bytes;
    }

    public String getName() { return name; }

    public long size() { return bytes; }   // base case of the recursion

    public void print(String indent) {
        System.out.println(indent + name + "  (" + bytes + " B)");
    }
}

// Composite: a folder that holds children and delegates
final class Directory implements FileSystemNode {
    private final String name;
    private final List<FileSystemNode> children = new ArrayList<>();

    Directory(String name) { this.name = name; }

    Directory add(FileSystemNode node) { children.add(node); return this; }
    void remove(FileSystemNode node)   { children.remove(node); }

    public String getName() { return name; }

    public long size() {                    // recursive step
        long total = 0;
        for (FileSystemNode child : children) {
            total += child.size();          // ask each child, leaf or folder
        }
        return total;
    }

    public void print(String indent) {
        System.out.println(indent + name + "/");
        for (FileSystemNode child : children) {
            child.print(indent + "  ");     // recurse into the subtree
        }
    }
}

// Client: treats a single file and a whole tree identically
FileSystemNode root = new Directory("project")
    .add(new FileLeaf("README.md", 1_200))
    .add(new Directory("src")
        .add(new FileLeaf("Main.java", 4_800))
        .add(new FileLeaf("Util.java", 2_100)));

System.out.println(root.size());   // 8100  -> one call, whole tree
root.print("");                    // pretty-prints the hierarchy

लक्षात घ्या की client कधीही तपासत नाही की एखादा node फाइल आहे की फोल्डर. तो एका FileSystemNode वर size() कॉल करतो आणि Directory recurse होतो तर FileLeaf आपले स्वतःचे bytes परत करतो. तो एकच polymorphic कॉल, अधिक कंटेनरच्या आतली recursion, हाच संपूर्ण pattern आहे.

Recursive पायरी जोडा

सर्वात वरच्या node वर operation चालवा. Polymorphism कोणत्याही type checks शिवाय प्रत्येक node वर Leaf किंवा Composite वर्तनाकडे पाठवते.

90
सोडवा

झाडाला वर गुंडाळू द्या

पाने आपले स्वतःचे निकाल परत करतात; कंटेनर आपल्या मुलांचे निकाल एकत्र करतात आणि मुळाला अंतिम उत्तर मिळेपर्यंत ते वर पाठवतात.

100
विस्तार

Node प्रकार सुरक्षितपणे जोडा

नंतर नवीन पाने किंवा कंटेनर आणा. कारण clients फक्त Component interface शीच स्पर्श करतात, सध्याचा code अबाधितपणे चालूच राहतो.

सामान्य अडचणी

अडचणी आणि anti-patterns

Composite सांगायला सोपा आणि चुकीच्या पद्धतीने वापरायलाही सोपा आहे. वास्तविक झाडांमध्ये दिसणारे हे सापळे आहेत.

🕳️ पानांवर गळणाऱ्या child methods

Transparency साठी add आणि remove Component वर ढकला, आणि आता Leaf ला त्या अंमलात आणाव्या लागतात. runtime मध्ये UnsupportedOperationException फेकणे हे compile-time सुरक्षिततेच्या बदल्यात सोय देते. जाणीवपूर्वक निवडा.

🔁 झाडातील चक्रे (cycles)

जर एखादा Composite स्वतःचाच वंशज बनू शकत असेल, तर recursion कधीही थांबत नाही. पूर्वजाला मूल म्हणून जोडण्यापासून सावध राहा, नाहीतर पहिलाच size() कॉल stack उडवून टाकतो.

📉 खोल झाडे stack ओसंडून टाकतात

अतिशय खोल उतरंडींवर भोळी recursion call stack संपवू शकते. अपायकारक खोलीसाठी, शुद्ध recursion ऐवजी स्पष्ट stack किंवा iterative traversal वापरा.

🧨 सपाट माहितीवर Composite लादणे

जर खरी भाग-आणि-संपूर्ण घरटी नसेल, तर interface प्रत्येक वस्तूला तिला न लागणाऱ्या container methods नी फुगवते. एक साधी list ही एक-पातळीच्या "झाडा" पेक्षा सोपी आहे.

🐌 प्रत्येक कॉलला aggregates पुन्हा मोजणे

झाड क्वचितच बदलत असेल तर प्रत्येक size() ला प्रचंड subtree ची बेरीज करणे व्यर्थ आहे. aggregate कॅश करा आणि बदल झाल्यावर parent साखळीत वर invalidate करा, पण profiling ने ते महत्त्वाचे आहे असे दाखवले तरच.

🎭 God Component interface

कोणत्याही node ला कधीही लागू शकणारी प्रत्येक operation Component मध्ये कोंबल्याने पाने अप्रस्तुत methods अंमलात आणतात. सामायिक interface सर्व nodes खरोखर सामायिक करतात तेवढ्यापुरतेच ठेवा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Composite child management कुठे राहते याविषयीच्या एका design निवडीच्या किमतीत एकसमानता आणि स्वच्छ recursion विकत घेतो.

पैलूतपशील
फायदेClients पाने आणि कंटेनर यांना एकसमानपणे वागवतात, type checks नाहीत; recursive operations स्वाभाविक असतात; नवीन node प्रकार कॉल करणाऱ्यांना स्पर्श न करता जोडले जातात (Open-Closed).
तोटेसामायिक interface एकतर खूप रुंद (पानांना container methods मिळतात) किंवा खूप अरुंद असू शकतो; खोल झाडांना stack overflow चा धोका; सपाट माहितीसाठी अतिरेकी.
केव्हा वापरावेतुमच्याकडे खरी भाग-आणि-संपूर्ण उतरंड आहे - फाइली आणि फोल्डर, UI panels, आकार आणि गट, org charts - आणि कोणत्याही subtree वर तीच operation चालवायची आहे.
केव्हा टाळावेमाहिती सपाट किंवा एक-पातळी खोल आहे, पाने आणि कंटेनर खूप वेगळे वागतात, किंवा घरटी संरचनात्मक नसून आनुषंगिक आहे.
गुंतागुंतरचनात्मकदृष्ट्या कमी: तीन भूमिका आणि एक recursion. सूक्ष्मता संपूर्णपणे child-management methods वरील safety विरुद्ध transparency निर्णयातच आहे.
संबंधितDecorator (तोच recursive आकार, एक मूल), Iterator (झाडावरून चालतो), Visitor (nodes न बदलता operations जोडतो), Builder (गुंतागुंतीची झाडे जुळवतो).
Safety विरुद्ध transparency, ढोबळ नियम: add/remove फक्त Composite वर ठेवा safety साठी - compiler तुम्हाला ते leaf वर कॉल करण्यापासून रोखतो, पण client ला कधीकधी downcast करावे लागते. ते Component वर ठेवा transparency साठी - प्रत्येक node सारखाच दिसतो, पण पानांना ते कॉल runtime मध्ये नाकारावे लागतात. Safety ला प्राधान्य द्या, जोपर्यंत clients ना खरोखर प्रत्येक node ला संभाव्य container म्हणून वागवण्याची गरज नसेल.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

production-दर्जाच्या systems मध्ये Composite दिसणाऱ्या तीन जागा, प्रत्येक एक खरे भाग-आणि-संपूर्ण झाड.

🗂️

1 · build tool मधले file-system झाड

Pattern: पाने म्हणजे फाइली, composites म्हणजे directories

एका build tool ला directory आकार मोजायचे, जुळणाऱ्या फायलींसाठी glob करायचे, आणि compilation साठी project झाडावरून चालायचे असते.

  • एक FileNode interface File पाने आणि Directory composites द्वारे अंमलात आणला जातो.
  • size(), walk(), आणि match(glob) directories मधून recurse होतात आणि फायलींपाशी थांबतात.
  • Child management (add, remove) फक्त Directory वरच राहते, त्यामुळे compiler फाइलला मूल जोडण्यासारखा मूर्खपणा रोखतो.
✅ निकाल: project मुळावर एक recursive कॉल कोणत्याही subtree साठी बेरजा आणि traversals मोजतो, कॉल करणाऱ्यामध्ये फाइली विरुद्ध फोल्डर असे कोणतेही विशेष प्रकरण न ठेवता.
🖼️

2 · widget toolkit मधले UI component झाड

Pattern: पाने म्हणजे widgets, composites म्हणजे containers

एक GUI toolkit buttons, labels, आणि घरटी panels यांनी बनलेल्या screens render व layout करते.

  • एक Component base render(), measure(), आणि hitTest(point) जाहीर करतो.
  • Button आणि Label ही पाने आहेत; Panel हा एक composite आहे जो आपली मुले क्रमाने render करतो.
  • एक render pass मुळावर render() कॉल करतो आणि संपूर्ण subtree स्वतःला recursively काढतो.
✅ निकाल: layout engine एकट्या button आणि खोलवर घरटी असलेल्या panel ला एकसारखे वागवते, त्यामुळे नवीन widget प्रकार render loop न बदलता जोडले जातात.
🎨

3 · गटबद्धतेसह vector graphics editor

Pattern: पाने म्हणजे आकार, composites म्हणजे गट

एक drawing app वापरकर्त्यांना आकार गटबद्ध करू देते, गटाला एकच म्हणून transform करू देते, आणि गट यथेच्छ घरटी करू देते.

  • एक Graphic interface draw(), bounds(), आणि move(dx, dy) उघड करतो.
  • Circle आणि Rect ही पाने आहेत; Group हा एक composite आहे जो transforms प्रत्येक मुलाकडे पाठवतो.
  • एक गट निवडून तो ओढल्याने संपूर्ण subtree हलतो कारण move() recurse होतो.
✅ निकाल: गटबद्ध करणे आणि गट सोडवणे operation code मध्ये काहीही अतिरिक्त खर्च करत नाही, कारण गट म्हणजे आणखी एक Graphic जे साधनांना आधीच कसे हाताळायचे ते माहीत आहे.
07 - सुसंगतता

आधुनिक सुसंगतता

Composite आजच्या बहुतांश stacks च्या आधीचा आहे, तरीही एकसमान-nodes-चे-झाड ही कल्पना आधुनिक software मध्ये सर्वत्र आहे.

🌐 Virtual DOM trees

React आणि तत्सम libraries elements ची झाडे बांधतात जिथे एक component आणि एक host node एकसमानपणे हाताळले जातात, मग recursively reconcile केले जातात. Composite विचारसरणी संपूर्ण render model च्या मुळाशी आहे.

🧾 Abstract syntax trees

Compilers आणि formatters code ला nodes म्हणून दर्शवतात जिथे एक expression मध्ये expressions असू शकतात. Traversal आणि transformation एका सामायिक node interface वरून recurse होतात.

🎬 Scene graphs

Game engines आणि 3D साधने transforms आणि meshes ला एका scene graph मध्ये घरटी करतात, world transforms झाडाच्या खाली अगदी Composite सांगतो तसेच पसरवतात.

📄 Document object models

HTML, XML, आणि rich-text documents ही Composite झाडे आहेत जिथे text nodes आणि element nodes traversal व editing साठी एक interface सामायिक करतात.

🧰 Functional variants

Functional languages मध्ये तोच आकार fold operations सह recursive algebraic data types म्हणून दिसतो, pattern चा संरचनात्मक गाभा वजा class hierarchy.

🗺️ Config आणि infra trees

घरटी configuration, JSON documents, आणि infrastructure resource graphs भाग व संपूर्ण यांच्या त्याच एकसमान, recursive वागणुकीने चालवले जातात.

सारांश: जेव्हा जेव्हा माहिती ही भाग-आणि-संपूर्ण उतरंड असते आणि तुम्हाला कोणत्याही subtree वर तीच operation चालवायची असते, तेव्हा Composite हेच उत्तर आहे. तो केंद्रस्थानी राहतो कारण झाडे केंद्रस्थानी आहेत - हा pattern एक युक्ती कमी आणि घरटी माहितीचा स्पष्ट केलेला नैसर्गिक आकार अधिक आहे.
