Proxy पॅटर्न - प्रवेश नियंत्रित करणारा प्रतिनिधी

Proxy हा एक प्रतिनिधी आहे जो खऱ्या ऑब्जेक्टप्रमाणेच तेच interface अंमलात आणतो आणि त्याच्यासमोर बसतो. कॉल करणाऱ्यांना वाटते की ते खऱ्या ऑब्जेक्टशी बोलत आहेत, पण proxy शांतपणे ठरवतो की कॉल केव्हा आणि करावा की नाही पुढे पाठवायचा - महाग काम पुढे ढकलणे, परवानग्या लागू करणे, निकाल cache करणे, किंवा नेटवर्कपलीकडे पोहोचणे. तेच interface, जास्तीचे नियंत्रण.

01 - काय

Proxy पॅटर्न म्हणजे काय?

Proxy हा दुसऱ्या ऑब्जेक्टसाठी एक जागाधारक पुरवतो जेणेकरून त्यावरील प्रवेश नियंत्रित करता येईल. Proxy आणि खरा ऑब्जेक्ट (subject) एकच interface सामायिक करतात, त्यामुळे proxy हा थेट बदली म्हणून वापरता येतो. Clients interface चा संदर्भ धरतात आणि त्यांना कधीच कळत नाही की ते खऱ्या subject शी जोडलेले आहेत की प्रतिनिधीशी - proxy प्रत्येक कॉल पकडतो आणि खऱ्या ऑब्जेक्टकडे सोपवण्यापूर्वी, नंतर, किंवा त्याऐवजी वर्तन जोडतो.

🎭 तेच interface

Proxy आणि खरा subject एकसारखाच प्रकार अंमलात आणतात. Client interface नुसार कोड लिहितो, त्यामुळे proxy client मध्ये कोणताही बदल न करता पारदर्शकपणे बदली होतो.

🛡️ प्रवेश नियंत्रित करतो

Proxy subject कडे जाणाऱ्या मार्गावर बसतो आणि त्यावर पहारा देतो: तो निर्मिती पुढे ढकलू शकतो, परवानग्या तपासू शकतो, cache करू शकतो, log करू शकतो, किंवा सीमेपलीकडे पुढे पाठवू शकतो.

🔗 खरा ऑब्जेक्ट धरतो

Proxy खऱ्या subject चा संदर्भ (किंवा तो तयार करण्याचे साधन) धरून ठेवतो आणि एकदा त्याने ठरवले की कॉल पुढे जावा, तेव्हा तो प्रत्यक्ष काम सोपवतो.

Proxy चे मुख्य प्रकार

प्रकारतो काय नियंत्रित करतोठराविक वापर
Virtual / lazyखरा ऑब्जेक्ट केव्हा तयार होतोमहाग ऑब्जेक्ट पहिल्या खऱ्या वापरापर्यंत बांधणे पुढे ढकलणे

02 - का

Proxy पॅटर्न का अस्तित्वात आहे

कधीकधी तुम्ही client ला खऱ्या ऑब्जेक्टला थेट स्पर्श करू देऊ शकत नाही किंवा देऊ नये. निर्मिती महाग असू शकते, ऑब्जेक्ट दुसऱ्या मशीनवर राहू शकतो, प्रवेशाला पहाऱ्याची गरज असू शकते, किंवा वारंवार कॉल्स वाया जाऊ शकतात. Proxy client ला कधीच न कळता एक नियंत्रण बिंदू घालतो.

⏳ महाग काम पुढे ढकला

Virtual proxy जड ऑब्जेक्ट्स (मोठ्या प्रतिमा, DB connections, parse केलेले models) बांधणे ते प्रत्यक्ष वापरात येण्याच्या क्षणापर्यंत पुढे ढकलतो, त्यामुळे startup वेगवान राहते आणि न वापरलेली संसाधने कधीच तयार होत नाहीत.

🌐 दूरस्थपणा लपवा

Remote proxy स्थानिक कोडला दुसऱ्या process मधील किंवा नेटवर्कपलीकडील ऑब्जेक्ट memory मध्ये असल्यासारखे कॉल करू देतो, serialization, transport, आणि retries त्याच interface मागे बंदिस्त करतो.

🔐 प्रवेश नियम लागू करा

Protection proxy सोपवण्यापूर्वी credentials किंवा roles तपासतो, authorization एका ठिकाणी केंद्रित करतो जेणेकरून खरा subject त्याच्या मुख्य कामावर लक्ष केंद्रित करू शकेल.

⚡ पुनरावृत्त काम टाळा

Caching proxy निकाल साठवतो आणि पुन्हा कॉल्सवर ते देतो, client ला कोणतेही cache व्यवस्थापन न करता latency आणि load कमी करतो.

सोप्या शब्दांत

उपमांसह Proxy समजावून

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती पटेल.

🎓 विद्यार्थ्यासाठी

Proxy म्हणजे एक teaching assistant जो नेहमीचे प्रश्न सोडवतो आणि फक्त अवघड प्रश्नच प्राध्यापकांकडे पाठवतो. तुम्हाला वाटते की तुम्ही प्राध्यापकांना विचारत आहात, पण TA त्यांच्या वतीने गाळून पुढे पाठवत असतो.

👩‍💻 डेव्हलपरसाठी

तो एक wrapper आहे जो subject चे interface सामायिक करतो. तुम्ही service.load() कॉल करता; proxy cache तपासतो, कदाचित खरी service lazily तयार करतो, मग सोपवतो. तुमचे call site कधीच बदलत नाही.

🏢 व्यावसायिकासाठी

एका executive assistant चा विचार करा. लोक अधिकाऱ्यापर्यंत पोहोचल्यासारखे वेळ ठरवतात, पण assistant विनंत्या तपासतो, अनधिकृत विनंत्या अडवतो, आणि फक्त तपासलेल्या बैठकाच खऱ्या व्यक्तीपर्यंत पोहोचू देतो.

💳 रोजच्या जीवनातील आवृत्ती

एक debit card तुमच्या bank account चा प्रतिनिधी असतो. तुम्ही card ने पैसे भरता, पण network आधी तुमची balance आणि परवानग्या तपासते, मग पडद्यामागे खरे पैसे हलवते.

03 - कसे

पडद्यामागे ते कसे काम करते

Proxy तेच Subject interface अंमलात आणतो जे खरा ऑब्जेक्टही अंमलात आणतो. तो खऱ्या ऑब्जेक्टचा संदर्भ धरतो, आणि प्रत्येक method एकतर थेट सोपवते किंवा नियंत्रण तर्कासह सोपवणे गुंडाळते: मागणीनुसार निर्मिती, परवानगी तपासणी, cache शोध, किंवा remote कॉल्स.

🧩 सामायिक interface

Client फक्त Subject वर अवलंबून असतो. RealSubject आणि Proxy दोघेही तो अंमलात आणतात, त्यामुळे कोणत्याही call site वर proxy खऱ्या ऑब्जेक्टशी बदली करता येतो.

🎚️ आधी पकडा मग सोपवा

Proxy आधी त्याचा नियंत्रण तर्क चालवतो, मग कॉल पुढे जावा असल्यास खऱ्या subject कडे पुढे पाठवतो - शक्यतो पहिल्या कॉलवर तो subject lazily तयार करतो.

रचना एका दृष्टीक्षेपात

रचना - client Subject नुसार कोड लिहितो; Proxy RealSubject वर पहारा देतो

Java मधील एक virtual (lazy-loading) proxy

// Shared interface: both real object and proxy implement it
interface Image {
    void render();
}

// RealSubject: construction is expensive (reads bytes from disk)
class HighResImage implements Image {
    private final String path;
    private byte[] pixels;

    HighResImage(String path) {
        this.path = path;
        loadFromDisk(); // heavy work happens in the constructor
    }

    private void loadFromDisk() {
        System.out.println("Loading " + path + " from disk...");
        this.pixels = new byte[10_000_000]; // pretend this is costly
    }

    public void render() {
        System.out.println("Rendering " + path);
    }
}

// Virtual Proxy: same interface, defers creation until first render()
class LazyImage implements Image {
    private final String path;
    private HighResImage real; // created on demand

    LazyImage(String path) {
        this.path = path; // cheap: no disk I/O yet
    }

    public void render() {
        if (real == null) {            // lazy load on first use
            real = new HighResImage(path);
        }
        real.render();                 // delegate to the real subject
    }
}

// Client codes to the interface and never knows it holds a proxy
class Gallery {
    public static void main(String[] args) {
        Image img = new LazyImage("photo.raw"); // instant, nothing loaded
        System.out.println("Gallery ready.");
        img.render(); // NOW the real image loads, then renders
        img.render(); // already loaded: just renders
    }
}

लक्षात घ्या की proxy कोणतीही नवी method जोडत नाही - तो नेमके Image उघड करतो. तो फक्त एवढेच बदलतो की जड HighResImage केव्हा बांधले जाते. LazyImage बदलून परवानग्या तपासणारे ProtectedImage, किंवा memoize करणारे CachedImage ठेवा, आणि client अस्पर्शित राहतो.

04 - Sequence आकृत्या

तपशीलवार sequence आकृत्या

तीन दृश्ये: lazily load करणारा virtual proxy, पुनरावृत्त कॉल short-circuit करणारा caching proxy, आणि परवानग्यांवर पहारा देणारा protection proxy.

आकृती 1 - Virtual proxy: खरा ऑब्जेक्ट फक्त पहिल्या वापरावरच तयार करा
sequenceDiagram
    autonumber
    participant C as 👤 Client
    participant P as 🎭 LazyImage proxy
    participant R as 🖼️ HighResImage

    C->>P: new LazyImage(path)
    Note over P: cheap, nothing loaded yet
    C->>P: render()
    alt real not created
        P->>R: new HighResImage(path)
        R-->>P: loaded from disk
    end
    P->>R: render()
    R-->>P: drawn
    P-->>C: done
    C->>P: render() again
    Note over P: real already exists
    P->>R: render()
    R-->>P: drawn
    P-->>C: done
आकृती 2 - Caching proxy: साठवलेले निकाल द्या, फक्त miss वरच पुन्हा आणा
sequenceDiagram
    autonumber
    participant C as 👤 Client
    participant P as ⚡ Caching proxy
    participant R as 🗄️ Real service

    C->>P: get(key)
    alt cache hit
        P-->>C: cached value
    else cache miss
        P->>R: get(key)
        R-->>P: fresh value
        P->>P: store in cache
        P-->>C: fresh value
    end
आकृती 3 - Protection proxy: सोपवण्यापूर्वी परवानग्या तपासा
sequenceDiagram
    autonumber
    participant C as 👤 Client
    participant P as 🛡️ Protection proxy
    participant R as 📁 Real subject

    C->>P: delete(record)
    P->>P: check caller role
    alt authorized
        P->>R: delete(record)
        R-->>P: removed
        P-->>C: success
    else denied
        P-->>C: throw AccessDenied
    end

नेहमीच्या अडचणी

अडचणी आणि anti-patterns

Proxies चुकीच्या पद्धतीने वापरणे सोपे आहे. स्वच्छ प्रतिनिधीला ओझे बनवणारे नेहमीचे सापळे हे आहेत.

🎭 Decorator शी गोंधळ

जर तुमचा wrapper प्रवेश नियंत्रित करण्याऐवजी निकालात नवे वर्तन जोडत असेल, तर तो Decorator आहे. Decorator ला proxy म्हणणे वाचकांपासून त्याचा खरा हेतू लपवते.

🧵 असुरक्षित lazy निर्मिती

Synchronization शिवाय lazy-load करणारा virtual proxy समांतर कॉल्सखाली खरा ऑब्जेक्ट दोनदा बांधू शकतो. निर्मितीवर पहारा द्या किंवा thread-safe holder वापरा.

🕰️ शिळे caches

कधीच अवैध न करणारा caching proxy कायमचा जुना डेटा देत राहतो. TTL किंवा invalidation hook शिवाय, वेगाचा फायदा शुद्धतेचा bug बनतो.

🫥 लपलेली latency

Remote proxy एक network कॉल स्थानिक method सारखा दिसवतो. Callers गृहीत धरतात की तो स्वस्त आहे आणि round trips व failure modes कडे दुर्लक्ष करून तो loops मध्ये हातोडतात.

🪆 अति-proxying

प्रत्येक चिंतेसाठी proxies रचणे असे indirection जोडते जे शोधणे आणि debug करणे कठीण असते. प्रत्येक थराने आपली जागा कमवावी लागते; निरुपयोगी प्रतिनिधी फक्त खरा ऑब्जेक्ट अस्पष्ट करतात.

🧬 Interface विचलन

जेव्हा खरा subject अशा methods मिळवतो ज्या proxy पुढे पाठवायला विसरतो, तेव्हा प्रतिनिधी शांतपणे विचलित होतो. Proxy ला Subject interface सोबत ताळमेळात ठेवा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Proxy तुम्हाला एका जास्तीच्या थराच्या किमतीत एक नियंत्रण बिंदू देतो. तो वापरण्याआधी त्याचे मोजमाप करा.

पैलूतपशील
फायदेप्रवेश नियंत्रण, laziness, caching, किंवा remoting पारदर्शकपणे जोडतो; client आणि खरा subject अस्पर्शित व अनभिज्ञ राहतात.
तोटेजास्तीचे indirection आणि सांभाळण्यासाठी एक class; किंमत किंवा latency लपवू शकतो आणि debugging व stack traces गुंतागुंतीचे करू शकतो.
केव्हा वापरावेतुम्हाला निर्मिती पुढे ढकलायची आहे, प्रवेशावर पहारा द्यायचा आहे, cache करायचे आहे, किंवा खऱ्या ऑब्जेक्टप्रमाणे त्याच interface मागे remote ऑब्जेक्ट दर्शवायचा आहे.
केव्हा टाळावेतुम्हाला वर्तन जोडायचे आहे (Decorator वापरा) किंवा interface बदलायचे आहे (Adapter वापरा), किंवा नियंत्रणाने कोणतेही खरे मूल्य जोडले जात नाही.
गुंतागुंतकमी ते मध्यम. पॅटर्न सोपा आहे; अडचण thread safety, invalidation, आणि remote error handling मध्ये राहते.
संबंधितDecorator (वर्तन जोडतो), Adapter (interface बदलतो), Facade (subsystem सोपे करतो), Flyweight (सूक्ष्म ऑब्जेक्ट्स सामायिक करतो).
अंगठ्याचा नियम: जेव्हा wrapper चे काम कॉल खऱ्या ऑब्जेक्टपर्यंत पोहोचतो की नाही, केव्हा, किंवा कुठे हे ठरवणे असते तेव्हा Proxy कडे वळा. जर wrapper चे काम कॉल काय करतो किंवा तो कसा आकार घेतो हे बदलणे असेल, तर तुम्हाला त्याऐवजी Decorator किंवा Adapter हवा असतो.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

Production-दर्जाच्या systems मध्ये Proxy चे तीन प्रातिनिधिक वापर.

🌱

1 · Hibernate lazy-loading proxies

प्रकार: virtual / lazy proxy

ORM ने प्रत्येक वेळी एक row आणताना संपूर्ण ऑब्जेक्ट graph load करू नये, नाहीतर एकच query संपूर्ण database ओढून आणेल.

  • Hibernate lazy associations साठी खऱ्या entity ऐवजी runtime मध्ये तयार केलेला proxy परत करतो.
  • खरा ऑब्जेक्ट आणि त्याच्या संबंधित rows database मधून फक्त method प्रथम कॉल केल्यावरच load होतात.
  • Proxy entity चा प्रकार अंमलात आणतो, त्यामुळे application कोड त्याला नेमके खऱ्या entity प्रमाणेच वागवतो.
✅ परिणाम: Queries हलक्या राहतात, memory वाचते, आणि developers ना fetch तर्क हाताने न लिहिता नैसर्गिक ऑब्जेक्ट प्रवेश मिळतो.
🛰️

2 · gRPC आणि RMI client stubs

प्रकार: remote proxy

एका service ला दुसऱ्या process किंवा datacenter मध्ये राहणाऱ्या ऑब्जेक्टला कॉल करावा लागतो, पण कॉल एका सामान्य method invocation सारखा दिसावा असे वाटते.

  • तयार केलेला client stub remote server सारखेच तेच service interface अंमलात आणतो.
  • Method कॉल केल्याने arguments serialize होतात, ते wire वरून पाठवले जातात, आणि उत्तर deserialize होते.
  • Transport, retries, आणि connection handling त्या स्थानिक दिसणाऱ्या interface मागे लपून राहतात.
✅ परिणाम: Teams स्वच्छ, typed method कॉल्सने remote services कॉल करतात तर networking तपशील stub मध्ये बंदिस्त राहतात.
🛡️

3 · Spring AOP आणि security proxies

प्रकार: protection / smart-reference proxy

Enterprise app ला business logic मध्ये cross-cutting चिंता न भरता परवानग्या, transactions, आणि logging लागू करावे लागते.

  • Spring beans ना dynamic proxies मध्ये गुंडाळतो जे bean चे interface अंमलात आणतात.
  • Proxy खऱ्या bean कडे सोपवण्यापूर्वी roles तपासतो, transactions सुरू करतो, किंवा metrics नोंदवतो.
  • Business methods स्वच्छ राहतात; प्रतिनिधी प्रत्येक पहारा दिलेल्या कॉलवर धोरण लागू करतो.
✅ परिणाम: Security आणि transaction नियम सातत्याने आणि केंद्रितपणे लागू होतात, तर खरे ऑब्जेक्ट्स त्यांच्या मुख्य कामावर लक्ष केंद्रित करतात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

कालबाह्य होण्यापासून दूर, Proxy पॅटर्न आजच्या बहुतांश पायाभूत सुविधांचा आधार आहे, language runtimes पासून ते service meshes पर्यंत.

🕸️ Service mesh sidecars

Envoy सारखे sidecar proxies प्रत्येक service शेजारी बसतात, प्रवेश, retries, आणि observability पारदर्शकपणे नियंत्रित करतात - platform प्रमाणावर remote proxy ची कल्पना.

🧠 JS runtime Proxy object

JavaScript चा अंगभूत Proxy property प्रवेश आणि कॉल्स runtime मध्ये पकडतो, classic प्रतिनिधी प्रतिमेने reactive frameworks आणि validation ला चालना देतो.

⚙️ Dynamic proxies

Java चा java.lang.reflect.Proxy आणि CGLIB runtime मध्ये proxies तयार करतात, जे AOP, mocking libraries, आणि ORM lazy loading चा कणा आहेत.

🚪 API gateways

Gateways संपूर्ण systems साठी protection आणि caching proxies आहेत, backend services समोर auth, rate limits, आणि response caching लागू करतात.

🔒 Lazy आणि सुरक्षित initialization

Virtual proxies memory-जागरूक आणि startup-संवेदनशील apps मध्ये महाग निर्मिती पुढे ढकलण्याचा आणि resource lifecycles व्यवस्थापित करण्याचा स्वच्छ मार्ग राहतात.

🧪 Test doubles

Mocking frameworks असे proxies बांधतात जे खऱ्या सहकाऱ्यांचे प्रतिनिधित्व करतात, tests ना त्याच interface द्वारे परस्परसंवाद नियंत्रित करू आणि निरीक्षण करू देतात.

सारांश: Proxy केंद्रस्थानी राहतो कारण ऑब्जेक्टवरील प्रवेश नियंत्रित करण्याची गरज - तो पुढे ढकलणे, पहारा देणे, cache करणे, किंवा remotely पोहोचणे - कधीच नाहीशी होत नाही. जेव्हा एका प्रतिनिधीने खऱ्या ऑब्जेक्टपासून अभेद्य असले पाहिजे, तेव्हा तुम्ही proxy पाहत आहात.
