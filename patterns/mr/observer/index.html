Observer पॅटर्न - एक बदल, अनेक प्रतिक्रिया

Observer हे ऑब्जेक्ट्समध्ये one-to-many अवलंबित्व निश्चित करते: जेव्हा एक ऑब्जेक्ट (subject) आपली स्थिती बदलतो, तेव्हा त्यावर अवलंबून असलेल्या सर्वांना (observers) आपोआप सूचित केले जाते आणि अद्ययावत केले जाते. हे इव्हेंट सिस्टिम्स, UI डेटा बाइंडिंग आणि reactive streams चा कणा आहे. बदलणारी गोष्ट आणि त्याची काळजी करणाऱ्या अनेक गोष्टी यांच्यात तुम्हाला loose coupling मिळते.

01 - काय

Observer पॅटर्न म्हणजे काय?

Observer एका ऑब्जेक्टला कोण ऐकत आहे हे न कळता बदल प्रकाशित करू देते. एक subject observers ची यादी ठेवतो आणि जेव्हा जेव्हा त्याची स्थिती बदलते, तेव्हा तो त्या यादीवर फिरून प्रत्येकावर update मेथड कॉल करतो. Observers रनटाइमला subscribe आणि unsubscribe करू शकतात, त्यामुळे ऐकणाऱ्यांचा संच पूर्णपणे डायनॅमिक असतो आणि subject ला ठोस observer प्रकारांविषयी काहीच माहीत नसते.

📣 Subject (publisher)

महत्त्वाची स्थिती आणि observers ची नोंदणी ठेवतो. subscribe, unsubscribe आणि notify उपलब्ध करून देतो. त्याला कधीच ठोस observer classes माहीत नसतात.

👂 Observer (subscriber)

एक समान interface लागू करतो, सहसा एक update मेथड. तो इतर observers पासून स्वतंत्रपणे, त्याला हवे तसे बदलावर प्रतिक्रिया देतो.

🔔 सूचना (Notification)

जेव्हा स्थिती बदलते, तेव्हा subject आपल्या यादीवर फिरतो आणि प्रत्येक observer वर update कॉल करतो. डेटा एकतर कॉलमध्ये push केला जातो किंवा subject कडून pull केला जातो.

02 - का

Observer का अस्तित्वात आहे

त्याशिवाय, बदलणाऱ्या ऑब्जेक्टला प्रतिक्रिया देणाऱ्या प्रत्येक ऑब्जेक्टचे कॉल हार्डकोड करावे लागतात. एक नवीन ग्राहक जोडा आणि तुम्हाला producer मध्ये बदल करावा लागतो. Observer ते अवलंबित्व तोडते जेणेकरून producers आणि consumers वेगवेगळे विकसित होतात.

🔗 Loose coupling

Subject फक्त observer interface वर अवलंबून असतो, ठोस listeners वर नाही. स्थिती बदलणाऱ्या कोडला हात न लावता तुम्ही प्रतिक्रिया जोडू, काढू किंवा बदलू शकता.

📡 प्रसारण संवाद

एका स्थिती-बदलामुळे अनेक इच्छुक पक्षांपर्यंत एकाच पावलात माहिती पसरते. नवीन consumers फक्त subscribe करतात; producer ला त्यांची नावे कधीच कळत नाहीत.

⏱️ रनटाइम लवचिकता

प्रोग्राम चालू असताना observers नोंदणी करतात आणि नोंदणी रद्द करतात. प्रतिक्रियांचा संच म्हणजे डेटा असतो, compile वेळी निश्चित केलेला कॉल आलेख नसतो.

🎯 जबाबदाऱ्यांचे विभाजन

स्थितीचा मालक असलेली गोष्ट स्वतःच्या कामावर केंद्रित राहते. Logging, UI रिफ्रेश, caching आणि analytics प्रत्येक स्वतःच्या observer मध्ये राहतात.

सोप्या शब्दांत

उपमांसह Observer समजावले

एकच कल्पना, कल्पना करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती पटकन कळेल.

🎓 विद्यार्थ्यासाठी

हे एका वर्गाच्या ग्रुप चॅटसारखे आहे. जेव्हा शिक्षक परीक्षेची तारीख पोस्ट करतात, तेव्हा subscribe केलेल्या प्रत्येकाला एकाच वेळी संदेश मिळतो. शिक्षक प्रत्येक विद्यार्थ्याला वेगळा मेसेज करत नाहीत, आणि विद्यार्थी कधीही ग्रुप सोडू शकतात.

👩‍💻 डेव्हलपरसाठी

हे addEventListener आहे. एक बटण callbacks ची यादी ठेवते; क्लिकवर ते सर्वांना कॉल करते. बटणाला तुमच्या handlers विषयी काहीच माहीत नसते, आणि component unmount झाल्यावर तुम्ही listener काढू शकता.

🏢 व्यावसायिकासाठी

एका कंपनीच्या मेलिंग यादीचा विचार करा. एक घोषणा प्रकाशित करा आणि प्रत्येक subscriber ला ती मिळते. लोक मुक्तपणे सामील होतात आणि बाहेर पडतात, आणि पाठवणारा कधीच प्रत्येक व्यक्तीचे पत्ते ठेवत नाही.

📰 रोजच्या जीवनातील आवृत्ती

एक वृत्तपत्राची वर्गणी. वृत्तपत्र एकदा छापले जाते आणि प्रत्येक सध्याच्या subscriber पर्यंत पोहोचवले जाते. रद्द करा आणि वितरण थांबते; प्रकाशकाला तुम्ही कोण आहात हे कळण्याची गरज नाही.

03 - कसे

ते आतून कसे कार्य करते

दोन हलणारे भाग: एक subject जो observers ची यादी सांभाळतो आणि सूचना पाठवतो, आणि observers जे एक सामायिक interface लागू करतात आणि प्रतिक्रिया देतात. एकमेव खरी डिझाइन निवड म्हणजे डेटा observer पर्यंत कसा पोहोचतो.

📤 Push मॉडेल

Subject बदललेला डेटा सूचनेच्या आत पाठवतो, उदाहरणार्थ update(temperature). सोपे आणि स्वयंपूर्ण, पण प्रत्येक observer ला काय हवे आहे याचा subject ला अंदाज लावावा लागतो.

📥 Pull मॉडेल

Subject फक्त काहीतरी बदलले असा संकेत देतो; प्रत्येक observer त्याला हवी असलेली नेमकी स्थिती वाचण्यासाठी परत कॉल करतो. अधिक लवचिक, पण अतिरिक्त फेऱ्या आणि subject वर घट्ट प्रवेशाच्या किंमतीवर.

TypeScript मधील एक वास्तववादी अंमलबजावणी

type Listener<T> = (event: T) => void;

class Subject<T> {
  private listeners = new Set<Listener<T>>();

  // subscribe returns an unsubscribe handle - the modern idiom
  subscribe(fn: Listener<T>): () => void {
    this.listeners.add(fn);
    return () => this.listeners.delete(fn);
  }

  // push model: the changed data travels with the notification
  notify(event: T): void {
    // copy first so an observer unsubscribing mid-notify is safe
    for (const fn of [...this.listeners]) fn(event);
  }
}

// --- usage ---
interface Weather { tempC: number; humidity: number }
const station = new Subject<Weather>();

const off = station.subscribe(w => console.log(`Phone: ${w.tempC}C`));
station.subscribe(w => console.log(`Log: humidity ${w.humidity}%`));

station.notify({ tempC: 21, humidity: 55 }); // both observers fire
off();                                        // phone stops listening
station.notify({ tempC: 22, humidity: 50 }); // only the log fires

subscribe मधून एक unsubscribe फंक्शन परत करणे ही या पॅटर्नची सर्वात महत्त्वाची सोयीस्कर सुधारणा आहे. ते प्रत्येक subscriber ला जुळणारी teardown देते, जे खालील lapsed-listener गळती नेमके तेच टाळते.

ठोस observers अंमलात आणा

Interface पूर्ण करणारे classes किंवा callbacks लिहा. प्रत्येक स्वतंत्रपणे प्रतिक्रिया देतो: एक view रिफ्रेश करा, log लिहा, cache अवैध करा.

रनटाइमला observers subscribe करा

Observers subscribe कॉल करतात आणि परत मिळालेला unsubscribe handle ठेवतात. Subject ला आता त्यांना भविष्यातील सूचनांमध्ये समाविष्ट करायचे कळते.

बदल

Subject स्थिती बदला

काही caller subject अद्ययावत करतो. Subject बदल शोधतो आणि ऐकणाऱ्या प्रत्येकाला तो प्रसारित करण्याची तयारी करतो.

60
सूचना

सर्व observers ना प्रसारित करा

Subject आपल्या यादीवर फिरतो, प्रत्येक observer वर update कॉल करतो. एका प्रतीवर फिरा जेणेकरून notify दरम्यानचा unsubscribe loop बिघडवू शकणार नाही.

70
प्रतिक्रिया

Observers इव्हेंट हाताळतात

प्रत्येक observer स्वतःचे logic चालवतो. अपयश वेगळे केले पाहिजे जेणेकरून एक अपवाद टाकणारा observer उर्वरित प्रसारणाला अडवणार नाही.

80
क्रम

क्रम आणि reentrancy विचारात घ्या

Notify दरम्यान एक observer subject बदलत असेल, तर तुम्ही एक cascade सुरू करू शकता. Reentrancy विरुद्ध रक्षण करा आणि कोणताही सूचना क्रम गृहीत धरू नका.

90
Unsubscribe

काम झाल्यावर वेगळे करा

जेव्हा एक observer यापुढे आवश्यक नसतो, तेव्हा त्याचा unsubscribe handle कॉल करा. हे संदर्भ काढून टाकते आणि मेमरी आरोग्यासाठी एकमेव सर्वात महत्त्वाचे पाऊल आहे.

100
पडताळणी

कोणतीही गळती उरली नाही याची खात्री करा

नष्ट झालेले observers नोंदणीतून गेले आहेत का ते तपासा. दीर्घायुषी subjects मध्ये, weak references किंवा स्पष्ट teardown listener यादीला अनंतपणे वाढण्यापासून रोखतात.

सामान्य धोके

धोके आणि anti-patterns

Observer जोडणे सोपे आहे आणि गैरवापर करणेही सोपे आहे. वास्तविक सिस्टिम्समध्ये दिसणारी ही अपयशे आहेत.

🕳️ Lapsed-listener गळती

क्लासिक बग: एक observer टाकून दिला जातो पण कधीच unsubscribe केला जात नाही, त्यामुळे subject त्याचा एक strong संदर्भ कायमचा ठेवतो. तो garbage collect होऊ शकत नाही आणि त्याचे update अजूनही चालते. नेहमी subscribe ला unsubscribe सोबत जोडा, किंवा weak references वापरा.

🔁 सूचना cascades

Notify दरम्यान subject बदलणारा observer आणखी एक notify सुरू करू शकतो, आणि आणखी एक. अनियंत्रित reentrancy मुळे अनावश्यक काम, शिळ्या मध्यवर्ती स्थिती किंवा अनंत loops होतात.

🧨 एक observer प्रसारण मोडतो

जर notify त्रुटी वेगळ्या न करता observers ना कॉल करते, तर एकच टाकलेला अपवाद loop रद्द करतो आणि नंतरचे observers कधीच चालत नाहीत. प्रत्येक observer साठी catch करा नाहीतर बदल गुपचूप अर्धवट लागू होतो.

❓ अनपेक्षित क्रम

Observers विशिष्ट क्रमाने चालण्यावर गुपचूप अवलंबून असणारा कोड नाजूक असतो. नोंदणी क्रम हा अंमलबजावणीचा तपशील आहे, तुम्ही अवलंबून राहावा असा करार नाही.

🌀 Update वादळे

प्रत्येक बारीक बदल एक सूचना सुरू करत असेल तर तो observers ना पूर आणू शकतो - एका तार्किक कृतीसाठी शेकडो updates. Broadcast करण्यापूर्वी batch किंवा debounce करा, किंवा बदल एकत्र करा.

🔗 इव्हेंटमार्फत लपलेले coupling

Events मध्ये subject चे अंतर्गत तपशील भरणे तुम्ही टाळत असलेले घट्ट coupling पुन्हा निर्माण करते. Payloads लहान आणि स्थिर ठेवा जेणेकरून observers subject च्या अंतर्गत भागांपर्यंत पोहोचणार नाहीत.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Observer decoupling आणि डायनॅमिक प्रतिक्रिया मिळवते, पण ते थेटपणा गमावते आणि नियंत्रण-प्रवाह अस्पष्ट करू शकते.

पैलूतपशील
फायदेLoose coupling, रनटाइम subscribe/unsubscribe, one-to-many प्रसारण, subject मध्ये बदल न करता नवीन observers साठी खुले.
तोटेअप्रत्यक्ष नियंत्रण-प्रवाह जो शोधणे कठीण, मेमरी गळतीचा धोका, cascades आणि अनिश्चित सूचना क्रम.
केव्हा वापरावेअनेक ऑब्जेक्ट्सना एका स्थिती-बदलावर प्रतिक्रिया द्यावी लागते, listeners चा संच रनटाइमला बदलतो, आणि producer ला त्याचे consumers माहीत नसावेत.
केव्हा टाळावेनेमका एक, निश्चित consumer असतो, किंवा जेव्हा reactive अप्रत्यक्षपणा एका साध्या थेट कॉलला विनाकारण अनुसरण्यास कठीण बनवते.
गुंतागुंतजोडणे सोपे, सुरक्षितपणे चालवणे मध्यम - lifecycle व्यवस्थापन आणि reentrancy ही खरी किंमत आहे, प्रारंभिक कोड नाही.
संबंधितPublish/subscribe (broker मार्फत decoupled), Mediator (परस्परसंवाद केंद्रित करते), Reactive streams (backpressure आणि operators सह observers).
अनुभवाचा नियम: जेव्हा एक बदलणारी गोष्ट अनेक, बदलणारे listeners असते तेव्हा Observer कडे वळा. जर संवाद many-to-many असेल आणि समन्वयाच्या नियमांची गरज असेल, तर त्याऐवजी Mediator कडे वळा.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन ठिकाणे जिथे Observer पॅटर्न शांतपणे सर्व सूत्रे चालवते.

🖱️

1 · ब्राउझर DOM events

पॅटर्न: addEventListener मार्फत push-model observers

प्रत्येक UI फ्रेमवर्क आणि साधे पान DOM एलिमेंट्सवर अवलंबून असते जे नोंदणीकृत handlers ना events प्रसारित करतात.

  • एक एलिमेंट म्हणजे subject; addEventListener एका callback observer ला subscribe करते.
  • परस्परसंवादावर एलिमेंट प्रत्येक handler ला एक Event ऑब्जेक्ट push करते.
  • removeEventListener unsubscribe करते; काढलेल्या node वर ते विसरल्याने handler ची गळती होते.
✅ परिणाम: कितीही स्वतंत्र handlers एकाच क्लिकला प्रतिसाद देतात, आणि एलिमेंटला त्यांच्याविषयी काहीच माहीत नसते.
🌊

2 · Reactive streams (RxJS, Reactor)

पॅटर्न: operators आणि backpressure सह observers

Reactive लायब्ररी Observer ला काळानुसार events च्या composable streams मध्ये सामान्यीकृत करतात.

  • एक Observable म्हणजे subject; subscribe एक observer जोडते आणि एक Subscription परत करते.
  • map, filter आणि debounce सारखे operators सूचना stream रूपांतरित करतात.
  • Unsubscribe केल्याने साखळी विरून जाते, आणि backpressure वेगवान producers नियंत्रित करते.
✅ परिणाम: जटिल async इव्हेंट pipelines त्याच subscribe-and-notify गाभ्यावर declarative पद्धतीने तयार होतात.
🗂️

3 · State stores आणि data binding

पॅटर्न: एका मध्यवर्ती store चे UI observers

Redux, MobX, Vue आणि signals सर्व, अनुप्रयोगाची स्थिती बदलल्यावर subscribe केलेल्या views ना सूचित करतात.

  • Store म्हणजे subject; components त्यांना ज्याची काळजी आहे त्या स्थितीच्या भागांना subscribe करतात.
  • एक dispatch केलेला बदल subscribers ना सूचित करतो, जे नवीन मूल्यासह पुन्हा render होतात.
  • फ्रेमवर्क unmount वर आपोआप unsubscribe करतात जेणेकरून lapsed-listener गळती टळते.
✅ परिणाम: UI आपोआप स्थितीशी सुसंगत राहते, store आणि प्रत्येक view यांच्यात कोणतीही मॅन्युअल जोडणी न करता.
07 - उपयुक्तता

आधुनिक उपयुक्तता

Gang of Four ने त्याला नाव दिले तेव्हापेक्षा Observer आता अधिक केंद्रस्थानी आहे, आपण रोज वापरत असलेल्या साधनांमध्ये लपलेले.

⚡ Signals आणि बारीक reactivity

Solid, Angular, Vue आणि Preact मधील signals म्हणजे मूल्याच्या पातळीवरचे Observer - एक signal वाचणे subscribe करते, ते लिहिणे notify करते, स्वयंचलित dependency tracking सह.

🌊 सर्वत्र reactive programming

RxJS, Reactor आणि Combine या पॅटर्नला operators, scheduling आणि async इव्हेंट प्रवाहांसाठी backpressure असलेल्या पूर्ण stream बीजगणितांमध्ये रूपांतरित करतात.

📨 Event-driven आर्किटेक्चर

Kafka, message brokers आणि pub/sub सिस्टिम्स त्याच publish-and-subscribe कल्पनेला सेवा आणि मशीन्सवर scale करतात.

🧹 Lifecycle-सुरक्षित subscriptions

फ्रेमवर्क hooks, AbortController आणि effect cleanup unsubscribe स्वयंचलित करतात, आणि lapsed-listener गळती डीफॉल्टपणे निवृत्त करतात.

🪶 Weak references

WeakRef आणि weak listener संग्रह subjects ना garbage collection रोखल्याशिवाय observers धरून ठेवू देतात, गळतीविरुद्ध एक अंगभूत संरक्षण.

🔌 WebSockets आणि live data

रिअल-टाइम डॅशबोर्ड, सहयोगी संपादक आणि live feeds म्हणजे बदल घडताच त्यांना push करणाऱ्या सर्व्हरला प्रतिक्रिया देणारे observers.

सारांश: कोण कशावर प्रतिक्रिया देतो हे हार्डवायर न करता सॉफ्टवेअर बदलावर कशी प्रतिक्रिया देते ते म्हणजे Observer. एका बटण क्लिकपासून ते वितरित इव्हेंट बसपर्यंत, तोच subscribe-and-notify गाभा तुम्ही स्पर्श करता त्या जवळपास प्रत्येक interactive आणि reactive सिस्टिमला आधार देतो.
