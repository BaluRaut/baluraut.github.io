Behavioral Pattern

Command पॅटर्न - क्रियांना ऑब्जेक्टमध्ये बदलणे

Command पॅटर्न एका विनंतीला execute() मेथड असलेल्या स्वतंत्र ऑब्जेक्टमध्ये गुंडाळतो, ज्यामुळे जी गोष्ट क्रिया सुरू करते तिला जी गोष्ट ती क्रिया पार पाडते तिच्यापासून वेगळे केले जाते. आता प्रत्येक क्रिया हा first-class ऑब्जेक्ट असल्यामुळे, तुम्ही तिला रांगेत लावू शकता, लॉग करू शकता, पुन्हा चालवू शकता, मॅक्रोमध्ये एकत्र करू शकता आणि सर्वात महत्त्वाचे म्हणजे undo करू शकता. तुम्ही कधीही वापरलेला प्रत्येक editor, task queue आणि transactional UI याचा हा कणा आहे.

01 - काय

Command पॅटर्न म्हणजे काय?

Command हा एक behavioral डिझाइन पॅटर्न आहे जो एका विनंतीला स्वयंपूर्ण ऑब्जेक्टमध्ये बदलतो. तो ऑब्जेक्ट ती क्रिया नंतर पार पाडण्यासाठी लागणारे सर्व काही सोबत घेऊन जातो: ज्यावर क्रिया करायची तो receiver, कोणती मेथड कॉल करायची, आणि कोणते arguments पास करायचे. कॉल करणारा आता "हे आत्ता कर" असे म्हणत नाही; तो एक ऑब्जेक्ट धरून ठेवतो आणि म्हणतो "तू तयार असशील तेव्हा हे चालव." तोच लहानसा बदल undo, रांग लावणे, लॉगिंग आणि मॅक्रो शक्य करून देतो.

📦 ऑब्जेक्ट रूपात विनंती

एक क्रिया अशी किंमत बनते जी तुम्ही variable मध्ये साठवू शकता, इकडून तिकडे पास करू शकता आणि यादीत ठेवू शकता, त्याऐवजी अशी मेथड कॉल जी चालते आणि नाहीशी होते.

▶️ एकसमान execute()

प्रत्येक command तोच लहानसा interface उघड करतो, त्यामुळे invoker "delete text" आणि "send email" या दोन्हींना तपशील न जाणता एकसारखेच वागवतो.

↩️ रचनेनेच उलटा करता येणारा

execute() सोबत undo() जोडा आणि प्रत्येक command स्वतःला कसे उलटवायचे हे जाणतो, ज्यामुळे तुम्हाला history, redo आणि transactional rollback फुकट मिळते.

02 - का

Command पॅटर्न का अस्तित्वात आहे

एखादी मेथड थेट कॉल करणे ठीक आहे, जोपर्यंत तुम्हाला ती पुढे ढकलायची, पुन्हा करायची, नोंदवायची, किंवा मागे घ्यायची गरज पडत नाही. साधी मेथड कॉल ला स्मृती नसते आणि उलट जाण्याचा गियर नसतो. त्या कॉलला ऑब्जेक्टमध्ये गुंडाळल्याने त्या क्रियेला एक ओळख मिळते जी तुम्ही व्यवस्थापित करू शकता.

↩️ Undo आणि redo

जर प्रत्येक command स्वतःला उलटवू शकत असेल, तर चालवलेल्या commands ची stack ही undo history बनते आणि undo केलेल्यांची stack ही redo बनते. हा पॅटर्न अस्तित्वात असण्याचे हे सर्वात मोठे एकमेव कारण आहे.

⏳ रांग आणि शेड्यूल

command हा फक्त data असल्यामुळे, तुम्ही त्याला queue वर ढकलू शकता, worker thread वर चालवू शकता, पुन्हा प्रयत्न करू शकता, किंवा उशीर करू शकता, आणि हे सर्व कॉल करणाऱ्याला तो केव्हा चालतो हे कळू न देता.

🧾 लॉग आणि replay

commands ना log मध्ये serialize करा आणि तुम्ही प्रत्येक बदलाचे ऑडिट करू शकता, state पुन्हा तयार करण्यासाठी त्यांना replay करू शकता, किंवा event stream म्हणून त्यांना नेटवर्कवर पाठवू शकता.

🔗 कॉल करणाऱ्याला कामगारापासून वेगळे करा

एक button, एक menu item, आणि एक keyboard shortcut हे सर्व तोच command ऑब्जेक्ट सुरू करू शकतात. receiver काय आहे किंवा तो कसा काम करतो हे invoker ला कधीच कळत नाही.

सोप्या शब्दांत

उपमांसह Command समजावून

एकच कल्पना, तिला चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती डोक्यात बसते.

🎓 विद्यार्थ्यासाठी

command म्हणजे index card वर लिहिलेली गृहपाठाची सूचना. शिक्षक (invoker) तुम्हाला cards ची चळत देतात; प्रत्येक card नेमके कोणते काम करायचे हे जाणते. शिक्षकाला कोणत्याही कामाचे तपशील न कळता तुम्ही चळत पुन्हा लावू शकता, एखादे card पुन्हा करू शकता, किंवा एखादे फाडून त्याला undo करू शकता.

👩‍💻 डेव्हलपरसाठी

हे नाव आणि उलट असलेले closure आहे. doc.insert("hi") आत्ता चालण्याऐवजी, तुम्ही receiver, args आणि एक undo() धरून ठेवणारा ऑब्जेक्ट बनवता. invoker cmd.execute() कॉल करतो आणि त्याला history stack वर ढकलू शकतो.

🏢 व्यावसायिकासाठी

रेस्टॉरंटच्या ऑर्डर तिकिटाचा विचार करा. वेटर (invoker) ऑर्डर लिहितो आणि रेलवर लावतो; स्वयंपाकघर (receiver) ती शिजवते. तिकीट रांगेत लागते, लॉग होते आणि रद्द करता येते. वेटर कधीच शेगडीला हात लावत नाही.

🔌 रोजच्या जीवनातली आवृत्ती

एक रिमोट कंट्रोल बटण. प्रत्येक बटण एका उपकरणाशी बांधलेला एक command धरून ठेवते. ती क्रिया चालवण्यासाठी दाबा, आणि चांगल्या रचलेल्या रिमोटमध्ये undo किंवा "last channel" असतो जो तुम्ही नुकतेच केलेले उलटवतो.

03 - कसे

ते आतून कसे काम करते

एक command एका receiver ला आणि arguments ना एका एकसमान execute() मागे बांधतो. एक invoker commands चालवतो आणि दोन stacks ठेवतो, एक undo साठी आणि एक redo साठी, त्यामुळे history ही साधी push आणि pop बनते.

🧱 command तयार करणे

client एक concrete command बांधतो, receiver आणि त्याला लागणारी arguments पकडून ठेवतो. undo साठी, command तो ज्या state वर लिहून टाकणार आहे तीही नोंदवतो, म्हणजे तो ती नंतर पुनर्संचयित करू शकतो.

🗂️ history चालवणे

invoker execute() कॉल करतो, command ला undo stack वर ढकलतो, आणि redo साफ करतो. Undo सर्वात वरचा command काढतो आणि undo() कॉल करतो; redo redo stack मधून काढतो आणि पुन्हा चालवतो.

एक वास्तववादी text-editor उदाहरण (Java)

// Command interface: every action is execute + undo
interface Command {
    void execute();
    void undo();
}

// Receiver: knows how to actually mutate text
class Document {
    private final StringBuilder buf = new StringBuilder();
    void insert(int pos, String text) { buf.insert(pos, text); }
    void delete(int from, int len)    { buf.delete(from, from + len); }
    String read(int from, int len)    { return buf.substring(from, from + len); }
    @Override public String toString() { return buf.toString(); }
}

// Concrete command: insert, and remember how to reverse it
class InsertTextCommand implements Command {
    private final Document doc;
    private final int pos;
    private final String text;
    InsertTextCommand(Document doc, int pos, String text) {
        this.doc = doc; this.pos = pos; this.text = text;
    }
    public void execute() { doc.insert(pos, text); }
    public void undo()    { doc.delete(pos, text.length()); }
}

// Concrete command: delete captures what it removed so undo can restore it
class DeleteTextCommand implements Command {
    private final Document doc;
    private final int from, len;
    private String removed;               // state saved during execute()
    DeleteTextCommand(Document doc, int from, int len) {
        this.doc = doc; this.from = from; this.len = len;
    }
    public void execute() {
        removed = doc.read(from, len);    // snapshot before destroying it
        doc.delete(from, len);
    }
    public void undo() { doc.insert(from, removed); }
}

// Invoker: runs commands and maintains undo/redo history
class CommandStack {
    private final Deque<Command> undo = new ArrayDeque<>();
    private final Deque<Command> redo = new ArrayDeque<>();
    void run(Command c) { c.execute(); undo.push(c); redo.clear(); }
    void undo() { if (!undo.isEmpty()) { Command c = undo.pop(); c.undo(); redo.push(c); } }
    void redo() { if (!redo.isEmpty()) { Command c = redo.pop(); c.execute(); undo.push(c); } }
}

// Client wiring it together
Document doc = new Document();
CommandStack editor = new CommandStack();
editor.run(new InsertTextCommand(doc, 0, "Hello world"));
editor.run(new DeleteTextCommand(doc, 5, 6));   // "Hello"
editor.undo();                                  // back to "Hello world"
editor.redo();                                  // "Hello" again

लक्षात घ्या की DeleteTextCommand काढून टाकलेल्या मजकुराचा snapshot execute() दरम्यान घेतो, त्याच्या constructor मध्ये नाही, कारण योग्य किंमत फक्त run time लाच अस्तित्वात असते. तीच पकडलेली state नेमकी undo() शक्य करते, आणि हाच तपशील बहुतेक भोळ्या अंमलबजावण्या चुकीचा करतात.

00
परिभाषित करा

Command interface घोषित करा

सर्वात लहान करारापासून सुरुवात करा: execute(), आणि उलटता येण्याला महत्त्व असेल तर undo(). सिस्टीममधली प्रत्येक क्रिया तो अंमलात आणेल.

10
Receiver

काम कोण करते ते ओळखा

ज्या ऑब्जेक्ट्सना क्रिया कशा पार पाडायच्या हे आधीच माहीत आहे ते शोधा, document, light, account. Commands त्यांना काम सोपवतात; खरा तर्क त्यांच्याकडे असतो.

20
गुंडाळा

Concrete commands तयार करा

प्रत्येक क्रियेसाठी, एक class बांधा जी एका receiver ला आणि त्याच्या arguments ना पकडते आणि execute() च्या आत receiver ला कॉल करते.

30
उलटवा

प्रत्येक command undo करता येण्याजोगा करा

undo() अंमलात आणा जेणेकरून command स्वतःचा परिणाम उलटवतो. तुम्ही जी state वर लिहून टाकणार आहात तिचा snapshot execute() दरम्यान घ्या, आधी नाही.

40
Invoker

invoker बांधा

एक घटक जोडा जो command ऑब्जेक्ट्स स्वीकारतो आणि त्यांच्यावर execute() कॉल करतो, प्रत्येक command प्रत्यक्षात काय करतो याबद्दल अनभिज्ञ राहून.

50
History

undo stack जोडा

प्रत्येक चालवलेला command एका stack वर ढकलला जातो. Undo सर्वात वरचा काढतो आणि त्याचा undo() कॉल करतो. आता तुमच्याकडे एक-पातळी आणि बहु-पातळी undo आहे.

60
Redo

redo stack जोडा

तुम्ही undo करता तेव्हा, command ला redo stack वर हलवा. Redo त्याला काढतो आणि पुन्हा चालवतो. कोणताही नवा command redo साफ करतो जेणेकरून history रेषीय राहते.

70
बांधा

triggers ना commands शी जोडा

buttons, menu items आणि shortcuts ना त्याच command ऑब्जेक्ट्सकडे रोखा. UI commands सुरू करते; ती कधीच receivers ना थेट कॉल करत नाही.

80
Macro

commands ना मॅक्रोमध्ये एकत्र करा

मॅक्रो command commands ची यादी धरून ठेवतो आणि त्यांना क्रमाने चालवतो, उलट क्रमाने undo करतो. एक वापरकर्त्याचा हावभाव अनेक अणुरूप पायऱ्या बनतो.

90
रांग

रांग लावा, लॉग करा, किंवा टिकवा

commands ऑब्जेक्ट्स असल्यामुळे, त्यांना worker साठी रांगेत लावा, audit log मध्ये लिहा, किंवा नंतर replay करून state पुन्हा तयार करण्यासाठी serialize करा.

पाठवा

भक्कम, उलटता येणाऱ्या क्रिया

आता तुमच्याकडे अशी सिस्टीम आहे जिथे प्रत्येक क्रिया testable, queueable, loggable आणि उलटता येण्याजोगी आहे, आणि हे सर्व एका लहानशा interface मागे.

सामान्य धोके

धोके आणि अँटी-पॅटर्न

पॅटर्न साधा आहे, पण undo आणि state capture हेच जिथे बहुतेक अंमलबजावण्या गुपचूप तुटतात.

📸 state फार लवकर पकडणे

पुनर्संचयित करायची किंमत execute() दरम्यानऐवजी constructor मध्ये नोंदवणे म्हणजे undo शिळी किंवा चुकीची किंमत पुनर्संचयित करते. अंमलबजावणीच्या वेळी snapshot घ्या.

🫥 अर्धवट undo होणारे मॅक्रो

मध्येच अपयशी होणारा पण आधीच अंमलात आणलेल्या पायऱ्या मागे न घेणारा मॅक्रो state विसंगत ठेवतो. अपयशावर अंमलात आणलेल्या sub-commands ना उलट क्रमाने undo करा.

🧨 देव-commands

receiver ला काम सोपवण्याऐवजी खरा व्यवसाय-तर्क command मध्ये कोंबणे commands ना कचराकुंडी बनवते आणि वेगळेपणाचा उद्देश हरवते.

♾️ अमर्याद history

प्रत्येक command कायमचा ठेवणे memory ला मर्यादेशिवाय वाढवते, विशेषतः जेव्हा commands मोठे snapshots धरून ठेवतात. stack ला मर्यादा घाला किंवा हलके deltas वापरा.

🔗 undo मधले गळणारे संदर्भ

साठवलेली state पुनर्संचयित करण्याऐवजी पुढचा तर्क पुन्हा चालवून उलटवणारा undo, मध्ये इतर commands चालले असल्यास भरकटतो. पकडलेल्या data पासून उलटवा.

🏗️ क्षुल्लक क्रियांचे अतिअभियांत्रिकीकरण

ज्याला कधीच undo, रांग किंवा लॉगिंगची गरज नाही अशा एकाच fire-and-forget कॉलला command class मध्ये गुंडाळल्याने कोणत्याही फायद्याशिवाय औपचारिकता वाढते. जिथे तो त्याची किंमत वसूल करतो तिथेच वापरा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Command तुम्हाला वेळ, पुनरावृत्ती आणि उलटवण्याभोवती लवचिकता विकत देतो, अधिक classes आणि अप्रत्यक्षतेच्या किंमतीवर.

पैलूतपशील
फायदेinvoker ला receiver पासून वेगळे करतो; undo/redo, रांग लावणे, लॉगिंग आणि मॅक्रो शक्य करतो; प्रत्येक command स्वतंत्रपणे test करणे सोपे; open/closed पूर्ण करतो - invoker ला हात न लावता क्रिया जोडा.
तोटेअनेक लहान classes आणतो; अप्रत्यक्षतेचा एक थर जोडतो; भक्कम undo आणि state capture ला काळजी लागते; साध्या क्रियांसाठी जड वाटू शकते.
केव्हा वापरावेतुम्हाला undo/redo लागते, काम रांगेत लावायचे किंवा शेड्यूल करायचे आहे, क्रिया लॉग किंवा replay करायच्या आहेत, मॅक्रो लागतात, किंवा एक क्रिया अनेक triggers पासून पोहोचण्याजोगी हवी आहे.
केव्हा टाळावेक्रिया ही एकदाच होणारी कॉल आहे जिला कधीच पुढे ढकलायचे, पुन्हा करायचे, लॉग किंवा उलटवायचे नाही. साधी मेथड किंवा lambda पुरेशी आहे.
गुंतागुंतसाध्या execute साठी कमी ते मध्यम; एकदा विश्वासार्ह undo, redo आणि transactional मॅक्रो जोडले की मध्यम.
संबंधितMemento (command जी state पुनर्संचयित करतो ती साठवतो), Observer (events वर commands सुरू करतो), Strategy (एक algorithm बदलतो), Chain of Responsibility (handlers मधून विनंती मार्गित करतो).
ठोकताळा: एखाद्या क्रियेला "आत्ता चालव" पलीकडे जीवन लागताच Command कडे वळा - जर तुम्हाला ती undo करायची, रांगेत लावायची, लॉग करायची किंवा गठ्ठ्यात करायची असेल, तर तिला command मध्ये गुंडाळा; अन्यथा मेथड थेट कॉल करा.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन प्रातिनिधिक सिस्टीम जिथे Command पॅटर्न ही भार पेलणारी रचना आहे.

📝

1 · मजकूर आणि ग्राफिक्स editor ची undo history

पॅटर्न: document वर उलटता येणारे बदल

word processor किंवा design tool ला टायपिंगपासून आकार हलवण्यापर्यंत प्रत्येक प्रकारच्या बदलावर अमर्याद undo आणि redo लागते.

  • प्रत्येक बदल - insert, delete, format, move - execute() आणि undo() असलेला एक command आहे.
  • एक undo stack आणि redo stack Ctrl+Z आणि Ctrl+Y ला साध्या push आणि pop मध्ये बदलतात.
  • गटबद्ध केलेले बदल मॅक्रो command बनतात जेणेकरून एक हावभाव एकल एकक म्हणून undo होतो.
✅ निष्कर्ष: वापरकर्ते निर्भयपणे संपादन करतात कारण कोणतीही क्रिया उलटवता येते, आणि editor ची कोड एकसमान राहते कारण invoker सर्व बदलांना सारखेच वागवतो.
📥

2 · Background task queue आणि job workers

पॅटर्न: पुढे ढकललेली, पुन्हा प्रयत्न करता येणारी, लॉग केलेली अंमलबजावणी

सिस्टीमला काम अ‍ॅसिंक्रोनसपणे चालवायचे असते - emails पाठवणे, images प्रक्रिया करणे, data sync करणे - विश्वासार्हपणे आणि audit trail सह.

  • प्रत्येक job हा एक serialize केलेला command आहे जो worker ने चालवण्यासाठी टिकाऊ queue वर ठेवला जातो.
  • अपयशी commands ना कॉल करणाऱ्यांना हात न लावता पुन्हा प्रयत्न केला जातो किंवा dead-letter queue कडे हलवले जाते.
  • command log एकाच वेळी audit trail म्हणून आणि खंडानंतर काम replay करण्याचा मार्ग म्हणून काम करते.
✅ निष्कर्ष: producers वेगवान आणि वेगळे राहतात तर workers स्वतंत्रपणे commands अंमलात आणतात, पुन्हा प्रयत्न करतात आणि लॉग करतात, ज्यामुळे टिकाऊपणा आणि निरीक्षणक्षमता फुकट मिळते.
🏠

3 · Smart-home आणि remote-control ऑटोमेशन

पॅटर्न: अनेक उपकरणांवर एक interface

एक universal remote किंवा home hub ला अनेक विक्रेत्यांच्या lights, blinds आणि media एकाच UI मधून नियंत्रित करावे लागते.

  • प्रत्येक बटण किंवा scene एका विशिष्ट device receiver शी बांधलेला command धरून ठेवतो.
  • "movie night" scene हा एक मॅक्रो command आहे जो एकाच वेळी अनेक device commands चालवतो.
  • एक undo किंवा "all off" command साठवलेल्या पूर्वीच्या states वापरून शेवटची scene उलटवतो.
✅ निष्कर्ष: hub आपले UI न बदलता नवी उपकरणे जोडतो, कारण प्रत्येक नियंत्रण म्हणजे त्याच execute() कॉलमागचा आणखी एक command आहे.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Command हा संग्रहालयातील वस्तूपासून फार दूर आहे; त्याची रचना आधुनिक software architecture मधल्या काही सर्वात सक्रिय कल्पनांचा आधार आहे.

🧩 CQRS command handlers

Command Query Responsibility Segregation प्रत्येक write ला एका handler कडे पाठवलेला command ऑब्जेक्ट म्हणून मांडते, या पॅटर्नचा थेट वंशज.

📜 Event sourcing

commands किंवा events चा append-only log साठवल्याने तुम्ही history replay करून state पुन्हा तयार करू शकता, नेमके log-and-replay वापर प्रकरण.

⚛️ Redux आणि reducers

Front-end state stores action ऑब्जेक्ट्स reducers कडे पाठवतात; time-travel debugging म्हणजे वेशांतर केलेला command history वरचा undo/redo.

🌐 Distributed task queues

Celery आणि Sidekiq सारख्या सिस्टीम commands ना brokers वर serialize करतात जेणेकरून workers त्यांना मशीनभर अंमलात आणतात, पुन्हा प्रयत्न करतात आणि शेड्यूल करतात.

🔄 Sagas आणि rollbacks

दीर्घकाळ चालणारे distributed transactions पूर्वीच्या पायऱ्या undo करण्यासाठी compensating commands वापरतात, क्लाउड प्रमाणावरची मॅक्रो rollback कल्पना.

🤖 Agent tool calls

एक LLM agent संरचित tool invocations उत्सर्जित करतो जे एक runtime अंमलात आणते आणि लॉग करते, हा AI क्रियांना लागू केलेला Command पॅटर्न आहे.

सारांश: Command पॅटर्न म्हणजे तुम्ही एका क्रियेला ओळख कशी देता जेणेकरून तुम्ही तिची वेळ, पुनरावृत्ती आणि उलटवणे नियंत्रित करू शकता. editors पासून event sourcing पर्यंत आणि agent tool वापरापर्यंत, ती कल्पना अधिकाधिक केंद्रस्थानी येत आहे.
