Creational Pattern

Abstract Factory - एकत्र येणाऱ्या ऑब्जेक्ट्सची कुटुंबे

काही ऑब्जेक्ट्स फक्त एकत्रच अर्थपूर्ण ठरतात: Windows बटणासोबत Windows चेकबॉक्स, dark-theme कार्डासोबत dark-theme स्क्रोलबार. Abstract Factory तुम्हाला प्रत्येक कुटुंबासाठी एक factory देते, जेणेकरून तुम्ही एकही concrete class ला नाव न देता संबंधित products चे संपूर्ण संच तयार करू शकता, आणि तुम्ही जे काही बनवता ते सगळे एकाच कुटुंबातून येते याची ते हमी देते.

संपूर्ण प्रवाह पाहा ↓ आकृत्यांकडे जा
Product कुटुंबे classes पेक्षा interfaces सुसंगततेची हमी बदलता येणारे platforms
01 - काय

Abstract Factory म्हणजे काय?

Abstract Factory संबंधित किंवा परस्परावलंबी ऑब्जेक्ट्सची कुटुंबे, त्यांच्या concrete classes न सांगता, तयार करण्यासाठी एक interface पुरवते. Client code फक्त abstract product interfaces (Button, Checkbox) आणि एका abstract factory interface (GUIFactory) शी बोलतो. Runtime ला तुम्ही एकच concrete factory (WindowsFactory किंवा MacFactory) जोडता, आणि ते जे product तयार करते ते प्रत्येक product एकाच कुटुंबातील असल्याची हमी असते.

🏭 Abstract factory

प्रत्येक product प्रकारासाठी एक create method असलेले interface: createButton(), createCheckbox(). ते काय बनवता येईल हे सांगते, कधीच concrete प्रकार नाही.

👪 Product कुटुंबे

प्रत्येक concrete factory एकच सुसंगत संच तयार करते. एक MacFactory नेहमी फक्त Mac widgets परत करते, त्यामुळे Mac बटण कधीच Windows चेकबॉक्सशेजारी बसत नाही.

🔌 Client अनभिज्ञ राहतो

Client ला एक factory आणि abstract products दिले जातात. तो कधीच new WindowsButton() पाहत नाही, त्यामुळे तुम्ही जे कुटुंब inject कराल त्यासोबत तो काम करतो.

मुख्य भूमिका

भूमिकाती काय करतेउदाहरण
Abstract Factoryप्रत्येक abstract product साठी creation methods घोषित करतेGUIFactory
Concrete Factoryएका कुटुंबासाठी त्या methods implement करतेWindowsFactory, MacFactory

मुख्य मानसिक मॉडेल: Factory Method inheritance द्वारे एक product बनवते. Abstract Factory composition द्वारे संबंधित products चा संच बनवते. तुम्ही एक factory inject करता आणि जुळणारा संच मिळवता, कधीच विसंगत जोडी नाही.
02 - का

Abstract Factory का अस्तित्वात आहे

ज्या क्षणी तुमचा code अनेक फाइल्समध्ये new ConcreteThing() कॉल्स विखुरवतो, तेव्हा संपूर्ण कुटुंब बदलणे search-and-replace चे दुःस्वप्न बनते, आणि विसंगत भाग एकत्र मिसळण्यापासून तुम्हाला कोणीही रोखत नाही. Abstract Factory कुटुंबाची निवड एका ऑब्जेक्टमध्ये केंद्रित करते.

🧩 सुसंगततेची हमी

कारण एकच factory संपूर्ण संच बनवते, products नेहमी जुळतात. तुम्ही चुकून dark-theme स्क्रोलबार light-theme पॅनेलसोबत जोडू शकत नाही - type system एका factory ला मिश्रित भाग परत करू देणार नाही.

🔀 एका ओळीत कुटुंबे बदला

Windows विरुद्ध Mac, किंवा MySQL विरुद्ध Postgres निवडणे हे सुरुवातीला एकच निर्णय बनते: concrete factory निवडा. उर्वरित अ‍ॅप कधीच बदलत नाही.

🚪 Client ला concretes पासून decouple करते

Client code फक्त interfaces वर अवलंबून असतो, Dependency Inversion Principle चा मान राखतो. नवीन कुटुंब जोडल्याने विद्यमान client code ला स्पर्श होत नाही.

🎯 Single Responsibility

Object creation factories मध्ये राहते, business logic मध्ये पसरलेले नसते. एका कुटुंबाचे बांधणीचे नियम एकाच ठिकाणी असतात, शोधायला आणि test करायला सोपे.

सोप्या शब्दांत

उपमांसह Abstract Factory ची समज

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ते समजते.

🎓 विद्यार्थ्यासाठी

हे एका थीम असलेल्या स्टेशनरी संचासारखे आहे. "अंतराळ" संच निवडा आणि तुम्हाला अंतराळ वही, अंतराळ पेन आणि अंतराळ फोल्डर मिळते जे सगळे जुळतात. "समुद्र" निवडा आणि सगळे एकत्र बदलते. तुम्हाला कधीच अंतराळ फोल्डरमध्ये समुद्री पेन मिळत नाही.

👩‍💻 डेव्हलपरसाठी

हे बदलता येणाऱ्या ब्रँड्ससह असलेले toolbox interface आहे. तुमचा code toolbox.getWrench() आणि toolbox.getDrill() कॉल करतो. सुरुवातीला त्याला DeWalt toolbox द्या किंवा Makita toolbox; कॉल करणारा code दोन्ही बाबतीत सारखाच असतो.

🏢 व्यावसायिकासाठी

संग्रहानुसार फर्निचर कॅटलॉग कल्पना करा. एक हॉटेल "Modern" संग्रह मागवते आणि जुळणारी खुर्ची, सोफा आणि टेबल मिळवते. "Victorian" कडे वळणे म्हणजे एकाच पुरवठादाराकडून संपूर्ण समन्वित संच पुन्हा मागवणे, ते एकत्र योग्य दिसतील याची हमी देत.

🍔 रोजच्या जीवनातील आवृत्ती

एक फास्ट-फूड कॉम्बो जेवण. "combo 2" मागवा आणि किचन एकत्र जाणारे विशिष्ट बर्गर, साइड आणि पेय जमवते. तुम्ही कॉम्बो निवडता, प्रत्येक वस्तू नाही, आणि कर्मचारी संच सुसंगत असल्याची हमी देतात.

03 - कसे

पडद्यामागे ते कसे कार्य करते

तुम्ही factory साठी आणि प्रत्येक product साठी abstract interfaces परिभाषित करता. Concrete factories त्या factory interface ला implement करतात, एकाच कुटुंबाचे concrete products परत करत. Client ला एक factory मिळतो आणि तो त्याद्वारे सगळे बनवतो.

🧱 करार परिभाषित करा

एक Button आणि Checkbox interface लिहा, मग प्रत्येकासाठी create method असलेले GUIFactory interface. Client कधीही import करणार असलेले हेच एकमेव प्रकार आहेत.

🎚️ काठावर कुटुंब जोडा

सुरुवातीला OS किंवा config ओळखा आणि जुळणारे concrete factory एकदाच instantiate करा. ते client मध्ये inject करा, जेणेकरून कुटुंबाची निवड नेमक्या एकाच ठिकाणी होते.

Java मधील वास्तववादी implementation

// Abstract products - the client depends only on these
interface Button   { void render(); }
interface Checkbox { void toggle(); }

// Abstract factory - one create method per product kind
interface GUIFactory {
    Button   createButton();
    Checkbox createCheckbox();
}

// Family 1: Windows
class WindowsButton   implements Button   { public void render() { System.out.println("[ Win Button ]"); } }
class WindowsCheckbox implements Checkbox { public void toggle() { System.out.println("Win check toggled"); } }
class WindowsFactory  implements GUIFactory {
    public Button   createButton()   { return new WindowsButton(); }
    public Checkbox createCheckbox() { return new WindowsCheckbox(); }
}

// Family 2: macOS
class MacButton   implements Button   { public void render() { System.out.println("( Mac Button )"); } }
class MacCheckbox implements Checkbox { public void toggle() { System.out.println("Mac check toggled"); } }
class MacFactory  implements GUIFactory {
    public Button   createButton()   { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}

// Client - never mentions a concrete product
class Application {
    private final Button   button;
    private final Checkbox checkbox;
    Application(GUIFactory factory) {          // family injected once
        this.button   = factory.createButton();
        this.checkbox = factory.createCheckbox();
    }
    void paint() { button.render(); checkbox.toggle(); }
}

class Main {
    public static void main(String[] args) {
        GUIFactory factory = System.getProperty("os.name").startsWith("Mac")
                ? new MacFactory()
                : new WindowsFactory();
        new Application(factory).paint();      // matched family, guaranteed
    }
}

लक्षात घ्या की Application कधीच new WindowsButton() लिहित नाही. त्याला एक GUIFactory मिळतो आणि एक सुसंगत संच मिळतो. कुटुंबाची निवड एकदाच, main मध्ये होते, त्यामुळे widgets कधीच विसंगत असू शकत नाहीत.

सामान्य अडचणी

अडचणी आणि anti-patterns

Abstract Factory स्थिर कुटुंबे आणि अनेक platforms सोबत फायदेशीर ठरते. खूप लवकर त्याकडे वळा आणि तुम्ही औपचारिकतेत बुडता.

🥱 अकाली abstraction

तुमच्याकडे नेहमी फक्त एकच कुटुंब असेल, तर अतिरिक्त interfaces हे निव्वळ ओझे आहे. दुसरे कुटुंब प्रत्यक्षात दिसेपर्यंत साधा constructor अधिक स्पष्ट असतो.

➕ नवीन product = सगळ्याला स्पर्श

Product प्रकार जोडणे म्हणजे factory interface आणि प्रत्येक concrete factory बदलणे. कुटुंबे जोडणे सोपे; products महाग. Product अक्ष आधीच काळजीपूर्वक आखा.

🔎 Concrete प्रकार गळणे

Client code WindowsButton कडे downcast करत असेल किंवा instanceof तपासत असेल, तर abstraction तुटते आणि सुसंगततेची हमी नाहीशी होते.

🧨 Class स्फोट

M product प्रकार आणि N कुटुंबे असल्यास तुम्हाला M x N concrete classes आणि N factories मिळतात. मोठ्या grids वर हे झपाट्याने फुगते आणि navigate करणे कठीण होते.

🔀 Factory Method शी गोंधळ

तुम्हाला प्रत्यक्षात products च्या कुटुंबाची गरज असताना inheritance आणि प्रत्येक product साठी subclass वापरणे, किंवा उलट, यामुळे अस्ताव्यस्त, जबरदस्ती केलेल्या hierarchies निर्माण होतात.

🌍 Global factory singleton

Factory inject करण्याऐवजी लपवलेल्या global factory कडे वळणे dependency लपवते, testability ला हानी पोहोचवते, आणि runtime ला कुटुंबे बदलणे अवघड करते.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Abstract Factory आगाऊ रचनेच्या किंमतीवर सुसंगतता आणि बदलण्याजोगेपणा विकत घेते. तुम्हाला खरोखर किती कुटुंबे लागतात याच्या तुलनेत त्याचे मूल्यमापन करा.

पैलूतपशील
फायदेएका कुटुंबातील products एकत्र वापरले जातील याची हमी देते; client ला concrete classes पासून decouple करते; बांधणी वेगळी करते; नवीन कुटुंब जोडणे क्षुल्लक आणि विद्यमान code साठी बंद असते.
तोटेलहान grids साठीसुद्धा अनेक interfaces आणि classes; नवीन product प्रकार जोडल्याने factory interface आणि प्रत्येक concrete factory मध्ये लाट पसरते; जड औपचारिकतेसारखे वाटू शकते.
केव्हा वापरावेतुमच्या system ला संबंधित products च्या अनेक कुटुंबांसोबत काम करावे लागेल (cross-platform UI, अनेक DB backends, themes) आणि कुटुंब कधीच मिसळले जाणार नाही हे तुम्हाला अंमलात आणायचे आहे.
केव्हा टाळावेफक्त एकच कुटुंब असेल, किंवा products असंबंधित असून स्वतंत्रपणे बदलत असतील. साधे factory किंवा साधा constructor हलका आणि स्पष्ट असतो.
क्लिष्टतामध्यम. Factory Method पेक्षा जास्त हलणारे भाग, पण प्रत्येक भाग लहान असतो. किंमत कुटुंबांपेक्षा (जोडायला सोपे) product प्रकारांसोबत (जोडायला कठीण) जास्त वाढते.
संबंधितFactory Method (inheritance द्वारे एक product), Builder (टप्प्याटप्प्याने जमवणी), Prototype (बांधणीऐवजी clone), Bridge (implementation पासून abstraction वेगळे करणे).
अंगठ्याचा नियम: जेव्हा product प्रकारांचा संच स्थिर असतो पण कुटुंबांची संख्या वाढणार असते तेव्हा Abstract Factory निवडा. त्याऐवजी तुम्ही नवीन product प्रकार जोडत राहिलात, तर पॅटर्न तुमच्याशी झगडतो - रचनेचा पुनर्विचार करा.
06 - केस स्टडीज

प्रत्यक्ष जगातील केस स्टडीज

तीन प्रातिनिधिक ठिकाणे जिथे संबंधित ऑब्जेक्ट्सची कुटुंबे सुसंगत राहिली पाहिजेत.

🖥️

1 · Cross-platform UI toolkit

पॅटर्न: प्रत्येक operating system साठी एक widget कुटुंब

एका desktop अ‍ॅपला सगळीकडे UI code शाखेत विभागल्याशिवाय Windows, macOS आणि Linux वर native दिसले पाहिजे.

  • एक GUIFactory createButton, createCheckbox आणि createMenu उघड करते.
  • प्रत्येक OS साठी एक concrete factory त्या platform चे natively styled widgets परत करते.
  • अ‍ॅप सुरुवातीला OS ओळखतो आणि जुळणारे factory एकदाच inject करतो.
✅ परिणाम: प्रत्येक स्क्रीन सुसंगत native लुक render करते, आणि नवीन platform जोडणे म्हणजे एक factory आणि त्याचे widgets लिहिणे, विद्यमान स्क्रीनमध्ये शून्य बदलांसह.
🗄️

2 · Pluggable database backends

पॅटर्न: प्रत्येक vendor साठी DB ऑब्जेक्ट्सचे कुटुंब

एका ORM ला MySQL आणि PostgreSQL ला आधार द्यावा लागतो, प्रत्येकाला स्वतःचे connection, command आणि dialect ऑब्जेक्ट्स लागतात जे जुळले पाहिजेत.

  • एक DbFactory Connection, Command आणि QueryBuilder ऑब्जेक्ट्स तयार करते.
  • MySqlFactory आणि PostgresFactory फक्त त्यांच्या vendor च्या implementations परत करतात.
  • Config factory निवडते, त्यामुळे Postgres command कधीच MySQL connection वर चालू शकत नाही.
✅ परिणाम: Database vendors बदलणे हा config बदल आहे, आणि type system vendor-विसंगत ऑब्जेक्ट्स कधीही एकत्र होण्यापासून रोखते.
🎨

3 · Design system ला theme देणे

पॅटर्न: सुसंगत light आणि dark component संच

एका web component library ला light आणि dark themes लागतात जिथे प्रत्येक घटक - card, input, tooltip - सक्रिय theme शी जुळतो.

  • एक ThemeFactory styled cards, inputs आणि tooltips तयार करते.
  • LightThemeFactory आणि DarkThemeFactory प्रत्येक एक पूर्णपणे समन्वित संच देतात.
  • एकच toggle factory बदलते, संपूर्ण UI एका theme मध्ये पुन्हा render करत.
✅ परिणाम: Themes अर्धवट styled स्क्रीनशिवाय अंतर्गतरित्या सुसंगत राहतात, आणि नवीन themes component logic ला स्पर्श न करता अतिरिक्त factories म्हणून जोडल्या जातात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Abstract Factory दशकांपूर्वीचे आहे, पण ते जी समस्या सोडवते - स्थिर interface मागे सुसंगत कुटुंबे बदलणे - ती कधीही नव्हती इतकी सामान्य आहे.

💉 Dependency injection

आधुनिक DI containers ही मोठ्या प्रमाणावरील Abstract Factory आहेत: तुम्ही एका interface ला implementation संचाशी एकदाच bind करता, आणि container संपूर्ण अ‍ॅपमध्ये एक सुसंगत कुटुंब जोडतो.

☁️ Cloud provider abstraction

AWS, Azure आणि GCP ला लक्ष्य करणाऱ्या libraries प्रत्येक cloud साठी एक factory उघड करतात जेणेकरून storage, queue आणि secrets clients नेहमी एकाच provider कडून येतात.

🧪 Test doubles

एक नकली factory inject केल्याने tests ला एकाच वेळी stub products चे संपूर्ण कुटुंब पुरवता येते, unit tests ला प्रत्यक्ष platform code पासून वेगळे ठेवत.

🔧 Feature-flagged rollouts

एका flag मागे factory बदलल्याने काही वापरकर्त्यांना नवीन सुसंगत implementation संच पाठवला जातो, तर बाकीचे सगळे जुने कुटुंब ठेवतात.

🌐 Multi-tenant systems

प्रति-tenant factories tenant-विशिष्ट पण अंतर्गतरित्या सुसंगत ऑब्जेक्ट्स देतात - billing, storage आणि policy - request च्या वेळी tenant नुसार निवडलेले.

🧱 Functional variants

First-class functions असलेल्या भाषांमध्ये, factory constructor functions च्या एका record पर्यंत आकुंचित होऊ शकते, पण कुटुंब-सुसंगततेची कल्पना एकसारखीच असते.

सारांश: जेव्हा तुम्हाला एका स्थिर जोडामागे implementations चा जुळणारा संच बदलावा लागतो आणि ते कधीच मिसळले जाणार नाहीत याची हमी द्यावी लागते, तेव्हा तुम्ही Abstract Factory कडे वळत असता - मग तुम्ही त्याला तसे म्हणा किंवा DI binding.
