Behavioral Pattern

Interpreter पॅटर्न - एका छोट्या भाषेचे objects मध्ये रूपांतर

काही समस्या ठराविक, रचनाबद्ध स्वरूपात पुन्हा पुन्हा येत राहतात: filter नियम, सूत्रे, search queries, feature flags. Interpreter पॅटर्न म्हणतो: त्या पुनरावृत्त स्वरूपाला एक grammar द्या, प्रत्येक grammar नियमाला एका class म्हणून मांडा, आणि त्या objects च्या tree मधून फिरून एका वाक्याचे मूल्यमापन करा. प्रत्येक node ला स्वतःचा अर्थ कसा लावायचा हे माहित असते, त्यामुळे भाषा एका लहान, जोडता येण्याजोग्या object graph मध्ये बदलते.

01 - काय

Interpreter पॅटर्न म्हणजे काय?

Interpreter हा एक behavioral पॅटर्न आहे जो, एक साधी grammar असलेली भाषा दिली असता, त्या grammar साठी एक प्रतिनिधित्व (representation) आणि त्या प्रतिनिधित्वाचा वापर करून भाषेतील वाक्यांचे मूल्यमापन करणारा interpreter परिभाषित करतो. grammar चा प्रत्येक नियम एक class बनतो, वाक्ये त्या class च्या instances च्या tree बनतात (एक abstract syntax tree), आणि एक सामायिक interpret(context) method tree चे recursive पद्धतीने मूल्यमापन करतो.

📐 एक grammar

production नियमांचा एक लहान, स्थिर संच, उदाहरणार्थ "expression म्हणजे एक संख्या, किंवा + अथवा * ने जोडलेली दोन expressions". जेव्हा ही grammar क्वचितच बदलते तेव्हा Interpreter योग्य ठरतो.

🌳 एक syntax tree

3 + 4 * 2 सारखे एक ठोस वाक्य expression objects च्या tree मध्ये बदलते. tree चा आकार कच्चा मजकूर नव्हे तर precedence आणि रचना दर्शवतो.

▶️ एक interpreter

root वर एक polymorphic interpret(context) कॉल संपूर्ण tree मधून फिरतो, प्रत्येक node आपल्या children चे निकाल एका मूल्यात एकत्र करतो.

02 - का

Interpreter पॅटर्न का अस्तित्वात आहे

जेव्हा एखादी पुनरावृत्त समस्या खरे तर एक छोटी भाषा असते, तेव्हा तिचे मूल्यमापन करण्यासाठी if/else चे जंगल हार्डकोड करणे देखभालीयोग्य राहत नाही. Interpreter त्या भाषेला first-class objects मध्ये बदलतो जे तुम्ही जोडू शकता, विस्तारू शकता आणि ज्यांबद्दल तर्क करू शकता.

🧩 Grammar classes शी जुळते

प्रत्येक production नियम एक class बनतो. code ची रचना भाषेच्या रचनेला प्रतिबिंबित करते, त्यामुळे grammar स्वतः type hierarchy द्वारेच दस्तऐवजित होते.

➕ नियम विस्तारणे सोपे

नवीन operator किंवा नियम जोडणे म्हणजे बहुधा एक नवीन expression class जोडणे. सध्याचे nodes अस्पर्श राहतात कारण मूल्यमापन polymorphic आहे, एखादा प्रचंड switch नाही.

🔁 अनेक वेळा स्वस्तात मूल्यमापन

एका नियमाला एकदा tree मध्ये parse करा, मग हजारो वेगवेगळ्या contexts विरुद्ध त्याचा अर्थ लावा. महागडा parsing खर्च प्रत्येक मूल्यमापनाला नव्हे तर एकदाच द्यावा लागतो.

🔓 वापरकर्ते logic ला data म्हणून मांडतात

प्रोग्रामर नसलेले लोक age > 18 AND country = 'US' सारखे नियम लिहू शकतात आणि तुमचे app त्यांना अनियंत्रित code चालवण्याऐवजी सुरक्षित, sandboxed trees मध्ये बदलते.

सोप्या शब्दांत

उपमांसह Interpreter समजावून

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असलात तरी ते पटकन समजेल.

🎓 विद्यार्थ्यासाठी

हे व्याकरणाच्या तासात वाक्याचे पृथक्करण करण्यासारखे आहे. "मांजर बसली" हे कर्ता आणि विधेय मध्ये विभागते, जे पुढे विभागतात. अर्थ शोधण्यासाठी तुम्ही त्या पृथक्करणातून फिरता, लहान भाग एकत्र करून संपूर्ण बनवता.

👩‍💻 डेव्हलपरसाठी

एका calculator च्या expression tree चा विचार करा. 3 + 4 * 2 हे अशा tree मध्ये parse होते जिथे * हे + च्या खाली बसते. root वर eval() कॉल केल्यावर ते खाली recursion करते आणि 11 वर परत आणते.

🏢 व्यावसायिकासाठी

हे एक rules engine आहे. व्यवसाय एका लहान DSL मध्ये पात्रता नियम लिहितो, engine प्रत्येकाला conditions च्या tree मध्ये compile करते, मग code deploy न करता प्रत्येक येणाऱ्या record विरुद्ध ते tree चालवते.

🎼 रोजच्या जीवनातील आवृत्ती

sheet music वाचणे. प्रत्येक चिन्ह एक terminal आहे, वाक्यांश चिन्हे गटात करतात, आणि एक रचना ही वाक्यांशांची tree आहे. एक संगीतकार प्रत्येक भाग क्रमाने प्रक्रिया करून संपूर्ण score चा "अर्थ लावतो".

03 - कसे

अंतर्गत ते कसे काम करते

दोन हालचाली आहेत: एक class hierarchy परिभाषित करा जिथे प्रत्येक grammar नियम एक expression आहे, मग tree च्या root वर एक polymorphic method कॉल करून मूल्यमापन करा. Terminals recursion थांबवतात, non-terminals ती पुढे चालवतात.

🌿 Terminal expressions

children नसलेली tree ची पाने: Number(7) सारखी literals किंवा Variable("x") सारखी lookups. गरज पडल्यास context मधून वाचून ते थेट स्वतःचा अर्थ लावतात.

🌲 Non-terminal expressions

इतर expressions पासून बनलेले नियम: Add(left, right), And(a, b). ते आधी आपल्या children चा अर्थ लावतात, मग निकाल एकत्र करतात. हे recursion हेच संपूर्ण engine आहे.

Java मधील एक चालणारा arithmetic interpreter

import java.util.Map;

// AbstractExpression: the shared contract
interface Expression {
    int interpret(Map<String, Integer> context);
}

// TerminalExpression: a literal number, a leaf
class NumberExpr implements Expression {
    private final int value;
    NumberExpr(int value) { this.value = value; }
    public int interpret(Map<String, Integer> ctx) { return value; }
}

// TerminalExpression: a variable looked up in the context
class VariableExpr implements Expression {
    private final String name;
    VariableExpr(String name) { this.name = name; }
    public int interpret(Map<String, Integer> ctx) {
        Integer v = ctx.get(name);
        if (v == null) throw new IllegalStateException("Unbound: " + name);
        return v;
    }
}

// NonterminalExpression: recurses into its children
class AddExpr implements Expression {
    private final Expression left, right;
    AddExpr(Expression left, Expression right) { this.left = left; this.right = right; }
    public int interpret(Map<String, Integer> ctx) {
        return left.interpret(ctx) + right.interpret(ctx);
    }
}

class MultiplyExpr implements Expression {
    private final Expression left, right;
    MultiplyExpr(Expression left, Expression right) { this.left = left; this.right = right; }
    public int interpret(Map<String, Integer> ctx) {
        return left.interpret(ctx) * right.interpret(ctx);
    }
}

// Client: build the AST for  x + 4 * 2  and evaluate with x = 3
class Demo {
    public static void main(String[] args) {
        Expression ast = new AddExpr(
            new VariableExpr("x"),
            new MultiplyExpr(new NumberExpr(4), new NumberExpr(2))
        );
        System.out.println(ast.interpret(Map.of("x", 3))); // prints 11
    }
}

लक्षात घ्या की tree आधीच precedence दर्शवते: MultiplyExpr हे AddExpr च्या आत nested आहे, म्हणून ते आधी मूल्यमापन होते. हा पॅटर्न रचना (tree बांधणे, बहुधा parser चे काम) या चिंतेला अर्थ (प्रत्येक node ची interpret method) पासून वेगळे करतो.

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

फळ्यावरील एका ढोबळ grammar पासून खरी वाक्ये मूल्यमापन करणाऱ्या चालत्या interpreter पर्यंत - संपूर्ण प्रवास क्रमाने.

00
व्याप्ती

ती एक छोटी भाषा आहे याची खात्री करा

समस्या खरेच एक स्थिर छोटी grammar आहे का ते तपासा - नियम, सूत्रे, filters - आणि ती पूर्ण programming language नाही. जर grammar मोठी किंवा अस्थिर असेल, तर थांबा आणि त्याऐवजी parser generator वापरा.

10
Grammar

production नियम लिहा

grammar स्पष्टपणे मांडा, उदाहरणार्थ: expr म्हणजे number, किंवा variable, किंवा expr + expr, किंवा expr * expr. प्रत्येक production ओळ एका class शी जुळेल.

20
Interface

AbstractExpression परिभाषित करा

सामायिक करार तयार करा, प्रत्येक expression अंमलात आणेल अशी एकच interpret(context) method. हाच तो सांधा आहे जो tree ला polymorphic बनवतो.

30
Terminals

leaf classes बांधा

Number आणि Variable सारख्या terminal expressions अंमलात आणा. त्या थेट एक मूल्य परत करतात, आणि बाह्य state ची गरज असल्यास context मधून वाचतात.

40
Non-terminals

composite नियम बांधा

Add आणि Multiply सारखी non-terminal expressions अंमलात आणा जी child expressions धारण करतात आणि त्यांचे interpret केलेले निकाल एकत्र करतात.

50
Context

context परिभाषित करा

मूल्यमापनाला कोणती सामायिक state लागते ते ठरवा: variable bindings, तपासला जाणारा record, किंवा एक बदलता येणारा accumulator. तो प्रत्येक interpret कॉलमधून पास करा.

60
tree बांधा

AST रचा

एका ठोस वाक्यासाठी expression objects एकत्र करून tree बनवा. tests साठी ते हाताने करा, किंवा खऱ्या input साठी parser मधून तयार करा.

70
Parse

मजकुराचे tree मध्ये रूपांतर करा

एक लहान parser जोडा जो वापरकर्त्याचा input वाचतो आणि precedence ला मान देत AST बाहेर काढतो. यामुळे callers ला हाताने nodes बांधावी लागत नाहीत.

80
मूल्यमापन

root चा अर्थ लावा

root.interpret(context) कॉल करा. recursion tree मधून फिरते, terminals मूल्ये परत करतात, non-terminals ती एकत्र करतात, आणि उत्तर वर येते.

90
विस्तार

नियम आणि operations जोडा

एक expression class जोडून नवीन operator ला आधार द्या. जर एकाच tree वर अनेक नवीन operations लागत असतील, तर प्रत्येक node फुगवण्याऐवजी वर एक Visitor स्तर लावा.

100
कणखर करा

तपासा, cache करा आणि पुन्हा वापरा

types तपासा, unbound variables पासून रक्षण करा, parse केलेली trees cache करा, आणि contexts मध्ये त्या पुन्हा वापरा. आता ती भाषा एक सुरक्षित, जोडता येण्याजोगी मालमत्ता आहे.

सामान्य अडचणी

अडचणी आणि anti-patterns

Interpreter छोट्या भाषांसाठी सुंदर आहे आणि मोठ्यांसाठी एक सापळा. या त्याच्या नेहमीच्या चुकीच्या वाटा आहेत.

📈 सतत वाढत जाणारी grammar

प्रत्येक नवीन नियम एक नवीन class असतो. डझनभर नियमांच्या पलीकडे hierarchy स्फोट होते आणि देखभालीयोग्य राहत नाही. मोठी किंवा उत्क्रांत होणारी grammar हे parser generator कडे वळण्याचे संकेत आहे.

🔀 nodes मध्ये कोंबलेले parsing

Interpreter tree आणि तिचे मूल्यमापन परिभाषित करतो, ती मजकुरातून कशी बांधायची हे नव्हे. tokenizing आणि parsing हे expression classes मध्ये मिसळल्याने दोन अगदी वेगळ्या चिंता गुंतागुंतीच्या होतात.

🧨 नवीन operation प्रत्येक class ला स्पर्श करते

pretty-printing किंवा type-checking सारखे दुसरे operation जोडल्याने सर्व node classes मध्ये बदल करावे लागतात. जेव्हा operations वाढतात, तेव्हा प्रत्येक node फुगवण्याऐवजी Visitor कडे वळा.

🕳️ खोल trees stack उधळतात

भाबडे recursive interpretation खोलवर nested input वर call stack overflow करू शकते. input ची खोली मर्यादित करा किंवा स्पष्ट stack वापरून iterative पद्धतीने मूल्यमापन करा.

🐌 प्रत्येक कॉलवर पुन्हा parsing

प्रत्येक मूल्यमापनाला मजकूर tree मध्ये parse करणे या पॅटर्नचा सर्वात मोठा फायदा वाया घालवते. एकदा parse करा, मग अनेक contexts मध्ये AST पुन्हा वापरा.

🎭 सर्वसामान्य भाषा म्हणून वापरणे

Interpreter हा संकुचित DSLs साठी आहे, खरी programming language बांधण्यासाठी नाही. जर तुम्हाला variables, functions आणि control flow लागत असतील, तर तुम्ही पॅटर्नच्या बाहेर वाढला आहात.

तडजोडी

तडजोडी आणि केव्हा वापरावे

वारंवार मूल्यमापन होणाऱ्या लहान, स्थिर grammars साठी Interpreter उजळून निघतो, आणि भाषा वाढत गेल्यास झगडतो. निर्णय घेण्याआधी त्याची खऱ्या parser शी तुलना करा.

पैलूतपशील
फायदेGrammar व्यवस्थितपणे classes शी जुळते, नवीन नियम जोडणे सोपे, वाक्ये पुन्हा वापरता येणाऱ्या trees बनतात, logic code ऐवजी सुरक्षित data म्हणून मांडता येते.
तोटेgrammar च्या आकारासोबत class संख्या वाढते, गुंतागुंतीच्या भाषांसाठी बोजड होते, नवीन operations जोडणे प्रत्येक node ला स्पर्श करते, recursion संथ किंवा stack-भारी असू शकते.
केव्हा वापरावेgrammar लहान आणि स्थिर असते, वाक्ये ठराविक स्वरूपात पुन्हा येतात (filters, सूत्रे, feature flags), आणि तुम्हाला एकाच नियमांविरुद्ध अनेक inputs मूल्यमापन करायची असतात.
केव्हा टाळावेgrammar मोठी किंवा उत्क्रांत होणारी असते, performance महत्त्वाची असते, किंवा तुम्हाला पूर्ण भाषा लागते. ANTLR, हाताने लिहिलेला recursive-descent parser, किंवा खरा DSL toolkit वापरा.
गुंतागुंतमूठभर नियमांसाठी कमी ते मध्यम; grammar च्या आकारासोबत वेगाने वाढते. मूल्यमापनाचे logic साधे recursion आहे; देखभालीचा खर्च म्हणजे class स्फोट.
संबंधितComposite (tree चा आकार), Visitor (nodes ला स्पर्श न करता operations जोडा), Iterator (tree मधून फिरा), Strategy (एका node चे मूल्यमापन बदला).
अंगठ्याचा नियम: जर तुम्ही संपूर्ण grammar एका रुमालावर लिहू शकत असाल आणि ती फारशी बदलणार नसेल, तर Interpreter एक आनंद आहे. ज्या क्षणी तिला precedence tables, error recovery, किंवा डझनभर नियम लागतात, त्या क्षणी parser तयार करा आणि Interpreter फक्त लहान मूल्यमापन गाभ्यासाठीच ठेवा.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

production-सदृश वापरात Interpreter दर्शवणारे तीन प्रातिनिधिक नमुने.

🎯

1 · Feature-flag आणि targeting नियम

नमुना: user record वर boolean expression tree

एक product संघ features सुरक्षितपणे रोल आउट करण्यासाठी नॉन-इंजिनियर लोकांना plan = 'pro' AND (country = 'US' OR beta = true) सारखे targeting नियम लिहू देतो.

  • प्रत्येक नियम And, Or, Equals, आणि GreaterThan expressions च्या tree मध्ये parse होतो.
  • context म्हणजे सध्याच्या user चे attributes, त्यामुळे तेच tree प्रत्येक request ला मूल्यमापन करते.
  • नियम database मध्ये data असतात, code नव्हे, त्यामुळे बदल deploy शिवाय पाठवले जातात.
✅ परिणाम: Product managers स्वतः targeting बदलतात, आणि engine लहान, sandboxed expression classes च्या संचाविरुद्ध लाखो records मूल्यमापन करते.
🧮

2 · Spreadsheet-शैलीचे formula engine

नमुना: cell references सह arithmetic AST

एक analytics साधन वापरकर्त्यांना report fields मध्ये revenue - cost * 1.2 सारखी सूत्रे टाइप करू देते.

  • सूत्रे number, cell-reference, आणि operator nodes असलेल्या arithmetic expression trees मध्ये parse होतात.
  • Cell references या terminal expressions आहेत ज्या sheet context मधून थेट मूल्ये वाचतात.
  • parse केलेले tree cache होते आणि जेव्हा एखादे input cell बदलते तेव्हा पुन्हा मूल्यमापन होते.
✅ परिणाम: वापरकर्त्यांना थेट, पुन्हा गणना होणारी सूत्रे मिळतात तर engine parsing आणि मूल्यमापन स्वच्छपणे वेगळे आणि जलद ठेवते.
🔍

3 · Search आणि query filters

नमुना: मूल्यमापन करता येणाऱ्या tree मध्ये compile केलेली DSL

एक log platform events फिल्टर करण्यासाठी level:error AND service:auth NOT env:test सारखी query भाषा उपलब्ध करते.

  • Queries match, and, or, आणि not expressions च्या tree मध्ये parse होतात.
  • तेच tree एकतर memory मध्ये मूल्यमापन होते किंवा index query मध्ये अनुवादित होते.
  • range किंवा regex सारखे नवीन match प्रकार नवीन expression classes म्हणून जोडले जातात.
✅ परिणाम: इंजिनियर अभिव्यक्त filters लिहितात, आणि platform अंदाजित, चाचणीयोग्य वर्तनासह streaming events विरुद्ध प्रत्येकाचा अर्थ लावते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

शास्त्रीय पॅटर्न लहान आहे, पण त्याचा आकार rules engines पासून compilers पर्यंत आश्चर्यकारकपणे मोठ्या प्रमाणात आधुनिक tooling ला आधार देतो.

⚙️ Rules आणि policy engines

Feature flags, pricing, fraud, आणि access policies या सर्व लहान भाषा आहेत ज्या trees म्हणून मूल्यमापन होतात. बहुतेक rules engines चे धडधडणारे हृदय Interpreter आहे.

🌳 सर्वत्र ASTs

Linters, formatters, आणि codemods हे सर्व एक abstract syntax tree बांधतात आणि त्यातून फिरतात. Interpreter जी AST कल्पना औपचारिक करतो ती आता प्रमाणित developer infrastructure आहे.

🧭 Visitor हा नैसर्गिक साथीदार

खरे compilers Interpreter मधील tree ठेवतात पण operations visitors मध्ये हलवतात, त्यामुळे type-checking, optimization, आणि codegen nodes च्या बाहेर राहतात.

🛡️ सुरक्षित user-पुरवठा केलेले logic

eval चालवण्याऐवजी user input ला एका मर्यादित expression tree मध्ये बदलणे हा एक सुरक्षा विजय आहे. पॅटर्न एक नियम काय करू शकतो ते sandbox करतो.

🔤 अंतर्गत DSLs आणि query builders

Fluent query builders आणि अंतर्गत DSLs code मध्ये expression trees एकत्र करतात, मग त्यांचा अर्थ लावतात किंवा अनुवाद करतात, अगदी Interpreter चा आकार.

🚀 फक्त अर्थ न लावता compile करा

Hot paths वाढत्या प्रमाणात tree एकदा bytecode किंवा native code मध्ये compile करतात, वाचनीय object model ठेवतात पण per-node dispatch खर्च टाकून देतात.

सारांश: Interpreter लहान ठेवणे उत्तम - एका संकुचित, स्थिर भाषेला class hierarchy देऊन तिचे मूल्यमापन करण्याचा एक नीटनेटका मार्ग. त्याची कमाल मर्यादा जाणा: जेव्हा grammar वाढते, तेव्हा parser तयार करा आणि Visitor ला operations वाहू द्या, पण object-चे-tree हा सुंदर गाभा टिकवून ठेवा.
