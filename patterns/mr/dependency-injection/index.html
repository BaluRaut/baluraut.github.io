Dependency Injection - class ला त्याचे सहकारी स्वतः बनवण्याऐवजी हातात द्या

जी class स्वतःचा database client, mailer, आणि clock स्वतः बनवते ती त्या नेमक्या implementations शी कायमची जोडली जाते. Dependency Injection हे उलटे करते: सहकारी बाहेरून दिले जातात, त्यामुळे तीच OrderService production मध्ये खऱ्या Postgres repository वर आणि tests मध्ये जलद in-memory fake वर, कोणताही code बदल न करता चालू शकते.

01 - काय

Dependency Injection म्हणजे काय?

Dependency Injection (DI) म्हणजे एखाद्या object ला त्याला लागणारे सहकारी स्वतः बनवू किंवा शोधू न देता बाहेरून देण्याची पद्धत. एखादी OrderService स्वतःच्या body मध्ये new PostgresOrderRepository(), new SmtpMailer(), आणि new SystemClock() कॉल करण्याऐवजी, ती तीन objects तिच्या हातात दिली जातात, बहुतेक वेळा तिच्या constructor मार्फत. ती service ते काय करतात यावर अवलंबून असते, जे interfaces मध्ये व्यक्त होते, कोणती concrete class ते पुरवते यावर नाही.

🏗️ Constructor injection

आवश्यक सहकारी constructor arguments म्हणून येतात. त्यांच्याशिवाय object कधीच वैध नसते, त्यामुळे अर्धवट बांधलेली अवस्था राहत नाही. हा default आणि पसंतीचा प्रकार आहे.

🔧 Setter injection

एखादा ऐच्छिक सहकारी construction नंतर setter किंवा property मार्फत दिला जातो. metrics sink सारख्या खरोखर ऐच्छिक वर्तनासाठी उपयुक्त, पण यामुळे object पूर्णपणे जोडले जाण्याआधीच अस्तित्वात येऊ शकते.

📨 Method injection

एखादा सहकारी object वर साठवण्याऐवजी ज्या एकाच method ला त्याची गरज असते तिला argument म्हणून दिला जातो. जेव्हा dependency प्रत्येक कॉलनुसार असते, जसे की request-scoped clock किंवा user context, तेव्हा हे चांगले.

02 - का

Dependency Injection का अस्तित्वात आहे

जेव्हा एखादी class स्वतःचे सहकारी स्वतः बनवते, तेव्हा ती caller च्या हातातील निर्णय hard-code करते: कोणते database, कोणता mail provider, कोणते clock. ते coupling त्या class ला पुन्हा वापरण्यास अशक्य, प्रत्येक environment साठी configure करण्यास कठीण, आणि test करण्यास त्रासदायक बनवते. DI ते निर्णय बाहेर, जिथे ते बदलू शकतात तिथे ओढून घेते.

🧪 संपूर्ण जगाशिवाय Testability

fake repository आणि stub clock द्या, आणि तुम्ही खात्री करू शकता की order देताना योग्य row जतन होते आणि ग्राहकाला email जाते, सर्व memory मध्ये, milliseconds मध्ये, network किंवा database शिवाय.

🔁 Implementations मुक्तपणे बदला

composition root मधील एक ओळ बदलून SMTP वरून transactional email API कडे, किंवा demo साठी Postgres वरून in-memory store कडे जा. service body कधीच बदलत नाही.

🔍 प्रामाणिक, दृश्य dependencies

ज्या constructor मध्ये repository, mailer, आणि clock यांची यादी असते तो तुम्हाला नेमके सांगतो की ती class कशाला स्पर्श करते. लपलेले new कॉल आणि global singletons तो पृष्ठभाग लपवतात आणि पुढच्या वाचकाला चकित करतात.

⚙️ Configuration काठावर राहते

Connection strings, API keys, आणि retry policies एकदाच, जिथे objects जोडली जातात तिथे ठरवली जातात, business logic मध्ये विखुरलेली नसतात. प्रत्येक environment स्वतःचा graph बांधते.

सोप्या शब्दांत

उपमांसह समजावलेले Dependency Injection

तीच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती पटकन समजते.

🎓 विद्यार्थ्यासाठी

जो परीक्षा तुमच्या हातात calculator देते आणि जो आधी तुम्हाला scratch पासून calculator बनवायला लावतो, त्यातील हा फरक आहे. साधन दिले असल्याने तुम्ही समस्येवर लक्ष केंद्रित करता; दुसरी परीक्षा तुम्हाला वेगळे साधन देऊ शकते.

👩‍💻 developer साठी

तुमची OrderService placeOrder च्या खोलात new SmtpMailer() लिहिण्याऐवजी, mailer हा constructor argument असतो. Production खरा mailer देते, tests recording fake देतात, आणि test होणाऱ्या method ला त्यातला फरक कधीच कळत नाही.

🏢 व्यावसायिकासाठी

चांगली चालणारी team प्रत्येक नव्या कर्मचाऱ्याला स्वतःचा laptop आणि vendor accounts स्वतः घ्यायला देत नाही. IT विभाग standard साधने केंद्रीयरित्या पुरवतो. कर्मचारी काम करतो; कोणती साधने त्याला आधार देतात हे संस्था ठरवते.

🔌 रोजच्या जीवनातील आवृत्ती

तुमच्या kettle ला plug आहे, hard-wired mains cabling नाही. socket वीज पुरवते, इमारत ती कुठूनही मिळवो. इमारतीचा पुरवठा बदला तरी kettle चालूच राहते, कारण ते power plant वर नव्हे तर socket वर अवलंबून असते.

03 - कसे

आतून ते कसे कार्य करते

client class ला जे लागते त्यासाठी ती interfaces घोषित करते आणि जे दिले जाईल ते साठवते. दुसरे काहीतरी, म्हणजे composition root किंवा IoC container, concrete classes ठरवते आणि startup वेळी object graph एकत्र जोडते.

📐 Contracts वर अवलंबून राहा

OrderService कडे एक Repository, एक Mailer, आणि एक Clock असते, ही सर्व interfaces. ती save, send, आणि now कॉल करते, हे न कळता की ते Postgres शी, email API शी, की system clock शी बोलतात.

🧬 composition root वर जोडा

एक startup जागा SmtpMailer, PostgresOrderRepository, आणि SystemClock बांधते, मग ते OrderService मध्ये देते. Tests त्याऐवजी fakes आणि stubs सह वेगळा graph बांधतात.

// Contracts the service depends on, not concrete classes
interface Clock { now(): Date; }
interface Mailer { send(to: string, subject: string, body: string): void; }
interface Repository {
  nextId(): string;
  save(order: Order): void;
}

interface Order { id: string; customerId: string; total: number; placedAt: Date; }

class OrderService {
  // Collaborators are injected, never constructed inside
  constructor(
    private readonly repo: Repository,
    private readonly mailer: Mailer,
    private readonly clock: Clock,
  ) {}

  placeOrder(customerId: string, total: number): Order {
    const order: Order = {
      id: this.repo.nextId(),
      customerId,
      total,
      placedAt: this.clock.now(),
    };
    this.repo.save(order);
    this.mailer.send(customerId, "Order confirmed", `Total ${order.total}`);
    return order;
  }
}

ती class खरोखर कशावर अवलंबून आहे याची यादी करा: orders जतन करण्यासाठी repository, ग्राहकाला सूचित करण्यासाठी mailer, आणि timestamp साठी clock. तीन खऱ्या dependencies, inject करण्यासाठी तीन जबाबदाऱ्या.

20
Contract

interfaces व्याख्यायित करा

service जे कॉल करते तेवढ्याच methods पकडणारे Repository, Mailer, आणि Clock interface लिहा, जसे की save, send, आणि now.

30
Depend

service ला contracts कडे वळवा

field types concrete classes वरून interfaces कडे बदला. service आता abstractions शी बोलते, ज्यामुळे Dependency Inversion Principle पूर्ण होते.

40
Inject

constructor parameters जोडा

तीनही सहकारी constructor arguments म्हणून स्वीकारा आणि साठवा. method bodies मधून सहकाऱ्यांसाठीचे प्रत्येक new हटवा.

50
Adapt

concrete implementations लिहा

interfaces विरुद्ध PostgresOrderRepository, SmtpMailer, आणि SystemClock implement करा. हे production adapters आहेत.

60
Wire

composition root बांधा

main() मध्ये प्रत्येक concrete सहकारी बांधा आणि ते new OrderService(...) मध्ये द्या. concrete types कोणते आहेत हे जाणणारी आता हीच एकमेव जागा असते.

70
Fake

test doubles तयार करा

orders एका list मध्ये साठवणारे FakeRepository, recipients नोंदवणारे SpyMailer, आणि स्थिर वेळ परत करणारे FixedClock लिहा.

80
Test

doubles inject करा

fakes सह service बांधा आणि placeOrder कॉल करा. order जतन झाले, ग्राहकाला email गेले, आणि timestamp deterministic आहे याची खात्री करा.

प्रत्येक environment नुसार बदला

staging मध्ये fake mailer, production मध्ये खरा, आणि demo मध्ये in-memory repository bind करा, हे सर्व OrderService ला स्पर्श न करता. तो seam कायम फायदा देत राहतो.

सामान्य धोके

धोके आणि anti-patterns

DI अतिरेक करणे सोपे आहे आणि बनावटी करणेही सोपे आहे. स्वच्छ seam ला गोंधळात बदलणाऱ्या चुका या आहेत.

🕳️ वेषातील Service locator

class मध्ये container देणे आणि method च्या आत container.resolve(Mailer) कॉल करणे dependencies पुन्हा लपवते. constructor ने त्यांची यादी करावी; global lookup परत आत घुसवू नका.

🧨 Constructor over-injection

दहा सहकारी घेणारा constructor म्हणजे DI ची जीत नाही, ती Single Responsibility ची चूक आहे. ती class खूप काही करत आहे. गर्दी inject करण्याआधी ती तोडा.

🔓 आवश्यक deps साठी Setter injection

अनिवार्य repository साठी setter वापरणे object ला अर्धवट जोडलेले अस्तित्वात राहू देते, त्यामुळे विसरलेला कॉल runtime ला crash होतो. आवश्यक सहकारी constructor मध्येच असावेत.

🎯 contracts नव्हे, concretes inject करणे

parameter Mailer ऐवजी SmtpMailer म्हणून घोषित करणे class ला एका implementation शी पुन्हा जोडते. तुम्हाला DI चा सोपस्कार मिळतो पण अदलाबदलक्षमता अजिबात नाही.

🏭 तरीही आत नव्याने बनवणे

mailer स्वीकारून पण timestamp साठी अजूनही new SystemClock() लिहिणे एक untestable seam ठेवते. clock सह प्रत्येक महत्त्वाचा सहकारी inject व्हावा.

🎭 सगळ्याचे Mocking

प्रत्येक सहकारी null परत करणाऱ्या auto-mock ने बदलणे वर्तन नव्हे तर wiring test करते. वास्तविक प्रतिसाद दाखवणारे साधे हाताने लिहिलेले fakes आणि stubs पसंत करा.

संकेत आणि मापे

संकेत आणि कसे मोजावे

DI थेट मोजता येत नाही, पण निरोगी injection संस्कृती code आणि test suite मध्ये ठसे सोडते.

संकेततो तुम्हाला काय सांगतो
business classes मधील new ची संख्यासहकाऱ्यांसाठी जवळपास शून्य म्हणजे बांधकाम composition root वर हलले आहे; वाढती संख्या म्हणजे लपलेले coupling परत रांगत येत आहे.
I/O ची गरज नसलेल्या testsजर unit tests खऱ्या database, network, किंवा mail server ला स्पर्श करत नसतील, तर dependencies खरोखर inject व fake केल्या आहेत.
Test setup च्या ओळींची संख्याजर test होणारी class जोडण्यास वीस ओळी mocks लागत असतील, तर बहुधा त्या class ला खूप dependencies आहेत किंवा ती concretes गळू देते.
Constructor parameter ची संख्यादोन ते चार सहकारी निरोगी असते; सतत जास्त संख्या DI ची जीत नव्हे तर Single Responsibility ची समस्या दर्शवते.
implementation जोडायला लागणारा वेळएका wiring ओळीत बदल करून SMTP ऐवजी email API आणणे स्वच्छ seam दर्शवते; codebase भर विखुरलेले बदल गळके abstractions दर्शवतात.
tests मधील अनिश्चितताअस्थिर वेळ किंवा random-id assertions एक न-inject केलेले clock किंवा id source उघड करतात जे आत द्यायला हवे होते.
अंगठ्याचा नियम: जर तुम्ही server सुरू केल्याशिवाय एखादी class test मध्ये instantiate करू शकत नसाल, तर ती कितीही interfaces घोषित करो, ती तिच्या dependencies inject करत नाही. तुमच्या DI चा प्रामाणिक न्यायाधीश म्हणजे test harness.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

तीन production सारख्या systems जिथे सहकारी inject करणे हा भार पेलणारा निर्णय आहे.

🛒

1 · e-commerce backend मधील checkout service

Pattern: payment, inventory, आणि notification graph भर constructor injection

checkout flow ला card charge करावे, inventory राखून ठेवावी, आणि receipt email करावी लागते, ही सर्व बाह्य systems आहेत जी tests मध्ये fake करावी लागतात.

  • CheckoutService payment gateway, inventory repository, आणि mailer constructor arguments म्हणून घेते.
  • Integration tests sandbox gateway आणि in-memory inventory store inject करतात, म्हणजे संपूर्ण flow खऱ्या charges शिवाय चालतो.
  • गोठवलेले clock receipt timestamps आणि idempotency keys test मध्ये deterministic बनवते.
✅ परिणाम: संपूर्ण खरेदी मार्ग unit tests मध्ये कोणत्याही live payment provider शिवाय चालवला जातो, त्यामुळे deploy आधीच regressions पकडली जातात.
🏦

2 · banking core मधील ledger posting

Pattern: auditable, testable व्यवहारांसाठी inject केलेले clock आणि repository

ledger ने debit आणि credit entries atomically post कराव्या आणि प्रत्येकावर auditors पुनरुत्पादित करू शकतील अशी नेमकी posting वेळ छापावी.

  • posting engine inject केलेल्या Clock वर अवलंबून असते, म्हणजे tests entries नेमक्या business date वर उतरतात याची खात्री करू शकतात.
  • एक repository interface त्याच engine ला production मध्ये Postgres वर आणि property-based tests मध्ये in-memory double वर चालवू देते.
  • clock बदलून team कोणत्याही ऐतिहासिक तारखेसाठी end-of-day batches engine code न बदलता पुन्हा चालवू शकते.
✅ परिणाम: वेळ आणि storage नियंत्रणीय seams असतात, त्यामुळे audit परिस्थिती आणि दिवसाच्या सीमारेषांचे प्रसंग सखोल व पुनरुत्पादनीयपणे test होतात.
🚚

3 · logistics मधील shipping label निर्मिती

Pattern: प्रत्येक region साठी एक carrier client bind करणारे IoC container

fulfillment service अनेक carrier APIs मार्फत labels तयार करते, आणि योग्य carrier destination आणि contract वर अवलंबून असतो.

  • प्रत्येक carrier client एक समान CarrierGateway interface implement करते, जे LabelService मध्ये inject होते.
  • एक IoC container configuration नुसार concrete carrier bind करते, त्यामुळे नवे carriers service ला स्पर्श न करता जोडले जातात.
  • एक fake carrier gateway ठराविक tracking numbers परत करते, म्हणजे label workflow offline test होतो.
✅ परिणाम: नवा carrier जोडणे म्हणजे एक container binding अधिक एक adapter class, तर मुख्य label logic अस्पर्शित आणि पूर्णपणे tested राहते.
07 - सुसंगतता

आधुनिक सुसंगतता

Dependency Injection दशकांपूर्वीचे आहे, पण ती जे रूप घेते ते frameworks, languages, आणि testing संस्कृतीसोबत बदलत राहते.

🧰 Framework-native containers

Spring, NestJS, ASP.NET Core, आणि Angular default composition यंत्रणा म्हणून IoC containers पुरवतात, ज्यामुळे apps एकत्र करण्याचा standard मार्ग constructor injection बनतो.

🪶 container शिवाय हाताने

अनेक teams जादूला विरोध करतात आणि composition root वर साध्या code मध्ये graphs जोडतात, DI हे pattern ठेवतात पण जड container सोडून देतात.

🧩 Functional injection

सहकाऱ्यांना function arguments किंवा partial applications म्हणून देणे, classes पासून न बनलेल्या code ला तीच अदलाबदलक्षमता आणते.

⏱️ Deterministic testing

clocks, id generators, आणि random sources inject करणे आता CI मधील पुनरुत्पादनीय tests आणि स्थिर snapshots साठी किमान अपेक्षा आहे.

🔒 security साठी सीमारेषा

permission-aware repository किंवा scoped credential provider inject करणे authorization निर्णय काठांवर आणि वेगळेपणाने testable ठेवते.

🤖 agentic आणि LLM code चे testing

model client आणि tool gateways inject केल्याने teams प्रतिसाद stub करू शकतात, त्यामुळे language models कॉल करणाऱ्या pipelines test मध्ये जलद आणि deterministic राहतात.

सारांश: तुम्ही पूर्ण container वापरा की main() मध्ये तीन objects जोडा, शिस्त तीच असते: new ला business logic बाहेर ठेवा आणि classes ला त्यांचे सहकारी हातात द्या. तीच एक सवय मोठ्या object-oriented systems ना configurable, अदलाबदल करण्याजोग्या, आणि testable बनवते.
