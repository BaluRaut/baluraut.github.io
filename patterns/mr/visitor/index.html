Behavioral पॅटर्न

Visitor पॅटर्न - ऑपरेशन्स जी तुमच्या ऑब्जेक्ट्सकडे प्रवास करतात

तुमच्याकडे ऑब्जेक्ट्सचे एक स्थिर झाड आहे (एक AST, एक document, एक shape hierarchy) आणि त्याच्यासोबत करण्याच्या गोष्टींची यादी सतत वाढत आहे. Visitor तुम्हाला element क्लासेसना स्पर्श न करता नवीन ऑपरेशन्स जोडू देते. ते प्रत्येक ऑपरेशन स्वतःच्या visitor ऑब्जेक्टमध्ये हलवते आणि double dispatch वापरते जेणेकरून योग्य element प्रकारासाठी योग्य कोड चालतो.

01 - काय

Visitor पॅटर्न म्हणजे काय?

Visitor एका ऑब्जेक्ट स्ट्रक्चरच्या elements वर करावयाच्या एका ऑपरेशनचे प्रतिनिधित्व करते. ज्या elements वर ते चालते त्यांच्या क्लासेस न बदलता तुम्हाला नवीन ऑपरेशन परिभाषित करण्याची मुभा देते. प्रत्येक node प्रकारावर एक method विखुरण्याऐवजी, तुम्ही ते ऑपरेशन एका visitor क्लासमध्ये एकत्र करता आणि प्रत्येक element ला accept कॉलद्वारे स्वतःला visitor कडे परत सोपवू देता.

🧩 Element

स्ट्रक्चरमधील प्रत्येक node प्रकार एक method उघड करतो, accept(visitor), ज्याचे एकमेव काम म्हणजे visitor वरील जुळणारी visit method परत बोलावणे.

🧳 Visitor

प्रत्येक concrete element प्रकारासाठी एक visit method असलेला interface. प्रत्येक concrete visitor म्हणजे एक संपूर्ण ऑपरेशन: एक printer, एक type checker, एक evaluator.

🌳 Object structure

elements चा संग्रह किंवा झाड जे त्याच्या nodes ची यादी करू शकते आणि प्रत्येकाला एक visitor देऊ शकते, बहुधा एका recursive traversal द्वारे.

02 - का

Visitor पॅटर्न का अस्तित्वात आहे

जेव्हा एखादी class hierarchy स्थिर असते पण तिच्यावरील ऑपरेशन्स सतत वाढत राहतात, तेव्हा प्रत्येक ऑपरेशन प्रत्येक node वर एक method म्हणून ठेवल्याने क्लासेस फुगतात आणि प्रत्येक नवीन फीचरसाठी संपूर्ण hierarchy मध्ये बदल करावे लागतात. Visitor अक्ष उलटवते: ते एक ऑपरेशन एका ठिकाणी गटबद्ध करते.

➕ नवीन ऑपरेशन्ससाठी खुले

एक नवीन visitor क्लास लिहून serializer, validator किंवा optimizer जोडा. element hierarchy ला कधीही स्पर्श होत नाही, त्यामुळे node प्रकारांचा स्थिर संच बदलांपासून बंद राहतो.

📚 ऑपरेशननुसार cohesion

एक AST सुरेखपणे छापण्याचे सर्व logic एका PrintVisitor मध्ये राहते, Add, Sub, Number आणि Call वर विखुरलेले नसते. संबंधित कोड एकत्र बसतो, जे वाचायला आणि तपासायला सोपे असते.

🎯 Double dispatch, type checks नव्हे

योग्य कोड element प्रकार आणि visitor प्रकार दोन्हींवर आधारित चालतो, लांब instanceof किंवा switch (node.kind) साखळ्यांशिवाय ज्या compiler पूर्णपणे तपासू शकत नाही.

🧮 स्ट्रक्चरभर जमा करा

एक visitor झाडावरून फिरताना state सोबत घेऊन जातो, त्यामुळे तो एका बिलाची बेरीज करू शकतो, free variables गोळा करू शकतो किंवा एकाच traversal मध्ये symbol table बनवू शकतो.

सोप्या शब्दांत

उपमांसह Visitor समजावून

तीच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी लक्षात येईल.

🎓 विद्यार्थ्यासाठी

एका पर्यायी शिक्षकाचा विचार करा जो प्रत्येक वर्गात जातो. प्रत्येक खोली (element) आपले दार उघडते आणि म्हणते "आत या" (accept); शिक्षक प्रत्येक इयत्तेनुसार तोच धडा जुळवून देतो. नवीन धड्यासाठी नवीन शिक्षक पाठवा; वर्ग कधीच बदलत नाहीत.

👩‍💻 डेव्हलपरसाठी

ही एक बाहेर काढलेली method आहे दोन-टप्प्यांच्या dispatch सह. node visitor.visitAdd(this) बोलावतो, त्यामुळे node प्रकार आणि ऑपरेशन प्रकार दोन्ही कोड निवडतात. ToJsonVisitor जोडायला node क्लासेसमध्ये शून्य बदल लागतात.

🏢 व्यावसायिकासाठी

विभागांचा दौरा करणाऱ्या compliance auditor सारखे. प्रत्येक विभाग आपली नोंदी सादर करतो (accept); auditor सर्वत्र एकच checklist लागू करतो. पुढच्या तिमाहीत एक वेगळा auditor त्याच विभागांवर वेगळी checklist चालवतो.

🏨 रोजच्या जीवनातील

एक हॉटेल housekeeping गाडी जी प्रत्येक खोली प्रकाराजवळ थांबते. एक standard खोली आणि एक suite दोन्ही गाडीला आत घेतात आणि त्यांना शोभेल अशी सेवा मिळवतात. खोल्या पुन्हा न बांधता गाडी बदला (साफसफाईकडून पुरवठ्याकडे).

03 - कसे

ते आतून कसे कार्य करते

युक्ती म्हणजे double dispatch. बहुतेक भाषांमध्ये एकच virtual call एका प्रकारावर (receiver) dispatch करतो. Visitor दोन virtual calls साखळीत जोडते जेणेकरून चालणारी method element प्रकार आणि visitor प्रकार दोन्हींवर अवलंबून असते.

1️⃣ पहिला dispatch (element)

तुम्ही element.accept(visitor) बोलावता. Virtual dispatch concrete element ची accept निवडते, त्यामुळे त्या method मध्ये node चा runtime प्रकार आता ज्ञात असतो.

2️⃣ दुसरा dispatch (visitor)

accept च्या आत, element visitor.visitAdd(this) बोलावतो. Overload resolution आणि virtual dispatch आता त्या नेमक्या element आणि त्या नेमक्या visitor साठी कोड निवडतात.

Java मधील एक वास्तववादी AST visitor

// Element hierarchy: a tiny expression AST
interface Expr {
    <R> R accept(Visitor<R> v);
}

record Number(double value) implements Expr {
    public <R> R accept(Visitor<R> v) { return v.visitNumber(this); }
}

record Add(Expr left, Expr right) implements Expr {
    public <R> R accept(Visitor<R> v) { return v.visitAdd(this); }
}

record Mul(Expr left, Expr right) implements Expr {
    public <R> R accept(Visitor<R> v) { return v.visitMul(this); }
}

// Visitor interface: one method per concrete element
interface Visitor<R> {
    R visitNumber(Number n);
    R visitAdd(Add a);
    R visitMul(Mul m);
}

// One whole operation = one visitor. Evaluate the tree to a double.
class EvalVisitor implements Visitor<Double> {
    public Double visitNumber(Number n) { return n.value(); }
    public Double visitAdd(Add a) {
        return a.left().accept(this) + a.right().accept(this);
    }
    public Double visitMul(Mul m) {
        return m.left().accept(this) * m.right().accept(this);
    }
}

// A second operation added with ZERO changes to Expr classes.
class PrintVisitor implements Visitor<String> {
    public String visitNumber(Number n) { return String.valueOf(n.value()); }
    public String visitAdd(Add a) {
        return "(" + a.left().accept(this) + " + " + a.right().accept(this) + ")";
    }
    public String visitMul(Mul m) {
        return "(" + m.left().accept(this) + " * " + m.right().accept(this) + ")";
    }
}

// Usage: (1 + 2) * 3
Expr ast = new Mul(new Add(new Number(1), new Number(2)), new Number(3));
double result = ast.accept(new EvalVisitor());   // 9.0
String pretty = ast.accept(new PrintVisitor());  // ((1.0 + 2.0) * 3.0)

लक्षात घ्या की EvalVisitor आणि PrintVisitor पूर्णपणे वेगळी ऑपरेशन्स आहेत, तरीही कोणालाही Number, Add किंवा Mul संपादित करण्याची गरज पडली नाही. recursion visitor मध्ये child.accept(this) द्वारे राहते, त्यामुळे प्रत्येक visitor स्वतःचे traversal आणि return प्रकार नियंत्रित करतो.

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

एका उघड्या element hierarchy पासून चालत्या visitor ऑपरेशनपर्यंत, आणि नंतर फुकटात जोडलेल्या दुसऱ्या ऑपरेशनपर्यंत.

00
Model

object structure ओळखा

तुम्ही ज्या node प्रकारांवर काम कराल ते निश्चित करा, जसे की AST expressions किंवा document nodes. हा संच स्थिर असतो आणि ऑपरेशन्स वाढतात तेव्हा Visitor फायदेशीर ठरते.

10
Element API

element interface मध्ये accept जोडा

base element प्रकारावर accept(visitor) घोषित करा जेणेकरून प्रत्येक concrete node स्वतःला visitor कडे सोपवण्याचे वचन देतो.

20
Visitor API

Visitor interface घोषित करा

प्रत्येक concrete element साठी एक visit method लिहा: visitNumber, visitAdd, इत्यादी. हा interface म्हणजे प्रत्येक ऑपरेशन अंमलात आणणारा करार आहे.

30
जोडणी

प्रत्येक node वर accept अंमलात आणा

प्रत्येक concrete element मध्ये, accept जुळणारी method बोलावते: return v.visitAdd(this). प्रत्येक क्लासमधील ही एक ओळ double dispatch सक्षम करते.

40
ऑपरेशन

पहिला concrete visitor लिहा

उदाहरणार्थ, प्रत्येक visit method अंमलात आणणारा EvalVisitor बनवा. सर्व मूल्यमापन logic इथे, एका सुसंगत क्लासमध्ये राहते.

50
Traverse

children मध्ये recurse करा

composite visits च्या आत, खाली उतरण्यासाठी child.accept(this) बोलावा. visitor फेरी चालवतो आणि क्रम, खोली आणि short-circuiting ठरवतो.

60
State

जमा होणारा state वाहून न्या

visitor ला fields धरू द्या (एक बेरीज, एक symbol table, एक StringBuilder) जेणेकरून एका फेरीत संपूर्ण स्ट्रक्चरभर निकाल गोळा होतात.

70
Run

root पासून सुरुवात करा

root.accept(new EvalVisitor()) बोलावा. पहिला dispatch node ठरवतो, दुसरा ऑपरेशन ठरवतो, आणि traversal उलगडते.

80
विस्तार

फुकटात एक नवीन ऑपरेशन जोडा

सुंदर छपाई किंवा JSON export हवे? PrintVisitor लिहा. element क्लासेस अस्पर्शित राहतात, जो या पॅटर्नचा संपूर्ण मुद्दा आहे.

90
Compose

visitors एकत्र करा किंवा साखळीत जोडा

त्याच झाडावर एक validating visitor, नंतर एक optimizing visitor, नंतर एक codegen visitor चालवा. प्रत्येक स्वतंत्र आणि वेगळेपणाने तपासण्याजोगा आहे.

100
Maintain

element बदल जाणीवपूर्वक हाताळा

एक node प्रकार जोडणे म्हणजे प्रत्येक visitor अद्ययावत करणे. तो खर्च जाणूनबुजून स्वीकारा; ऑपरेशन्स खुली आणि सुसंगत ठेवण्यासाठी तुम्ही केलेला तो सौदा आहे.

सामान्य अडचणी

अडचणी आणि anti-patterns

Visitor शक्तिशाली आहे पण चुकीच्या पद्धतीने वापरणे सोपे आहे. या नेहमीच्या सापळ्या आहेत.

🔁 अस्थिर element संच

जर node प्रकार वारंवार बदलत असतील, तर प्रत्येक नवीन प्रकार प्रत्येक visitor मध्ये बदल करण्यास भाग पाडतो. hierarchy अस्थिर आणि ऑपरेशन्स थोडी असताना Visitor चुकीची निवड आहे.

🕳️ encapsulation मोडणे

visitors ना element च्या अंतर्गत भागांची गरज असते, त्यामुळे nodes शेवटी getters किंवा public fields उघड करतात. यामुळे क्लासला लपवायची असलेली implementation तपशील बाहेर पडू शकतात.

🧨 Default catch-all visits

no-op default असलेला एक base visitor मोठ्याने अपयशी होण्याऐवजी नवीन element प्रकार शांतपणे गिळंकृत करतो. न हाताळलेली प्रकरणे शोधण्यात compiler ची मदत तुम्ही गमावता.

🌀 लपलेला traversal क्रम

प्रत्येक visit method मध्ये traversal logic मिसळल्याने क्रम अस्पष्ट होतो आणि visitors मध्ये विसंगत राहतो. एका वेगळ्या traversal strategy किंवा एका base walker चा विचार करा.

🧱 साध्या प्रकरणांसाठी अतिरेक

दोन node प्रकार आणि एक ऑपरेशन यांना accept, एक visitor interface आणि double dispatch ची गरज नसते. एक साधी method किंवा एक switch अधिक स्पष्ट आणि छोटा असतो.

🔗 चक्रीय अवलंबित्व

elements visitor interface import करतात आणि visitors प्रत्येक element import करतात, ज्यामुळे घट्ट दुहेरी coupling तयार होते जे कोड modules मध्ये विभागण्यास विरोध करते.

फायदे-तोटे

फायदे-तोटे आणि केव्हा वापरावे

Visitor बदलाचा एक अक्ष स्वस्त आणि दुसरा महाग करते. तुमची प्रणाली प्रत्यक्षात कोणत्या अक्षावर सरकते हे जाणून घ्या.

पैलूतपशील
फायदेelements संपादित न करता नवीन ऑपरेशन्स; संबंधित logic प्रत्येक ऑपरेशननुसार एकत्र; double dispatch type-switch साखळ्यांची जागा घेते; एक visitor संपूर्ण traversal भर निकाल जमा करू शकतो.
तोटेएक element प्रकार जोडल्याने प्रत्येक visitor ला स्पर्श होतो; बहुधा element encapsulation मोडते; भरपूर boilerplate; elements आणि visitors यांच्यात दुहेरी coupling.
केव्हा वापरावेelement hierarchy स्थिर आहे पण ऑपरेशन्स वाढत राहतात; तुमच्याकडे अनेक प्रकारे फिरवला जाणारा AST, parse tree, document model किंवा shape hierarchy आहे.
केव्हा टाळावेnode प्रकार वारंवार बदलतात, ऑपरेशन्स थोडी आहेत, किंवा एखादे भाषा वैशिष्ट्य (pattern matching, sealed types) आधीच तुम्हाला संपूर्ण, स्वस्त dispatch देते.
गुंतागुंतमध्यम. यंत्रणा लहान आहे पण indirection आणि accept/visit सोपस्कार आकलनाचा भार आणि files वाढवतात.
संबंधितComposite (Visitor ज्या झाडावर फिरतो), Iterator (एक पर्यायी traversal), Interpreter (Visitor बहुधा त्याचे grammar मूल्यमापन करते), Strategy (प्रत्येक visitor एक अदलाबदल करण्याजोगे ऑपरेशन).
अंगठ्याचा नियम: जेव्हा तुम्हाला प्रकारांच्या स्थिर संचावर अनेक नवीन ऑपरेशन्सची अपेक्षा असेल तेव्हा Visitor कडे वळा. उलट जर तुम्हाला ऑपरेशन्सच्या स्थिर संचावर अनेक नवीन प्रकारांची अपेक्षा असेल, तर methods क्लासेसवरच ठेवा; Visitor प्रत्येक नवीन node वर तुमच्याशी झगडेल.
06 - उदाहरणे

प्रत्यक्ष जगातील उदाहरणे

production प्रणालींमध्ये Visitor आपली किंमत वसूल करते अशी तीन ठिकाणे.

🛠️

1 · Compiler आणि interpreter ASTs

पॅटर्न: एका node संचावर अनेक passes

एक language front end source ला AST मध्ये parse करते, नंतर त्याच nodes वर pass मागून pass चालवते.

  • वेगवेगळे visitors type checking, constant folding आणि bytecode generation अंमलात आणतात.
  • node क्लासेस (literals, calls, loops) बंद राहतात तर नवीन passes मुक्तपणे जोडली जातात.
  • प्रत्येक visitor स्वतःचा state वाहून नेतो, जसे की एक scope stack किंवा एक emitted-instruction buffer.
✅ परिणाम: नवीन विश्लेषणे grammar किंवा node hierarchy अस्थिर न करता नवीन visitor क्लासेस म्हणून येतात, जो नेमका बदलाचा पॅटर्न compiler ला हवा असतो.
📄

2 · Document trees आणि rendering

पॅटर्न: एक model, अनेक output formats

एक rich-text किंवा Markdown editor documents ना headings, paragraphs, lists आणि images यांचे झाड म्हणून धरून ठेवतो.

  • एक HtmlVisitor HTML मध्ये render करतो, एक LatexVisitor LaTeX मध्ये, एक WordCountVisitor एका आकडेवारीत.
  • नवीन export formats म्हणजे नवीन visitors; node प्रकारांना output बद्दल कधीच कळत नाही.
  • visitors एक सामायिक traversal पुन्हा वापरतात जेणेकरून स्ट्रक्चर आणि formatting वेगळे राहतात.
✅ परिणाम: एक PDF किंवा plain-text exporter जोडणे म्हणजे एक स्वयंपूर्ण क्लास, त्यामुळे document model प्रत्येक format भर सत्याचा एकमेव स्रोत राहतो.
🧾

3 · Static analysis आणि linters

पॅटर्न: एका syntax tree वर नियम

एक linter समस्या दर्शवण्यासाठी एका code AST वरून फिरतो, आणि rule sets सतत वाढतात.

  • प्रत्येक नियम एक visitor आहे जो विशिष्ट node प्रकार तपासतो आणि निष्कर्ष कळवतो.
  • नियम त्याच parse केलेल्या झाडावर स्वतंत्रपणे चालतात, त्यामुळे अपयशे वेगळी राहतात.
  • parser आणि node model सामायिक असतात आणि भाषा निश्चित झाल्यावर क्वचितच बदलतात.
✅ परिणाम: संघ parser कधीही संपादित न करता lint नियम जोडतात आणि चालू-बंद करतात, ज्यामुळे मोठा rule catalog देखभालीजोगा आणि नियमानुसार तपासायला सोपा राहतो.
07 - सुसंगतता

आधुनिक सुसंगतता

भाषा वैशिष्ट्यांनी Visitor केव्हा योग्य साधन आहे हे पुनर्रचित केले आहे, पण ते सोडवत असलेली मूळ समस्या अजूनही जिवंत आहे.

🧵 Pattern matching त्याच्याशी स्पर्धा करते

Java, Kotlin आणि TypeScript-शैलीच्या unions मधील sealed types आणि संपूर्ण switch स्वस्त, compiler-तपासलेले dispatch देतात, बहुधा साध्या प्रकरणांसाठी हाताने लिहिलेल्या visitors ची जागा घेतात.

🌲 मोठ्या ASTs साठी अजूनही राजा

Compilers, transpilers आणि query engines Visitor वापरत राहतात कारण grammar स्थिर राहत असताना passes वाढतात, नेमका तोच आकार ज्यासाठी Visitor बनवले गेले.

⚙️ Generated visitors

ANTLR सारखी साधने एका grammar मधून visitor आणि listener base क्लासेस उत्सर्जित करतात, त्यामुळे तुम्ही boilerplate हाताने लिहिण्याऐवजी subclass करता.

🔀 Listener variants

Event-शैलीचे listeners (enter/exit callbacks) traversal ला action पासून वेगळे करतात, parsing frameworks आणि tree walkers मधील Visitor चा एक सामान्य विकास.

🧬 Functional fold

FP मध्ये, एका algebraic data type वरील fold किंवा catamorphism हीच कल्पना व्यक्त करते; Visitor म्हणजे त्या recursion scheme चे ऑब्जेक्ट-ओरिएंटेड रूप.

🧰 Expression-tree साधने

ORMs आणि rule engines queries अनुवादित करण्यासाठी, predicates पुनर्लेखन करण्यासाठी आणि runtime वर plans optimize करण्यासाठी visitors सह expression trees वरून फिरतात.

सारांश: एका स्थिर type hierarchy वर ऑपरेशन्स वाढतात तेव्हा Visitor हे पहिल्या पसंतीचे साधन राहते. जिथे भाषा संपूर्ण pattern matching देतात, तिथे लहान प्रकरणांसाठी त्यालाच प्राधान्य द्या; जिथे तुमच्याकडे अनेक प्रकारे फिरवला जाणारा खरा AST किंवा document tree असतो, तिथे Visitor अजूनही आपल्या सोपस्कारांची किंमत वसूल करते.
