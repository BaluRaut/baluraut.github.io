Value Objects विरुद्ध Entities - identity आणि equality चे मॉडेलिंग

payments आणि orders प्रणालीत, काही गोष्टी त्या ज्या गोष्टींनी बनल्या आहेत, त्याच असतात, तर काही गोष्टी त्या जे कोण आहेत, त्यावरून असतात. Money किंवा Email सारखे value object पूर्णपणे त्याच्या attributes वरून ठरते आणि कधीही बदलत नाही. Order किंवा Customer सारख्या entity ला एक स्थिर identity असते आणि एक lifecycle असते जी कोणत्याही एका field values च्या संचापेक्षा जास्त काळ टिकते.

01 - काय

value objects आणि entities म्हणजे काय?

domain design मधील हा सर्वात परिणामकारक मॉडेलिंग निर्णय आहे. entity म्हणजे एक विशिष्ट identity असलेली गोष्ट जी बदलामधून टिकून राहते: Order हा तोच order असतो, मग तो pending असो, paid असो, किंवा shipped असो. value object म्हणजे केवळ त्याच्या attributes वरून ठरणारी गोष्ट: 25.00 USD चे दोन Money instances परस्पर बदलण्याजोगे असतात, आणि दोघांपैकी कोणाचीही अशी काही कहाणी नसते जिचा मागोवा ठेवण्यासारखे असेल.

🆔 Entity

याला एक identity (एक id) असते जी स्थिर राहते तर त्याचे attributes काळानुसार बदलतात. Order, Customer आणि Payment प्रत्येकाची मागोवा ठेवण्यासारखी lifecycle असते.

💠 Value object

याला id नसते. ते पूर्णपणे त्याच्या fields वरून वर्णन केले जाते आणि immutable असते. Money, Email आणि Address ची तुलना content वरून केली जाते, reference वरून नाही.

⚖️ Equality चा भेद

entities समान असतात जेव्हा त्यांच्या ids जुळतात. value objects समान असतात जेव्हा प्रत्येक attribute जुळते. हे चुकल्यास caches, sets आणि lookups बिघडतात.

02 - का

हा भेद का महत्त्वाचा आहे

या दोन श्रेणी एकत्र मिसळणे हे संपूर्ण एका प्रकारच्या bugs चे मूळ आहे: mutable रकमा ज्या हळूहळू बदलतात, fields वरून तुलना केल्या जाणाऱ्या entities ज्या गुपचूप duplicate होतात, आणि equality जी set मध्ये आणि if मध्ये वेगळी वागते. श्रेणी आधीच नाव देऊन ठेवल्यास correctness हा default बनतो.

🛡️ Immutability shared-state bugs दूर करते

बदलू न शकणारे Money checkout च्या एका भागाकडून बदलले जाऊ शकत नाही तर दुसरा भाग ते वाचत असतो. defensive copies शिवाय तुम्ही value objects मुक्तपणे इकडे-तिकडे पाठवता.

🎯 योग्य equality collections ला बळ देते

content वरून समान असलेली value objects sets मध्ये योग्यरित्या deduplicate होतात, विश्वासार्ह map keys म्हणून काम करतात, आणि duplicates गळू देण्याऐवजी caches ला hit होऊ देतात.

🧭 Identity खरी गोष्ट मागोवा ठेवते

एक Order cart पासून delivery पर्यंत एकच id राखते. प्रत्येक state transition, event आणि audit row त्या स्थिर identity वर अवलंबून असते, त्याच्या fields च्या snapshot वर नाही.

🧱 समृद्ध types primitive गोंधळाची जागा घेतात

एक Email किंवा Money type construction च्या वेळी एकदाच validate होते, त्यामुळे प्रणालीचा उर्वरित भाग सर्वत्र raw strings आणि floats पुन्हा तपासण्याऐवजी value वर विश्वास ठेवतो.

सोप्या शब्दांत

उपमांसह Value objects विरुद्ध entities चे स्पष्टीकरण

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती लक्षात येते.

🎓 विद्यार्थ्यासाठी

एक विद्यार्थी id क्रमांक ही entity आहे: तुम्ही तुमचे नाव, पत्ता किंवा शाखा बदलली तरी ती अजूनही तुम्हीच असता. एक दहा डॉलरची नोट हे value object आहे: कोणतीही दहा डॉलरची नोट अगदी सारखीच खर्च होते, त्यामुळे तुमच्याकडे कोणती आहे याचा कोणीही मागोवा ठेवत नाही.

👩‍💻 डेव्हलपरसाठी

primary key असलेली database row ही entity आहे; तुम्ही तिचे columns अपडेट करता पण key कधीही हलत नाही. Color(255, 0, 0) किंवा Money(25, "USD") हे value object आहे: fields वरून समान, edit करण्याऐवजी बदलले जाते.

🏢 व्यावसायिकासाठी

एक customer account ही entity आहे जिचा तुमचा व्यवसाय प्रत्येक order मध्ये वर्षानुवर्षे मागोवा ठेवतो. एका order वर छापलेला shipping address हे value object आहे: fields चा एक snapshot, स्वतःपुरता वैध, स्वतःची अशी काही कहाणी नसलेली गोष्ट.

🏦 रोजच्या जीवनातील आवृत्ती

तुमचे बँक खाते ही entity आहे: balance वाढत-कमी होत असताना खाते क्रमांक तोच राहतो. एक नोट हे value object आहे: एकाच चलनाच्या दोन वीसच्या नोटा परस्पर बदलण्याजोग्या असतात, केवळ त्यांच्या मूल्यावरून ठरतात.

03 - कसे

प्रत्येकाचे मॉडेलिंग कसे करावे

value object त्याच्या constructor मध्ये validate करते, read-only fields उघड करते, आणि कोणत्याही operation मधून नवीन instances परत करते. entity एक id वाहते, स्वतःच्या state transitions चे रक्षण करते, आणि equality केवळ id वरून ठरवते.

💠 value object तयार करणे

fields freeze करा, एकदाच validate करा, आणि content वरून तुलना करा. दोन Money values जोडण्यासारखे arithmetic कोणत्याही operand ला बदलण्याऐवजी नवीन Money परत करते.

🆔 entity तयार करणे

निर्मितीच्या वेळी एक id नेमा, ती स्थिर ठेवा, आणि methods ना lifecycle चालवू द्या. एक Order त्याच्या total आणि address साठी value objects धारण करते तर त्याची status विकसित होत जाते.

// Money: a value object - immutable, equal by attributes
class Money {
  constructor(
    readonly amountCents: number,
    readonly currency: string,
  ) {
    if (!Number.isInteger(amountCents)) throw new Error("amount must be whole cents");
    Object.freeze(this);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("currency mismatch");
    return new Money(this.amountCents + other.amountCents, this.currency);
  }

  equals(other: Money): boolean {
    return this.amountCents === other.amountCents && this.currency === other.currency;
  }
}

// Order: an entity - equal by identity, mutable lifecycle
class Order {
  private lines: Money[] = [];
  status: "pending" | "paid" = "pending";

  constructor(readonly id: string, readonly customerId: string) {}

  addLine(price: Money): void {
    this.lines.push(price); // attributes change; id does not
  }

  total(): Money {
    return this.lines.reduce((sum, m) => sum.add(m), new Money(0, "USD"));
  }

  pay(): void {
    this.status = "paid";
  }

  equals(other: Order): boolean {
    return this.id === other.id; // identity, not fields
  }
}

const order = new Order("ord_1001", "cus_42");
order.addLine(new Money(1999, "USD"));
order.addLine(new Money(500, "USD"));
console.log(order.total().equals(new Money(2499, "USD"))); // true
order.pay();
console.log(order.status); // "paid"
from dataclasses import dataclass, field

# Money: a value object - frozen and equal by attributes
@dataclass(frozen=True)
class Money:
    amount_cents: int
    currency: str

    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError("currency mismatch")
        return Money(self.amount_cents + other.amount_cents, self.currency)

# frozen dataclass gives __eq__ by fields and __hash__ for free

# Order: an entity - equal by identity, mutable lifecycle
class Order:
    def __init__(self, id: str, customer_id: str):
        self.id = id
        self.customer_id = customer_id
        self._lines: list[Money] = []
        self.status = "pending"

    def add_line(self, price: Money) -> None:
        self._lines.append(price)  # attributes change; id does not

    def total(self) -> Money:
        total = Money(0, "USD")
        for line in self._lines:
            total = total.add(line)
        return total

    def pay(self) -> None:
        self.status = "paid"

    def __eq__(self, other: object) -> bool:
        return isinstance(other, Order) and self.id == other.id  # identity

    def __hash__(self) -> int:
        return hash(self.id)

order = Order("ord_1001", "cus_42")
order.add_line(Money(1999, "USD"))
order.add_line(Money(500, "USD"))
print(order.total() == Money(2499, "USD"))  # True
order.pay()
print(order.status)  # "paid"
# Money: a value object - immutable and equal by attributes
class Money
  attr_reader :amount_cents, :currency

  def initialize(amount_cents, currency)
    raise ArgumentError, "amount must be whole cents" unless amount_cents.is_a?(Integer)
    @amount_cents = amount_cents
    @currency = currency
    freeze
  end

  def add(other)
    raise ArgumentError, "currency mismatch" unless other.currency == currency
    Money.new(amount_cents + other.amount_cents, currency)
  end

  def ==(other)
    other.is_a?(Money) && amount_cents == other.amount_cents && currency == other.currency
  end
  alias eql? ==

  def hash
    [amount_cents, currency].hash
  end
end

# Order: an entity - equal by identity, mutable lifecycle
class Order
  attr_reader :id, :customer_id
  attr_accessor :status

  def initialize(id, customer_id)
    @id = id
    @customer_id = customer_id
    @lines = []
    @status = :pending
  end

  def add_line(price)
    @lines << price # attributes change; id does not
  end

  def total
    @lines.reduce(Money.new(0, "USD")) { |sum, m| sum.add(m) }
  end

  def pay
    @status = :paid
  end

  def ==(other)
    other.is_a?(Order) && id == other.id # identity, not fields
  end
end

order = Order.new("ord_1001", "cus_42")
order.add_line(Money.new(1999, "USD"))
order.add_line(Money.new(500, "USD"))
puts order.total == Money.new(2499, "USD") # true
order.pay
puts order.status # paid

हा भेद लक्षात घ्या: Money frozen आहे आणि त्याच्या fields वरून equality ठरवते, त्यामुळे तुमच्याकडे कोणतेही instance असो, 2499 cents हे 2499 cents च्या समान असते. Order एक स्थिर id राखते, त्याच्या lines आणि status बदलते, आणि फक्त id वरून तुलना करते, त्यामुळे paid केलेला order अजूनही तो एकेकाळी असलेल्या pending order च्या समानच असतो.

Freeze

value objects immutable करा

value objects ना read-only fields द्या म्हणजे तयार झाल्यानंतर कोणताही caller एखादी shared रक्कम किंवा address बदलू शकणार नाही.

40
Validate

constructor मध्ये invariants चे रक्षण करा

construction च्या वेळीच एक ऋण अपूर्णांक cent, एक चुकीचा email, किंवा रिकामे currency नाकारा म्हणजे प्रत्येक विद्यमान value आधीच वैध असते.

50
Equality

fields वरून value equality ठरवा

सर्व attributes वर equals आणि hash अंमलात आणा म्हणजे दोन समान Money values sets मध्ये आणि map keys म्हणून एकसारख्या वागतात.

60
Identity

entity ids नेमा

निर्मितीच्या वेळी प्रत्येक entity ला एक id द्या आणि entities ची तुलना केवळ त्या id वरून करा, त्यांच्या सध्याच्या field values वरून कधीही नाही.

70
Compose

entities च्या आत values समाविष्ट करा

Order ला एक Money total आणि एक Address धारण करू द्या, आणि Customer ला एक Email धारण करू द्या. entities value objects च्या मालक असतात, उलट नाही.

80
Transition

methods ने lifecycle चालवा

Order ला नियम लागू करणाऱ्या methods द्वारे pending पासून paid पर्यंत आणि shipped पर्यंत हलवा, तर id संपूर्ण वेळ स्थिर राहते.

90

entities id वरून, values inline साठवा

विश्वास

आत्मविश्वासाने विचार करा

प्रणालीचा उर्वरित भाग आता विश्वास ठेवतो की values वैध आणि immutable आहेत आणि entities स्थिर identity वरून मागोवा ठेवल्या जातात, ज्यामुळे संपूर्ण एका प्रकारच्या bugs नष्ट होतात.

सामान्य अडचणी

अडचणी आणि anti-patterns

बहुतांश identity bugs दोन श्रेणी एकत्र मिसळण्यापर्यंत मागे जातात. हे नेहमीचे दोषी आहेत.

🧨 Mutable value objects

Money किंवा Address ला setter जोडणे म्हणजे एक caller एक shared instance बदलू शकतो आणि इतरत्र एका order total ला गुपचूप बदलू शकतो. value objects freeze केलेली आणि बदलली जाणारी असावीत, edit केलेली नाही.

🪞 entities ची fields वरून तुलना करणे

सर्व attributes ची तुलना करण्यासाठी entity equality overriding केल्याने एकाच नावाचे दोन customers समान दिसतात, records duplicate होतात आणि lookups बिघडतात. entities ची तुलना फक्त id वरून होते.

🆔 value object वर identity

Money किंवा Email वर एक database id चिकटवणे साध्या value ला कोणालाही नको असलेल्या मागोवा ठेवलेल्या row मध्ये बदलते, schema गोंधळवते आणि जे समान असायला हवे होते ते अपघाती duplicates आमंत्रित करते.

💵 money साठी floats

रकमा floating point म्हणून साठवणे rounding drift आमंत्रित करते जिथे 0.1 अधिक 0.2 हे 0.3 नसते. value object च्या आत integer cents किंवा decimal type वर Money चे मॉडेलिंग करा.

🧵 Primitive obsession

email साठी raw strings आणि रकमांसाठी raw numbers पाठवणे validation सर्वत्र विखुरते आणि एक currency string एका email field मध्ये पडू देते. त्यांना typed value objects मध्ये गुंडाळा.

♻️ equals सह hash विसरणे

value equality ठरवणे पण जुळणारे hash न ठरवणे म्हणजे समान Money values वेगवेगळ्या set buckets मध्ये पडतात, त्यामुळे deduplication आणि caching गुपचूप फसतात.

संकेत आणि मापदंड

संकेत आणि मोजमाप कसे करावे

तुम्हाला हा भेद कोडच्या आकारातच जाणवतो. हे संकेत तुम्हाला सांगतात की सीमा योग्यरित्या आखली आहे का.

संकेततो तुम्हाला काय सांगतो
value type वर settersएक गळणारी abstraction; value object mutable आहे आणि shared-state bugs निर्माण करेल
entity equals fields वाचतेIdentity content सोबत गोंधळली जात आहे, त्यामुळे वेगळे records समान म्हणून तुलना होऊ शकतात
समान values साठी duplicate rowsएका value object ला त्याला नको असलेली id दिली गेली, नैसर्गिक deduplication बिघडवत आहे
call sites वर validation पुनरावृत्तीएक गहाळ value object; तीच तपासणी एका constructor ऐवजी अनेक ठिकाणी राहते
Set किंवा map keys विचित्र वागणेएका value object वर equals आणि hash एकमेकांशी जुळत नाहीत
lifecycle दरम्यान id बदलणेentity ची सीमा चुकीची आहे; identity निर्मितीपासून हटवण्यापर्यंत स्थिर असावी
अनुभवाचा नियम: जर एका type ला setter असेल, तर त्याला id नसावी; जर एका type ला id असेल, तर त्याच्या equality ने फक्त ती id वाचावी. जेव्हा त्या नियमाचे दोन्ही अर्धे संपूर्ण मॉडेलमध्ये टिकतात, तेव्हा entity आणि value ची सीमा स्वच्छ असते.
06 - Case Studies

वास्तविक जगातील case studies

तीन production-शैलीच्या प्रणाली जिथे entity आणि value object ची विभागणी भार वाहणारी आहे.

💳

1 · Money value object सह payments ledger

Pattern: immutable रकमा, मागोवा ठेवलेले transactions

एका payments platform ला एकही cent न गमावता किंवा shared state न बदलता रकमा जोडणे, विभागणे आणि रूपांतरित करणे आवश्यक असते.

  • Money हे integer minor units अधिक एक currency code वरचे एक frozen value object आहे, content वरून समान.
  • प्रत्येक Transaction ही एक स्थिर id, एक immutable Money रक्कम, आणि एक status lifecycle असलेली entity आहे.
  • Arithmetic नवीन Money instances परत करते, त्यामुळे reports मध्ये पुन्हा वापरल्यावर ledger entries कधीही बदलत नाहीत.
✅ परिणाम: Reconciliation cent पर्यंत जुळते कारण रकमा immutable values आहेत तर प्रत्येक transaction id वरून स्वतंत्रपणे मागोवा ठेवला जातो.
📦

2 · E-commerce orders आणि addresses

Pattern: value snapshots वरची entity lifecycle

एका online store ला एक order edits आणि shipping मधून टिकून राहणे आवश्यक आहे तर ज्या नेमक्या address सह तो दिला गेला तो जपणे आवश्यक आहे.

  • Order आणि Customer entities आहेत; shipping Address आणि line prices value objects आहेत.
  • checkout च्या वेळी नोंदवलेला Address हा एक frozen snapshot आहे, त्यामुळे नंतरचे profile edits कधीही जुने orders पुन्हा लिहीत नाहीत.
  • Order id cart पासून delivery पर्यंत स्थिर राहते तर त्याची status आणि lines विकसित होतात.
✅ परिणाम: ऐतिहासिक orders त्यांचे मूळ addresses आणि totals जपतात, तर live customer entity एका identity खाली विकसित होत राहते.
📧

3 · Email value object सह accounts आणि auth

Pattern: एका entity चे रक्षण करणारी validated values

एका user-accounts सेवेने email ला एक validated, तुलनायोग्य value म्हणून वागवावे तर account स्वतः एक दीर्घकाळ टिकणारी entity असते.

  • Email हे एक value object आहे जे construction च्या वेळी त्याचा address एकदाच normalize आणि validate करते.
  • Customer ही एक user id वर keyed entity आहे, त्यामुळे email बदलल्याने customer कोण आहे हे कधीही बदलत नाही.
  • समान Email values एकसारख्या तुलना आणि hash होतात, uniqueness तपासण्या आणि lookups ला बळ देतात.
✅ परिणाम: Duplicate-email तपासण्या विश्वासार्ह असतात आणि account identity स्थिर असते, कारण value validate केलेली असते आणि entity id वरून मागोवा ठेवली जाते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

entity आणि value object ची विभागणी आधुनिक frameworks च्या आधीची आहे आणि भाषा immutable data ला first-class समर्थन जोडत असताना ती अधिकाधिक उपयुक्त होत जाते.

🧊 Records आणि frozen data

TypeScript readonly, Python frozen dataclasses, Kotlin data classes, आणि Java records value objects ला एका ओळीचे बनवतात, त्यामुळे mutable value types साठी कोणतेही निमित्त नाही.

🏗️ Domain-driven design

DDD बरोबर याच विभागणीतून aggregates बांधते: identity असलेल्या entities एका aggregate ला अँकर करतात तर value objects त्याची measurements आणि descriptions व्यक्त करतात.

🔗 Event sourcing

Events ही immutable value objects आहेत; entity म्हणजे त्यांची पुनरावृत्ती करून पुनर्रचित केलेले aggregate, जे identity-विरुद्ध-content ही रेषा स्पष्ट करते.

🧪 सोपे testing

Immutable value objects ना setup किंवा teardown ची गरज नसते आणि ती content वरून तुलना करतात, त्यामुळे assertions स्वच्छ वाचली जातात आणि tests cases दरम्यान state गळू देत नाहीत.

🧵 Concurrency सुरक्षा

Immutable values locks शिवाय threads आणि async tasks मध्ये सामायिक करणे सुरक्षित असते, जे सेवा अधिक concurrent होत असताना महत्त्वाचे आहे.

🗃️ ORM mapping

आधुनिक ORMs value objects ना embedded किंवा owned types म्हणून आणि entities ला keys असलेल्या tables मध्ये map करतात, हा भेद थेट persistence layer मध्ये encode करतात.

सारांश: entity विरुद्ध value object ठरवणे हा तुम्ही घेतलेला पहिला खरा मॉडेलिंग निर्णय आहे, आणि त्याचा फायदा सर्वत्र होतो: योग्य equality, सुरक्षित सामायिकीकरण, स्वच्छ persistence, आणि जे म्हणते तेच सांगणारा कोड.
