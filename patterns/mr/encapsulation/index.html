Encapsulation - डेटा खाजगी ठेवा, वर्तन खुले करा

Encapsulation state आणि त्याचे नियंत्रण करणारे नियम एका ऑब्जेक्टमध्ये एकत्र बांधते, आणि मग कच्ची फील्ड्स एका लहान, हेतुपुरस्सर API मागे लपवते. Callers आत पोहोचून balance किंवा एखाद्या order च्या total ला बिघडवू शकत नाहीत; ते फक्त ऑब्जेक्टला अशा गोष्टी करायला सांगू शकतात ज्या सुरक्षित असल्याचे त्याला माहीत असते. याचा परिणाम असा की ऑब्जेक्ट नेहमी वैध राहतो, कारण त्याला बदलण्याचा एकमेव मार्ग अशा methods मधून जातो ज्या त्याच्या invariants चे रक्षण करतात.

01 - काय

Encapsulation म्हणजे काय?

Encapsulation म्हणजे एखाद्या ऑब्जेक्टचे अंतर्गत state लपवणे आणि बाहेरील जगाला ते फक्त नियंत्रित methods च्या संचामधूनच स्पर्श करू देणे. ऑब्जेक्ट स्वतःच्या डेटाचा आणि तो डेटा वैध कशामुळे राहतो याच्या नियमांचा मालक असतो. एखादे बदलता येणारे balance फील्ड उघड करण्याऐवजी, BankAccount हे deposit() आणि withdraw() उघड करते, आणि त्या methods खात्याला मोडणारी कोणतीही गोष्ट नाकारतात.

🔒 डेटा लपवणे

फील्ड्स private म्हणून चिन्हांकित केली जातात जेणेकरून कोणताही caller त्यांना थेट नियुक्त करू शकत नाही. state बदलण्याचा एकमेव मार्ग म्हणजे नियम लागू करणाऱ्या methods मधून जाणे.

🚪 एक अरुंद सार्वजनिक API

ऑब्जेक्ट withdraw(amount) सारखी हेतू-प्रकट करणारी operations उघड करते, कच्चे setters नाही. पृष्ठभाग लहान राहतो आणि चुकीने वापरणे कठीण असते.

🛡️ संरक्षित invariants

"balance कधीही ऋण होत नाही" किंवा "एखाद्या order चे total त्याच्या lines च्या बेरजेइतके असते" असे नियम प्रत्येक क्षणी टिकून राहतात कारण फक्त विश्वासार्ह कोडच state बदलू शकतो.

02 - का

Encapsulation का अस्तित्वात आहे

जेव्हा state सार्वजनिक असते, तेव्हा सिस्टीममधील कोडची प्रत्येक ओळ ती बिघडवू शकणारे संभाव्य ठिकाण बनते. Encapsulation तो स्फोट-परिघ काही मोजक्या methods पर्यंत आकुंचित करते ज्या तुम्ही वाचू शकता, तपासू शकता आणि त्यांच्यावर विश्वास ठेवू शकता.

🐛 बिघडलेल्या-state च्या कमी बग्स

जर कधी ऋण balance दिसला, तर त्याचे कारण एका class च्या आत असते, फील्डला थेट स्पर्श करणाऱ्या डझनभर call sites मध्ये विखुरलेले नसते.

🔧 अंतर्गत गोष्टी बदलण्याचे स्वातंत्र्य

पैसे cents म्हणून साठवा, मग एका Money value type कडे वळा, आणि कोणताही caller मोडत नाही कारण त्यांनी नेहमी फक्त methods पाहिल्या, कधीही फील्ड नाही.

🧪 तपासणे आणि समजणे सोपे

तुम्ही नियम एकाच ठिकाणी तपासता. एक वैध ऑब्जेक्ट दिल्यास, त्याचे invariants टिकतात हे तुम्हाला माहीत असते, त्यामुळे पुढच्या कोडला कमी बचावात्मक तपासण्यांची गरज लागते.

🤝 संघांमधील स्पष्ट करार

सार्वजनिक method यादी हाच करार आहे. संघ कोणती फील्ड संयोजने सुरक्षित आहेत याचा अंदाज लावण्याऐवजी हेतू-प्रकट करणाऱ्या operations विरुद्ध एकत्रीकरण करतात.

सोप्या शब्दांत

उपमांसह समजावलेले Encapsulation

तीच कल्पना, ती चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ते तुमच्या डोक्यात बसेल.

🎓 विद्यार्थ्यासाठी

Encapsulation हे एका vending machine सारखे आहे. तुम्ही बटणे दाबता आणि नाणी टाकता; तारा पकडायला तुम्ही कधीही पॅनेल उघडत नाही. मशीन ती वस्तू देऊ शकते का हे ठरवते, आणि स्वतःच्या नाण्यांच्या मोजणीचे रक्षण करते.

👩‍💻 डेव्हलपरसाठी

ती एक अशी class आहे जिथे फील्ड्स private असतात आणि बदल methods मधून जातो. order.total = 90 ऐवजी, तुम्ही order.addLine(item) कॉल करता आणि total स्वतःची पुनर्गणना करते, त्यामुळे ते कधीही lines शी विसंगत होऊ शकत नाही.

🏢 व्यावसायिकासाठी

एका बँक टेलर खिडकी चा विचार करा. ग्राहक तिजोरीत चालत जात नाहीत; ते टेलरला एक स्लिप देतात, जो पैसे हलवण्यापूर्वी नियम तपासतो. प्रवेश मध्यस्थीने होतो म्हणून तिजोरी सुसंगत राहते.

💊 रोजच्या जीवनातील आवृत्ती

एक child-proof झाकण असलेली औषधाची बाटली. आतील सामग्री पोहोचण्याजोगी आहे, पण फक्त अशा एका हेतुपुरस्सर हालचालीतून जी अपघाती, असुरक्षित प्रवेश थांबवते. तो अडथळाच मुद्दा आहे.

03 - कसे

Encapsulation प्रत्यक्षात कसे काम करते

ऑब्जेक्टने कोणत्या invariants ची हमी दिली पाहिजे हे ठरवण्यापासून तुम्ही सुरुवात करता, मग प्रत्येक फील्ड private करता आणि सर्व बदल त्या invariants ना लागू करणाऱ्या methods मधून वळवता. Access modifiers हे भाषा-स्तरावरील साधन आहे जे "कृपया याला स्पर्श करू नका" चे रूपांतर "तुम्ही याला स्पर्श करू शकत नाही" मध्ये करते.

🔐 Access modifiers

private म्हणजे फक्त हीच class ते पाहते, protected म्हणजे ही class आणि subclasses, public म्हणजे प्रत्येकजण. Python आघाडीच्या underscore (_field) ने हेतू दर्शवते आणि __field चे name-mangle करते; Ruby by default state private करते आणि ते फक्त attr_reader किंवा methods द्वारे उघड करते.

🎯 वर्तन-समृद्ध ऑब्जेक्ट्स विरुद्ध get/set बॅग्स

प्रत्येक फील्डसाठी सार्वजनिक getter आणि setter असलेला अशक्त (anemic) ऑब्जेक्ट म्हणजे class चा पोशाख घातलेला केवळ एक struct आहे. वर्तन-समृद्ध ऑब्जेक्ट क्रियापदे (deposit, cancel, applyDiscount) उघड करतो जी नियम वाहून नेतात, त्यामुळे callers कच्ची फील्ड्स फिरवण्याऐवजी परिणामांची मागणी करतात.

Classes एका दृष्टिक्षेपात

// Money is stored as integer cents so we never leak floating-point rounding.
class InsufficientFundsError extends Error {}

class BankAccount {
  // Truly private: the # fields are invisible and unwritable from outside.
  #balanceCents: number;
  readonly #overdraftLimitCents: number;

  constructor(openingCents: number, overdraftLimitCents = 0) {
    if (overdraftLimitCents < 0) throw new Error("Overdraft limit must be >= 0");
    if (openingCents < -overdraftLimitCents) {
      throw new Error("Opening balance breaks the overdraft limit");
    }
    this.#balanceCents = openingCents;
    this.#overdraftLimitCents = overdraftLimitCents;
  }

  deposit(amountCents: number): void {
    if (amountCents <= 0) throw new Error("Deposit must be positive");
    this.#balanceCents += amountCents;
  }

  withdraw(amountCents: number): void {
    if (amountCents <= 0) throw new Error("Withdrawal must be positive");
    if (this.#balanceCents - amountCents < -this.#overdraftLimitCents) {
      throw new InsufficientFundsError("Withdrawal exceeds available funds");
    }
    this.#balanceCents -= amountCents;
  }

  // Queries return safe, derived views. No setter for the balance exists.
  get balanceCents(): number { return this.#balanceCents; }
  get availableToSpendCents(): number {
    return this.#balanceCents + this.#overdraftLimitCents;
  }
}

const acct = new BankAccount(5_000, 2_000); // $50.00, $20 overdraft
acct.deposit(2_500);                        // $75.00
acct.withdraw(9_000);                       // dips into overdraft, still legal
console.log(acct.balanceCents);             // -500  (i.e. -$5.00)
// acct.#balanceCents = 1_000_000;          // compile error: private field
try {
  acct.withdraw(5_000);                     // would exceed overdraft
} catch (e) {
  console.log((e as Error).message);        // "Withdrawal exceeds available funds"
}

    def __init__(self, opening_cents: int, overdraft_limit_cents: int = 0):
        if overdraft_limit_cents < 0:
            raise ValueError("Overdraft limit must be >= 0")
        if opening_cents < -overdraft_limit_cents:
            raise ValueError("Opening balance breaks the overdraft limit")
        # Double underscore triggers name mangling: hard to touch by accident.
        self.__balance_cents = opening_cents
        self.__overdraft_limit_cents = overdraft_limit_cents

    def deposit(self, amount_cents: int) -> None:
        if amount_cents <= 0:

    @property
    def balance_cents(self) -> int:
        return self.__balance_cents

    @property
    def available_to_spend_cents(self) -> int:

# Money is stored as integer cents so we never leak floating-point rounding.
class InsufficientFundsError < StandardError; end

class BankAccount
  # attr_reader exposes a getter only; there is no writer for the balance.
  attr_reader :balance_cents

  def initialize(opening_cents, overdraft_limit_cents = 0)
    raise ArgumentError, "Overdraft limit must be >= 0" if overdraft_limit_cents < 0
    if opening_cents < -overdraft_limit_cents
      raise ArgumentError, "Opening balance breaks the overdraft limit"
    end
    @balance_cents = opening_cents
    @overdraft_limit_cents = overdraft_limit_cents
  end

  def deposit(amount_cents)
    raise ArgumentError, "Deposit must be positive" if amount_cents <= 0
    @balance_cents += amount_cents
  end

  def withdraw(amount_cents)
    raise ArgumentError, "Withdrawal must be positive" if amount_cents <= 0
    if @balance_cents - amount_cents < -@overdraft_limit_cents
      raise InsufficientFundsError, "Withdrawal exceeds available funds"
    end
    @balance_cents -= amount_cents
  end

  def available_to_spend_cents
    @balance_cents + @overdraft_limit_cents
  end
end

तिन्हींमध्ये, balance फक्त deposit आणि withdraw मधूनच हलू शकते, आणि बदल करण्यापूर्वी दोन्ही overdraft नियम तपासतात. कोणताही सार्वजनिक setter नाही, त्यामुळे "balance कधीही overdraft मर्यादेखाली जात नाही" हे invariant प्रत्येक caller योग्य वागेल अशी आशा करून नव्हे, तर बांधणीनेच हमी दिलेले असते.

एका अशक्त get/set बॅगपासून वर्तन-समृद्ध ऑब्जेक्टकडे

// BEFORE: anemic Order. Public fields, no rules. Any caller can corrupt it.
class OrderBag {
  totalCents = 0;
  status = "open";
}
const bad = new OrderBag();
bad.totalCents = -999;        // negative total, nobody stopped it
bad.status = "shpped";        // typo, meaningless state, no complaint

// AFTER: Order owns its lines and derives its total. Illegal states blocked.
type Line = { sku: string; unitCents: number; qty: number };

class Order {
  #lines: Line[] = [];
  #status: "open" | "placed" | "cancelled" = "open";

  addLine(sku: string, unitCents: number, qty: number): void {
    if (this.#status !== "open") throw new Error("Cannot edit a closed order");
    if (unitCents < 0 || qty <= 0) throw new Error("Invalid line");
    this.#lines.push({ sku, unitCents, qty });
  }

  place(): void {
    if (this.#lines.length === 0) throw new Error("Cannot place an empty order");
    this.#status = "placed";
  }

  // Total is DERIVED, so it can never disagree with the lines.
  get totalCents(): number {
    return this.#lines.reduce((sum, l) => sum + l.unitCents * l.qty, 0);
  }
  get status(): string { return this.#status; }
}

const order = new Order();
order.addLine("SKU-42", 1_299, 2);   // $25.98
order.place();
console.log(order.totalCents);       // 2598, always in sync with the lines

# AFTER: Order owns its lines and derives its total. Illegal states blocked.
from dataclasses import dataclass, field


@dataclass(frozen=True)
class Line:
    sku: str
    unit_cents: int
    qty: int


class Order:
    def __init__(self):
        self.__lines: list[Line] = []
        self.__status = "open"

    def add_line(self, sku: str, unit_cents: int, qty: int) -> None:
        if self.__status != "open":
            raise ValueError("Cannot edit a closed order")
        if unit_cents < 0 or qty <= 0:
            raise ValueError("Invalid line")
        self.__lines.append(Line(sku, unit_cents, qty))

    def place(self) -> None:
        if not self.__lines:
            raise ValueError("Cannot place an empty order")
        self.__status = "placed"

    # Total is DERIVED, so it can never disagree with the lines.
    @property
    def total_cents(self) -> int:
        return sum(l.unit_cents * l.qty for l in self.__lines)

    @property
    def status(self) -> str:
        return self.__status


order = Order()
order.add_line("SKU-42", 1_299, 2)   # $25.98
order.place()
print(order.total_cents)             # 2598, always in sync with the lines
# BEFORE: anemic Order. Public fields, no rules. Any caller can corrupt it.
class OrderBag
  attr_accessor :total_cents, :status
  def initialize
    @total_cents = 0
    @status = "open"
  end
end

bad = OrderBag.new
bad.total_cents = -999   # negative total, nobody stopped it
bad.status = "shpped"    # typo, meaningless state, no complaint


# AFTER: Order owns its lines and derives its total. Illegal states blocked.
Line = Struct.new(:sku, :unit_cents, :qty)

class Order
  attr_reader :status

  def initialize
    @lines = []
    @status = "open"
  end

  def add_line(sku, unit_cents, qty)
    raise "Cannot edit a closed order" unless @status == "open"
    raise "Invalid line" if unit_cents < 0 || qty <= 0
    @lines << Line.new(sku, unit_cents, qty)
  end

  def place
    raise "Cannot place an empty order" if @lines.empty?
    @status = "placed"
  end

  # Total is DERIVED, so it can never disagree with the lines.
  def total_cents
    @lines.sum { |l| l.unit_cents * l.qty }
  end
end

order = Order.new
order.add_line("SKU-42", 1_299, 2)   # $25.98
order.place
puts order.total_cents               # 2598, always in sync with the lines

अशक्त बॅग कोणत्याही caller ला निरर्थक total किंवा चुकीचे शब्दलेखन केलेली status नियुक्त करू देते. वर्तन-समृद्ध Order total कधीही साठवतच नाही; ते आत येताना तपासलेल्या lines मधून एक total व्युत्पन्न करते, त्यामुळे total आणि lines कधीही एकमेकांपासून विलग होऊ शकत नाहीत.

सामान्य अडचणी

अडचणी आणि anti-patterns

Encapsulation चा बनाव करणे सोपे आहे आणि ते गळणेही सोपे आहे. हे असे संकेत आहेत जे शांतपणे ते पूर्ववत करतात.

🎭 Getter/setter नाटक

प्रत्येक private फील्डला केवळ नियुक्ती करण्यापलीकडे काहीही न करणाऱ्या सार्वजनिक getter आणि setter मध्ये गुंडाळणे म्हणजे फील्ड सार्वजनिक करण्यासारखेच आहे. नियम अजूनही कुठेच राहत नाहीत.

🩸 बदलता येणारे अंतर्गत भाग गळणे

प्रत्यक्ष अंतर्गत list किंवा map परत केल्याने caller ऑब्जेक्टच्या पाठीमागे तिला बदलू शकतो. त्याऐवजी एक प्रत किंवा read-only दृश्य परत करा.

🧟 अशक्त domain model

जे ऑब्जेक्ट्स फक्त डेटा धरून ठेवतात तर सगळे logic service classes मध्ये राहते ते वेशांतर केलेले structs असतात. वर्तन आणि ते जो डेटा राखते तो एकत्र असले पाहिजेत.

🔓 Input वर विश्वास ठेवणारा constructor

Arguments न तपासता ऑब्जेक्ट बांधल्याने अवैध instance जन्मापासूनच अस्तित्वात राहू शकतो, त्यामुळे नंतरच्या प्रत्येक method ला त्याच गोष्टी पुन्हा तपासाव्या लागतात.

📢 अती-उघड API

सोयीसाठी helpers ना public चिन्हांकित केल्याने करार रुंदावतो. Callers तुम्ही बदलण्यास मोकळे ठेवू इच्छित असलेल्या अंतर्गत भागांवर अवलंबून राहू लागतात.

🧮 व्युत्पन्न मूल्ये साठवणे

Order total lines सोबत एका फील्डमध्ये cache केल्याने विलगता निमंत्रित होते; एक line जोडा आणि तिला update करायला विसरा, आणि दोघे विसंगत होतात. मागणीनुसार व्युत्पन्न करा.

संकेत आणि मापदंड

संकेत आणि मोजमाप कसे करावे

Encapsulation वर तुम्ही एकच आकडा ठेवू शकत नाही, पण हे संकेत तुम्हाला सांगतात की तुमचे ऑब्जेक्ट्स प्रत्यक्षात स्वतःचे रक्षण करत आहेत का.

संकेतते तुम्हाला काय सांगते
सार्वजनिक setter ची संख्याअनेक सरसकट setters म्हणजे state प्रत्यक्षात खुले आहे आणि नियम इतरत्र किंवा कुठेच राहतात.
Commands आणि accessors चे गुणोत्तरबहुतांश क्रियापदे वर्तन-समृद्ध ऑब्जेक्ट्स दर्शवतात; बहुतांश get/set एक अशक्त डेटा बॅग दर्शवते.
प्रति फील्ड invariant तपासण्यातीच पडताळणी अनेक call sites वर पुनरावृत्त होणे म्हणजे ऑब्जेक्ट स्वतःच्या state चे रक्षण करत नाही.
परत केलेल्या संग्रहांचे बाह्य बदलजर callers एखादा getter जे परत करतो ते बदलू शकत असतील, तर अंतर्गत भाग गळत आहेत आणि encapsulation मोडलेले आहे.
अशक्य states च्या बग रिपोर्ट्सProduction मध्ये ऋण balances किंवा totals थेट एका गहाळ किंवा टाळता येणाऱ्या guard कडे बोट दाखवतात.
बदलाचा स्फोट-परिघतुम्ही एखादे फील्ड पुनर्नामित केल्यावर किती फायली मोडतात यावरून अंतर्गत भाग किती चांगले लपवले होते हे मोजले जाते.
ठोकताळा: जर तुम्ही एखादा अवैध ऑब्जेक्ट बांधू शकत असाल, किंवा class च्या बाहेरून आत पोहोचून एखादा वैध ऑब्जेक्ट बिघडवू शकत असाल, तर तो ऑब्जेक्ट encapsulated नाही, त्यावर कितीही private keywords असले तरी.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन production-शैलीच्या सिस्टीम्स जिथे encapsulation हेच डेटा विश्वासार्ह ठेवते.

🏦

1 · Payments platform मधील ledger service

Pattern: account balance जे कधीही अवैध होऊ शकत नाही

एक payments platform पैशांची प्रत्येक हालचाल नोंदवते आणि खात्याने कधीही शांतपणे त्याच्या परवानगीच्या मर्यादेखाली जाऊ नये याची हमी देणे आवश्यक असते.

  • Balance हे cents चा एक private integer आहे; एकमेव बदल म्हणजे post आणि reverse operations जी आधी मर्यादा तपासतात.
  • Constructor overdraft नियम आधीच मोडणाऱ्या opening states ना नाकारतो, त्यामुळे कोणतेही अवैध खाते कधीही साठवले जात नाही.
  • Queries available-to-spend एक गणना केलेले मूल्य म्हणून उघड करतात, कधीही कच्चे फील्ड नाही, त्यामुळे callers नियम टाळू शकत नाहीत.
✅ परिणाम: Reconciliation मध्ये अशक्य balances दिसणे थांबते कारण पैशांची मालकी असलेली एकमेव class हाच त्यांना हलवू शकणारा एकमेव कोड असतो.
🛒

2 · E-commerce backend मधील checkout आणि cart

Pattern: पडताळलेल्या lines मधून व्युत्पन्न केलेले order total

एका e-commerce backend ने हे सुनिश्चित करणे आवश्यक असते की items जोडले आणि काढले जात असले तरी order total नेहमी discounts नंतरच्या त्याच्या lines च्या बेरजेइतके असते.

  • Order lines ची एक private list धरून ठेवते आणि total मागणीनुसार गणते, त्यामुळे दोघे कधीही विलग होऊ शकत नाहीत.
  • Placed order ला line जोडल्यास त्रुटी येते, ज्यामुळे placed orders गोठलेली असतात हे invariant संरक्षित होते.
  • Discounts अशा methods मधून लावले जातात ज्या परिणाम शून्यावर मर्यादित करतात, त्यामुळे total कधीही ऋण होऊ शकत नाही.
✅ परिणाम: जुळत नसलेल्या totals मुळे होणारे किंमत वाद नाहीसे होतात कारण total हे एक गणना केलेले सत्य आहे, caller बदलू शकेल असे फील्ड नाही.
📦

3 · Warehouse system मधील inventory मोजण्या

Pattern: oversell पासून रक्षिलेली stock पातळी

एक warehouse system on-hand आणि reserved प्रमाणांचा मागोवा घेते आणि reserved ने कधीही on-hand पेक्षा जास्त होऊ देता कामा नये.

  • दोन्ही मोजण्या private आहेत; reserve आणि release हेच त्यांना बदलण्याचे एकमेव मार्ग आहेत, आणि प्रत्येक invariant तपासतो.
  • Reserved ला on-hand पेक्षा वर ढकलणारे reservation शांतपणे जास्त सेट न करता स्पष्ट domain error सह नाकारले जाते.
  • उपलब्ध stock हे on-hand वजा reserved म्हणून उघड केले जाते, साठवून जुने होण्याचा धोका न पत्करता प्रत्येक वेळी गणले जाते.
✅ परिणाम: Overselling च्या घटना झपाट्याने कमी होतात कारण stock ऑब्जेक्ट स्वतःची सुसंगती मोडणारी कोणतीही operation नाकारते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Encapsulation आजच्या बहुतांश stacks च्या आधीचे आहे, तरीही प्रत्येक आधुनिक कल त्यावर कमी नव्हे तर अधिक जोर देतो.

🧱 Domain-driven design

Aggregates म्हणजे मोठ्या प्रमाणावरील encapsulation: एक root ऑब्जेक्ट्सचा एक समूह आणि त्यांच्या invariants चे रक्षण करते, आणि बाहेरील कोड त्या समूहाला फक्त त्याच्यामार्फतच स्पर्श करतो.

🔗 Microservice सीमा

API मागे स्वतःचा database लपवणारी service म्हणजे नेटवर्कवरील encapsulation. Private state म्हणजे schema; सार्वजनिक पृष्ठभाग म्हणजे करार.

🧊 Value objects आणि immutability

Money, Email, आणि Quantity types पडताळणी एकदाच encapsulate करतात, त्यामुळे एक वैध मूल्य जिथे जिथे प्रवास करते तिथे वैधच राहते, पुन्हा तपासण्याची गरज नाही.

🦀 भाषा-लागू केलेली गोपनीयता

Rust modules, TypeScript private fields, आणि Kotlin visibility compiler ला लपवणे लागू करायला लावतात, ज्यामुळे एका प्रथेचे रूपांतर एका हमीमध्ये होते.

🤖 सुरक्षित code generation

जेव्हा ऑब्जेक्ट्स स्वतःचे नियम लागू करतात, तेव्हा generated किंवा agent ने लिहिलेली call sites state बिघडवू शकत नाहीत, कारण एकमेव दरवाजा अजूनही पडताळणी करतो.

⚡ Concurrency सुरक्षा

एका रक्षिलेल्या ऑब्जेक्टमधून पोहोचता येणारे state सर्वत्र स्पर्श केलेल्या फील्ड्सपेक्षा synchronize करणे खूप सोपे असते, त्यामुळे encapsulation हे concurrency चे मित्र आहे.

सारांश: encapsulation म्हणजे डेटा आणि त्याचे नियम एकाच रक्षिलेल्या ठिकाणी ठेवून अवैध states अशक्य करण्याची शिस्त. सिस्टीम्स वाढत जातात आणि अधिक कोड, मानवी किंवा generated, त्यांना स्पर्श करतो तसे, स्वतःचे रक्षण करणारा ऑब्जेक्ट हाच संपूर्ण सिस्टीमला प्रामाणिक ठेवतो.
