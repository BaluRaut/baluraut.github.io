The Anemic Domain Model - डेटा असलेली पण वर्तन नसलेली objects

Anemic domain model म्हणजे असा codebase जिथे तुमच्या entities फक्त getters आणि setters ची पिशवी असतात आणि प्रत्येक नियम वेगळ्या service layer मध्ये राहतो. तो object-oriented वाटतो, पण तो खरे तर class चा पोशाख घातलेला procedural code असतो. Rich पर्याय वर्तन त्या डेटाच्या शेजारी ठेवतो ज्याचे ते रक्षण करते, म्हणजे एखादा Order स्वतःचे invariants स्वतः लागू करतो, आणि ते लक्षात ठेवण्यासाठी OrderService वर विश्वास ठेवत नाही.

01 - काय

Anemic Domain Model म्हणजे काय?

एक anemic domain model म्हणजे असे design जिथे domain objects स्थिती (state) बाळगतात पण जवळपास कोणतेही लॉजिक नसते. Order, Cart आणि Invoice हे classes public fields (किंवा प्रत्येक field साठी getters आणि setters) उघड करतात आणि त्यापलीकडे काहीच नाही. सर्व खरे वर्तन - एखादे transition तपासणे, एकूण रक्कम काढणे, discount लावणे - stateless service classes मध्ये ढकलले जाते, जे त्या objects मध्ये पोहोचतात, डेटा वाचतात, त्यात बदल करतात आणि परत लिहितात. ही objects anemic असतात कारण रक्त, म्हणजेच वर्तन, त्यांच्यातून काढून टाकलेले असते.

🩸 फक्त-डेटा entities

Order सारखे classes fields आणि accessors बाळगतात. व्यवसायाच्या भाषेत अर्थपूर्ण असे त्यांना कोणतेही methods नसतात, फक्त getStatus() आणि setStatus().

🏭 जाडजूड service layer

एक OrderService प्रत्येक नियम बाळगतो. Order कधी पाठवला जाऊ शकतो, एकूण रक्कम कशी मोजली जाते आणि कोणती transitions वैध आहेत हे तो ठरवतो - entity ला बाहेरून वाचून आणि लिहून.

🔓 Invariants खुली राहतात

कोणताही caller कोणतेही field सेट करू शकत असल्याने, object कधीही वैध स्थितीत आहे याची खात्री काहीच देत नाही. नियम इतरत्र कुठेतरी राहतात, आणि तेही फक्त तेव्हाच जर caller ने service मार्गे जाण्याचे लक्षात ठेवले.

Martin Fowler ने याला anti-pattern हे नाव नेमके यासाठी दिले कारण ते domain model ची किंमत (mapping, hydration) मोजते आणि त्याचा फायदा (encapsulated वर्तन) गमावते.
02 - का

हे का महत्त्वाचे आहे

Anemic शैली मोहक असते कारण ती सुरू करणे सोपे आहे आणि database rows शी एक-एक जुळते. किंमत नंतर येते, जेव्हा तोच नियम तीन services मध्ये पुन्हा तपासावा लागतो आणि त्यातली एक विसरते.

🛡️ Encapsulation गमावले जाते

Public setters म्हणजे कुठलाही कोड कुठेही एखाद्या Order ला अशक्य स्थितीत टाकू शकतो - पैसे भरण्याआधी पाठवलेला, ऋण संख्या. Object स्वतःचा बचाव करू शकत नाही, म्हणून ती हमी प्रत्येक ठिकाणी पुन्हा द्यावी लागते.

🧭 लॉजिकचे घर हरवते

वर्तन जेव्हा डेटाबरोबर राहत नाही, तेव्हा तेच total-calculation किंवा state-check OrderService, CheckoutService आणि ReportService मध्ये पुन्हा पुन्हा दिसते. Duplication हळूहळू भरकटते आणि प्रती शांतपणे एकमेकांशी विसंगत होतात.

🔍 Domain वाचता येत नाही

एखादा order काय करू शकतो हे जाणून घ्यायला तुम्ही Order class वाचू शकत नाही - तुम्हाला संपूर्ण service layer मधून grep करावे लागते. व्यवसायाची ubiquitous language कधीच methods म्हणून दिसत नाही.

🧪 Testing अवघड होते

Stateless services मध्ये अडकलेल्या नियमांना "unpaid order पाठवता येत नाही" इतकेच सिद्ध करायला सहसा repository, gateway आणि clock चे mocks लागतात, आणि हे तर खरे तर एकाच object बद्दलचे सत्य आहे.

सोप्या शब्दांत

उपमांसह समजावलेले Anemic Domain Model

तीच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती पटकन समजेल.

🎓 विद्यार्थ्यासाठी

Anemic object म्हणजे उत्तराची किल्ली नसलेली रिकाम्या जागा भरा अशी worksheet. कुणीही चौकटींमध्ये काहीही लिहू शकतो; काय बरोबर मानायचे याचे नियम शिक्षकाच्या डोक्यात, दुसऱ्या खोलीत असतात. Rich object म्हणजे अशी worksheet जी तुम्ही लिहित असतानाच अवैध उत्तरे नाकारते.

👩‍💻 developer साठी

ते manager function असलेले struct आहे. तुमच्याकडे एक डेटा record आहे आणि त्यावर काम करणाऱ्या मोकळ्या functions चा ढीग आहे. C मध्ये हे ठीक आहे, पण object language मध्ये तुम्ही classes साठी किंमत मोजली आहे आणि त्यांना समर्थन देणारे एकमेव वैशिष्ट्य - state च्या शेजारी वर्तन - फेकून दिले आहे.

🏢 व्यावसायिकासाठी

अशी कल्पना करा की बँक खाते जिथले शिल्लक कुणीही खोडून पुन्हा लिहू शकते, आणि "शून्याखाली कधीच जाऊ नका" हा नियम फक्त teller च्या हस्तपुस्तिकेत असतो. एखादा teller पुस्तिका उघडायला विसरला, तर खाते ऋण होते. Rich model हा नियम खात्यातच बेक करतो.

🚗 रोजच्या भाषेत

अशी कार जिचे engine, brakes आणि steering काढून garage मध्ये ठेवले आहेत, शेजारी एक चिठ्ठी आहे "mechanic तुमच्यासाठी हे चालवेल." तिच्याकडे कारचे सर्व भाग आहेत आणि चालवण्याची कोणतीही क्षमता नाही. वर्तन ज्याला त्याची गरज आहे त्या गोष्टीपासून वेगळे केले गेले.

03 - कसे

ते कसे ओळखायचे आणि कसे दुरुस्त करायचे

Anemic पासून rich कडे refactor यांत्रिक आहे: एखाद्या service मध्ये एक नियम शोधा, ज्या object चा डेटा तो वाचतो तो शोधा, आणि तो नियम त्या object वर एक नाव असलेले method म्हणून हलवा. मग fields private करा जेणेकरून कुणी त्याला बगल देऊ शकणार नाही.

🩸 Anemic आकार

Public status, items आणि paidAt असलेला Order, आणि त्या fields ला बाहेरून वाचून बदलणारे OrderService.markPaid, OrderService.ship आणि OrderService.total.

💪 Rich आकार

तोच Order पण private state आणि pay(), ship() आणि total() ही methods असलेला. प्रत्येक method आधी invariant तपासते, म्हणून unpaid order पाठवला जाऊच शकत नाही, तो कुणीही बोलावला तरी.

तीन भाषांत तुलना: anemic vs rich

// ANEMIC: Order is a data bag, OrderService does everything.
class Order {
  status: "pending" | "paid" | "shipped" = "pending";
  items: { quantity: number; unitPriceCents: number }[] = [];
  paidAt: Date | null = null;
}

class OrderService {
  markPaid(order: Order, clock: () => Date): void {
    // The rule lives out here, and nothing forces callers through it.
    order.status = "paid";
    order.paidAt = clock();
  }
  ship(order: Order): void {
    if (order.status !== "paid") throw new Error("Order not paid");
    order.status = "shipped";
  }
  totalCents(order: Order): number {
    return order.items.reduce((s, i) => s + i.quantity * i.unitPriceCents, 0);
  }
}

// A caller can bypass every rule; the object cannot defend itself.
const bad = new Order();
bad.status = "shipped"; // shipped without ever being paid. Nothing stops it.

// RICH: behavior and invariants live on the Order itself.
class RichOrder {
  private status: "pending" | "paid" | "shipped" = "pending";
  private paidAt: Date | null = null;
  constructor(private readonly items: LineItem[]) {
    if (items.length === 0) throw new Error("Order needs at least one line item");
  }
  pay(clock: () => Date): void {
    if (this.status !== "pending") throw new Error("Only a pending order can be paid");
    this.status = "paid";
    this.paidAt = clock();
  }
  ship(): void {
    if (this.status !== "paid") throw new Error("Cannot ship an unpaid order");
    this.status = "shipped";
  }
  total(): Money {
    return this.items.reduce((sum, i) => sum.add(i.subtotal()), Money.zero());
  }
}

const order = new RichOrder([new LineItem(2, Money.cents(1999))]);
order.pay(() => new Date());
order.ship();                 // legal: it was paid first
console.log(order.total().format());  // behavior lives where the data lives

from dataclasses import dataclass, field
from datetime import datetime

@dataclass
class Order:
    status: str = "pending"
    items: list = field(default_factory=list)
    paid_at: datetime | None = None

class OrderService:
    def mark_paid(self, order: Order, now: datetime) -> None:
        # The rule lives out here; nothing forces callers through it.
        order.status = "paid"
        order.paid_at = now

    def ship(self, order: Order) -> None:
        if order.status != "paid":
            raise ValueError("Order not paid")
        order.status = "shipped"

    def total_cents(self, order: Order) -> int:
        return sum(i["quantity"] * i["unit_price_cents"] for i in order.items)

# A caller can bypass every rule; the object cannot defend itself.
bad = Order()
bad.status = "shipped"  # shipped without ever being paid. Nothing stops it.

# RICH: behavior and invariants live on the Order itself.
class RichOrder:
    def __init__(self, items: list["LineItem"]):
        if not items:
            raise ValueError("Order needs at least one line item")
        self._items = items
        self._status = "pending"
        self._paid_at: datetime | None = None

    def pay(self, now: datetime) -> None:
        if self._status != "pending":
            raise ValueError("Only a pending order can be paid")
        self._status = "paid"
        self._paid_at = now

    def ship(self) -> None:
        if self._status != "paid":
            raise ValueError("Cannot ship an unpaid order")
        self._status = "shipped"

    def total(self) -> "Money":
        return sum((i.subtotal() for i in self._items), Money.zero())

    @items = []

  end

class OrderService
  def mark_paid(order, now)
    # The rule lives out here; nothing forces callers through it.
    order.status = "paid"
    order.paid_at = now
  end

  def ship(order)
    raise "Order not paid" unless order.status == "paid"
    order.status = "shipped"
  end

  def total_cents(order)
    order.items.sum { |i| i[:quantity] * i[:unit_price_cents] }

class RichOrder
  def initialize(items)
    raise "Order needs at least one line item" if items.empty?
    @items = items
    @status = "pending"
    @paid_at = nil
  end

  def pay(now)
    raise "Only a pending order can be paid" unless @status == "pending"
    @status = "paid"
    @paid_at = now
  end

  def ship
    raise "Cannot ship an unpaid order" unless @status == "paid"
    @status = "shipped"
  end

  def total
    @items.reduce(Money.zero) { |sum, i| sum.add(i.subtotal) }
  end
end

काय हलले ते लक्षात घ्या. Anemic आवृत्तीत कुठलीही कोड-ओळ status = "shipped" सेट करू शकते आणि payment पूर्णपणे वगळू शकते. Rich आवृत्तीत field private आहे आणि आत जाणारे एकमेव दार ship() आहे, जे order भरला गेल्याशिवाय नकार देते. नियम सर्वजण पाळतील अशी आशा असलेल्या प्रथेवरून, object लागू करत असलेल्या हमीत बदलला.

Anemic कधी योग्य निवड असते

// DTOs and API payloads SHOULD be anemic. They carry data across a
// boundary and have no invariants of their own to protect.
interface CreateOrderRequest {
  customerId: string;
  lines: { sku: string; quantity: number }[];
  couponCode?: string;
}

// The wire type is a plain record. Behavior belongs on the domain object
// you build FROM it, not on the transport shape itself.
function toDomain(req: CreateOrderRequest): RichOrder {
  const items = req.lines.map(l => LineItem.fromSku(l.sku, l.quantity));
  return new RichOrder(items); // the RichOrder enforces the rules
}
# DTOs and API payloads SHOULD be anemic. They carry data across a
# boundary and have no invariants of their own to protect.
from dataclasses import dataclass

@dataclass(frozen=True)
class CreateOrderRequest:
    customer_id: str
    lines: list[dict]           # {"sku": str, "quantity": int}
    coupon_code: str | None = None

# The wire type is a plain record. Behavior belongs on the domain object
# you build FROM it, not on the transport shape itself.
def to_domain(req: CreateOrderRequest) -> "RichOrder":
    items = [LineItem.from_sku(l["sku"], l["quantity"]) for l in req.lines]
    return RichOrder(items)     # the RichOrder enforces the rules

# you build FROM it, not on the transport shape itself.
def to_domain(req)
  items = req.lines.map { |l| LineItem.from_sku(l[:sku], l[:quantity]) }
  RichOrder.new(items)          # the RichOrder enforces the rules
end

Anemic नेहमीच चुकीचे नसते. Data transfer objects, API request आणि response bodies, event payloads आणि read-model projections यांना रक्षण करण्यासाठी कोणतेही वर्तन नसते, म्हणून त्यांना methods देणे म्हणजे नुसता गोंधळ ठरेल. हे anti-pattern विशेषतः खऱ्या व्यवसाय नियम असलेल्या domain entities ला records मध्ये घटवण्याबद्दल आहे, तर नियम services मध्ये गळतात.

04 - Sequence आकृत्या

तपशीलवार sequence आकृत्या

तीन दृश्ये: anemic shipping प्रवाह जिथे service सर्वकाही करतो, rich प्रवाह जिथे object स्वतःचा बचाव करतो, आणि सीमा जिथे anemic DTO ला योग्यरीत्या rich entity मध्ये रूपांतरित केले जाते.

    C->>S: ship(orderId)
    S->>R: findById(orderId)
    R-->>S: order
    S->>O: getStatus()
    O-->>S: "paid"
    Note over S,O: The rule lives in the service, not the object
    S->>O: setStatus("shipped")
    S->>R: save(order)
    R-->>S: ok
    S-->>C: shipped
आकृती 2 - Rich: caller एक message पाठवतो आणि object स्वतःचे invariant लागू करतो
sequenceDiagram
    autonumber
    participant C as 🖥️ Controller
    participant S as 🎯 ShipOrderService
    participant O as 💪 Order (rich)
    participant R as 🗄️ OrderRepository

    C->>S: handle(shipCommand)
    S->>R: findById(orderId)
    R-->>S: order

    alt order is paid
        O->>O: change status to shipped

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

Anemic model हेरण्यापासून ते निरोगी rich model पर्यंत, संपूर्ण refactor क्रमाने.

00
हेरा

वास ओळखा

तुमच्या entities फक्त getters आणि setters पलीकडे काहीच नाहीत, आणि वाढणारा ...Service classes चा संच प्रत्येक नियम बाळगतो. हे संयोजन म्हणजे anemic ची स्वाक्षरी.

10
शोधा

खरे नियम शोधा

Service layer मध्ये व्यवसाय लॉजिक शोधा: state transitions, total calculations, discount अटी. ही अशी वर्तने आहेत जी एखाद्या object वर असायला हवीत.

20
जुळवा

प्रत्येक नियम त्याच्या डेटाशी जुळवा

प्रत्येक नियमासाठी, तो जी fields वाचतो आणि लिहितो त्यांचा मालक कोणती entity आहे ते ओळखा. "भरल्याशिवाय पाठवता येत नाही" हा नियम Order वरचे status वाचतो, म्हणून तो Order वर असायला हवा.

30
नाव द्या

हेतू स्पष्ट करणारी methods निवडा

setStatus("shipped") ऐवजी ship() सारखे domain क्रियापद वापरा. Method चे नाव field च्या बदलासारखे नव्हे तर व्यवसाय घटनेसारखे वाचले पाहिजे.

40
हलवा

लॉजिक entity वर हलवा

नियम service मधून कापा आणि entity वरच्या नव्या method मध्ये चिकटवा, state बदलण्याआधी invariant तपासत.

50
रक्षण करा

Constructor मध्ये validate करा

एखादे object अवैध स्थितीत तयारच होऊ शकणार नाही याची खात्री करा. शून्य line items असलेल्या Order ने error फेकावा, अस्तित्वात असू नये.

60
बंद करा

Fields private करा

Public setters काढून टाका. आता state बदलण्याचा एकमेव मार्ग नियम लागू करणाऱ्या methods मार्गे आहे. Encapsulation पुनर्स्थापित झाले.

70
पातळ करा

Service ला समन्वयकात आकुंचित करा

आता service entity load करतो, एक method बोलावतो आणि save करतो. तो persistence आणि transactions चे समन्वय साधतो, व्यवसाय नियम नाही.

80
काढा

Value objects बाहेर काढा

Money, Quantity किंवा Email सारख्या संकल्पना स्वतःच्या नियमांसह छोटे types बनतात, आणखी विखुरलेली validation जागच्या जागी आणतात.

90
Test करा

Mocks शिवाय वर्तन test करा

आता नियम साध्या objects वर राहत असल्याने, तुम्ही Order तयार करता आणि ship() error फेकते हे सिद्ध करता. कोणतेही repository किंवा gateway mock आवश्यक नाही.

100
राखा

DTOs जाणूनबुजून anemic ठेवा

Request bodies, event payloads आणि read models ही साधी records म्हणून ठेवा. तुम्ही वर्तन जिथे ते असायला हवे तिथे हलवले आहे, सर्वत्र नाही.

सामान्य अडचणी

अडचणी आणि anti-patterns

Anemic model क्वचितच जाणूनबुजून येते. ते framework defaults आणि काही वाजवी दिसणाऱ्या शॉर्टकट्समधून वाढते.

⚙️ Getter आणि setter ची प्रतिक्षिप्त क्रिया

प्रत्येक field साठी getter आणि setter आपोआप निर्माण करणे हा anemia कडे जाणारा सर्वात जलद मार्ग आहे. आधी वर्तन उघड करा, आणि बाह्य जगाला ज्यांची खरोखर गरज आहे तेवढेच accessors.

🏭 कधीच न आकुंचित होणारा service

प्रत्येक नियमासाठी नवे method वाढवणारा OrderService हे लक्षण आहे की नियमांना घर नाही. जर एखाद्या method चा गाभा मुख्यतः एका entity ची fields वाचणे आणि लिहिणे असेल, तर तो त्या entity वर असायला हवा.

🧬 ORM entities हेच domain

Persistence framework च्या row-mapped class ला तुमचे व्यवसाय मॉडेल बनू देणे तुम्हाला public fields आणि वर्तनहीनतेकडे ढकलते. एका वेगळ्या rich model कडे mapping करण्याचा विचार करा.

🔁 डुप्लिकेट invariants

तीच "ऋण होऊ शकत नाही" तपासणी तीन services मध्ये कॉपी केली की ती भरकटेल. ती एकदाच object वर हलवा जेणेकरून सत्याचा एकच स्रोत असेल.

🦴 अति-दुरुस्तीने god entity

असंबंधित लॉजिक आणि बाह्य कॉल्स एका entity मध्ये कोंबून anemia दुरुस्त करणे ही उलटी चूक आहे. Object शी संबंधित असलेले वर्तन ठेवा; समन्वय आणि I/O services मध्ये राहू द्या.

🧾 DTOs ना entities समजण्याचा गोंधळ

Transport object ला नियम जोडणे, किंवा rich entity ला transport object सारखे वागवणे सीमा अस्पष्ट करते. DTOs फक्त-डेटा आणि entities वर्तन-समृद्ध ठेवा, आणि त्यांच्यात mapping करा.

संकेत आणि मापदंड

संकेत आणि ते कसे मोजायचे

Anemia मोजता येते. हे संकेत तुम्हाला सांगतात की वर्तन डेटाबरोबर राहते की service layer मध्ये गळले आहे.

संकेततो तुम्हाला काय सांगतो
Entities वर method-ते-accessor गुणोत्तरजर entities जवळपास सर्व getters आणि setters असतील आणि कोणतीही domain methods नसतील, तर मॉडेल anemic आहे.
Public setter ची संख्याअनेक public setters म्हणजे invariants रक्षिली जाऊ शकत नाहीत; कोणताही caller आत पोहोचून state तोडू शकतो.
प्रति entity service ओळीज्या entity वर तो काम करतो त्याहून खूप मोठा service class वर्तन प्रत्यक्षात कुठे राहते ते दाखवतो.
डुप्लिकेट नियमांची घटनातीच validation अनेक services मध्ये दिसणे हे एका नियमाला एकही घर नसल्याचे सूचित करते.
नियम test करायला लागणारे mocksशुद्ध व्यवसाय नियम सिद्ध करायला repository आणि gateway mocks लागत असतील, तर नियम service मध्ये अडकला आहे.
कोडमध्ये पोहोचता येणाऱ्या अवैध स्थितीव्यवसाय जी स्थिती निषिद्ध करतो त्यात object किती मार्गांनी तयार किंवा बदलता येतो ते मोजा.
अंगठ्याचा नियम: जर तुम्ही एखाद्या class चे संपूर्ण काम "fields बाळगते आणि एका service ला ती बदलू देते" असे वर्णन करू शकत असाल, तर ते anemic आहे. निरोगी entity ला किमान एक असे method असते ज्याचे नाव domain तज्ज्ञ ओळखेल, आणि invariant तोडू शकेल असे एकही public setter नसते.
06 - उदाहरण अभ्यास

वास्तविक जगातील उदाहरण अभ्यास

तीन प्रातिनिधिक systems जिथे anemic विरुद्ध rich modeling चे खरे परिणाम झाले.

🛒

1 · जाडजूड OrderService असलेले ई-कॉमर्स checkout

Pattern: state transitions परत entity वर आणले

एका retail platform कडे फक्त accessors असलेला Order class आणि प्रत्येक transition नियम बाळगणारा कित्येक हजार ओळींचा OrderService होता.

  • एका bug ने payment पूर्ण होण्याआधी orders पाठवू दिले, कारण एका code path ने status थेट सेट केला आणि service तपासणी वगळली.
  • टीमने transition नियम Order वर pay(), ship() आणि cancel() म्हणून हलवले, प्रत्येक आपली precondition राखत.
  • Public setters काढून टाकले, म्हणून अवैध path compile होणे थांबले आणि तो पुन्हा घडू शकला नाही.
✅ परिणाम: "अशक्य" स्थिती bugs चा एक संपूर्ण वर्ग अप्रस्तुत झाला, आणि service एका method कॉलभोवती पातळ समन्वयकात आकुंचित झाला.
🏦

2 · services मध्ये पैशाचे गणित असलेले banking ledger

Pattern: value objects विखुरलेली validation शोषून घेतात

एका payments टीमने शिल्लक Account record वर कच्च्या integers म्हणून ठेवली, आणि rounding व currency तपासण्या transfer, fee आणि refund services मध्ये कॉपी केल्या.

  • प्रती rounding बाबत विसंगत होत्या, ज्यामुळे reconciliation दरम्यान एका-सेंटच्या फरकाच्या तफावती निर्माण झाल्या.
  • त्यांनी currency, rounding आणि अ-ऋणत्व बाळगणारे Money value object आणले, आणि पुरेसा निधी लागू करणारे rich Account.withdraw().
  • Services ने integers ला थेट स्पर्श करणे थांबवले आणि फक्त खात्याला पैसे हलवायला सांगितले.
✅ परिणाम: एका type ने पैशाचे नियम स्वतःकडे घेतल्यावर reconciliation तफावती नाहीशा झाल्या, आणि overdraft तपासण्या यापुढे विसरता येईनाशा झाल्या.
📅

3 · जाणूनबुजून API anemic ठेवणारी booking system

Pattern: rich entities, काठावर anemic transport

एका reservations platform कडे overlap आणि capacity नियम लागू करणाऱ्या rich Reservation entities होत्या, आणि HTTP सीमेवर जाणूनबुजून anemic request व response objects.

  • येणारी CreateBookingRequest objects ही वर्तनहीन साधी records होती, एका पातळ अनुवादकाद्वारे rich entities मध्ये मॅप केलेली.
  • सर्व availability आणि cancellation-window नियम Reservation वर राहिले, कोणत्याही infrastructure mocks शिवाय test केलेले.
  • एकही व्यवसाय नियमाला स्पर्श न करता wire format स्वतंत्रपणे उत्क्रांत होऊ शकला.
✅ परिणाम: टीमला दोन्ही फायदे मिळाले: बचावयोग्य domain गाभा आणि लवचिक API पृष्ठभाग, कारण त्यांनी anemic आणि rich प्रत्येक जिथे बसते तिथे निवडले.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Frameworks, functional शैली आणि typed भाषांनी चर्चा बदलली आहे, पण डेटा आणि वर्तन यांच्यातील मूलभूत ताण नेहमीप्रमाणेच जिवंत आहे.

🧱 Domain-driven design चे पुनरुज्जीवन

DDD ची aggregates हे anemia वरचे मुख्य प्रवाहातील उत्तर आहे: स्वतःच्या सुसंगतता सीमेचे रक्षण करणारी entity म्हणजे मूर्त झालेले rich model.

🧮 Functional core, imperative shell

Functional codebases शुद्ध लॉजिक I/O पासून वेगळे करतात. शुद्ध गाभा वर्तन बाळगतो, म्हणून नियम आणि डेटा एकाच module मध्ये ठेवून anemia टाळले जाते, एकाच class मध्ये नव्हे.

🔒 स्थिती अप्रस्तुत करणारे types

Sum types आणि branded types तुम्हाला "shipped order भरला गेला होता" हे type system मध्ये encode करू देतात, invariants runtime तपासणीहूनही आधी ढकलतात.

🧬 ORMs अजूनही anemia कडे ढकलतात

अनेक persistence frameworks default नुसार public-field entities बनवतात. Rich domain model ला persistence model पासून वेगळे करणे हा जिवंत design निर्णय राहतो.

📨 Events आणि CQRS काठावर anemia स्वीकारतात

Event payloads आणि read models जाणूनबुजून anemic असतात, तर write-side aggregate rich राहतो. Pattern प्रत्येक शैली कुठे बसते ते स्पष्ट करते.

🤖 Generated code दोन्ही वाढवतो

Scaffolding आणि AI-सहाय्यित कोड getter-आणि-setter entities वेगाने निर्माण करतात, म्हणून वर्तन objects वर हलवण्याची शिस्त अधिक महत्त्वाची ठरते, कमी नव्हे.

निष्कर्ष: anemic domain model म्हणजे "methods नसलेले classes नेहमी चुकीचे" असे नाही. ती एक आठवण आहे की domain entities वर्तन बाळगून आणि आपली invariants राखून आपली किंमत वसूल करतात. नियम त्या objects वर ठेवा जे डेटा बाळगतात, आणि तुमचे transport आकार साधे ठेवा - प्रत्येक जाणीवपूर्वक निवडा.
