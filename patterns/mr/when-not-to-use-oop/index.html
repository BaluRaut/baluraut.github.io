OOP संकल्पना

OOP कधी वापरू नये - आणि त्याऐवजी काय निवडावे

जेव्हा तुमच्याकडे identity, mutable state, आणि data सोबत प्रवास करणारे behavior असते, तेव्हाच objects आपली किंमत वसूल करतात. पण खरा कोड बराचसा फक्त data आत, data बाहेर इतकाच असतो: एखादे ETL transform, pricing गणित, एकदाच चालणारे migration script. त्यांना classes मध्ये गुंडाळल्याने नुसता सोपस्कार वाढतो, त्यातून काहीच मिळत नाही. procedural, functional किंवा data-oriented कोड कधी अधिक स्पष्ट पर्याय ठरतो हे ओळखणे, आणि हट्ट न धरता paradigms कसे मिसळायचे, हा या पानाचा विषय आहे.

01 - काय

"OOP नको" म्हणजे नेमके काय

हे OOP-विरोधी नाही. समस्येच्या आकाराला योग्य ते साधन जुळवण्याबद्दल आहे. OOP हे state आणि behavior एका interface मागे बांधून ठेवते, जेणेकरून objects कालांतराने एकत्र काम करू शकतात. जेव्हा तुमच्या समस्येत दीर्घकाळ टिकणारे state नसते आणि रक्षण करण्यासारखी identity नसते, तेव्हा हे बांधणे नुसते ओझे बनते: constructors, dependency जोडणी, mocks, आणि तुम्हाला नको असणारे lifecycle. त्याचे पर्याय म्हणजे procedural कोड, functional pipelines, आणि data-oriented design, जे साधे data आणि त्यावरील functions वेगळे ठेवते.

🔁 Stateless transforms

rows आत घेऊन rows बाहेर देणारे ETL step दोन calls मध्ये कोणतेही state ठेवत नाही. एक pure function ही प्रामाणिक signature आहे; एकाच run() method असलेला class म्हणजे वेषभूषा घातलेली function आहे.

🧮 Pure गणिते

Pricing, tax, discounts, आणि currency गणित deterministic असते: सारखे inputs, सारखे output. Functions सहज compose होतात आणि सहज test होतात. Objects एक lifecycle जोडतात जे pure गणिताने कधी मागितलेच नाही.

📜 छोटे scripts

एकदा चालून बंद होणारे backfill किंवा CSV साफसफाई करणारे script याला class hierarchy लागत नाही. एका नजरेत वाचता येईल असा वरून खालपर्यंतचा procedural कोड हीच योग्य तेवढी रचना आहे.

OOP कुठे बसते आणि कुठे बसत नाही

02 - का

OOP जबरदस्तीने लादल्याने त्रास का होतो

हट्टी OOP साध्या data प्रवाहाचे रूपांतर सहकाऱ्यांच्या एका जाळ्यात करते, ज्यांना तुम्हाला बांधावे, inject करावे आणि mock करावे लागते. हा सोपस्कार खरे गणन झाकून टाकतो आणि पुढच्या प्रत्येक वाचकाला मंदावतो.

🎭 आशयाऐवजी सोपस्कार

तीन ओळींचे transform एका constructor, private field, आणि process() method असलेला class बनते. वाचकांना आता एक map शोधण्यासाठी boilerplate चाळावे लागते. signal-to-noise गुणोत्तर घसरते.

🧪 अवघड testing

Pure functions ला फक्त inputs आणि तपासलेले outputs लागतात. तेच logic test करण्यासाठी object graph ला बांधलेली dependencies, mocks, आणि stubs लागतात. तुम्ही behavior ऐवजी जोडणी test करता.

🕳️ लपलेले mutation

Objects mutable fields ला आमंत्रण देतात. जिथे immutable stages ची स्वच्छ मालिका असावी अशा data pipeline मध्ये, लपलेले state order वर अवलंबून असणारे bugs निर्माण करते, जे पुन्हा घडवणे त्रासदायक असते.

🧩 पोकळ कवचे

फक्त fields get आणि set करणाऱ्या classes मध्ये data-only records गुंडाळल्याने anemic domain model तयार होते: objects चा सगळा सोपस्कार, पण त्यांना न्याय्य ठरवणारे कोणतेही behavior नाही.

सोप्या शब्दांत

उपमांसह समजावून सांगितलेले OOP कधी वापरू नये

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ते पटकन कळेल.

🎓 विद्यार्थ्यासाठी

कागदाच्या चिटोऱ्यावर दोन आकडे बेरीज करण्यासाठी तुम्ही कपाट बनवत नाही. pricing formula म्हणजे कागदाची चिटोरी आहे. Objects म्हणजे कपाट: जेव्हा तुम्ही अनेक गोष्टी कालांतराने साठवता आणि सांभाळता तेव्हा फायद्याचे, पण एका बेरजेसाठी वाया घालवणे.

👩‍💻 developer साठी

ETL stage म्हणजे एक Unix pipe: read | clean | enrich | write. प्रत्येक stage एक stream घेते आणि एक परत करते. फक्त ओळी filter करण्यासाठी तुम्ही grep ला lifecycle असलेल्या stateful object मध्ये बदलणार नाही.

🏢 व्यावसायिकासाठी

कर फॉर्म भरणे ही एक कृती आहे: ठराविक inputs, ठराविक नियम, एक आकडा बाहेर. एक return मोजण्यासाठी तुम्ही कायमस्वरूपी विभाग नेमत नाही. चालू व्यवसायासाठी संघटनेचा तक्ता (objects आणि भूमिका) राखून ठेवा, एकदाच्या गणनेसाठी नाही.

🍳 रोजच्या भाषेत

टोस्ट बनवायला तुम्ही काही पायऱ्या पाळता, Bread repository सांभाळणारा Toast Manager नेमत नाही. साध्या सरळ कामांना कृती हवी असते, विभाग आणि सोपवासोपवी असलेली संघटना नव्हे.

03 - कसे

अति-objects बनवलेली परिस्थिती कशी ओळखावी आणि refactor करावी

खूण अशी: कोणतेही अर्थपूर्ण state नसलेला, एकच public method असलेला, आणि -er किंवा -Manager ने संपणारे नाव असलेला class. ही एक अशी function आहे जिला constructor फुटला. उपाय म्हणजे ती एका pure function मध्ये किंवा त्यांच्या छोट्या pipeline मध्ये आकुंचित करणे.

🔎 दुर्गंध ओळखा

ज्या classes चे एकमेव field म्हणजे inject केलेले config आहे आणि एकमेव method म्हणजे run, process किंवा calculate आहे, त्या शोधा. ते एक stateless गणन आहे. त्याला function व्हायचे आहे, हवे तर आपल्या config सह curry केलेली.

🧵 stages compose करा

ETL प्रवाहाला immutable data पास करणाऱ्या छोट्या pure functions ची मालिका म्हणून model करा. प्रत्येक stage स्वतंत्रपणे testable, पुन्हा क्रमवारी लावता येणारे, आणि पुनर्वापर करता येणारे असते, batch धरून ठेवणारे कोणतेही shared mutable object नसते.

// OVER-OBJECTED: four classes to compute one price.
class TaxService {
  apply(cents: number, region: string): number {
    const rate = region === "EU" ? 0.20 : 0.0725;
    return Math.round(cents * (1 + rate));
  }
}
class DiscountEngine {
  apply(cents: number, coupon?: string): number {
    return coupon === "SAVE10" ? Math.round(cents * 0.9) : cents;
  }
}
class PriceCalculator {
  constructor(private tax: TaxService, private discounts: DiscountEngine) {}
  calculate(order: { subtotalCents: number; region: string; coupon?: string }): number {
    const discounted = this.discounts.apply(order.subtotalCents, order.coupon);
    return this.tax.apply(discounted, order.region);
  }
}
const calc = new PriceCalculator(new TaxService(), new DiscountEngine());
calc.calculate({ subtotalCents: 5000, region: "EU", coupon: "SAVE10" }); // 5400

const applyDiscount = (cents: number, coupon?: string): number =>
  coupon === "SAVE10" ? Math.round(cents * 0.9) : cents;

const applyTax = (cents: number, region: string): number => {
  const rate = region === "EU" ? 0.20 : 0.0725;
  return Math.round(cents * (1 + rate));
};

const priceOrder = (o: Order): number =>
  applyTax(applyDiscount(o.subtotalCents, o.coupon), o.region);

दोन्ही आवृत्त्या तेच 5400 cents मोजतात. functional आवृत्ती constructors, inject केलेली fields, आणि object graph test करण्यासाठी लागणारे mocks टाकून देते. उरते ते नेमके गणित, composition म्हणून व्यक्त केलेले. हेच data-oriented design आहे: साधे data pure functions मधून वाहते, आणि calls मध्ये कोणतेही state लपत नाही.

ETL pipeline stateful engine नव्हे तर composed stages म्हणून

// A transform pipeline: each stage is data-in, data-out. No engine object.
type Row = { email: string; amount: string; region: string };
type Clean = { email: string; cents: number; region: string };

const parse = (rows: Row[]): Clean[] =>
  rows.map(r => ({
    email: r.email.trim().toLowerCase(),
    cents: Math.round(parseFloat(r.amount) * 100),
    region: r.region.toUpperCase(),
  }));

const dropInvalid = (rows: Clean[]): Clean[] =>
  rows.filter(r => r.email.includes("@") && r.cents > 0);

const totalsByRegion = (rows: Clean[]): Record<string, number> =>
  rows.reduce((acc, r) => ({ ...acc, [r.region]: (acc[r.region] ?? 0) + r.cents }), {} as Record<string, number>);

// Compose the whole pipeline as a single expression.
const run = (rows: Row[]) => totalsByRegion(dropInvalid(parse(rows)));

def parse(rows):
    return [
        {
            "email": r["email"].strip().lower(),
            "cents": round(float(r["amount"]) * 100),
            "region": r["region"].upper(),
        }
        for r in rows
    ]

def drop_invalid(rows):
    return [r for r in rows if "@" in r["email"] and r["cents"] > 0]

def totals_by_region(rows):
    acc = {}
    for r in rows:
        acc[r["region"]] = acc.get(r["region"], 0) + r["cents"]
    return acc

# Compose the whole pipeline as a single expression.
def run(rows):

def parse(rows)
  rows.map do |r|
    {
      email: r[:email].strip.downcase,
      cents: (r[:amount].to_f * 100).round,
      region: r[:region].upcase,
    }
  end
end

def drop_invalid(rows)
  rows.select { |r| r[:email].include?("@") && r[:cents] > 0 }
end

def totals_by_region(rows)
  rows.each_with_object(Hash.new(0)) { |r, acc| acc[r[:region]] += r[:cents] }
end

# Compose the whole pipeline with method chaining.
def run(rows)
  totals_by_region(drop_invalid(parse(rows)))
end

येथे काहीही lifecycle असलेले object नाही. प्रत्येक stage एक pure transformation आहे, जी तुम्ही वेगळेपणाने unit-test करू शकता, पुन्हा क्रमवारी लावू शकता, किंवा दुसऱ्या pipeline मध्ये पुनर्वापर करू शकता. एक stage जोडणे म्हणजे एक function जोडणे, stateful engine संपादित करून त्याचे invariants पुन्हा तपासणे नव्हे.

कोडाच्या प्रत्येक एककासाठी paradigm निवडण्याची निर्णय प्रक्रिया, पहिल्या नजरेपासून ते सांभाळण्यायोग्य निकालापर्यंत.

00
मांडणी

एककाचे वर्णन एका वाक्यात करा

ते काय करते ते मोठ्याने सांगा: "order मधून total मोजते", "CSV साफ करते". input पासून output पर्यंतचे pure वाक्य function कडे झुकणारा भक्कम इशारा आहे.

10
State

विचारा: दीर्घकाळ टिकणारे state आहे का?

calls मध्ये काही टिकून राहून बदलण्याची गरज आहे का? cart, account, connection pool. जर काहीच टिकत नसेल, तर बहुधा तुम्हाला object लागणार नाही.

20
Identity

विचारा: रक्षण करण्यासारखी identity आहे का?

सारख्या वस्तू असलेल्या दोन carts तरीही वेगळ्या carts आहेत. जर instances ला identity आणि invariants असतील, तर objects बसतात. जर तुमचे data फक्त values असेल, तर records आणि functions निवडा.

30
प्रकार

विचारा: तुम्हाला polymorphism लागते का?

एका interface मागे अनेक अदलाबदल करता येणारे providers classes ला न्याय्य ठरवतात. कोणतेही प्रकार नसलेली एकच ठराविक गणना नाही; function पुरेशी आहे.

40
आयुष्य

script विरुद्ध service ची तुलना करा

चालून बंद होणाऱ्या एकदाच्या backfill ला वरून खालपर्यंतचा procedural कोड हवा. sessions असलेली दीर्घकाळ चालणारी service म्हणजे तिथे object lifecycles फायदेशीर ठरतात.

50
Data आकार

आधी साधे data model करा

वाहणारे records परिभाषित करा: rows, orders, line items. कोणते behavior, असल्यास, जोडायचे हे ठरवण्याआधी त्यांना साधी immutable values म्हणून ठेवा.

60
Functions लिहा

गाभा pure functions म्हणून व्यक्त करा

प्रत्येक transform ला side effects नसलेली function बनवा. Deterministic गणित आणि पुनर्रचना इथे येतात, I/O पासून वेगळे.

70
Compose

stages ला pipeline मध्ये जोडा

functions ला एका प्रवाहात compose करा. प्रत्येक stage एकटी testable असते आणि संपूर्ण गोष्ट एक मालिका म्हणून वाचली जाते, सहकाऱ्यांचे जाळे म्हणून नव्हे.

80
सीमा

objects ला कडेला ढकला

जिथे तुम्हाला खरोखर state लागते, एक repository, session, stateful client, ते सीमेवर ठेवा आणि त्याला pure गाभ्याला call करू द्या.

90
Test

inputs आणि outputs थेट तपासा

Pure functions mocks शिवाय test होतात: data द्या, निकाल तपासा. जास्त वजनदार integration tests पातळ stateful कडांसाठी राखून ठेवा.

100
आढावा

सोपस्कार काढून टाका

जर एका class ला एकच method आणि खरे state नसेल, तर तिला function मध्ये आकुंचित करा. फक्त जिथे identity, state किंवा polymorphism ने न्याय्य ठरवले तिथेच objects ठेवा.

सामान्य अडचणी

अडचणी आणि anti-patterns

अपयशाच्या पद्धती दोन्ही बाजूंनी असतात: जिथे functions बसतात तिथे objects लादणे, आणि इतक्या जोरात दुसऱ्या टोकाला झुकणे की objects जी रचना योग्यरित्या पुरवतात ती तुम्ही गमावता.

🏭 -er class

कोणतेही state नसलेला आणि एकच method असलेला Manager, Processor, किंवा Handler म्हणजे वेषांतरातील function. काहीही encapsulate न करता तो constructors आणि mocks वाढवतो.

💉 Injection चा तमाशा

stateless helpers ला DI container मधून जोडणे जेणेकरून तुम्ही pure गणित mock करू शकाल. जर dependency ला कोणतेही side effects नसतील, तर तुम्ही तिला थेट call करू शकता; container म्हणजे निव्वळ ओझे.

🩻 Anemic domain model

फक्त data वरील getters आणि setters असलेले classes. तुम्ही object कर भरला पण कोणतेही behavior मिळाले नाही. एकतर खरे invariants जोडा किंवा साधे record वापरा.

🌀 Stateful pipeline engine

mutable fields मध्ये batch जमा करणारे ETL "engine" object order वर अवलंबून असणारे bugs निर्माण करते. pure stages मधून immutable data संपूर्ण दोषवर्गच टाळते.

🔨 spaghetti कडे अति-सुधारणा

सर्वत्र objects नाकारल्याने global state वाटून घेणाऱ्या free functions चा ढीग तयार होतो. functional म्हणजे रचनाहीन नव्हे; module नुसार गट करा आणि data immutable ठेवा.

🧬 गणनेसाठी खोल hierarchies

एक formula बदलण्यासाठी subclassing करणे एक वर्गीकरण inheritance मध्ये भाजून टाकते. strategy किंवा lookup table घेणारी function ठिसूळ base class शिवाय लवचिक राहते.

संकेत आणि मापके

संकेत आणि कसे मोजावे

हे जाणवण्यासाठी तुम्हाला क्वचितच एखादे औपचारिक मापक लागते, पण हे संकेत निर्णय ठोस आणि तपासण्याजोगा बनवतात.

संकेततो तुम्हाला काय सांगतो
प्रत्येक class मधील fieldsशून्य खरे state (फक्त inject केलेले config) म्हणजे class हे object च्या वेषातील stateless गणन आहे. त्याला function मध्ये आकुंचित करा.
प्रत्येक class मधील public methodsrun किंवा calculate नावाची नेमकी एकच public method म्हणजे "ही एक function आहे" हा भक्कम संकेत.
प्रत्येक unit test मधील mocksसाधे logic test करण्यासाठी अनेक mocks लागणे म्हणजे तुम्ही behavior नव्हे तर जोडणी test करत आहात. Pure functions ला एकही लागत नाही.
transforms मधील mutationdata pipeline मध्ये जागच्या जागी mutation order वर अवलंबून असणाऱ्या bugs ची भविष्यवाणी करते. pure stages मधून immutable data अधिक सुरक्षित असते.
constructor-ते-logic गुणोत्तरकाम करण्यापेक्षा dependencies जोडण्यात जास्त ओळी म्हणजे function मिटवून टाकेल असा सोपस्कार दर्शवते.
Instance चे आयुष्यएकाच call मध्ये तयार होऊन टाकून दिलेल्या objects ला न्याय्य ठरवणारे lifecycle नाही. function ला तेच आयुष्य प्रामाणिकपणे असते.
ढोबळ नियम: जर एका class ला अर्थपूर्ण state नसेल, एकच public method असेल, आणि स्वतःचे logic test करण्यासाठी mocks लागत असतील, तर ती एक function असावी. identity, invariants, आणि polymorphism साठी objects ठेवा; stateless transforms आणि pure गणितासाठी functions वापरा.
06 - उदाहरणे

प्रत्यक्ष जगातील उदाहरणे

तीन production-सदृश परिस्थिती जिथे OOP सोडून किंवा मर्यादित करून system अधिक स्पष्ट आणि सुरक्षित बनली.

🧾

1 · Billing engine pure functions म्हणून पुन्हा बांधले

क्षेत्र: subscriptions आणि invoicing

एका subscriptions संघाकडे proration, tax, आणि discount logic service objects च्या जाळ्यात पसरलेले होते, जे test करणे आणि समजणे अवघड होते.

  • immutable invoice data वरील pure functions मध्ये गणित काढून घेतले, I/O कडेला एका पातळ repository मध्ये ठेवले.
  • डझनभर mock-भरलेल्या tests च्या जागी leap-year proration सारख्या edge cases व्यापणारी साधी input-output तपासणी आणली.
  • Subscription aggregate object म्हणूनच ठेवले कारण त्याला खरे state आणि रक्षण करण्यायोग्य lifecycle नियम आहेत.
✅ परिणाम: pricing गाभा deterministic आणि सहज testable बनला, तर objects नेमके तिथेच राहिले जिथे identity आणि invariants ने त्यांना न्याय्य ठरवले.
🔀

2 · ETL pipeline composed stages म्हणून

क्षेत्र: data ingestion आणि reporting

एका reporting pipeline ने mutable fields मध्ये rows जमा करणारे stateful "processor" object वापरले, ज्यातून अधूनमधून येणारे, order वर अवलंबून असणारे totals निर्माण झाले.

  • प्रत्येक step, parse, validate, enrich, aggregate, immutable batches पुढे पाठवणारी pure function म्हणून पुन्हा लिहिले.
  • stages ला एका प्रवाहात compose केले जेणेकरून नवीन enrichment म्हणजे जोडलेली function, shared mutable state चे संपादन नव्हे.
  • tests साठी stages वेगळेपणाने चालवल्या आणि त्यातील दोन दुसऱ्या pipeline मध्ये न बदलता पुनर्वापर केल्या.
✅ परिणाम: order वर अवलंबून असणारे bugs नाहीसे झाले, आणि stages जोडणे किंवा पुन्हा क्रमवारी लावणे कमी जोखमीचा, स्थानिक बदल बनला.
📜

3 · एकदाच चालणारे data migration script

क्षेत्र: schema migration आणि backfill

एका अभियंत्याने एकदा चालून हटवल्या जाणाऱ्या migration साठी class hierarchy, readers, mappers, writers, बांधायला सुरुवात केली.

  • hierarchy च्या जागी वरून खालपर्यंतचे procedural script आणले, जे स्पष्ट टप्प्यांत वाचते, map करते आणि लिहिते.
  • abstraction थर ऐवजी dry-run flag आणि idempotent upserts ने अचूकतेचे रक्षण केले.
  • script एका नजरेत वाचता येईल असे ठेवले जेणेकरून समीक्षक indirection चा मागोवा न घेता backfill पडताळू शकतील.
✅ परिणाम: migration खूप कमी वेळात पूर्ण झाले, समीक्षा करणे सोपे होते, आणि चालल्यानंतर सुरक्षितपणे हटवले गेले, सांभाळण्यासाठी कोणतेही framework नाही.
07 - सुसंगती

आधुनिक सुसंगती

मुख्य प्रवाहातील भाषांमध्ये functional आणि data-oriented वैशिष्ट्ये वाढली आहेत, ज्यामुळे "प्रत्येक गोष्ट object नाही" ही किनारी भूमिका न राहता व्यवहार्य default बनली आहे.

🧊 Records आणि value types

आधुनिक TypeScript मधील immutable records, Python dataclasses, आणि Ruby Data तुम्हाला पूर्ण classes च्या सोपस्काराशिवाय साधे data देतात, नेमका तोच आकार जो pipelines ला हवा असतो.

🧵 Pattern matching

Python, Ruby, आणि TS-लगतच्या साधनांमधील structural matching तुम्हाला प्रत्येक प्रकारासाठी polymorphic class hierarchy न लागता data च्या आकारावर branch करू देते.

🚿 Data-oriented design

साधे data त्यावरील functions पासून वेगळे केल्याने cache वर्तन आणि स्पष्टता सुधारते, हे तत्त्व आता game engines पलीकडे बरेच सामान्य आहे.

⚙️ Functional cores

"functional core, imperative shell" शैली ही मुख्य प्रवाहातील architecture आहे: आत pure logic, सीमेवर side effects.

🔗 Composable pipelines

Stream आणि iterator abstractions composed stateless stages ला रूढ बनवतात, त्यामुळे ETL आणि transforms ला क्वचितच खास engine object लागते.

🤝 व्यवहार्य polyglot कोड

संघ माफी न मागता प्रत्येक module नुसार paradigms मिसळतात: stateful aggregates साठी objects, गणित आणि transforms साठी functions, जुळणीनुसार निवडलेले.

सारांश: OOP हे एक साधन आहे, सर्व कोडाचे default आवरण नव्हे. जेव्हा तुमच्याकडे रक्षण करण्यासारखी identity, state, आणि invariants असतील तेव्हा objects निवडा; stateless transforms, pure गणिते, आणि छोट्या scripts साठी functions आणि data-oriented design निवडा. वरिष्ठ पाऊल म्हणजे paradigms जाणीवपूर्वक मिसळणे, सर्वत्र एकच लादणे नव्हे.
