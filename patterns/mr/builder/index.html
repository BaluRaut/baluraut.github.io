Creational पॅटर्न

Builder पॅटर्न - गुंतागुंतीच्या ऑब्जेक्ट्सची टप्प्याटप्प्याने रचना

काही ऑब्जेक्ट्सना अनेक भाग योग्य क्रमाने जोडावे लागतात, आणि दहा आर्ग्युमेंट्स असलेला constructor हा एक सापळा असतो. Builder पॅटर्न ऑब्जेक्ट कसा तयार होतो हे तो शेवटी काय आहे यापासून वेगळे करतो: तुम्ही एका छोट्या, वाचनीय API द्वारे एका वेळी एक call करून fields सेट करता, आणि मग तयार झालेले, बहुधा immutable असे उत्पादन मागता. ऐच्छिक Director हा एक पुनर्वापर करता येणारा कृतीक्रम पकडून ठेवतो, जेणेकरून तेच टप्पे वेगवेगळी रूपे तयार करू शकतात.

01 - काय

Builder पॅटर्न म्हणजे काय?

Builder हा एक creational पॅटर्न आहे जो तुम्हाला एका मोठ्या constructor call ऐवजी गुंतागुंतीचा ऑब्जेक्ट हळूहळू तयार करू देतो. तुम्ही छोट्या टप्प्यांच्या क्रमाद्वारे ऑब्जेक्ट कॉन्फिगर करता, आणि मग शेवटचा build() टप्पा तयार झालेले उत्पादन परत देतो. रचनेचे तर्क उत्पादनाच्या बाहेर राहत असल्यामुळे, तीच रचना-प्रक्रिया वेगवेगळी रूपे तयार करू शकते, आणि उत्पादन स्वतःच शेवटी validate करून freeze करता येते.

🧱 टप्प्याटप्प्याने जुळणी

प्रत्येक भाग त्याच्या स्वतःच्या नावाच्या call ने सेट होतो, त्यामुळे अर्धवट कॉन्फिगर केलेला ऑब्जेक्ट कधीही बाहेर पडत नाही. क्रम आणि defaults हे builder च्या आत हाताळले जातात.

🔗 Fluent interface

प्रत्येक setter builder परत करतो, त्यामुळे calls एका वाचनीय अभिव्यक्तीमध्ये साखळीसारखे जोडले जातात, जे ऑब्जेक्टच्या वर्णनासारखे वाचले जाते.

🧊 Immutable उत्पादन

build() चालण्यापूर्वी सर्व fields गोळा केली जातात, त्यामुळे अंतिम ऑब्जेक्ट एकदाच तयार करून, validate करून, read-only बनवता येतो.

02 - का

Builder पॅटर्न का अस्तित्वात आहे

हा पॅटर्न telescoping constructor संपवण्यासाठी जन्माला आला: तो anti-pattern जिथे एक class constructor मागून constructor वाढत जाते, प्रत्येक एक अधिक parameter जोडतो, जोपर्यंत call sites हे positional arguments च्या अवाचनीय भिंती बनत नाहीत.

🪜 telescoping constructors संपवतो

new Pizza(12, true, false, true, null, 2) ऐवजी, तुम्ही प्रत्येक निवडीला नाव देता. कोणता boolean कोणता आहे हे ओळखण्यासाठी commas मोजण्याची गरज उरत नाही.

📖 call site वर वाचनीय

साखळीत जोडलेले, नाव दिलेले टप्पे गद्यासारखे वाचले जातात. एक reviewer .size(12).cheese(true) पाहतो आणि class न उघडता हेतू समजतो.

🧊 सुरक्षित immutability शक्य करतो

ऐच्छिक fields मुटेबल builder वर सेट होतात, उत्पादनावर नाही. उत्पादनाला प्रत्येक मूल्य एकाच वेळी मिळते आणि ते final व thread-safe बनू शकते.

♻️ प्रक्रिया परिणामापासून वेगळी करतो

ऑब्जेक्ट जुळवण्याचे टप्पे त्याच्या concrete class पासून decouple केले जातात, त्यामुळे एकच कृतीक्रम अनेक प्रकार किंवा output स्वरूपे तयार करू शकतो.

सोप्या भाषेत

उपमांसह Builder समजावून

तीच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असलात तरी ती डोक्यात बसते.

🎓 विद्यार्थ्यासाठी

हे lab report फॉर्म भरण्यासारखे आहे. तुम्हाला हव्या असलेल्या fields कोणत्याही क्रमाने भरता, बाकीच्या त्यांच्या defaults वर सोडता, आणि तुम्ही तो जमा केल्यावरच तो एक अंतिम, तपासलेला दस्तावेज बनतो जो तुम्ही संपादित करू शकत नाही.

👩‍💻 डेव्हलपरसाठी

query methods साखळीत जोडण्याचा विचार करा: query().where(x).orderBy(y).limit(10). प्रत्येक call एक plan सुधारते आणि तो plan परत करते, आणि फक्त build() किंवा run() तो खऱ्या गोष्टीत रूपांतरित करते.

🏢 व्यावसायिकासाठी

हे sandwich counter वर सानुकूल ऑर्डर आहे. तुम्ही एकेक करून घटक सांगता; कामगार (builder) ते योग्य क्रमाने जुळवतो, आणि तुम्हाला एक तयार sandwich मिळते, भागांचा ढीग नाही.

🏠 रोजच्या जीवनातील आवृत्ती

फर्निचर flat-pack सूचनांसह बांधकाम: सूचना पत्रक (Director) सांगते की कोणते पॅनल कोणत्या क्रमाने जोडायचे, तर तेच पॅनल (भाग) एक desk किंवा एक shelf बनवू शकतात.

03 - कसे

ते आतून कसे काम करते

Builder मुटेबल, अंशतः सेट केलेली state धरून ठेवतो. Step methods ती state बदलतात आणि builder परत करतात जेणेकरून calls साखळीत जोडतात. शेवटचा build() सर्व काही validate करतो आणि एक immutable उत्पादन तयार करतो. एक ऐच्छिक Director टप्प्यांचा एक निश्चित क्रम एक नावाचा कृतीक्रम म्हणून गुंडाळतो.

🔧 builder state गोळा करतो

Fields defaults पासून सुरू होतात. प्रत्येक fluent step एक field overwrite करतो आणि this परत करतो. अजून काहीही validate होत नाही, त्यामुळे caller ला क्रमाचा फरक पडत नाही.

🎬 Director कृतीक्रम चालवतो

जेव्हा अनेक उत्पादने तोच रचना-क्रम सामायिक करतात, तेव्हा Director builder टप्पे एका निश्चित क्रमाने call करतो, जेणेकरून callers तो कृतीक्रम पुन्हा लिहिण्याऐवजी पुनर्वापर करतात.

Java मधील एक वास्तववादी fluent builder

public final class HttpRequest {
    private final String method;
    private final String url;
    private final Map<String, String> headers;
    private final String body;

    // Private: the only way in is through the Builder.
    private HttpRequest(Builder b) {
        this.method  = b.method;
        this.url     = b.url;
        this.headers = Map.copyOf(b.headers); // defensive, immutable copy
        this.body    = b.body;
    }

    public String method()  { return method; }
    public String url()     { return url; }
    public Map<String, String> headers() { return headers; }

    public static Builder to(String url) {
        return new Builder(url);
    }

    // Static nested Builder holds the mutable, half-built state.
    public static final class Builder {
        private String method = "GET";              // sensible default
        private final String url;                   // required
        private final Map<String, String> headers = new LinkedHashMap<>();
        private String body = null;                 // optional

        private Builder(String url) {
            if (url == null || url.isBlank())
                throw new IllegalArgumentException("url is required");
            this.url = url;
        }

        public Builder method(String m) { this.method = m; return this; }
        public Builder header(String k, String v) { headers.put(k, v); return this; }
        public Builder body(String b) { this.body = b; return this; }

        public HttpRequest build() {
            // Central place to validate cross-field invariants.
            if (body != null && method.equals("GET"))
                throw new IllegalStateException("GET cannot have a body");
            return new HttpRequest(this);
        }
    }
}

// Call site reads like a description of the request:
HttpRequest req = HttpRequest.to("https://api.example.com/orders")
        .method("POST")
        .header("Content-Type", "application/json")
        .header("Authorization", "Bearer " + token)
        .body("{\"item\":\"book\"}")
        .build();

लक्षात घ्या की उत्पादनाचा constructor private आहे आणि तो builder स्वतःच घेतो. build() ऑब्जेक्ट validate करून freeze करण्यापूर्वी प्रत्येक field सेट केलेली असते, त्यामुळे एक HttpRequest कधीही अर्धवट कॉन्फिगर केलेल्या किंवा मुटेबल स्थितीत असू शकत नाही.

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

खूप जास्त constructor parameters असलेल्या class पासून, fluent builder द्वारे जुळवलेल्या स्वच्छ, immutable उत्पादनापर्यंत.

00
वास

telescoping constructor ओळखा

तुमच्या लक्षात येते की एका class ला अनेक overloaded constructors आहेत, किंवा एक असा जो अनेक positional आणि ऐच्छिक parameters घेतो. Call sites अवाचनीय आणि चुकांना प्रवण असतात.

10
Product

उत्पादनाची fields final करा

उत्पादन immutable असावे असे ठरवा. प्रत्येक field final म्हणून चिन्हांकित करा आणि त्या सर्व एका private constructor मध्ये अगदी एकदाच सेट करण्याची योजना करा.

20
Builder

nested Builder class तयार करा

एक static nested Builder जोडा जो उत्पादनाच्या fields ला मुटेबल state म्हणून प्रतिबिंबित करतो, ऐच्छिक मूल्यांसाठी समजूतदार defaults सह भरलेला.

30
आवश्यक

आवश्यक fields आधीच घ्या

अनिवार्य मूल्ये builder च्या constructor मध्ये किंवा एका static entry point मध्ये पास करा, जेणेकरून एक builder कधीही अवैध स्थितीत सुरू होऊ शकत नाही.

40
टप्पे

fluent step methods जोडा

प्रत्येक ऐच्छिक field साठी, एक नावाचा setter जोडा जो मूल्य नियुक्त करतो आणि return this करतो, ज्यामुळे साखळीत जोडलेले calls शक्य होतात.

50
गोपनीयता

उत्पादनाचा constructor बंद करा

उत्पादनाचा constructor private करा आणि तो builder स्वीकारेल असे करा, जेणेकरून builder हा ऑब्जेक्ट तयार करण्याचा एकमेव, नियंत्रित मार्ग बनतो.

60
Validate

build() मध्ये invariants लागू करा

build() मध्ये, रचना करण्यापूर्वी cross-field नियम आणि आवश्यक मूल्ये तपासा. तुटलेला ऑब्जेक्ट पाठवण्याऐवजी इथे मोठ्याने अपयशी व्हा.

70
Freeze

collections कॉपी करून freeze करा

मुटेबल inputs (lists, maps) constructor च्या आत immutable मध्ये संरक्षणात्मकपणे कॉपी करा जेणेकरून बाहेरील references नंतर उत्पादन बदलू शकत नाहीत.

80
Director

सामायिक कृतीक्रम काढा (ऐच्छिक)

जर अनेक call sites टप्प्यांचा तोच क्रम पुन्हा करत असतील, तर त्यांना एका Director method मध्ये गुंडाळा जेणेकरून तो कृतीक्रम एकाच ठिकाणी राहतो.

90
वापर

call site वर build करा

Callers त्यांना हवे असलेले टप्पे साखळीत जोडतात आणि build() ने समाप्त करतात, एक पूर्णपणे तयार, immutable उत्पादन परत मिळवतात.

100
विकसित

callers न मोडता fields जोडा

नवीन ऐच्छिक fields defaults सह नवीन fluent methods बनतात. अस्तित्वात असलेली call sites compile होत राहतात, त्यामुळे API उलथापालथ न होता वाढते.

सामान्य धोके

धोके आणि anti-patterns

खरोखरच गुंतागुंतीच्या ऑब्जेक्ट्ससाठी Builder फायदेशीर ठरतो. तो खूप लवकर वापरा, किंवा निष्काळजीपणे अंमलात आणा, आणि तो केवळ औपचारिकता बनतो.

🪶 क्षुल्लक ऑब्जेक्ट्ससाठी Builder

दोन fields असलेल्या value type ला builder मध्ये गुंडाळल्याने काहीही फायदा न होता boilerplate वाढतो. जेव्हा थोड्या, सर्व आवश्यक fields असतात तेव्हा साधा constructor किंवा record अधिक स्पष्ट असतो.

🕳️ validate करायला विसरणे

जर build() invariant तपासण्या वगळत असेल, तर builder फक्त समस्या दुसरीकडे हलवतो. अवैध संयोजन नाकारण्यासाठी एक केंद्रीय जागा हाच संपूर्ण उद्देश आहे.

🔓 मुटेबल references गळती

caller ची list किंवा map थेट, संरक्षणात्मक कॉपीशिवाय साठवल्याने, बाहेरील कोड कथितरित्या immutable असलेले उत्पादन तयार झाल्यानंतर बदलू शकतो.

🔁 गलिच्छ builder पुन्हा वापरणे

एका builder वरून दोनदा build() call करून स्वतंत्र ऑब्जेक्ट्सची अपेक्षा करणे लोकांना आश्चर्यचकित करते जर state पुढे नेली गेली तर. पुनर्वापर document करा, किंवा प्रत्येक वेळी नवीन builder परत करा.

🧩 आवश्यक-field लागू न करणे

प्रत्येक field ला ऐच्छिक fluent step बनवल्याने callers अनिवार्य fields विसरू शकतात. आवश्यक मूल्ये builder च्या constructor मध्ये घ्या जेणेकरून compiler मदत करतो.

🎛️ Director ओव्हरलोड करणे

Director ला डझनभर कृतीक्रम methods चा god-object बनवल्याने Builder ज्या गुंतागुंतीला काबूत आणण्यासाठी होता तीच पुन्हा निर्माण होते. कृतीक्रम थोडे आणि केंद्रित ठेवा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Builder अतिरिक्त कोडच्या किंमतीत वाचनीयता आणि सुरक्षित immutability खरेदी करतो. records, named parameters, किंवा साधा constructor सारख्या सोप्या पर्यायांशी त्याची तुलना करा.

पैलूतपशील
फायदेवाचनीय, स्वयंस्पष्ट call sites; immutable ऑब्जेक्ट्सची सुरक्षित रचना; केंद्रीय validation; callers न मोडता ऐच्छिक fields जोडणे सोपे.
तोटेअधिक कोड (एक संपूर्ण nested class); डुप्लिकेट झालेल्या field घोषणा; थोडे indirection; साध्या value types साठी अतिरेक.
केव्हा वापरावेऑब्जेक्टला अनेक ऐच्छिक किंवा default असलेली fields आहेत, immutable असणे आवश्यक आहे, किंवा अस्तित्वात येण्यापूर्वी cross-field validation आवश्यक आहे.
केव्हा टाळावेऑब्जेक्टला थोड्या, बहुतांश आवश्यक fields आहेत. record, साधा constructor, किंवा भाषा-स्तरीय named parameters ला प्राधान्य द्या.
गुंतागुंतमध्यम. पॅटर्न स्वतः साधा आहे; किंमत ही boilerplate आहे, जी कोड जनरेटर (Lombok, IDE tooling) कमी करू शकतात.
संबंधितFactory Method आणि Abstract Factory (ऑब्जेक्ट्सही तयार करतात), Prototype (जुळवण्याऐवजी clone करा), Composite (उत्पादन तयार करू शकणारी trees बनवा).
ठोकताळा: जेव्हा एका constructor call ला तीन किंवा चारपेक्षा जास्त arguments लागतील, त्यातील अनेक ऐच्छिक, आणि तुम्हाला निकाल immutable हवा असेल तेव्हा Builder वापरा. त्या मर्यादेखाली, record किंवा साधा constructor अधिक स्पष्ट असतो.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

production कोडमध्ये Builder पॅटर्नवर अवलंबून असलेल्या तीन व्यापकपणे वापरल्या जाणाऱ्या APIs.

🌐

1 · OkHttp Request.Builder

पॅटर्न: immutable HTTP requests साठी fluent builder

OkHttp client एका HTTP request ला nested builder द्वारे जुळवलेला immutable ऑब्जेक्ट म्हणून मॉडेल करतो.

  • Callers एक frozen Request मिळवण्यासाठी .url(), .header(), .post() आणि मग .build() साखळीत जोडतात.
  • आवश्यक आणि ऐच्छिक भाग कोणत्याही क्रमाने, समजूतदार method defaults सह सेट होतात.
  • तयार झालेली request immutable आहे आणि threads व retries मध्ये सामायिक करण्यास सुरक्षित आहे.
✅ निष्पत्ती: Request setup हे call च्या वर्णनासारखे वाचले जाते, आणि परिणामी ऑब्जेक्ट रचनेनुसारच thread-safe असतो.
🧵

2 · Java StringBuilder

पॅटर्न: एका अंतिम मूल्याची हळूहळू जुळणी

StringBuilder हा रोजचा builder आहे: तो टप्प्याटप्प्याने अक्षरे जमा करतो, मग एक अंतिम String तयार करतो.

  • प्रत्येक append() builder परत करतो, त्यामुळे अनेक appends एका अभिव्यक्तीत साखळीत जोडतात.
  • मुटेबल buffer प्रत्येक concatenation वर नवीन String तयार करणे टाळतो.
  • toString() हा build() टप्पा आहे जो immutable निकाल देतो.
✅ निष्पत्ती: वारंवार allocation च्या किंमतीशिवाय एका मोठ्या immutable string ची कार्यक्षम रचना.
🐳

3 · Kubernetes आणि Docker client builders

पॅटर्न: खोलवर nested config ऑब्जेक्ट्ससाठी builders

Fabric8 आणि तत्सम Kubernetes clients pod, deployment, आणि service specs तयार करण्यासाठी fluent builders उघड करतात.

  • खोलवर nested specs प्रचंड constructors ऐवजी साखळीत जोडलेल्या, nested builders ने जुळवल्या जातात.
  • Kubernetes ऑब्जेक्ट वाहू शकणाऱ्या अनेक ऐच्छिक fields defaults भरतात.
  • तयार झालेला spec हा एक validated, serializable ऑब्जेक्ट आहे जो API server ला पाठवण्यास तयार असतो.
✅ निष्पत्ती: गुंतागुंतीचे, खोलवर संरचित configuration positional argument सूपमध्ये कोसळण्याऐवजी वाचनीय आणि type-safe राहते.
07 - उपयुक्तता

आधुनिक उपयुक्तता

नवीन भाषा-वैशिष्ट्ये तुम्ही किती manual builder कोड लिहिता ते बदलतात, पण पॅटर्नचा हेतू आधुनिक APIs मध्ये केंद्रस्थानी राहतो.

🗒️ Records आणि data classes

Java records आणि Kotlin data classes साध्या immutables साठी boilerplate काढून टाकतात, ज्यामुळे हाताने लिहिलेला builder उपयुक्त ठरणाऱ्या प्रकरणांची संख्या कमी होते.

🏷️ Named आणि default parameters

Kotlin, Python, आणि C# named arguments अनेक builder वापर-प्रसंग थेट पूर्ण करतात, त्यामुळे builders खरोखरच गुंतागुंतीच्या ऑब्जेक्ट्ससाठी राखीव राहतात.

🤖 Generated builders

Lombok चे @Builder, IDE generators, आणि annotation processors boilerplate तयार करतात, टायपिंगशिवाय पॅटर्नचे फायदे टिकवून ठेवतात.

🧪 Test data builders

object-mother आणि test-data-builder संकल्पना unit tests मध्ये वाचनीय, बदलता येण्याजोगे fixtures तयार करण्यासाठी fluent builders वापरतात.

🔒 Staged (step) builders

Type-safe staged builders compile time वेळी आवश्यक टप्पे क्रमाने लागू करण्यासाठी interfaces वापरतात, त्यामुळे अनिवार्य fields सेट झाल्यावरच build() पर्यंत पोहोचता येते.

🧵 Fluent DSLs

query builders पासून UI आणि infrastructure DSLs पर्यंत, fluent-builder शैली आधुनिक frameworks पसंत करत असलेल्या साखळीत जोडलेल्या, declarative APIs चा आधार आहे.

सारांश: Builder पॅटर्न अवाचनीय, चुकांना प्रवण रचनेचे एका छोट्या, सुरक्षित, स्वयंस्पष्ट API मध्ये रूपांतर करतो आणि immutable ऑब्जेक्ट्स देतो. भाषा-वैशिष्ट्ये boilerplate स्वयंचलित करतात, पण हेतू, रचना प्रतिनिधित्वापासून वेगळे करणे, पूर्वीपेक्षा अधिक उपयुक्त आहे.
