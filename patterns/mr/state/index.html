Behavioral पॅटर्न

State पॅटर्न - ऑब्जेक्टसोबत बदलणारे वर्तन

काही ऑब्जेक्ट्स ते कोणत्या मोडमध्ये आहेत यावर अवलंबून पूर्णपणे वेगळ्या प्रकारे वागतात: draft ऑर्डर ही shipped ऑर्डर नसते, थांबवलेला (paused) प्लेयर हा वाजणाऱ्या (playing) प्लेयरसारखा नसतो. State पॅटर्न एखाद्या ऑब्जेक्टला त्याच्या अंतर्गत state बदलल्यावर त्याचे वर्तन बदलू देतो, आणि हे तो अदलाबदल करता येण्याजोग्या state ऑब्जेक्ट्सकडे काम सोपवून करतो. if आणि switch ब्लॉक्सने भरलेल्या एका class ऐवजी, प्रत्येक state स्वतःचा एक class बनतो, ज्याला माहीत असते की कसे वागायचे आणि पुढच्या state कडे नियंत्रण केव्हा सोपवायचे.

01 - काय

State पॅटर्न म्हणजे काय?

State हा एक behavioral डिझाइन पॅटर्न आहे जो एखाद्या ऑब्जेक्टला त्याच्या अंतर्गत state बदलल्यावर त्याचे वर्तन बदलू देतो, त्यामुळे तो जणू आपला class बदलतो असे वाटते. context म्हटला जाणारा हा ऑब्जेक्ट एका state ऑब्जेक्टचा संदर्भ ठेवतो आणि state वर अवलंबून असलेली सगळी कामे त्याच्याकडे सोपवतो. प्रत्येक concrete state हा एक वेगळा class असतो जो एका सामायिक interface ची अंमलबजावणी करतो, आणि एखादा state context ला वेगळ्या state कडे वळवू शकतो, ज्यामुळे एका finite state machine ची transitions घडतात.

📦 Context

ज्याचे वर्तन बदलते तो ऑब्जेक्ट. तो सध्याच्या-state चा संदर्भ ठेवतो आणि विनंत्या त्याच्याकडे पाठवतो, state वर स्वतः कधीही branching करत नाही.

🔌 State interface

state वर अवलंबून असलेल्या क्रियांची यादी असलेला एक सामायिक करार. प्रत्येक concrete state त्याची अंमलबजावणी करतो, त्यामुळे context त्यांना एकसमान वागणूक देऊ शकतो.

🎭 Concrete states

प्रत्येक मोडसाठी एक class. प्रत्येक त्या मोडचे वर्तन आपल्यात सामावून घेतो आणि एखाद्या घटनेनंतर पुढचा state कोणता येईल हे ठरवतो.

02 - का

State पॅटर्न का अस्तित्वात आहे

एका lifecycle मधून जाणारे ऑब्जेक्ट्स सहसा flags आणि conditionals ची गुंतागुंत वाढवत जातात. प्रत्येक method ला एक switch (status) फुटतो, आणि एक नवा state जोडायचा म्हणजे प्रत्येक method संपादित करावा लागतो. State पॅटर्न त्याऐवजी स्थानिक, single-responsibility state classes आणतो.

🧹 मोठे switch नाहीसे करतो

प्रत्येक मोडचे वर्तन प्रत्येक method मधल्या डझनभर conditionals मध्ये पसरण्याऐवजी स्वतःच्या class मध्ये राहते. एक state वाचला की तो काय करतो हे सगळे कळते.

➕ नव्या states साठी खुला

state जोडणे म्हणजे एक नवा class लिहिणे, context चा प्रत्येक method संपादित करणे नव्हे. हे open-closed तत्त्व पाळते आणि बदल स्थानिक ठेवते.

🚦 Transitions स्पष्ट करतो

प्रत्येक state तो नेमका कोणत्या states कडे जाऊ शकतो हे नाव घेऊन सांगतो, त्यामुळे machine ची रचना boolean flags मध्ये लपण्याऐवजी code मध्ये दिसते.

🛡️ अवैध क्रिया रोखतो

एखाद्या मोडमध्ये अवैध असलेली क्रिया त्या state class मध्ये फक्त काहीच करत नाही किंवा error देते, त्यामुळे कधीही payment न झालेली ऑर्डर तुम्ही ship करू शकत नाही.

सोप्या शब्दांत

उपमांसह State ची ओळख

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती पटकन कळेल.

🎓 विद्यार्थ्यासाठी

पाण्याच्या अवस्थांचा विचार करा. बर्फ, द्रव, आणि वाफ हे सगळे तेच H2O आहेत, पण ते वेगवेगळ्या प्रकारे वागतात. उष्णता द्या आणि प्रत्येक पुढच्या अवस्थेत जातो. पाणी हा context आहे; बर्फ, द्रव, आणि वाफ हे state ऑब्जेक्ट्स आहेत.

👩‍💻 डेव्हलपरसाठी

हे वर्तनाच्या lookup table चे polymorphism मध्ये रूपांतर आहे. प्रत्येक method मध्ये switch (status) लिहिण्याऐवजी तुम्ही state.handle() कॉल करता आणि सध्याच्या ऑब्जेक्टला निर्णय घेऊ देता. status जोडल्याने आधीच्या code ला कधीही धक्का लागत नाही.

🏢 व्यावसायिकासाठी

document मंजुरी workflow सारखे: Draft, In Review, Approved, Rejected. तुम्ही कोणती बटणे दाबू शकता हे टप्प्यावर अवलंबून असते, आणि एक दाबल्याने document पुढच्या टप्प्यात जाते. प्रत्येक टप्पा एक state आहे.

🚦 रोजच्या जीवनातील आवृत्ती

एक traffic light. हिरवा, पिवळा, आणि लाल प्रत्येकाला माहीत असते की तो काय दाखवतो आणि पुढे काय येते. light सगळीकडे "मी हिरवा आहे का?" असे तपासत नाही; प्रत्येक रंग फक्त वागतो आणि मग पुढच्याकडे सोपवतो.

03 - कसे

आतमध्ये ते कसे काम करते

तुम्ही प्रत्येक state वर अवलंबून असलेला method एका state interface मध्ये काढता, प्रत्येक मोडसाठी एक concrete state class लिहिता, आणि context ला जो state सध्या चालू असेल त्याच्याकडे काम सोपवायला लावता. states हे context ला त्याचा सध्याचा state बदलायला सांगून transitions घडवतात.

🧭 सोपवणे, branching नव्हे

context कधीही स्वतःचा status तपासत नाही. तो प्रत्येक कॉल सध्याच्या state ऑब्जेक्टकडे पाठवतो, जो त्या मोडसाठी योग्य वर्तन पुरवतो.

🔁 Transitions चा मालक state असतो

पुढे काय होते हे concrete state ठरवतो. एखादी घटना हाताळल्यानंतर तो context मध्ये परत कॉल करून नवा सध्याचा state सेट करतो, आणि अशा प्रकारे machine ची एक edge encode करतो.

Java मध्ये एक finite state machine: एक media player

// State interface: the state-dependent operations
interface PlayerState {
    void play(Player p);
    void pause(Player p);
    void stop(Player p);
}

// Context: delegates every request to the current state
class Player {
    private PlayerState state = new Stopped();

    void setState(PlayerState next) { this.state = next; }

    void play()  { state.play(this); }
    void pause() { state.pause(this); }
    void stop()  { state.stop(this); }
}

// Concrete state: nothing is playing yet
class Stopped implements PlayerState {
    public void play(Player p) {
        System.out.println("Starting playback");
        p.setState(new Playing());        // transition
    }
    public void pause(Player p) { /* no-op: cannot pause when stopped */ }
    public void stop(Player p)  { /* already stopped */ }
}

// Concrete state: audio is running
class Playing implements PlayerState {
    public void play(Player p)  { /* already playing */ }
    public void pause(Player p) {
        System.out.println("Pausing");
        p.setState(new Paused());         // transition
    }
    public void stop(Player p) {
        System.out.println("Stopping");
        p.setState(new Stopped());        // transition
    }
}

// Concrete state: playback is suspended
class Paused implements PlayerState {
    public void play(Player p) {
        System.out.println("Resuming");
        p.setState(new Playing());        // transition
    }
    public void pause(Player p) { /* already paused */ }
    public void stop(Player p) {
        System.out.println("Stopping");
        p.setState(new Stopped());        // transition
    }
}

लक्षात घ्या की Player मध्ये कुठेही if किंवा switch नाही. प्रत्येक state त्याच तीन methods ला उत्तर देतो पण वेगळ्या प्रकारे वागतो, आणि प्रत्येक जण player पुढे कोणता state बनेल हे ठरवतो. Stopped असताना pause() कॉल करणे हा फक्त एक वैध no-op आहे, त्यामुळे अवैध transitions रचनेनेच हाताळल्या जातात, विखुरलेल्या guards ने नव्हे.

सामान्य अडचणी

अडचणी आणि anti-patterns

State पॅटर्न शक्तिशाली आहे पण त्याचा अतिवापर करणे किंवा तो चुकीच्या पद्धतीने जोडणे सोपे आहे. या गोष्टींकडे लक्ष द्या.

🪆 दोन states साठी वापरणे

एका boolean flag ला class hierarchy ची गरज नाही. जेव्हा अनेक मोड असतील आणि वर्तन खरोखर वेगळे होत असेल तेव्हा State वापरा, on आणि off साठी नव्हे.

🕸️ सगळीकडे transition logic

कोणत्याही नकाशाशिवाय states मध्ये setState कॉल विखुरल्याने machine वाचणे अशक्य होते. रचना स्पष्ट राहावी म्हणून एक स्पष्ट आकृती किंवा table ठेवा.

🔓 context चे अंतर्गत तपशील उघड करणे

states ना प्रत्येक field चा थेट access दिल्याने ते घट्टपणे जोडले जातात. context वर एक मर्यादित API उघड करा जेणेकरून states फक्त तेच बदलतील जे त्यांनी बदलावे.

💾 transition वर state गमावणे

प्रत्येक वेळी नवा state ऑब्जेक्ट तयार करणे वर्तनासाठी ठीक आहे, पण जर data बदलानंतरही टिकावा लागत असेल, तर तो state वर नव्हे तर context वर साठवा.

🐘 God states

अंतर्गत branching ने अनेक विशेष केसेस हाताळणारा एक state फक्त switch एका class च्या आत सरकवतो. त्याऐवजी त्याचे वेगवेगळ्या states मध्ये विभाजन करा.

🎭 त्याचा Strategy शी गोंधळ

जर caller एकदाच वर्तन निवडत असेल आणि ते स्वतः कधीही बदलत नसेल, तर तो Strategy आहे. तिथे State वापरल्याने तुम्हाला गरज नसलेली transition यंत्रणा जोडली जाते.

तडजोडी

तडजोडी आणि केव्हा वापरावे

State काही मूठभर लहान classes च्या बदल्यात पसरलेल्या conditionals चे निर्मूलन करतो. हा प्रामाणिक ताळेबंद आहे, त्यात तो Strategy पेक्षा कसा वेगळा आहे हेही आहे.

बाबतपशील
फायदेमोठे conditional आणि switch ब्लॉक्स काढून टाकतो, प्रत्येक मोडचे वर्तन स्थानिक करतो, transitions स्पष्ट करतो, आणि open-closed व single-responsibility तत्त्वे पाळतो.
तोटेअधिक classes आणि indirection, states मध्ये पसरलेली transition logic, आणि जेव्हा फक्त एक-दोन साधे मोड असतात तेव्हा अतिरेक.
केव्हा वापरावेएका ऑब्जेक्टला अनेक वेगळे मोड असतात, प्रत्येक मोडनुसार वर्तन खूप वेगळे होते, आणि मोडांमधली transitions नियमांनुसार होतात, म्हणजेच एक finite state machine.
केव्हा टाळावेजेव्हा किरकोळ फरक असलेले फक्त दोन-चार states असतात, किंवा मोड runtime ला कधीच बदलत नाही, तिथे एक flag किंवा एक Strategy अधिक सोपे असते.
गुंतागुंतप्रत्येक state साठी कमी, एकूण मध्यम. प्रत्येक state छोटा असतो, पण संपूर्ण संचात transition नकाशा सुसंगत ठेवावा लागतो.
संबंधितStrategy ची रचना तीच असते पण client वर्तन निवडतो आणि states कधीही स्वतःची अदलाबदल करत नाहीत. State ऑब्जेक्ट्स स्वतःच्या transitions घडवतात. दोन्ही रचनात्मकदृष्ट्या त्याच सोपवण्याच्या कल्पनेतून येतात.
ढोबळ नियम: जेव्हा तुमचा ऑब्जेक्ट खरोखर एक finite state machine असतो आणि त्याचे methods सतत "मी कोणत्या मोडमध्ये आहे?" असे विचारत राहतात तेव्हा State वापरा. जर त्याऐवजी caller फक्त एक अदलाबदल करता येण्याजोगा algorithm लावतो जो स्वतःहून कधीच बदलत नाही, तर तो Strategy आहे, State नव्हे.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

जिथे lifecycles आणि मोड डिझाइनवर वर्चस्व गाजवतात तिथे State पॅटर्न दाखवणारे तीन प्रातिनिधिक वापर.

🛒

1 · E-commerce ऑर्डर lifecycle

पॅटर्न: lifecycle एक finite state machine म्हणून

एक ऑर्डर New, Paid, Shipped, Delivered, आणि Cancelled मधून जाते, आणि प्रत्येक टप्पा वेगवेगळ्या क्रियांना परवानगी देतो.

  • प्रत्येक status हा एक state class आहे जो फक्त त्याच्या वैध क्रियांना परवानगी देतो, त्यामुळे payment आधी ship() अशक्य आहे.
  • Transitions state classes मध्ये राहतात, ज्यामुळे ऑर्डर lifecycle चा एकच, तपासता येण्याजोगा नकाशा मिळतो.
  • Refunded state जोडणे म्हणजे एक नवा class आणि त्याच्या edges, आधीच्या statuses मध्ये कोणतीही संपादने न करता.
✅ परिणाम: अवैध transitions रचनेनेच compile-safe बनतात, आणि पूर्वी ऑर्डर service मध्ये असलेला पसरलेला status switch नाहीसा होतो.
🎬

2 · Media player नियंत्रणे

पॅटर्न: मोडवर अवलंबून असलेले UI वर्तन

एक player Stopped, Playing, किंवा Paused असतो, आणि तीच बटणे प्रत्येक मोडमध्ये वेगवेगळी कामे करावी लागतात.

  • प्रत्येक state ठरवतो की play, pause, आणि stop कसे वागतील, त्यामुळे paused असताना play बटण पुन्हा सुरू करते पण stopped असताना सुरुवात करते.
  • UI फक्त क्लिक्स सध्याच्या state कडे पाठवते आणि कधीही status flag तपासत नाही.
  • Buffering किंवा Error state आधीच्या नियंत्रणांना हात न लावता आणखी एक class म्हणून बसतो.
✅ परिणाम: नियंत्रण logic प्रत्येक मोडसाठी छोटी आणि योग्य राहते, आणि नवे playback states player ला गुंतागुंतीचा न करता त्याचा विस्तार करतात.
🔌

3 · TCP connection protocol

पॅटर्न: एका classic संदर्भातील protocol states

एक TCP connection Established, Listening, किंवा Closed असते, हे मूळ design patterns साहित्यातील एक पाठ्यपुस्तकी उदाहरण आहे.

  • open, close, आणि acknowledge सारख्या क्रिया connection च्या state वर अवलंबून वेगवेगळ्या प्रकारे वागतात.
  • प्रत्येक protocol state आपला प्रतिसाद आणि प्रत्येक घटनेवर तो कोणत्या state कडे जातो हे आपल्यात सामावतो.
  • connection ऑब्जेक्ट सध्याच्या state कडे सोपवतो, ज्यामुळे protocol हाताळणी एका राक्षसी method बाहेर राहते.
✅ परिणाम: protocol चे नियम थेट state classes च्या संचासारखे वाचता येतात, जे spec शी जवळून जुळतात आणि पडताळणी सोपी करतात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Finite state machines आधुनिक software मध्ये सर्वत्र आहेत, आणि State पॅटर्न त्यांना व्यक्त करण्याचा स्वच्छ object-oriented मार्ग राहतो.

⚛️ UI state machines

Front-end साधने components ना स्पष्ट states आणि transitions म्हणून model करतात, तीच शिस्त State encode करतो, ज्यामुळे गुंतागुंतीचे interactive flows आटोक्यात येतात.

🔄 Workflow engines

Order, approval, आणि onboarding workflows मुळात finite state machines आहेत, जिथे प्रत्येक टप्पा स्वाभाविकपणे एका state class शी जुळतो.

🧩 Enum-आधारित states

आधुनिक भाषा एका state ला data आणि वर्तन एकत्र वाहू देतात, त्यामुळे हा पॅटर्न sealed types किंवा methods असलेल्या enums ने व्यक्त करता येतो.

🕹️ Game आणि agent logic

पात्रे आणि agents idle, patrol, chase, आणि attack मोडांमध्ये बदलतात, जो game development मधील एक प्रातिनिधिक State पॅटर्न वापर आहे.

☁️ Distributed sagas

दीर्घकाळ चालणारे distributed transactions आपली प्रगती states म्हणून मागोवा घेतात, आणि एखादा टप्पा अयशस्वी झाल्यास compensating transitions सह.

🔬 चाचणी करता येण्याजोग्या transitions

प्रत्येक edge स्पष्ट असल्यामुळे, state machines model-check आणि property-test करणे सोपे असते, ज्यामुळे महत्त्वाच्या flows वरील विश्वास वाढतो.

सारांश: जेव्हा एखाद्या ऑब्जेक्टचे वर्तन नियमांनुसार कालांतराने बदलणाऱ्या मोडवर अवलंबून असते, तेव्हा तुमच्याकडे एक finite state machine असते. State पॅटर्न हा त्या machine ला सतत वाढणाऱ्या conditionals मध्ये लपू न देता स्पष्ट, चाचणी करता येण्याजोगी, आणि सहज विस्तारता येण्याजोगी बनवण्याचा मार्ग आहे.
