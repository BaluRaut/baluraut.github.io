कलेक्शन एन्कॅप्सुलेट करणे - list राखा, ती हातात देऊ नका

जो class ऑर्डरच्या line items ची, playlist च्या tracks ची किंवा team च्या members ची यादी बाळगतो, तो त्या यादीबद्दलचे नियम देखील बाळगतो. ज्या क्षणी तुम्ही एखाद्या getter मधून raw कलेक्शन परत करता, त्या क्षणी कोणताही caller तुमच्या नकळत त्यात भर घालू शकतो, काढू शकतो किंवा ती रिकामी करू शकतो आणि तुमचे invariants शांतपणे मरतात. कलेक्शन एन्कॅप्सुलेट करणे म्हणजे container नव्हे तर वर्तन उघड करणे: वाचनासाठी प्रती किंवा read-only view परत करा, आणि नियम पाळणाऱ्या methods मधूनच बदल करा.

01 - काय

कलेक्शन एन्कॅप्सुलेट करणे म्हणजे काय?

कलेक्शन एन्कॅप्सुलेट करणे म्हणजे आतील list, set किंवा map हा एक private अंमलबजावणीचा तपशील असतो ज्याला बाहेरचे जग कधीही थेट स्पर्श करत नाही. Callers ऑब्जेक्टला गोष्टी करण्यास सांगतात, एखादा line item जोडा, एखादा track काढा, members मोजा, आणि ऑब्जेक्ट uniqueness, बेरीज, मर्यादा आणि क्रम यांसारखे नियम पाळत आपल्याच कलेक्शनमध्ये बदल करतो. वाचन एक प्रत किंवा एक बदल न करता येणारे view परत देते, कधीही जिवंत reference नाही.

🔒 Container लपवा

list किंवा map धारण करणारे field private असते. ते परत करणारा कोणताही getter नसतो आणि ते बदलणारा कोणताही setter नसतो. Callers आत पोहोचू शकत नाहीत.

👁️ सुरक्षित वाचन उघड करा

वाचनाने एक immutable view किंवा एक ताजी प्रत परत मिळते. Iterate करणे किंवा मोजणे ठीक आहे; परत केलेले मूल्य बदलल्यास मालकाच्या स्थितीला स्पर्श होता कामा नये.

🛠️ Methods मधूनच बदल करा

addItem आणि removeItem हेच आत जाणारे एकमेव दरवाजे आहेत. बदल टिकण्याआधी प्रत्येक जण input तपासतो आणि invariants पुन्हा तपासतो.

02 - का

कलेक्शन एन्कॅप्सुलेट का करावे

कलेक्शन म्हणजे केवळ data नाही; ते म्हणजे data आणि ते वैध ठेवणारे नियम. Container लीक केल्याने नियम आणि data वेगळे होतात आणि codebase मधल्या कुठूनही भ्रष्टाचाराला निमंत्रण मिळते.

🛡️ Invariants खरे राहतात

ज्या ऑर्डरची total तिच्या line items च्या बेरजेइतकी असलीच पाहिजे, तिच्यावर तेव्हाच विश्वास ठेवता येतो जेव्हा प्रत्येक add आणि remove ऑर्डरमधूनच जातो. बाहेरून एक थेट push झाला की cached total खोटी ठरते.

🧭 नियम बदलण्याची एकच जागा

प्रत्येक playlist ला 500 tracks ची मर्यादा हवी आहे, किंवा डुप्लिकेट SKUs रोखायचे आहेत? list ला कधी स्पर्श केलेल्या प्रत्येक caller चे ऑडिट करण्याऐवजी तुम्ही एकाच method मध्ये तपासणी जोडता.

🔎 Bugs चा माग लहान असतो

जेव्हा स्थिती फक्त नाव असलेल्या methods मधूनच बदलू शकते, तेव्हा भ्रष्ट कलेक्शनमागे संपूर्ण application नव्हे तर मोजके संशयित असतात. तुम्ही भिंतींवर नव्हे तर दरवाज्यांवर breakpoints ठेवता.

🔀 Internals बदलण्याचे स्वातंत्र्य

ते array आहे यावर कोणीही अवलंबून नसल्याने, एकाही caller ला न मोडता तुम्ही uniqueness साठी set किंवा जलद lookup साठी map वर जाऊ शकता.

सोप्या शब्दांत

उपमांसह समजावून सांगितलेले कलेक्शन एन्कॅप्सुलेशन

तीच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती समजेल.

🎓 विद्यार्थ्यासाठी

हे एक ग्रंथालय आहे, पुस्तकांचा मुक्त ढीग नाही. तुम्ही रॅकमध्ये चालत जाऊन कपाटे पुन्हा लावत नाही. तुम्ही काउंटरवर घेण्या-देण्याची विनंती करता, आणि ग्रंथपाल कॅटलॉग सुसंगत ठेवतो.

👩‍💻 डेव्हलपरसाठी

getter ने readonly किंवा एक प्रत परत करावी. जिवंत array परत देणे म्हणजे एका private field चे mutable reference परत देण्यासारखे आहे, त्याने private keyword केवळ सजावट बनते आणि प्रत्येक invariant आता ऐच्छिक होतो.

🏢 व्यावसायिकासाठी

एका बँकेच्या खातेवहीचा विचार करा. कारकून थेट वहीत खरडत नाहीत; ते व्यवहार दाखल करतात जे system नोंदवते. प्रत्येक नोंद एका नियंत्रित operation मधून जात असल्याने खातेवही ताळेबंद राहते.

🎟️ रोजच्या जीवनातील आवृत्ती

एक पाहुण्यांच्या यादीसह मैफल. पाहुणे दारात यादी बदलत नाहीत; ते नाव जोडण्यास किंवा काढण्यास यजमानाला विनंती करतात, त्यामुळे क्षमता आणि डुप्लिकेट नेहमी नियंत्रणात राहतात.

03 - कसे

कोडमध्ये ते कसे चालते

एक Order घ्या जी आपले line items बाळगते. ती list private आहे. वाचन एक read-only view परत करते. Adds आणि removes अशा methods मधून जातात ज्या तपासणी करतात आणि total प्रामाणिक ठेवतात.

📥 लेखनाचे रक्षण करा

addItem quantity तपासतो, डुप्लिकेट SKUs एकत्र करतो, आणि बदल committed होण्याआधी कमाल-item मर्यादा पाळतो. काहीही त्याला वळसा घालत नाही.

📤 वाचन निष्प्रभ करा

lineItems एक frozen किंवा read-only क्रम परत करते. Callers loop करू शकतात आणि बेरीज करू शकतात, पण एखादा भरकटलेला push किंवा clear एकतर fail होतो किंवा एका टाकाऊ प्रतीवर आपटतो.

class LineItem {
  constructor(
    readonly sku: string,
    readonly name: string,
    readonly unitPriceCents: number,
    readonly quantity: number,
  ) {}
  subtotalCents(): number {
    return this.unitPriceCents * this.quantity;
  }
}

class Order {
  // Private backing collection: no getter returns it, no setter replaces it.
  private readonly items: LineItem[] = [];

  constructor(private readonly maxItems = 100) {}

  addItem(sku: string, name: string, unitPriceCents: number, qty: number): void {
    if (qty <= 0) throw new Error("quantity must be positive");
    if (unitPriceCents < 0) throw new Error("price cannot be negative");

    const existing = this.items.find((i) => i.sku === sku);
    if (existing) {
      this.replace(sku, new LineItem(sku, name, unitPriceCents, existing.quantity + qty));
      return;
    }
    if (this.items.length >= this.maxItems) throw new Error("order is full");
    this.items.push(new LineItem(sku, name, unitPriceCents, qty));
  }

  removeItem(sku: string): void {
    const idx = this.items.findIndex((i) => i.sku === sku);
    if (idx === -1) throw new Error(`no line item for ${sku}`);
    this.items.splice(idx, 1);
  }

  changeQuantity(sku: string, qty: number): void {
    if (qty <= 0) { this.removeItem(sku); return; }
    const cur = this.items.find((i) => i.sku === sku);
    if (!cur) throw new Error(`no line item for ${sku}`);
    this.replace(sku, new LineItem(sku, cur.name, cur.unitPriceCents, qty));
  }

  // Read-only view: callers can iterate but cannot mutate our state.
  get lineItems(): readonly LineItem[] {
    return this.items as readonly LineItem[];
  }

  totalCents(): number {
    return this.items.reduce((sum, i) => sum + i.subtotalCents(), 0);
  }

  count(): number {
    return this.items.length;
  }

  private replace(sku: string, next: LineItem): void {
    const idx = this.items.findIndex((i) => i.sku === sku);
    this.items[idx] = next;
  }
}

from dataclasses import dataclass
from typing import Sequence


@dataclass(frozen=True)
class LineItem:
    sku: str
    name: str
    unit_price_cents: int
    quantity: int

    def subtotal_cents(self) -> int:
        return self.unit_price_cents * self.quantity


class Order:
    def __init__(self, max_items: int = 100) -> None:
        # Name-mangled backing list: no accessor returns it directly.
        self.__items: list[LineItem] = []
        self.__max_items = max_items

    def add_item(self, sku: str, name: str, unit_price_cents: int, qty: int) -> None:
        if qty <= 0:
            raise ValueError("quantity must be positive")
        if unit_price_cents < 0:
            raise ValueError("price cannot be negative")

        existing = self.__find(sku)
        if existing is not None:
            self.__replace(sku, LineItem(sku, name, unit_price_cents,
                                         existing.quantity + qty))
            return
        if len(self.__items) >= self.__max_items:
            raise ValueError("order is full")
        self.__items.append(LineItem(sku, name, unit_price_cents, qty))

    def remove_item(self, sku: str) -> None:
        item = self.__find(sku)
        if item is None:
            raise KeyError(f"no line item for {sku}")
        self.__items.remove(item)

    def change_quantity(self, sku: str, qty: int) -> None:
        if qty <= 0:
            self.remove_item(sku)
            return
        cur = self.__find(sku)
        if cur is None:
            raise KeyError(f"no line item for {sku}")
        self.__replace(sku, LineItem(sku, cur.name, cur.unit_price_cents, qty))

    @property
    def line_items(self) -> Sequence[LineItem]:
        # Read-only copy: mutating the tuple cannot touch our list.
        return tuple(self.__items)

    def total_cents(self) -> int:
        return sum(i.subtotal_cents() for i in self.__items)

    def count(self) -> int:
        return len(self.__items)

    def __find(self, sku: str) -> LineItem | None:
        return next((i for i in self.__items if i.sku == sku), None)

    def __replace(self, sku: str, nxt: LineItem) -> None:
        idx = next(i for i, it in enumerate(self.__items) if it.sku == sku)
        self.__items[idx] = nxt

LineItem = Struct.new(:sku, :name, :unit_price_cents, :quantity) do
  def subtotal_cents
    unit_price_cents * quantity
  end
end

class Order
  def initialize(max_items: 100)
    # Private backing array; no attr_accessor exposes it.
    @items = []
    @max_items = max_items
  end

  def add_item(sku, name, unit_price_cents, qty)
    raise ArgumentError, "quantity must be positive" if qty <= 0
    raise ArgumentError, "price cannot be negative"  if unit_price_cents < 0

    existing = find(sku)
    if existing
      replace(sku, LineItem.new(sku, name, unit_price_cents,
                                existing.quantity + qty))
      return
    end
    raise "order is full" if @items.size >= @max_items
    @items << LineItem.new(sku, name, unit_price_cents, qty)
  end

  def remove_item(sku)
    item = find(sku) or raise KeyError, "no line item for #{sku}"
    @items.delete(item)
  end

  def change_quantity(sku, qty)
    return remove_item(sku) if qty <= 0
    cur = find(sku) or raise KeyError, "no line item for #{sku}"
    replace(sku, LineItem.new(sku, cur.name, cur.unit_price_cents, qty))
  end

  # Frozen copy: callers iterate, but cannot mutate our state.
  def line_items
    @items.map(&:dup).freeze
  end

  def total_cents
    @items.sum(&:subtotal_cents)
  end

  def count
    @items.size
  end

  private

  def find(sku)
    @items.find { |i| i.sku == sku }
  end

  def replace(sku, nxt)
    idx = @items.index { |i| i.sku == sku }
    @items[idx] = nxt
  end
end

तिन्ही Order ची व्याख्या करतात, एक तयार करतात, आणि तिला फक्त methods मधूनच चालवतात. तोच SKU दोनदा जोडल्यास एक row डुप्लिकेट करण्याऐवजी quantities एकत्र होतात, आणि total नेहमी जिवंत items मधून काढला जातो, कधीही cache करून सडायला सोडला जात नाही. Read accessor caller ला असे काहीतरी परत देते जे तो ऑर्डर भ्रष्ट करण्यासाठी वापरू शकत नाही: TypeScript मध्ये एक readonly type, Python मध्ये एक tuple, Ruby मध्ये एक frozen प्रत.

05 - टप्प्याटप्प्याने

एका भोळ्या उघड केलेल्या list पासून ते पूर्णपणे संरक्षित कलेक्शनपर्यंत, संपूर्ण refactor क्रमाने.

00
शोधा

लीक करणारा getter शोधा

raw array, list किंवा map परत करणारे accessors शोधा. field परत करणारा get items() हा सर्व काही सुरू करणारा वास आहे.

10
Private करा

field private बनवा

backing कलेक्शन private म्हणून चिन्हांकित करा आणि संपूर्ण गोष्ट बदलणारा कोणताही setter काढून टाका. बाहेरच्या कोणालाही आता reference मिळत नाही.

20
यादी करा

Callers ती कशी वापरतात ते नोंदवा

प्रत्येक call site grep करा. त्यांना reads (iterate, count, sum) आणि writes (add, remove, clear, reorder) मध्ये गटबद्ध करा. हेच तुमचे method surface बनते.

30
वाचन

एक read-only accessor जोडा

एक readonly type, एक tuple किंवा एक frozen प्रत परत करा. Callers iterate करत राहतात; त्यांना जे परत मिळते ते ते फक्त बदलू शकत नाहीत.

40
Queries

Derived प्रश्न आत ढकला

order.items.length आणि हाताने केलेल्या बेरजा order.count() आणि order.total() ने बदला. Callers विचारतात, ते गणना करत नाहीत.

50
लेखन

Command methods जोडा

addItem आणि removeItem तयार करा. प्रत्येक बाहेरचा बदल एका वेळी एक call site याप्रमाणे त्यांच्यात हलवा.

60
Invariants

नियम आत लागू करा

quantity तपासा, डुप्लिकेट रोखा किंवा एकत्र करा, आकार मर्यादित करा. जे तपासे विखुरलेले होते ते आता एकाच जागी राहतात.

70
स्थलांतर करा

प्रत्येक caller पुन्हा लिहा

थेट push/splice कॉल नव्या methods ने बदला. Compiler आणि fail होणाऱ्या tests तुम्हाला मागे राहिलेल्यांकडे बोट दाखवतात.

80
बंद करा

raw getter हटवा

जिवंत कलेक्शन परत करणारा accessor काढून टाका. आता आत आणि बाहेर जाणारे एकमेव मार्ग तुमच्या नियंत्रणातलेच आहेत.

90
सिद्ध करा

Guards ची चाचणी करा

invariants मोडण्याचा प्रयत्न करणाऱ्या tests लिहा: ऋण quantity, मर्यादेपलीकडे, डुप्लिकेट SKU, आणि परत केलेले view बदलणे. सर्व नाकारले गेले पाहिजेत किंवा निरुपद्रवी असले पाहिजेत.

100
विकसित व्हा

Internals मुक्तपणे बदला

आकारावर कोणीही अवलंबून नसल्याने, uniqueness साठी किंवा जलद lookup साठी array ला set किंवा map मध्ये बदला. Callers ला कधीही कळत नाही.

सामान्य अडचणी

अडचणी आणि anti-patterns

कलेक्शन एन्कॅप्सुलेट करणे अर्धवट करणे सोपे आहे. हे असे लीक आहेत जे review मधून निसटतात.

🔓 जिवंत reference परत करणे

प्रत नव्हे तर field स्वतःच परत करणारा getter callers ना एक private setter देतो. ते शून्य तपासणीसह तुमची स्थिती push, splice किंवा clear करू शकतात.

🪟 उथळ प्रत, mutable elements

तुम्ही list ची प्रत करता पण elements अजूनही शेअर केलेले mutable ऑब्जेक्ट्स असतात. एक caller जागच्या जागी item.quantity संपादित करतो आणि तुमची total शांतपणे भरकटते. खोलवर प्रत करा किंवा elements immutable बनवा.

🏗️ Constructor मधून लीक

caller ने पास केलेली अगदी तीच array साठवणे म्हणजे ते अजूनही ती धरून असतात आणि नंतर तिला बदलू शकतात. येणारी कलेक्शन्स फक्त बाहेर जाताना नव्हे तर आत येतानाच प्रत करा.

📊 सडणारी cached total

हाताने update केलेले total field तेव्हाच चालते जेव्हा प्रत्येक बदल तुमच्यातूनच जातो. एक थेट संपादन आणि cache खोटे बोलते. ती derive करा, किंवा फक्त संरक्षित methods च्या आत update करा.

🧵 Iterator invalidation

एक जिवंत iterator किंवा view देऊन नंतर कलेक्शन बदलल्यास loop च्या मध्येच throw होऊ शकते किंवा elements वगळले जाऊ शकतात. उघड करण्याआधी snapshot घ्या, किंवा iteration दरम्यान बदल रोखा.

🕳️ रक्तहीन wrapper

list ला wrap करणे पण तरीही ती परत करणारा getItems() जोडणे. एन्कॅप्सुलेशन हे केवळ नाटक आहे; वर्तन अजूनही ऑब्जेक्टमध्ये नव्हे तर callers मध्येच राहते.

संकेत आणि मापदंड

संकेत आणि कसे मोजावे

तुम्ही अभिरुचीची unit-test करू शकत नाही, पण तुम्ही लीक झालेल्या कलेक्शनच्या ठशांवर लक्ष ठेवू शकता.

संकेततो तुम्हाला काय सांगतो
Getter field परत करतोकलेक्शन लीक झाले आहे; कोणताही caller ते बदलू शकतो. हा grep करण्यासारखा प्राथमिक वास आहे.
Callers getter च्या निकालावर .push/.add कॉल करतातबदलाचे logic मालकाच्या बाहेर राहते, त्यामुळे invariants सुसंगतपणे लागू होत नाहीत.
Call sites मध्ये डुप्लिकेट झालेली validationतोच "रिकामे नाकारा / N वर मर्यादा" तपास copy-paste केलेला आहे; तो एका command method मध्ये असायला हवा.
स्थिती चुकीची पण कोणतीही method दोषी न दिसणारे bugsएका लीक झालेल्या reference द्वारे ऑब्जेक्टच्या नकळत कशाने तरी कलेक्शन बदलले.
Cached aggregate items शी जुळत नाहीtotal किंवा count हाताने राखले जाते तर बदल त्याला वळसा घालतात. लीकचे भक्कम चिन्ह.
Data structure बदलणे कठीणCallers ते array आहे यावर अवलंबून असतात; set किंवा map बदल त्यांना मोडतो. एन्कॅप्सुलेशनने आकार लपवला असता.
ठोकळमानाचा नियम: जर तुम्ही मालक class च्या बाहेरील एखाद्या ओळीकडे बोट दाखवू शकत असाल जी तिचे कलेक्शन बदलते, तर ते कलेक्शन एन्कॅप्सुलेट केलेले नाही. वाचन class मधून प्रती किंवा read-only views म्हणून बाहेर पडते; लेखन फक्त नाव असलेल्या methods मधूनच आत येते.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन systems जिथे कलेक्शन राखणे हे बरोबर आणि भ्रष्ट यांच्यातील फरक असतो.

🛒

1 · Checkout: Order आणि तिचे line items

Pattern: संरक्षित कलेक्शनमधून काढलेल्या totals

एका e-commerce ऑर्डरने तिची total, tax आणि discounts तिच्या line items शी नेहमी सुसंगत ठेवली पाहिजे.

  • Order addItem, removeItem आणि changeQuantity उघड करते; list private आहे.
  • अस्तित्वात असलेला SKU जोडल्यास quantities एकत्र होतात त्यामुळे पावतीवर डुप्लिकेट rows दिसत नाहीत.
  • Total items मधून काढला जातो, त्यामुळे ग्राहकाला जे दिसते त्याच्याशी तो कधीही विसंगत होऊ शकत नाही.
✅ परिणाम: दाखवलेला total आकारलेल्या रकमेपासून भरकटणारे pricing bugs नाहीसे होतात, कारण प्रत्येक बदल त्याच सत्याच्या स्रोतातून पुन्हा derive होतो.
🎵

2 · Music app: Playlist आणि तिचे tracks

Pattern: invariants म्हणून क्रम आणि मर्यादा

एका streaming playlist ने कमाल लांबी पाळली पाहिजे, क्रम जपला पाहिजे, आणि तोच track लगोलग दोनदा रोखला पाहिजे.

  • Playlist.addTrack insert करण्याआधी मर्यादा आणि लगतच्या-डुप्लिकेट-नको नियम तपासतो.
  • tracks एक read-only view परत करते जेणेकरून UI ला थेट स्थिती पुनर्क्रमित न करता render करता येते.
  • पुनर्क्रम ही एक method आहे जी एक index हलवते, callers वर विश्वास ठेवण्याऐवजी स्थान वैध ठेवते.
✅ परिणाम: client आणि server track क्रम आणि लांबीच्या मर्यादांवर सहमत होतात, कारण फक्त playlist च आपला क्रम बदलू शकते.
👥

3 · Collaboration tool: Team आणि तिचे members

Pattern: uniqueness आणि role invariants

एका workspace team मध्ये नेहमी किमान एक owner असला पाहिजे आणि तोच user कधीही दोनदा नोंदवला जाता कामा नये.

  • Team.addMember डुप्लिकेट नाकारतो आणि परवानगी असलेल्या मूल्यांशी role तपासतो.
  • removeMember शेवटचा owner काढण्यास नकार देतो, "नेहमी एक owner" invariant चे रक्षण करतो.
  • members प्रती परत करते, त्यामुळे permissions UI चुकून कोणालाही न उतरवता iterate करू शकते.
✅ परिणाम: अनाथ teams नाहीत आणि बिलावर डुप्लिकेट seats नाहीत, कारण membership नियम एकाच संरक्षित जागी लागू होतात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

कलेक्शन राखणे ही जुनी सोय नाही; concurrency, immutability आणि समृद्ध domain models अंतर्गत आधुनिक systems कशी बरोबर राहतात याचा तो पाया आहे.

🧱 Domain-driven aggregates

एक aggregate root आपले child कलेक्शन बाळगतो आणि ते बदलण्याचा एकमेव gateway असतो. कलेक्शन एन्कॅप्सुलेट करणे हाच अगदी तो मार्ग आहे ज्याने aggregates आपली सुसंगततेची सीमा सुरक्षित ठेवतात.

🧊 Immutability by default

Records, frozen dataclasses आणि readonly types elements ना देण्यास सुरक्षित बनवतात. प्रवृत्ती अशा वाचनांकडे आहे जे अक्षरशः बदलताच येत नाहीत.

🔁 Concurrency सुरक्षा

दोन threads मधून बदललेले लीक झालेले कलेक्शन म्हणजे data race. बदल संरक्षित methods च्या आत ठेवल्याने locking किंवा copy-on-write जोडण्यासाठी तुम्हाला एकच जागा मिळते.

🧪 Testability

जेव्हा स्थिती फक्त नाव असलेल्या methods मधूनच बदलते, तेव्हा तुम्ही private fields वर नव्हे तर वर्तनावर assert करता. Guards लहान, लक्ष्यित unit tests बनतात.

🌐 API आणि DTO सीमा

एखादी entity serialize करताना ती जिवंत model उघड न करता एक प्रत प्रक्षेपित करावी. जी शिस्त कलेक्शन राखते तीच wire format राखते.

♻️ Event sourcing

स्थिती methods मधून events लागू करून पुन्हा बांधली जाते, कधीही कलेक्शनला ढोसून नाही. विश्वासार्ह event log साठी एन्कॅप्सुलेशन ही पूर्वअट आहे.

सारांश: कलेक्शन म्हणजे data चा पोशाख घातलेले वर्तन. Container लपवा, प्रती किंवा read-only views द्या, आणि प्रत्येक बदल नियम राखणाऱ्या एका method मधून जाऊ द्या. तसे केले तर तुम्हाला कोण कॉल करते याची पर्वा न करता तुमचे invariants टिकतात.
