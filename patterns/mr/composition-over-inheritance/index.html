Composition over inheritance - सहकाऱ्यांपासून वर्तन घडवा

Inheritance म्हणते की एखादी वस्तू तिच्या पालकाचा is-a प्रकार आहे आणि पालकाचे आतडे प्रत्येक subclass मध्ये कॉपी करते. Composition म्हणते की वस्तूकडे has-a म्हणजे सहकाऱ्यांचा एक संच असतो, ज्यांच्याकडे ती काम सोपवते. Composition ला प्राधान्य दिल्याने वर्तन runtime वर बदलण्याजोगे राहते, base classes ठिसूळ होण्यापासून वाचतात, आणि खोल class वृक्षाऐवजी retry, auth आणि logging या भागांपासून HTTP client सारखी वैशिष्ट्ये जोडता येतात.

01 - काय

Composition over inheritance म्हणजे काय?

Composition over inheritance हे एक design मार्गदर्शक तत्त्व आहे: कोड पुन्हा वापरण्यासाठी एखाद्या वस्तूला base class पासून घेण्याऐवजी, ती वस्तू लहान सहकाऱ्यांपासून जोडणे आणि त्यांच्याकडे काम सोपवणे यास प्राधान्य द्या. base classes च्या साखळीचा विस्तार करणाऱ्या RetryingAuthenticatedHttpClient ऐवजी, तुम्ही एक HttpClient बनवता ज्याच्याकडे has a retry policy असते, has an auth provider असतो, आणि has a logger असतो, यातील प्रत्येक एक स्वतंत्र वस्तू असते जी तुम्ही बदलू शकता.

🧩 Has-a (composition)

एक वस्तू सहकाऱ्यांचे संदर्भ धरून ठेवते आणि काम त्यांच्याकडे पुढे पाठवते. वर्तन हे अशा भागांची बेरीज असते जे तुम्ही एका वेळी एक बदलू शकता.

🌳 Is-a (inheritance)

एक subclass base चा विस्तार करते आणि तिचे fields व methods वारशाने घेते. पुनर्वापर खरा असतो पण कठोर: तो compile time वर निश्चित होतो आणि संपूर्ण hierarchy मध्ये पसरतो.

🔁 Delegation

ही अशी यंत्रणा जी composition ला कार्यरत करते: host वरील एक method धरून ठेवलेल्या सहकाऱ्यावर तीच किंवा संबंधित method कॉल करते आणि निकाल परत बाहेर पाठवते.

मुख्य मानसिक प्रतिमा: inheritance तुम्हाला पालक कसा बनवला आहे याच्याशी बांधते; composition तुम्हाला फक्त सहकारी काय देण्याचे वचन देतो याच्याशी बांधते. सहकारी उघड करत असलेल्या interface शी program करा आणि मग class वृक्ष पुन्हा लिहून नव्हे, तर भाग बदलून तुम्ही वर्तन नव्याने घडवू शकता.
02 - का

Composition ला प्राधान्य का द्यावे

Inheritance ही object orientation मधील सर्वात घट्ट coupling आहे: एक subclass base च्या public API वर, तिच्या protected सदस्यांवर, आणि बहुधा तिच्या खासगी कॉल क्रमावर अवलंबून असते. Composition ती लपलेली coupling स्पष्ट, बदलण्याजोग्या सहकाऱ्यांशी अदलाबदल करते.

🔧 Runtime वर बदलण्याजोगे

Client ला हात न लावता चाचण्यांमध्ये HttpClient ला NoRetry policy द्या आणि production मध्ये ExponentialBackoff policy द्या. Inheritance प्रत्येक संयोजनासाठी नवीन subclass सक्तीने लादेल.

🧱 संयोजनांचा स्फोट नाही

Retry, auth आणि logging हे तीन सहकारी कोणत्याही मिश्रणात जुळतात. Subclasses म्हणून ते वाढतात: authenticated-retrying, logged-retrying, logged-authenticated, आणि असेच पुढे.

🛡️ Fragile base class टाळते

सहकारी फक्त एकमेकांचा public करार पाहतात, त्यामुळे एकाचा अंतर्गत refactor दुसऱ्याला नकळत तोडू शकत नाही, जसे base class बदल तिच्या subclasses ना तोडतो.

🧪 स्वतंत्रपणे चाचणी करणे सोपे

Constructor मध्येच थेट एक बनावट auth provider किंवा नोंद करणारा logger पाठवा. चाचणी करत असलेल्या unit ला subclass करण्याची गरज नाही, तिचे निरीक्षण करण्यासाठी protected hooks override करण्याची गरज नाही.

सोप्या शब्दांत

उपमांसह समजावलेले composition over inheritance

तीच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती पटकन समजते.

🎓 विद्यार्थ्यासाठी

Inheritance म्हणजे कुटुंबाची पाककृती वारशाने घेणे, जी तुम्ही बदलल्यास ती वारशाने घेतलेल्या प्रत्येक चुलत भावंडावर परिणाम होतो. Composition म्हणजे वेगवेगळ्या मसाल्याच्या बरण्या ठेवणे: कोणत्या या पदार्थात घालायच्या ते तुम्ही निवडता आणि केव्हाही मीठ बदलून मिरी घालू शकता.

👩‍💻 डेव्हलपरसाठी

Retry base चा विस्तार करणारा HttpClient त्याला वेल्ड केलेला असतो. आपल्या constructor मध्ये RetryPolicy घेणारा HttpClient हा जोडलेला असतो, वेल्ड केलेला नाही: तुम्ही प्रत्येक वातावरणासाठी त्याची जोडणी पुन्हा करता.

🏢 व्यावसायिकासाठी

Inheritance म्हणजे एक कठोर org chart जिथे प्रत्येक संघाला पालक विभाग सांगतो तसेच करावे लागते. Composition म्हणजे तज्ज्ञ कंत्राटदार नेमणे: प्रकल्पाकडे एक सुरक्षा कंपनी, एक auditor आणि एक courier असतो, आणि कंपनीची पुनर्रचना न करता कोणालाही बदलता येते.

🔌 रोजच्या जीवनातील आवृत्ती

एक power strip दिव्यापासून वारसा घेत नाही. ती उपकरणे प्लग-इन करते. Composition म्हणजे तो socket: तुम्ही जे काही प्लग-इन कराल ते वर्तन पुरवते, आणि एक गोष्ट अनप्लग केल्याने इतर कधीच तुटत नाहीत.

03 - कसे

आतील पातळीवर हे कसे कार्य करते

मुख्य हालचाल म्हणजे प्रत्येक cross-cutting काळजीला तिचा स्वतःचा लहान interface म्हणून नाव देणे, मग त्या interfaces चे instances host मध्ये धरून ठेवणे आणि त्यांच्याकडे delegate करणे. Host समन्वय साधतो; सहकारी विशेष काम करतात.

📇 सहकाऱ्यांचे करार परिभाषित करा

प्रत्येक काळजीला एक अरुंद interface मिळतो: RetryPolicy.run(op), AuthProvider.authorize(req), RequestLogger.log(req, res). Host या interfaces वर अवलंबून असतो, ठोस classes वर नव्हे.

🔗 Inject करा आणि delegate करा

Host आपल्या constructor द्वारे सहकारी स्वीकारतो आणि send() मध्ये त्यांना कॉल करतो. वर्तन बदलणे म्हणजे वेगळे implementation पाठवणे, host कधीच संपादित न करता.

Composition विरुद्ध inheritance, तीन भाषांमध्ये

// Collaborator contracts
interface AuthProvider { authorize(req: Request): Request; }
interface RetryPolicy { run<T>(op: () => Promise<T>): Promise<T>; }
interface RequestLogger { log(req: Request, res: Response): void; }

class BearerTokenAuth implements AuthProvider {
  constructor(private token: string) {}
  authorize(req: Request): Request {
    req.headers.set("Authorization", `Bearer ${this.token}`);
    return req;
  }
}

class ExponentialBackoff implements RetryPolicy {
  constructor(private tries = 3, private baseMs = 100) {}
  async run<T>(op: () => Promise<T>): Promise<T> {
    for (let attempt = 1; ; attempt++) {
      try { return await op(); }
      catch (err) {
        if (attempt >= this.tries) throw err;
        await new Promise(r => setTimeout(r, this.baseMs * 2 ** attempt));
      }
    }
  }
}

class ConsoleLogger implements RequestLogger {
  log(req: Request, res: Response): void {
    console.log(`${req.method} ${req.url} -> ${res.status}`);
  }
}

// The host HAS-A each collaborator and delegates to it.
class HttpClient {
  constructor(
    private auth: AuthProvider,
    private retry: RetryPolicy,
    private logger: RequestLogger,
  ) {}

  async send(req: Request): Promise<Response> {
    const authed = this.auth.authorize(req);              // delegate auth
    const res = await this.retry.run(() => fetch(authed)); // delegate retry
    this.logger.log(authed, res);                         // delegate logging
    return res;
  }
}

// Assemble by wiring parts; swap any part without a new subclass.
const client = new HttpClient(
  new BearerTokenAuth(process.env.API_TOKEN!),
  new ExponentialBackoff(4, 200),
  new ConsoleLogger(),
);
const res = await client.send(new Request("https://api.example.com/v1/orders"));

from __future__ import annotations
from typing import Protocol, Callable, TypeVar
import os, time

T = TypeVar("T")

# Collaborator contracts
class AuthProvider(Protocol):
    def authorize(self, req: Request) -> Request: ...

class RetryPolicy(Protocol):
    def run(self, op: Callable[[], T]) -> T: ...

class RequestLogger(Protocol):
    def log(self, req: Request, res: Response) -> None: ...

class BearerTokenAuth:
    def __init__(self, token: str) -> None:
        self._token = token
    def authorize(self, req: Request) -> Request:
        req.headers["Authorization"] = f"Bearer {self._token}"
        return req

class ExponentialBackoff:
    def __init__(self, tries: int = 3, base_ms: int = 100) -> None:
        self._tries, self._base_ms = tries, base_ms
    def run(self, op: Callable[[], T]) -> T:
        attempt = 1
        while True:
            try:
                return op()
            except Exception:
                if attempt >= self._tries:
                    raise
                time.sleep(self._base_ms * 2 ** attempt / 1000)
                attempt += 1

class ConsoleLogger:
    def log(self, req: Request, res: Response) -> None:
        print(f"{req.method} {req.url} -> {res.status}")

# The host HAS-A each collaborator and delegates to it.
class HttpClient:
    def __init__(self, auth: AuthProvider, retry: RetryPolicy, logger: RequestLogger) -> None:
        self._auth, self._retry, self._logger = auth, retry, logger

    def send(self, req: Request) -> Response:
        authed = self._auth.authorize(req)                 # delegate auth
        res = self._retry.run(lambda: do_fetch(authed))    # delegate retry
        self._logger.log(authed, res)                      # delegate logging
        return res

# Assemble by wiring parts; swap any part without a new subclass.
client = HttpClient(
    BearerTokenAuth(os.environ["API_TOKEN"]),
    ExponentialBackoff(tries=4, base_ms=200),
    ConsoleLogger(),
)
res = client.send(Request("GET", "https://api.example.com/v1/orders"))

# Collaborator contracts are duck-typed: any object answering the
# right message plays the role. No base class needed.

class BearerTokenAuth
  def initialize(token) = @token = token
  def authorize(req)
    req.headers["Authorization"] = "Bearer #{@token}"
    req
  end
end

class ExponentialBackoff
  def initialize(tries: 3, base_ms: 100)
    @tries, @base_ms = tries, base_ms
  end

  def run
    attempt = 1
    begin
      yield
    rescue => e
      raise e if attempt >= @tries
      sleep(@base_ms * 2**attempt / 1000.0)
      attempt += 1
      retry
    end
  end
end

class ConsoleLogger
  def log(req, res) = puts("#{req.method} #{req.url} -> #{res.status}")
end

# The host HAS-A each collaborator and delegates to it.
class HttpClient
  def initialize(auth:, retry:, logger:)
    @auth, @retry, @logger = auth, retry, logger
  end

  def send(req)
    authed = @auth.authorize(req)            # delegate auth
    res = @retry.run { do_fetch(authed) }    # delegate retry
    @logger.log(authed, res)                 # delegate logging
    res
  end
end

# Assemble by wiring parts; swap any part without a new subclass.
client = HttpClient.new(
  auth:   BearerTokenAuth.new(ENV.fetch("API_TOKEN")),
  retry:  ExponentialBackoff.new(tries: 4, base_ms: 200),
  logger: ConsoleLogger.new,
)
res = client.send(Request.new(:get, "https://api.example.com/v1/orders"))

Host चा send() कोणती retry किंवा auth धोरण तो धरून आहे हे कधीच जाणत नाही; तो फक्त पाठवायचा संदेश जाणतो. हेच delegation आहे: वर्तन जोडणीद्वारे निवडले जाते, त्यामुळे प्रत्येक संयोजनासाठी subclass वाढवण्याऐवजी फक्त constructor argument बदलून तोच class test, staging आणि production व्यापतो.

वर्तन सहकाऱ्यांमध्ये हलवा

Auth तर्क base मधून बाहेर काढून BearerTokenAuth मध्ये घाला; retry आणि logging साठी तेच करा. प्रत्येक एक स्वतंत्र class बनतो.

40
धरून ठेवा

Host ला has-a fields द्या

HttpClient आता ठोस नव्हे तर interfaces नुसार typed केलेले auth, retry आणि logger field साठवतो.

50
Inject करा

Constructor मध्ये सहकारी स्वीकारा

Host आपले भाग argument म्हणून घेतो, त्यामुळे कोणती implementations जोडायची हे caller ठरवतो.

60
Delegate करा

send() मध्ये काम पुढे पाठवा

send() प्रथम auth.authorize, मग retry.run, मग logger.log कॉल करतो. Host समन्वय साधतो; भाग काम करतात.

70
हटवा

Subclass वृक्ष कोसळवा

विशेष-प्रकरणाच्या subclasses नाहीशा होतात. एकच HttpClient आता जोडणीद्वारे प्रत्येक संयोजन व्यापतो.

80
बदला

प्रत्येक वातावरणासाठी पुनर्रचना करा

चाचण्यांमध्ये NoRetry आणि NullLogger जोडा, production मध्ये ExponentialBackoff आणि structured logger जोडा. सर्वत्र तोच class.

90
चाचणी करा

बनावट inject करा आणि पडताळणी करा

Subclass न करता किंवा network ला हात न लावता client पडताळण्यासाठी नोंद करणारा logger आणि stub auth पाठवा.

100
निर्णय घ्या

Inheritance जिथे कमावते तिथे ठेवा

स्थिर, पातळ base आणि खऱ्या substitutability सह खऱ्या is-a subtypes साठी, inheritance अजूनही योग्य आहे. ते जाणीवपूर्वक वापरा, आपोआप नव्हे.

सामान्य धोके

धोके आणि anti-patterns

Composition फुकट नाही; निष्काळजीपणे केल्यास ते एका गोंधळाची जागा दुसऱ्या गोंधळाने घेते. या गोष्टींकडे लक्ष द्या.

🏗️ फक्त पुनर्वापरासाठी inheritance

खरा is-a संबंध नसताना, फक्त काही methods उधार घेण्यासाठी subclass करणे हा उत्कृष्ट गैरवापर आहे. जर मूल पालकाच्या जागी वापरता येत नसेल, तर त्याने वर्तन धरून ठेवावे, वारशाने घेऊ नये.

🧨 Fragile base class

जो base अंतर्गतरीत्या आपल्याच override करण्याजोग्या methods कॉल करतो, तो एका खासगी refactor ला प्रत्येक subclass नकळत तोडू देतो. जितके अधिक subclasses protected अंतर्गत भागांत हात घालतात, तितके ते वाईट होते.

🪆 खोल hierarchies

Extends चे चार-पाच स्तर वर्तन शोधणे अशक्य करतात: एक कॉल काय करतो हे समजण्यासाठी तुम्हाला संपूर्ण साखळी वाचावी लागते. सहकाऱ्यांमध्ये सपाट करा.

🕸️ Composition मार्फत god object

Composition एक monolith देखील लपवू शकते: पंधरा सहकारी धरून ठेवणारा आणि त्या सर्वांचे समन्वय साधणारा host म्हणजे अतिरिक्त indirection असलेला मातीचा मोठा गोळाच. Hosts एकाग्र ठेवा.

🔁 Boilerplate delegation

धरून ठेवलेल्या वस्तूकडे वीस methods हाताने पुढे पाठवणे कंटाळवाणे आणि चुका-प्रवण असते. त्याऐवजी भाषेची delegation वैशिष्ट्ये (Ruby Forwardable, Kotlin by) किंवा एक पातळ facade वापरा.

🧬 Mixin टकराव

दोन mixins जे दोन्ही save परिभाषित करतात किंवा दोन्ही एकाच state ला स्पर्श करतात, ते आश्चर्यकारक method resolution order bugs निर्माण करतात. Mixins लहान, ऑर्थोगोनल आणि namespaced ठेवा.

संकेत आणि मापदंड

संकेत आणि कसे मोजावे

तुम्ही design मार्गदर्शक तत्त्वाची unit-test करू शकत नाही, पण एखादी hierarchy बिघडली आहे का आणि composition मदत करेल का हे हे संकेत सांगतात.

संकेततो तुम्हाला काय सांगतो
Inheritance खोली (DIT)खोल वृक्षांबद्दल विचार करणे कठीण असते; तीन-चार स्तरांपुढे झेप बहुधा reuse-by-inheritance दर्शवते, जे composition सपाट करेल.
संयोजनांसाठी subclass संख्याजर N वैशिष्ट्ये साधारण 2^N subclasses निर्माण करत असतील, तर तुम्ही संयोजनात्मक कर भरत आहात जो composition काढून टाकते.
ठराविक क्रमात super कॉल करणारे overridesBase च्या अंतर्गत कॉल क्रमावर अवलंबून असलेले subclasses म्हणजे कधीही उफाळणारा fragile-base-class धोका.
Protected सदस्य पृष्ठभागरुंद protected API म्हणजे subclasses अंतर्गत भागांत हात घालतात; base सुरक्षितपणे विकसित होऊ शकत नाही. तो अरुंद करा आणि composition ला प्राधान्य द्या.
चाचणी सेटअपची गुंतागुंतजर एका class ची चाचणी करण्यासाठी तिला subclass करावे लागते किंवा protected hooks override करावे लागतात, तर तिचे वर्तन injectable नाही आणि composition ते सोपे करेल.
वृक्षभर बदलाची लाटएका base संपादनामुळे अनेक subclasses मध्ये संपादने करावी लागणे हे घट्ट structural coupling दर्शवते, जे बदलण्याजोगे सहकारी टाळतात.
अंगठ्याचा नियम: जर प्रस्तावित subclass Liskov चाचणी अपयशी करेल (base अपेक्षित असेल तिथे सर्वत्र तो वापरता येत नाही), किंवा फक्त कोड पुन्हा वापरण्यासाठी अस्तित्वात असेल, तर त्याऐवजी त्याचे has-a सहकारी म्हणून प्रतिरूपण करा. खऱ्या, पातळ, स्थिर is-a subtypes साठी inheritance राखून ठेवा.
06 - प्रकरण अभ्यास

वास्तविक जगातील प्रकरण अभ्यास

तीन production-शैलीच्या प्रणाली जिथे composition ने class hierarchy ला मात दिली.

🔌

1 · एक HTTP API client SDK

Pattern: retry, auth आणि logging सहकाऱ्यांपासून client जोडा

एका payments SDK ची सुरुवात प्रत्येक auth योजना आणि retry वर्तनाच्या संयोजनासाठी subclass केलेल्या BaseClient ने झाली, आणि वृक्ष असंभाळण्याजोगा बनला.

  • Auth, retry आणि instrumentation client धरून ठेवणाऱ्या injectable interfaces मध्ये बाहेर काढले गेले.
  • Sandbox आणि live modes दोन subclasses नव्हे तर एकाच HttpClient च्या दोन जोडण्या बनल्या.
  • नवीन auth योजना client मध्ये शून्य बदलांसह नवीन AuthProvider implementations म्हणून पाठवल्या गेल्या.
✅ निष्पत्ती: Subclass वृक्ष एकाच client class पर्यंत कोसळला, आणि वैशिष्ट्ये जोडणे inheritance शस्त्रक्रियेऐवजी जोडणी बनले.
📊

2 · एक reporting आणि export engine

Pattern: एका Report कडे has-a datasource आणि एक formatter असतो

एका analytics platform ने प्रथम reports ला Report चा विस्तार करणारे SalesReport चा विस्तार करणारे PdfSalesReport असे प्रतिरूपित केले, जे formats आणि sources वाढल्याने स्फोट पावले.

  • एक Report आता एक DataSource आणि एक OutputFormatter धरून ठेवतो, fetch आणि render त्यांच्याकडे delegate करतो.
  • CSV, PDF आणि XLSX तीन formatters बनले; warehouse आणि API दोन datasources बनले.
  • कोणताही source runtime वर कोणत्याही format शी जुळतो, प्रत्येक जोडीसाठी नवीन class नाही.
✅ निष्पत्ती: Format-गुणिले-source संयोजने भागांच्या एका लहान संचात बदलली, आणि नवीन export format म्हणजे वृक्षाची नवीन फांदी नव्हे तर एक class बनले.
🔔

3 · एक notification service

Pattern: channel hierarchy ऐवजी mixins आणि channel सहकारी

एका messaging प्रणालीत Notification वृक्षाचा विस्तार करणारा EmailNotification होता, ज्यात retry आणि templating दुहेरी होते किंवा अवघडपणे base मध्ये ढकलले होते.

  • Channels (email, SMS, push) sender धरून ठेवणारे अदलाबदल करण्याजोगे Channel सहकारी बनले.
  • Timestamping आणि rate limiting सारख्या cross-cutting काळज्या base methods नव्हे तर लहान mixins बनल्या.
  • एक digest sender फक्त अनेक channels धरून ठेवून त्यांना पसरवत असे, नवीन subclass ची गरज नाही.
✅ निष्पत्ती: Slack channel जोडणे म्हणजे एक नवीन Channel class होते, आणि फुगणाऱ्या base ऐवजी सामायिक वर्तन एकाग्र mixins मध्ये राहिले.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Composition over inheritance बहुतेक frameworks पेक्षा जुने आहे, तरीही आधुनिक भाषा आणि platform design ते अधिकाधिक मुख्य प्रवाहात ढकलत राहते.

🧵 Traits आणि protocols

Rust traits, Swift protocol extensions, आणि Go चे interface embedding class hierarchy शिवायच composition-शैलीचा पुनर्वापर देतात, has-a ला default बनवतात.

💉 सर्वत्र dependency injection

Spring, NestJS आणि .NET मधील DI containers नेमके सहकाऱ्यांना hosts मध्ये जोडण्यासाठी अस्तित्वात आहेत, संपूर्ण codebases मध्ये composition pattern चे औद्योगिकीकरण करतात.

🎛️ Delegation एक keyword म्हणून

Kotlin चे by आणि Ruby चे Forwardable delegation ला first class बनवतात, एकेकाळी composition ला inheritance पेक्षा जड वाटायला लावणारे boilerplate काढून टाकतात.

⚛️ UI frameworks मधील composition

React आणि आधुनिक component प्रणालींनी inheritance-आधारित UI ला composed components आणि hooks ने बदलले, is-a पेक्षा has-a चा मोठ्या प्रमाणावरील पुरस्कार.

🧩 Entity-component प्रणाली

Game आणि simulation engines खोल class वृक्षांऐवजी जोडलेल्या components पासून entities बनवतात, runtime वर composition चे शुद्धतम रूप.

🌳 Inheritance, जाणीवपूर्वक राखलेले

Sealed classes आणि interfaces खऱ्या is-a प्रतिरूपणासाठी जागा राखतात, त्यामुळे भविष्य शून्य inheritance नाही तर हेतुपुरस्सर वापरलेले inheritance आहे.

सारांश: वर्तन बदलण्याजोगे, चाचणीयोग्य आणि fragile-base-class तुटीपासून सुरक्षित ठेवण्यासाठी composition ला प्राधान्य द्या, आणि खऱ्या, पातळ, बदलण्याजोग्या is-a संबंधांसाठी inheritance राखून ठेवा. आधी सहकाऱ्यांपासून वस्तू जोडा; subtype संबंध खरा असेल तेव्हाच base चा विस्तार करा.
