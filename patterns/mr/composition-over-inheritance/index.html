Composition over inheritance - वर्तन extend करून नव्हे, तर जोडून तयार करा

Inheritance एका subclass ला त्याच्या parent च्या प्रत्येक तपशीलाशी बांधून टाकते, त्यामुळे झाडाच्या वरच्या भागातील एक बदल खाली पसरतो आणि कोणालाही आठवत नसलेले classes मोडतो. Composition हे उलटे करते: एखादी base class असण्याऐवजी, एखादा object त्याच्याकडे असलेल्या collaborators कडे delegate करतो, म्हणजे तो त्यांना बाळगतो. तुम्ही वर्तन runtime ला एकत्र जोडता, तुकडे मुक्तपणे बदलता, आणि प्रत्येक भाग लहान व testable ठेवता.

01 - काय

Composition over inheritance म्हणजे काय?

Composition over inheritance हे एक design मार्गदर्शक तत्त्व आहे जे सांगते: एखादा type तो extend करणाऱ्या base class मधून (is-a नाते) तयार करण्याऐवजी, तो बाळगून delegate करणाऱ्या लहान objects मधून (has-a नाते) तयार करणे अधिक चांगले. दोन्ही पद्धती code पुन्हा वापरतात, पण inheritance संपूर्ण implementation वारसा म्हणून घेऊन पुन्हा वापरते, तर composition स्वतंत्र तुकडे एकत्र जोडून पुन्हा वापरते. हे मार्गदर्शक तत्त्व अस्तित्वात आहे कारण खोल inheritance झाडे कठोर ठरतात, तर जोडलेले objects लवचिक राहतात.

🧬 Inheritance (is-a)

एक subclass एका base class ला extend करते आणि तिचे fields व methods वारसा म्हणून घेते. मजबूत, static coupling: मूल त्याच्या parent च्या internals वर अवलंबून असते आणि compile time ला निश्चित होते.

🧩 Composition (has-a)

एक object collaborator objects चे references बाळगतो आणि काम त्यांच्याकडे पुढे पाठवतो. Interfaces मार्फत सैल coupling: तुकडे बदलता येतात, अगदी runtime लाही.

🔀 Delegation

Composition ला कार्यरत करणारी यंत्रणा: एक method त्याच method ला एका बाळगलेल्या collaborator वर call करते, त्यामुळे बाहेरचा object स्वतः न बनवलेले वर्तन उघड करतो.

02 - का

Composition ला प्राधान्य का

Inheritance हे object-oriented programming मधील सर्वात घट्ट coupling आहे: एक subclass protected members पाहते, call च्या क्रमावर अवलंबून असते, आणि तिला हवे असो वा नसो, सर्व काही वारसा म्हणून घेते. हेच खोल hierarchies ला ठिसूळ बनवते. Composition ती कठोरता लवचिकतेच्या बदल्यात देते.

🧱 Fragile base class पासून सुटका

जेव्हा वर्तन interfaces मागच्या collaborators मध्ये राहते, तेव्हा एक बदलल्याने subclasses गुपचूप मोडत नाहीत. बदल त्या तुकड्यापुरता मर्यादित राहतो जो त्याचा मालक आहे, झाडाखाली पसरण्याऐवजी.

🔧 Runtime ला लवचिक

Program चालू असताना तुम्ही एक collaborator बदलू शकता, किंवा अनेक रचू शकता. Inheritance तुम्ही compile करताच निश्चित होते; composition configuration आणि dependency injection ला वर्तन ठरवू देते.

🚫 Diamond समस्या टाळते

Single inheritance बेढब hierarchies ला भाग पाडते आणि multiple inheritance संदिग्ध method resolution तयार करते. अनेक collaborators बाळगल्याने तुम्हाला शून्य संदिग्धतेसह अनेक वर्तने मिळतात.

🧪 test करणे सोपे

प्रत्येक collaborator लहान असतो आणि त्याच्या interface मार्फत mock करता येतो. तुम्ही एक unit वेगळ्याने test करता, पाच-स्तरीय base class लपलेल्या state व setup सह ओढून आणण्याऐवजी.

सोप्या शब्दांत

Composition over inheritance उपमांसह समजावून सांगितले

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असा तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

Inheritance म्हणजे संपूर्ण निबंध कॉपी करणे आणि काही ओळी बदलणे - जर मूळात चूक असेल, तर तुमच्यातही असेल. Composition म्हणजे स्रोत उद्धृत करणे: तुम्हाला हवे तेच परिच्छेद तुम्ही आणता आणि संपूर्ण पेपर पुन्हा न लिहिता एक स्रोत बदलता.

👩‍💻 developer साठी

Inheritance म्हणजे extends BaseController आणि base अपेक्षेप्रमाणे वागेल अशी आशा करणे. Composition म्हणजे एक Logger, एक Validator, आणि एक Repository inject करणे - प्रत्येक एक interface जो तुम्ही बाकीच्याला हात न लावता mock, बदलू, किंवा पुन्हा क्रमबद्ध करू शकता.

🏢 व्यावसायिकासाठी

Inheritance म्हणजे एक कठोर संघटन तक्ता जिथे प्रत्येकजण एका निश्चित साखळीत वर अहवाल देतो. Composition म्हणजे तज्ज्ञांमधून जमवलेली एक प्रकल्प टीम: तुम्ही कामासाठी योग्य लोक आणता आणि काम झाल्यावर विसर्जित करता.

🔌 दैनंदिन आवृत्ती

वेल्ड केलेली battery असलेला फोन म्हणजे inheritance: काहीतरी बदलावे लागेपर्यंत स्वस्त, मग तुम्ही संपूर्ण उपकरण बदलता. plug-in उपकरणे असलेला फोन म्हणजे composition: तुम्हाला हवे तेव्हा नवीन charger, case, किंवा lens क्लिक करून जोडा.

03 - कसे

आतल्या बाजूने ते कसे कार्य करते

ही हालचाल यांत्रिक आहे: जे वर्तन पूर्वी base class मध्ये राहत होते ते घ्या, ते एका interface मागे ठेवा, ते लहान classes मध्ये implement करा, आणि बाहेरच्या object ने parent extend करण्याऐवजी त्यांपैकी एकाला बाळगून delegate करा.

🧬 Inheritance design

एक Bird base class fly() परिभाषित करते. मग एक पेंग्विन येतो जो उडू शकत नाही, एक शहामृग जो धावतो, एक पक्षी जो पोहतो. Hierarchy विशेष प्रकरणांमध्ये आणि exceptions फेकणाऱ्या overrides मध्ये तुटते.

🧩 Composition design

FlyBehavior, SwimBehavior interfaces परिभाषित करा. एका पक्ष्याकडे एक fly strategy आणि एक swim strategy असते. पेंग्विनला NoFly आणि StrongSwim मिळते - कोणतेही exceptions नाहीत, कोणतेही मोडलेले करार नाहीत.

रचना - डावीकडे एक कठोर झाड, उजवीकडे बदलता येणारी वर्तने बाळगणारा object

तीच समस्या, TypeScript मध्ये दोन designs

// INHERITANCE: rigid, and Penguin is forced to lie about fly()
abstract class Bird {
  eat(): string { return "peck peck"; }
  fly(): string { return "flap and take off"; }
}
class Duck extends Bird {}
class Penguin extends Bird {
  // A penguin is-a Bird, but cannot fly -> the contract breaks
  override fly(): string { throw new Error("penguins can't fly"); }
}

// COMPOSITION: behavior is injected, so no class ever lies
interface FlyBehavior { fly(): string; }
class WingFly  implements FlyBehavior { fly() { return "flap and take off"; } }
class NoFly    implements FlyBehavior { fly() { return "stays grounded"; } }

class Animal {
  // has-a, not is-a: the fly behavior is a collaborator
  constructor(private readonly flyer: FlyBehavior) {}
  move(): string { return this.flyer.fly(); }   // delegation
  setFlyer(f: FlyBehavior) { /* swap at runtime */ }
}

const duck    = new Animal(new WingFly());   // "flap and take off"
const penguin = new Animal(new NoFly());     // "stays grounded" - honest, no throw

लक्षात घ्या की जोडलेला Animal कधीच काहीही override करत नाही आणि कधीच throw करत नाही. वर्तन constructor मार्फत पुरवले जाते आणि setFlyer ने बदलता येते - नेमकी तीच लवचिकता जी एक निश्चित extends नाते देऊ शकत नाही.

सामान्य अडचणी

अडचणी आणि anti-patterns

Inheritance आणि composition दोन्हींचा गैरवापर होऊ शकतो. या अशा सापळ्या आहेत ज्या वास्तविक code मध्ये सर्वात जास्त दिसतात.

🕳️ खोल inheritance hierarchies

पाच किंवा सहा स्तरांचे extends म्हणजे एका method call ने संपूर्ण झाडात विखुरलेला code चालतो. कोणीही त्याबद्दल विचार करू शकत नाही, आणि कोणताही base बदल म्हणजे भूसुरुंग. Composition ने ते सपाट करा.

🧱 Fragile base class

एक base method किंवा त्याचा call क्रम बदलल्याने जुन्या वर्तनावर अवलंबून असलेल्या subclasses गुपचूप मोडतात. parent सुरक्षितपणे विकसित होऊ शकत नाही कारण तो प्रत्येक मुलाशी coupled आहे.

💎 diamond कडे झुकणे

Multiple inheritance जिथे दोन मार्ग एकाच पूर्वजापर्यंत पोहोचतात, तिथे संदिग्ध method आणि state resolution तयार होते. भाषा त्यावर बंदी घालतात किंवा त्याला गुंतागुंतीचे करतात, ते चांगल्या कारणासाठी - त्याऐवजी compose करा.

🎭 फक्त code पुनर्वापरासाठी inheritance

फक्त एक helper method मिळवण्यासाठी class extend करणे तुम्हाला अभिप्रेत नसलेला is-a दावा करण्यास भाग पाडते. तुम्ही त्याची संपूर्ण पृष्ठभाग आणि coupling वारसा म्हणून घेता. त्याला collaborator म्हणून बाळगणे अधिक चांगले.

🧨 Liskov उल्लंघने

एखादी method throw करण्यासाठी किंवा करार कमकुवत करण्यासाठी override करणे, जसे Penguin.fly() throw करणे, substitutability मोडते. base type च्या callers ना आश्चर्ये मिळतात. हे is-a चुकीचे होते याचे लक्षण आहे.

🍝 Delegation boilerplate

Composition दुसऱ्या दिशेने वाहू शकते: फक्त calls पुढे पाठवण्यासाठी डझनभर एक-ओळीच्या pass-through methods. ते सुटसुटीत ठेवण्यासाठी भाषेची delegation वैशिष्ट्ये, interfaces, किंवा एक decorator base वापरा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Composition हा एक default आहे, नियम नव्हे. एखादी hierarchy refactor करण्यापूर्वी किंवा एखाद्या base class कडे झुकण्यापूर्वी या गोष्टींचा विचार करा.

पैलूतपशील
फायदेसैल coupling, runtime लवचिकता, लहान testable units, fragile base class नाही, diamond समस्या टाळते, open-closed principle चा सन्मान करते.
तोटेसुरुवातीला अधिक classes आणि interfaces, delegation boilerplate, indirection एका साध्या प्रवाहाला अस्पष्ट करू शकते, wiring constructors किंवा एका DI container कडे जाते.
केव्हा वापरावेजेव्हा वर्तन प्रकरणांनुसार बदलते, runtime ला बदलण्याची गरज असते, खोल किंवा ठिसूळ झाड तयार होईल, किंवा नाते खरोखर has-a किंवा can-do असते.
केव्हा टाळावेsubtype खरा, स्थिर is-a असेल, तुम्हाला खरी polymorphic substitutability हवी असेल, किंवा एखादी template-method framework तुम्ही base class extend करावी अशी अपेक्षा करते.
गुंतागुंतसंकल्पनेत कमी, wiring मध्ये मध्यम. काही अतिरिक्त types च्या बदल्यात नंतरचा बदल खूप सोपा देते - क्षुल्लक प्रकरणांपलीकडे सहसा एक चांगला सौदा.
संबंधितStrategy, Decorator, Bridge, आणि Adapter हे सर्व कृतीतील composition आहेत; SOLID चे dependency-inversion आणि open-closed principles त्याला प्रेरित करतात.
ढोबळ नियम: inheritance कडे तेव्हाच झुका जेव्हा subtype एक खरा, कायमचा is-a असतो जो तुम्ही आश्चर्याशिवाय त्याच्या base च्या जागी वापराल. जे फक्त वर्तन पुन्हा वापरते किंवा बदलते त्या प्रत्येक गोष्टीसाठी, compose आणि delegate करा. Default म्हणून composition ला अनुकूलता द्या, समर्थनासह inheritance ला परवानगी द्या.
06 - उदाहरण अभ्यास

वास्तविक जगातील उदाहरण अभ्यास

तीन ठिकाणे जिथे inheritance ऐवजी composition निवडल्याने परिणाम बदलला.

🎮

1 · component systems मार्फत game entities

Pattern: entity-component composition

सुरुवातीच्या game engines ने Enemy extends Character extends GameObject सारखी खोल class झाडे वापरली, मग जेव्हा एका खोक्याला AI नव्हे तर physics हवे होते तेव्हा ती मोडली.

  • वर्तन components मध्ये विभागले: Position, Render, Physics, AI, प्रत्येक एका entity ने बाळगलेले.
  • एक नवा entity प्रकार म्हणजे components ची एक नवी पिशवी, कठोर झाडातील एक नवा subclass नव्हे.
  • Designers programmer ने hierarchy संपादित न करता runtime ला क्षमता मिसळतात.
✅ परिणाम: Entity-component-system architecture उद्योगाचा प्रमाण बनला कारण जिथे inheritance combinatorially फुटले तिथे composition scale झाले.
☕

2 · Java I/O streams

Pattern: Decorator, गुंडाळून composition

Java ला प्रत्येक संयोजनासाठी एक class न बनवता कोणत्याही stream वर buffering, compression, आणि encryption हवे होते.

  • BufferedInputStream दुसऱ्या InputStream ला गुंडाळते आणि त्याला delegate करते.
  • तुम्ही wrappers रचता: file stream भोवती gzip, त्याभोवती buffer, runtime ला जोडलेले.
  • एक क्षमता जोडणे म्हणजे एक नवा decorator, प्रत्येक stream प्रकाराचा subclass नव्हे.
✅ परिणाम: मूठभर composable decorators प्रत्येक संयोजन कव्हर करतात, stream subclasses चा एक प्रचंड inheritance matrix टाळतात.
🛒

3 · payment आणि pricing strategies

Pattern: Strategy, inject केलेले वर्तन

एक checkout service CreditCardOrder extends Order ने सुरू झाली आणि झाड अव्यवस्थापनीय होईपर्यंत प्रत्येक payment व discount नियमासाठी एक subclass मिळवत गेली.

  • PaymentMethod आणि DiscountPolicy हे order बाळगणारे interfaces बनले.
  • एका order ला निर्मितीच्या वेळी एक payment strategy आणि एक discount strategy सह configure केले जाते.
  • नव्या जाहिराती आणि providers हे नवे strategy classes आहेत, Order ला हात न लावता inject केलेले.
✅ परिणाम: order class बदलणे थांबले, tests ने प्रत्येक strategy वेगळ्याने mock केली, आणि नवे payment पर्याय regression धोक्याशिवाय पाठवले गेले.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

जुनाट असण्यापासून दूर, composition over inheritance आधुनिक भाषा, frameworks, आणि प्रतिमाने कशी design केली जातात याचा पाया आहे.

🧵 Traits आणि mixins मुख्य प्रवाहात

Rust traits, Scala traits, आणि TypeScript mixins तुम्हाला base class शिवाय क्षैतिज वर्तन compose करू देतात, ज्यामुळे composition हा सोयीस्कर default बनतो.

🚫 Go आणि Rust inheritance सोडतात

Go कडे struct embedding आणि interfaces आहेत, Rust कडे traits आहेत, आणि दोघेही class inheritance अजिबात देत नाहीत - composition वर एक जाणीवपूर्वक पैज.

⚛️ React ने composition निवडले

React स्पष्टपणे पुनर्वापरासाठी inheritance ऐवजी composition ची शिफारस करते, base components extend करण्याऐवजी hooks आणि child components वापरते.

💉 Dependency injection सर्वत्र

Spring, Angular, आणि NestJS collaborators constructors मार्फत जोडतात, ज्यामुळे has-a design हा frameworks apps जमवण्याचा default मार्ग बनतो.

🧩 Patterns म्हणजे composition

Strategy, Decorator, Bridge, आणि Adapter, Gang of Four चे कामाचे घोडे, हे सर्व एका विशिष्ट कामासाठी सजवलेले composition आहेत.

🔬 Testability ची मागणी

आधुनिक testing संस्कृती interfaces मागच्या लहान, mock करता येणाऱ्या units ला बक्षीस देते, जे नेमके composition तयार करते आणि inheritance नाकारते.

सारांश: खऱ्या, स्थिर is-a subtyping आणि template methods साठी inheritance अजूनही त्याचे स्थान कमावते, पण composition हा default आहे जो systems लवचिक, testable, आणि बदलण्यास सुरक्षित ठेवतो. आधी has-a कडे झुका, आणि inheritance ला ते तिथे बसते हे सिद्ध करू द्या.
