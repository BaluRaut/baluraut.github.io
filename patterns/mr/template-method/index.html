Behavioral Pattern

Template Method - अल्गोरिदम निश्चित करा, पायऱ्या बदला

Template Method एका बेस-क्लास मेथडमध्ये अल्गोरिदमचा सांगाडा निश्चित करते, आणि नंतर विशिष्ट पायऱ्या सबक्लासेसकडे सोपवते. एकंदर क्रम एकाच ठिकाणी बंद केलेला असतो, तर सबक्लासेस वेगळे असणारे भाग भरतात किंवा ओव्हरराइड करतात. बेस क्लास सबक्लासला कॉल करते, उलट नाही, आणि हेच नेमके Hollywood Principle आहे: आम्हाला कॉल करू नका, आम्ही तुम्हाला कॉल करू.

01 - काय

Template Method म्हणजे काय?

Template Method हा एक behavioral पॅटर्न आहे जिथे बेस क्लास एका मेथडमध्ये अल्गोरिदमला ठराविक पायऱ्यांच्या क्रमाच्या रूपात निश्चित करते, आणि काही पायऱ्या abstract किंवा ओव्हरराइड करण्यायोग्य म्हणून चिन्हांकित करते. सबक्लासेस स्वतः क्रमाला हात न लावता बदलणाऱ्या पायऱ्या पुरवतात. अपरिवर्तनीय रचना पालकात राहते; बदल मुलांमध्ये राहतो.

🧱 Template method

बेस क्लासमधली एक concrete मेथड जी पायऱ्यांना ठराविक क्रमाने कॉल करते. ती सहसा final असते जेणेकरून सबक्लासेस अल्गोरिदमचा क्रम बदलू शकणार नाहीत.

🧩 Abstract पायऱ्या

बेस ज्या ऑपरेशन्स जाहीर करते पण अंमलात आणत नाही. प्रत्येक सबक्लासने त्या पुरवल्याच पाहिजेत, सांगाड्यातील आवश्यक जागा भरत.

🪝 Hook मेथड्स

रिकाम्या किंवा डीफॉल्ट शरीरासह पर्यायी पायऱ्या. सबक्लासेस त्यांना वर्तन वाढवण्यासाठी किंवा किंचित बदलण्यासाठी ओव्हरराइड करू शकतात, पण त्यांना तसे करण्याची सक्ती नाही.

02 - का

Template Method का अस्तित्वात आहे

जेव्हा अनेक क्लासेस एकाच एकंदर प्रक्रियेत सामायिक असतात पण काही पायऱ्यांमध्ये वेगळे असतात, तेव्हा ती प्रक्रिया प्रत्येकात कॉपी-पेस्ट केल्याने control flow ची पुनरावृत्ती होते. प्रत्येक बग फिक्स किंवा क्रमबदल मग सर्वत्र पुन्हा करावा लागतो. Template Method तो सामायिक सांगाडा एकाच ठिकाणी आणते.

♻️ पुनरावृत्ती काढून टाकते

सामायिक क्रम बेस क्लासमध्ये एकदाच राहतो. सबक्लासेस फक्त फरक देतात, त्यामुळे सामायिक control flow variants मध्ये कधीही कॉपी-पेस्ट होत नाही.

🔒 अल्गोरिदमचे रक्षण करते

Template method ला final चिन्हांकित केल्याने पायऱ्यांचा क्रम बंद होतो. सबक्लासेस चुकून validation वगळू शकत नाहीत किंवा महत्त्वाचे टप्पे क्रमबदल करू शकत नाहीत.

🎯 सबक्लासेसना केंद्रित करते

नवीन variant फक्त abstract पायऱ्या अंमलात आणतो. डेव्हलपर्सना नेमके कोणते रिकामे भाग भरायचे ते दिसते, संपूर्ण workflow पुन्हा वाचण्याऐवजी.

🔄 नियंत्रण उलटवते

Framework प्रवाह चालवते आणि ठराविक बिंदूंवर तुमच्या कोडला कॉल करते, त्यामुळे विस्तार पुनर्लेखनांऐवजी सुस्पष्ट hooks मार्फत होतो.

सोप्या भाषेत

उपमांनी समजावलेले Template Method

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती समजेल.

🎓 विद्यार्थ्यासाठी

ती एक रिकाम्या जागा भरण्याची कार्यपत्रिका आहे. शिक्षक प्रश्न आणि त्यांचा क्रम निश्चित करतात; तुम्ही फक्त रिकाम्या जागांमध्ये उत्तरे लिहिता. तुम्ही प्रश्नांची फेरमांडणी करू शकत नाही, फक्त रिकाम्या जागा पूर्ण करता.

👩‍💻 डेव्हलपरसाठी

setUp आणि tearDown असलेल्या बेस टेस्ट क्लासचा विचार करा. Framework आधी setUp चालवते, मग तुमची test, मग tearDown, त्याच क्रमाने. तुम्ही hooks ओव्हरराइड करता; runner क्रमाच्या मालकीचे असते.

🏢 व्यावसायिकासाठी

ती एक प्रमाणित कार्यपद्धती आहे. पायऱ्या आणि त्यांचा क्रम धोरणाने निश्चित केलेला असतो; प्रत्येक विभाग प्रक्रिया न बदलता आपल्या कामाशी संबंधित तपशील भरतो.

☕ रोजच्या जीवनातील आवृत्ती

गरम पेय बनवणे: पाणी उकळा, मुख्य घटक टाका, ओता, अतिरिक्त गोष्टी टाका. चहा आणि कॉफी recipe सांगाडा सामायिक करतात; फक्त "घटक टाका" आणि पर्यायी "अतिरिक्त गोष्टी टाका" या पायऱ्या वेगळ्या असतात.

03 - कसे

ते आतून कसे काम करते

बेस क्लास एक सार्वजनिक template method आणि संरक्षित पायऱ्यांचा संच उघड करते. काही पायऱ्या abstract असतात (अंमलात आणल्याच पाहिजेत), इतर hooks असतात (ओव्हरराइड करू शकता). रनटाइमला dynamic dispatch प्रत्येक पायरीच्या कॉलला योग्य concrete सबक्लासकडे मार्गित करते.

🧭 बेस क्लास नेतृत्व करते

ती template method अंमलात आणते आणि प्रत्येक पायरीला नावाने कॉल करते. सामायिक, अपरिवर्तनीय logic थेट बेसमध्ये असते जेणेकरून प्रत्येक सबक्लास ती फुकट वारशाने मिळवते.

🔌 सबक्लासेस जोडले जातात

प्रत्येक concrete क्लास abstract पायऱ्या आणि त्याला हव्या असलेल्या कोणत्याही hooks ओव्हरराइड करतो. तो template method चे अंतर्गत भाग कधीही कॉल करत नाही, फक्त तुकडे पुरवतो.

रचना एका दृष्टिक्षेपात

Class रचना - बेस अल्गोरिदमच्या मालकीचे असते, सबक्लासेस पायऱ्या पुरवतात
classDiagram
    class AbstractClass {
        +templateMethod() final
        #stepOne()* abstract
        #stepTwo()* abstract
        #hook() default
    }
    class ConcreteA {
        #stepOne()
        #stepTwo()
    }
    class ConcreteB {
        #stepOne()
        #stepTwo()
        #hook()
    }
    AbstractClass <|-- ConcreteA
    AbstractClass <|-- ConcreteB
    note for AbstractClass "templateMethod calls stepOne, stepTwo, hook in fixed order"

Java मधले एक वास्तववादी उदाहरण

abstract class DataImporter {

    // The template method: the algorithm skeleton, locked with final.
    public final void run(String path) {
        String raw = read(path);          // abstract step
        List<Record> records = parse(raw); // abstract step
        if (shouldValidate()) {            // hook controls an optional step
            validate(records);            // hook step
        }
        save(records);                    // shared, invariant step
        onComplete(records.size());       // hook, empty by default
    }

    // Required steps: every subclass MUST provide these.
    protected abstract String read(String path);
    protected abstract List<Record> parse(String raw);

    // Hook methods: optional, with sensible defaults.
    protected boolean shouldValidate() { return true; }
    protected void validate(List<Record> records) { /* default no-op */ }
    protected void onComplete(int count) { /* subclasses may log here */ }

    // Invariant step shared by all importers.
    private void save(List<Record> records) {
        Database.bulkInsert(records);
    }
}

class CsvImporter extends DataImporter {
    protected String read(String path) { return Files.readString(path); }
    protected List<Record> parse(String raw) { return Csv.toRecords(raw); }
    protected void onComplete(int count) {
        System.out.println("Imported " + count + " CSV rows");
    }
}

class JsonImporter extends DataImporter {
    protected String read(String path) { return Http.get(path); }
    protected List<Record> parse(String raw) { return Json.toRecords(raw); }
    // Trusted feed, so skip validation via the hook.
    protected boolean shouldValidate() { return false; }
}

लक्षात घ्या की run() ही final आहे: सबक्लासेस read, parse, validate, save यांचा क्रम बदलू शकत नाहीत. ते फक्त पायऱ्या ओव्हरराइड करतात. बेस क्लास सबक्लासमध्ये खाली कॉल करते, कधीही उलट नाही, आणि हेच कृतीत असलेले Hollywood Principle आहे: आम्हाला कॉल करू नका, आम्ही तुम्हाला कॉल करू.

पर्यायी hooks जोडा

पर्यायी पायऱ्यांना डीफॉल्ट किंवा रिकामे शरीर द्या. सबक्लासेस वर्तन वाढवण्यासाठी ओव्हरराइड करू शकतात, पण त्यांनी तसे केले नाही तरी काहीही तुटत नाही.

90
चालवा

Clients बेस-प्रकाराच्या संदर्भावर template method कॉल करतात. Dynamic dispatch प्रत्येक पायरीला योग्य सबक्लासकडे मार्गित करते.

100
देखभाल

सामायिक पायरीची फेरमांडणी किंवा दुरुस्ती बेसमध्ये एकदाच होते आणि प्रत्येक variant ला लगेच लागू होते. पुनरावृत्ती नाहीशी झाली.

सामान्य धोके

धोके आणि anti-patterns

Template Method inheritance वर अवलंबून असते, त्यामुळे त्याचे अपयशाचे प्रकार म्हणजे inheritance चे उत्कृष्ट सापळे.

🧨 नाजूक बेस क्लास

सांगाडा किंवा सामायिक पायरी संपादित केल्याने प्रत्येक सबक्लास गुपचूप तुटू शकतो. Inheritance मार्फत घट्ट coupling म्हणजे बदल अशा प्रकारे खाली पसरतात जे पाहणे कठीण असते.

🪜 खूप जास्त abstract पायऱ्या

जर जवळजवळ प्रत्येक पायरी abstract असेल, तर बेस थोडाच पुनर्वापर देते आणि सबक्लासेस सर्व ओझे वाहतात. हे लक्षण आहे की सामायिक सांगाडा फारसा अस्तित्वातच नाही.

🔓 Template लॉक करायला विसरणे

Template method ओव्हरराइड करण्यायोग्य ठेवल्याने एखादा सबक्लास अल्गोरिदमचा क्रम पुन्हा लिहू शकतो, जे संपूर्ण उद्देशच पराभूत करते. तिला final चिन्हांकित करा.

🕸️ खोल श्रेणीक्रम

अंशतः वर्तन पुन्हा वापरण्यासाठी सबक्लासच्या अनेक स्तरांची साखळी जोडल्याने प्रवाह अनुसरणे अशक्य होते. बदलाचा एक स्तर सहसा योग्य असतो.

🎭 आवश्यकता गळणारे hooks

जे hooks एकत्र, किंवा ठराविक संयोजनात ओव्हरराइड केले पाहिजेत ते अस्पष्ट करार लपवतात. एखादा लपलेला नियम चुकल्यास सबक्लासेस सूक्ष्मपणे तुटतात.

🔁 वर्तन डेटा असताना त्याकडे वळणे

जर पायऱ्या प्रत्येक ऑब्जेक्टनुसार रनटाइमला बदलत असतील, तर inheritance मदत करू शकत नाही. प्रत्येक संयोजनासाठी सबक्लास लादल्याने क्लासची संख्या स्फोट पावते. त्याऐवजी compose करा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

जेव्हा अल्गोरिदम निश्चित असतो आणि फक्त त्याच्या पायऱ्या बदलतात तेव्हा Template Method हा पहिला पर्याय असतो. त्याचा मुख्य तणाव Strategy आहे: inheritance विरुद्ध composition.

पैलूतपशील
फायदेपुनरावृत्त control flow काढून टाकते, अल्गोरिदमचा क्रम एकाच ठिकाणी बंद करते, सबक्लासेसना स्पष्ट विस्तार बिंदू देते, आणि inversion of control सक्षम करते.
तोटेInheritance वर अवलंबून असते, त्यामुळे सबक्लासेसना बेसशी couple करते, नाजूक-बेस-क्लास समस्यांना आमंत्रण देते, आणि compile वेळी वर्तन निश्चित करते.
केव्हा वापरावेतुमच्याकडे एकाच प्रक्रियेचे अनेक variants आहेत जे फक्त काही पायऱ्यांमध्ये वेगळे आहेत, आणि क्रम स्वतः कधीही बदलू नये.
केव्हा टाळावेबदलणारे वर्तन रनटाइमला निवडले किंवा बदलले गेले पाहिजे, किंवा पायऱ्यांची संयोजने झाकण्यासाठी तुम्हाला अनेक सबक्लासेस लागतील.
जटिलताकमी. एक abstract class अधिक प्रत्येक variant साठी एक सबक्लास. कठीण भाग म्हणजे कोणत्या पायऱ्या abstract आणि कोणत्या hooks हे निवडणे.
संबंधितStrategy (composition पर्याय), Factory Method (बहुधा template मधली एक पायरी), आणि hooks Observer callback शैलीसारखे असतात.
अंगठ्याचा नियम: जेव्हा अल्गोरिदम निश्चित असतो आणि पायऱ्या प्रकारानुसार बदलतात तेव्हा Template Method कडे वळा. जेव्हा संपूर्ण वर्तन रनटाइमला बदलले गेले पाहिजे तेव्हा Strategy कडे वळा. Template Method वारसा घेते, Strategy compose करते: जेव्हा बदलाचा अक्ष गतिशील असतो तेव्हा composition ला प्राधान्य द्या.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन ठिकाणे जिथे तुम्ही जवळजवळ नक्कीच वापरलेल्या कोडमध्ये हा पॅटर्न दिसतो.

🧪

1 · JUnit test lifecycle

पॅटर्न: hooks सह framework च्या मालकीचा run क्रम

Testing framework ने प्रत्येक test सुसंगत lifecycle मध्ये चालवला पाहिजे, तर प्रत्येक test क्लासला setup आणि teardown सानुकूल करू दिले पाहिजे.

  • Runner निश्चित क्रमाच्या मालकीचे असते: setUp, test body चालवा, tearDown.
  • Test क्लासेस setUp आणि tearDown hooks म्हणून ओव्हरराइड करतात; ओव्हरराइड करणे पर्यायी असते.
  • तुम्ही lifecycle स्वतः कधीही कॉल करत नाही, framework तुमच्या क्लासमध्ये कॉल करते.
✅ परिणाम: प्रत्येक test विश्वासार्ह, एकसमान lifecycle सामायिक करतो तर प्रत्येक क्लास फक्त त्याला हवे असलेले भाग सानुकूल करतो, एक पाठ्यपुस्तकी Hollywood Principle मांडणी.
📥

2 · HTTP servlet request हाताळणी

पॅटर्न: ओव्हरराइड करण्यायोग्य पायऱ्यांसह dispatch सांगाडा

Web framework ला प्रत्येक request सामायिक pipeline मार्फत मार्गित करावे लागते, तर handlers ना फक्त त्यांना हवे असलेले verb अंमलात आणू दिले पाहिजे.

  • service() ही template method आहे: ती HTTP verb तपासते आणि dispatch करते.
  • ती doGet, doPost आणि तत्सम ओव्हरराइड करण्यायोग्य पायऱ्या म्हणून कॉल करते.
  • तुमचे servlet फक्त ते समर्थित करत असलेल्या verbs साठीच्या मेथड्स अंमलात आणते.
✅ परिणाम: सामायिक request dispatch बेस servlet मध्ये एकदाच राहते, आणि प्रत्येक handler pipeline पुन्हा न लिहिता फक्त verb-विशिष्ट logic देते.
🍜

3 · Build आणि deployment pipelines

पॅटर्न: निश्चित टप्पे, प्रकल्प-विशिष्ट पायऱ्या

एक CI बेस job प्रत्येक प्रकल्प चालवत असलेले प्रमाण टप्पे निश्चित करते, तर वैयक्तिक प्रकल्प आपल्या स्वतःच्या commands जोडतात.

  • बेस क्रम निश्चित करते: checkout, install, build, test, package, publish.
  • प्रकल्प त्यांच्या stack साठी build आणि test सारख्या abstract पायऱ्या ओव्हरराइड करतात.
  • afterPublish सारखा एक hook काही प्रकल्पांना releases सूचित किंवा tag करू देतो.
✅ परिणाम: एकच, ऑडिट करण्यायोग्य pipeline क्रम प्रत्येक प्रकल्पभर लागू होतो, आणि संघ संपूर्ण workflow fork करण्याऐवजी फक्त त्यांच्या स्वतःच्या पायऱ्या बदलतात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

हा पॅटर्न तुम्ही वापरता त्या बहुतेक frameworks च्या आधीचा आहे, तरीही त्याचा आकार पुन्हा पुन्हा दिसत राहतो, बहुधा class श्रेणीक्रमाशिवायच व्यक्त होत.

🏗️ सर्वत्र frameworks

तुमच्या lifecycle मेथड्सना निश्चित क्रमाने कॉल करणारे प्रत्येक framework म्हणजे एक template method. Inversion of control म्हणजे संपूर्ण प्रणालीपर्यंत सामान्यीकृत केलेला हाच पॅटर्न.

🧬 डीफॉल्ट interface मेथड्स

Java default मेथड्स आणि TypeScript abstract classes template ला interface वर राहू देतात, सामायिक प्रवाह आवश्यक पायऱ्यांशी पूर्वीपेक्षा अधिक लवचिकपणे मिसळत.

🧩 Functional variants

निश्चित pipeline फंक्शनमध्ये step फंक्शन्स पास केल्याने composition सह तोच सांगाडा साध्य होतो, Strategy शी असलेली रेषा अस्पष्ट करत.

🪝 First-class API म्हणून hooks

आधुनिक libraries lifecycle hooks (beforeCreate, mounted, onRequest) उघड करतात जे नेमके पर्यायी-पायरीची कल्पनाच आहे, सार्वजनिक आणि दस्तऐवजीकृत केलेली.

⚖️ Composition-प्रथम संस्कृती

संघ inheritance पेक्षा composition ला पसंती देत असल्याने, अनेक template methods Strategy किंवा higher-order functions मध्ये refactor केले जातात, पण सांगाड्याची कल्पना टिकून राहते.

🔌 Plugin architectures

Plugin प्रणाली निश्चित विस्तार बिंदू निश्चित करतात आणि ठराविक क्षणी नोंदणीकृत कोड कॉल करतात, Template Method चा एक inversion-of-control वंशज.

सारांश: Template Method म्हणजे तुम्ही सामायिक अल्गोरिदम कसा वेगळा काढता आणि variants ना रिकाम्या जागा भरू देता. जेव्हा बदल प्रकारानुसार असतो आणि प्रवाह निश्चित असतो, तेव्हा inheritance बसते. जेव्हा बदल instance-नुसार आणि गतिशील असतो, तेव्हा Strategy आणि composition ला प्राधान्य द्या. सांगाड्याची कल्पना यंत्रणेपेक्षा जास्त काळ टिकते.
