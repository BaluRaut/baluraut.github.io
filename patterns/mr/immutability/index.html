Immutability - बांधणीनंतर कधीही न बदलणारे objects

Immutable object हे त्याच्या constructor कडून पूर्णपणे तयार होते आणि पुन्हा कधीही बदलले जात नाही. प्रत्येक field एकदाच सेट होते आणि आधीच तपासले जाते, त्यामुळे object नेहमी वैध स्थितीत असते. जेव्हा तुम्हाला एखादी वेगळी आवृत्ती हवी असते, तेव्हा तुम्ही त्याला बदलत नाही - तुम्ही एक नवीन object तयार करता आणि मूळ object तसेच ठेवता.

कोड पाहा आकृत्यांकडे जा
Readonly fields Functional updates Thread safety सुरक्षित sharing
01 - काय

Immutability म्हणजे काय?

Immutable object असे कोणतेही operation उघड करत नाही जे त्याची दृश्यमान स्थिती बदलेल. Money, एखादी date range, किंवा एखादे application config एकदाच तयार होते, एकदाच तपासले जाते, आणि त्यानंतर ते फक्त-वाचनासाठी (read-only) राहते. ज्यांना वेगळे मूल्य हवे असते ते callers एखाद्या method कडून ताज्या object ची मागणी करतात; receiver कधीही जागच्या जागी पुन्हा लिहिले जात नाही. तो एकच नियम bugs चा एक संपूर्ण वर्ग नाहीसा करतो आणि सुरक्षित sharing शक्य करतो.

🧱 बांधणीच्या वेळी एकदाच सेट

सर्व fields constructor मध्ये नेमली जातात आणि तिथेच तपासली जातात. ऋण minor-unit रक्कम असलेले किंवा जुळत नसलेले currency असलेले Money अस्तित्वातच येऊ शकत नाही.

🔒 कोणतेही mutators नाहीत

कोणतेही setters नाहीत आणि fields ला पुन्हा नेमणाऱ्या कोणत्याही methods नाहीत. सार्वजनिक पृष्ठभाग म्हणजे queries आणि नवीन instances परत करणारी शुद्ध (pure) रूपांतरे.

➕ Functional updates

add किंवा withCurrency सारखी operations एक अगदी नवीन object परत करतात. मूळ object जसेच्या तसे राहते, त्यामुळे जुन्या references ना अचानक झालेले बदल कधीही दिसत नाहीत.

02 - का

Immutability का अस्तित्वात आहे

Mutable shared state हे बहुतेक concurrency bugs आणि aliasing च्या आश्चर्यांचे मूळ आहे. जेव्हा एखादे object तुमच्या नकळत बदलू शकते, तेव्हा त्याकडील प्रत्येक reference एक धोका बनतो. Immutability थोडेसे copying देऊन मोठ्या प्रमाणात निश्चितता मिळवते.

🧵 विनासायास thread safety

जर कोणताही thread एखादे object बदलू शकत नसेल, तर ते वाचण्यासाठी कोणत्याही thread ला lock ची गरज नाही. Immutable Money आणि Config कोणत्याही synchronization शिवाय request pool मध्ये shared करता येतात.

🔗 सुरक्षित sharing आणि caching

तुम्ही तेच instance अनेक callers ना देऊ शकता, ते cache करू शकता, आणि hash-map key म्हणून वापरू शकता, याची भीती न बाळगता की खालच्या बाजूला कोणीतरी ते बदलेल आणि बाकीच्या सर्वांची प्रत बिघडवेल.

🐛 Aliasing bugs नाहीत

एकाच object कडे निर्देश करणारी दोन variables अनपेक्षितपणे कधीही वेगळी होऊ शकत नाहीत, कारण object कधीही बदलत नाही. ते एखाद्या function ला दिल्याने caller ला आश्चर्य वाटत नाही.

🧭 समजायला सोपे

State फक्त constructors मध्येच दिसते, त्यामुळे तुम्ही एकाच ठिकाणी शुद्धतेचे लेखापरीक्षण करता. जुनी मूल्ये अजूनही अस्तित्वात असल्याने Undo, retries, आणि time-travel debugging क्षुल्लक होतात.

सोप्या भाषेत

उपमांसह समजावलेले Immutability

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती लगेच समजेल.

🎓 विद्यार्थ्यासाठी

हे पेनाने लिहिलेल्या परीक्षेच्या उत्तरासारखे आहे. एकदा लिहून झाले की तुम्ही ते पुसत नाही; जर तुमचे मत बदलले तर तुम्ही एक नवीन, दुरुस्त केलेली प्रत लिहिता. जुनी शीट जशीच्या तशी राहते.

👩‍💻 developer साठी

बहुतेक भाषांमधील string चा विचार करा. "hello".toUpperCase() मूळ बदलत नाही; ते एक नवीन string परत करते. Immutable domain objects अगदी त्याच प्रकारे वागतात.

🏢 व्यावसायिकासाठी

स्वाक्षरी केलेल्या कराराप्रमाणे. अंमलात आलेल्या दस्तऐवजावर तुम्ही कधीही खरडत नाही; तुम्ही एक नवीन आवृत्तीबद्ध दस्तऐवज म्हणून सुधारणा जारी करता. काय ठरले याचा दाखला म्हणून मूळ दस्तऐवज तसाच राहतो.

🧾 दैनंदिन आवृत्ती

एक छापलेली पावती. एखादे शुल्क दुरुस्त करण्यासाठी दुकान तुमची पावती पुन्हा लिहीत नाही; ते एक नवीन पावती छापते. दोन्ही चिठ्ठ्या अस्तित्वात राहतात, आणि इतिहास प्रामाणिक राहतो.

03 - कसे

आतमध्ये हे कसे कार्य करते

Immutability म्हणजे एकत्र काम करणाऱ्या दोन शिस्ती: fields ला कुलूप लावा जेणेकरून त्यांना काहीही पुन्हा नेमू शकणार नाही, आणि objects ला संपादित करण्याऐवजी संपूर्ण objects बदला. भाषा तुम्हाला कुलूप देते; तुम्ही functional-update methods पुरवता.

🔐 Fields ला कुलूप लावा

प्रत्येक field ला type पातळीवर read-only म्हणून चिन्हांकित करा. TypeScript readonly वापरते, Python frozen=True dataclass वापरते, आणि Ruby constructor मध्ये freeze बोलावते. पुन्हा नेमण्याचा कोणताही प्रयत्न ही compile error किंवा runtime error असते.

🔁 नवीन objects परत करा

प्रत्येक "बदल" ही एक method असते जी सध्याची fields वाचते, पुढील मूल्ये मोजते, आणि एक ताजे instance तयार करते. Caller त्यांचे variable पुन्हा बांधतो; जुने object अस्पर्श आणि अजूनही वैध राहते.

तीन भाषांमध्ये तीच immutable class

// Money as an immutable value object. Amount is in minor units (cents).
class Money {
  constructor(
    public readonly amount: number,
    public readonly currency: string,
  ) {
    if (!Number.isInteger(amount)) throw new Error("amount must be integer minor units");
    if (currency.length !== 3) throw new Error("currency must be an ISO code");
    Object.freeze(this); // lock the instance at runtime too
  }

  // Functional update: returns a NEW Money, never mutates `this`.
  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("currency mismatch");
    return new Money(this.amount + other.amount, this.currency);
  }

  scale(factor: number): Money {
    return new Money(Math.round(this.amount * factor), this.currency);
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }

  format(): string {
    return `${(this.amount / 100).toFixed(2)} ${this.currency}`;
  }
}

const price = new Money(1999, "USD");
const shipping = new Money(500, "USD");
const total = price.add(shipping);   // -> new Money(2499, "USD")
console.log(price.format());         // "19.99 USD" (unchanged)
console.log(total.format());         // "24.99 USD"
# Money as an immutable value object using a frozen dataclass.
from dataclasses import dataclass, replace

@dataclass(frozen=True)          # frozen -> fields cannot be reassigned
class Money:
    amount: int                  # minor units (cents)
    currency: str

    def __post_init__(self):
        if not isinstance(self.amount, int):
            raise ValueError("amount must be integer minor units")
        if len(self.currency) != 3:
            raise ValueError("currency must be an ISO code")

    # Functional update: returns a NEW Money, never mutates self.
    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError("currency mismatch")
        return replace(self, amount=self.amount + other.amount)

    def scale(self, factor: float) -> "Money":
        return replace(self, amount=round(self.amount * factor))

    def format(self) -> str:
        return f"{self.amount / 100:.2f} {self.currency}"

price = Money(1999, "USD")
shipping = Money(500, "USD")
total = price.add(shipping)      # -> Money(amount=2499, currency='USD')
print(price.format())            # "19.99 USD" (unchanged)
print(total.format())            # "24.99 USD"

# Money as an immutable value object. freeze locks the instance.
class Money
  attr_reader :amount, :currency   # readers only, no writers

  def initialize(amount, currency)
    raise ArgumentError, "amount must be integer minor units" unless amount.is_a?(Integer)
    raise ArgumentError, "currency must be an ISO code" unless currency.length == 3
    @amount = amount
    @currency = currency.freeze
    freeze                          # no ivar can be reassigned after this
  end

  # Functional update: returns a NEW Money, never mutates self.
  def add(other)
    raise ArgumentError, "currency mismatch" unless other.currency == @currency
    Money.new(@amount + other.amount, @currency)
  end

  def scale(factor)
    Money.new((@amount * factor).round, @currency)
  end

  def ==(other)
    other.is_a?(Money) && amount == other.amount && currency == other.currency
  end

  def format
    format_amount = (@amount / 100.0)
    "%.2f %s" % [format_amount, @currency]
  end
end

price = Money.new(1999, "USD")
shipping = Money.new(500, "USD")
total = price.add(shipping)       # -> new Money(2499, "USD")
puts price.format                 # "19.99 USD" (unchanged)
puts total.format                 # "24.99 USD"
# price.instance_variable_set(:@amount, 0)  # FrozenError

तिन्हीमध्ये, add receiver वाचते, पुढील रक्कम मोजते, आणि एक नवीन Money परत देते. बेरजेनंतरही मूळ price अजूनही 19.99 असे format होते. Frozen किंवा readonly घोषणा हीच ती गोष्ट आहे जी त्या हमीला केवळ एक परंपरा न ठेवता अंमलात आणण्याजोगी बनवते.

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

एका value ची रचना करण्यापासून ते जिवंत system मध्ये ते सुरक्षितपणे sharing करण्यापर्यंत - संपूर्ण प्रवास क्रमाने.

00
Model

एक value ओळखा

पूर्णपणे त्याच्या data द्वारे परिभाषित होणारी संकल्पना शोधा, जसे Money, एखादी DateRange, किंवा app Config. immutability साठी ही उमेदवार असतात कारण इथे identity ला महत्त्व नाही, फक्त fields ला असते.

10
Fields

Read-only fields घोषित करा

किमान fields ची यादी करा आणि त्यांना read-only म्हणून चिन्हांकित करा: TS readonly, Python frozen dataclass, किंवा Ruby instance variables ज्यांना तुम्ही freeze कराल.

20
Validate

Constructor मध्ये guard ठेवा

चुकीचा input आधीच नाकारा - non-integer रकमा, अज्ञात currency, अशी range जिचा शेवट सुरुवातीच्या आधी येतो. बांधलेले object नेहमी वैध असते.

30
Freeze

Instance ला कुलूप लावा

Immutability अंतिम करा: Object.freeze(this), frozen dataclass यंत्रणा, किंवा constructor ची शेवटची ओळ म्हणून freeze.

40
Query

Read-only methods उघड करा

format(), contains(date), किंवा isEnabled(flag) सारख्या शुद्ध queries जोडा ज्या काहीही न बदलता fields वरून मोजतात.

50
Update

Functional updates जोडा

add, withCurrency, किंवा extendTo(date) लिहा जे receiver ला बदलण्याऐवजी एक नवीन instance तयार करून परत करतात.

60
Equality

Value द्वारे तुलना करा

Field-by-field equality आणि जुळणारे hash लागू करा जेणेकरून दोन समान मूल्ये परस्पर बदलण्याजोगी आणि map keys म्हणून वापरण्याजोगी असतील.

70
Nesting

Collections ला guard ठेवा

आतील arrays किंवा maps देखील frozen किंवा बचावात्मकरीत्या copy केलेली असल्याची खात्री करा, जेणेकरून shared आतील list mutability बाहेर पाडू शकणार नाही.

80
Share

मुक्तपणे द्या, locks नाहीत

तेच instance अनेक callers आणि threads ना द्या. ते कधीही बदलत नसल्याने, ते वाचण्यासाठी कोणत्याही synchronization ची गरज नाही.

90
Cache

सुरक्षितपणे cache आणि key करा

निकाल memoize करा आणि value ला cache key म्हणून वापरा. खालच्या बाजूला काहीही cached नोंद बदलून तिला बिघडवू शकत नाही.

100
Evolve

नवीन objects द्वारे आवृत्ती करा

जेव्हा आवश्यकता बदलतात, तेव्हा नवीन स्थितींसाठी नवीन instances तयार करा. जुनी मूल्ये टिकून राहतात, undo, audit trails, आणि सोप्या तर्काला बळ देतात.

सामान्य धोके

धोके आणि anti-patterns

Immutability घोषित करणे सोपे आहे आणि चुकून तोडणेही सोपे आहे. हे नेहमीचे गळती-बिंदू आहेत.

🕳️ Shallow freeze

Object ला read-only चिन्हांकित करणे पण आतील array किंवा map mutable ठेवणे. Callers आतील collection संपादित करतात आणि "immutable" object शांतपणे बदलते. आतील state देखील freeze किंवा copy करा.

🚪 अंतर्गत references बाहेर पडणे

Getter मधून प्रत्यक्ष अंतर्गत list परत केल्याने callers ना ती थेट बदलता येते. जिवंत reference ऐवजी एक copy, एक frozen view, किंवा एक iterator परत करा.

🔧 लपलेले setters

"फक्त याच वेळी" एखादे field पुन्हा नेमणारी सोयीस्कर method जोडल्याने प्रत्येक हमी नष्ट होते. जर कोणताही code path state बदलत असेल, तर ते immutable नाही. पृष्ठभाग फक्त-query ठेवा.

🐢 Hot loops मध्ये copy ची गर्दी

हजारो मूल्यांची बेरीज करताना प्रत्येक फेरीला एक नवीन object तयार केल्याने भरपूर allocation होऊ शकते. एक builder वापरा किंवा primitives जमा करा, मग एक अंतिम immutable निकाल तयार करा.

🎭 Identity द्वारे equality

Value equality विसरल्याने दोन समान Money instances वेगळी दिसतात, ज्यामुळे sets, cache keys, आणि deduplication तुटते. Immutable मूल्यांना field-आधारित equals आणि hash आवश्यक असते.

🧨 Mutable default arguments

Python मध्ये list सारखा एक mutable default instances मध्ये शेअर केल्याने objects दरम्यान state गळते. प्रत्येक instance स्वतंत्र राहावे यासाठी immutable defaults किंवा एक factory वापरा.

संकेत आणि मापदंड

संकेत आणि कसे मोजावे

Codebase मध्ये आणि runtime वर काही संकेतांचे निरीक्षण करून immutability खरी आहे की केवळ आकांक्षा आहे हे तुम्ही सांगू शकता.

संकेतते तुम्हाला काय सांगते
Value types वरील setter संख्याशून्य setters किंवा field पुनर्नेमणुका म्हणजे object खरोखर immutable आहे, केवळ तसे लेबल केलेले नाही.
Freeze / readonly व्याप्तीकिती value classes प्रत्यक्षात frozen किंवा readonly fields घोषित करतात, आणि किती फक्त परंपरेवर अवलंबून आहेत.
Defensive-copy लेखापरीक्षणGetters copies किंवा frozen views परत करतात का; बाहेर पडलेली जिवंत references लपलेली mutability उघड करतात.
Shared state भोवतीचे locksजसजशी अधिक shared objects immutable होतात तसतसे कमी locks लागतात - एक थेट concurrency-सोपेपणाचा संकेत.
Aliasing bug दरएखादे type immutable केल्यानंतर "value अनपेक्षितपणे बदलले" या दोषांमधील घट.
Allocation profileHot paths मध्ये functional updates मुळे होणारी object गर्दी, जी तुम्हाला सांगते की builder किंवा batching कुठे उपयुक्त आहे.
ढोबळ नियम: जर तुम्हाला अशी एकही कोड ओळ सापडली जी बांधणीनंतर value object वरील एखादे field पुन्हा नेमते, तर ते अजून immutable नाही. लेबलवर विश्वास ठेवण्याआधी setters आणि field writes साठी grep करा.
06 - उदाहरण अभ्यास

वास्तविक जगातील उदाहरण अभ्यास

तीन production-शैलीतील systems जिथे immutability भार-वाहक आहे.

💳

1 · Payments ledger मधील Money

Pattern: रकमांसाठी immutable value object

एक payments platform प्रत्येक रक्कम integer minor units मध्ये immutable Money म्हणून दर्शवते, जी pricing, tax, आणि settlement मध्ये shared असते.

  • रकमा कधीही बदलत नाहीत: एक discount एक नवीन Money तयार करते, त्यामुळे मूळ line price audit साठी जपली जाते.
  • Currency जुळत नसताना बेरीज करणे अशक्य असते, हे खालच्या बाजूच्या report ऐवजी operation च्या वेळीच पकडले जाते.
  • Ledger नोंदी cache आणि reconcile करण्यासाठी सुरक्षित असतात कारण कोणताही code path पोस्ट केलेली रक्कम पुन्हा लिहू शकत नाही.
✅ निकाल: कमी rounding आणि currency दोष, आणि एक स्वच्छ audit trail कारण ऐतिहासिक रकमा बांधणीमुळेच कायमस्वरूपी असतात.
📅

2 · Bookings engine मधील DateRange

Pattern: functional updates सह immutable interval

एक reservations service उपलब्धतेच्या windows ना immutable DateRange म्हणून दर्शवते, अशी तपासलेली की शेवट कधीही सुरुवातीच्या आधी येत नाही.

  • मुक्काम वाढवल्याने एक नवीन DateRange परत येते, ज्यामुळे मूळ booking window change log साठी अखंड राहते.
  • Overlap आणि contains तपासण्या शुद्ध queries आहेत, अनेक availability workers मध्ये concurrently चालवण्यासाठी सुरक्षित.
  • Ranges pricing साठी cache keys म्हणून वापरल्या जातात, जे फक्त तेव्हाच शक्य होते कारण त्या value द्वारे तुलना करतात आणि कधीही बदलत नाहीत.
✅ निकाल: Concurrency-सुरक्षित availability तपासण्या आणि प्रत्येक reservation window कशी विकसित झाली याचा विश्वासार्ह इतिहास.
🎛️

3 · सुरुवातीला immutable app Config

Pattern: सर्वत्र shared केलेले frozen configuration

एक backend service आपले configuration एकदाच एका immutable Config object मध्ये load करते जे प्रत्येक request handler आणि thread वाचतो.

  • Config boot च्या वेळी तपासले आणि frozen केले जाते, त्यामुळे कोणतीही request मध्येच चुकून एखादे flag बदलू शकत नाही.
  • Config reload एक संपूर्ण नवीन Config तयार करते आणि reference अणुरूपात (atomically) बदलते, जिवंत Config कधीही संपादित न करता.
  • ते कधीही बदलत नसल्याने, हजारो एकाच वेळी होणाऱ्या reads ना कोणत्याही locks किंवा बचावात्मक copying ची गरज नसते.
✅ निकाल: प्रत्येक deploy मागे निर्धारक (deterministic) वर्तन, reference बदलाद्वारे सुरक्षित hot reloads, आणि सर्वात व्यस्त read path वर कोणतीही lock स्पर्धा नाही.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Immutability हा functional programming चा अवशेष नाही; आधुनिक concurrent आणि reactive systems कशी बरोबर राहतात याच्या केंद्रस्थानी तो आहे.

⚛️ Reactive UI state

React सारखी frameworks immutable state वर अवलंबून असतात जेणेकरून change detection ही एक स्वस्त reference तुलना बनते. नवीन state म्हणजे एक नवीन object, कधीही जागच्या जागी संपादन नाही.

🧵 Locks शिवाय concurrency

जसजशी core संख्या वाढते, तसतसे mutable data ला locks ने राखण्यापेक्षा immutable data sharing करणे चांगले ठरते. Value objects threads आणि actors मध्ये सुरक्षितपणे पास होतात.

🗃️ Event sourcing

Immutable events हे सत्याचे स्रोत असतात; state म्हणजे इतिहासावरील एक fold. काहीही overwrite होत नाही, त्यामुळे audit आणि replay अंगभूतच असतात.

📦 Persistent data structures

Structural sharing immutable maps आणि lists ना जवळपास mutable कामगिरी देते, त्यामुळे functional updates मोठ्या प्रमाणातही स्वस्त राहतात.

🧊 भाषा समर्थन

Java मधील Records, Kotlin मधील data classes, Python मधील frozen dataclasses, आणि TypeScript मधील readonly immutability ला एक first-class, कमी-सोपस्कार default बनवतात.

🔎 Caching आणि CDNs

Immutable, content-addressed मूल्ये सहजपणे cacheable असतात, तोच गुणधर्म जो hashed asset URLs ना कायमस्वरूपी ठेवण्यास सुरक्षित बनवतो.

सारांश: Immutability shared state ला धोक्यातून मालमत्तेत बदलते. कधीही न बदलणारी objects तयार करा, बदलण्याऐवजी बदला (replace) करा, आणि concurrency व aliasing bugs चे संपूर्ण वर्ग घडणेच बंद होतात.
