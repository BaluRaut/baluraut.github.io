Behavioral पॅटर्न

Mediator पॅटर्न - तारांच्या गुंत्याऐवजी एकच केंद्र

जेव्हा अनेक ऑब्जेक्ट एकमेकांशी थेट बोलतात, तेव्हा प्रत्येक नवीन सहभागी कनेक्शनची संख्या वाढवतो आणि कोडबेस स्पॅगेटीसारखा गुंतागुंतीचा होतो. Mediator पॅटर्न तो संवाद एकाच ऑब्जेक्टमध्ये हलवतो: colleagues एकमेकांचा संदर्भ घेणे थांबवतात आणि त्याऐवजी एका mediator ला सूचित करतात, जो कोणी प्रतिक्रिया द्यायची आणि कशी हे ठरवतो. Many-to-many coupling हे many-to-one मध्ये कोसळते.

01 - काय

Mediator पॅटर्न म्हणजे काय?

Mediator हा एक behavioral डिझाइन पॅटर्न आहे जो असा एक ऑब्जेक्ट परिभाषित करतो जो अनेक ऑब्जेक्ट एकमेकांशी कसे संवाद साधतात हे encapsulate करतो. प्रत्येक ऑब्जेक्टने आपल्या शेजारच्यांचे थेट संदर्भ ठेवण्याऐवजी आणि त्यांना कॉल करण्याऐवजी, ते ऑब्जेक्ट (ज्यांना colleagues म्हणतात) फक्त mediator ला ओळखतात. काही घडले की एक colleague mediator ला सांगतो, आणि mediator बाकीचे समन्वय साधतो. यामुळे कनेक्शनचे दाट जाळे hub-and-spoke आकारात बदलते.

🧑‍🤝‍🧑 Colleagues

वैयक्तिक components (form fields, चॅट वापरकर्ते, UI widgets). ते इव्हेंट उत्पन्न करतात आणि सूचनांना प्रतिसाद देतात, पण एकमेकांना कधीही थेट कॉल करत नाहीत.

🎛️ Mediator

मध्यवर्ती समन्वयक. तो colleagues चे संदर्भ ठेवतो आणि पूर्वी त्यांच्यात विखुरलेली असणारी interaction logic स्वतःमध्ये सामावतो.

🔌 The interface

एक सामायिक करार (बहुतेक वेळा एकच notify(sender, event) method) जेणेकरून colleagues त्याचा concrete प्रकार न ओळखता mediator ला संकेत देऊ शकतात.

02 - का

Mediator पॅटर्न का अस्तित्वात आहे

एका ऑब्जेक्टकडून दुसऱ्याला थेट संदर्भ देणे सुरुवातीला नैसर्गिक वाटते, पण ते चांगले scale होत नाही. n ऑब्जेक्ट मुक्तपणे बोलत असतील तर तुमच्याकडे साधारण n squared इतकी कनेक्शन असू शकतात, आणि त्यातील प्रत्येक अशी जागा आहे जिथे एक बदल पसरू शकतो. Mediator तो quadratic गुंता एका linear spokes च्या संचाशी बदलतो.

🕸️ Many-to-many coupling नष्ट करतो

प्रत्येक colleague फक्त mediator वर अवलंबून असतो, इतर प्रत्येक colleague वर नाही. एखादा सहभागी जोडणे किंवा काढणे यासाठी डझनभर कनेक्शन पुन्हा जोडण्याऐवजी एका class ला स्पर्श करावा लागतो.

🧭 Control flow केंद्रित करतो

"काय कशाशी बोलते, आणि केव्हा" याचे नियम एका वाचनीय जागी राहतात, त्यामुळे interaction logic असंबंधित components मध्ये लपणे थांबते.

♻️ colleagues पुनर्वापरयोग्य बनवतो

एखादा button किंवा field आपल्या शेजारच्यांना यापुढे hardcode करत नसल्यामुळे, तुम्ही तोच component वेगळ्या mediator असलेल्या वेगळ्या dialog मध्ये टाकू शकता.

🧪 चाचणी आणि बदल सोपे

तुम्ही एका mock mediator सह colleague ची unit-test करू शकता, आणि कोणत्याही colleague ला संपादित न करता mediator बदलून समन्वयाचे वर्तन बदलू शकता.

सोप्या शब्दांत

उपमांसह Mediator समजावून

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असा, ते नीट समजेल.

🎓 विद्यार्थ्यासाठी

एका गटचर्चा चालवणाऱ्या शिक्षकाचा विचार करा. विद्यार्थी एकमेकांवर ओरडत नाहीत; ते हात वर करतात आणि पुढे कोण बोलणार हे शिक्षक ठरवतात. वीस विद्यार्थ्यांना एक शिक्षक लागतो, दोनशे बाजूच्या संभाषणांची गरज नाही.

👩‍💻 डेव्हलपरसाठी

हा एक चॅट-रूम सर्व्हर आहे. क्लायंट एकमेकांशी sockets उघडत नाहीत; ते room ला संदेश पाठवतात आणि room तो प्रसारित करतो. एक नवीन वापरकर्ता जोडा आणि तुम्ही एकच कनेक्शन नोंदवता, प्रत्येक विद्यमान वापरकर्त्यासाठी एक नाही.

🏢 व्यावसायिकासाठी

एका हवाई वाहतूक नियंत्रकाची कल्पना करा. वैमानिक runways बाबत एकमेकांशी थेट वाटाघाटी करत नाहीत; ते टॉवरशी बोलतात, आणि टॉवर सर्वांचा क्रम लावतो. एक अधिकारी peer-to-peer रेडिओ कॉलच्या गोंधळाची जागा घेतो.

📞 दैनंदिन आवृत्ती

एक जुना टेलिफोन स्विचबोर्ड ऑपरेटर. कॉल करणारे स्वतःच्या तारा जोडत नाहीत; ते ऑपरेटरला विचारतात, जो योग्य लाइन जोडतो. "कोण कोणापर्यंत पोहोचतो" याची गुंतागुंत ऑपरेटरकडे असते.

03 - कसे

अंतर्गत कसे कार्य करते

एक colleague आपल्या शेजारच्यांना कधीही import करत नाही. तो एकच field ठेवतो: mediator चा संदर्भ. state बदलली की तो mediator.notify(this, event) कॉल करतो, आणि concrete mediator समन्वयाची logic चालवतो आणि ज्या colleagues ना गरज आहे त्यांच्याकडे updates पाठवतो.

📨 Colleague कडून mediator कडे

एक colleague वरच्या दिशेने एक इव्हेंट कळवतो: "मी बदललो" किंवा "माझ्यावर क्लिक झाले." तो sender म्हणून स्वतःला पाठवतो जेणेकरून mediator ला स्रोत कळेल, आणि तो सूचनांची वाट पाहतो.

🎚️ Mediator कडून colleagues कडे

mediator इव्हेंट तपासतो, नियम लागू करतो (validation, सक्षम करणे, प्रसारण), आणि ज्या विशिष्ट colleagues ना प्रतिक्रिया द्यायची आहे त्यांच्यावर methods कॉल करतो.

Java मध्ये एक dialog form

// The contract every colleague uses to talk to the hub
interface Mediator {
    void notify(Component sender, String event);
}

// Colleagues know only the mediator, never each other
abstract class Component {
    protected Mediator mediator;
    Component(Mediator mediator) { this.mediator = mediator; }
}

class TextBox extends Component {
    private String text = "";
    TextBox(Mediator m) { super(m); }
    void type(String value) {
        this.text = value;
        mediator.notify(this, "changed");   // report upward
    }
    String getText() { return text; }
}

class Button extends Component {
    private boolean enabled = false;
    Button(Mediator m) { super(m); }
    void setEnabled(boolean e) { this.enabled = e; }
    boolean isEnabled() { return enabled; }
}

// The concrete mediator holds the interaction rules in ONE place
class LoginDialog implements Mediator {
    private final TextBox username = new TextBox(this);
    private final TextBox password = new TextBox(this);
    private final Button submit = new Button(this);

    public void notify(Component sender, String event) {
        if (event.equals("changed")) {
            boolean ready = !username.getText().isBlank()
                         && password.getText().length() >= 8;
            submit.setEnabled(ready);       // coordinate the peers
        }
    }

    public TextBox username() { return username; }
    public TextBox password() { return password; }
    public Button submit()    { return submit; }
}

// Usage
LoginDialog dialog = new LoginDialog();
dialog.username().type("ada");
dialog.password().type("hunter2secret");
// submit is now enabled - the fields never touched each other

लक्षात घ्या की TextBox आणि Button मध्ये कोणतेही परस्पर संदर्भ नाहीत. "दोन्ही fields वैध असतील तेव्हा submit सक्षम करा" हा नियम फक्त LoginDialog.notify मध्ये अस्तित्वात आहे, त्यामुळे तो नियम बदलणे म्हणजे एका फाइलमधील संपादन आहे.

सामान्य अडचणी

अडचणी आणि anti-patterns

Mediator चा अतिरेक करणे सोपे आहे. या अशा अपयशाच्या पद्धती आहेत ज्या स्वच्छ केंद्राला पुन्हा गोंधळात बदलतात.

👑 god object

सर्वात मोठा धोका. तुम्ही colleagues मधून काढलेली सर्व logic mediator मध्ये जमा होते जोपर्यंत त्याला सर्व काही माहीत असते आणि तो सर्व काही करतो. तो अस्पर्श्य होण्यापूर्वी त्याला वैशिष्ट्यानुसार विभागा किंवा sub-mediators काढा.

🔗 concretes शी लपलेले coupling

जर mediator अगदी विशिष्ट colleague प्रकारांवर अगदी विशिष्ट methods कॉल करत असेल, तर colleagues आणि mediator घट्ट बांधले जातात. जिथे शक्य असेल तिथे mediator ला interfaces वर प्रोग्रॅम करत ठेवा.

🌀 साध्या प्रकरणांवर अतिवापर

स्वच्छपणे बोलणाऱ्या दोन ऑब्जेक्टना केंद्राची गरज नाही. क्षुल्लक one-to-one संबंधासाठी mediator आणल्याने फक्त indirection आणि सांभाळण्यासाठी एक class वाढते.

🧵 इव्हेंट सूप

event नावांवर मोठ्या if-else असलेला एकच stringly-typed notify समजायला कठीण होतो. branching वाढल्यावर typed events किंवा dispatch map वापरा.

🔁 Notification loops

एक colleague mediator ला सूचित करतो, जो दुसऱ्या colleague ला update करतो, जो परत सूचित करतो, अशी अनंत साखळी. re-entrant updates आणि अनंत प्रतिध्वनी विरुद्ध सांभाळ करा.

🕳️ मागोवा हरवणे

परस्परसंवाद अप्रत्यक्ष असल्यामुळे, mediator मार्गे एक वापरकर्ता क्रिया अनुसरणे थेट कॉलपेक्षा कठीण असू शकते. events ना चांगली नावे द्या आणि प्रवाह log करा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Mediator ही एक coupling ची तडजोड आहे: dependencies विकेंद्रित करण्यासाठी तुम्ही गुंतागुंत केंद्रित करता. तुम्ही काय विकत घेत आहात हे जाणून घ्या.

पैलूतपशील
फायदेMany-to-many coupling हे many-to-one पर्यंत कमी करतो, interaction logic केंद्रित करतो, colleagues पुनर्वापरयोग्य आणि चाचणीयोग्य बनवतो, आणि सहभागी जोडणे स्वस्त करतो.
तोटेmediator god object मध्ये वाढू शकतो, control flow अप्रत्यक्ष आणि मागोवा घ्यायला कठीण होते, आणि तो एक class अधिक indirection चा एक थर जोडतो.
केव्हा वापरावेऑब्जेक्टचा एक गट गुंतागुंतीच्या, गोंधळलेल्या मार्गांनी संवाद साधतो; तुम्हाला components स्वतंत्रपणे पुनर्वापर करायचे आहेत; किंवा interaction नियम वारंवार बदलतात आणि एका जागी राहावेत.
केव्हा टाळावेसंबंध साधे किंवा one-to-one असतात, समन्वयाची logic क्षुल्लक असते, किंवा केंद्रीकरण फक्त एक bottleneck class तयार करेल जो कोणालाही सांभाळायचा नसतो.
गुंतागुंतआणण्यासाठी कमी ते मध्यम. चालू खर्च म्हणजे mediator ची वाढ अशी सांभाळणे की तो कचरा साठवण्याचे ठिकाण न होता cohesive राहील.
संबंधितObserver (notification यंत्रणा), Facade (सोपे प्रवेश), Command (encapsulated requests), Colleague आणि coupling कमी करण्याची तत्त्वे.
अंगठ्याचा नियम: जेव्हा ऑब्जेक्टमधील कनेक्शन ही समस्या असते, स्वतः ऑब्जेक्ट नाहीत, तेव्हा Mediator कडे वळा. तुम्ही dependency graph काढू शकत असाल आणि तो एकमेकांना छेदणाऱ्या रेषांच्या गोंधळासारखा दिसत असेल, तर एक केंद्र तो सरळ करेल. तो आधीच स्वच्छ tree असेल, तर त्याला तसाच राहू द्या.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

तीन प्रातिनिधिक ठिकाणे जिथे Mediator पॅटर्न आपली किंमत सिद्ध करतो.

🖥️

1 · GUI dialogs आणि forms

पॅटर्न: dialog controller द्वारे समन्वित components

एका settings dialog मध्ये date pickers सक्षम करणारी checkboxes असतात, save button ला अटी घालणारी fields असतात, आणि panels बदलणारे radio groups असतात.

  • प्रत्येक widget आपल्या शेजारच्यांना ढोसण्याऐवजी बदल एका dialog mediator ला कळवतो.
  • mediator सर्व enable, disable, आणि validation नियम एका method मध्ये ठेवतो.
  • तेच widgets वेगळ्या mediator सह इतर dialogs मध्ये पुनर्वापरले जातात.
✅ निकाल: interaction नियम एका class मध्ये वाचनीय असतात, आणि नवीन field जोडणे म्हणजे प्रत्येक विद्यमान widget नाही तर mediator संपादित करणे.
💬

2 · चॅट रूम आणि संदेशवहन

पॅटर्न: एक room सर्व सहभागींच्या संदेशांची दलाली करते

गट चॅटमधील वापरकर्त्यांनी प्रत्येक वैयक्तिक शेजाऱ्याशी कनेक्शन न उघडता इतर सर्वांपर्यंत पोहोचायचे असते.

  • प्रत्येक वापरकर्ता room ला पाठवतो; room वितरण, क्रम, आणि filtering ठरवते.
  • नवीन वापरकर्ते room कडे एकदाच नोंदवतात, प्रत्येक विद्यमान वापरकर्त्यासाठी एकदा नाही.
  • mute, history, आणि moderation सारखी वैशिष्ट्ये clients मध्ये नाही तर room मध्ये राहतात.
✅ निकाल: वापरकर्ता जोडणे हे O(1) जोडणी आहे, आणि cross-cutting वैशिष्ट्ये प्रत्येक client मध्ये नाही तर mediator मध्ये बसतात.
✈️

3 · हवाई वाहतूक आणि dispatch नियंत्रण

पॅटर्न: एक controller स्वतंत्र actors चा क्रम लावतो

विमाने (किंवा ride-share drivers, किंवा warehouse robots) यांनी स्पर्धेच्या परिस्थितीत हालचालीचा समन्वय peer to peer करू नये.

  • प्रत्येक actor आपले स्थान आणि हेतू एका मध्यवर्ती controller ला कळवतो.
  • controller संघर्ष सोडवतो आणि प्रत्येक actor ला परत सूचना देतो.
  • actors साधे आणि परस्पर बदलण्यायोग्य राहतात; समन्वय धोरण एका जागी असते.
✅ निकाल: सुरक्षित, ऑडिट करण्यायोग्य क्रमवारी जिथे कठीण logic केंद्रित आणि चाचणीयोग्य असते, आणि actors ना एकमेकांचे कोणतेही ज्ञान नसते.
07 - सुसंगतता

आधुनिक सुसंगतता

Mediator ची कल्पना आधुनिक software मध्ये सर्वत्र आहे, बहुतेक वेळा वेगळ्या नावांखाली, कारण loose coupling कधीही जुनी झाली नाही.

🧩 Front-end state stores

Redux-शैलीचे stores आणि event buses हे mediators आहेत: components एकमेकांना थेट बदलण्याऐवजी एका मध्यवर्ती store कडे actions dispatch करतात.

📮 Message brokers

Kafka, RabbitMQ, आणि service buses हे वितरित mediators आहेत, जे producers ना consumers पासून decouple करतात जेणेकरून एकाला दुसऱ्याचे अस्तित्व माहीत नसते.

🎯 MediatR लायब्ररी

.NET जगात, in-process mediators requests हे handlers कडे मार्गस्थ करतात, controllers पातळ ठेवत आणि समन्वय केंद्रित ठेवत.

🕹️ microservices मधील orchestration

Orchestrators बहु-service workflows चा समन्वय साधतात जेणेकरून वैयक्तिक services व्यापक choreography बद्दल अनभिज्ञ राहतात.

🤖 Multi-agent systems

specialist agents कडे tasks मार्गस्थ करणारा एक orchestrator agent हा एक mediator आहे, जो agents ना एकमेकांपासून decoupled ठेवतो.

⚠️ चिरंतन इशारा

प्रत्येक प्रमाणावर तोच इशारा लागू होतो: परस्परसंवाद केंद्रित करा, पण केंद्राला god object किंवा single point of failure मध्ये फुगू देऊ नका.

सारांश: Mediator हा असा मार्ग आहे ज्याने तुम्ही परस्परसंवाद करणाऱ्या ऑब्जेक्टचा गोंधळ त्यांच्या संभाषणाला एकच घर देऊन आवरता. शिस्तीने वापरल्यास तो quadratic coupling हे linear, वाचनीय समन्वयात बदलतो; निष्काळजीपणे वापरल्यास तो फक्त गोंधळ एका अवाढव्य class मध्ये हलवतो.
