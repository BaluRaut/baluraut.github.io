Objects आणि Classes - blueprints आणि त्यांतून तयार होणारी instances

एक class म्हणजे blueprint: object कोणता डेटा साठवतो आणि तो काय करू शकतो हे ती जाहीर करते. एक object म्हणजे त्या blueprint मधून बनवलेली जिवंत instance, जिचे स्वतःचे state आणि स्वतःची identity असते. हा फरक नीट समजला की OOP मधले बाकी सगळे - encapsulation, inheritance, polymorphism - आपोआप जागी बसते.

01 - काय

Objects आणि classes म्हणजे काय?

एक class एक प्रकार (type) व्याख्यायित करते: प्रत्येक instance जी fields बाळगेल आणि प्रत्येक instance जी methods चालवू शकेल. एक object म्हणजे त्या type ची एक ठोस instance, जी runtime ला तयार होते. एका shopping Cart class चा विचार करा जी "एका cart मध्ये line items असतात आणि ती त्यांना जोडू किंवा त्यांची बेरीज करू शकते" असे वर्णन करते, आणि दुसरीकडे Ada सध्या भरत असलेली प्रत्यक्ष cart जिच्यात तीन items आहेत.

📐 Class = blueprint

एकदाच लिहिलेला साचा. ती fields आणि methods यांना नाव देते पण स्वतः कोणताही जिवंत डेटा बाळगत नाही. class Cart { ... } ही एक योजना आहे, खरेदी नव्हे.

🛒 Object = instance

blueprint मधून new ने बनवलेली एक ठोस गोष्ट. एकाच class पासून बनवलेल्या दोन carts म्हणजे स्वतंत्र आशयाची दोन वेगळी objects.

🆔 Identity

प्रत्येक object चा स्वतःचा reference असतो. एकसारखे items असलेल्या दोन carts तरीही वेगळी objects असतात; आशयाची समानता म्हणजे तेच object असणे नव्हे.

एक object ज्या तीन गोष्टी एकत्र बांधतो

02 - का

Classes आणि objects का अस्तित्वात आहेत

संबंधित डेटा आणि त्यावर काम करणाऱ्या क्रिया एकत्र बांधल्याने प्रणाली वाढत असतानाही ती समजण्याजोगी राहते. सर्वत्र फिरणाऱ्या सैल dictionaries ऐवजी तुम्हाला नावे असलेली types मिळतात जी स्वतःचे नियम स्वतः जपतात.

🧱 डोमेनचे प्रतिरूप

Classes मुळे कोड व्यवसायाचे प्रतिबिंब बनतो: एक Account, एक Cart, एक Invoice. वाचणारे कच्चे maps आणि tuples उलगडण्याऐवजी संकल्पना थेट types शी जोडतात.

🔒 Invariants एकाच ठिकाणी

फक्त Account च्या methods त्याला हात लावू शकत असतील तर balance कधीच ऋण होऊ शकत नाही. संहितेत सर्वत्र तपासण्या विखुरण्याऐवजी class स्वतःच्या नियमांची एकमेव रक्षक बनते.

♻️ copy-paste शिवाय पुनर्वापर

blueprint एकदाच व्याख्यायित करा आणि हजारो instances तयार करा. प्रत्येक cart तेच तपासलेले behavior वाटून घेते; तुम्ही bug एकाच ठिकाणी दुरुस्त करता, प्रत्येक प्रतीत नव्हे.

🧩 पुढे बांधण्यासाठी शब्दसंग्रह

Objects आणि classes हा पाया आहे ज्यावर बाकीचे स्तंभ उभे असतात: encapsulation fields लपवते, inheritance blueprints वाटून घेते, polymorphism सामायिक type मागे instances बदलते.

सोप्या शब्दांत

Objects आणि Classes उपमांसह समजावून

तीच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असलात तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

Class म्हणजे अभ्यासक्रम (syllabus); object म्हणजे तुम्ही नोंदणी केलेली तुकडी. अभ्यासक्रम कोर्समध्ये काय आहे ते सांगतो; तुमच्या तुकडीत खरे विद्यार्थी, खरी खोली आणि स्वतःची हजेरी असते. अनेक तुकड्या, एकच अभ्यासक्रम.

👩‍💻 डेव्हलपरसाठी

Class म्हणजे एक struct आणि त्यावर काम करणारी functions, एकत्र जोडलेली. Constructor ही factory function आहे जी initialized मूल्य परत करते; methods म्हणजे अशा functions ज्यांचा पहिला छुपा argument म्हणजे instance स्वतः.

🏢 व्यावसायिकासाठी

Class म्हणजे नोकरीचे वर्णन (job description); object म्हणजे त्या भूमिकेत नेमलेली व्यक्ती. वर्णन जबाबदाऱ्या आणि डेटा (पदनाम, वेतनश्रेणी) ठरवते; प्रत्येक नेमणूक हे काम करणारी एक वेगळी व्यक्ती असते.

🏦 रोजच्या जीवनातील रूप

बँकेचा खाते-उघडण्याचा अर्ज म्हणजे class: कोणती fields असतील आणि तुम्ही काय करू शकता हे तो ठरवतो. स्वतःचा क्रमांक आणि balance असलेले तुमचे प्रत्यक्ष खाते म्हणजे त्या अर्जातून तयार झालेले object.

03 - कसे

अंतर्गत ते कसे चालते

एक class व्याख्यायित केल्याने एक type नोंदवला जातो. Constructor कॉल केल्याने एक नवीन object वाटप होते, त्याची fields ठरवण्यासाठी initializer चालतो आणि एक reference परत मिळतो. मग method कॉल्स त्या reference मधून instance च्या स्वतःच्या state पर्यंत पोहोचण्यासाठी this किंवा self वापरून dispatch होतात.

🏗️ Instance members

प्रत्येक object च्या मालकीच्या fields आणि methods. this.balance प्रत्येक instance साठी वेगळे असते; प्रत्येक Account कडे स्वतःचे असते. Methods ज्या विशिष्ट object वर कॉल झाल्या त्याचेच state वाचतात आणि बदलतात.

📌 Static / class members

class च्या स्वतःच्या मालकीचा, सर्व instances मध्ये वाटलेला डेटा आणि behavior: Account.MIN_BALANCE सारखे constants, counters, किंवा Account.open() सारख्या factory methods ज्या नवीन objects बनवून परत करतात.

Class आणि तिची objects एका दृष्टिक्षेपात

एक Cart class, तिचे instance आणि static members, आणि तिच्यातून तयार झालेली दोन जिवंत objects

// A bank Account: state, behavior, identity, and a static factory.
class Account {
  // static/class member: shared by every instance
  static readonly MIN_BALANCE = 0;
  private static nextId = 1;

  // instance state (fields)
  readonly id: number;
  private balance: number;

  // constructor: initializes a fresh instance
  constructor(private readonly owner: string, opening: number) {
    if (opening < Account.MIN_BALANCE) {
      throw new Error("Opening balance cannot be negative");
    }
    this.id = Account.nextId++;   // identity, assigned once
    this.balance = opening;
  }

  // behavior: methods act on this instance's state via `this`
  deposit(amount: number): void {
    this.balance += amount;
  }

  withdraw(amount: number): void {
    if (amount > this.balance) throw new Error("Insufficient funds");
    this.balance -= amount;
  }

  getBalance(): number {
    return this.balance;
  }

  // static factory method: builds and returns a new object
  static open(owner: string): Account {
    return new Account(owner, 0);
  }
}

// create objects (instances) from the blueprint
const ada = new Account("Ada Lovelace", 100);
const liam = Account.open("Liam Reyes");

// call methods on each independent object
ada.deposit(50);
ada.withdraw(30);

console.log(ada.id, ada.getBalance());   // 1 120
console.log(liam.id, liam.getBalance()); // 2 0
console.log(ada === liam);               // false: distinct identities

# A bank Account: state, behavior, identity, and a static factory.
class Account:
    # class member: shared by every instance
    MIN_BALANCE = 0
    _next_id = 1

    # constructor: initializes a fresh instance
    def __init__(self, owner: str, opening: float):
        if opening < Account.MIN_BALANCE:
            raise ValueError("Opening balance cannot be negative")
        self.id = Account._next_id      # identity, assigned once
        Account._next_id += 1
        self._owner = owner
        self._balance = opening         # instance state (fields)

    # behavior: methods act on this instance via `self`
    def deposit(self, amount: float) -> None:
        self._balance += amount

    def withdraw(self, amount: float) -> None:
        if amount > self._balance:
            raise ValueError("Insufficient funds")
        self._balance -= amount

    def get_balance(self) -> float:
        return self._balance

    # classmethod factory: builds and returns a new object
    @classmethod
    def open(cls, owner: str) -> "Account":
        return cls(owner, 0)

# A bank Account: state, behavior, identity, and a static factory.
class Account
  MIN_BALANCE = 0            # class-level constant, shared by all
  @next_id = 1              # class-level state

  class << self
    attr_accessor :next_id   # class member accessors
  end

  attr_reader :id            # expose identity, keep balance private

  # constructor: initializes a fresh instance
  def initialize(owner, opening)
    raise ArgumentError, "Opening balance cannot be negative" if opening < MIN_BALANCE

    @id = self.class.next_id           # identity, assigned once
    self.class.next_id += 1
    @owner = owner
    @balance = opening                 # instance state (fields)
  end

  # behavior: methods act on this instance via `self`/@ivars
  def deposit(amount)
    @balance += amount
  end

  def withdraw(amount)
    raise "Insufficient funds" if amount > @balance

    @balance -= amount
  end

  def balance
    @balance
  end

  # class method factory: builds and returns a new object
  def self.open(owner)
    new(owner, 0)
  end
end

# create objects (instances) from the blueprint
ada  = Account.new("Ada Lovelace", 100)
liam = Account.open("Liam Reyes")

# call methods on each independent object
ada.deposit(50)
ada.withdraw(30)

puts "#{ada.id} #{ada.balance}"    # 1 120
puts "#{liam.id} #{liam.balance}"  # 2 0
puts ada.equal?(liam)              # false: distinct identities

तिन्ही एकच blueprint व्याख्यायित करतात, दोन स्वतंत्र objects तयार करतात, आणि प्रत्येकाचे खाजगी balance त्याच्या स्वतःच्या methods मधून बदलतात. लक्षात घ्या की this (TypeScript), self (Python), आणि instance variables (Ruby) हे सर्व method ज्या विशिष्ट object वर चालते त्याकडे निर्देश करतात, तर MIN_BALANCE आणि open factory class वर राहतात, प्रत्येक instance नी वाटून घेतलेले.

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

एका संकल्पनेला नाव देण्यापासून ते स्वतःचे नियम जपणारे एक जिवंत, कार्यरत object हातात असण्यापर्यंत - संपूर्ण प्रवास क्रमाने.

00
Model

type योग्य ठरणारी संकल्पना ओळखा

तुमच्या लक्षात येते की डोमेनमध्ये "एक cart" किंवा "एक account" वारंवार येत आहे. डेटा आणि नियमांसह येणारे ते वारंवार नाम म्हणजे संभाव्य class.

10
Fields

State ठरवा

प्रत्येक instance ने काय लक्षात ठेवायचे याची यादी करा: एका cart ची items आणि currency, एका account चा owner आणि balance. ही instance fields बनतात.

20
Behavior

Methods ठरवा

object आपल्या स्वतःच्या state वर काय करू शकते याची यादी करा: addItem, total, deposit, withdraw. Behavior ते स्पर्श करत असलेल्या डेटासोबतच राहते.

30
Invariants

नियमांना नाव द्या

नेहमी काय खरे असले पाहिजे ते लिहा: balance कधीच ऋण नाही, quantity नेहमी धन. class हे लागू करेल जेणेकरून कोणताही caller ते मोडू शकणार नाही.

40
Blueprint

class जाहीर करा

तिच्या fields आणि method signatures सह class Account { ... } लिहा. अजून काहीही चालत नाही; तुम्ही फक्त type व्याख्यायित केला आहे.

50
Constructor

Initializer लिहा

नवीन instance स्वतःला कसे तयार करते ते व्याख्यायित करा: inputs तपासा, एक identity द्या, सुरुवातीचे state पेरा. वैध object पर्यंत हा एकमेव प्रवेश बिंदू आहे.

60
Instantiate

एक object तयार करा

new Account("Ada", 100) कॉल करा. Memory वाटप होते, constructor चालतो, आणि तुम्हाला एका जिवंत instance चा reference परत मिळतो.

70
Identity

object ही स्वतःची गोष्ट आहे

प्रत्येक instance एक वेगळा reference बाळगते. तेवढेच balance असलेले दुसरे account तरीही एक वेगळे object असते; डेटाची समानता म्हणजे identity ची समानता नव्हे.

80
Invoke

तिच्या methods कॉल करा

संदेश पाठवा: ada.deposit(50). आत, this/self याच object कडे निर्देश करते, म्हणून फक्त ada चे balance बदलते.

90
Static

class-पातळीच्या members कडे वळा

सामायिक constants आणि factories वापरा: Account.MIN_BALANCE, Account.open(...). ही class ची मालमत्ता असते, कोणत्याही एका instance ची नव्हे.

100
Compose

Objects एकत्र काम करतात

Instances इतर instances बाळगतात आणि कॉल करतात - एक cart line items बाळगते, एक order एका account चा संदर्भ देते. या blueprints मधून तुम्ही संपूर्ण प्रणाली उभी करता.

सामान्य अडचणी

अडचणी आणि anti-patterns

Objects आणि classes शी संबंधित बहुतेक अडचणी blueprint/instance ची सीमा अस्पष्ट केल्याने किंवा class ने जपायला हवे असे state गळू दिल्याने येतात.

🩹 अशक्त (anemic) classes

फक्त सार्वजनिक fields असलेली आणि कोणतेही behavior नसलेली class म्हणजे वेषांतरातील struct. मग logic प्रत्येक caller मध्ये गळते, आणि invariants जपले जात नाहीत. methods डेटा जिथे राहतो तिथे ठेवा.

🌐 Global बदलणारे statics

प्रत्येक request चा डेटा static fields मध्ये साठवल्याने सर्व instances तो वाटून घेतात, ज्यामुळे users मध्ये गोंधळ होतो. Statics constants आणि factories साठी असतात, instance state बाळगण्यासाठी नव्हे.

🪢 this/self चा गैरवापर

TypeScript मध्ये एखादी method उघड callback म्हणून पाठवल्याने तिचे this binding हरवते; कॉलच्या वेळी instance गायब होते. Bind करा किंवा arrow methods वापरा जेणेकरून behavior आपले object जपते.

🧨 खूप काही करणारे constructors

Network कॉल्स किंवा जड काम करणारा constructor objects बांधणे आणि तपासणे कठीण करतो. तो फक्त inputs तपासणे आणि state ठरवणे यापुरता ठेवा; side effects factory किंवा उघड method कडे हलवा.

🎭 equality आणि identity यांचा गोंधळ

"तेच instance" असे म्हणायचे असताना == ने objects तुलना करणे, किंवा "तेच मूल्य" असे म्हणायचे असताना reference-तुलना करणे, सूक्ष्म bugs निर्माण करते. तुम्हाला काय हवे ते ठरवा आणि जाणीवपूर्वक अंमलात आणा.

🏰 God objects

संपूर्ण डोमेनचे प्रतिरूप करणारी एकच class - एक Cart जी payments, shipping आणि email सुद्धा करते - बदलण्याजोगी राहत नाही. जबाबदाऱ्या केंद्रित, एकत्र काम करणाऱ्या classes मध्ये विभागा.

संकेत आणि मापदंड

संकेत आणि कसे मोजायचे

तुम्ही "objects" ला क्वचितच थेट गुण देता, पण हे संकेत तुम्हाला सांगतात की तुमच्या classes आपला भार उचलत आहेत की नाही.

संकेततो तुम्हाला काय सांगतो
प्रति class methods विरुद्ध सार्वजनिक fieldsभरपूर उघड fields आणि कमी methods म्हणजे अशक्त, behavior-रहित classes जी logic callers कडे गळू देतात.
Production पर्यंत पोहोचणारी invariant उल्लंघनेअवैध objects (ऋण balances, रिकामी आवश्यक fields) runtime ला अस्तित्वात असतील, तर बांधणी किंवा methods state जपत नाहीत.
object च्या fields थेट बदलणाऱ्या जागाएका field वर अनेक बाह्य लिहिणारे म्हणजे encapsulation मोडले आहे आणि class यापुढे स्वतःच्या state ची मालक नाही.
Constructor ची गुंतागुंत / side effectsजड किंवा effect असलेले constructors दर्शवतात की objects वेगळेपणाने तयार करणे आणि तपासणे कठीण आहे.
Runtime ला बदलणारे static stateConstants पलीकडचे बदलणारे statics छुपे सामायिक state आणि संभाव्य concurrency bugs चे संकेत देतात.
Class चा आकार आणि जबाबदाऱ्यावाढणारी ओळींची संख्या आणि अनेक असंबंधित methods विभागायला हव्या अशा god object कडे इशारा करतात.
अंगठ्याचा नियम: एक निरोगी class फक्त वैध state मध्येच तयार करता येते आणि फक्त तिच्या स्वतःच्या methods मधूनच बदलता येते. callers जर तुटलेली instance बांधू शकत असतील किंवा तिच्या fields ना थेट हात लावू शकत असतील, तर blueprint आपले काम करत नाही.
06 - प्रकरण अभ्यास

वास्तविक जगातील प्रकरण अभ्यास

तीन production-शैलीच्या प्रणाली जिथे class/object हा फरक खरे काम करतो.

🛒

1 · e-commerce backend मधील checkout carts

Pattern: एक class, लाखो स्वतंत्र instances

एक retail platform प्रत्येक ग्राहकाची cart एकाच Cart class ची instance म्हणून प्रतिरूपित करते जी एकाच वेळी वाहतूक हाताळते.

  • प्रत्येक सक्रिय session स्वतःचे Cart object खाजगी line items आणि totals सह बाळगते; instances कधीच state वाटून घेत नाहीत.
  • addItem आणि applyCoupon quantity आणि stock invariants class च्या आत लागू करतात, controllers मध्ये नव्हे.
  • एक static Cart.fromSavedOrder factory साठवलेल्या order मधून cart पुन्हा उभी करते, बांधणीचे नियम एकाच ठिकाणी ठेवत.
✅ परिणाम: हजारो एकाच वेळी चालणाऱ्या carts वेगळ्या आणि सुसंगत राहतात, कारण प्रत्येक हे स्वतःचा आशय जपणारे एक वेगळे object असते.
🏦

2 · banking core मधील ledger accounts

Pattern: identity आणि invariants प्रथम-श्रेणीच्या चिंता म्हणून

एक payments प्रणाली प्रत्येक ग्राहकाचे balance ledger भर स्थिर identity असलेले Account object म्हणून दर्शवते.

  • प्रत्येक account ला बांधणीच्या वेळी दिलेला अपरिवर्तनीय id असतो; transfers accounts ना identity ने संदर्भित करतात, balances जुळवून कधीच नाही.
  • debit आणि credit हेच balance बदलणारे एकमेव मार्ग आहेत, म्हणून "कधीच overdraw नाही" हा नियम सर्वत्र टिकतो.
  • class-पातळीचे constants (किमान balance, currency ची अचूकता) प्रत्येक account नी वाटून घेतलेले static members म्हणून राहतात.
✅ परिणाम: पैशाच्या हालचाली तपासण्याजोग्या आणि अचूक राहतात कारण identity आणि invariants object स्वतः लागू करते.
🔔

3 · delivery service मधील notification messages

Pattern: factories नी तयार केलेली मूल्य-वाहक objects

एक notifications platform email, SMS आणि push वरील प्रत्येक बाहेर जाणाऱ्या संदेशासाठी एक Notification object बनवते.

  • प्रत्येक संदेश स्वतःचा recipient, channel आणि payload असलेली एक instance असते; class आपल्या constructor मध्ये आवश्यक fields तपासते.
  • Notification.forPasswordReset सारख्या static factories सामान्य घटनांसाठी योग्य आकाराची instances जुळवतात.
  • render आणि markSent सारखे behavior फक्त त्या instance च्या state वर this द्वारे काम करते.
✅ परिणाम: लाखो स्वतंत्र message objects pipeline मधून वाहतात, प्रत्येक स्वयंपूर्ण आणि अर्धवट तयार करणे अशक्य.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Functional आणि data-केंद्रित शैलींच्या मध्येही, class/object हा फरक state आणि behavior रचण्याचा एक मूलभूत मार्ग राहतो.

🧊 अपरिवर्तनीय (immutable) objects आणि records

आधुनिक भाषा अशी objects पसंत करतात जी तुम्ही वैध बनवता आणि कधीच बदलत नाही. blueprint ची कल्पना टिकते; तुम्ही जागेवरच्या बदलांऐवजी नवीन instances तयार करता.

🧬 Data classes आणि case classes

Python, Kotlin आणि Scala मधील संक्षिप्त class वाक्यरचना type आणि त्याचा डेटा ठेवते पण boilerplate कमी करते, ज्यामुळे छोटी value objects व्याख्यायित करणे स्वस्त होते.

🧭 Domain-driven design

Entities (identity महत्त्वाची) विरुद्ध value objects (फक्त डेटा महत्त्वाचा) हा नेमका class/object/identity चा फरक खऱ्या डोमेनवर लागू केलेला आहे.

⚙️ service सीमांवरील objects

Functional cores सुद्धा I/O आणि connections - clients, sessions, repositories - objects म्हणून गुंडाळतात, कारण ते नैसर्गिकरित्या state आणि behavior बाळगतात.

🧰 खोल पदानुक्रमांपेक्षा composition

संघ आता लांब inheritance साखळ्यांऐवजी छोटे सहकारी एकत्र करून objects बांधतात, पण composition चे एकक अजूनही class च आहे.

🔎 Type systems चांगल्या classes ना बक्षीस देतात

समृद्ध types आणि pattern matching नीट व्याख्यायित classes अधिक सुरक्षित आणि अभिव्यक्तिशील करतात, compile वेळीच अवैध instances पकडतात.

सारांश: classes आणि objects म्हणजे OOP ची मुळाक्षरे. blueprint-विरुद्ध-instance हा फरक, state/behavior/identity ही त्रयी, आणि instance-विरुद्ध-static हे विभाजन नीट समजून घ्या, म्हणजे प्रत्येक उच्च pattern त्यांतून बनलेले एक नैसर्गिक वाक्य होते.
