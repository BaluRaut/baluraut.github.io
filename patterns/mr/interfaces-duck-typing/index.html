Interfaces आणि duck typing - class ला नव्हे तर contract ला अनुसरून कोड लिहिणे

Interface म्हणजे एक contract: methods चा असा संच ज्यावर caller अवलंबून राहू शकतो, त्यामागचा concrete type माहीत नसतानाही. भाषा तो contract नावाने (nominal) तपासो की आकाराने (structural), फायदा एकच असतो - तुमचा checkout कोड एका PaymentGateway शी बोलतो, आणि caller ची एकही ओळ न बदलता Stripe किंवा PayPal अदलाबदल करता येते.

01 - काय

Interfaces आणि duck typing म्हणजे काय?

एक interface (किंवा protocol) methods चा संच आणि त्यांच्या signatures नाव देतो, पण ते कसे काम करतात हे सांगत नाही. जो कोणताही object त्या methods पुरवतो तो contract पूर्ण करतो. Duck typing हे याच्या तार्किक टोकापर्यंत नेते: जर एखादा object बदकासारखा चालतो आणि बदकासारखा quack करतो, तर runtime त्याला बदक मानतो, कोणतेही घोषित interface लागत नाही. दोन्हीही calling कोडला object काय करू शकतो यावर अवलंबून ठेवतात, तो कोणता class आहे यावर नव्हे.

📜 Contract

Interface सांगतो की एका collaborator ने कोणत्या methods उघड्या ठेवल्या पाहिजेत, जसे charge(amount, token) आणि refund(chargeId). Caller आकारावर विश्वास ठेवतो, स्रोतावर नव्हे.

🏷️ Nominal typing

Type तेव्हाच अनुरूप ठरतो जेव्हा तो स्पष्टपणे नावाने तसे घोषित करतो. Java आणि C# अशाच पद्धतीने चालतात: class ला implements PaymentGateway असे म्हणावे लागते.

🦆 Structural / duck typing

Type ला योग्य आकार असेल तर तो अनुरूप ठरतो, कोणतीही घोषणा लागत नाही. TypeScript compile time ला structure तपासतो; Ruby आणि Python ते call time ला तपासतात.

महत्त्वाचे मानसिक चित्र: interface म्हणजे वर्तनाबद्दलचे एक वचन. Nominal typing ते वचन एका स्वाक्षरी केलेल्या घोषणेने पडताळते; duck typing ते object प्रत्यक्षात पाळताना पाहून पडताळते. दोन्ही मार्गांनी, consumer ला concrete class कधीच माहीत असण्याची गरज नसते.
02 - का

Interfaces का अस्तित्वात आहेत

Concrete classes कोडला विशिष्ट तपशिलांशी जोडून टाकतात. Interfaces तुम्हाला फक्त गरजेचे वर्तन नाव देऊ देतात, त्यामुळे implementations अदलाबदल करण्यायोग्य, testable आणि सुरक्षितपणे विकसित करण्यायोग्य बनतात.

🔌 अदलाबदल करण्यायोग्य implementations

कोणतेही PaymentGateway स्वीकारणारा CheckoutService स्वतःच्या logic ला हात न लावता Stripe वरून PayPal कडे जाऊ शकतो, किंवा दोन्ही चालवू शकतो. Contract हाच जोडबिंदू आहे.

🧪 वेगळेपणाने testable

Consumer interface वर अवलंबून असल्याने, tests खऱ्या payment API ला न मारता calls नोंदवणारे बनावट gateway inject करतात. वेगवान, निश्चित, network नाही.

🧱 विलग modules

Teams contract वर एकमत करतात, मग दोन्ही बाजू स्वतंत्रपणे बांधतात. Billing team आणि checkout team कधीच concrete types सामायिक करत नाहीत, फक्त interface.

🔭 स्पष्ट अपेक्षा

Interface नेमके सांगतो की collaborator ने काय पुरवले पाहिजे. नवीन engineers contract वाचतात आणि class ची उलट-अभियांत्रिकी न करता काय implement करायचे हे समजतात.

सोप्या शब्दांत

Interfaces आणि duck typing उपमांसह समजावले

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असलात तरी ती पटकन समजते.

🎓 विद्यार्थ्यासाठी

Interface म्हणजे परीक्षेतील प्रश्नपत्रिका. ती सांगते की कोणत्या प्रश्नांची उत्तरे द्यावीत; तुमचे नेमके शब्द ती ठरवत नाही. ज्याची उत्तरे प्रत्येक प्रश्न व्यापतात तो विद्यार्थी उत्तीर्ण होतो, तो कसाही मांडणी करो.

👩‍💻 डेव्हलपरसाठी

हा एक प्रकारचा plug socket आहे. तुमचा checkout कोड PaymentGateway आकाराचा socket उघड करतो; Stripe आणि PayPal हे जुळणारे plugs असलेली उपकरणे आहेत. भिंतीला कोणता brand जोडता याची पर्वा नसते.

🏢 व्यावसायिकासाठी

एका job description चा विचार करा. ती एका भूमिकेने पार पाडायच्या कर्तव्यांची यादी देते. तुम्ही अंतर्गत team ठेवा की एजन्सी, जो कोणी ती कर्तव्ये करू शकतो तो ती भूमिका भरतो. Org chart भूमिकेवर अवलंबून असते, व्यक्तीवर नव्हे.

🎫 रोजच्या जीवनातील आवृत्ती

एक theme park वैध तिकीट म्हणून scan होणारी कोणतीही गोष्ट स्वीकारते. कागदाचा तुकडा, फोनवरचा barcode, किंवा wristband - turnstile वर्तन तपासतो (ते scan होते का), साहित्य नव्हे. तेच द्वारावरचे duck typing.

03 - कसे

अंतर्गत हे कसे चालते

तुम्ही एक PaymentGateway contract परिभाषित करता, दोन concrete implementations लिहिता, आणि consumer ला फक्त contract वर अवलंबून ठेवता. Conformance कसे तपासले जाते हे भाषा ठरवते: घोषणेने, structure ने, किंवा call time च्या वर्तनाने.

🧾 Contract परिभाषित करा

Consumer ला हव्या असलेल्या methods ना नाव द्या: charge(amountCents, token) एक result परत करते, refund(chargeId) तो उलटवते. HTTP, keys, किंवा vendors याबद्दल काहीही आत झिरपत नाही.

🔁 Interface ला अनुसरून प्रोग्रामिंग

CheckoutService एक PaymentGateway reference धरतो. Runtime ला तो StripeGateway किंवा PayPalGateway असतो, configuration ने निवडलेला, आणि service कधीच कोणता ते विचारत नाही.

तोच contract तीन भाषांमध्ये

// TypeScript: a nominal-looking interface checked structurally at compile time.
interface ChargeResult { id: string; ok: boolean; }

interface PaymentGateway {
  charge(amountCents: number, token: string): ChargeResult;
  refund(chargeId: string): boolean;
}

class StripeGateway implements PaymentGateway {
  constructor(private apiKey: string) {}
  charge(amountCents: number, token: string): ChargeResult {
    // POST https://api.stripe.com/v1/charges
    return { id: `ch_${token.slice(0, 6)}`, ok: amountCents > 0 };
  }
  refund(chargeId: string): boolean {
    return chargeId.startsWith("ch_");
  }
}

class PayPalGateway implements PaymentGateway {
  charge(amountCents: number, token: string): ChargeResult {
    return { id: `PAYID-${token.slice(0, 6)}`, ok: amountCents > 0 };
  }
  refund(chargeId: string): boolean {
    return chargeId.startsWith("PAYID");
  }
}

// CheckoutService is programmed to the interface, not a concrete gateway.
class CheckoutService {
  constructor(private gateway: PaymentGateway) {}
  pay(amountCents: number, token: string): ChargeResult {
    const result = this.gateway.charge(amountCents, token);
    if (!result.ok) throw new Error("Payment declined");
    return result;
  }
}

const checkout = new CheckoutService(new StripeGateway("sk_live_123"));
console.log(checkout.pay(4999, "tok_visa")); // { id: "ch_tok_vi", ok: true }

# Python: a Protocol gives structural typing; conformance is by shape, no inheritance.
from dataclasses import dataclass
from typing import Protocol

@dataclass
class ChargeResult:
    id: str
    ok: bool

class PaymentGateway(Protocol):
    def charge(self, amount_cents: int, token: str) -> ChargeResult: ...
    def refund(self, charge_id: str) -> bool: ...

class StripeGateway:  # note: no explicit base class needed
    def __init__(self, api_key: str) -> None:
        self.api_key = api_key
    def charge(self, amount_cents: int, token: str) -> ChargeResult:
        return ChargeResult(id=f"ch_{token[:6]}", ok=amount_cents > 0)
    def refund(self, charge_id: str) -> bool:
        return charge_id.startswith("ch_")

class PayPalGateway:
    def charge(self, amount_cents: int, token: str) -> ChargeResult:
        return ChargeResult(id=f"PAYID-{token[:6]}", ok=amount_cents > 0)
    def refund(self, charge_id: str) -> bool:
        return charge_id.startswith("PAYID")

class CheckoutService:
    def __init__(self, gateway: PaymentGateway) -> None:
        self.gateway = gateway  # any object matching the Protocol shape
    def pay(self, amount_cents: int, token: str) -> ChargeResult:
        result = self.gateway.charge(amount_cents, token)
        if not result.ok:
            raise RuntimeError("Payment declined")
        return result

checkout = CheckoutService(StripeGateway("sk_live_123"))
print(checkout.pay(4999, "tok_visa"))  # ChargeResult(id='ch_tok_vi', ok=True)

# Ruby: pure duck typing. No interface declaration; the object just responds to the methods.
ChargeResult = Struct.new(:id, :ok)

class StripeGateway
  def initialize(api_key)
    @api_key = api_key
  end
  def charge(amount_cents, token)
    ChargeResult.new("ch_#{token[0, 6]}", amount_cents > 0)
  end
  def refund(charge_id)
    charge_id.start_with?("ch_")
  end
end

class PayPalGateway
  def charge(amount_cents, token)
    ChargeResult.new("PAYID-#{token[0, 6]}", amount_cents > 0)
  end
  def refund(charge_id)
    charge_id.start_with?("PAYID")
  end
end

# CheckoutService accepts any object that quacks like a payment gateway.
class CheckoutService
  def initialize(gateway)
    @gateway = gateway
  end
  def pay(amount_cents, token)
    result = @gateway.charge(amount_cents, token)
    raise "Payment declined" unless result.ok
    result
  end
end

checkout = CheckoutService.new(StripeGateway.new("sk_live_123"))
puts checkout.pay(4999, "tok_visa").inspect # #<struct ChargeResult id="ch_tok_vi", ok=true>

तिन्ही snippets वर्तनाच्या दृष्टीने एकसारखे आहेत, पण contract वेगवेगळ्या ठिकाणी राहतो. TypeScript तो compile time ला तपासला जाणारा स्पष्ट interface म्हणून लिहितो. Python तो एक Protocol म्हणून सांगतो जो classes structurally पूर्ण करतात, कोणताही base class न लागता. Ruby कोणताही contract लिहीतच नाही - gateway फक्त charge आणि refund ला प्रतिसाद देतो, आणि जो कोणताही object तसे करतो तो त्याच्या जागी उभा राहू शकतो.

Nominal विरुद्ध structural: तोच class, दोन तपासण्या

// Structural: a plain object with the right shape is accepted, even without `implements`.
const sandboxGateway = {
  charge(amountCents: number, token: string) {
    return { id: `test_${token}`, ok: true };
  },
  refund(chargeId: string) { return true; },
};

// No class, no `implements PaymentGateway`, yet it type-checks as one:
const testCheckout = new CheckoutService(sandboxGateway);
console.log(testCheckout.pay(100, "tok_test")); // accepted by structure alone

# Structural: a bare object satisfies the Protocol if it has the methods.
class SandboxGateway:
    def charge(self, amount_cents: int, token: str) -> ChargeResult:
        return ChargeResult(id=f"test_{token}", ok=True)
    def refund(self, charge_id: str) -> bool:
        return True

# CheckoutService never asked for a base class, only the shape:
test_checkout = CheckoutService(SandboxGateway())
print(test_checkout.pay(100, "tok_test"))  # accepted by structure

# Duck typing: conformance is decided at the moment charge is actually called.
sandbox_gateway = Object.new
def sandbox_gateway.charge(amount_cents, token)
  ChargeResult.new("test_#{token}", true)
end
def sandbox_gateway.refund(charge_id)
  true
end

test_checkout = CheckoutService.new(sandbox_gateway)
puts test_checkout.pay(100, "tok_test").inspect # works: it responds to charge

हाच फरक एका पडद्यावर. TypeScript आणि Python sandbox object स्वीकारतात कारण त्याचे structure contract शी जुळते, प्रोग्राम चालण्याआधीच तपासले जाते. Ruby तो स्वीकारते कारण, जेव्हा pay हे charge ला बोलावते, तेव्हा object योगायोगाने प्रतिसाद देतो, चालताना तपासले जाते. Java सारखी nominal भाषा तिन्हीही नाकारेल, जोपर्यंत ते implements PaymentGateway असे म्हणत नाहीत.

सामान्य धोके

धोके आणि anti-patterns

Interfaces घोषित करणे सोपे आहे आणि त्यांचा गैरवापर करणेही सोपे. या वारंवार होणाऱ्या चुका आहेत.

🧿 Leaky abstractions

PaymentGateway interface वर stripeCustomerId किंवा HTTP status ठेवल्याने vendor तपशील contract मध्ये ओढला जातो, त्यामुळे PayPal ते स्वच्छपणे implement करू शकत नाही आणि abstraction मोडते.

🗑️ Fat interfaces

वीस methods असलेले gateway प्रत्येक implementation ला ते न पेलणाऱ्या methods stub करण्यास भाग पाडते. Contracts अरुंद ठेवा जेणेकरून implementers फक्त consumers प्रत्यक्षात बोलावतात तेच पुरवतील.

🔎 सर्वत्र isinstance तपासण्या

जर CheckoutService हे if gateway is StripeGateway विचारून शाखा करत असेल, तर तुम्ही interface फेकून दिले आहे. वर्तन implementation मध्ये असावे, type सुंघण्यात नव्हे.

💥 शांत duck-typing तफावती

Ruby किंवा Python मध्ये, गहाळ refund production मध्ये बोलावले जाईपर्यंत पकडले जात नाही. प्रत्येक method चालवणाऱ्या tests शिवाय, structural विसंगती अगदी वाईट क्षणापर्यंत लपून राहतात.

🎯 Contract चा विरोधाभास

नाकारलेल्या कार्डावर ok=true परत करणारे implementation तांत्रिकदृष्ट्या आकाराशी जुळते पण वचन मोडते. Signatures शी अनुरूप असणे म्हणजे वर्तन पाळणे नव्हे.

🏗️ एकाच impl साठी interface

फक्त Stripe कधीही अस्तित्वात असेल तेव्हा PaymentGateway काढणे कोणत्याही फायद्याविना indirection जोडते. दुसरे implementation किंवा test double खरे असेल तेव्हाच contract आणा.

संकेत आणि मापदंड

संकेत आणि कसे मोजावे

तुम्ही "चांगली रचना" unit-test करू शकत नाही, पण हे निरीक्षणीय संकेत तुम्हाला सांगतात की तुमचे interfaces त्यांचे मोल कमावत आहेत का.

संकेततो काय सांगतो
प्रति interface implementationsदोन किंवा अधिक (test doubles सह) म्हणजे contract हा खरा जोडबिंदू आहे; कायमचा नेमका एकच असणे अकाली abstraction सुचवते.
Consumer कडून concrete types चे importsजर CheckoutService हे StripeGateway import करत असेल, तर interface प्रत्यक्षात काहीही decouple करत नाही. शून्याचे लक्ष्य ठेवा.
Type-narrowing शाखाImplementations विरुद्ध isinstance / is_a? तपासण्या मोजल्याने polymorphism caller मध्ये कुठे परत झिरपले हे दिसते.
प्रति interface methodsलहान, सुसंगत interfaces (2-5 methods) implement करणे सोपे असते; फुगणारी method संख्या फोडण्यासाठी एक fat contract दर्शवते.
Test double चा प्रयत्नTest मध्ये interface बनावट करणे क्षुल्लक असेल तर contract स्वच्छ आहे; ते databases किंवा HTTP ओढून आणत असेल तर abstraction leaky आहे.
Runtime NoMethodError दरDuck-typed कोडमध्ये, production मधील method-missing त्रुटी compiler ने पकडल्या असत्या अशा structural तफावती उघड करतात.
अंगठ्याचा नियम: निरोगी interface ला थोड्या methods, किमान दोन implementations, आणि त्याच्या consumers मध्ये शून्य concrete imports असतात. जर एखादा consumer त्याला कोणता class मिळाला हे कधी तपासत असेल, तर abstraction आधीच अपयशी झाले आहे.
06 - प्रकरण अभ्यास

वास्तविक जगातील प्रकरण अभ्यास

Interface ला अनुसरून प्रोग्रामिंग भोवती बांधलेल्या तीन production प्रणाली.

💳

1 · अनेक gateways वरून marketplace payments

Pattern: एक PaymentGateway contract, अनेक vendors

एका marketplace ला US मध्ये Stripe, Europe मध्ये PayPal, आणि Brazil मध्ये स्थानिक processor लागतो, प्रत्येक प्रदेशासाठी checkout पुन्हा न लिहिता.

  • Checkout फक्त PaymentGateway.charge आणि refund वर अवलंबून असतो, कधीही vendor SDK वर नाही.
  • एक factory request time ला प्रत्येक खरेदीदाराच्या प्रदेशानुसार concrete gateway निवडते.
  • Brazilian processor जोडणे म्हणजे विद्यमान contract implement करणारा एक नवीन class.
✅ परिणाम: नवीन payment vendors विलग classes म्हणून येतात, आणि checkout logic अस्पर्श राहते व बनावट gateway वापरून tests ने पूर्णपणे व्यापली जाते.
📣

2 · चॅनेलांवरून notification वितरण

Pattern: email, SMS, आणि push साठी एक Notifier protocol

एक product email, SMS, आणि push वरून order updates पाठवते, आणि sending कोडला त्रास न देता नंतर Slack जोडू इच्छिते.

  • एक Notifier protocol एक method घोषित करतो, send(recipient, message).
  • EmailNotifier, SmsNotifier, आणि PushNotifier प्रत्येक तो structurally पूर्ण करतात.
  • Dispatcher notifiers च्या यादीवर फिरतो, contract ला बोलावतो, चॅनेलबद्दल अनभिज्ञ.
✅ परिणाम: send ला प्रतिसाद देणारा एक class लिहून Slack channel जोडली जाते, dispatcher मध्ये कोणताही बदल न करता.
🗄️

3 · Ruby app मधील pluggable file storage

Pattern: local disk आणि S3 वरून duck-typed Storage

एक Rails app development मध्ये local disk वर आणि production मध्ये S3 वर user uploads साठवते, config ने ठरवलेले.

  • Upload कोड त्याला दिलेल्या कोणत्याही object वर store.put(key, io) आणि store.url(key) बोलावतो.
  • DiskStorage आणि S3Storage त्याच methods ला प्रतिसाद देतात; कोणीही interface घोषित करत नाही.
  • Tests त्याच पद्धतीने quack करणारे in-memory storage double inject करतात, त्यामुळे disk किंवा network ला स्पर्श होत नाही.
✅ परिणाम: storage backend हा एक config switch आहे, आणि duck typing disk, S3, आणि test double या सर्वांत upload path एकसारखा ठेवते.
07 - सुसंगतता

आधुनिक सुसंगतता

Interfaces आणि structural typing हे आधुनिक भाषा व साधने कशी विकसित होतात याच्या केंद्रस्थानी शांतपणे आहेत.

🧩 Structural typing मुख्य प्रवाहात

TypeScript ने structural typing लाखो लोकांना परिचित केले; Go च्या implicit interfaces ने backend वर तेच केले. घोषणेने नव्हे तर आकाराने अनुरूप होणे ही आता default अपेक्षा आहे.

🐍 Dynamic भाषांमध्ये gradual typing

Python चे Protocol आणि Ruby चे RBS व Sorbet duck-typed कोडला ऐच्छिक static contracts आणतात, लवचिकता न सोडता runtime आधी structural तफावती पकडतात.

🔗 Service सीमांवर contracts

तीच प्रवृत्ती मोठ्या प्रमाणात वाढते: OpenAPI आणि gRPC schemas हे services दरम्यानचे interfaces आहेत, teams ना concrete server ऐवजी contract विरुद्ध बांधू देतात.

🧪 Test doubles default म्हणून

Interface ला अनुसरून प्रोग्रामिंग हेच वेगवान, विलग tests शक्य करते. Suites वाढल्यावर, contract विरुद्ध बनावट inject करणे ही चैन नव्हे तर प्रमाणित प्रथा आहे.

🧱 Ports आणि adapters

Hexagonal architecture खालपर्यंत interfaces च आहे: domain ports परिभाषित करते, आणि PaymentGateway सारखे adapters कडेला जोडले जातात, business logic vendor-मुक्त ठेवतात.

🤖 Agents साठी tool contracts

LLM tool-calling देखील एका घोषित schema वर अवलंबून असते, एक interface ज्याविरुद्ध agent प्रोग्राम करतो, त्यामुळे आकाराशी जुळणारे कोणतेही tool special-casing शिवाय बोलावता येते.

सारांश: भाषा नावाने तपासो, आकाराने तपासो, की call time ला तपासो, contract ला अनुसरून कोड लिहिणे हेच software अदलाबदल करण्यायोग्य, testable, आणि विकसित होण्यास मुक्त ठेवते. Interfaces आणि duck typing ही एकाच चिरंतन प्रश्नाची दोन उत्तरे आहेत - concrete types वर नव्हे, तर वर्तनावर अवलंबून राहा.
