Creational Pattern

Prototype पॅटर्न - cloning करून नवीन ऑब्जेक्ट्स तयार करा

काही ऑब्जेक्ट्स सुरुवातीपासून तयार करणे महागडे असते: ते config लोड करतात, database ला भेट देतात, किंवा वापरण्यायोग्य स्थितीत पोहोचण्यासाठी एक मोठी फाइल parse करतात. Prototype पॅटर्न हे टाळतो कारण तो नवीन instance बांधण्याऐवजी पूर्णपणे तयार असलेल्या instance चे cloning करतो. तुम्ही एक तयार उदाहरण जवळ ठेवता, आणि जेव्हा दुसरे तसेच हवे असेल तेव्हा त्याची कॉपी करता.

01 - काय

Prototype पॅटर्न म्हणजे काय?

Prototype हा एक creational पॅटर्न आहे जो class थेट instantiate करण्याऐवजी विद्यमान instance - म्हणजेच prototype - चे copying करून नवीन ऑब्जेक्ट्स तयार करतो. ऑब्जेक्ट स्वतःच स्वतःची कॉपी कशी तयार करायची हे जाणतो, त्यामुळे ज्या कोडला नवीन ऑब्जेक्ट हवा असतो त्याला त्याचा concrete type किंवा तो कसा configure करायचा हे माहीत असण्याची गरज नसते. तुम्ही एका template चे clone करता आणि फक्त फरक असलेल्या गोष्टी बदलता.

🧬 Clone करा, construct नको

एक clone() मेथड असा नवीन ऑब्जेक्ट परत करते जो विद्यमान ऑब्जेक्टची कॉपी म्हणून सुरू होतो, आधीच भरलेला आणि configured.

🙈 Concrete types लपवतो

Callers एक prototype interface धरतात आणि त्याचे clone करतात. ते कधीही new ConcreteThing() कॉल करत नाहीत, त्यामुळे ते class पासून decoupled राहतात.

🗂️ Templates ची registry

एक registry keys ना पूर्व-निर्मित prototypes शी जोडते. नावाने विचारा आणि ती वापरण्यास तयार असलेले ताजे clone परत देते.

02 - का

Prototype पॅटर्न का अस्तित्वात आहे

थेट construction तुम्हाला concrete classes शी जोडते आणि प्रत्येक वेळी महागडे setup पुन्हा करायला भाग पाडते. जेव्हा दोन ऑब्जेक्ट्स फक्त काही fields नी वेगळे असतात, तेव्हा शून्यापासून पुन्हा बांधणे वेळखाऊ आणि चुका होण्यास प्रवण असते. ज्ञात-चांगल्या template चे cloning जलद आणि सुरक्षित असते.

⚡ महागडे setup वगळते

जर एखाद्या ऑब्जेक्टला मंद init (parsing, network, जड computation) लागत असेल, तर तुम्ही ती किंमत prototype साठी एकदाच देता आणि नंतर प्रत्येक पुढील instance साठी स्वस्तात clone करता.

🔌 Classes पासून decouple करते

Clients एका interface मधून clone करतात, त्यामुळे ते एका मोठ्या switch ला किंवा hardcoded new ला हात न लावता runtime मध्ये concrete types जोडतात किंवा बदलतात.

🎛️ Configured state पकडते

एक prototype डझनभर set fields असलेला पूर्णपणे ट्यून केलेला ऑब्जेक्ट असू शकतो. त्याचे cloning केल्याने ते configuration प्रत्येक वेळी पुन्हा नमूद न करता जपले जाते.

➕ Subclassing कमी करते

प्रत्येक variant साठी एक factory subclass ठेवण्याऐवजी, तुम्ही configured instances register करता. नवीन variants नवीन classes नव्हे तर data बनतात.

सोप्या भाषेत

उपमांसह Prototype समजावून

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

ही तुमच्या नोट्ससाठी फोटोकॉपी मशीन आहे. सूत्रांचे संपूर्ण पान सुरुवातीपासून पुन्हा लिहिण्याऐवजी, तुम्ही तयार पानाची कॉपी करता आणि नंतर समासात तुमचे स्वतःचे बदल खरडता.

👩‍💻 डेव्हलपरसाठी

ही ऑब्जेक्ट्ससाठी Ctrl+C, Ctrl+V आहे. तुमच्याकडे memory मध्ये चांगल्या प्रकारे configured instance आहे; त्याचे cloning केल्याने constructor आणि त्याचे सर्व setup पुन्हा न चालवता दुसरा स्वतंत्र ऑब्जेक्ट मिळतो.

🏢 व्यावसायिकासाठी

एका document template चा विचार करा. कायदेशीर विभाग एक मास्टर करार ठेवतो; प्रत्येक नवीन करार त्या मास्टरची कॉपी म्हणून सुरू होतो, आणि नंतर तुम्ही कोऱ्या पानावरून मसुदा तयार करण्याऐवजी नावे आणि तारखा भरता.

🍪 रोजच्या जीवनातील आवृत्ती

एक कुकी कटर एका मास्टर आकारातून एकसारखे आकार ठोकून काढतो. प्रत्येक कुकी वेगळी असते, पण त्या सर्वांना कटरचा आकार तत्काळ मिळतो.

03 - कसे

आतल्या बाजूने ते कसे काम करते

एक prototype एक copy operation उघड करतो. Client ते कॉल करतो आणि एक नवीन, स्वतंत्र ऑब्जेक्ट परत मिळवतो. खरे काम त्या copy ने reference fields कसे हाताळले यात असते: एक shallow copy ती share करते, तर एक deep copy ती recursively duplicate करते.

🪞 Shallow copy

Primitives कॉपी करते आणि प्रत्येक reference जशीच्या तशी कॉपी करते. Clone आणि original एकाच nested ऑब्जेक्ट्सकडे बोट दाखवतात. जलद, पण mutations एका कॉपीतून दुसरीत झिरपतात.

🌊 Deep copy

Nested ऑब्जेक्ट्सचेही recursively cloning करते, त्यामुळे copy पूर्णपणे स्वतंत्र असते. Mutable state साठी सुरक्षित, पण मंद आणि cycles सोबत अधिक अवघड.

Java मधील एक वास्तविक उदाहरण

public abstract class Shape implements Cloneable {
    public int x, y;
    public String color;
    public List<String> tags = new ArrayList<>();

    protected Shape() { }

    // Copy constructor: the explicit, safe way to copy
    protected Shape(Shape source) {
        this.x = source.x;
        this.y = source.y;
        this.color = source.color;
        // DEEP copy the mutable list, do not share the reference
        this.tags = new ArrayList<>(source.tags);
    }

    public abstract Shape clone();
}

public final class Rectangle extends Shape {
    public int width, height;

    public Rectangle() { }

    public Rectangle(Rectangle source) {
        super(source);            // copies base fields + deep-copies tags
        this.width = source.width;
        this.height = source.height;
    }

    @Override
    public Rectangle clone() {
        return new Rectangle(this);   // returns an independent copy
    }
}

// Prototype registry: clone by key, never call new in the client
public final class ShapeRegistry {
    private final Map<String, Shape> prototypes = new HashMap<>();

    public void register(String key, Shape prototype) {
        prototypes.put(key, prototype);
    }

    public Shape create(String key) {
        Shape proto = prototypes.get(key);
        if (proto == null) throw new NoSuchElementException(key);
        return proto.clone();     // caller gets a fresh, independent object
    }
}

लक्षात घ्या की copy constructor tags ला reference कॉपी करण्याऐवजी new ArrayList<>(source.tags) ने पुन्हा बांधतो. ती एकच ओळ सुरक्षित deep copy आणि shared-mutable-state बग यातील फरक आहे. Registry मुळे clients concrete class किंवा त्याचे setup न जाणता create("wide-blue") म्हणू शकतात.

Deep copy

Mutable references duplicate करा

प्रत्येक mutable field साठी, जुनी reference share करण्याऐवजी नवीन instance बांधा. स्वतःची mutable state धरणाऱ्या nested ऑब्जेक्ट्समध्ये recurse करा.

सामान्य अडचणी

अडचणी आणि anti-patterns

बहुतेक Prototype बग हे copy बग असतात. जोपर्यंत दोन ऑब्जेक्ट्स शांतपणे एकच nested state share करत नाहीत तोपर्यंत clone ठीक दिसतो.

🪢 Shared references

Shallow copy मुळे clone हा original च्या mutable fields कडे बोट दाखवत राहतो. एक mutate केल्यास दुसरा गुपचूप बदलतो. हा क्रमांक-एकचा Prototype बग आहे.

🔒 Final fields

clone() मेथडमध्ये तुम्ही final fields पुन्हा नेमून देऊ शकत नाही, त्यामुळे एक भोळसट override त्यांचे deep-copy करू शकत नाही. construction वेळी ती सेट करणारा copy constructor वापरा.

🧩 Java चे तुटलेले Cloneable

Object.clone() protected आहे, एक checked exception फेकते, shallow copy करते, आणि constructors ला बगल देते. स्पष्ट copy constructors किंवा factory copy() मेथड वापरा.

🔁 Cyclic ऑब्जेक्ट graphs

Cycles असलेल्या graph चे deep-copy (A बोट दाखवतो B कडे, B परत A कडे) कायम recurse होऊ शकते. Loop तोडण्यासाठी तुम्हाला आधीच-कॉपी झालेल्या ऑब्जेक्ट्सचा एक identity map हवा असतो.

🌀 Serialization चा गैरवापर

Serialize-मग-deserialize द्वारे deep-copy करणे सोपे पण मंद असते, सर्व काही serializable असणे आवश्यक असते, आणि कोणती fields खरंच कॉपी झाली हे लपवते. ते शेवटचा उपाय म्हणून राखून ठेवा.

🎭 new पुरेसे असताना cloning

जर ऑब्जेक्ट्स बांधणे स्वस्त आणि immutable असतील, तर साधा constructor अधिक स्पष्ट असतो. Prototype indirection जोडतो जो फक्त खर्चिक setup किंवा अनेक variants साठीच फायदेशीर ठरतो.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Prototype हा construction खर्च आणि coupling यांची copy गुंतागुंतीशी तडजोड करतो. जेव्हा बांधणे महागडे असते आणि ऑब्जेक्ट्स configuration नुसार वेगळे असतात तेव्हा तो चमकतो.

पैलूतपशील
फायदेमहागडे re-initialization टाळते, concrete classes लपवते, configured state पकडते, subclass ची भरमसाठ वाढ कमी करते, आणि तुम्हाला runtime मध्ये variants data म्हणून जोडू देते.
तोटेगुंतागुंतीच्या किंवा cyclic graphs चे deep-copy कठीण असते, shared-reference बग सूक्ष्म असतात, आणि Java चे Cloneable भोळसट मार्ग असुरक्षित बनवते.
केव्हा वापरावेConstruction खर्चिक असते, ऑब्जेक्ट्स मुख्यतः configuration नुसार वेगळे असतात, तुम्हाला clients ना concrete types पासून decouple करायचे असते, किंवा तुम्हाला templates ची runtime registry हवी असते.
केव्हा टाळावेऑब्जेक्ट्स बांधणे स्वस्त आणि immutable असतात, graph खोलवर nested किंवा cyclic असतो, किंवा साधा constructor किंवा Builder अधिक स्पष्ट वाचतो.
गुंतागुंतरचनात्मकदृष्ट्या कमी, पण योग्यता प्रत्येक mutable field साठी shallow विरुद्ध deep बरोबर मिळवण्यावर अवलंबून असते. चुका मूक असतात, गोंगाट करणाऱ्या नसतात.
संबंधितFactory Method आणि Abstract Factory (तयार करण्याचे पर्यायी मार्ग), Builder (टप्प्याटप्प्याने जुळवणे), Memento (state चा snapshot घेणे आणि पुनर्संचयित करणे).
ढोबळ नियम: जेव्हा "याच्यासारखा आणखी एक बनव" हे नेहमीचे असते आणि शून्यापासून बांधणे महागडे असते, तेव्हा Prototype कडे वळा. मग एक copy constructor लिहा, प्रत्येक mutable field चे मुद्दाम deep-copy करा, आणि clone mutate केल्याने original ला कधीही स्पर्श होत नाही याची चाचणी करा.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन प्रातिनिधिक ठिकाणे जिथे prototype चे cloning शून्यापासून बांधण्यापेक्षा सरस ठरते.

🎨

1 · Graphics editor मधील shapes आणि tools

पॅटर्न: canvas वरील configured ऑब्जेक्ट्स clone करा

एक vector editor वापरकर्त्यांना style, transforms, आणि grouping धारण करणारे shapes copy-paste आणि duplicate करू देतो.

  • प्रत्येक shape clone() implement करते, त्याची style आणि child shapes चे deep-copy करते जेणेकरून duplicates स्वतंत्र असतात.
  • Prototype shapes चा एक palette (styled rectangle, arrow, sticky note) registry मध्ये साठवला जातो आणि drag वर clone होतो.
  • Undo snapshots canvas state पकडण्यासाठी आणि पुनर्संचयित करण्यासाठी तेच copy logic पुन्हा वापरतात.
✅ परिणाम: पूर्णपणे styled shape चे duplication तत्काळ आणि सुरक्षित असते, आणि नवीन tools class लिहिण्याऐवजी prototype register करून जोडले जातात.
🎮

2 · Game entity spawning

पॅटर्न: runtime मध्ये जड templates clone करा

एक game शेकडो शत्रू spawn करतो ज्यांचे setup (mesh handles, stats, AI config) बांधणे खर्चिक असते.

  • एक पूर्णपणे-लोड झालेला "orc" prototype एकदाच बांधला जातो; प्रत्येक spawn जड init पुन्हा चालवण्याऐवजी त्याचे clone करतो.
  • प्रत्येक-instance ची mutable state (position, health, cooldowns) deep-copy केली जाते जेणेकरून instances ती कधीही share करत नाहीत.
  • Designers नवीन शत्रू variants configured prototypes म्हणून register करतात, engine कोडमध्ये कोणतेही बदल नाहीत.
✅ परिणाम: Spawn खर्च memory copy इतका कमी होतो, frame spikes नाहीशा होतात, आणि content teams नवीन units data म्हणून पाठवतात.
📄

3 · Document आणि config templates

पॅटर्न: मास्टर कॉपीपासून सुरू करा, मग edit करा

एक SaaS अ‍ॅप templated documents आणि pipeline configs देतो जे वापरकर्ते clone आणि सानुकूल करतात.

  • प्रत्येक template हा registry मध्ये key ने साठवलेला पूर्णपणे-भरलेला prototype ऑब्जेक्ट असतो.
  • नवीन document तयार करणे template चे खोलवर clone करते जेणेकरून edits कधीही मास्टरकडे परत झिरपत नाहीत.
  • Template जोडणे ही एक data क्रिया आहे: एक configured instance register करा, नवीन class नाही.
✅ परिणाम: वापरकर्ते कोऱ्या पानाऐवजी एका कार्यरत उदाहरणापासून सुरुवात करतात, आणि templates ची यादी कोड बदलांशिवाय वाढते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Cloning आधुनिक कोडमध्ये सर्वत्र शांतपणे आहे, अगदी जेव्हा शास्त्रीय Gang of Four रचना स्पष्टपणे मांडलेली नसते तेव्हाही.

🧊 Immutable + withers

Records आणि value objects with-शैलीच्या copy मेथड्सना प्राधान्य देतात जे एक field बदललेला नवीन instance परत करतात. ते mutation च्या जोखमीशिवाय Prototype विचारसरणी आहे.

🌐 JS मधील structuredClone

Browsers आणि Node आता structuredClone() पाठवतात, एक built-in deep copy जो cycles आणि अनेक types हाताळतो, ज्यामुळे सुरक्षित deep clones एक-ओळीचे बनतात.

🧬 Prototypal inheritance

JavaScript ऑब्जेक्ट्स अक्षरशः एका prototype ला delegate करतात आणि Object.create() विद्यमान ऑब्जेक्टमधून नवीन ऑब्जेक्ट्स फिरवते, हा पॅटर्न भाषेतच रुजवलेला आहे.

📸 State snapshots

Redux-शैलीचे stores आणि undo systems state चे clone करतात जेणेकरून जुन्या आवृत्त्या अखंड राहतात, time-travel debugging साठी Prototype ला Memento सोबत जोडतात.

🧪 Test fixtures

Test builders एका वैध base ऑब्जेक्टचे clone करतात आणि प्रत्येक case साठी एक field बदलतात, चाचण्या महत्त्वाच्या फरकावर केंद्रित ठेवतात.

⚙️ Config profiles

Infrastructure आणि ML tooling एका base config चे clone करतात आणि प्रत्येक environment किंवा experiment साठी काही keys override करतात, अगदी registry-of-prototypes ची कल्पना.

सारांश: Prototype टिकून राहतो कारण "याच्यासारखा आणखी एक दे, पण स्वतंत्र" ही सतत गरज असते. हा पॅटर्न Cloneable interface बद्दल कमी आणि एका शिस्तीबद्दल अधिक आहे: मुद्दाम copy करा, जिथे महत्त्वाचे तिथे deep, आणि दोन ऑब्जेक्ट्सना चुकून mutable state कधीही share करू देऊ नका.
