Behavioral Pattern

Memento पॅटर्न स्थिती कशी जतन करून पुन्हा प्रस्थापित करतो

कधीकधी तुम्हाला एखादा ऑब्जेक्ट आधीच्या क्षणापर्यंत मागे न्यावा लागतो: एखादे संपादन undo करणे, अयशस्वी झालेला transaction परत फिरवणे, जतन केलेला गेम पुन्हा प्रस्थापित करणे. Memento तुम्हाला ऑब्जेक्टच्या अंतर्गत स्थितीचा snapshot घेऊ देतो आणि नंतर तो पुन्हा प्रस्थापित करू देतो, तेही ऑब्जेक्टच्या खाजगी fields बाहेरील जगाला न दाखवता. ज्या ऑब्जेक्टकडे ती स्थिती असते तोच काय जतन करायचे आणि कसे यावर नियंत्रण ठेवतो.

01 - काय

Memento पॅटर्न म्हणजे काय?

Memento हा एक behavioral पॅटर्न आहे जो एखाद्या ऑब्जेक्टची अंतर्गत स्थिती वेगळ्या ऑब्जेक्टमध्ये जतन करतो, जेणेकरून मूळ ऑब्जेक्टचे encapsulation न मोडता ती स्थिती नंतर पुन्हा प्रस्थापित करता येते. जतन केलेला snapshot हा त्याला तयार करणाऱ्या ऑब्जेक्टशिवाय बाकी सर्वांसाठी अपारदर्शक असतो, म्हणजेच केवळ जतन आणि पुनर्प्रस्थापन करण्यासाठी खाजगी fields कधीही client कोडमध्ये गळत नाहीत.

🧑‍🎨 Originator

ज्या ऑब्जेक्टची स्थिती महत्त्वाची असते तो. तो आपली सध्याची स्थिती जतन करणारा memento तयार करतो आणि नंतर स्वतःला पुन्हा प्रस्थापित करण्यासाठी memento वापरतो.

📦 Memento

Originator च्या स्थितीचा snapshot धारण करणारा एक value object. बाहेरील लोकांसाठी अपारदर्शक; फक्त originator च त्याचा संपूर्ण मजकूर वाचू शकतो.

🗂️ Caretaker

mementos ना इतिहासात (बहुधा एका stack मध्ये) ठेवतो आणि जतन किंवा पुनर्प्रस्थापनासाठी विनंती करतो, पण memento च्या आत काय आहे ते कधीही तपासत किंवा संपादित करत नाही.

02 - का

Memento पॅटर्न का अस्तित्वात आहे

undo जोडण्याचा भोळा मार्ग म्हणजे प्रत्येक field सार्वजनिक करणे जेणेकरून एखादा manager class त्यांची नक्कल करून पुन्हा सेट करू शकेल. यामुळे encapsulation चूरचूर होते आणि manager अंतर्गत रचनेशी घट्ट जोडला जातो. Memento तुम्हाला ती गळती न करता मागे फिरण्याची सोय देतो.

🔒 encapsulation जपते

स्थिती originator स्वतःच जतन करतो आणि पुन्हा प्रस्थापित करतो. केवळ जतनासाठी खाजगी fields कधीही सार्वजनिक होत नाहीत, त्यामुळे अंतर्गत रचना लपलेली राहते आणि बदलण्यास मोकळी राहते.

↩️ स्वच्छ undo आणि redo शक्य करते

mementos चा एक stack तुम्हाला जवळजवळ फुकटात multi-level undo देतो. प्रत्येक बदलापूर्वी push करा, परत फिरण्यासाठी pop करा, आणि दुसऱ्या दिशेसाठी एक redo stack ठेवा.

🧩 जबाबदाऱ्या वेगळ्या करते

Originator त्याच्या वर्तनावर लक्ष केंद्रित करतो; caretaker इतिहास व्यवस्थापनावर लक्ष केंद्रित करतो. कोणालाही दुसऱ्याचे अंतर्गत तपशील माहीत असण्याची गरज नसते.

🕰️ checkpoints आणि rollback ला आधार देते

एखाद्या धोकादायक क्रियेपूर्वी snapshot घ्या, आणि ती क्रिया अयशस्वी झाल्यास तो पुन्हा प्रस्थापित करा. यामुळे साध्या ऑब्जेक्ट्सना transactional, सर्व-किंवा-काहीच-नाही असे वर्तन मिळते.

सोप्या शब्दांत

उपमांसह Memento समजावून

तीच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही जे कोणी असाल त्याला ती पटेल.

🎓 विद्यार्थ्यासाठी

हा व्हिडिओ गेममधील save point आहे. एखाद्या कठीण boss समोर तुम्ही save करता; तुम्ही हरलात तर तेच नेमके save पुन्हा load करून पुन्हा प्रयत्न करता. गेमचे जग save फाइल लिहिते आणि वाचते; तुम्ही फक्त कधी save आणि load करायचे ते निवडता.

👩‍💻 डेव्हलपरसाठी

तुमच्या editor मधील Ctrl+Z चा विचार करा. प्रत्येक कीस्ट्रोक buffer चा एक snapshot undo stack वर push करतो. Undo शेवटचा snapshot pop करतो आणि documents स्वतःला पुन्हा प्रस्थापित करतो; तुमचा history manager कधीही document चे स्वरूप parse करत नाही.

🏢 व्यावसायिकासाठी

हा एक document version history आहे. प्रत्येक save एक संपूर्ण आवृत्ती नोंदवतो. मागे फिरण्यासाठी तुम्ही एक आवृत्ती निवडता आणि document ती पुन्हा load करतो. संग्रहालय आवृत्त्या साठवते पण त्यांचा मजकूर संपादित करत नाही.

📸 दैनंदिन आवृत्ती

एका खोलीचा Polaroid फोटो. नंतर तुम्ही फर्निचर पुन्हा त्या फोटोशी जुळवून लावता. फोटोने एक क्षण गोठवला; फोटोला फर्निचर कसे हलते हे न कळता खोली त्या क्षणापर्यंत पुन्हा प्रस्थापित करता येते.

03 - कसे

पडद्यामागे ते कसे काम करते

Originator दोन क्रिया उघड करतो: save, जी त्याची सध्याची स्थिती धारण करणारा memento परत करते, आणि restore, जी एका memento मधून स्थिती पुन्हा स्वतःमध्ये वाचते. Caretaker ते mementos क्रमाने ठेवतो आणि केव्हा save किंवा rollback करायचे ते ठरवतो.

💾 Save

Originator त्याची संबंधित fields एका नवीन, immutable memento मध्ये नक्कल करतो आणि तो एका narrow interface द्वारे बाहेर देतो. Caretaker तो history stack वर push करतो.

♻️ Restore

undo च्या वेळी caretaker एक memento pop करतो आणि तो originator ला परत देतो, जो साठवलेल्या fields पुन्हा स्वतःमध्ये नक्कल करतो, त्या नेमक्या भूतकाळातील स्थितीत परततो.

TypeScript मधील एक कार्यरत उदाहरण

// Memento: opaque snapshot. Only the Originator reads its full state.
class EditorMemento {
  constructor(
    private readonly content: string,
    private readonly cursor: number,
  ) {}

  // Wide interface, used by the Originator only.
  getContent(): string { return this.content; }
  getCursor(): number { return this.cursor; }
}

// Originator: owns the state, creates and restores snapshots.
class Editor {
  private content = "";
  private cursor = 0;

  type(text: string): void {
    this.content =
      this.content.slice(0, this.cursor) + text + this.content.slice(this.cursor);
    this.cursor += text.length;
  }

  save(): EditorMemento {
    return new EditorMemento(this.content, this.cursor);
  }

  restore(m: EditorMemento): void {
    this.content = m.getContent();
    this.cursor = m.getCursor();
  }

  toString(): string { return this.content; }
}

// Caretaker: keeps history, never inspects a memento.
class History {
  private readonly stack: EditorMemento[] = [];

  backup(editor: Editor): void {
    this.stack.push(editor.save());
  }

  undo(editor: Editor): void {
    const m = this.stack.pop();
    if (m) editor.restore(m);
  }
}

const editor = new Editor();
const history = new History();

history.backup(editor);
editor.type("Hello");
history.backup(editor);
editor.type(", world");
console.log(editor.toString()); // Hello, world

history.undo(editor);
console.log(editor.toString()); // Hello
history.undo(editor);
console.log(editor.toString()); // (empty)

लक्षात घ्या की caretaker कधीही getContent() किंवा getCursor() वाचत नाही. तो mementos आंधळेपणाने साठवतो आणि परत करतो, त्यामुळे editor इतिहास न मोडता आपला मजकूर कसा दर्शवतो हे बदलण्यास मोकळा असतो.

history store तयार करा

mementos चा stack धारण करणारा एक caretaker जोडा. तो प्रत्येक बदलापूर्वी save कॉल करतो आणि परत आलेला memento ठेवतो.

Backup

बदलण्यापूर्वी save करा

caretaker अशा प्रकारे जोडा की प्रत्येक user क्रिया आधी एक memento push करेल, मग बदल लागू करेल. आता आधीची स्थिती नेहमीच पुन्हा मिळवता येते.

70
Undo

Pop करा आणि restore करा

undo अंमलात आणा: शेवटचा memento pop करा आणि तो originator च्या restore ला द्या. ऑब्जेक्ट एक पाऊल मागे उडी घेतो.

80
Redo

redo stack जोडा

तुम्ही undo करता तेव्हा pop केलेली स्थिती एका redo stack वर push करा जेणेकरून user पुन्हा पुढे जाऊ शकेल. कोणत्याही नवीन संपादनावर तो साफ करा.

90
मर्यादा

history चा आकार मर्यादित करा

तुम्ही किती mementos ठेवता ते मर्यादित करा जेणेकरून मेमरी मर्यादित राहील. सर्वात जुने टाका, किंवा कमी वेळा snapshot घ्या, खर्च नियंत्रित करण्यासाठी.

100
Ship

Undo, redo आणि rollback जागच्या जागी

Originator encapsulation अबाधित ठेवून संपूर्ण undo आणि redo ला आधार देतो, तसेच धोकादायक क्रियांसाठी checkpoint आणि rollback देखील.

सामान्य अडचणी

अडचणी आणि anti-patterns

Memento सांगायला सोपा आहे आणि सूक्ष्मपणे चुकीचा करणे सोपे आहे. या नेहमीच्या सापळ्या आहेत.

💥 मेमरी फुगणे

प्रत्येक snapshot म्हणजे स्थितीची संपूर्ण नक्कल. मोठ्या document वर प्रत्येक कीस्ट्रोकला save केल्यास मेमरी अमर्याद वाढते. history मर्यादित करा आणि ढोबळ सीमांवर snapshot घ्या.

🔗 उथळ नकला

deep copy ऐवजी references साठवल्यास नंतरची mutations जुन्या mementos ना गुपचूप बिघडवतात. मग restore चुकीची स्थिती परत करतो. mutable डेटा value ने नक्कल करा.

🔓 गळणारे interface

memento ची संपूर्ण स्थिती caretaker ला दाखवल्यास तुम्ही टाळू पाहत असलेली encapsulation ची फूट पुन्हा निर्माण होते. wide interface originator पुरतेच खाजगी ठेवा.

🧨 Caretaker mementos संपादित करणे

caretaker memento च्या आतील गोष्टी बदलत किंवा अर्थ लावत असेल तर तो originator च्या अंतर्गत तपशिलांशी जोडला जातो. Caretaker ने mementos ना अपारदर्शक tokens म्हणून वागवले पाहिजे.

🐌 प्रचंड स्थितीचा snapshot

मोठ्या ऑब्जेक्ट्सचे संपूर्ण snapshots मंद आणि जड असतात. मोठ्या स्थितीसाठी संपूर्ण नकलांऐवजी diffs साठवणारे incremental किंवा command-आधारित undo पसंत करा.

🌐 स्थितीत बाह्य संसाधने

Sockets, file handles किंवा threads यांचा अर्थपूर्ण snapshot घेऊन पुन्हा प्रस्थापित करता येत नाही. फक्त serializable, value-सारखी स्थिती जतन करा, live संसाधने नव्हे.

तडजोडी

तडजोडी आणि कधी वापरावे

Memento मेमरी आणि नकलेच्या खर्चाच्या किमतीत स्वच्छ, encapsulated rollback देतो. त्याकडे वळण्यापूर्वी दोन्हींचा विचार करा.

पैलूतपशील
फायदेencapsulation जपते, स्वच्छ undo आणि rollback देते, आणि इतिहासाचे तर्क originator च्या बाहेर ठेवते.
तोटेसंपूर्ण snapshots मेमरी आणि नकलेचा वेळ खर्च करतात; मोठ्या स्थितीचे वारंवार जतन संसाधन वापरावर वर्चस्व गाजवू शकते.
केव्हा वापरावेतुम्हाला undo, redo, checkpoints किंवा transactional rollback हवे असते आणि ऑब्जेक्टचे अंतर्गत तपशील दाखवायचे नसतात.
केव्हा टाळावेस्थिती खूप मोठी असते किंवा सतत बदलते; संपूर्ण नकला साठवण्याऐवजी command-आधारित diffs किंवा event sourcing पसंत करा.
गुंतागुंतरचनात्मकदृष्ट्या कमी, पण अचूकता deep copying वर आणि memento caretaker साठी अपारदर्शक ठेवण्यावर अवलंबून असते.
संबंधितCommand उलट करण्याच्या क्रिया साठवतो; Prototype स्थितीचे clone करतो; State तुम्ही snapshot घेता त्या modes चे model करतो; Iterator इतिहासातून फिरू शकतो.
ठोकताळा: स्थितीचा snapshot स्वस्त आणि स्वयंपूर्ण असेल तेव्हा Memento कडे वळा. स्थिती मोठी असेल किंवा संपादने वारंवार असतील तेव्हा संपूर्ण ऑब्जेक्टऐवजी काय बदलले (Command) ते साठवा.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

production-शैलीतील वापरात Memento दाखवणारे तीन प्रातिनिधिक नमुने.

📝

1 · टेक्स्ट editor मधील undo history

नमुना: multi-level undo आणि redo

एका code editor ला buffer चे अंतर्गत तपशील न दाखवता संपादने, निवडी आणि cursor हालचालींवर अमर्याद undo हवे असते.

  • प्रत्येक संपादन document originator कडे त्याच्या buffer आणि cursor चा memento मागते.
  • एक caretaker undo आणि redo stacks ठेवतो, user मागे फिरत असताना त्यांच्यामध्ये pop करतो.
  • History मर्यादित असते आणि snapshots एकत्र केले जातात जेणेकरून जलद टाइपिंग मेमरी संपवत नाही.
✅ निष्कर्ष: buffer चे स्वरूप पूर्णपणे लपवलेले असताना विश्वासार्ह undo आणि redo, त्यामुळे editor त्याचे अंतर्गत model इतिहास कोडला स्पर्श न करता बदलू शकतो.
🎮

2 · गेममधील save आणि load

नमुना: checkpoints आणि restore

एका गेमला खेळाडूंना checkpoints वर प्रगती save करू द्यावी लागते आणि पराभवानंतर नेमकी जगाची स्थिती पुन्हा load करावी लागते.

  • गेम स्थिती ऑब्जेक्ट खेळाडूचे स्थान, inventory आणि world flags यांचा memento तयार करतो.
  • एक save manager mementos ना नाव दिलेल्या slots म्हणून साठवतो आणि त्यांना disk वर serialize करतो.
  • load करताना निवडलेला memento स्थिती ऑब्जेक्टला परत दिला जातो जेणेकरून तो क्षण नेमका पुन्हा प्रस्थापित होईल.
✅ निष्कर्ष: खेळाडू संपूर्ण जग शाबूत असताना कोणत्याही checkpoint वरून पुन्हा सुरू करतात, तर save प्रणाली गेम स्थिती कशी रचली आहे यापासून वेगळी राहते.
🔁

3 · form wizard मधील transactional rollback

नमुना: सर्व-किंवा-काहीच-नाही स्थिती बदल

एक multi-step wizard user पुढे जाताना बदल लागू करतो पण अंतिम submission अयशस्वी झाल्यास सर्वकाही परत फिरवावे लागते.

  • धोकादायक commit च्या आधी, model त्याची संपूर्ण स्थिती एका checkpoint memento मध्ये snapshot करतो.
  • server ने submission नाकारल्यास, model checkpoint atomically पुन्हा प्रस्थापित करतो.
  • यशस्वी झाल्यास checkpoint टाकून दिला जातो, नवीन स्थिती commit करून सोडली जाते.
✅ निष्कर्ष: Users कधीही अर्धवट लागू केलेली स्थिती पाहत नाहीत; अयशस्वी submit कोणत्याही manual undo तर्काशिवाय शेवटच्या चांगल्या snapshot वर स्वच्छपणे परत फिरतो.
07 - सुसंगतता

आधुनिक सुसंगतता

Memento जुना आहे, पण स्थिती जतन करून पुन्हा प्रस्थापित करण्याची त्याची कल्पना आजच्या बऱ्याच सॉफ्टवेअरमधून वाहते.

🧠 state management libraries

Redux time-travel debugging म्हणजे मोठ्या प्रमाणावरील Memento: प्रत्येक dispatch केलेली action store चा snapshot घेते जेणेकरून तुम्ही स्थितीतून मागे पाऊल टाकू शकता.

📼 event sourcing शी विरोधाभास

Event sourcing संपूर्ण snapshots ऐवजी बदलांच्या log मधून स्थिती पुन्हा बांधते, पण replay जलद करण्यासाठी सहसा नियतकालिक snapshots ना Memento-शैलीतील checkpoints म्हणून वापरते.

🗄️ database savepoints

Transactional savepoints आणि rollbacks Memento च्या checkpoint वापराचे प्रतिबिंब आहेत, ज्यामुळे एक कामाचे एकक ज्ञात चांगल्या बिंदूकडे परत फिरू शकते.

📸 immutable snapshots

Persistent, immutable डेटा रचना Memento स्वस्त करतात: न बदललेले भाग सामायिक केल्याने प्रत्येक snapshot फक्त फरक साठवतो.

🧩 Command अधिक Memento

undo प्रणाली अनेकदा दोन्ही एकत्र करतात: Command action नोंदवतो तर Memento action पुन्हा गणू शकत नाही अशी कोणतीही स्थिती जतन करतो.

☁️ serverless आणि workflows

Durable workflow engines अंमलबजावणीची स्थिती checkpoint करतात जेणेकरून थांबलेली किंवा क्रॅश झालेली run नेमकी जिथे थांबली होती तिथून पुन्हा सुरू होऊ शकते.

सारांश: Memento म्हणजे एखाद्या ऑब्जेक्टला त्याला उघडून न पाहता rewind बटण देण्याचा मार्ग. जेव्हाही तुम्हाला encapsulation अबाधित ठेवून undo, checkpoints किंवा rollback हवे असते, तेव्हा snapshot-आणि-restore ही कल्पना योग्य साधन आहे, तिच्या मेमरी खर्चाशी तोलून.
