Creational पॅटर्न

Singleton पॅटर्न - एकच instance, एकच जागतिक दरवाजा

Singleton हमी देतो की एका class ला नेमके एकच instance असते आणि त्याच्यापर्यंत पोहोचण्यासाठी एकच, जागतिक प्रवेश बिंदू पुरवतो. वर्णन करायला हा सर्वात सोपा creational पॅटर्न आहे आणि चुकीचा वापर करायलाही सर्वात सोपा: initialization आणि threading बरोबर केले, तर खरोखर अनन्य साधन मांडण्याचा हा स्वच्छ मार्ग आहे; सवयीने त्याकडे वळलात, तर तो लपलेली global state बनतो जी हळूच तुमच्या चाचण्यांचा नाश करते.

01 - काय

Singleton म्हणजे काय?

Singleton हा एक creational डिझाइन पॅटर्न आहे जो class ला एकाच instance पुरता मर्यादित करतो आणि ते instance एका जागतिक प्रवेश बिंदूद्वारे, सहसा static getInstance() method द्वारे, उघड करतो. Constructor private केला जातो जेणेकरून इतर कोणताही code new कॉल करू शकत नाही, आणि class स्वतः तो एकमेव object धारण करते जो ती कधीही देते.

🔒 Private constructor

Constructor लपवलेला असतो जेणेकरून कॉलर स्वतःच्या प्रती तयार करू शकत नाहीत. Instance केव्हा आणि तयार करायचे का हे फक्त class ठरवते.

📦 Static धारक

एक private static field हे एकमेव instance साठवते. हा class-पातळीचा कप्पा आहे जो सर्व कॉलर अखेरीस सामायिक करतात.

🚪 जागतिक प्रवेश बिंदू

एक public static getInstance() सामायिक instance परत करते, गरज पडल्यास पहिल्या वापरावेळी ते तयार करते.

02 - का

Singleton का अस्तित्वात आहे

काही साधने खरोखरच अनन्य असतात: एकच connection pool, एकच in-memory cache, एकच hardware device handle. अनेक तयार करणे चुकीचे किंवा वाया घालवणारे ठरेल, आणि एकच वस्तू सर्वत्र हाताने फिरवणे कंटाळवाणे आहे. Singleton तो "नेमके एकच आहे" हा नियम class मध्येच केंद्रित करतो.

🎯 अनन्यता लागू करते

जेव्हा एकापेक्षा जास्त instance state भ्रष्ट करेल किंवा दुर्मिळ साधनाची नक्कल करेल, तेव्हा private constructor दुसरी प्रत केवळ नापसंत न करता अशक्य बनवते.

🌍 एकच सुप्रसिद्ध प्रवेश बिंदू

कोणताही code सामायिक object पर्यंत constructors आणि method parameters मधून न फिरवता पोहोचू शकतो, जे logging सारख्या cross-cutting बाबींसाठी सोयीचे आहे.

💤 नियंत्रित, lazy निर्मिती

Instance startup वेळी न करता पहिल्या वापरावेळी तयार होऊ शकते, त्यामुळे महागडे setup फक्त object खरोखर गरजेचे असल्यासच होते.

📉 सामायिक, समन्वयित state

ज्यावर सर्वांचे एकमत असावे असे caches, configuration, आणि counters एकाच ठिकाणी राहतात, त्यामुळे भरकटणाऱ्या प्रतींऐवजी एकच सत्याचा स्रोत असतो.

सोप्या शब्दांत

उपमांसह Singleton समजावून

तीच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असलात तरी ती पटेल.

🎓 विद्यार्थ्यासाठी

Singleton म्हणजे registrar तुम्हाला देणारे एकच विद्यार्थी ओळखपत्र. नेमके एकच असते, सर्वजण त्याच क्रमांकाचा उल्लेख करतात, आणि तुम्ही स्वतःला दुसरी अधिकृत प्रत छापू शकत नाही.

👩‍💻 डेव्हलपरसाठी

तो एका factory method मागचा module-पातळीचा constant object आहे. पहिला कॉल तो तयार करतो, नंतरचा प्रत्येक कॉल तोच reference मिळवतो, आणि new पर्याय राहत नाही.

🏢 व्यावसायिकासाठी

कंपनीच्या एकाच अधिकृत शिक्क्याचा विचार करा. कोणताही विभाग कागदावर शिक्का मारू शकतो, पण एकाच ठिकाणी ठेवलेला एकच अधिकृत शिक्का असतो जो सर्वजण सामायिक करतात.

🏛️ रोजच्या जीवनातील आवृत्ती

एका देशाला एका वेळी एकच राष्ट्रपती असतो. लोक कोणाचेही नाव न घेता "राष्ट्रपती" असा उल्लेख करतात, आणि ते पद हमी देते की एकाच वेळी दोन कधीच नसतात.

03 - कसे

ते आतून कसे काम करते

Singleton आपला constructor लपवतो आणि एक static accessor उघड करतो. रंजक निर्णय म्हणजे instance केव्हा तयार होते (eager विरुद्ध lazy) आणि अनेक threads एकाच वेळी accessor कॉल करतात तेव्हा निर्मिती कशी बरोबर राहते.

🌅 Eager initialization

Instance class लोड होताना, एका static field मध्ये तयार होते. Class loader एकवेळ init ची हमी देत असल्याने ते स्वाभाविकपणे thread-safe आहे, पण object कधीही न वापरले तरी तयार होते.

🌙 Lazy initialization

Instance पहिल्या getInstance() कॉलवर तयार होते. न वापरल्यास काम वाचते, पण check-then-create पायरी concurrency खाली race असते आणि सुरक्षित राहण्यासाठी काळजी लागते.

रचना एका दृष्टिक्षेपात

रचना - एक private constructor आणि एक static accessor जो एका सामायिक field चे रक्षण करतो
classDiagram
    class Singleton {
        -static Singleton instance
        -Singleton()

    class Client {

Java मध्ये thread-safe lazy Singleton

public final class Config {

    // volatile so the half-built instance is never seen by another thread
    private static volatile Config instance;

    private final Map<String, String> settings;

    private Config() {
        settings = loadFromDisk();      // expensive, do it once
    }

    public static Config getInstance() {
        Config result = instance;        // read the volatile field once
        if (result == null) {            // first check (no lock, fast path)
            synchronized (Config.class) {
                result = instance;
                if (result == null) {    // second check (inside the lock)
                    instance = result = new Config();
                }
            }
        }
        return result;
    }

    public String get(String key) {
        return settings.get(key);
    }
}

हे double-checked locking आहे. Instance अस्तित्वात आल्यावर पहिली null तपासणी lock वगळते, त्यामुळे सामान्य मार्ग वेगवान राहतो; volatile keyword हेच ते बरोबर बनवते, कारण त्याशिवाय दुसरा thread अंशतः तयार झालेले object पाहू शकेल.

04 - Sequence आकृत्या

तपशीलवार sequence आकृत्या

तीन दृश्ये: lazy पहिला-आणि-नंतरचा प्रवेश, double-checked locking द्वारे सोडवलेली concurrent race, आणि चाचणी करता येण्याजोगा पर्याय म्हणून dependency injection.

आकृती 1 - पहिल्या कॉलवर lazy निर्मिती, नंतर cache केलेला पुनर्वापर

आकृती 2 - दोन threads race करतात, double-checked locking ते एकच ठेवते
sequenceDiagram
    autonumber
    participant T1 as Thread 1
    participant T2 as Thread 2
    participant S as Singleton class
    participant L as Lock

    T1->>S: getInstance()
    T2->>S: getInstance()

    T2->>L: release

05 - पायरी दर पायरी

0 ते 100 प्रवाह

तुम्हाला एकच instance हवे असे ठरवण्यापासून ते सुरक्षितपणे वापरणे आणि त्याभोवती चाचणी करणे - संपूर्ण प्रवास क्रमाने.

00
ठरवा

एकच instance खरोखर आवश्यक आहे याची खात्री करा

एकापेक्षा जास्त object खरोखर चुकीचे ठरेल का हे विचारा. दोन प्रती फक्त गैरसोयीच्या असतील, तर सामान्य object आणि injection हे Singleton पेक्षा अधिक योग्य आहे.

10
बंद करा

Constructor private करा

Constructor लपवा जेणेकरून बाहेरचा कोणताही code new कॉल करू शकत नाही. "कृपया फक्त एकच बनवा" याचे लागू केलेल्या हमीमध्ये रूपांतर करणारी हीच यंत्रणा आहे.

20
साठवा

Static instance field जोडा

तो एकमेव object धारण करण्यासाठी एक private static field घोषित करा. Lazy निर्मितीसाठी ते volatile चिन्हांकित करा जेणेकरून concurrent वाचन बरोबर राहते.

30
उघड करा

Static accessor लिहा

सामायिक field परत करणारे एक public static getInstance() जोडा. प्रत्येक कॉलर वापरत असलेला हा एकमेव जागतिक दरवाजा आहे.

40
निवडा

Eager किंवा lazy init निवडा

Object स्वस्त आणि नेहमी गरजेचे असल्यास class लोडवेळी eagerly बनवा; निर्मिती महागडी असल्यास किंवा कधीच होणार नसेल तर lazy जा.

50
रक्षण करा

निर्मिती thread-safe करा

Lazy निर्मितीचे double-checked locking ने रक्षण करा, किंवा holder idiom किंवा enum ने locks पूर्णपणे टाळा. Concurrent code मध्ये उघडी check-then-create कधीही सोडू नका.

60
बळकट करा

मागचे दरवाजे बंद करा

Reflection, serialization, आणि अनेक class loaders विरुद्ध रक्षण करा जे प्रत्येकी दुसरे instance बनवू शकतात. एक enum Singleton तिन्ही फुकट हाताळतो.

70
वापरा

गरजेच्या ठिकाणी getInstance कॉल करा

Consumers class कडे instance मागतात आणि त्याचे वर्तन वापरतात. पहिला कॉल ते तयार करतो; नंतरचा प्रत्येक कॉल cache केलेले object पुन्हा वापरतो.

80
वास तपासा

लपलेल्या coupling वर लक्ष ठेवा

प्रत्येक थेट getInstance() कॉल एक अदृश्य dependency आहे. त्यांची मोजणी करा; Singleton lookups ने भरलेली class समजायला आणि पुन्हा वापरायला कठीण असते.

90
Refactor

Instance inject करण्यास प्राधान्य द्या

"फक्त एकच" हे container scope म्हणून किंवा main मधील एकाच wiring म्हणून ठेवा, पण ते constructors मधून पास करा जेणेकरून सहकारी static कॉलवर नव्हे तर एका interface वर अवलंबून राहतील.

100
चाचणी करा

चाचण्यांमध्ये त्याची अदलाबदल करा

Dependency inject केलेली असल्याने, चाचण्या खऱ्या Singleton ऐवजी fake किंवा mock देतात. चाचण्यांमध्ये resetकरायला global state नाही, क्रमावर अवलंबून अस्थिरता नाही.

सामान्य धोके

धोके आणि anti-patterns

Singleton हा anti-pattern असे लेबल लागण्याची सर्वात जास्त शक्यता असलेला पॅटर्न आहे, आणि सहसा योग्य कारणासाठी. हे ते सापळे आहेत.

🕳️ लपलेली global state

Singleton म्हणजे class चा पोशाख घातलेला global variable. कोणतीही method कुठूनही त्याची state बदलू शकते, त्यामुळे bugs गैर-स्थानिक बनतात आणि वर्तन अदृश्य कॉल इतिहासावर अवलंबून राहते.

🧪 चाचणी न करता येणारा code

अंतर्गतपणे getInstance() कॉल करणाऱ्या classes स्वतंत्रपणे चाचणी करता येत नाहीत. तुम्ही fake बदलू शकत नाही, आणि सामायिक state चाचणी प्रकरणांमध्ये गळते ज्यामुळे क्रमावर अवलंबून अस्थिरता येते.

🧵 तुटलेली lazy init

साधी null तपासणी असलेला भोळा lazy Singleton threads खाली race करतो आणि दोन instances तयार करू शकतो, किंवा volatile नसल्यास अंशतः तयार झालेले object देऊ शकतो.

🔗 घट्ट coupling

थेट static कॉल कॉलरना ठोस class शी घट्ट जोडतात. Dependencies यापुढे constructor signature मध्ये दिसत नाहीत, त्यामुळे class ला खरोखर काय हवे ते तुम्ही पाहू शकत नाही.

🪞 Reflection आणि serialization गळती

Reflection private constructor कॉल करू शकते आणि deserialization object पुन्हा बांधू शकते, दोन्ही दुसरे instance बनवतात जोपर्यंत तुम्ही स्पष्टपणे त्यांच्याविरुद्ध रक्षण करत नाही.

🧲 Singleton चा अतिवापर

प्रत्येक manager, helper, आणि service ला "सोयीसाठी" Singleton बनवल्याने अस्पष्ट आयुष्यमान आणि startup क्रमाच्या दु:स्वप्नांसह global objects चे जाळे तयार होते.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Singleton testability आणि लपलेल्या coupling च्या किमतीत हमी दिलेली अनन्यता आणि सोपा प्रवेश विकत घेतो. त्याकडे वळण्यापूर्वी दोन्ही बाजूंचे वजन करा.

फायदेएकच instance ची हमी देतो, एकच प्रवेश बिंदू देतो, lazy महागड्या setup ला आधार देतो, आणि सामायिक state एकाच अधिकृत ठिकाणी केंद्रित करतो.
तोटेलपलेली global state आणतो, testability आणि isolation ला हानी पोहोचवतो, ठोस class शी coupling घट्ट करतो, आणि constructors पासून खऱ्या dependencies लपवतो.
केव्हा वापरावेएखादे साधन खरोखर अनन्य असेल (device handle, एकच connection pool) आणि पर्याय खरोखरच सामान्य inject केलेले object असू शकत नाही.
केव्हा टाळावेतुम्हाला फक्त सोयीचा प्रवेश हवा असेल, किंवा object बदलणारी व्यावसायिक state धारण करत असेल. त्याऐवजी single-instance scope असलेले dependency injection वापरा.
गुंतागुंतState च्या दृष्टीने कमी, पण thread-safe आणि reflection-safe करायला सूक्ष्म. Enum आणि holder idiom बहुतांश ती गुंतागुंत लपवतात.
संबंधितFactory Method आणि Abstract Factory (सहसा singleton-scoped), Prototype (सामायिक करण्याऐवजी cloning), Facade (लागू केलेल्या अनन्यतेशिवाय एकच प्रवेश बिंदू).
ठोकताळा: तुम्हाला "फक्त एकच" हवे असेल, तर DI container चे singleton scope वापरा आणि ते inject करा. भाषेनेच अनन्यता लागू करावी लागणाऱ्या दुर्मिळ प्रकरणांसाठी पारंपरिक static Singleton राखून ठेवा, आणि तेव्हा enum Singleton कडे वळा.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

वास्तविक प्रणालींमध्ये Singleton आणि त्याचे सुरक्षित प्रकार दाखवणारे तीन प्रातिनिधिक नमुने.

🗄️

1 · Database connection pool

नमुना: एकच सामायिक, महागडे साधन

Application ने database connections चा एकच pool सामायिक केला पाहिजे जेणेकरून database ची connection मर्यादा कधीही संपत नाही.

  • Pool बांधायला महाग असल्याने, तो thread-safe accessor मागे पहिल्या वापरावेळी lazily तयार होतो.
  • प्रत्येक request त्या एकाच pool मधून connections घेते आणि परत करते, एकूण connections मर्यादित ठेवते.
  • आधुनिक stacks मध्ये pool container singleton म्हणून नोंदवला जातो आणि inject केला जातो, statically मिळवला जात नाही.
✅ परिणाम: connections मर्यादेत राहतात आणि setup एकदाच होते, तर injection pool ला in-memory test double साठी अदलाबदल करण्याजोगा ठेवते.
🪵

2 · Application logger

नमुना: cross-cutting प्रवेश बिंदू

प्रत्येक स्तरातील code ला एकाच logging backend वर सुसंगत configuration आणि buffering सह लिहायचे असते.

  • एकच logger instance output sinks, formatters, आणि async buffer ची मालकी घेते.
  • पारंपरिक अंमलबजावणी ते statically उघड करतात, जे सोयीचे आहे पण प्रत्येक class ला logger शी जोडते.
  • Frameworks आता प्रत्येक class मागे logger inject करतात, एकच backend जपत चाचणी करता येण्याजोग्या, स्पष्ट dependencies पुनर्संचयित करतात.
✅ परिणाम: सर्वत्र सुसंगत, buffered logging, injection प्रत्येक class ला नाव असलेला logger देते जो तुम्ही चाचण्यांमध्ये पकडू आणि तपासू शकता.
⚙️

3 · Runtime configuration आणि enum registry

नमुना: सुरक्षित अनन्यतेसाठी enum Singleton

एखाद्या service ला एकच अधिकृत, अपरिवर्तनीय configuration object हवे असते जे reflection आणि serialization हल्ल्यांना दाद देत नाही.

  • Configuration एकल-मूल्य enum म्हणून मांडली जाते, जी JVM नेमके एकदाच instantiate करण्याची हमी देते.
  • Enum स्वरूप reflection आणि deserialization ने दुसरे instance बनवण्यापासून प्रतिकारक्षम आहे, साध्या class च्या उलट.
  • मूल्ये class-load वेळी एकदाच लोड होतात आणि read-only accessors म्हणून उघड होतात.
✅ परिणाम: भाषा एकच instance ची हमी देत असल्यामुळे, शून्य locking code सह खरोखर अनन्य, छेडछाड-प्रतिरोधक config object.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

"नेमके एकच" ची गरज कधीही नाहीशी झाली नाही, पण आपण ते कसे साध्य करतो हे static accessors कडून container-व्यवस्थापित आयुष्यमानाकडे सरकले आहे.

💉 DI containers जिंकले

Spring, Guice, आणि .NET services singleton scope मध्ये नोंदवतात आणि inject करतात. Static कॉलशिवाय तुम्हाला एकच instance मिळते, आणि चाचण्यांमध्ये ते सहज बदलता येते.

🏅 Enum Singleton हा सुवर्ण मानक आहे

Java मध्ये तुम्हाला खरोखर static Singleton हवे असेल, तेव्हा एकल-मूल्य enum हे शिफारस केलेले स्वरूप आहे कारण ते संक्षिप्त आणि reflection व serialization विरुद्ध सुरक्षित आहे.

🪟 Locks शिवाय lazy साठी holder idiom

Initialization-on-demand holder idiom एक nested static class वापरतो जेणेकरून JVM च्या class-loading हमी तुम्हाला synchronization शिवाय lazy, thread-safe init देतात.

📦 JS/TS मधील module singletons

ES module एकदाच evaluate होते, त्यामुळे एक instance export केल्याने class किंवा static method शिवाय नैसर्गिक singleton मिळते - runtime caching करते.

🧊 Immutability धोका निष्प्रभ करते

बहुतांश हानी बदलणाऱ्या global state मुळे होते. Stateless किंवा immutable Singleton (शुद्ध config, constants) खूप कमी तोट्यांसह सोय जपते.

🧭 सावधगिरीची कथा म्हणून शिकवले जाते

Singleton हे सहज हाती घेता येणाऱ्या पण सोबत जगायला कठीण अशा पॅटर्नचे उत्कृष्ट उदाहरण राहिले आहे, त्यामुळे आता ते त्याच्या स्वतःच्या anti-pattern टीकेसह शिकवले जाते.

सारांश: ध्येय ठेवा, सवय सोडा. तुम्हाला एकच instance हवे असेल, तेव्हा ते तुमच्या composition root मधील एकच wiring किंवा container scope म्हणून व्यक्त करा आणि ते inject करा. भाषेनेच अनन्यता लागू करावी लागणाऱ्या दुर्मिळ प्रकरणासाठी पारंपरिक static Singleton, आदर्शतः enum स्वरूप, राखून ठेवा.
