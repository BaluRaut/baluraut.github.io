Interface Segregation - clients ना कधीही न वापरणाऱ्या methods पासून दूर ठेवा

Interface Segregation Principle सांगते की कोणत्याही client ला त्याने न वापरलेल्या methods वर अवलंबून राहण्यास भाग पाडले जाऊ नये. जेव्हा एकच मोठे fat interface वाचन, लेखन, refunds आणि exports एकत्र बांधून ठेवते, तेव्हा प्रत्येक consumer ला तो कधीही स्पर्श न करणाऱ्या कोडशी बांधले जाते. ISP त्या प्रचंड contract ला लहान, केंद्रित role interfaces मध्ये विभागते, जेणेकरून प्रत्येक caller ला त्याला खरोखर हवा असलेला तेवढाच भाग अवलंबून राहावा लागतो.

01 - काय

Interface Segregation Principle म्हणजे काय?

Interface Segregation हे SOLID मधील "I" आहे. ते सांगते की एखाद्या class ला अशा फुगलेल्या interface ची अंमलबजावणी करण्यास, आणि caller ला त्यावर अवलंबून राहण्यास कधीही भाग पाडू नये जिच्या methods तो वापरणारच नाही. एका सर्वज्ञ contract ऐवजी, तुम्ही अनेक लहान role interfaces ठरवता - client एखाद्या object शी ज्या वेगवेगळ्या पद्धतीने संवाद साधतो त्यातील प्रत्येकासाठी एक - आणि types ना नेमक्या त्याच roles ची अंमलबजावणी करू देता ज्यांना त्या support करतात.

🧩 Role interfaces

एक fat contract ला OrderReader आणि OrderWriter सारख्या केंद्रित भागांमध्ये मोडा. प्रत्येक भाग एका client अवलंबून राहू शकेल अशा एकाच जबाबदारीला नाव देतो.

🔌 Client-specific contracts

फक्त वाचन करणारी reporting service OrderReader मागते आणि तिला save किंवा delete कधीही दिसत नाही. Interface implementer नव्हे तर consumer कडून आकार घेते.

🧱 जोडा, फुगवू नका

एकच concrete class एकाच वेळी अनेक role interfaces ची अंमलबजावणी करू शकते. Callers ना तरीही फक्त त्यांना दिलेला अरुंद role दिसतो, त्यामुळे coupling किमान राहते.

02 - का

Interface Segregation का अस्तित्वात आहे

Fat interfaces खोटे coupling पसरवतात. charge, refund आणि payout एकाच interface मध्ये एकत्र करणारा payment gateway फक्त charge करणाऱ्या checkout स्क्रीनला payout API बदलल्यावर recompile करण्यास भाग पाडतो. ISP ती काल्पनिक अवलंबित्वे कापून टाकते.

🎯 कमीवर अवलंबून राहा

फक्त inventory वाचणारा client, write path विकसित झाल्यावर तुटू नये, recompile होऊ नये किंवा पुन्हा test होऊ नये. अरुंद contracts consumer बांधलेला पृष्ठभाग आकुंचित करतात.

🧪 वेगळेपणाने test करा

पाच-method role mock करणे सोपे आहे; चाळीस-method god interface mock करणे हे एक कष्टाचे काम आहे जे teams ना ठिसूळ, अति-विस्तृत fakes कडे ढकलते.

🚫 throw-not-supported stubs नकोत

जेव्हा read replica write करू शकत नाही, तेव्हा fat interface runtime ला throw होणारा save() सक्तीने लादते. विभागलेले roles तिला फक्त writer contract ची अंमलबजावणी न करण्याची मुभा देतात.

🔭 नावानेच हेतू

एखाद्या service ला OrderReader देणे हे दस्तऐवजीकरण करते की ती काहीही बदलणार नाही. Type स्वतःच एक सुरक्षाकडे आणि design विधान आहे.

सोप्या शब्दांत

उपमांसह Interface Segregation ची ओळख

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती नीट समजते.

🎓 विद्यार्थ्यासाठी

अशा एका लायब्ररी कार्डाची कल्पना करा जे तुम्हाला कायदेशीररीत्या पुस्तके रचायला, payroll सांभाळायला आणि boiler दुरुस्त करायला बांधून टाकते. तुम्हाला फक्त उसने घ्यायचे आहे. ISP तुम्हाला फक्त उसने घेणारे कार्ड देते आणि सफाई कर्मचाऱ्याला वेगळे कार्ड देते.

👩‍💻 डेव्हलपरसाठी

वीस methods असणाऱ्या एका Repository ऐवजी, तुम्ही Reader आणि Writer उघड करता. एक query handler Reader घेतो; तो अक्षरशः delete करूच शकत नाही, आणि write बाजू बदलल्यावर तो कधीही पुन्हा build होत नाही.

🏢 व्यावसायिकासाठी

"फक्त refunds" पुरता मर्यादित vendor contract म्हणजे तुम्ही त्यांच्या payout जबाबदाऱ्यांसाठी उत्तरदायी नाही. Contract नेमक्या वापरलेल्या service पुरता अरुंद करा आणि कायदेशीर फैलाव त्यासोबतच आकुंचित होतो.

🔧 रोजची आवृत्ती

एक power outlet तुम्हाला दोन slots देतो, संपूर्ण breaker panel नाही. तुम्हाला जे हवे ते तुम्ही plug करता; फक्त फोन charge करण्यासाठी तुमच्या हातात इमारतीतील प्रत्येक switch दिला जात नाही.

03 - कसे

ते आतून कसे कार्य करते

एका fat contract पासून सुरुवात करा, त्याचे clients जे वेगवेगळे roles बजावतात ते ओळखा, आणि प्रत्येक role साठी एक interface कोरून काढा. एक concrete class ती खरोखर support करणाऱ्या प्रत्येक role ची अंमलबजावणी करते; प्रत्येक caller फक्त त्याला हवा असलेला role मागतो.

🔎 Client roles शोधा

Interface च्या प्रत्येक consumer ची आणि प्रत्येकजण खरोखर call करणाऱ्या methods ची यादी करा. एकत्र वापरल्या जाणाऱ्या methods चे समूह नैसर्गिक role सीमा उघड करतात - reader, writer, refunder, payout.

✂️ विभागा, मग जोडा

प्रत्येक समूह त्याच्या स्वतःच्या interface मध्ये काढा. Concrete gateway त्या सर्वांची अंमलबजावणी करते; checkout प्रवाह Charger वर, ops साधन Refunder वर अवलंबून राहते.

एक fat interface role interfaces मध्ये विभागणे

// Role interfaces, not one fat PaymentGateway
interface Charger {
  charge(amountCents: number, cardToken: string): Receipt;
}
interface Refunder {
  refund(chargeId: string, amountCents: number): Receipt;
}
interface Payout {
  payout(accountId: string, amountCents: number): Transfer;
}

// One concrete implementation can play many roles
class StripeGateway implements Charger, Refunder, Payout {
  charge(amountCents: number, cardToken: string): Receipt {
    return { id: "ch_1", amountCents, status: "captured" };
  }
  refund(chargeId: string, amountCents: number): Receipt {
    return { id: "re_1", amountCents, status: "refunded" };
  }
  payout(accountId: string, amountCents: number): Transfer {
    return { id: "po_1", accountId, amountCents };
  }
}

// Checkout depends ONLY on Charger - it cannot refund or pay out
class CheckoutService {
  constructor(private readonly gateway: Charger) {}
  placeOrder(cart: Cart): Receipt {
    return this.gateway.charge(cart.totalCents, cart.cardToken);
  }
}

const stripe = new StripeGateway();
const checkout = new CheckoutService(stripe); // passes as a Charger
const receipt = checkout.placeOrder({ totalCents: 4999, cardToken: "tok_visa" });
console.log(receipt.status); // "captured"
from typing import Protocol

# Role interfaces expressed as structural Protocols
class Charger(Protocol):
    def charge(self, amount_cents: int, card_token: str) -> Receipt: ...

class Refunder(Protocol):
    def refund(self, charge_id: str, amount_cents: int) -> Receipt: ...

class Payout(Protocol):
    def payout(self, account_id: str, amount_cents: int) -> Transfer: ...

# One concrete gateway satisfies all three roles
class StripeGateway:
    def charge(self, amount_cents: int, card_token: str) -> Receipt:
        return Receipt(id="ch_1", amount_cents=amount_cents, status="captured")

    def refund(self, charge_id: str, amount_cents: int) -> Receipt:
        return Receipt(id="re_1", amount_cents=amount_cents, status="refunded")

    def payout(self, account_id: str, amount_cents: int) -> Transfer:
        return Transfer(id="po_1", account_id=account_id, amount_cents=amount_cents)

# Checkout depends ONLY on Charger
class CheckoutService:
    def __init__(self, gateway: Charger) -> None:
        self._gateway = gateway

    def place_order(self, cart: Cart) -> Receipt:
        return self._gateway.charge(cart.total_cents, cart.card_token)

stripe = StripeGateway()
checkout = CheckoutService(stripe)  # accepted as a Charger
receipt = checkout.place_order(Cart(total_cents=4999, card_token="tok_visa"))
print(receipt.status)  # "captured"

# One concrete gateway mixes in every role it supports
class StripeGateway
  include Charger, Refunder, Payout

  def charge(amount_cents, card_token)
    Receipt.new(id: "ch_1", amount_cents: amount_cents, status: "captured")
  end

  def refund(charge_id, amount_cents)
    Receipt.new(id: "re_1", amount_cents: amount_cents, status: "refunded")
  end

  def payout(account_id, amount_cents)
    Transfer.new(id: "po_1", account_id: account_id, amount_cents: amount_cents)
  end
end

# Checkout only ever calls the charging role
class CheckoutService
  def initialize(gateway)
    @gateway = gateway
  end

  def place_order(cart)
    @gateway.charge(cart.total_cents, cart.card_token)
  end
end

stripe = StripeGateway.new
checkout = CheckoutService.new(stripe)
receipt = checkout.place_order(Cart.new(total_cents: 4999, card_token: "tok_visa"))
puts receipt.status # "captured"

लक्षात घ्या की CheckoutService ला नेहमी फक्त एक Charger मिळतो. त्याला refunds किंवा payouts बद्दल compile-time ला काहीही माहिती नसते, त्यामुळे ते roles विकसित झाले तरी त्याला तोडू शकत नाहीत - हेच ISP एका विस्तृत अवलंबित्वाचे नेमक्या अवलंबित्वात रूपांतर करत आहे.

आधी आणि नंतर: एक fat repository Reader आणि Writer मध्ये विभागलेली

// BEFORE - one fat interface every client must depend on
interface OrderRepository {
  findById(id: string): Order | null;
  search(query: OrderQuery): Order[];
  save(order: Order): void;
  delete(id: string): void;
}

// AFTER - segregated roles
interface OrderReader {
  findById(id: string): Order | null;
  search(query: OrderQuery): Order[];
}
interface OrderWriter {
  save(order: Order): void;
  delete(id: string): void;
}

class SqlOrderRepo implements OrderReader, OrderWriter {
  findById(id: string): Order | null { return null; }
  search(_: OrderQuery): Order[] { return []; }
  save(_: Order): void {}
  delete(_: string): void {}
}

// A reporting job asks for the Reader role only
class RevenueReport {
  constructor(private readonly orders: OrderReader) {}
  monthlyTotal(q: OrderQuery): number {
    return this.orders.search(q).reduce((s, o) => s + o.totalCents, 0);
  }
}

const repo = new SqlOrderRepo();
const report = new RevenueReport(repo); // narrowed to OrderReader
console.log(report.monthlyTotal({ month: "2026-07" }));
from typing import Optional, Protocol

# BEFORE - one fat interface
class OrderRepository(Protocol):
    def find_by_id(self, id: str) -> Optional[Order]: ...
    def search(self, query: OrderQuery) -> list[Order]: ...
    def save(self, order: Order) -> None: ...
    def delete(self, id: str) -> None: ...

# AFTER - segregated roles
class OrderReader(Protocol):
    def find_by_id(self, id: str) -> Optional[Order]: ...
    def search(self, query: OrderQuery) -> list[Order]: ...

class OrderWriter(Protocol):
    def save(self, order: Order) -> None: ...
    def delete(self, id: str) -> None: ...

class SqlOrderRepo:
    def find_by_id(self, id: str) -> Optional[Order]: return None
    def search(self, query: OrderQuery) -> list[Order]: return []
    def save(self, order: Order) -> None: ...
    def delete(self, id: str) -> None: ...

# Reporting job depends on the Reader role only
class RevenueReport:
    def __init__(self, orders: OrderReader) -> None:
        self._orders = orders

    def monthly_total(self, q: OrderQuery) -> int:
        return sum(o.total_cents for o in self._orders.search(q))

repo = SqlOrderRepo()
report = RevenueReport(repo)  # narrowed to OrderReader
print(report.monthly_total(OrderQuery(month="2026-07")))
# BEFORE - one fat module every client mixed in
module OrderRepository
  def find_by_id(id); end
  def search(query); end
  def save(order); end
  def delete(id); end
end

# AFTER - segregated roles
module OrderReader
  def find_by_id(id); raise NotImplementedError; end
  def search(query); raise NotImplementedError; end
end

module OrderWriter
  def save(order); raise NotImplementedError; end
  def delete(id); raise NotImplementedError; end
end

class SqlOrderRepo
  include OrderReader, OrderWriter
  def find_by_id(id) = nil
  def search(query) = []
  def save(order) = nil
  def delete(id) = nil
end

# Reporting job accepts anything that plays the reader role
class RevenueReport
  def initialize(orders)
    @orders = orders
  end

  def monthly_total(query)
    @orders.search(query).sum(&:total_cents)
  end
end

repo = SqlOrderRepo.new
report = RevenueReport.new(repo) # uses only OrderReader methods
puts report.monthly_total(OrderQuery.new(month: "2026-07"))

Concrete SqlOrderRepo अजूनही सर्व काही करते, पण consumers ना आता सर्व काही दिसत नाही. एक read replica फक्त OrderReader ची अंमलबजावणी करू शकते आणि ती write करू शकत नाही हे प्रामाणिकपणे जाहीर करू शकते, त्याने कधीही support न केलेल्या save मधून throw करण्याऐवजी.

ओळखा

Fat interface लक्षात घ्या

एकच PaymentGateway किंवा Repository सतत methods वाढवत जाते, आणि त्यातील कोणतीही बदलली की असंबंधित clients recompile होतात.

आराखडा

खरे clients यादी करा

प्रत्येक consumer ची गणना करा: checkout, support console, payouts job, reporting. प्रत्येकजण खरोखर कोणत्या methods call करतो ते नोंदवा.

20
समूह

Methods role नुसार गटांत करा

Clients एकत्र वापरणाऱ्या methods एक सुसंगत role बनवतात: charge, refund, payout, reader, writer. हे समूह तुमची interfaces बनतात.

30
काढा

प्रत्येक role साठी एक interface ठरवा

Charger, Refunder, Payout (किंवा OrderReader, OrderWriter) तयार करा, प्रत्येक फक्त त्याच्या समूहाचे वचन देतो.

40
अंमलबजावणी

Concrete class ला अनेक roles बजावू द्या

खरी StripeGateway ती support करणाऱ्या प्रत्येक role ची एकाच वेळी अंमलबजावणी करते, त्यामुळे वर्तन अपरिवर्तित आणि केंद्रित राहते.

50
अरुंद करा

प्रत्येक client त्याच्या role नुसार retype करा

Constructor आणि parameter types बदला: checkout Charger घेते, reporting OrderReader घेते. संपूर्ण नव्हे तर तुकड्यावर अवलंबून राहा.

Inject

Concrete एकदाच wire करा

Composition root ला, एकच StripeGateway प्रत्येक client मध्ये पाठवा. प्रत्येकाला त्याचा parameter जाहीर करणारा role तेवढाच दिसतो.

अंमलात आणा

Compiler ला गैरवापर मनाई करू द्या

Checkout आता refund call करू शकत नाही - ते Charger type वर नाही. बेकायदेशीर calls production मध्ये नव्हे तर build ला fail होतात.

Test

लहान role mock करा

Unit tests वीस-method gateway ऐवजी दोन-method Charger खोटी तयार करतात. Fixtures आकुंचित होतात आणि हेतू तीक्ष्ण होतो.

काढून टाका

Fat interface हटवा

एकदा सर्व clients roles वर अवलंबून झाले की, मूळ god interface आणि तिने classes ना खोट्या तयार करण्यास भाग पाडलेल्या कोणत्याही no-op stubs हटवा.

विकसित करा

एक role सुरक्षितपणे बदला

Payout मध्ये एक method जोडणे आता फक्त payout clients ना स्पर्श करते. फैलाव बदलाशी जुळतो - ISP साध्य झाले.

सामान्य अडचणी

अडचणी आणि anti-patterns

ISP उल्लंघने कोणते आकार घेतात हे एकदा कळले की ती सहज ओळखता येतात.

🗑️ God interface

findById, search, save, delete, export आणि audit असणारी Repository प्रत्येक client ला त्या सर्वांवर अवलंबून राहण्यास भाग पाडते. Type च्या नावाला काही अर्थच उरत नाही.

💥 throw new NotSupported

जेव्हा read replica एका fat writer interface ची अंमलबजावणी करते, तेव्हा save() runtime ला throw होते. ती throw होणारी stub म्हणजे interface त्या class साठी खूप विस्तृत होती याचा पुरावा.

📎 समीपतेमुळे coupling

charge आणि payout एकाच interface मध्ये बांधल्याने checkout ला payouts बदलल्यावर recompile करावे लागते, जरी checkout कोणालाही payout करत नसले तरी.

🪆 अति-विभागणी

प्रत्येक method साठी एक interface अशी विभागणी केल्याने single-method contracts चा थवा तयार होतो जो खरे roles झाकून टाकतो. Method संख्येनुसार नव्हे तर client गरजेनुसार विभागा.

🎭 Tests मध्ये fat mocks

जर एका unit test ला एकच गोष्ट exercise करण्यासाठी पंधरा methods stub कराव्या लागत असतील, तर कोड ज्यावर अवलंबून आहे ते interface खूप मोठे आहे. Test ची अडचण हाच design चा वास आहे.

🧟 गळके role naming

एका role interface ला IManager किंवा IService म्हणणे त्याचा हेतू लपवते. त्याला क्षमतेनुसार नाव द्या - Refunder, OrderReader - जेणेकरून callers ना काय मिळते ते दिसते.

संकेत आणि मापके

संकेत आणि कसे मोजावे

काही ठोस संकेतांकडे लक्ष देऊन तुम्ही fat interfaces ना त्रास होण्याआधी ओळखू शकता.

संकेततो तुम्हाला काय सांगतो
प्रति interface methodsएकाच contract वर सतत वाढणारी method संख्या सूचित करते की ती विभागल्या जाव्यात अशा अनेक roles शोषून घेत आहे.
प्रति client न वापरलेल्या methods चे प्रमाणजर बहुतेक clients interface च्या फक्त काही methods call करत असतील, तर interface कोणत्याही consumer च्या गरजेपेक्षा विस्तृत आहे.
NotImplemented / throw stubs"not supported" throw करणारी प्रत्येक method अशा client ला चिन्हांकित करते ज्याला तो न करू शकणाऱ्या गोष्टीवर अवलंबून राहण्यास भाग पाडले गेले.
Recompile फैलावInterface बदलल्यावर किती modules पुन्हा build होतात ते मोजा. असंबंधित बदलावर विस्तृत फैलाव खोटे coupling सूचित करतो.
Tests मध्ये mock चा आकारप्रति test मोठे हाताने लिहिलेले mocks किंवा अनेक stubbed methods उघड करतात की consumers वापरतात त्याहून जास्तवर अवलंबून आहेत.
Fan-in विरुद्ध method वापरअशा interface वर उच्च fan-in जिच्या methods वेगळ्या client गटांकडून वापरल्या जातात, हे segregation साठी पाठ्यपुस्तकातील उदाहरण आहे.
अंगठ्याचा नियम: जर कोणताही एकच client call करणाऱ्या methods चा संघ interface पेक्षा खूप लहान असेल, तर ती विभागा. योग्य आकाराचा contract तोच असतो जिथे प्रत्येक method त्यावर अवलंबून असणाऱ्या प्रत्येक client कडून पोहोचण्यायोग्य असते.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन production-सारख्या systems जिथे fat interface विभागल्याने फायदा झाला.

💳

1 · Payments gateway Charge, Refund, Payout मध्ये विभागलेला

Pattern: प्रति consumer role interfaces

एका marketplace ने checkout, एक support console आणि seller-payouts job एकाच PaymentGateway interface विरुद्ध चालवले. Payouts मधील कोणताही बदल checkout ला redeploy करण्यास भाग पाडायचा.

  • Fat interface ला Charger, Refunder आणि Payout role interfaces मध्ये विभागले गेले.
  • Concrete provider client तिन्हींची अंमलबजावणी करत राहिला; प्रत्येक service त्याच्या एकाच role नुसार retype केली गेली.
  • Checkout आता चुकूनही payout call करू शकत नव्हते, आणि payout बदल checkout builds मध्ये पसरणे थांबले.
✅ निष्कर्ष: प्रति क्षमता स्वतंत्र deploys आणि एक compiler जो checkout path ला कधीही payout करण्यापासून रोखतो.
🗄️

2 · CQRS repository Reader आणि Writer मध्ये विभागलेली

Pattern: read/write segregation

एका orders service ने वाचन replica ने आणि लेखन primary ने पाठबळ दिले, पण एकाच OrderRepository interface मुळे प्रत्येक query handler ला save आणि delete वाहावे लागत होते.

  • Interface ला OrderReader आणि OrderWriter मध्ये विभागले गेले.
  • Read handlers replica ने पाठबळ दिलेल्या OrderReader वर अवलंबून राहिले, जी प्रामाणिकपणे writer ची अंमलबजावणी करत नाही.
  • Command handlers OrderWriter वर अवलंबून राहिले, primary database कडे routed.
✅ निष्कर्ष: Read paths ना data भौतिकदृष्ट्या बदलताच येत नाही, आणि read-only replicas ना throw होणाऱ्या save stubs ची गरज उरली नाही.
📨

3 · Notification provider channel क्षमतेनुसार विभागलेला

Pattern: capability role interfaces

एका notifications platform कडे send, schedule, template render आणि delivery-receipt methods असणारे एकच NotificationChannel interface होते. SMS providers rich templates render करू शकत नव्हते, म्हणून ते throw करायचे.

  • Contract ला Sender, Schedulable आणि TemplateRenderer roles मध्ये विभागले गेले.
  • प्रत्येक provider ने फक्त तो खरोखर support करणाऱ्या roles ची अंमलबजावणी केली; SMS ने template rendering पूर्णपणे वगळले.
  • Callers क्षमतेनुसार channels मागत, त्यामुळे rich-template प्रवाहाने कधीही SMS-only provider निवडला नाही.
✅ निष्कर्ष: Runtime "not supported" चुका नाहीशा झाल्या कारण क्षमता send ला शोधण्याऐवजी type system मध्ये व्यक्त झाली.
07 - उपयुक्तता

आधुनिक उपयुक्तता

ISP हा classic OOP चा अवशेष नाही; आधुनिक typed आणि structural भाषा मोठ्या systems ना decoupled कशा ठेवतात याचा तो पाया आहे.

🦫 Go मधील लहान interfaces

Go ची संस्कृती ("accept interfaces, return structs") ही मूलतः ISP आहे: io.Reader आणि io.Writer सारखी छोटी interfaces जी client ला नेमकी गरज असेल तेव्हाच मागतो.

🧬 Structural आणि duck typing

Python Protocols आणि TypeScript structural types तुम्हाला client अवलंबून असणारा अरुंद role जाहीर करू देतात, त्यासाठी implementer ला interface अस्तित्वात आहे हेदेखील माहीत असण्याची गरज नाही.

🧭 CQRS आणि ports

Command/query separation आणि hexagonal ports हे संपूर्ण subsystems ना लागू केलेले ISP आहे: read ports आणि write ports वेगळे, किमान contracts म्हणून.

🔒 Capability-based security

एखाद्या component ला फक्त त्याला हवी असणारी अरुंद क्षमता देणे आणि त्याहून विस्तृत काहीही न देणे, हे केवळ design ची शोभा नव्हे तर सुरक्षा सीमा म्हणून ISP आहे.

🧩 API आणि RPC design

gRPC आणि GraphQL schemas ना केंद्रित service definitions चा फायदा होतो जेणेकरून clients एका monolithic service पृष्ठभागाला नव्हे तर ते call करणाऱ्या methods ना bind होतात.

🤖 Agents साठी tool interfaces

एखाद्या agent किंवा plugin ला एका task साठी लागणारी नेमकी tools तेवढीच उघड करणे हे ISP चे प्रतिबिंब आहे: प्रत्येक caller ला सर्वात लहान सक्षम contract द्या.

सारांश: ISP म्हणजे consumers भोवती contracts आकारण्याची शिस्त. प्रत्येक client ला त्याचे काम करू देणारे सर्वात लहान interface द्या, आणि coupling, test आकार आणि deploy फैलाव हे सर्व एकत्र आकुंचित होतात.
