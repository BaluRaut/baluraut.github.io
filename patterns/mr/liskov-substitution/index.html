Liskov Substitution Principle - जिथे base type अपेक्षित असेल तिथे विश्वासाने वापरता येणारे subtypes

Liskov Substitution Principle सांगते की base type वापरणारा कोणताही प्रोग्राम, त्याला कोणताही subtype दिला तरी बरोबर चालत राहिला पाहिजे, कोणत्याही खास तपासणीशिवाय आणि कोणत्याही आश्चर्याशिवाय. हे वचन तेव्हाच पाळले जाते जेव्हा subtype base contract चा मान राखतो: तो callers कडून जास्त मागणी करू शकत नाही, त्यांना जे सांगितले होते त्यापेक्षा कमी देऊ शकत नाही, आणि base type ने दिलेली हमी गुपचूप मोडू शकत नाही. जेव्हा subtype त्या contract शी बेईमानी करतो, तेव्हा polymorphic दिसणारा कोड production मध्ये फसू लागतो.

01 - काय

Liskov Substitution Principle म्हणजे काय?

LSP हे SOLID मधील "L" आहे. Barbara Liskov यांचे मूळ वाक्य असे आहे की जर S हा T चा subtype असेल, तर T प्रकारच्या objects च्या जागी S प्रकारचे objects वापरता आले पाहिजेत, प्रोग्रामच्या कोणत्याही इष्ट गुणधर्मांना बाधा न आणता. सोप्या शब्दांत: subtype ने आपल्या base type सारखे वागले पाहिजे, फक्त त्याचा आकार सारखा असून चालत नाही. Inheritance तुम्हाला method signatures फुकट देते; LSP म्हणजे त्या signatures ने दिलेल्या वर्तनाचा मान राखणे.

🔁 Substitutability

Base type साठी लिहिलेला कोणताही कोड, subtype दिला तरी चालत राहतो. Caller ला कधीही concrete class तपासण्याची गरज पडू नये.

📜 Behavioral subtyping

Interface फक्त inherit करणे किंवा implement करणे पुरेसे नाही. Subtype ने प्रत्येक method चा अर्थ पाळला पाहिजे, फक्त त्याचे parameters आणि return type जुळवून चालत नाही.

🤝 Contract, आकार नव्हे

प्रत्येक method सोबत एक contract असतो, तिला काय हवे आणि ती काय हमी देते याचा. Subtype त्याच contract ने बांधलेला असतो, अधिक कडक नाही आणि अधिक ढिला नाही.

02 - का

LSP महत्त्वाचे का आहे

LSP मुळेच polymorphism सुरक्षित होते. त्याशिवाय, प्रत्येक call site ला माहीत असावे लागते की त्याला कोणता concrete subtype मिळाला, आणि तुम्ही बांधलेली abstraction type checks च्या ढिगात कोसळते.

🧱 विश्वास ठेवता येणारा polymorphism

जेव्हा subtypes प्रामाणिक असतात, तेव्हा एका ओळीचा कोड प्रत्येक implementation साठी चालतो. Checkout प्रवाह कोणताही PaymentGateway स्वीकारू शकतो आणि vendor वरून कधीही branch करत नाही.

🚫 Defensive type checks नष्ट करते

if (repo instanceof ReadOnlyRepo) ने भरलेला कोड म्हणजे मोडलेल्या subtype चा वास. Contract चा मान राखा आणि त्या branches नाहीशा होतात.

🔌 सुरक्षित extension points

Callers ला हात न लावता नवीन subtypes जोडता येतात. हेच Open-Closed Principle चे संपूर्ण वचन आहे, आणि LSP मुळेच ते खरे राहते.

🐞 कमी runtime आश्चर्ये

उल्लंघने production incidents म्हणून उघड होतात: फेकणारे save, गुपचूप टाकून देणारे queue, वचन दिलेल्या मूल्याच्या जागी null. LSP हे design चूक shipping आधीच पकडते.

सोप्या शब्दांत

उपमांसह समजावलेले Liskov Substitution

एकच तत्त्व, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असलात तरी ते डोक्यात बसते.

🎓 विद्यार्थ्यासाठी

पर्यायी शिक्षकाला त्याच पाठ योजनेतून वर्ग चालवता आला पाहिजे. जर पर्यायी शिक्षक अर्धा अभ्यासक्रम शिकवायला नकार देत असेल किंवा नेहमीच्या शिक्षकाला कधीही न लागलेली परवानगी चिठ्ठी मागत असेल, तर विद्यार्थ्यांचे नुकसान होते. चांगला पर्याय योजनेच्या उद्देशासाठी ओळखता न येणारा असतो.

👩‍💻 डेव्हलपरसाठी

जर एखादे function Repository घेते आणि save() कॉल करते, तर तुम्ही देत असलेल्या प्रत्येक repository ने खरोखर save केले पाहिजे. save वर फेकणारे read-only repository व्यवस्थित compile होते पण runtime ला फुटते. ते interface मध्ये बसते पण contract मोडते.

🏢 व्यावसायिकासाठी

तुमचा मानक contract सही करणाऱ्या vendor ने त्याच्या अटी पूर्ण केल्या पाहिजेत. जर नवा पुरवठादार तोच करार पूर्ण करत असल्याचा दावा करत कमी order प्रकार स्वीकारत असेल किंवा अर्धवट pallets पाठवत असेल, तर कागदपत्रे जुळली तरी तुमचे कामकाज मोडते.

🔑 रोजच्या जीवनातली आवृत्ती

डुप्लिकेट किल्लीने तेच कुलूप उघडले पाहिजे जे मूळ किल्लीने उघडते. जी किल्ली भोकात बसते पण फक्त अर्धीच फिरते, किंवा आधी लपलेले बटण दाबल्याशिवाय अडकते, ती हुबेहूब दिसली तरी खरा पर्याय नाही.

03 - कसे

आत मध्ये हे कसे चालते

जिथे तुमच्याकडे खरा contract असलेला base type आणि एकापेक्षा जास्त implementation असतात, तिथे LSP लगेच समोर येते. उत्कृष्ट सापळा म्हणजे फक्त "is-a" चाचणीने modeling करणे: archived, read-only order repository इंग्रजीत "is a" repository आहे, म्हणून लोक writable ला extend करतात आणि save() ला फेकण्यासाठी override करतात. ते typecheck होते. ते LSP मोडते.

🧨 उल्लंघन

ReadOnlyOrderRepository हा writable base ला extend करतो आणि save() ला UnsupportedOperation फेकण्यासाठी override करतो. Base reference धरणारे callers save() कॉल करतात आणि crash होतात. Subtype ने precondition अधिक कडक करून "save कधीही कॉल करू नका" असे बनवले, जे कोणताही caller पाळू शकत नाही.

🛠️ उपाय

Contract विभागा. संकुचित ReadableOrders base फक्त reads चे वचन देतो; WritableOrders subtype save() जोडतो. Archive read-only आहे, म्हणून तो लिहिण्याचा दावा कधीही करत नाही, आणि कोणताही caller object ला न झेपणारी method कधीही कॉल करू शकत नाही.

// VIOLATION: an archive repo that "is a" repository but refuses to save.
class OrderRepository {
  save(order: Order): void { /* writes to the primary DB */ }
  findById(id: string): Order | null { /* ... */ return null; }
}

class ArchiveOrderRepository extends OrderRepository {
  // Strengthens the precondition to "never call me" - no caller can honor that.
  save(_order: Order): void {
    throw new Error("Archive is read-only");
  }
}

// A caller written against the base type has no way to know:
function reconcile(repo: OrderRepository, order: Order) {
  order.status = "reconciled";
  repo.save(order);            // 💥 blows up when repo is an archive
}

reconcile(new ArchiveOrderRepository(), someOrder); // runtime crash

खाली उपाय आहे: readable contract ला writable पासून वेगळे करा. आता archive फक्त तेच implement करतो जे तो पाळू शकतो, live repository दोन्ही implement करते, आणि reconcile नेमकी तीच capability मागते जी ती वापरते. प्रत्येक subtype तो जाहीर करत असलेल्या interface साठी पूर्णपणे substitutable असतो.

// FIX: split the contract so no subtype has to lie.
interface ReadableOrders {
  findById(id: string): Order | null;
}
interface WritableOrders extends ReadableOrders {
  save(order: Order): void;
}

class LiveOrderRepository implements WritableOrders {
  findById(id: string): Order | null { /* ... */ return null; }
  save(order: Order): void { /* writes to the primary DB */ }
}

class ArchiveOrderRepository implements ReadableOrders {
  findById(id: string): Order | null { /* reads cold storage */ return null; }
  // No save() - it never claims a capability it cannot deliver.
}

// The caller asks only for what it uses, so substitution is always safe:
function reconcile(repo: WritableOrders, order: Order) {
  order.status = "reconciled";
  repo.save(order);
}

const live = new LiveOrderRepository();
reconcile(live, someOrder);         // works for every WritableOrders
// reconcile(new ArchiveOrderRepository(), ...) // won't even compile

class ReadableOrders(ABC):

धडा: इंग्रजीतील "is-a" नाते तुम्हाला खोटे सांगत होते. Archive हा order store चा "एक प्रकार आहे", पण तो writable प्रकार नाही. Noun नव्हे तर capability चे modeling करणे, हेच प्रत्येक subtype ला substitutable बनवते आणि callers ला type checks पासून मुक्त ठेवते.

05 - टप्प्याटप्प्याने

0 -> 100 प्रवाह

डळमळीत "is-a" ओळखण्यापासून ते पूर्णपणे substitutable असणाऱ्या subtypes च्या संचापर्यंत, क्रमाने.

00
Model

Base type आणि त्याचे काम नावाने सांगा

Base type काय वचन देतो ते लिहा. OrderRepository वचन देतो "तुम्ही orders वाचू आणि save करू शकता." तेच वाक्य म्हणजे contract.

10
Contract

प्रत्येक method चे pre आणि postconditions सांगा

save(order) साठी: precondition म्हणजे वैध order; postcondition म्हणजे order टिकाऊपणे जतन केला जातो. वचन स्पष्ट करा.

20
Invariants

नेहमी खरी असणारी सत्ये यादी करा

एक invariant असू शकते "save केलेल्या order ला नेहमी id असतो." प्रत्येक subtype ने ते प्रत्येक कॉलच्या आधी आणि नंतर खरे ठेवले पाहिजे.

30
Subtype

एक उमेदवार subtype सुचवा

40
Check

Preconditions तपासा - त्या ढिल्या आहेत की समान?

Subtype ने callers कडून जास्त मागणी करू नये. जर archive ला वाचण्यासाठी खास flag लागत असेल, तर त्याने precondition अधिक कडक केली. धोक्याचा इशारा.

50
Check

Postconditions तपासा - त्या कडक आहेत की समान?

Subtype ने किमान वचन दिलेले तरी दिले पाहिजे. जर save() जतन करण्याऐवजी फेकत असेल, तर त्याने postcondition शून्यावर आणून ढिली केली.

60
Check

Invariants आणि history तपासा

Subtype कधीही base ला मान्य नसलेली state सोडत नाही आणि base ने प्रतिबंधित केलेले बदल होऊ देत नाही याची खात्री करा. Immutable ते immutable राहते.

70
Detect

उल्लंघन ओळखा

Archive save() पाळू शकत नाही. त्याला फेकायला भाग पाडणे म्हणजे उल्लंघन. "is-a" खरे तर "is a read-only kind of" होते.

80
Refactor

Capability नुसार contract विभागा

ReadableOrders आणि WritableOrders काढा. Archive फक्त तेच implement करतो जे तो पाळू शकतो; live repo दोन्ही implement करते.

90
Depend

Callers ला सर्वात संकुचित contract कडे वळवा

reconcile ला WritableOrders घेण्यासाठी पुन्हा लिहा. आता compiler save न करू शकणारा कोणताही subtype नाकारतो. Substitution ची हमी मिळते.

100
Verify

प्रत्येक subtype वर तेच tests चालवा

एक सामायिक contract test suite सर्व implementations वर चालतो. जर कोणताही subtype base-level test मध्ये अपयशी ठरला, तर तुम्हाला shipping आधीच LSP भंग सापडला.

सामान्य अडचणी

अडचणी आणि anti-patterns

बहुतेक LSP भंग तेव्हा होतात जेव्हा वर्तन खरेच जुळत नसताना कोड पुनर्वापरासाठी inherit केले जाते. हे नेहमीचे गुन्हेगार आहेत.

🚫 "not supported" फेकणे

Base method ला UnsupportedOperation फेकण्यासाठी override करणे हे सर्वात मोठ्याने ओरडणारे LSP उल्लंघन आहे. जर subtype ते करू शकत नसेल, तर त्याने ते करू शकतो हे वचन inherit करू नये.

🔒 Preconditions अधिक कडक करणे

Base ने स्वीकारलेले inputs नाकारणारा subtype, जसे currencies नाकारणारा region-locked PaymentGateway, विस्तृत contract वर अवलंबून असणाऱ्या callers ना मोडतो.

📉 Postconditions अधिक ढिली करणे

null परतणे, अर्धवट यादी देणे, किंवा वचन दिलेला side effect वगळणे यामुळे callers कडे base ने हमी दिलेल्यापेक्षा कमी उरते. मग गुपचूप data loss होतो.

🕵️ caller मध्ये instanceof

if (repo instanceof ArchiveRepo) skip() म्हणजे caller मोडलेल्या subtype ची भरपाई करत आहे. प्रत्येक type check हे लक्षण आहे, उपाय नाही.

🧊 Immutable base चा mutable subtype

Callers ज्याला गोठलेले मानत होते अशा value type ला setters जोडणे history constraint चे उल्लंघन करते आणि debug करायला अत्यंत त्रासदायक अशा प्रकारे सामायिक state भ्रष्ट करते.

🎣 भरगच्च base interface

एक अवाढव्य interface प्रत्येक subtype ला न झेपणाऱ्या methods implement करण्यास भाग पाडते. यामुळे teams stub-and-throw कडे ढकलली जातात, जो नेमका LSP सापळा आहे.

संकेत आणि मापदंड

संकेत आणि कसे मोजावे

तुम्ही LSP ला एका आकड्यात मांडू शकत नाही, पण हे संकेत तुम्हाला तुमचे subtypes प्रामाणिक आहेत की नाही हे विश्वासाने सांगतात.

संकेततो तुम्हाला काय सांगतो
NotSupported फेकणारे overridesLSP उल्लंघनांची थेट मोजणी - प्रत्येक एक म्हणजे आपल्या contract चा भाग नाकारणारा subtype
callers मधील instanceof / type-check घनताCalling कोड किती वेळा concrete subtypes ला खास वागवते, मोडलेल्या abstraction ची खूण

अंगठ्याचा नियम: जर एखादी method सुरक्षितपणे कॉल करण्यासाठी तुम्हाला कधी concrete class माहीत असणे गरजेचे असेल, तर तो subtype खरोखर substitutable नाही. एक contract test suite लिहा आणि तो प्रत्येक implementation वर चालवा; अपयशी ठरणारा पहिला subtype म्हणजे तुमचे उल्लंघन.
06 - केस स्टडीज

प्रत्यक्ष जगातील केस स्टडीज

Production-शैलीच्या तीन systems जिथे LSP ने design टिकेल की नाही हे ठरवले.

💳

1 · अनेक processors वरील payment gateway abstraction

Pattern: एका charge contract मागे प्रामाणिक subtypes

एक checkout system charge(amount, currency) contract असलेल्या एकाच PaymentGateway interface मागे अनेक processors मधून charges route करते.

  • एक processor फक्त देशांतर्गत currency ला support करत होता आणि बाकी सर्वांवर फेकत होता, precondition अधिक कडक करून आंतरराष्ट्रीय checkout crash करत होता.
  • उपायाने supported currencies ला capability metadata म्हणून जाहीर केले आणि त्यानुसार route केले, म्हणून प्रत्येक gateway ने त्याला मिळालेल्या traffic साठी पूर्ण contract पाळला.
  • एका सामायिक contract test ने तेच charge, refund, आणि idempotency प्रकरणे प्रत्येक processor adapter वर चालवली.
✅ निकाल: Checkout ने processor-विशिष्ट exceptions पकडण्याऐवजी capability वर branch केले, आणि नवीन processor जोडण्यासाठी caller मध्ये बदल लागणे थांबले.
🗄️

2 · read-only archive असलेला repository layer

Pattern: read आणि write contracts विभागा

एक orders service अलीकडचे orders primary database मध्ये आणि जुने read-only archive मध्ये ठेवत होती, दोन्ही एकाच repository interface मागे.

  • Archive repository ने save() inherit केले आणि फेकले, म्हणून background reconciliation jobs जेव्हा जेव्हा archived order ला स्पर्श करत तेव्हा अपयशी ठरत.
  • ReadableOrders आणि WritableOrders मध्ये विभागल्याने archive ला फक्त reads implement करता आले, आणि compiler ने कोणताही write path तिथपर्यंत पोहोचण्यापासून रोखला.
  • Callers ना ते प्रत्यक्षात वापरत असलेल्या सर्वात संकुचित interface वर अवलंबून राहण्यासाठी पुन्हा लिहिले गेले.
✅ निकाल: "archived order save करता येत नाही" या प्रकारच्या runtime errors पूर्णपणे नाहीशा झाल्या, आणि write jobs compile वेळी सिद्धपणे सुरक्षित झाल्या.
📨

3 · एका delivery interface मागे notification senders

Pattern: सर्व channels वर एकसमान postconditions

एक platform delivery receipt चे वचन देणाऱ्या send(message) contract असलेल्या सामायिक NotificationSender मधून email, SMS, आणि push पाठवत होती.

  • Device token नसताना push sender receipt शिवाय लवकर परतत होता, postcondition ढिली करून audit logs अपूर्ण ठेवत होता.
  • Contract असा कडक केला की प्रत्येक sender स्पष्ट delivered किंवा failed निकाल परततो, कधीही गुपचूप no-op नाही.
  • एका सामायिक suite ने तिन्ही channels साठी postcondition, म्हणजे receipt नेहमी परतला जातो, याची खात्री केली.
✅ निकाल: Downstream retry आणि audit logic प्रत्येक channel साठी सारखीच चालली, कारण प्रत्येक sender ने base type ने वचन दिलेली नेमकी हमी दिली.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

LSP आजच्या भाषांच्या आधीचे आहे, पण त्याची मूळ कल्पना, behavioral substitutability, systems जसजशी interfaces आणि plugins वर अवलंबून राहत आहेत तसतशी पूर्वीपेक्षा अधिक प्रासंगिक आहे.

🧩 Interface segregation चे भागीदार

भरगच्च interfaces ला role-आधारित मध्ये विभागणे हा LSP समाधानी करण्याचा बहुधा सर्वात स्वच्छ मार्ग आहे. दोन्ही SOLID तत्त्वे एकमेकांना थेट बळकटी देतात.

🔗 Plugin आणि adapter ecosystems

प्रत्येक plugin API म्हणजे एक LSP contract. Interface अर्धवट implement करणारा plugin host मोडतो, म्हणून प्रामाणिक subtyping हा platform च्या टिकाव धरण्याचा गुण आहे.

🦆 Structural आणि duck typing

TypeScript structural types आणि Python protocols मध्ये, compiler आकार तपासतो पण वर्तन नाही. LSP ही ती शिस्त आहे जी ती दरी हाताने भरून काढते.

🧪 Contract आणि property-based tests

प्रत्येक implementation वर एक सामायिक suite चालवणे, किंवा postconditions तपासण्यासाठी inputs निर्माण करणे, LSP ला तत्त्वापासून automated gate मध्ये बदलते.

🏗️ Inheritance पेक्षा composition

आधुनिक designs वर्तन compose करण्याला पसंती देतात, जे subtype पाठवू न शकणारे "is-a" कधीही दावा न करता अनेक LSP सापळे टाळते.

🤖 Typed API आणि RPC schemas

Versioned service contracts म्हणजे network सीमेवरचे LSP: नवी server आवृत्ती जुन्यासाठी बांधलेल्या clients साठी substitutable राहिली पाहिजे.

सारांश: LSP हा तो नियम आहे जो polymorphism विश्वासार्ह ठेवतो. Subtypes ला बरोबर वाटणाऱ्या noun भोवती नव्हे तर ते खरोखर पाळू शकणाऱ्या वर्तनाभोवती design करा, आणि तुमच्या abstractions स्वच्छ राहतील, तुमचे callers type checks पासून मुक्त राहतील, आणि तुमचे extensions सुरक्षित राहतील.
