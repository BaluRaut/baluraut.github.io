Errors as Objects - type system मध्ये अपयशाचे मॉडेलिंग

अयशस्वी payment ही एखादी string नसते किंवा भटकलेली -1 नसते. ती एक अशी गोष्ट असते जिला नाव, कारण आणि context असतो: कोणते कार्ड, किती रक्कम, बँकेने का नकार दिला. जेव्हा तुम्ही errors ला जादुई मूल्यांऐवजी first-class objects बनवता, तेव्हा अपयश ही अशी गोष्ट बनते जिच्याबद्दल compiler आणि तुमचे handlers विचार करू शकतात, तिला मार्गी लावू शकतात आणि तिच्यातून सावरू शकतात.

01 - काय

"errors as objects" म्हणजे काय?

object-oriented भाषांमध्ये exception हा काही खास primitive नसतो: तो एका class चा सामान्य object असतो, ज्याला तुम्ही subclass करू शकता, विस्तारू शकता आणि समृद्ध करू शकता. "errors as objects" ही अशी शिस्त आहे जिथे प्रत्येक वेगळ्या अपयशाला त्याचा स्वतःचा type म्हणून नाव दिले जाते, त्याला fields दिली जातात जी काय चुकले याची तथ्ये वाहतात, आणि callers ना message parse करण्याऐवजी किंवा numeric code तपासण्याऐवजी type वर जुळवण्याची मुभा दिली जाते.

🏷️ एक नामकरण केलेला type

PaymentDeclined ही एक class आहे, string नाही. Handlers तिला नावाने catch करतात, त्यामुळे "declined" आणि "network timeout" वेगवेगळ्या शाखांमध्ये जातात, string matching शिवाय.

🎒 context वाहते

object मध्ये रक्कम, currency, card fingerprint, आणि decline code असतो. catch करणाऱ्या जागी संरचित data मिळतो, तिला उलटा शोधावा लागणारे वाक्य नाही.

🌳 एका hierarchy चा भाग

InsufficientFunds हे PaymentDeclined ला विस्तारते, जे मूळ PaymentError ला विस्तारते. संपूर्ण कुटुंब हाताळण्यासाठी base catch करा, किंवा एका नेमक्या प्रकरणासाठी leaf.

02 - का

errors ला objects म्हणून का मॉडेल करावे

खऱ्या systems मध्ये अपयश हे नंतरचा विचार नसते - एक payments service आपली बहुतांश edge cases पैसे न हलण्याचे मार्ग हाताळण्यातच घालवते. त्या cases ना स्पष्ट types बनवल्याने "काही throw होणार नाही अशी आशा" चे रूपांतर code अंमलात आणणाऱ्या checklist मध्ये होते.

🎯 नेमके हाताळणे

InsufficientFunds catch केल्याने "निधी घाला" असे सुचवता येते, तर CardExpired "कार्ड अद्यतनित करा" सुचवते. एकच सामान्य catch यांच्यात फरक करू शकत नाही, त्यामुळे तो दोन्हीसाठी चुकीचे करतो.

📦 context अपयशासोबत प्रवास करते

decline code, retry करण्याची शक्यता, आणि gateway reference हे सर्व object च्या आत stack च्या शेवटपर्यंत सोबत जातात. कोणताही global lookup नाही, मूळ जागेला आधीच माहीत असलेली तथ्ये पुन्हा काढणे नाही.

🧭 type system अपयशाचे दस्तऐवजीकरण करते

एक Result<Receipt, PaymentError> return type प्रत्येक caller ला, compile time ला, सांगते की हा call अयशस्वी होऊ शकतो आणि नेमके कसे. अपयश रात्री 3 वाजता येणारे आश्चर्य राहत नाही.

🧱 callers न तोडता विस्तारते

PaymentDeclined खाली FraudSuspected जोडा आणि base catch करणारे जुने handlers अजूनही चालतात. नवीन handlers तयार असताना बारीक प्रकरणात सामील होतात.

सोप्या शब्दांत

उपमांसह errors as objects समजावून

तीच कल्पना, कल्पना करण्याचे चार मार्ग, त्यामुळे तुम्ही कोणीही असाल तरी ती डोक्यात बसते.

🎓 विद्यार्थ्यासाठी

फक्त "चूक" असे सांगणारी तपासलेली परीक्षा तुम्हाला काहीच शिकवत नाही. "चूक: प्रश्न 4 मध्ये तुम्ही गुणाकाराऐवजी भागाकार केला" असे सांगणारी परीक्षा तुम्हाला नेमके काय दुरुस्त करायचे ते सांगते. error object हा दुसऱ्या प्रकारचा अभिप्राय आहे.

👩‍💻 डेव्हलपरसाठी

false return करणारे function आणि typed failure value return करणारे function यांतील हा फरक आहे. एक तुम्हाला अंदाज लावायला भाग पाडते; दुसरे तुम्हाला अशी class देते जी तुम्ही नावाने catch करू शकता आणि जिच्यातून fields वाचू शकता.

🏢 व्यावसायिकासाठी

नाकारलेल्या व्यवहाराच्या पावतीवर फक्त "नाही" नव्हे तर reason code, रक्कम, आणि व्यापारी यांची यादी असते. बँक अपयशाला संरचित नोंद म्हणून encode करते, जेणेकरून पुढील systems योग्य कृती करतील. ती पावती म्हणजे error object.

📮 रोजच्या जीवनातली आवृत्ती

"असा पत्ता नाही" असा शिक्का मारलेले परत आलेले पत्र विरुद्ध "स्थलांतरित, forwarding संपले" असा शिक्का असलेले पत्र. दोन्ही पोहोचली नाहीत, पण लिफाफ्यावरील कारण तुमची पुढील हालचाल ठरवते. तो शिक्का म्हणजे typed error.

03 - कसे

ते कसे बांधावे

तुम्ही दोन गोष्टी करता: एका domain base मध्ये मूळ असलेली error classes ची hierarchy परिभाषित करता, आणि प्रत्येक operation साठी ठरवता की त्यांना raise करायचे (खरोखर अपवादात्मक, स्थानिक नसलेल्या अपयशांसाठी) की Result म्हणून return करायचे (अपेक्षित, business-level परिणामांसाठी जे callers ना inline हाताळावे लागतात).

🌳 hierarchy ची रचना करा

एक base PaymentError जेणेकरून कोणताही handler संपूर्ण domain catch करू शकेल. InsufficientFunds आणि CardExpired सारख्या leaf classes त्यांच्या प्रकरणाला विशिष्ट fields जोडतात. जेव्हा तुम्ही पहिल्यांदा त्यावर routing करता तेव्हा खोली स्वतःचा मोबदला देते.

🔀 raise विरुद्ध return

caller सहसा येथे सावरू शकत नसेल आणि ते वर पोहोचावे असे इच्छित असेल (gateway बंद पडणे) तेव्हा raise करा. जेव्हा अपयश हे एक सामान्य business परिणाम असते जिथे तात्काळ caller ला शाखा करावी लागते (नाकारलेले कार्ड) तेव्हा Result return करा.

// A domain error is a real class: named, typed, context-carrying.
class PaymentError extends Error {
  constructor(
    message: string,
    readonly amount: number,
    readonly currency: string,
  ) {
    super(message);
    this.name = new.target.name; // keeps the leaf class name
  }
}

class InsufficientFunds extends PaymentError {
  constructor(amount: number, currency: string, readonly shortfall: number) {
    super(`Short by ${shortfall} ${currency}`, amount, currency);
  }
}

class CardExpired extends PaymentError {
  constructor(amount: number, currency: string, readonly expiry: string) {
    super(`Card expired ${expiry}`, amount, currency);
  }
}

class PaymentGateway {
  charge(cardBalance: number, expiry: string, amount: number): string {
    if (expiry < "2026-07") throw new CardExpired(amount, "USD", expiry);
    if (cardBalance < amount)
      throw new InsufficientFunds(amount, "USD", amount - cardBalance);
    return `receipt_${Date.now()}`; // charge succeeded
  }
}

// Handle by TYPE, not by parsing a message.
const gateway = new PaymentGateway();
try {
  const receipt = gateway.charge(40, "2027-01", 99.5);
  console.log("Charged:", receipt);
} catch (err) {
  if (err instanceof InsufficientFunds) {
    console.log(`Ask for ${err.shortfall} ${err.currency} more`);
  } else if (err instanceof CardExpired) {
    console.log(`Prompt to update card (was ${err.expiry})`);
  } else if (err instanceof PaymentError) {
    console.log("Generic payment failure:", err.message);
  } else {
    throw err; // not ours - let it bubble
  }
}
# A domain error is a real class: named, typed, context-carrying.
class PaymentError(Exception):
    def __init__(self, message: str, amount: float, currency: str):
        super().__init__(message)
        self.amount = amount
        self.currency = currency


class InsufficientFunds(PaymentError):
    def __init__(self, amount: float, currency: str, shortfall: float):
        super().__init__(f"Short by {shortfall} {currency}", amount, currency)
        self.shortfall = shortfall


class CardExpired(PaymentError):
    def __init__(self, amount: float, currency: str, expiry: str):

            raise CardExpired(amount, "USD", expiry)
        if card_balance < amount:

class PaymentError < StandardError
  attr_reader :amount, :currency

  def initialize(message, amount:, currency:)
    super(message)
    @amount = amount
    @currency = currency
  end
end

class InsufficientFunds < PaymentError
  attr_reader :shortfall

  def initialize(amount:, currency:, shortfall:)
    super("Short by #{shortfall} #{currency}", amount: amount, currency: currency)
    @shortfall = shortfall
  end
end

class CardExpired < PaymentError
  attr_reader :expiry

  def initialize(amount:, currency:, expiry:)
    super("Card expired #{expiry}", amount: amount, currency: currency)
    @expiry = expiry
  end
end

class PaymentGateway

लक्षात घ्या की प्रत्येक rescue / catch शाखा एका class शी जुळते आणि मग fields वाचते. base PaymentError शाखा ही तुम्ही अजून न लिहिलेल्या भविष्यातील leaf types साठी सुरक्षा जाळे आहे, आणि परकी काहीही पुन्हा raise केल्याने असंबंधित bugs मोठ्याने वाजत राहतात.

अपयश नित्याचे असते तेव्हा: raise करण्याऐवजी Result return करा

// Result makes the failure visible in the signature - callers cannot forget it.
type Ok<T> = { ok: true; value: T };
type Err<E> = { ok: false; error: E };
type Result<T, E> = Ok<T> | Err<E>;

function authorize(balance: number, amount: number): Result<string, PaymentError> {
  if (balance < amount)
    return { ok: false, error: new InsufficientFunds(amount, "USD", amount - balance) };
  return { ok: true, value: `auth_${amount}` };
}

const res = authorize(40, 99.5);
if (res.ok) {
  console.log("Authorized:", res.value);
} else {
  console.log("Declined:", res.error.message); // typed error, no throw
}
# Result makes the failure visible in the signature - callers cannot forget it.
from dataclasses import dataclass
from typing import Generic, TypeVar, Union

T = TypeVar("T")
E = TypeVar("E")


@dataclass
class Ok(Generic[T]):
    value: T


@dataclass
class Err(Generic[E]):
    error: E


Result = Union[Ok[T], Err[E]]


def authorize(balance: float, amount: float) -> Result[str, PaymentError]:
    if balance < amount:
        return Err(InsufficientFunds(amount, "USD", amount - balance))
    return Ok(f"auth_{amount}")


res = authorize(40, 99.5)
if isinstance(res, Ok):
    print("Authorized:", res.value)
else:
    print("Declined:", res.error)  # typed error, no raise
# Result makes the failure visible in the return value - callers must branch on it.
Ok  = Struct.new(:value)
Err = Struct.new(:error)

def authorize(balance:, amount:)
  if balance < amount
    return Err.new(InsufficientFunds.new(amount: amount, currency: "USD", shortfall: amount - balance))
  end
  Ok.new("auth_#{amount}")
end

res = authorize(balance: 40, amount: 99.5)
case res
when Ok  then puts "Authorized: #{res.value}"
when Err then puts "Declined: #{res.error.message}" # typed error, no raise
end

त्याच error classes, वेगळी पोहोचवण्याची पद्धत. खोल call chain रद्द करावी अशा अपयशांना raise करणे शोभते; Result return करणे अशा अपेक्षित परिणामांना शोभते जिथे तात्काळ caller ला मूल्य स्पर्श करण्याआधी सामोरे जावे लागते. error object दोन्ही बाबतीत एकसारखाच असतो - फक्त त्याची वाहतूक बदलते.

charge function false return करते किंवा उघडी string throw करते. Callers कारणाचा अंदाज लावतात, आणि प्रत्येक नवीन decline प्रकरण आणखी एक ठिसूळ if message.includes(...) जोडते.

10
Base

एक domain base class तयार करा

भाषेच्या exception type ला विस्तारणारे PaymentError परिभाषित करा. प्रत्येक payment अपयश त्यातून उतरेल जेणेकरून एकच handler संपूर्ण कुटुंब catch करू शकेल.

20
Fields

base ला सामाईक context द्या

base ला amount, currency, आणि एक retryable flag जोडा जेणेकरून प्रत्येक payment अपयश शेअर करणारा context नेमक्या एकाच ठिकाणी राहील.

30
Leaves

प्रत्येक वेगळ्या अपयशाला नाव द्या

InsufficientFunds, CardExpired, GatewayUnavailable मध्ये subclass करा. प्रत्येक आपल्या प्रकरणाला विशिष्ट fields वाहते, जसे shortfall किंवा statusCode.

40
Raise

मूळ जागी नेमका type throw करा

अट सापडताच gateway नेमकी leaf class बांधते आणि raise करते, आपल्या हाताशी आधीच असलेली तथ्ये टिपून घेते.

50
Propagate

त्याला अबाधित वर जाऊ द्या

मधले स्तर त्याला गिळत नाहीत किंवा पुन्हा गुंडाळत नाहीत. object त्याचा type आणि context अबाधित ठेवून वर प्रवास करतो, जोपर्यंत निर्णय घेऊ शकणारा एखादा स्तर त्याला catch करत नाही.

60
Catch

message ने नव्हे तर class ने हाताळा

सीमा InsufficientFunds विरुद्ध CardExpired वर जुळते आणि त्यांची fields वाचते, प्रत्येकाला अनुरूप वापरकर्ता प्रतिसाद देते.

70
जाळे

base-class सुरक्षा शाखा ठेवा

अंतिम catch PaymentError तुम्ही अजून खास न हाताळलेली कोणतीही leaf हाताळते, जेणेकरून नवीन error types कच्चे बाहेर पडण्याऐवजी सौम्यपणे मार्गी लागतात.

80
निवडा

प्रत्येक call साठी raise विरुद्ध Result ठरवा

callers ना सामोरे जावे लागणाऱ्या अपेक्षित business परिणामांसाठी, Result<Receipt, PaymentError> return करा जेणेकरून अपयश signature मध्ये दिसेल.

90
Log

वाक्य नव्हे तर object serialize करा

एक toLog() method संरचित fields (code, amount, gatewayRef) उत्सर्जित करते जेणेकरून dashboards अपयशाच्या प्रकारांवर नेमकेपणे गट करू शकतील आणि alert देऊ शकतील.

100
विकसित

callers न तोडता नवीन अपयशे जोडा

PaymentDeclined खाली FraudSuspected आणा. जुने base-class handlers अजूनही चालतात; नवीन handlers तयार असताना बारीक प्रकरणात सामील होतात.

सामान्य अडचणी

अडचणी आणि anti-patterns

errors चांगल्या प्रकारे मॉडेल करणे सूक्ष्मपणे चुकणे सोपे आहे. या वारंवार होणाऱ्या चुका आहेत.

🕳️ सर्व काही गिळणे

log करून पुढे जाणारा एक उघडा catch (e) {} किंवा rescue => e हा InsufficientFunds ला खऱ्या NullPointer शेजारी लपवतो. तुम्ही खरोखर हाताळू शकाल तो सर्वात संकुचित type catch करा.

🧵 stringly-typed कारणे

if err.message.includes("declined") वर शाखा करणे कोणीतरी message ची शब्दरचना बदलताच किंवा त्याचे स्थानिकीकरण करताच तुटते. class वर जुळवा, कधीही गद्यावर नाही.

🥞 एक अवाढव्य error class

type string field असलेली एकच AppError ही वेषातील enum च आहे. तुम्ही instanceof routing आणि प्रत्येक प्रकरणाची fields गमावता. खऱ्या subclasses ला प्राधान्य द्या.

📭 rethrow वर context काढून टाकणे

समृद्ध error catch करून new Error("payment failed") पुन्हा throw केल्याने decline code आणि कारण मिटते. cause सह गुंडाळा, कधीही string मध्ये सपाट करू नका.

🚦 control flow साठी exceptions

एका सामान्य, अपेक्षित परिणामाचे (रिकामी cart) संकेत देण्यासाठी throw करणे हे stack-unwinding यंत्रणेचा गैरवापर आहे. raise करणे खऱ्या अपवादात्मक गोष्टींसाठी राखून ठेवा; अन्यथा Result return करा.

🌊 अति-खोल hierarchies

कोणीही स्वतंत्रपणे कधीही catch न करणाऱ्या abstract error classes चे दहा स्तर हे स्पष्टता नव्हे तर औपचारिकता आहे. एखादा handler त्यावर शाखा करेल तेव्हाच subclass जोडा.

संकेत आणि मापके

संकेत आणि कसे मोजावे

तुमचे error model आपले वजन पेलत आहे की नाही हे code मध्ये आणि production telemetry मध्ये दिसते.

संकेततो तुम्हाला काय सांगतो
typed catches चे bare catches शी गुणोत्तरउच्च typed गुणोत्तर म्हणजे handlers विशिष्ट अपयशांवर कृती करतात; अनेक bare catches म्हणजे अपयशाचा तपशील फेकून दिला जात आहे.
error messages वर string matchingcontrol flow मधील कोणतेही message.includes(...) हे संकेत आहे की अपयश एक वेगळा type असायला हवा होता.
log dashboards मध्ये उपस्थित error typesतुम्ही class नाव आणि field ने घटनांचे गट करू शकत असाल, तर तुमचे errors पुरेशी संरचना वाहतात. सर्व काही फक्त "Error" असेल, तर ते वाहत नाहीत.
कारण गमावणारे rethrowscause जपून न ठेवता गुंडाळल्याने stack traces तुटतात आणि on-call debugging दरम्यान मूळ कारणे लपतात.
callers ना स्पर्श न करता जोडलेले नवीन अपयशनवीन leaf type विद्यमान base खाली बसते आणि जुने handlers अजूनही compile होतात व वागतात, तर तुमची hierarchy चांगली रचलेली आहे.
अयशस्वी होऊ शकणाऱ्या signatures मध्ये Result typesज्यांच्या signatures अपयश मान्य करतात असे अयशस्वी होणारे operations callers ना ते हाताळायला भाग पाडतात; लपलेले throws callers ना विसरू देतात.
ढोबळ नियम: catch block वाचणारा माणूस throw करणारे function उघडल्याशिवाय काय अयशस्वी झाले हे सांगू शकत नसेल, तर error हा एक समृद्ध object असायला हवा होता. अपयशाला नाव द्या, त्याचा context वाहा, आणि त्याच्या type वर routing करा.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन production systems जिथे errors-as-objects हे भार पेलणारे आहे.

💳

1 · Stripe-शैलीतील payment API error taxonomy

Pattern: context वाहणारे typed decline codes

एका payments platform ने integrators ना charge नेमके का अयशस्वी झाले हे सांगावेच लागते जेणेकरून त्यांची apps योग्य प्रतिक्रिया देतील, फक्त "ते चालले नाही" नव्हे.

  • एक CardError base card_declined, expired_card, insufficient_funds मध्ये विभागतो, प्रत्येकाला machine वाचता येणारा decline_code असतो.
  • प्रत्येक error object request id, रक्कम, आणि retry यशस्वी होण्याची शक्यता वाहतो.
  • प्रत्येक भाषेतील SDKs हीच taxonomy native exception classes म्हणून समोर आणतात, ज्या callers type ने catch करतात.
✅ परिणाम: Integrators नेमके recovery flows (retry विरुद्ध prompt विरुद्ध सोडून देणे) लिहितात कारण अपयश अस्पष्ट status ऐवजी संरचित, typed data म्हणून येते.
✅

2 · अनेक typed errors return करणारे form validation

Pattern: throwing ऐवजी एकत्रित error objects

एका signup service ने पहिल्या चुकीच्या input वर लगेच अयशस्वी न होता प्रत्येक अवैध field एकाच वेळी नोंदवावे लागते.

  • प्रत्येक नियम एक ValidationError subclass (Required, TooShort, NotUnique) देतो, ज्यात दोषी field आणि एक स्थिर code असतो.
  • validator error objects ची यादी धारण करणारे Result return करते, त्यामुळे सामान्य चुकीच्या input साठी काहीही raise होत नाही.
  • API स्तर प्रत्येक error चे field आणि code एका JSON प्रतिसादात serialize करते, जो front end inline messages मध्ये मॅप करते.
✅ परिणाम: वापरकर्ते त्यांच्या सर्व चुका एकाच फेरीत पाहतात, आणि front end इंग्रजी वाक्ये parse करण्याऐवजी स्थिर codes वरून messages render करते.
🦀

3 · Rust आणि Go ने संपूर्ण उद्योगाला Result कडे वळवले

Pattern: return type मध्ये encode केलेले अपयश

दोन मुख्य प्रवाहातील भाषांनी अपयशक्षमतेला लपलेला दुय्यम मार्ग नव्हे तर signature चा भाग जाणीवपूर्वक बनवले.

  • Rust चे Result<T, E> आणि Go चे स्पष्ट error return प्रत्येक caller ला call site वर अपयशाला सामोरे जाण्यास भाग पाडतात.
  • Custom error enums आणि types context वाहतात आणि callers ना विशिष्ट variant वर जुळू देतात.
  • या pattern ने TypeScript, Kotlin, आणि Swift परिसंस्थांना अपेक्षित अपयशांसाठी typed-result libraries कडे ढकलले.
✅ परिणाम: कमी विसरलेले अपयश-मार्ग आणि अधिक स्पष्ट APIs, कारण "हे अयशस्वी होऊ शकते, आणि ते असे" हे documentation किंवा नशिबावर न सोडता type मध्ये लिहिलेले असते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

type systems आणि distributed systems परिपक्व होत असताना अपयशाला first-class data म्हणून वागवणे अधिकाधिक केंद्रस्थानी येत आहे.

🧬 typed results मुख्य प्रवाहात येत आहेत

TypeScript, Kotlin, आणि Swift हे Result-शैलीतील types पुरवतात किंवा लोकप्रिय करतात, ज्यामुळे अपेक्षित अपयश हे लपलेल्या throw ऐवजी signatures चा दृश्य भाग बनते.

🔗 cause chain असलेले errors

native cause समर्थन (JavaScript, Python चे raise from) एका error object ला खालच्या object ला गुंडाळू देते, मूळापासून सीमेपर्यंतची संपूर्ण कहाणी जपून ठेवते.

🌐 services मध्ये संरचित errors

gRPC status details आणि HTTP साठी Problem Details (RFC 9457) typed, field-समृद्ध errors network वर वाहतात, object model एका process च्या पलीकडे विस्तारतात.

🔭 error types वर आधारित observability

Tracing tools error class आणि attributes वर गट करतात व alert देतात. समृद्ध error objects incident triage ला log grepping ऐवजी एका query मध्ये बदलतात.

🛡️ exhaustiveness checking

Union-typed errors compiler ला तुम्ही प्रत्येक प्रकरण हाताळले हे सिद्ध करू देतात, त्यामुळे नवीन failure variant जोडल्याने जुळवून घ्यावी लागणारी प्रत्येक जागा समोर येते.

🤖 machine ने कृती करता येणारी अपयशे

Agents आणि automated retries ना अशी अपयशे हवी असतात ज्यांवर ते programmatically शाखा करू शकतील. typed object वरील retryable flag हा message वाचण्यापेक्षा चांगला असतो.

सारांश: अपयश हा प्रत्येक खऱ्या system चा सामान्य भाग असतो, म्हणून त्याला तसेच मॉडेल करा. प्रत्येक वेगळ्या अपयशाला नाव द्या, त्याला तथ्ये वाहू द्या, त्याला hierarchy मध्ये ठेवा, आणि त्याला raise करायचे की return करायचे हे जाणीवपूर्वक निवडा. Errors as objects "काहीतरी बिघडले" चे रूपांतर अशा गोष्टीत करतात जिच्याबद्दल तुमचा code, आणि तुमची टीम, खरोखर विचार करू शकते.
