Inheritance - is-a चे मॉडेलिंग आणि वर्तनाचा सुरक्षित पुनर्वापर

Inheritance मुळे एक class दुसऱ्या class ला extend करू शकते, जेणेकरून एक subtype हे base type च्या डेटा आणि वर्तनाचा पुनर्वापर करते आणि त्याला विशेष रूप देते. योग्य वापरल्यास ते खरे is-a नाते टिपते, जसे की एक ईमेल notification हे एक notification आहे. निष्काळजीपणे वापरल्यास ते classes ना एकत्र जोडून टाकते आणि fragile base class चा सापळा तयार करते.

01 - काय

Inheritance म्हणजे काय?

Inheritance ही अशी यंत्रणा आहे जिथे एक subclass हे एका base class पासून तयार होते आणि आपोआप त्याचे fields व methods मिळवते. Subclass नवीन वर्तन जोडू शकते, वारसाहक्काने मिळालेल्याचा पुनर्वापर करू शकते, किंवा methods override करून त्यांना विशेष रूप देऊ शकते. डिझाइनची कसोटी म्हणजे is-a हा प्रश्न: एक SMS notification हे एक notification आहे, एक पगारी कर्मचारी हा एक कर्मचारी आहे. जर हे वाक्य चुकीचे वाटत असेल, तर inheritance हे चुकीचे साधन आहे.

🧬 Base class

सामायिक contract आणि state धारण करते, जसे की recipient, retry policy, आणि प्रत्येक channel साठी समान असणारी delivery routine असलेले एक Notification.

📨 Subclass

Base ला extend करून त्याला विशेष रूप देते, जसे की retry आणि logging लॉजिकचा पुनर्वापर करत EmailNotification मध्ये subject आणि HTML body जोडणे.

🔁 Override + super

एक subclass base method ला स्वतःच्या आवृत्तीने बदलते, आणि त्याचाच भाग म्हणून base implementation चालवण्यासाठी super ला कॉल करू शकते.

मुख्य मानसिक प्रतिमा: inheritance म्हणजे कोड शेअर करण्यासाठी कोड शेअर करणे नव्हे, ते subtyping आहे. एक subclass हे असे वचन आहे की जिथे base अपेक्षित आहे तिथे त्याची instances वापरता येतील. जर एखादी subtype हे वचन मोडते, तर तुमच्याकडे सुरक्षिततेशिवाय coupling असते, जे fragile base class समस्येचे बीज आहे.
02 - का

Inheritance का अस्तित्वात आहे

जेव्हा types चे एक कुटुंब खरोखर एक contract आणि वर्तनाचा मोठा भाग सामायिक करते, तेव्हा inheritance आपली जागा मिळवते. ते डुप्लिकेशन काढून टाकते, hierarchy थेट व्यक्त करते, आणि सामायिक लॉजिक बदलण्यासाठी एकच जागा देते.

♻️ copy-paste शिवाय पुनर्वापर

Retry, logging, आणि validation base मध्ये एकदाच राहतात. प्रत्येक channel subtype त्यांचा वारसा घेते, ईमेल, SMS आणि push senders मध्ये नाजूक boilerplate डुप्लिकेट करण्याऐवजी.

🗂️ खरी hierarchy मॉडेल करते

जेव्हा डोमेनमध्ये खरोखरच एक is-a वृक्ष असतो, जसे की payroll मधील कर्मचाऱ्यांचे प्रकार, तेव्हा class आलेख व्यवसायाच्या भाषेचे प्रतिबिंब दाखवतो आणि नवागतांना स्पष्ट वाचता येतो.

🎯 polymorphism सक्षम करते

Base type स्वीकारणारा कोड कोणत्याही subclass सोबत चालतो. एक dispatcher notifications वर लूप करते आणि ठोस channel न जाणता send() कॉल करते.

🧩 extend करण्यासाठी एकच जागा

नवीन channel जोडणे म्हणजे एक नवीन subclass, switch statement मध्ये विखुरलेले बदल नव्हे. Base contract तुम्हाला नेमके काय अंमलात आणायचे ते सांगतो.

सोप्या शब्दांत

उपमांसह Inheritance समजावून

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती पटकन उमजते.

🎓 विद्यार्थ्यासाठी

Inheritance म्हणजे फरकांसह एक मूळ पाककृती. मुख्य कणीक एकदाच लिहिली जाते; sourdough आणि focaccia आवृत्त्या त्या पायऱ्यांचा वारसा घेतात आणि फक्त त्यांना वेगळे करणारे तेवढेच बदलतात.

👩‍💻 डेव्हलपरसाठी

हे extends अधिक override आहे. एक PaymentGateway base charge() ठरवते; StripeGateway retry loop चा पुनर्वापर करते आणि फक्त provider-विशिष्ट कॉल override करते, सामायिक भागांसाठी super ला बोलावते.

🏢 व्यावसायिकासाठी

विभागीय पुरवण्यांसह कंपनी धोरण असे समजा. प्रत्येक टीम कॉर्पोरेट हँडबुकचा वारसा घेते; प्रत्येक विभाग काही कलमे override करतो. स्पष्टपणे विशेष केल्याशिवाय मूळ नियम लागू राहतात.

🏛️ रोजच्या जीवनातील आवृत्ती

कायदेशीर पूर्वदाखला: एक सामान्य कायदा सर्वांना लागू होतो, आणि एक विशिष्ट निकाल एका प्रकरणासाठी त्यात सुधारणा करतो. विशिष्ट निकाल तरीही खालील सामान्य कायद्यावर अवलंबून असतो.

03 - कसे

Inheritance आतून कसे काम करते

एक subclass जाहीर करते की ते एका base ला extend करते, base members मिळवते, आणि methods override करू शकते. कॉलच्या वेळी runtime ऑब्जेक्टचा खरा प्रकार वापरून method निवडते, आणि super मुळे एक override ला base आवृत्तीचा पुनर्वापर करता येतो.

🧬 Subclassing आणि constructors

Subclass constructor प्रथम base constructor (super(...)) ला कॉल करते जेणेकरून वारसाहक्काने मिळालेली state सुरू होते, नंतर स्वतःची fields सेट करते. तो कॉल वगळला तर वारसाहक्काने मिळालेल्या invariants कधीच प्रस्थापित होत नाहीत.

🔒 Protected members

Protected चिन्हांकित केलेली fields subclasses ना पोहोचता येतात पण बाहेरील callers पासून लपलेली असतात, त्यामुळे subtypes अंतर्गत state ला public API म्हणून उघड न करता त्यावर बांधकाम करू शकतात.

// Base class: shared delivery contract for every channel
abstract class Notification {
  protected retries = 3;

  constructor(protected recipient: string) {}

  // Subclasses MUST specialize how the body is rendered
  abstract formatBody(): string;

  protected log(msg: string): void {
    console.log(`[notify] ${msg}`);
  }

  // Template behavior reused by all subtypes
  send(): boolean {
    const body = this.formatBody();
    for (let attempt = 1; attempt <= this.retries; attempt++) {
      this.log(`attempt ${attempt} -> ${this.recipient}`);
      if (this.transmit(body)) return true;
    }
    return false;
  }

  protected transmit(_body: string): boolean {
    return true; // pretend the carrier accepted it
  }
}

class EmailNotification extends Notification {
  constructor(recipient: string, private subject: string) {
    super(recipient); // initialize inherited state first
  }

  formatBody(): string {
    return `Subject: ${this.subject}\n<html>Hello</html>`;
  }
}

class SmsNotification extends Notification {
  constructor(recipient: string, private senderId: string) {
    super(recipient);
    this.retries = 2; // SMS carriers are stricter, override default
  }

  formatBody(): string {
    return `From ${this.senderId}: your code is 4821`;
  }

  // Override that reuses the base via super
  send(): boolean {
    this.log("checking SMS opt-in");
    return super.send();
  }
}

const outbox: Notification[] = [
  new EmailNotification("ana@shop.io", "Order shipped"),
  new SmsNotification("+15550100", "SHOPIO"),
];

for (const n of outbox) {
  n.send(); // dynamic dispatch picks the right formatBody + send
}
from abc import ABC, abstractmethod

class Notification(ABC):
    """Base class: shared delivery contract for every channel."""

    def __init__(self, recipient: str) -> None:
        self._recipient = recipient   # protected by convention
        self._retries = 3

    @abstractmethod
    def format_body(self) -> str:
        ...

    def _log(self, msg: str) -> None:
        print(f"[notify] {msg}")

    def _transmit(self, body: str) -> bool:
        return True  # pretend the carrier accepted it

    def send(self) -> bool:
        body = self.format_body()
        for attempt in range(1, self._retries + 1):
            self._log(f"attempt {attempt} -> {self._recipient}")
            if self._transmit(body):
                return True
        return False


class EmailNotification(Notification):
    def __init__(self, recipient: str, subject: str) -> None:
        super().__init__(recipient)   # initialize inherited state
        self._subject = subject

    def format_body(self) -> str:
        return f"Subject: {self._subject}\n<html>Hello</html>"


class SmsNotification(Notification):
    def __init__(self, recipient: str, sender_id: str) -> None:
        super().__init__(recipient)
        self._sender_id = sender_id
        self._retries = 2             # override the default

    def format_body(self) -> str:
        return f"From {self._sender_id}: your code is 4821"

    def send(self) -> bool:           # override that reuses super
        self._log("checking SMS opt-in")
        return super().send()

# Base class: shared delivery contract for every channel
class Notification
  def initialize(recipient)
    @recipient = recipient   # instance vars are protected by design
    @retries = 3
  end

  # Subclasses must specialize this
  def format_body
    raise NotImplementedError, "subclass must implement format_body"
  end

  def send
    body = format_body
    (1..@retries).each do |attempt|
      log("attempt #{attempt} -> #{@recipient}")
      return true if transmit(body)
    end
    false
  end

  protected

  def log(msg)
    puts "[notify] #{msg}"
  end

  def transmit(_body)
    true # pretend the carrier accepted it
  end
end

class EmailNotification < Notification
  def initialize(recipient, subject)
    super(recipient)   # initialize inherited state first
    @subject = subject
  end

  def format_body
    "Subject: #{@subject}\n<html>Hello</html>"
  end
end

class SmsNotification < Notification
  def initialize(recipient, sender_id)
    super(recipient)
    @sender_id = sender_id
    @retries = 2       # override the default
  end

  def format_body
    "From #{@sender_id}: your code is 4821"
  end

  def send             # override that reuses super
    log("checking SMS opt-in")
    super
  end
end

outbox = [
  EmailNotification.new("ana@shop.io", "Order shipped"),
  SmsNotification.new("+15550100", "SHOPIO")
]

outbox.each(&:send) # dynamic dispatch picks the right format_body + send

तिन्ही snippets एक base contract ठरवतात, दोन subclasses जोडतात, आणि सामायिक send routine मधून जाणारे खरे objects तयार करतात. लक्षात घ्या की SmsNotification हे send override करते पण तरीही super ला कॉल करते, त्यामुळे ते retry loop पुन्हा अंमलात न आणता एक opt-in तपासणी जोडते.

धोके आणि anti-patterns

जेव्हा inheritance खऱ्या subtype नात्यासाठी न वापरता पुनर्वापरासाठी वापरले जाते, तेव्हा ते सर्वात मोठ्याने अपयशी ठरते. हे नेहमीचे गुन्हेगार आहेत.

🏚️ Fragile base class

Base मधील निरुपद्रवी दिसणारा बदल, जसे की अंतर्गत कॉल्सचा क्रम बदलणे, जुन्या प्रवाहावर अवलंबून असणाऱ्या subclasses ना शांतपणे मोडतो. वृक्ष जितका खोल, तितका स्फोटाचा परीघ मोठा.

🧱 फक्त पुनर्वापरासाठी वारसा

फक्त methods उसन्या घेण्यासाठी ArrayList ला subclass करणे, जेव्हा तुमचा type खरोखर list नसतो, तेव्हा तुम्ही पाळू न शकणारा API सोबत ओढून आणते. जर ते is-a नसेल, तर composition वापरा.

🚫 substitution मोडणे

जिथे base परत करते तिथे throw करणारे, किंवा स्वीकारलेले inputs अरुंद करणारे एक override हे base contract चे उल्लंघन करते. Base reference धरणाऱ्या callers ना runtime वेळी आश्चर्य वाटते.

🕳️ खोल hierarchies

पाच पातळ्यांचे extends म्हणजे वर्तन संपूर्ण साखळीवर पसरलेले असते. एक method समजण्यासाठी संपूर्ण वंशावळ वाचावी लागते, आणि प्रत्येक बदल खाली लाटा उठवतो.

🔓 गळणारी protected state

खूप जास्त protected fields उघड केल्याने internals एका अनधिकृत API मध्ये बदलतात. Subclasses त्यांच्यावर घट्ट पकड घेतात, आणि तुम्ही यापुढे base मुक्तपणे refactor करू शकत नाही.

🧨 constructors मध्ये overridable methods कॉल करणे

Subclass ने आपली fields सुरू करण्यापूर्वी base constructor एक overridden method कॉल करते, त्यामुळे override अर्धवट-बांधलेल्या state विरुद्ध चालते आणि गैरवर्तन करते.

संकेत आणि मेट्रिक्स

संकेत आणि कसे मोजायचे

निरोगी inheritance उथळ राहते, आपल्या contracts चा आदर करते, आणि क्वचितच base बदल भाग पाडते. ऱ्हास लवकर पकडण्यासाठी या संकेतांवर लक्ष ठेवा.

संकेततो काय सांगतो
Hierarchy खोलीदोन किंवा तीन पातळ्यांपेक्षा खोल साखळ्या सहसा असे दर्शवतात की वर्तनाचा माग काढणे कठीण आहे आणि flattening किंवा composition साठी हा उमेदवार आहे.
Base बदलाच्या लाटाBase बदलल्यावर किती subclasses मोडतात. जास्त लाटा म्हणजे आकड्यांत मांडलेली fragile base class समस्या.
Override बंधनएका subclass ने अंमलात आणायच्या abstract methods ची संख्या. खूप जास्त असल्यास base coupling चे समर्थन करण्यासाठी फारच कमी करत आहे.
Liskov उल्लंघनेBase वर पास होणाऱ्या पण subclass वर अपयशी ठरणाऱ्या tests हे दर्शवतात की एक subtype खरोखर substitutable नाही.
Protected पृष्ठभागाचा आकारमोठा protected member संच म्हणजे subclasses internals वर अवलंबून असतात, ज्यामुळे refactor करण्याचे तुमचे स्वातंत्र्य आकुंचन पावते.
super-call गुणोत्तरsuper ला कधीच कॉल न करणारी overrides extend करण्याऐवजी बदलत असतील, जे base abstraction चुकीचे असल्याचे सूचित करते.
ठोकताळा: जर base class मधील बदल नियमितपणे subclasses मध्ये बदल भाग पाडतो किंवा tests मोडतो, तर hierarchy नाजूक आहे. उथळ वृक्ष, लहान protected पृष्ठभाग, आणि नाते is-a ऐवजी has-a असेल तेव्हा composition ला प्राधान्य द्या.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तीन प्रातिनिधिक प्रणाली जिथे inheritance एक खरी type hierarchy मॉडेल करते.

💳

1 · Payment gateway adapters

Pattern: base charge प्रवाह, provider-विशिष्ट overrides

एक checkout service अनेक payment providers एकत्र करते जे एक lifecycle सामायिक करतात पण प्रत्यक्ष API कॉलमध्ये भिन्न असतात.

  • एक PaymentGateway base validation, idempotency keys, आणि retry loop यांचा मालक असतो.
  • StripeGateway आणि AdyenGateway फक्त provider request override करतात, सामायिक हाताळणीसाठी super कॉल करतात.
  • Order service base type ला प्रोग्राम करते, त्यामुळे एक provider जोडणे म्हणजे एक नवीन subclass.
✅ परिणाम: नवीन processors checkout ला हात न लावता शिप होतात, आणि सामायिक सुरक्षा लॉजिक नेमके एकाच ठिकाणी राहते.
🧾

2 · Payroll employee types

Pattern: pay गणनेसाठी is-a hierarchy

एक payroll engine पगारी, तासिक, आणि commission कर्मचाऱ्यांसाठी pay मोजते जे identity आणि tax हाताळणी सामायिक करतात.

  • एक Employee base tax withholding आणि pay-stub formatting धारण करतो.
  • SalariedEmployee, HourlyEmployee, आणि CommissionEmployee हे calculateGrossPay() override करतात.
  • Run loop प्रत्येक कामगाराला एक Employee म्हणून वागवते आणि कधीच type वर branch करत नाही.
✅ परिणाम: एक नवीन कामगार वर्गीकरण जोडणे म्हणजे एक subclass आणि pay run अस्पर्शित व अचूक राहतो.
🖼️

3 · UI component frameworks

Pattern: base widget, विशेष controls

एक component toolkit controls ला एक hierarchy म्हणून मॉडेल करते जिथे प्रत्येक widget layout आणि event plumbing सामायिक करते.

  • एक base View किंवा Component measure, layout, आणि render lifecycle हाताळते.
  • Buttons, text fields, आणि lists हे त्याला extend करतात आणि render व event hooks override करतात.
  • Framework base references चा एक वृक्ष चालवते आणि सर्व काही सामायिक lifecycle मधून चालवते.
✅ परिणाम: Widget लेखक संपूर्ण lifecycle चा पुनर्वापर करतात आणि फक्त त्यांच्या control ला खरोखर विशिष्ट असणारे तेवढेच अंमलात आणतात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Inheritance हा सुरुवातीच्या OOP मध्ये होता तसा default हातोडा राहिलेला नाही, पण तो खऱ्या is-a hierarchies आणि शिस्तबद्ध framework डिझाइनसाठी योग्य साधन राहतो.

🧩 आधी composition

आधुनिक मार्गदर्शन पुनर्वापरासाठी composition ला अनुकूल करते आणि inheritance खऱ्या subtyping साठी राखून ठेवते. दोन्ही एका निरोगी codebase मध्ये आहेत, वेगवेगळ्या कामांसाठी वापरले जातात.

🧭 खोल वृक्षांपेक्षा interfaces

Teams state न ओढता contracts सामायिक करण्यासाठी interfaces आणि लहान traits वर विसंबतात, ज्यामुळे hierarchies उथळ आणि लवचिक राहतात.

🏛️ Frameworks अजूनही यावर विसंबतात

UI toolkits, ORMs, आणि test frameworks तुम्ही extend करता अशी base classes उघड करतात. Inheritance lifecycles साठी ergonomic विस्तार बिंदू राहतो.

🔐 sealed आणि final

भाषा sealed आणि final जोडतात जेणेकरून लेखक hierarchies ला मर्यादित करू शकतील, कोण extend करू शकते हे नियंत्रित करून fragile base class समस्या आटोक्यात आणतात.

📐 रक्षक म्हणून Liskov

Substitution तत्त्व हे एक subclass प्रामाणिक आहे की नाही याची कसोटी आहे. ते inheritance ला केवळ सोयीस्कर न ठेवता सुरक्षित ठेवते.

🧬 Mixins आणि traits

Ruby modules आणि तत्सम यंत्रणा single-inheritance मर्यादांशिवाय लक्ष्यित वर्तन सामायिकरण देतात, पुनर्वापराला स्वच्छ contracts सोबत मिसळतात.

सारांश: inheritance कडे तेव्हाच वळा जेव्हा एक subtype खरोखर एक base type is-a असते आणि त्याचा contract सामायिक करते. वृक्ष उथळ ठेवा, substitution चा आदर करा, आणि साध्या पुनर्वापरासाठी composition ला प्राधान्य द्या. तसे केल्यास, inheritance एक coupling सापळ्याऐवजी एक अचूक मॉडेलिंग साधन राहते.
