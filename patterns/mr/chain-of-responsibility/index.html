Behavioral Pattern

Chain of Responsibility - कोणीतरी हाताळेपर्यंत विनंती पुढे पाठवणे

काही विनंत्या एका ठराविक, ज्ञात ऑब्जेक्टच्या मालकीच्या नसतात. Chain of Responsibility तुम्हाला हँडलर एकमेकांना जोडून विनंती रांगेत पुढे पाठवण्याची मुभा देते, जोपर्यंत त्यांच्यापैकी कोणीतरी ती हाताळत नाही. sender ला कधीच कळत नाही की कोणत्या हँडलरने उत्तर दिले, आणि caller ला हात न लावता तुम्ही दुवे जोडू, त्यांचा क्रम बदलू किंवा काढून टाकू शकता.

01 - काय

Chain of Responsibility म्हणजे काय?

Chain of Responsibility हा एक behavioral pattern आहे जो विनंतीला स्वतंत्र ऑब्जेक्टमध्ये रूपांतरित करतो आणि संभाव्य हँडलरच्या साखळीतून पुढे पाठवतो. प्रत्येक हँडलर दोनपैकी एक गोष्ट ठरवतो: विनंती स्वतः हाताळायची, किंवा साखळीतील पुढच्या हँडलरकडे सोपवायची. विनंती सुरू करणाऱ्या client ला कोणता हँडलर ती हाताळेल हे माहीत नसते किंवा त्याची पर्वाही नसते.

🧩 Handler interface

प्रत्येक दुवा अंमलात आणतो असा एक समान करार, सहसा handle(request) मेथड आणि पुढच्या हँडलरचा संदर्भ.

🔗 साखळी

क्रमाने जोडलेले concrete हँडलर. प्रत्येक जण एकतर विनंती पूर्ण करतो किंवा शेवट येईपर्यंत आपल्या उत्तराधिकाऱ्याकडे सोपवतो.

📨 Client

साखळी एकदाच बांधतो, मग पहिल्या दुव्याकडे विनंत्या पाठवतो. शेवटी कोण उत्तर देते याबद्दल तो अनभिज्ञच राहतो.

02 - का

Chain of Responsibility का अस्तित्वात आहे

याशिवाय, विनंती हाताळणी एका प्रचंड conditional मध्ये कोसळते: एक पसरलेला if / else if जो प्रत्येक संभाव्य हँडलर ठराविक क्रमाने ओळखतो आणि caller ला जोडलेला असतो. तो ब्लॉक वाढवणे कठीण, स्वच्छपणे क्रम बदलणे अशक्य, आणि प्रत्येक वेळी नवीन केस आली की open/closed तत्त्वाचे उल्लंघन करतो.

🔓 Sender ला receiver पासून वेगळे करते

caller हँडलरचे नाव न घेता विनंती सुरू करतो. हँडलर बदलू शकतात, वाढू शकतात किंवा नाहीसे होऊ शकतात आणि caller ला कधीच त्याची जाणीव होत नाही.

🧱 विस्तारासाठी खुले

एक दुवा घालून नवीन बाब जोडा. अस्तित्वातील हँडलर आणि client तसेच राहतात, त्यामुळे तपासलेल्या कोडला संपादित न करता तुम्ही वर्तन वाढवता.

🔄 क्रम हे कॉन्फिगरेशन बनते

दुवे runtime ला जोडले जात असल्याने, तुम्ही branching लॉजिक पुन्हा लिहिण्याऐवजी साखळी बांधण्याची पद्धत बदलून पायऱ्यांचा क्रम बदलता किंवा त्यांची अदलाबदल करता.

🎯 प्रत्येक दुव्याला एकच जबाबदारी

प्रत्येक हँडलर नेमके एकच काम करतो आणि फक्त स्वतःचा नियम अन् त्याचा उत्तराधिकारी जाणतो, ज्यामुळे प्रत्येक class लहान आणि testable राहतो.

सोप्या भाषेत

उपमांसह Chain of Responsibility ची उकल

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती पटकन कळेल.

🎓 विद्यार्थ्यासाठी

हे प्रश्न वरच्या स्तरावर नेण्यासारखे आहे. तुम्ही ट्यूटरला विचारता; त्यांना उत्तर देता आले नाही तर ते तुम्हाला व्याख्यात्याकडे पाठवतात; त्यांना जमले नाही तर तो प्राध्यापकाकडे जातो. तुम्ही फक्त एकदाच विचारता, आणि ज्याला उत्तर देता येईल तो उत्तर देतो.

👩‍💻 डेव्हलपरसाठी

ही एक middleware pipeline आहे. एक विनंती येते, प्रत्येक middleware एकतर उत्तर देते किंवा next() ला कॉल करते, आणि जोपर्यंत काहीतरी response लिहीत नाही किंवा विनंती पूर्ण होत नाही तोपर्यंत नियंत्रण रांगेत पुढे वाहत जाते.

🏢 व्यावसायिकासाठी

एका खर्च मंजुरी प्रवाहाचा विचार करा. मॅनेजर एका मर्यादेपर्यंत मंजूर करतो; त्याहून अधिक असेल तर विनंती डायरेक्टरकडे, मग finance कडे वर जाते. दावा दाखल करणाऱ्याला कोण मंजुरी देतो हे माहीत असण्याची गरज नसते.

🎧 रोजच्या जीवनातील रूप

एक सपोर्ट हॉटलाइन. Tier 1 आधी प्रयत्न करतो; समस्या त्यांच्या आवाक्याबाहेर असेल तर ते तुम्हाला tier 2 कडे, मग एका तज्ज्ञाकडे वळवतात. तुम्ही एकच नंबर फिरवता आणि कॉल योग्य व्यक्तीपर्यंत पोहोचतो.

03 - कसे

आतमध्ये हे कसे कार्य करते

प्रत्येक हँडलर एक समान interface अंमलात आणतो आणि पुढच्या हँडलरचा संदर्भ धरून ठेवतो. जेव्हा विनंती येते, तेव्हा हँडलर ती पूर्ण करायची की सोपवायची हे ठरवतो. दुवे एकत्र जोडल्याने साखळी बनते; सुरुवातीच्या दुव्याकडे विनंती पाठवल्याने ती सुरू होते.

🔗 हँडलर जोडणे

प्रत्येक concrete हँडलर एक next संदर्भ साठवतो. setNext() सारखा एक मदतनीस तो पुढचा हँडलर परत करतो, जेणेकरून तुम्ही साखळी सुबक, वाचनीय क्रमाने जोडू शकता.

🚦 हाताळा किंवा पुढे पाठवा

handle() च्या आत, हँडलर एक अट तपासतो. ती जुळली तर तो कृती करतो आणि साखळी थांबवू शकतो; नाहीतर तो उत्तराधिकाऱ्याला कॉल करतो, किंवा तो शेवटचा दुवा असेल तर काहीच करत नाही.

TypeScript मधील एक वास्तववादी अंमलबजावणी

interface Request {
  user?: string;
  role?: string;
  body: string;
}

abstract class Handler {
  private next?: Handler;

  setNext(handler: Handler): Handler {
    this.next = handler;
    return handler; // enables fluent wiring
  }

  // Default: pass the request along the chain.
  handle(req: Request): void {
    if (this.next) this.next.handle(req);
  }
}

class AuthHandler extends Handler {
  handle(req: Request): void {
    if (!req.user) throw new Error("401 Unauthorized");
    super.handle(req); // authenticated, keep going
  }
}

class RoleHandler extends Handler {
  handle(req: Request): void {
    if (req.role !== "admin") throw new Error("403 Forbidden");
    super.handle(req);
  }
}

class ValidationHandler extends Handler {
  handle(req: Request): void {
    if (req.body.trim() === "") throw new Error("400 Empty body");
    super.handle(req); // reached the end, request is served
  }
}

// Wire the chain once, then just fire requests at the head.
const chain = new AuthHandler();
chain.setNext(new RoleHandler()).setNext(new ValidationHandler());

chain.handle({ user: "ada", role: "admin", body: "ship it" });

लक्षात घ्या की AuthHandler ला validation बद्दल काहीच माहीत नाही, आणि caller ला दोन्हींपैकी कशाबद्दलही माहीत नाही. प्रत्येक दुवा एका नियमाचा मालक आहे आणि एकतर विनंती पुढे नेतो किंवा थांबवतो, आणि नेमके हेच साखळीला लवचिक ठेवते.

30

उत्तराधिकारी साठवणारा आणि डीफॉल्टपणे पुढे पाठवणारा एक abstract base द्या, जेणेकरून concrete हँडलर फक्त त्यांचे स्वतःचे वेगळे लॉजिक लिहितील.

निर्भयपणे घाला किंवा क्रम बदला

नवीन बाब? एक दुवा जोडा. वेगळा प्राधान्यक्रम? पुन्हा जोडा. client आणि अस्तित्वातील हँडलर कधीच बदलत नाहीत, त्यामुळे रचनेचा फायदा मिळत राहतो.

नेहमीचे धोके

धोके आणि anti-pattern

पॅटर्न सोपा आहे, पण साखळी निष्काळजीपणे बांधली किंवा तिच्याबद्दल विचार केला की तो अंदाज करता येण्याजोग्या मार्गांनी अपयशी ठरतो.

🕳️ शांतपणे खाली पडणे

कोणताही हँडलर पूर्ण न करणारी विनंती शेवटातून घसरून नाहीशी होते. जर विनंती हाताळणे आवश्यक असेल, तर न हाताळलेली विनंती हा एक दोष आहे, म्हणून शेवटच्या दुव्याला throw किंवा log करायला लावा.

🔁 तुटलेले पुढे-पाठवणे

एक हँडलर आपल्या उत्तराधिकाऱ्याला कॉल करायला विसरतो, त्यामुळे त्यानंतरचे दुवे कधीच चालत नाहीत. एक हरवलेला super.handle() शांतपणे अर्धी साखळी मारून टाकतो.

🧭 लपलेले क्रम-अवलंबित्व

दुसऱ्या दुव्याच्या आधी किंवा नंतर चालण्यावर गुप्तपणे अवलंबून असणारे हँडलर साखळीला नाजूक बनवतात. मग क्रम बदलल्याने वर्तन अस्पष्ट मार्गांनी तुटते.

🌀 मागोवा घेत debugging

caller ला receiver माहीत नसल्याने, अनेक दुव्यांतून विनंतीचा पाठलाग करणे कठीण असते. लांब, गतिशील साखळ्यांबद्दल विचार करणे अवघड होते.

🧨 अति-अभियांत्रिकी

कधीच न बदलणाऱ्या दोन-तीन केसच्या ठराविक संचासाठी, साखळी अशी औपचारिकता जोडते जी एक साधा switch अधिक स्पष्टपणे हाताळेल.

🪢 गुबगुबीत हँडलर

एका दुव्यात अनेक असंबंधित नियम कोंबल्याने मूळ हेतूच फोल ठरतो. प्रत्येक हँडलरकडे एकच निर्णय असावा, नाहीतर साखळी लवचिक राहात नाही.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Chain of Responsibility थोड्याशा अप्रत्यक्षतेच्या बदल्यात भरपूर लवचिकता देते. हँडलरचा संच किंवा त्यांचा क्रम बदलण्याची अपेक्षा असेल तेव्हा त्याकडे वळा.

पैलूतपशील
फायदेsender ला receiver पासून वेगळे करते, प्रत्येक दुव्याला एकच जबाबदारी, client किंवा इतर हँडलरना संपादित न करता हँडलर जोडा किंवा क्रम बदला.
तोटेविनंती न हाताळता राहू शकते, नियंत्रण प्रवाहाचा मागोवा घेणे कठीण, आणि लांब गतिशील साखळ्या कामगिरी अन् वाचनीयतेला हानी पोहोचवू शकतात.
केव्हा वापरावेअनेक ऑब्जेक्ट एक विनंती हाताळू शकतात, हँडलर आधीच माहीत नसतो, किंवा हँडलरचा संच आणि क्रम runtime ला कॉन्फिगर करता येण्याजोगा असावा.
केव्हा टाळावेनेमका एकच ज्ञात ऑब्जेक्ट नेहमी विनंती हाताळतो, किंवा केसेस थोड्या आणि ठराविक असतात, जिथे एक साधा conditional अधिक स्पष्ट असतो.
गुंतागुंतकमी संरचनात्मक खर्च, एक interface अन् लहान हँडलर, पण जोडलेली runtime अप्रत्यक्षता जिचा तुम्हाला मागोवा घेता आला पाहिजे.
संबंधितCommand (विनंत्या ऑब्जेक्ट म्हणून), Decorator (हीदेखील एक गुंडाळणारी साखळी), Mediator (साखळणीऐवजी केंद्रीकरण करते), Observer (सर्वांना प्रसारित करते).
अंगठ्याचा नियम: "हे कोण हाताळतो?" या प्रश्नाचे उत्तर "ते अवलंबून असते, आणि यादी बदलत राहते" असे असेल, तर साखळी वापरा. जर ते "नेहमी हाच एक ऑब्जेक्ट" असेल, तर वापरू नका, फक्त थेट कॉल करा. आणि विनंती खाली पडू शकते की तिला हाताळणे आवश्यक आहे हे नेहमी स्पष्टपणे ठरवा.
06 - केस स्टडी

प्रत्यक्ष जगातील केस स्टडी

production सिस्टीममध्ये पॅटर्न खरे काम करत असल्याचे दाखवणारे तीन प्रातिनिधिक उपयोग.

🌐

1 · HTTP middleware pipeline

पॅटर्न: विनंतीवर प्रक्रिया व्हायलाच हवी, response परत गुंडाळतो

Express, ASP.NET Core, आणि Java servlet filter सारखे web framework विनंतीच्या जीवनचक्राचे मॉडेल middleware च्या साखळीरूपात करतात.

  • प्रत्येक middleware, logging, CORS, auth, compression, एकतर उत्तर देते किंवा पुढे जाण्यासाठी next() ला कॉल करते.
  • क्रम हे कॉन्फिगरेशन आहे: authentication route handler च्या आधी चालते, compression नंतर response ला गुंडाळते.
  • एक middleware लगेच 401 परत करून साखळी थांबवू शकते, जेणेकरून खालचे दुवे कधीच चालत नाहीत.
✅ निष्कर्ष: प्रत्येक route मध्ये गुंतागुंतीचे न बनता, cross-cutting बाबी लहान, पुनर्क्रमबद्ध करता येण्याजोग्या, स्वतंत्रपणे testable दुव्यांमध्ये राहतात.
🪵

2 · Logging framework चे स्तर

पॅटर्न: विनंती खाली पडू शकते, सर्वोत्तम जुळणी जिंकते

java.util.logging आणि log4j मधील logger severity स्तरानुसार parent logger अन् हँडलरच्या साखळीतून चालतात.

  • एक log record पदानुक्रमात वरच्या प्रत्येक logger ला दिला जातो, जोपर्यंत एखादा तो उत्सर्जित करण्यासाठी कॉन्फिगर केलेला असतो.
  • Level चे उंबरठे ठरवतात की एक दुवा record हाताळतो की मूळाकडे पुढे पाठवतो.
  • प्रत्येक उंबरठ्याखालचा record सरळ खाली पडतो आणि टाकून दिला जातो, जे इथे अपेक्षित वर्तन आहे.
✅ निष्कर्ष: कॉल साइटवरील कोडमध्ये कोणताही बदल न करता, साखळी पुन्हा कॉन्फिगर करून टीम प्रत्येक component ची शब्दबहुलता समायोजित करतात.
💳

3 · मंजुरी आणि validation workflow

पॅटर्न: एखादा अधिकारी निर्णय घेऊ शकेपर्यंत वर न्या

खर्च मंजुरी, खरेदी ऑर्डर, आणि बहु-टप्प्याचे input validation एका विनंतीला अधिकाराच्या स्तरांमधून वर नेतात.

  • मॅनेजर एका मर्यादेपर्यंत मंजूर करतो; मोठ्या रकमा डायरेक्टरकडे, मग finance कडे जातात.
  • प्रत्येक validator एक नियम तपासतो, format, range, व्यावसायिक अट, मग यशस्वी झाल्यावर पुढे पाठवतो.
  • सादरकर्ता एकच विनंती पाठवतो आणि कोणता स्तर मंजुरी देतो हे कधीच जाणण्याची गरज नसते.
✅ निष्कर्ष: साखळी संपादित करून मंजुरीच्या मर्यादा अन् validation नियम बदलतात, ज्यामुळे व्यावसायिक धोरण caller बाहेर राहते.
07 - उपयुक्तता

आधुनिक उपयुक्तता

कालबाह्य होण्यापासून दूर, Chain of Responsibility हा आधुनिक सॉफ्टवेअरमधील सर्वात व्यापकपणे तैनात केलेल्या पॅटर्नपैकी एक आहे, सहसा "pipeline" किंवा "middleware" या नावाखाली लपलेला.

🧅 सर्वत्र middleware

Express, Koa, ASP.NET Core, Django, आणि gRPC interceptor या सर्व साखळ्या आहेत. तुम्ही next() कॉल लिहिला असेल, तर तुम्ही हा पॅटर्न वापरला आहे.

🛡️ API gateway

Gateway आणि service mesh विनंत्या क्रमबद्ध filter मधून, auth, rate limiting, routing, चालवतात, जे तुम्ही घोषणात्मकपणे रचता.

⚙️ Functional composition

आधुनिक codebase मध्ये साखळी बहुधा फक्त composed function असतात, प्रत्येक पुढचा हँडलर घेणारा, जी कमी औपचारिकतेसह तीच कल्पना आहे.

🤖 LLM आणि agent pipeline

Guardrail आणि tool-routing स्टॅक एका विनंतीला validator अन् हँडलरमधून पाठवतात, जोपर्यंत एखादा ती स्वीकारत नाही, एक ठराविक साखळी.

🧪 Event आणि stream प्रक्रिया

Kafka, message broker, आणि ETL टप्प्यांतील interceptor साखळ्या प्रत्येक टप्प्याला record रूपांतरित करू, टाकून देऊ किंवा पुढे पाठवू देतात.

🔌 Plugin आर्किटेक्चर

विस्तारक्षम साधने तिसऱ्या पक्षांना core ला त्यांच्या अस्तित्वाची जाणीव न होता विनंती साखळीत हँडलर घालू देतात.

निष्कर्ष: जेव्हा एखादी विनंती प्रोसेसरच्या क्रमबद्ध, बदलता येण्याजोग्या संचातून वाहावी, आणि कोण उत्तर देते याबद्दल sender अनभिज्ञ राहावा असे तुम्हाला वाटते, तेव्हा Chain of Responsibility हाच पॅटर्न आहे. विनंत्या हाताळणे आवश्यक आहे की त्या खाली पडू शकतात हे आधीच ठरवा, बाकी सगळे आपोआप जुळेल.
