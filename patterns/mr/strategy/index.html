Behavioral Pattern

Strategy पॅटर्न - caller ला हात न लावता algorithms अदलाबदल करा

काही कोडला तेच काम अनेक प्रकारे करावे लागते: card ने किंवा PayPal ने पैसे भरणे, किंमतीनुसार किंवा rating नुसार sort करणे, zip किंवा gzip ने compress करणे. Strategy प्रत्येक प्रकाराला एका समान interface मागे वेगळा object म्हणून पकडते, आणि मग तुम्हाला runtime ला एक निवडू देते. Client तसेच काम करत राहतो, तर तो वापरत असलेले वर्तन एक plug-in बनते जे तुम्ही जोडू, बदलू किंवा स्वतंत्रपणे test करू शकता.

01 - काय

Strategy पॅटर्न म्हणजे काय?

Strategy algorithms च्या एका कुटुंबाला परिभाषित करते, प्रत्येकाला त्याच्या स्वतःच्या class मध्ये encapsulate करते, आणि एका सामायिक interface मागे त्यांना अदलाबदल करण्यायोग्य बनवते. ज्या object ला काम हवे असते (तो context) एका strategy चा reference धरून ठेवतो आणि त्याला delegate करतो, त्यामुळे algorithm हे त्याचा वापर करणाऱ्या कोडपासून स्वतंत्रपणे बदलू शकते. एखादी गोष्ट कशी करायची हे ठरवणाऱ्या वाढत्या if/else च्या साखळीऐवजी, तुम्ही context ला एक असा object देता जो ते कसे करायचे हे आधीच जाणतो.

🧩 Strategy interface

एकच method (किंवा लहान संच) जी प्रत्येक algorithm अंमलात आणते. हा तो contract आहे ज्यावर context अवलंबून असतो, कधीही concrete classes वर नाही.

⚙️ Concrete strategies

अदलाबदल करता येणाऱ्या implementations - card payment, gzip compression, price sort. प्रत्येक स्वयंपूर्ण आणि स्वतःच testable आहे.

📦 Context

एक strategy धरून ठेवतो आणि तिला delegate करतो. तो एक setter उघड करतो किंवा strategy आपल्या constructor मध्ये घेतो, आणि मग त्याच्याकडे कोणती आहे याची कधीच पर्वा करत नाही.

02 - का

Strategy पॅटर्न का अस्तित्वात आहे

पर्याय म्हणजे एक अशी method जी प्रत्येक वेळी नवीन variant आल्यावर नवीन if branch वाढवते. ती method open/closed तत्त्वाचे उल्लंघन करते, असंबंधित logic एकत्र मिसळते, आणि तुकड्यांमध्ये test करणे अशक्य बनते. Strategy प्रत्येक variant ला त्याच्या स्वतःच्या object मध्ये बाहेर काढते जेणेकरून caller ला edit न करता वर्तन बदलू शकते.

🚫 Conditional पसरणे थांबवते

"Type" वरील जाड switch ला polymorphism ने बदलते. एक variant जोडणे म्हणजे एक class जोडणे, इतर प्रत्येक variant सामायिक करत असलेली branch edit करणे नव्हे.

🔓 विस्तारासाठी खुले

नवीन algorithms context किंवा अस्तित्वातील strategies न बदलता जोडले जातात. बदलासाठी बंद, विस्तारासाठी खुले - व्यवहारात open/closed तत्त्व.

🔁 Runtime ला अदलाबदल करता येते

Program चालू असताना वर्तन बदला: config मधून compression level निवडा, load च्या आधारावर routing algorithm निवडा, प्रत्येक ग्राहकासाठी pricing नियम बदला.

🧪 स्वतंत्र आणि testable

प्रत्येक strategy एका कामाचा लहान एकक आहे, त्यामुळे तुम्ही algorithms स्वतंत्रपणे test करता आणि context test करताना त्यांना mock करता.

सोप्या शब्दांत

उपमांसह Strategy समजावून

तीच कल्पना, कल्पना करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ते लक्षात येईल.

🎓 विद्यार्थ्यासाठी

हे घरी जाण्याचा मार्ग निवडण्यासारखे आहे. चालणे, bus, किंवा bike सर्व तुम्हाला तिथे पोहोचवतात; हवामान आणि वेळेनुसार तुम्ही एक निवडता. गंतव्यस्थान (interface) निश्चित असते; पद्धत (strategy) अदलाबदल करण्यायोग्य असते.

👩‍💻 developer साठी

हे argument म्हणून पाठवलेले function आहे. Sort कसे करायचे हे hardcode करण्याऐवजी, तुम्ही sorter ला एक comparator देता. तीच call site, वेगळे वर्तन, जो object पुरवतो त्याने ठरवलेले.

🏢 व्यावसायिकासाठी

card, contactless, किंवा wallet स्वीकारणाऱ्या payment terminal चा विचार करा. Cashier तेच "payment घ्या" पाऊल चालवतो; ग्राहक पद्धत निवडतो. Till ला प्रत्येक payment प्रकारासाठी branch लागत नाही.

🧳 रोजच्या जीवनातील आवृत्ती

प्रवासासाठी power adapter. तुमचा laptop तसाच plug होतो; तुम्ही ज्या देशात आहात त्यासाठी wall prong बदलता. उपकरण तसेच राहते; फक्त plug ची strategy बदलते.

03 - कसे

ते आतून कसे काम करते

Strategy composition आणि delegation वर बांधलेली आहे. Context एका strategy चा subclass असण्याऐवजी तिला धरून ठेवतो, त्यामुळे algorithm एका वेगळ्या object मध्ये राहते जो client आपल्या इच्छेनुसार inject आणि बदलू शकतो.

🔗 Composition, inheritance नव्हे

Context एक strategy field धरतो आणि बदलणारे पाऊल तिला delegate करतो. वर्तन runtime ला objects जोडून एकत्र केले जाते, class hierarchy ने compile time ला निश्चित केले जात नाही.

🎯 Interface साठी program करा

Context फक्त strategy interface वर अवलंबून असतो. Concrete algorithms त्याला दिसत नाहीत, आणि यामुळेच ते अदलाबदल करण्यायोग्य आणि स्वतंत्रपणे testable बनतात.

Java मधील एक वास्तववादी उदाहरण

// 1. The strategy interface - the common contract
interface PaymentStrategy {
    void pay(int amountCents);
}

// 2. Interchangeable concrete strategies
class CreditCardPayment implements PaymentStrategy {
    private final String number;
    CreditCardPayment(String number) { this.number = number; }
    public void pay(int amountCents) {
        System.out.printf("Charged %d to card %s%n", amountCents, mask(number));
    }
    private String mask(String n) { return "****" + n.substring(n.length() - 4); }
}

class PayPalPayment implements PaymentStrategy {
    private final String email;
    PayPalPayment(String email) { this.email = email; }
    public void pay(int amountCents) {
        System.out.printf("Charged %d via PayPal (%s)%n", amountCents, email);
    }
}

// 3. The context - delegates, never branches on payment type
class Checkout {
    private PaymentStrategy strategy;
    void setStrategy(PaymentStrategy s) { this.strategy = s; }
    void checkout(int amountCents) {
        if (strategy == null) throw new IllegalStateException("No payment method");
        strategy.pay(amountCents);   // the varying step, delegated
    }
}

// 4. The client selects a strategy at runtime
Checkout checkout = new Checkout();
checkout.setStrategy(new CreditCardPayment("4242424242424242"));
checkout.checkout(1999);

checkout.setStrategy(new PayPalPayment("buyer@example.com")); // swap, same call
checkout.checkout(1999);

लक्षात घ्या की context मध्ये payment प्रकारावर कोणतीही conditional नाही. CryptoPayment जोडणे म्हणजे एक नवीन class लिहिणे - Checkout कधीच बदलत नाही. हेच composition ते काम करत आहे जे पूर्वी एक switch statement करत असे.

Lambdas सह functional strategies (TypeScript)

// When a strategy is a single method, it is just a function type.
type SortStrategy<T> = (a: T, b: T) => number;

class ProductList {
  constructor(private items: Product[]) {}
  sortBy(strategy: SortStrategy<Product>): Product[] {
    return [...this.items].sort(strategy);
  }
}

// Strategies as plain lambdas - no class boilerplate needed
const byPriceAsc:  SortStrategy<Product> = (a, b) => a.price - b.price;
const byRatingDesc: SortStrategy<Product> = (a, b) => b.rating - a.rating;

const list = new ProductList(catalog);
list.sortBy(byPriceAsc);    // choose an algorithm at the call site
list.sortBy(byRatingDesc);  // swap it freely

// A registry makes runtime selection data-driven
const sorters: Record<string, SortStrategy<Product>> = {
  price:  byPriceAsc,
  rating: byRatingDesc,
};
list.sortBy(sorters[userChoice] ?? byPriceAsc);

आधुनिक भाषांमध्ये एका method ची strategy एका lambda मध्ये आटते. पॅटर्न तसाच आहे - interface, अदलाबदल करण्यायोग्य implementations, runtime निवड - पण एक functional interface (Comparator, Runnable, एक function type) class चा सोहळा काढून टाकते.

काढा

प्रत्येक branch एका class मध्ये काढा

Conditional ची प्रत्येक शाखा interface अंमलात आणणाऱ्या तिच्या स्वतःच्या concrete strategy मध्ये हलवा. एक algorithm, एक class, एक जबाबदारी.

जोडा

Context ला एक strategy field द्या

Interface प्रकाराचे एक field आणि एक constructor किंवा setter जोडा. Context आता algorithm hardcode करण्याऐवजी एक strategy धरून ठेवतो.

40
Delegate करा

Branch ला call ने बदला

जुन्या switch ला strategy.execute(...) ने बदला. Context कोणते algorithm चालते हे जाणणे थांबवतो; तो फक्त delegate करतो.

50
Inject करा

Client कडून strategy जोडा

Client, factory, किंवा DI container एक concrete strategy निवडतो आणि ती आत पाठवतो. निवडीचे logic काठावर राहते, context आत नाही.

60
निवडा

Runtime input ला strategy शी जोडा

User च्या निवडीने किंवा config ने keyed केलेला registry किंवा factory runtime ला algorithm निवडतो, mapping एका लहान, स्पष्ट जागी ठेवतो.

70
सोपे करा

लहान strategies lambdas मध्ये आटवा

Interface ला एक method असल्यास, साध्या strategies lambdas किंवा function references म्हणून व्यक्त करा आणि class चा boilerplate टाकून द्या.

80

प्रत्येक algorithm एकट्याने unit test करा

प्रत्येक strategy स्वतंत्र आहे, त्यामुळे तिला थेट test करा. Context ला एका stub strategy सह test करा जेणेकरून तो योग्यरित्या delegate करतो हे सिद्ध होईल.

पाठवा

सामान्य अडचणी

अडचणी आणि anti-patterns

Strategy सोपी आहे, ज्यामुळे तिचा अतिवापर करणे किंवा चुकीच्या पद्धतीने जोडणे सोपे होते. या गोष्टींकडे लक्ष द्या.

🪆 Strategy चा स्फोट

कधीच न बदलणाऱ्या वर्तनासाठी, किंवा एकवेळच्या वापरासाठी class तयार करणे, फायद्याविना indirection जोडते. जेव्हा खरोखर, अनेक अदलाबदल करण्यायोग्य algorithms असतील - फक्त एक नव्हे - तेव्हाच Strategy कडे वळा.

🔀 निवड पुन्हा आत आणणे

कोणती strategy बांधायची हे ठरवण्यासाठी context अजूनही switch करत असेल, तर तुम्ही conditional हलवली, काढली नाही. निवड एका factory किंवा registry मध्ये ठेवा, context आत नाही.

🧷 जाड interface

Strategy interface मध्ये अनेक असंबंधित methods कोंबल्याने प्रत्येक algorithm ला ज्याची गरज नाही ते अंमलात आणावे लागते. Contract प्रत्यक्षात बदलणाऱ्या एका operation पुरता ठेवा.

📤 खूप जास्त context पाठवणे

Strategy ला संपूर्ण context object देणे त्यांना घट्ट जोडते. Algorithm ला लागणारा फक्त तेवढाच data parameters म्हणून पाठवा जेणेकरून strategies स्वतंत्र आणि पुनर्वापर करण्यायोग्य राहतील.

🌀 State शी गोंधळ

जिथे object ने स्वतःच वर्तनांमध्ये संक्रमण करावे तिथे Strategy वापरल्याने बाहेरून विचित्र switching होते. जर वर्तन बदल अंतर्गत आणि स्वयंचलित असेल, तर तुम्हाला State हवे.

🧊 State असलेल्या सामायिक strategies

एका सामायिक strategy instance ला बदलणारे per-call state दिल्याने ती अनेक threads किंवा requests मध्ये पुनर्वापरली गेल्यास race conditions होतात. Strategies stateless ठेवा किंवा प्रत्येक वापरासाठी एक तयार करा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Strategy थोड्याशा indirection च्या बदल्यात भरपूर लवचिकता देते. जेव्हा variants खरे असतात आणि वाढण्याची शक्यता असते तेव्हा ते वापरा.

पैलूतपशील
फायदेConditional पसरणे काढते, open/closed पाळते, runtime अदलाबदल सक्षम करते, प्रत्येक algorithm चे testing स्वतंत्र आणि सोपे करते.
तोटेअधिक classes आणि indirection, एक निवडण्यासाठी clients ला strategies अस्तित्वात आहेत हे माहीत असावे लागते, वर्तन कधीच बदलत नसेल तेव्हा अनावश्यक.
केव्हा वापरावेएक काम करण्याचे अनेक अदलाबदल करण्यायोग्य मार्ग असतील, संच वाढण्याची शक्यता असेल, किंवा तुम्हाला config किंवा input ने runtime ला वर्तन निवडावे लागेल.
केव्हा टाळावेफक्त एकच algorithm असेल, variants कधीच बदलत नसतील, किंवा वर्तन संक्रमणे अंतर्गत आणि स्वयंचलित असतील (ते State आहे).
गुंतागुंतकमी. एक interface, N implementations, एक delegate करणारे field. एका method च्या strategies साठी lambdas ती आणखी कमी करतात.
संबंधितState (स्वयंचलित संक्रमणे), Template Method (निश्चित सांगाडा, inheritance), Decorator (वर्तन जोडण्यासाठी wrap), Factory Method (strategy तयार करा).
अंगठ्याचा नियम: जर तुम्ही एखादी गोष्ट कशी करायची हे ठरवण्यासाठी "type" वर switch लिहीत असाल, आणि तो switch सतत नवीन cases मिळवत असेल, तर Strategy कडे वळा. जर object ने स्वतःचे पुढील वर्तन ठरवावे, तर त्याऐवजी State कडे वळा.
06 - Case Studies

वास्तविक जगातील case studies

Production-शैलीच्या कोडमध्ये Strategy दाखवणारे तीन प्रातिनिधिक वापर.

💳

1 · Checkout ला payment प्रक्रिया

पॅटर्न: अदलाबदल करण्यायोग्य payment algorithms

एका e-commerce checkout ला card, PayPal, wallet, आणि नंतर buy-now-pay-later स्वीकारावे लागते, order flow ने प्रत्येकावर branch न करता.

  • प्रत्येक provider एका pay(amount) method सह एक PaymentStrategy अंमलात आणतो.
  • एक registry user ने निवडलेल्या पद्धतीला runtime ला योग्य strategy शी जोडतो.
  • नवीन provider जोडणे म्हणजे एक नवीन class आणि एक registry नोंद, checkout अस्पर्श राहतो.
✅ परिणाम: Checkout flow न बदलता किंवा पुन्हा test न करता नवीन payment पद्धती पाठवल्या जातात, आणि प्रत्येक provider स्वतंत्रपणे test केला जातो.
🗜️

2 · Storage layer मध्ये pluggable compression

पॅटर्न: config किंवा content ने निवडलेले algorithm

एक file service uploads compress करते, पण सर्वोत्तम codec हा file प्रकार आणि tune करण्यायोग्य speed-विरुद्ध-ratio सेटिंगवर अवलंबून असतो.

  • एक Compressor interface gzip, zstd, आणि एका no-op strategy ने अंमलात आणले जाते.
  • निवडलेली strategy configuration मधून येते, त्यामुळे operators redeploy न करता तिला tune करतात.
  • Benchmarks प्रत्येक strategy स्वतंत्रपणे चालवतात कारण कोणतीही storage context वर अवलंबून नाही.
✅ परिणाम: Team config मार्फत प्रत्येक bucket साठी codecs बदलते आणि upload pipeline मध्ये शून्य बदल करून zstd जोडते.
🔢

3 · Product catalog मध्ये sorting आणि ranking

पॅटर्न: comparators म्हणून functional strategies

एक catalog page खरेदीदारांना किंमत, rating, relevance, किंवा नवीनतेनुसार sort करू देते, नवीन क्रमवारी वारंवार जोडल्या जातात.

  • प्रत्येक क्रमवारी एक comparator lambda आहे, class चा boilerplate लागत नाही.
  • UI निवडीपासून comparator पर्यंतचे एक map प्रत्येक request साठी strategy निवडते.
  • Composite strategies chaining करून comparators एकत्र करतात (rating मग किंमत).
✅ परिणाम: Product managers sort पर्याय लहान, शुद्ध functions म्हणून जोडतात, प्रत्येक सहज unit test केलेले, page logic ला कोणताही धोका न देता.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Strategy हा सर्वात टिकाऊ पॅटर्नपैकी एक आहे कारण आधुनिक भाषा त्याला जवळपास मोफत बनवतात आणि dependency injection त्याला वर्तन बदलण्याचा default मार्ग बनवते.

🧬 Lambdas ने ते क्षुल्लक बनवले

Functional interfaces आणि function types एका method च्या strategy ला एका ओळीच्या lambda मध्ये बदलतात, त्यामुळे जुन्या class overhead शिवाय पॅटर्न सर्वत्र दिसतो.

💉 ते dependency injection ला शक्ती देते

एका interface implementation ला inject करणे म्हणजे दुसऱ्या नावाने Strategy. DI containers नेहमीच concrete strategies contexts मध्ये जोडतात.

🎚️ Feature flags मागे वर्तन

Flag किंवा config ने strategy निवडल्याने teams caller redeploy न करता production मध्ये algorithm variants रोल आउट आणि A/B test करू शकतात.

🔌 Plugin architectures

विस्तारित करता येणाऱ्या systems एक strategy interface उघड करतात जेणेकरून तिसरे पक्ष सुरक्षितपणे नवीन algorithms - payment providers, exporters, validators - आत टाकू शकतात.

⚡ रचनेने testable

स्वतंत्र strategies unit testing आणि mocking मध्ये अगदी चपखल बसतात, म्हणूनच जलद, केंद्रित tests ला महत्त्व देणाऱ्या codebases मध्ये त्यांना पसंती दिली जाते.

🧠 ML आणि pricing मधील policy objects

Ranking, routing, आणि pricing "policies" या Strategy objects आहेत ज्या models आणि नियम विकसित होताना अदलाबदल केल्या जातात, आजूबाजूची system स्थिर ठेवतात.

सारांश: Strategy हा तो मार्ग आहे ज्याने तुम्ही वर्तनाला first-class, अदलाबदल करण्यायोग्य गोष्ट बनवता. जेव्हा कधी logic च्या एका तुकड्याला अनेक अदलाबदल करण्यायोग्य implementations असतात, तेव्हा त्यांना एका interface मागे पकडल्याने तुमचा कोड नवीन variants साठी खुला राहतो आणि आधीच काम करणारे तोडण्यासाठी बंद राहतो.
