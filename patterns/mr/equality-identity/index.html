समानता आणि ओळख - दोन ऑब्जेक्ट "समान" केव्हा असतात?

5 USD धारण करणारे दोन Money ऑब्जेक्ट समान मानले पाहिजेत, पण वेगवेगळ्या व्यक्तींसाठीचे दोन User रेकॉर्ड कधीच समान नसावेत, जरी प्रत्येक दृश्य फील्ड जुळत असले तरी. हे चुकीचे केल्याने sets खराब होतात, deduplication मोडते, आणि जुन्या प्रती खऱ्या गोष्टीचे सोंग घेतात. ही identity (समान ऑब्जेक्ट) आणि equality (समान मूल्य) यांच्यातील सीमारेषा आहे.

01 - काय

equality विरुद्ध identity म्हणजे काय?

Identity विचारते "हे मेमरीमधील नेमके तेच ऑब्जेक्ट आहेत का?" Equality विचारते "हे दोन ऑब्जेक्ट समान मूल्य दर्शवतात का?" एका payment ledger साठी महत्त्वाचे असते की 5 USD चे दोन Money रकमेचे एकमेकांशी अदलाबदल करता येते; एका auth प्रणालीसाठी महत्त्वाचे असते की दोन User हँडल एकाच खात्याकडे निर्देश करतात, केवळ एकच नाव असणाऱ्या व्यक्तींकडे नव्हे. प्रत्येक भाषा तुम्हाला एक default देते, आणि तो default जवळजवळ नेहमीच identity असतो, जो value objects साठी तुमच्या डोमेनला क्वचितच हवा असतो.

🧷 Reference identity

दोन व्हेरिएबल तेव्हाच identical असतात जेव्हा ते एकाच instance कडे निर्देश करतात. TS मध्ये objects वर ===, Python मध्ये is, Ruby मध्ये equal? साठी हा default आहे.

⚖️ Value equality

दोन instances तेव्हा equal असतात जेव्हा त्यांची अर्थपूर्ण फील्ड जुळतात. equals मेथड, __eq__, किंवा == लागू करून तुम्ही यात सामील होता.

🔑 Hashing

जर equal ऑब्जेक्ट set members किंवा map keys म्हणून वापरता आले पाहिजेत, तर त्यांना जुळणारे hash codes लागतात. Equality आणि hashing सोबतच जातात.

02 - का

equality आणि identity का महत्त्वाची

Collections, caches, आणि deduplication हे सर्व मूकपणे तुमच्या equality व्याख्येवर अवलंबून असतात. ते default म्हणून सोडा आणि एक shopping cart दोन "identical" line items धरून ठेवेल जे तिला वेगळे वाटतात, किंवा authorized users चा एक set duplicates स्वीकारेल.

🧺 Collections योग्यरित्या वागतात

Sets, maps, आणि includes तपासण्या equality वर अवलंबून असतात. योग्य equality असलेले Money value object एका discount engine ला विचारू देते "ही रक्कम आधीच applied set मध्ये आहे का?" आणि खरे उत्तर मिळवते.

🧭 Entities स्वतःच राहतात

ईमेल, नाव, आणि avatar बदलणारा User तरीही तोच user असतो. स्थिर id वर आधारित identity प्रत्येक संपादनातून टिकते, त्यामुळे audit logs आणि permissions योग्य खात्याशी जोडलेली राहतात.

🔁 Deduplication खरोखर काम करते

दोन प्रणालींमधून orders एकत्र करण्यासाठी "समान order line" ची निश्चित कल्पना लागते. अर्थपूर्ण फील्डवरील value equality तुम्हाला दुहेरी शुल्क आकारण्याऐवजी duplicates एकत्र करू देते.

🧱 Contract भ्रष्टाचार रोखते

equals/hashCode contract चा सन्मान केल्याने hash-आधारित रचना सुसंगत राहतात. ते मोडा आणि ऑब्जेक्ट sets मधून गायब होतात, किंवा दोन "equal" keys एकाच map मध्ये राहतात.

सोप्या भाषेत

उपमांसह समजावलेली equality आणि identity

तोच फरक, चित्रित करण्याचे चार मार्ग, त्यामुळे तुम्ही कोणीही असाल तरी लक्षात येईल.

🎓 विद्यार्थ्यासाठी

दहा-दहा रुपयांच्या दोन नोटा मूल्यात equal असतात, तुम्ही विचार न करता एक दुसरीशी बदलाल. पण तुमचे विद्यार्थी ओळखपत्र म्हणजे identity: नवीन फोटोसह पुन्हा छापलेले कार्ड तरीही तुमचेच रेकॉर्ड असते, आणि इतर कोणत्याही विद्यार्थ्याचे कार्ड त्याच्याशी अदलाबदल करता येत नाही.

👩‍💻 डेव्हलपरसाठी

Reference identity म्हणजे दोन pointers ची तुलना; value equality म्हणजे ते जिकडे निर्देश करतात त्याची तुलना. Default === pointer तपासतो, म्हणून जेव्हा तुमच्या डोमेनला address नव्हे तर मजकूर महत्त्वाचा असतो तेव्हा तुम्ही equality override करता.

🏢 व्यावसायिकासाठी

समान रकमेच्या दोन invoices equal रकमा असतात पण वेगळ्या invoices असतात. Finance प्रणाली प्रत्येक invoice ला त्याच्या क्रमांकाने (identity) key करते तर पैशांचे आकडे मूल्यानुसार तुलना करते.

🚚 रोजच्या जीवनातील आवृत्ती

एकाच शेल्फवरचे दोन एकसारखे courier बॉक्स equal असतात. एकदा एकावर तुमचा tracking number आला की तो तोच पार्सल बनतो: दुसरा बॉक्स बदलून टाका आणि डिलिव्हरी चुकीची होते, जरी बॉक्स सारखेच दिसत असले तरी.

03 - कसे

equality योग्यरित्या कशी लागू करावी

value objects (जसे Money) मजकुरानुसार equality आणि जुळणाऱ्या hash सह मॉडेल करा; entities (जसे User) एका स्थिर id नुसार equality सह मॉडेल करा. दोन्ही कधीही मिसळू नका: आपल्या mutable फील्डनुसार तुलना करणारी entity, कोणी संपादन करताच "identity बदलेल".

💵 Value object: Money

अपरिवर्तनीय, id नाही. Currency आणि minor units जुळल्यास दोन रकमा equal असतात. Equality आणि hash दोन्ही त्या दोन फील्डमधून निघतात, त्यामुळे Money map key आणि set member म्हणून काम करते.

🧑 Entity: User

याला जीवनचक्र आणि एक स्थिर id असतो. Equality फक्त ids ची तुलना करते. ईमेल, नाव, आणि role सर्व बदलू शकतात, दोन references एकाच खात्याला दर्शवतात की नाही यावर परिणाम न करता.

Money वर value equality लागू करणे

// Money is a value object: two amounts are equal by content, not by reference.
class Money {
  private constructor(
    readonly amountMinor: number, // cents, avoids float drift
    readonly currency: string,
  ) {}

  static of(amountMinor: number, currency: string): Money {
    return new Money(amountMinor, currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) {
      throw new Error(`Currency mismatch: ${this.currency} vs ${other.currency}`);
    }
    return new Money(this.amountMinor + other.amountMinor, this.currency);
  }

  // Value equality: same currency AND same amount.
  equals(other: unknown): boolean {
    return (
      other instanceof Money &&
      other.amountMinor === this.amountMinor &&
      other.currency === this.currency
    );
  }

  // Stable string key for use in a Map/Set that lacks value hashing.
  hashKey(): string {
    return `${this.currency}:${this.amountMinor}`;
  }
}

const a = Money.of(500, "USD");
const b = Money.of(500, "USD");

console.log(a === b);        // false -> different references (identity)
console.log(a.equals(b));    // true  -> same value (equality)

// Dedup by value using the hash key, since === would keep both.
const seen = new Map<string, Money>();
for (const m of [a, b, Money.of(750, "USD")]) seen.set(m.hashKey(), m);
console.log(seen.size);      // 2 -> the two 5.00 USD amounts collapsed

@dataclass(frozen=True)  # frozen -> immutable and auto-hashable
class Money:
    amount_minor: int  # cents, avoids float drift
    currency: str

    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError(f"Currency mismatch: {self.currency} vs {other.currency}")
        return Money(self.amount_minor + other.amount_minor, self.currency)

    # dataclass generates __eq__ (compares fields) and __hash__ (from the tuple
    # of fields) for us, so equal Money objects share a hash automatically.

b = Money(500, "USD")

# Money is a value object: == for equality, eql? + hash for hashing.
class Money
  attr_reader :amount_minor, :currency

  def initialize(amount_minor, currency)
    @amount_minor = amount_minor # cents, avoids float drift
    @currency = currency
    freeze                       # immutable value object
  end

  def add(other)
    unless other.currency == currency
      raise ArgumentError, "Currency mismatch: #{currency} vs #{other.currency}"
    end
    Money.new(amount_minor + other.amount_minor, currency)
  end

  # Value equality: same class, same fields.
  def ==(other)
    other.is_a?(Money) &&
      other.amount_minor == amount_minor &&
      other.currency == currency
  end

  # Hash-key equality for Set / Hash keys. eql? and hash must agree with ==.
  alias eql? ==

  def hash
    [amount_minor, currency].hash
  end
end

a = Money.new(500, "USD")
b = Money.new(500, "USD")

puts a.equal?(b)  # false -> different objects (identity)
puts a == b       # true  -> same value (equality)

# eql? + hash agree, so a Set deduplicates by value.
seen = [a, b, Money.new(750, "USD")].to_set
puts seen.size    # 2 -> the two 5.00 USD amounts collapsed

लक्षात घ्या की दोनदा तयार केलेले तेच ऑब्जेक्ट identity तपासणीत (=== / is / equal?) अपयशी ठरते पण value equality पास होते. आणि hashing equality शी सुसंगतपणे परिभाषित असल्यामुळे, एक set दोन्ही साठवण्याऐवजी duplicates एकत्र करते.

तुलना: id नुसार key केलेली entity

// User is an entity: equality is its identity (id), never its mutable fields.
class User {
  constructor(
    readonly id: string,
    private email: string,
    private displayName: string,
  ) {}

  changeEmail(email: string): void {
    this.email = email; // identity is unaffected by attribute changes
  }

  equals(other: unknown): boolean {
    return other instanceof User && other.id === this.id;
  }

  hashKey(): string {
    return `user:${this.id}`;
  }
}

const u1 = new User("u-42", "ada@corp.io", "Ada");
const u2 = new User("u-42", "ada.new@corp.io", "Ada L.");

console.log(u1.equals(u2)); // true -> same account despite different email/name

u1.changeEmail("ada@newco.io");
console.log(u1.equals(u2)); // still true -> identity survives edits
# User is an entity: equality is its identity (id), never its mutable fields.
class User:
    def __init__(self, user_id: str, email: str, display_name: str):
        self.id = user_id
        self.email = email
        self.display_name = display_name

    def change_email(self, email: str) -> None:
        self.email = email  # identity is unaffected by attribute changes

    def __eq__(self, other: object) -> bool:
        return isinstance(other, User) and other.id == self.id

    def __hash__(self) -> int:
        return hash(self.id)  # hash on the stable id, matching __eq__


u1 = User("u-42", "ada@corp.io", "Ada")
u2 = User("u-42", "ada.new@corp.io", "Ada L.")

print(u1 == u2)  # True -> same account despite different email/name

u1.change_email("ada@newco.io")
print(u1 == u2)  # still True -> identity survives edits
# User is an entity: equality is its identity (id), never its mutable fields.
class User
  attr_reader :id
  attr_accessor :email, :display_name

  def initialize(id, email, display_name)
    @id = id
    @email = email
    @display_name = display_name
  end

  def ==(other)
    other.is_a?(User) && other.id == id
  end
  alias eql? ==

  def hash
    id.hash # hash on the stable id, matching ==
  end
end

u1 = User.new("u-42", "ada@corp.io", "Ada")
u2 = User.new("u-42", "ada.new@corp.io", "Ada L.")

puts u1 == u2      # true -> same account despite different email/name

u1.email = "ada@newco.io"
puts u1 == u2      # still true -> identity survives edits

entity फक्त आपल्या id ची तुलना करते, त्यामुळे खाते u-42 कडील दोन references ईमेल आणि display name वेगळे झाल्यानंतरही equal राहतात. हे Money च्या अगदी विरुद्ध धोरण आहे, आणि प्रत्येक प्रकारासाठी योग्य ते निवडणे हीच संपूर्ण शिस्त आहे.

प्रथम दुसऱ्या ऑब्जेक्टचा प्रकार तपासा, नंतर निवडलेली फील्ड (value) किंवा id (entity) ची तुलना करा. परक्या प्रकारांसाठी exception टाकण्याऐवजी false परत करा.

50
Hash

जुळणारा hash लागू करा

equality जी फील्ड वापरते नेमक्या त्याच फील्डमधून hash काढा. Equal ऑब्जेक्ट समान hash द्यायलाच हवेत, नाहीतर sets आणि maps त्यांना मूकपणे गमावतात.

60
Contract

reflexive, symmetric, transitive पडताळा

a.equals(a) याची खात्री करा, की a.equals(b) हे b.equals(a) दर्शवते, आणि equality तिसऱ्या ऑब्जेक्टमधून साखळीने जाते.

70
Null

null आणि इतर प्रकार हाताळा

null/None/nil किंवा असंबंधित class शी तुलना केल्यास false परत येते, कधीही exception नाही. फील्डला स्पर्श करण्यापूर्वी प्रकार तपासा.

80
Collections

एका set आणि map मध्ये वापरून पाहा

एका set मध्ये duplicates टाका आणि ते एकत्र होतात याची खात्री करा; ऑब्जेक्टला map key म्हणून वापरा आणि lookups जुळतात याची खात्री करा. हे hash आणि equals सहमत असल्याचे सिद्ध करते.

90
Mutation

संपादनांमधून identity तपासा

entity ची फील्ड बदला आणि equality वर परिणाम होत नाही याची खात्री करा. value objects निर्मितीनंतर अजिबात बदलता येत नाहीत याची खात्री करा.

100
Ship

धोरण दस्तऐवजित करा

प्रकाराच्या docs मध्ये सांगा की Money मूल्यानुसार आणि User id नुसार तुलना केली जाते, जेणेकरून भविष्यातील callers पुन्हा कधीही default कडे वळणार नाहीत.

सामान्य धोके

धोके आणि anti-patterns

Equality बग शांत असतात: काहीही क्रॅश होत नाही, पण sets मध्ये duplicates गळतात आणि lookups चुकतात. हे नेहमीचे दोषी आहेत.

🧨 hashCode शिवाय equals

value equality override करून default hash सोडणे म्हणजे दोन "equal" Money ऑब्जेक्ट वेगळ्या buckets मध्ये पडतात, त्यामुळे एक set दोन्ही ठेवते आणि एक map key कधीच जुळत नाही. त्यांना नेहमी एकत्र परिभाषित करा.

🌀 hash मध्ये mutable फील्ड

नंतर बदलणाऱ्या फील्डवर hashing केल्याने ऑब्जेक्ट set मध्ये असतानाच नवीन bucket मध्ये सरकते, ज्यामुळे ते सापडता आणि काढता येत नाही. फक्त अपरिवर्तनीय डेटावर hash करा.

🪞 entities ची मजकुरानुसार तुलना

समान नाव असलेले दोन वेगळे users "equal" बनतात, वेगळी खाती एकत्र होतात. Entities ने स्थिर id नुसार तुलना केली पाहिजे, कधीही त्यांच्या attributes नुसार नाही.

💥 परक्या प्रकारांवर exception टाकणे

argument तोच class आहे असे गृहीत धरणारे equals, जेव्हा एखादे collection त्याची null किंवा दुसऱ्या प्रकाराशी तुलना करते तेव्हा फुटते. instance तपासणीने संरक्षण करा आणि false परत करा.

🔗 Asymmetric equality

स्वतःला एका base instance शी equal मानणारा पण उलट नाही असा subclass, symmetry नियम मोडतो आणि दोन्ही धरून ठेवणारे कोणतेही collection भ्रष्ट करतो. Equality symmetric ठेवा.

😵 references वर == वर विश्वास

दोन नुकत्याच लोड केलेल्या Money rows ची तुलना करण्यासाठी === किंवा is कडे वळणे नेहमी false परत करते, कारण ते वेगळे instances आहेत. value objects साठी value equality वापरा.

06 - Case Studies

वास्तविक जगातील उदाहरणे

तीन production-शैलीच्या प्रणाली जिथे equality-विरुद्ध-identity निवड भार वाहणारी आहे.

💳

1 · Money value object सह payments ledger

Pattern: रकमांसाठी value equality, transactions साठी identity

एक billing सेवा line रकमा जोडते, discounts लागू करते, आणि currencies ओलांडून totals ताळमेळ करते.

  • Money अपरिवर्तनीय आहे आणि currency अधिक minor units नुसार तुलना केली जाते, त्यामुळे 5.00 USD कोणत्याही इतर 5.00 USD शी equal असते.
  • Transactions या transaction id नुसार key केलेल्या entities आहेत; समान रकमेचे दोन transfers कधीच समान transaction नसतात.
  • applied discounts चा एक set एकच रक्कम दोनदा लागू होऊ नये म्हणून Money चा value hash वापरतो.
✅ निष्कर्ष: Reconciliation गणित duplicated रकमांमध्येही योग्य असते, तर प्रत्येक transfer आपल्या id नुसार अद्वितीयपणे auditable राहते.
🔐

2 · User entities चा मागोवा घेणारी auth प्रणाली

Pattern: profile संपादनांतून स्थिर id नुसार identity

एक identity provider अशी खाती व्यवस्थापित करतो ज्यांचे ईमेल, display name, आणि roles सतत बदलतात.

  • User equality फक्त अपरिवर्तनीय account id ची तुलना करते, त्यामुळे नाव बदलणे किंवा ईमेल बदलणे कधीही खात्याचे विभाजन करत नाही.
  • Session आणि permission sets users ना id-आधारित hash नुसार साठवतात, त्यामुळे lookups profile updates टिकवतात.
  • Duplicate signup एकत्र करणे हा एक जाणीवपूर्वक id remap आहे, अपघाती मजकूर जुळणी नाही.
✅ निष्कर्ष: Audit trails आणि permissions प्रत्येक संपादनातून योग्य खात्याशी बांधलेली राहतात, सारख्या दिसणाऱ्या users चे कोणतेही अपघाती विलीनीकरण न होता.
🛒

3 · Cart आणि catalog deduplication

Pattern: SKUs आणि options वर value equality

एका e-commerce cart ने समान product-आणि-options चे पुनरावृत्त adds एका quantity असलेल्या एका line मध्ये एकत्र केले पाहिजेत.

  • एक LineItemKey value object (SKU अधिक निवडलेले options) गटबद्धतेसाठी equality आणि hash परिभाषित करते.
  • समान configured product दोनदा जोडल्याने दुसरी row तयार करण्याऐवजी quantity वाढते.
  • Orders या order id नुसार key केलेल्या entities आहेत, त्यामुळे एकसारखा मजकूर असलेल्या दोन carts वेगळ्या orders राहतात.
✅ निष्कर्ष: Cart प्रत्येक वेगळ्या configuration साठी अचूक quantities सह एक line दाखवते, तर प्रत्येक ठेवलेली order आपली स्वतःची identity ठेवते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

भाषेची वैशिष्ट्ये योग्य equality स्वस्त करत राहतात, पण value-विरुद्ध-entity निर्णय मानवीच राहतो.

🧊 Records आणि data classes

Python @dataclass(frozen=True) आणि Ruby चा Data.define तुमच्यासाठी value equality आणि hashing तयार करतात, value objects साठीचे बहुतांश हस्तलिखित boilerplate काढून टाकतात.

🧩 Structural typing

TypeScript चे structural मॉडेल तुम्ही डेटाची तुलना कशी करता ते ठरवते, पण object identity अजूनही default ने reference असते, त्यामुळे value objects ना अजूनही स्पष्ट equals लागते.

🛡️ Branded आणि opaque ids

Branded id प्रकार तुम्हाला चुकून UserId ची OrderId शी तुलना करण्यापासून थांबवतात, entity identity तपासण्या type-safe बनवतात.

🧪 Property-based testing

fast-check आणि Hypothesis सारखी साधने reflexive, symmetric, आणि transitive नियम आपोआप तपासतात, contract मोडणे लवकर पकडतात.

🗃️ Domain-driven design

DDD चे value objects आणि entities यांच्यातील स्पष्ट विभाजन आता मुख्य प्रवाहातील शब्दसंग्रह आहे, प्रत्येक प्रकारासाठी equality धोरणाला एक सामायिक नाव देते.

🔀 Default ने Immutability

Persistent data structures आणि readonly-by-default शैली value objects ना keys म्हणून सुरक्षित बनवतात, कारण त्यांचा hash एका collection खाली कधीही बदलू शकत नाही.

सारांश: साधने equals आणि hashCode तयार करू शकतात, पण एखादा प्रकार मजकुरानुसार तुलना केलेले value आहे की id नुसार तुलना केलेली entity आहे हे फक्त तुम्हीच ठरवू शकता. तो निर्णय स्पष्टपणे घ्या, contract चा सन्मान करा, आणि तुमच्या collections, caches, आणि dedup logic अगदी सहज काम करतील.
