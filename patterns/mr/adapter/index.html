Structural पॅटर्न

Adapter पॅटर्न - विसंगत interface एकत्र काम करण्यासाठी

तुमचा client एक interface अपेक्षित करतो, पण तुमच्याकडे असलेला class वेगळी भाषा बोलतो. Adapter मधे बसतो आणि भाषांतर करतो: तो अस्तित्वात असलेला object wrap करतो आणि client ला हवा असलेला interface उघड करतो, वाटेत calls आणि data रूपांतरित करतो. legacy कोड, third-party लायब्ररी आणि जुळत नसलेल्या API कुठलीही बाजू पुन्हा लिहिल्याशिवाय codebase मधे जोडण्याची ही पद्धत आहे.

01 - काय

Adapter पॅटर्न म्हणजे काय?

Adapter हा एक structural पॅटर्न आहे जो एका class चा interface, client ला अपेक्षित असलेल्या दुसऱ्या interface मधे रूपांतरित करतो. client एका Target interface विरुद्ध कोड लिहितो; Adaptee हा उपयुक्त अंमलबजावणी असलेला पण चुकीच्या signature असलेला अस्तित्वात असलेला class असतो. Adapter हा Target ची अंमलबजावणी करतो आणि Adaptee धारण करतो किंवा त्याचा विस्तार करतो, प्रत्येक call पुढे पाठवतो आणि arguments व results अशी नव्याने घडवतो की दोन्ही बाजू जुळतात.

🎯 Target

client आधीपासूनच ज्यावर अवलंबून आहे तो interface. client कधीच बदलत नाही; त्याला फक्त हाच करार दिसतो.

🔌 Adaptee

तुम्हाला हवी असलेली क्षमता असलेला अस्तित्वातील किंवा third-party class, पण चुकीच्या method नावांसह, आकारांसह किंवा एककांसह.

🔄 Adapter

Target ची अंमलबजावणी करतो, Adaptee ला काम सोपवतो आणि दोघांमधे भाषांतर करतो. दोन्ही जग जाणणारा एकमेव class.

02 - का

Adapter का अस्तित्वात आहे

खऱ्या प्रणाली वेगवेगळ्या वेळी वेगवेगळ्या लोकांनी लिहिलेल्या भागांतून जुळवल्या जातात. एखाद्या integration च्या दोन्ही बाजू तुमच्या ताब्यात क्वचितच असतात, आणि एखादी स्थिर लायब्ररी किंवा vendor SDK तुमच्या interface शी जुळण्यासाठी पुन्हा लिहिणे महाग आणि जोखमीचे असते. Adapter दोन्ही बाजूंना जशाच्या तशा राहू देतो.

🧱 पुन्हा न लिहिता पुनर्वापर

तुम्ही एका सिद्ध Adaptee ला जसाच्या तसा ठेवता आणि स्वच्छ Target द्वारे त्याचा पुनर्वापर करता, तुमच्या मालकीचा किंवा विश्वासाचा नसलेला कोड संपादित करण्याऐवजी.

🔗 vendor पासून decouple

client तुमच्या Target वर अवलंबून असतो, third-party API वर नाही. नवीन adapter लिहून Stripe च्या जागी Adyen आणा; client ला कधीच कळत नाही.

🧪 testable जोड

client interface शी बोलत असल्यामुळे, तुम्ही चाचण्यांमधे बनावट adapter बदलू शकता आणि खऱ्या प्रणालीला स्पर्श न करता edge cases चालवू शकता.

🕰️ legacy कोड आटोक्यात

जुने module आधुनिक interface मागे wrap करा, जेणेकरून नवीन कोड स्वच्छ राहील तर legacy अंतर्भाग स्वतःच्या वेळापत्रकानुसार स्थलांतरित किंवा निवृत्त होतील.

सोप्या शब्दांत

उपमांसह Adapter समजावून

एकच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती पटेल.

🎓 विद्यार्थ्यासाठी

ती एका संभाषणातील भाषांतरकार आहे. तुम्ही इंग्रजी बोलता, समोरची व्यक्ती जपानी बोलते; भाषांतरकार तुमच्यापैकी कोणाचाही अर्थ बदलत नाही, तो फक्त शब्द रूपांतरित करतो जेणेकरून तुम्ही एकमेकांना समजता.

👩‍💻 developer साठी

ती एक wrapper class आहे जी तुमचा interface अंमलात आणते आणि वेगळ्या signature असलेल्या लायब्ररीला calls पुढे पाठवते, तिचे return प्रकार आणि errors तुमचा कोड आधीच हाताळत असलेल्या आकारांमधे mapping करते.

🏢 व्यावसायिकासाठी

एका चलन विनिमय केंद्राचा विचार करा. तुमच्या पाकिटात euro आहेत, दुकानाला yen हवे आहेत; केंद्र एका ज्ञात दराने एकाचे दुसऱ्यात रूपांतर करते जेणेकरून कोणतीही बाजू न बदलता खरेदी पूर्ण होते.

🔌 रोजच्या जीवनातील आवृत्ती

एक प्रवासी वीज adapter. भिंतीवरचे सॉकेट आणि तुमच्या laptop चा plug दोन्ही ठीक आहेत; adapter फक्त जोडणीचा आकार बदलतो जेणेकरून एका मानकासाठी बनवलेले उपकरण दुसऱ्यासोबत काम करते.

03 - कसे

आतून तो कसा काम करतो

दोन उत्कृष्ट प्रकार आहेत. object adapter Adaptee ला एक field म्हणून धारण करतो आणि त्याला काम सोपवतो (composition). class adapter Target आणि Adaptee दोघांकडून वारसा घेतो (inheritance). ज्या भाषांमधे multiple inheritance नाही तेथे object adapters हे मूलभूत असतात; class adapters Adaptee चे वर्तन override करू शकतात पण तुम्हाला त्याच्या class शी जोडतात.

🧩 Object adapter (composition)

adapter कडे Adaptee असतो. तो Adaptee च्या कोणत्याही subclass ला wrap करू शकतो आणि एकाच वेळी अनेक adaptees adapt करू शकतो. लवचिक आणि शिफारस केलेला मूलभूत पर्याय.

🧬 Class adapter (inheritance)

adapter हा Adaptee आहे आणि Target आहे. delegation object नाही, आणि तो protected सदस्य override करू शकतो, पण तो एका ठोस Adaptee शी बांधला जातो आणि त्याला multiple inheritance लागते.

एका दृष्टीक्षेपात रचना

Class आकृती - client Target वर अवलंबून असतो; object adapter Adaptee ला काम सोपवतो

Java मधील एक object adapter

// Target: the interface our application already speaks
public interface PaymentGateway {
    Receipt charge(Money amount, String customerId);
}

// Adaptee: a third-party SDK we do not control
public final class StripeClient {
    public StripeResult createCharge(long cents, String currency, String customer) {
        // ... real HTTP call to Stripe ...
        return new StripeResult("ch_123", "succeeded");
    }
}

// Adapter: implements Target, holds the Adaptee (composition), translates both ways
public final class StripePaymentAdapter implements PaymentGateway {
    private final StripeClient stripe; // has-a Adaptee

    public StripePaymentAdapter(StripeClient stripe) {
        this.stripe = stripe;
    }

    @Override
    public Receipt charge(Money amount, String customerId) {
        long cents = amount.toMinorUnits();               // reshape input
        StripeResult r = stripe.createCharge(cents, amount.currencyCode(), customerId);
        if (!"succeeded".equals(r.status())) {            // translate errors
            throw new PaymentFailedException(r.id());
        }
        return new Receipt(r.id(), amount);               // reshape output
    }
}

// Client stays blissfully unaware of Stripe
PaymentGateway gateway = new StripePaymentAdapter(new StripeClient());
Receipt receipt = gateway.charge(Money.usd(49.99), "cus_42");

client ला फक्त PaymentGateway दिसतो. सर्व विसंगती - dollars ते cents, vendor result चा आकार, vendor error प्रथा - adapter च्या आत सामावली जाते, त्यामुळे providers बदलणे म्हणजे नवीन adapter लिहिणे, client ला स्पर्श करणे नाही.

सामान्य अडचणी

अडचणी आणि anti-patterns

Adapters सोपे असतात, म्हणूनच त्यांचा गैरवापर होतो. या गोष्टींकडे लक्ष ठेवा.

🧠 Logic ची घुसखोरी

adapter ने भाषांतर करावे, निर्णय घेऊ नये. जेव्हा business नियम, caching किंवा retries त्याच्या आत साचतात, तेव्हा तुम्ही adapter मागे एक service लपवली आहे आणि जोड गमावली आहे.

🪆 Adapter रचणे

एका adapter ला adapt करणाऱ्या adapter ला adapt करणे बहुधा चुकीचा Target दर्शवते. भाषांतरकार साखळीत लावण्याऐवजी interface ची पुनर्रचना करा.

💧 Leaky abstraction

जर Adaptee चे exceptions, प्रकार किंवा विचित्रता Target मधून झिरपत असतील, तर client अजूनही vendor शी जोडलेला आहे आणि adapter ने तुम्हाला काहीच दिले नाही.

🎭 Facade शी गोंधळ

एक संपूर्ण सोपे केलेले subsystem प्रवेशद्वार बांधून त्याला adapter म्हणणे उद्देश धूसर करते. Adapter अस्तित्वातील interface शी जुळतो; Facade एक सोपा शोधून काढतो.

🧬 class adapters चा अतिवापर

Adaptee कडून वारसा घेतल्याने तुम्ही एका ठोस class आणि त्याच्या अंतर्भागाशी बांधले जाता. Composition कमी coupling सह अधिक targets adapt करते.

🔕 errors गिळणे

Adaptee चे अपयश पकडून एक निरस default परत करणे खरे प्रश्न लपवते. errors प्रामाणिकपणे अर्थपूर्ण domain exceptions मधे भाषांतरित करा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Adapter स्वस्त आणि कमी-जोखमीचा आहे, पण तो एक भाषांतर स्तर आहे, वाईट interface वरचा उपाय नाही. त्याचे प्रामाणिकपणे मूल्यमापन करा.

पैलूतपशील
फायदेअस्तित्वातील कोड जसाच्या तसा पुनर्वापर करतो, client ला vendors पासून decouple करतो, एक testable जोड तयार करतो, आणि बदल एका छोट्या class पुरता मर्यादित ठेवतो.
तोटेएक indirection स्तर जोडतो, Target नीट न निवडल्यास Adaptee ची विचित्रता झिरपू शकते, आणि logic घुसखोरीचा मोह होतो.
केव्हा वापरावेतुम्हाला एखादा अस्तित्वातील किंवा third-party class अशा interface शी जुळवायचा असतो जो तुम्ही कोणत्याही बाजूने बदलू शकत नाही किंवा बदलू इच्छित नाही.
केव्हा टाळावेतुमच्या ताब्यात दोन्ही interface आहेत आणि तुम्ही ते फक्त संरेखित करू शकता, किंवा खरी गरज नवीन वर्तनाची (Decorator) किंवा सोप्या प्रवेशद्वाराची (Facade) असते.
गुंतागुंतकमी. सहसा प्रत्येक integration मागे एक छोटा class, class inheritance पेक्षा object (composition) प्रकार सुरक्षित मूलभूत पर्याय म्हणून.
संबंधितBridge आधीच abstraction ला implementation पासून वेगळे करतो; Decorator वर्तन जोडतो; Facade subsystem सोपे करतो; Proxy प्रवेश नियंत्रित करतो.
ठोकताळा: जेव्हा आकार बरोबर आहेत पण signatures चुकीचे आहेत तेव्हा Adapter कडे वळा. जर तुम्ही जबाबदाऱ्या भाषांतरित करण्याऐवजी जोडत असाल, तर तुम्ही या पॅटर्नच्या पलीकडे गेला आहात.
06 - केस स्टडी

वास्तविक जगातील केस स्टडी

production-शैलीच्या कोडमधे Adapter दर्शवणारे तीन प्रातिनिधिक वापर.

💳

1 · Payment provider abstraction

पॅटर्न: vendor-निरपेक्ष Target प्रत्येक provider साठी adapters सह

एका checkout service ने प्रत्येकासाठी order logic पुन्हा न लिहिता अनेक payment vendors ला आधार द्यायचा असतो.

  • domain एक PaymentGateway Target परिभाषित करते ज्यात स्वच्छ charge आणि refund असते.
  • प्रत्येक vendor SDK ला स्वतःचा adapter मिळतो जो money, currency आणि result प्रकार map करतो.
  • नवीन provider जोडणे म्हणजे factory मधे नोंदवलेला एक नवीन adapter class, बाकी काही नाही.
✅ परिणाम: order प्रवाह फक्त Target वर अवलंबून असतो, त्यामुळे business कोडला स्पर्श न करता vendors जोडता, बदलता किंवा A/B चाचणी करता येतात.
🕰️

2 · legacy module wrap करणे

पॅटर्न: जुन्या अंतर्भागावर आधुनिक interface

एक दशकभर जुनी reporting लायब्ररी छान काम करते पण एक अवघड, stateful API उघड करते ज्यावर नवीन codebase अवलंबून राहू नये.

  • एक आधुनिक ReportSource interface नवीन कोडला प्रत्यक्षात काय हवे आहे ते वर्णन करतो.
  • एक adapter legacy लायब्ररी wrap करतो, तिच्या setup calls आणि global state स्वच्छ methods मागे लपवतो.
  • legacy कोड कालांतराने adapter मागे शून्य client बदलांसह स्थलांतरित केला जातो.
✅ परिणाम: नवीन वैशिष्ट्ये स्वच्छ interface विरुद्ध बांधली जातात तर जुनी लायब्ररी जोडेमागे शांतपणे refactor किंवा निवृत्त केली जाते.
📚

3 · java.util adapter (Arrays.asList)

पॅटर्न: arrays ला Collections interface शी adapt करणे

Java arrays आणि Collections framework ही वेगळी जगे आहेत; List साठी लिहिलेला कोड कच्चा array घेऊ शकत नाही.

  • Arrays.asList(arr) एक List view परत करतो जो array ला Collections API शी adapt करतो.
  • Iterators, streams, आणि कोणतीही List-वापरणारी method आता अंतर्निहित array वर काम करते.
  • adapter elements copy न करता reads array कडे पुढे पाठवतो.
✅ परिणाम: एक साधा array संपूर्ण Collections परिसंस्थेतून वाहतो, लाखो programs वापरतात असा standard-library Adapter.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Adapter हा सर्वात शांतपणे सर्वव्यापी पॅटर्नांपैकी एक आहे. प्रणाली जसजशा अधिक वितरित आणि बाह्य सेवांवर अधिक अवलंबून होतात, तसतसे भाषांतर स्तर अधिकच सामान्य होतात.

🔌 Hexagonal architecture

Ports आणि adapters म्हणजे Adapter ला architectural शैलीत बढती दिलेली: domain ports परिभाषित करते, आणि adapters त्याला databases, queues आणि APIs शी जोडतात.

🌐 Anti-corruption layers

domain-driven design मधे, adapter हा anti-corruption layer असतो जो दुसऱ्या प्रणालीचे model तुमच्या bounded context मधे झिरपण्यापासून रोखतो.

🤖 LLM tool आणि API bridging

Agent frameworks विषम API एका एकसमान tool interface मागे wrap करतात, प्रत्येक integration मागे एक adapter जेणेकरून model एकाच सुसंगत आकाराला call करतो.

🧱 Framework binding

ORMs, loggers आणि HTTP clients adapters पाठवतात जेणेकरून एक interface (SLF4J, JPA) deploy वेळी निवडलेल्या अनेक ठोस backends समोर उभा राहतो.

🧪 Test doubles

clients Target वर अवलंबून असल्यामुळे, बनावट adapters integration जोड stub करणे सोपे करतात, जलद आणि निर्धारक चाचण्या चालवतात.

🔁 टप्प्याटप्प्याने स्थलांतर

Strangler-fig स्थलांतरे adapters वर विसंबून राहतात जेणेकरून प्रणाली तुकड्या-तुकड्याने बदलली जात असताना जुन्या आणि नवीन अंमलबजावणींमधे मार्ग वळवता येतो.

सारांश: Adapter हा तो सांधा आहे जो स्वतंत्रपणे बांधलेल्या भागांना एकत्र जुळू देतो. जेव्हाही तुम्ही स्वतः न लिहिलेला कोड एकत्रित करता, किंवा तुमच्या ताब्यात नसलेल्या आकारापासून तुमचा गाभा वाचवता, तेव्हा तुम्ही त्याच्याकडे वळता, अनेकदा त्याचे नाव न घेता.
