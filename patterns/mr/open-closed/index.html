Open/Closed तत्त्व - जे आधीच काम करते ते न बदलता नवीन वर्तन जोडा

सॉफ्टवेअर घटक विस्तारासाठी खुले पण बदलासाठी बंद असावेत. जेव्हा एखादा नवीन सवलतीचा नियम, शिपिंग कॅरियर, किंवा पेमेंट पद्धत येते, तेव्हा तुम्ही एक नवीन class जोडता, स्थिर फाइल पुन्हा उघडून वाढत्या switch ला आणखी एक शाखा जोडत नाही. Polymorphism ही तीच यंत्रणा आहे जी हे शक्य करते.

01 - काय

Open/Closed तत्त्व म्हणजे काय?

Open/Closed तत्त्व (SOLID मधील O) असे सांगते की एखाद्या module चे वर्तन त्याचा source कोड बदलल्याशिवाय विस्तारता आले पाहिजे. हे तुम्ही एका abstraction वर, म्हणजे एका स्थिर interface वर अवलंबून राहून साध्य करता, आणि नवीन वर्तन त्या abstraction च्या नवीन implementation च्या रूपात येऊ देता. काम पार पाडणाऱ्या कोडला किती implementation अस्तित्वात आहेत हे कधीच माहीत असण्याची गरज नसते.

🔓 विस्तारासाठी खुले

नवीन गरजा अस्तित्वातील करार पूर्ण करणाऱ्या नवीन class जोडून पूर्ण होतात, त्यामुळे प्रणाली तिच्या कडांवर वाढते.

🔒 बदलासाठी बंद

चाचणी झालेला, पाठवलेला कोड अस्पर्शित राहतो. आणखी एक कॅरियर जोडण्यासाठी तुम्ही checkout गणकातील regression चा धोका पत्करत नाही.

🧩 कराराने बांधलेले

एक interface किंवा abstract base ती जोडणी-रेषा ठरवते. कॉलर त्या रेषेशी प्रोग्राम करतात, कधीच एखाद्या ठोस type शी नाही.

02 - का

OCP का महत्त्वाचे आहे

प्रत्येक वेळी तुम्ही शाखा जोडण्यासाठी एक काम करणारी फाइल पुन्हा उघडता, तेव्हा तिथे आधीच असलेल्या शाखा बिघडवण्याचा धोका तुम्ही पत्करता. OCP तो धोका मुख्य मार्गावरून काढून वेगळ्या, जोडणाऱ्या एककांमध्ये हलवते.

🛡️ कमी regression

जेव्हा प्रत्येक नियम स्वतःच्या चाचण्यांसह स्वतःचा class असतो, तेव्हा दहावा सवलत नियम जोडल्याने बाकीचे नऊ बिघडू शकत नाहीत. स्थिर गाभ्याला कधीच स्पर्श होत नाही.

🔀 छोटे merge conflict

दोन पेमेंट पद्धती जोडणारे दोन संघ त्याच वाढत्या switch विधानावरून भांडण्याऐवजी दोन वेगवेगळ्या फाइल संपादित करतात.

🧪 स्वतंत्रपणे चाचणीयोग्य

प्रत्येक strategy ही एक छोटी वस्तू आहे जिची तुम्ही थेट unit चाचणी करू शकता, एका शाखेपर्यंत पोहोचण्यासाठी संपूर्ण checkout चालू न करता.

🔌 Plugin-अनुकूल

कॅरियर, gateway आणि स्वरूप हे registry द्वारे runtime ला सापडवता येतात, त्यामुळे विस्तार गाभ्याच्या पुनर्तैनातीशिवाय पाठवता येतात.

सोप्या शब्दांत

उपमांसह Open/Closed चे स्पष्टीकरण

तीच कल्पना, चित्रित करण्याचे चार मार्ग, त्यामुळे तुम्ही कोणीही असाल तरी ती लक्षात येते.

🎓 विद्यार्थ्यासाठी

हे एका बहुपर्यायी उत्तरपत्रिकेसारखे आहे. आणखी एक शक्य उत्तर जोडणे म्हणजे आणखी एक गोल छापणे, संपूर्ण प्रश्न आणि प्रत्येक अस्तित्वातील पर्याय पुन्हा टाइप करणे नाही.

👩‍💻 डेव्हलपरसाठी

एका plugin रचनेचा विचार करा. होस्ट interface एकदाच ठरवतो आणि गोठलेला राहतो; प्रत्येक plugin तो interface अंमलात आणून क्षमता जोडतो, आणि होस्टला त्यांची नावेही कधी कळत नाहीत.

🏢 व्यावसायिकासाठी

व्यवस्थित चालणारा मंजुरी workflow: नवीन मंजूरदार भूमिका जोडणे म्हणजे प्रणालीला आधीच समजणारा एक फॉर्म भरणे, routing engine पुन्हा लिहिणे नाही.

🔌 रोजच्या जीवनातील रूप

एक पॉवर स्ट्रिप. नवीन उपकरणाला वीज देण्यासाठी तुम्ही अस्तित्वातील सॉकेटमध्ये प्लग लावता. प्रत्येक वेळी उपकरण विकत घेतल्यावर तुम्ही भिंतीतील वायरिंग पुन्हा करत नाही.

03 - कसे

तुम्ही ते प्रत्यक्षात कसे साध्य करता

बदलाचा अक्ष शोधा, त्याला interface म्हणून नाव द्या, आणि orchestrator ला फक्त त्या interface वर अवलंबून राहू द्या. मग नवीन वर्तन हा एक नवीन class असतो ज्याचे नाव orchestrator ला कधीच माहीत असण्याची गरज नसते.

🎯 abstraction ला नाव द्या

जिथे प्रकार वेगळे होतात ती जोडणी-रेषा ठरवा. checkout साठी ती रेषा म्हणजे PaymentMethod.charge(amount). कॉलर interface धरतात, ठोस gateway नाही.

➕ class जोडून विस्तार करा

एक नवीन पद्धत, PayPal, Klarna, किंवा गिफ्ट कार्ड, हा तोच करार अंमलात आणणारा एक नवीन class असतो. Processor पद्धतींवरून polymorphic पद्धतीने फिरतो आणि type वर कधीच शाखा करत नाही.

// The stable contract. The processor depends only on this.
interface PaymentMethod {
  name(): string;
  charge(amountCents: number): Receipt;
}
interface Receipt { method: string; amountCents: number; ref: string; }

// The orchestrator is CLOSED: it never changes when methods are added.
class CheckoutProcessor {
  pay(order: { totalCents: number }, method: PaymentMethod): Receipt {
    if (order.totalCents <= 0) throw new Error("empty order");
    return method.charge(order.totalCents);
  }
}

// Shipped, tested, frozen.
class CardPayment implements PaymentMethod {
  constructor(private last4: string) {}
  name() { return `card ****${this.last4}`; }
  charge(amountCents: number): Receipt {
    return { method: this.name(), amountCents, ref: `ch_${Date.now()}` };
  }
}

from dataclasses import dataclass
from time import time

@dataclass

    amount_cents: int
    ref: str

# The stable contract.
class PaymentMethod(ABC):
    @abstractmethod
    def name(self) -> str: ...
    @abstractmethod
    def charge(self, amount_cents: int) -> Receipt: ...

# The orchestrator is CLOSED: unchanged as methods are added.
class CheckoutProcessor:
    def pay(self, order, method: PaymentMethod) -> Receipt:
        if order["total_cents"] <= 0:

एक पद्धत type-टॅगवर शाखा करते, आणि प्रत्येक नवीन गरज म्हणजे आणखी एक case. ती फाइल प्रत्येक feature वर संपादित होते.

10
अक्ष

बदलाच्या अक्षाला नाव द्या

काय बदलते ते ओळखा: पेमेंट पद्धत, कॅरियर, सवलत नियम. तो बदल हेच तुमचे भविष्यातील abstraction आहे.

20
करार

interface ठरवा

जोडणी-रेषा एकदाच लिहा: charge(amount), price(weight, zone). ती कमीत कमी आणि वर्तन-केंद्रित ठेवा.

30
काढणे

प्रत्येक शाखा एका class मध्ये हलवा

प्रत्येक case चा भाग करार अंमलात आणणारा एक छोटा class होतो. वर्तन जपले जाते, फक्त जागा बदलते.

40
उलटवणे

abstraction वर अवलंबून राहा

orchestrator आता interface ला parameter म्हणून स्वीकारतो आणि एक polymorphic पद्धत कॉल करतो. switch काढून टाकला जातो.

50
चाचणी

प्रत्येक strategy ची unit चाचणी करा

प्रत्येक class ला नेमक्या चाचण्या मिळतात. एका शाखेची कसोटी घेण्यासाठी तुम्हाला यापुढे संपूर्ण pipeline ची गरज नाही.

60
नोंदणी

निवड कडेला जोडा

एक registry किंवा factory input ला योग्य class शी एकाच ठिकाणी जोडते, त्यामुळे runtime निवड ही data असते, control flow नाही.

70
गोठवा

गाभा बंद करा

orchestrator पूर्ण झाला. अकरावा प्रकार आल्यावर तो संपादित होणार नाही. हा "बंद" अर्धा भाग आहे.

80
विस्तार

पुढचा प्रकार जोडा

नवीन कॅरियर म्हणजे एक नवीन class आणि एक registry नोंद. अस्तित्वातील कोणतीही फाइल उघडली जात नाही. हा "खुला" अर्धा भाग आहे.

90
सावधानी

अति-abstraction पासून सावध राहा

जे अक्ष कधीच बदलत नाहीत त्यांच्यासाठी interface जोडू नका. दोन स्थिर प्रकरणे क्वचितच plugin framework चे समर्थन करतात.

100
पाठवा

कडांवर वाढा

आता features जोडणाऱ्या class च्या रूपात येतात. प्रत्येक बदलाची परिणाम-व्याप्ती एक नवीन फाइल असते, आणि चाचणी झालेला गाभा हिरवा राहतो.

सामान्य धोके

धोके आणि विरोधी-नमुने

OCP अति करणे सोपे आहे आणि बनावट दाखवणेही सोपे आहे. हे नेहमीचे अपयश आहेत.

🔮 काल्पनिक abstraction

"आणखी जोडल्यास" म्हणून एकाच पेमेंट पद्धतीसाठी plugin प्रणाली बनवणे. अकाली interface कोणताही फायदा न देता अप्रत्यक्षपणा जोडतात आणि हीच सर्वात सामान्य OCP चूक आहे.

🕵️ लपलेला switch-on-type

processor च्या आत switch च्या जागी if isinstance(m, CardPayment) ठेवणे. तुम्ही शाखा हलवली, ती काढली नाही. गाभा अजूनही बंद नाही.

🧱 गळका interface

पेमेंट करारावरील getStripeToken() सारखे ठोस तपशील उघड करणारे abstraction कॉलरना विशेष प्रकरण हाताळायला भाग पाडते आणि जोडणी-रेषा निष्फळ करते.

💥 जाडजूड base class

abstract base मध्ये सामायिक तर्क इतका भरणे की subclass ला त्यातील अर्धा override करावा लागतो. त्या coupling चा अर्थ नवीन प्रकार अजूनही सामायिक कोड संपादित करतात.

🚪 मागच्या दाराने बदल

वर्तन दुभंगवण्यासाठी अस्तित्वातील class ला एक boolean flag जोडणे. हा बदल आहे, विस्तार नाही, आणि तो संयोगात्मकपणे वाढतो.

🗺️ संपादित करावा लागणारा registry

जर प्रत्येक नवीन class साठी एक मध्यवर्ती नकाशा हाताने संपादित करावा लागत असेल, तर तो नकाशा हाच नवीन switch बनतो. स्वयं-नोंदणी किंवा dependency injection ला प्राधान्य द्या.

संकेत आणि मापदंड

संकेत आणि कसे मोजायचे

तुम्ही OCP वर एकच आकडा लावू शकत नाही, पण हे संकेत तुम्हाला सांगतात की एखादे module खरोखर बदलासाठी बंद आहे का.

संकेततो तुम्हाला काय सांगतो
प्रत्येक नवीन प्रकारासाठी स्पर्श झालेल्या फाइलजर कॅरियर जोडल्याने गणक संपादित होतो, तर गाभा बंद नाही. आदर्शतः तो एक नवीन फाइल आणि एक जोडणी ओळ असावी.
orchestrator वरील churn"स्थिर असावी" अशा dispatch फाइलवर वारंवार commit होणे हे वाढत राहणाऱ्या switch कडे निर्देश करते.
dispatch ची cyclomatic complexityएका पद्धतीत वाढणारी शाखांची संख्या हे संख्यात्मक रूपातील switch-on-type चा वास आहे.
गाभ्यातील type तपासण्याorchestration कोडमधील instanceof / isinstance / is_a? मोजा. शून्यापेक्षा जास्त म्हणजे सहसा abstraction गळते.
चाचणीची परिणाम-व्याप्तीजर नवीन प्रकारामुळे अस्तित्वातील चाचण्या संपादित कराव्या लागत असतील, तर वर्तन खरोखर वेगळे केलेले नव्हते.
एकच implementation असलेले interfaceअनेक एकल-वापर abstraction हे अति-अभियांत्रिकीचे संकेत देतात: कोणीही न वापरणाऱ्या विस्तार-बिंदूंसाठी तुम्ही पैसे मोजले.
अंगठ्याचा नियम: एखादा अक्ष खरोखर बदलतो त्या पहिल्या वेळी नाही तर दुसऱ्या किंवा तिसऱ्या वेळी OCP लागू करा. डुप्लिकेशन हे चुकीच्या abstraction पेक्षा स्वस्त असते; बदल अंदाजित नसून सिद्ध झाल्यावर जोडणी-रेषा जोडा.
06 - उदाहरण अभ्यास

वास्तविक जगातील उदाहरण अभ्यास

तीन उत्पादन-शैलीच्या प्रणाली जिथे बदलाशिवाय विस्तार ही भार पेलणारी रचना आहे.

💳

1 · plug करण्यायोग्य पेमेंट पद्धतींसह checkout

नमुना: स्थिर processor मागे strategy

एक marketplace कार्ड, wallet, buy-now-pay-later, आणि store credit आधार देते, आणि नवीन पद्धती अनेकदा जोडते.

  • प्रत्येक पद्धत charge आणि refund सह PaymentMethod करार अंमलात आणते.
  • checkout processor आणि order state machine गोठलेले असतात; ते फक्त interface बोलतात.
  • Klarna जोडणे म्हणजे एक नवीन class आणि एक registry नोंद, checkout ला स्पर्श न करता पाठवलेले.
✅ निष्कर्ष: नवीन पेमेंट पद्धती वेगळे, चाचणी झालेले class म्हणून उत्पादनात पोहोचतात, आणि गाभ्यातील checkout कित्येक महिन्यांत regression साठी पुन्हा उघडले गेले नाही.
🚚

2 · कॅरियरांमधील शिपिंग-खर्च गणक

नमुना: प्रत्येक कॅरियरसाठी rate strategy

एक लॉजिस्टिक्स प्लॅटफॉर्म अनेक कॅरियरांकडून दर देते, प्रत्येकाचे स्वतःचे वजन, झोन, आणि अधिभार नियम असतात.

  • एक ShippingRate interface price(weight, zone) उघड करते; प्रत्येक कॅरियर हा एक implementation आहे.
  • quoting engine नोंदणी झालेल्या दरांवरून फिरते आणि सर्वात स्वस्त निवडते, प्रत्येक कॅरियरसाठी शाखा न करता.
  • एका प्रादेशिक courier ला engine startup ला सापडणारा एक class टाकून सामील केले जाते.
✅ निष्कर्ष: कॅरियर एकत्रीकरणे संघांमध्ये समांतर करता आली, कारण प्रत्येक एक सामायिक गणकातील बदल नसून जोडणारी strategy आहे.
🏷️

3 · plug करण्यायोग्य सवलत आणि प्रचार नियम

नमुना: जोडता येणारी rule pipeline

एक किरकोळ प्लॅटफॉर्म एकावर एक प्रचार चालवते: loyalty स्तर, coupon, bundle सौदे, आणि flash sale.

  • प्रत्येक प्रचार हा चालू subtotal वर क्रमाने लागू केलेला एक DiscountRule आहे.
  • Marketing कोणते नियम सक्रिय आहेत हे data म्हणून ठरवते; pricing गाभा कधीच बदलत नाही.
  • हंगामी नियम एक class म्हणून जोडला जातो आणि config ने सक्रिय केला जातो, नंतर मोहीम संपल्यावर स्वच्छपणे काढला जातो.
✅ निष्कर्ष: मोहिमा pricing तर्कात अभियांत्रिकी बदलाशिवाय marketing च्या वेगाने पाठवल्या जातात, आणि कालबाह्य प्रचार switch मध्ये कोणतीही जखम न ठेवता काढले जातात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

OCP आजच्या बहुतांश stack च्या आधीचे आहे, पण जिथे विस्तारक्षमता हे एक feature आहे तिथे त्याचा आकार सर्वत्र दिसतो.

🔌 Plugin परिसंस्था

Editor, CI runner, आणि पेमेंट SDK एक interface उघड करतात आणि तिसऱ्या पक्षांना होस्ट fork न करता वर्तन विस्तारू देतात.

🎛️ Feature flag आणि strategy

flag मागे algorithm अदलाबदल करणे हे प्रत्यक्षात OCP आहे: कॉलर बंद असतो, strategy जोडणीसाठी खुल्या असतात.

🧩 Dependency injection

Framework implementation ला runtime ला एका स्थिर गाभ्यात जोडतात, त्यामुळे विस्तार म्हणजे configuration असते, कोड शस्त्रक्रिया नाही.

☁️ Serverless handler

नवीन event type म्हणजे एका स्थिर router विरुद्ध नोंदणी झालेला एक नवीन handler, मध्यवर्ती dispatch फंक्शनमधील बदल नाही.

🤖 tool वापरणारे agent

agent ला नवीन क्षमता देणे म्हणजे एका निश्चित कॉलिंग प्रोटोकॉल विरुद्ध आणखी एक tool नोंदवणे, हा थेट OCP आकार आहे.

⚖️ YAGNI ची प्रतिशक्ती

आधुनिक पद्धत OCP ला "you are not gonna need it" शी जोडते: जोडणी-रेषा हुंकाराने नाही तर बदल खरा असल्यावर जोडा.

सारांश: OCP हा सर्वत्र लागू करण्याचा नियम नाही; तो खरोखर बदलणाऱ्या अक्षांसाठीचे साधन आहे. तिथे वापरल्यास, तो एका प्रणालीला तिचा चाचणी झालेला गाभा पुन्हा न उघडता वर्षानुवर्षे वाढू देतो. सर्वत्र वापरल्यास, तो तुम्हाला कोणालाही न लागणाऱ्या interface मध्ये बुडवतो.
