Structural Pattern

Decorator पॅटर्न - subclassing न करता गुंडाळून वर्तन जोडा

Decorator तुम्हाला एखाद्या ऑब्जेक्टला रनटाइममध्ये नवीन जबाबदाऱ्या जोडू देतो, त्याच interface शेअर करणाऱ्या दुसऱ्या ऑब्जेक्टमध्ये त्याला गुंडाळून. कारण wrapper तो ज्याला गुंडाळतो तोच type अंमलात आणतो, म्हणून तुम्ही decorators कोणत्याही क्रमाने एकावर एक रचू शकता आणि प्रत्येक एक वर्तनाचा एक तुकडा जोडतो. java.io हे असेच एका कच्च्या stream ला buffered, compressed, data-typed stream मध्ये बदलते, प्रत्येक संयोजनासाठी एकही नवीन subclass न लिहिता.

01 - काय

Decorator पॅटर्न म्हणजे काय?

Decorator हा एक structural पॅटर्न आहे जो तुम्हाला एका स्वतंत्र ऑब्जेक्टला डायनॅमिकपणे जबाबदाऱ्या जोडू देतो. तुम्ही लक्ष्य ऑब्जेक्टला एका decorator ऑब्जेक्टमध्ये गुंडाळता जो तोच interface अंमलात आणतो, गुंडाळलेल्या ऑब्जेक्टकडे calls पुढे पाठवतो, आणि प्रत्येक पुढे पाठवलेल्या call च्या आधी, नंतर किंवा आजूबाजूला वर्तन जोडतो. wrapper आणि गुंडाळलेला दोघे एकच type शेअर करत असल्याने, client कोडला फरक कळत नाही आणि decorators थरांमध्ये रचता येतात.

🧩 एकच interface

Decorator तो ज्या ऑब्जेक्टला गुंडाळतो त्याचाच नेमका interface अंमलात आणतो, म्हणून जिथे base type अपेक्षित असतो तिथे तो थेट बदली म्हणून वापरता येतो.

🎁 एका component ला गुंडाळतो

तो एका गुंडाळलेल्या component चा reference धरून ठेवतो आणि त्याकडे delegate करतो, delegate केलेल्या call च्या आजूबाजूला स्वतःचे वर्तन जोडतो.

🥞 थरांमध्ये रचतो

एक decorator दुसऱ्या decorator ला गुंडाळू शकतो, म्हणून जबाबदाऱ्या कांद्याच्या थरांप्रमाणे एकत्र येतात, प्रत्येक स्वतंत्रपणे जोडलेला.

02 - का

Decorator का अस्तित्वात आहे

तो जी समस्या नष्ट करतो ती म्हणजे subclass स्फोट. जर तुम्ही inheritance ने प्रत्येक ऐच्छिक वैशिष्ट्याच्या प्रत्येक संयोजनाचे मॉडेल करण्याचा प्रयत्न केला, तर classes ची संख्या संयोजनात्मकपणे वाढते. Decorator प्रत्येक वैशिष्ट्याला एक लहान wrapper बनवतो जो तुम्ही रनटाइममध्ये मुक्तपणे मिसळता.

💥 subclass स्फोट नष्ट करतो

Inheritance मार्गे तीन वैशिष्ट्ये म्हणजे प्रत्येक संयोजनासाठी एक class: Buffered, Compressed, BufferedCompressed, आणि असेच. decorators सोबत तुम्ही तीन wrappers लिहिता आणि त्यांना एकत्र करता, म्हणून N वैशिष्ट्यांना N classes लागतात, 2 च्या घात N नव्हे.

🔓 Open/Closed पाळतो

तुम्ही base class किंवा विद्यमान decorators ला हात न लावता क्षमता जोडता. नवीन वर्तन नवीन wrapper म्हणून येते, म्हणून चाचणी केलेला कोड बदलासाठी बंद पण विस्तारासाठी खुला राहतो.

🎚️ प्रति-ऑब्जेक्ट, रनटाइममध्ये

एकाच class च्या दोन instances कडे वेगवेगळे decorators असू शकतात. compile time ला नव्हे, तर configuration, user input किंवा request context नुसार तुम्ही stack ठरवता.

🎯 एकच जबाबदारी

प्रत्येक decorator एकच गोष्ट करतो: buffer, compress, encrypt, log. प्रत्येक ऐच्छिक चिंता सांभाळणाऱ्या एका class पेक्षा लहान, केंद्रित classes चाचणी करणे आणि समजणे सोपे असते.

सोप्या शब्दांत

उपमांसह Decorator चे स्पष्टीकरण

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

कपड्यांच्या थरांचा विचार करा. माणूस स्वेटर, मग कोट, मग स्कार्फ घातला तरी माणूसच राहतो. प्रत्येक थर माणूस काय आहे ते न बदलता उब जोडतो, आणि तुम्ही गरजेनुसार थर जोडता किंवा काढता.

👩‍💻 डेव्हलपरसाठी

ते म्हणजे new BufferedInputStream(new FileInputStream(f)). प्रत्येक constructor तोच interface घेतो जो तो परत करतो, म्हणून गुंडाळणे म्हणजे फक्त घरटी करणे, आणि प्रत्येक थर अजूनही InputStream ला प्रतिसाद देतो.

🏢 व्यावसायिकासाठी

मंजुरीच्या शिक्क्यांमधून जाणाऱ्या दस्तऐवजासारखे. दस्तऐवज अपरिवर्तित असतो, पण प्रत्येक टेबल त्याला शिक्का, कव्हर नोट किंवा redaction ने गुंडाळते. पुढे अजूनही एक "दस्तऐवज" हाताळला जातो, आता त्यावर अतिरिक्त हाताळणी लागू केलेली.

☕ रोजच्या जीवनातील आवृत्ती

कॉफीची ऑर्डर. तुम्ही espresso ने सुरुवात करता, मग दूध जोडता, मग caramel, मग whipped cream. प्रत्येक add-on पेयाला गुंडाळतो आणि किंमत व वर्णनात भर घालतो, पण ते अजूनही ग्राहकाला देता येणारे पेयच असते.

03 - कसे

ते आतून कसे काम करते

एक decorator त्याच interface च्या component चा reference धरतो, मुख्य call त्याकडे delegate करतो, आणि त्या delegation च्या आजूबाजूला वर्तन जोडतो. रचना कार्य करते कारण एका decorator चे गुंडाळलेले field स्वतः दुसरा decorator असू शकते.

🔁 Delegate करा मग जोडा

प्रत्येक method सहसा wrapped.method() ला call करतो आणि आधी किंवा नंतर काम जोडतो. गुंडाळलेला reference तोच type असतो, म्हणून call साखळी खालपर्यंत एकसमान असते.

🥞 क्रम महत्त्वाचा

compress-मग-buffer गुंडाळणे हे buffer-मग-compress पेक्षा वेगळे वागते. सर्वात बाहेरचा decorator त्याचे "आधीचे" काम प्रथम आणि "नंतरचे" काम शेवटी चालवतो, stack उलगडल्यासारखे.

Java मधील एक वास्तववादी उदाहरण

// Component: the shared interface
interface DataSource {
    void writeData(String data);
    String readData();
}

// Concrete Component: does the real work
class FileDataSource implements DataSource {
    private final String path;
    FileDataSource(String path) { this.path = path; }
    public void writeData(String data) { /* write raw bytes to file */ }
    public String readData()          { /* read raw bytes from file */ return "..."; }
}

// Base Decorator: implements the interface, forwards to the wrappee
abstract class DataSourceDecorator implements DataSource {
    protected final DataSource wrappee;
    DataSourceDecorator(DataSource source) { this.wrappee = source; }
    public void writeData(String data) { wrappee.writeData(data); }
    public String readData()           { return wrappee.readData(); }
}

// Concrete Decorator: adds behavior around the forwarded call
class CompressionDecorator extends DataSourceDecorator {
    CompressionDecorator(DataSource source) { super(source); }
    public void writeData(String data) { wrappee.writeData(compress(data)); }
    public String readData()           { return decompress(wrappee.readData()); }
    private String compress(String s)   { /* deflate */ return s; }
    private String decompress(String s) { /* inflate */ return s; }
}

class EncryptionDecorator extends DataSourceDecorator {
    EncryptionDecorator(DataSource source) { super(source); }
    public void writeData(String data) { wrappee.writeData(encrypt(data)); }
    public String readData()           { return decrypt(wrappee.readData()); }
    private String encrypt(String s) { /* cipher */ return s; }
    private String decrypt(String s) { /* decipher */ return s; }
}

// Client: composes the stack at runtime, then uses the base interface
DataSource source = new EncryptionDecorator(
                        new CompressionDecorator(
                            new FileDataSource("out.dat")));
source.writeData("salary report");   // compresses, then encrypts, then writes
String plain = source.readData();     // reads, decrypts, then decompresses

Client ला फक्त DataSource दिसतो. लिहिणे stack ला बाहेरून आत चालवते (encrypt compress ला गुंडाळते, compress file ला गुंडाळते); वाचणे ते आतून बाहेर उलगडते. एखादी नवीन चिंता, समजा LoggingDecorator, कोणतीही विद्यमान class न बदलता जोडा.

00
Interface

Component व्याख्या करा

खरे ऑब्जेक्ट आणि प्रत्येक decorator दोघेही अंमलात आणतील तो शेअर केलेला interface घोषित करा, उदाहरणार्थ read आणि write सह DataSource.

10
Base

Concrete Component बांधा

खरे काम करणारी class लिहा, जसे FileDataSource. हेच केंद्रात बसते आणि गुंडाळले जाते.

20
Wrapper

Base Decorator तयार करा

interface अंमलात आणणारा, त्याच type चे wrappee field धरणारा, आणि प्रत्येक call अपरिवर्तित त्याकडे पुढे पाठवणारा एक abstract decorator बनवा.

30
वर्तन

Concrete Decorator जोडा

base decorator ला subclass करा आणि delegate करण्यापूर्वी किंवा नंतर काम जोडण्यासाठी एका method ला override करा, जसे write वर compress करणे आणि read वर decompress करणे.

40
वर्तन

अधिक decorators जोडा

इतर चिंतांसाठी स्वतंत्र wrappers लिहा: encryption, logging, buffering. प्रत्येक लहान राहतो आणि इतरांबद्दल काहीही जाणत नाही.

50
रचा

रनटाइममध्ये गुंडाळा

Client stack बांधण्यासाठी constructors घरटी करतो, उदाहरणार्थ file source भोवती compression, त्या भोवती encryption, क्रम जाणीवपूर्वक निवडून.

60
Call

interface मार्गे invoke करा

Client सर्वात बाहेरच्या ऑब्जेक्टला फक्त DataSource type वापरून call करतो, खाली किती थर आहेत याबद्दल अनभिज्ञ.

70
खाली

stack खाली delegate करा

प्रत्येक decorator त्याचे "आधीचे" काम लागू करतो आणि त्याच्या wrappee कडे पुढे पाठवतो, म्हणून call बाहेरून आत प्रवास करतो जोपर्यंत तो concrete component पर्यंत पोहोचत नाही.

80
वर

निकाल उलगडा

Concrete component परत येतो, आणि प्रत्येक decorator परत वर येताना त्याचे "नंतरचे" काम लागू करतो, गुंडाळण्याच्या उलट क्रमाने.

90
विस्तार

संपादन न करता वैशिष्ट्ये जोडा

एक नवीन आवश्यकता stack मध्ये घातलेला नवीन decorator बनते. विद्यमान classes कधीही बदलल्या जात नाहीत, Open/Closed पाळत.

100
Ship

प्रति context stacks configure करा

वेगवेगळ्या requests किंवा configs त्याच बांधकाम ब्लॉक्समधून वेगवेगळ्या साखळ्या जुळवतात, म्हणून नवीन classes शिवाय प्रति ऑब्जेक्ट वर्तन बदलते.

सामान्य धोके

धोके आणि anti-patterns

Decorator शक्तिशाली आहे पण अतिवापर करणे सोपे आहे. हे नेहमीचे सापळे आहेत.

🧅 खूप लहान थर

दहा wrappers खोल असलेली stack वाचणे आणि debug करणे कठीण असते. stack trace पुढे पाठवणाऱ्या calls ची भिंत बनते. संयोजने खरोखर बदलतात तेव्हाच Decorator कडे वळा, प्रत्येक पर्यायासाठी नव्हे.

🔀 क्रम-संवेदनशीलतेकडे दुर्लक्ष

compress-मग-encrypt आणि encrypt-मग-compress वेगवेगळे निकाल देतात, आणि एखादे कदाचित चालणारही नाही. गुंडाळण्याचा क्रम अपघात नव्हे तर करारचा भाग माना.

🪪 concrete type गळणे

जर clients एका decorator च्या अतिरिक्त method पर्यंत पोहोचण्यासाठी downcast करतात, तर substitutability तुटते. Decorators ने शेअर केलेल्या interface मार्गे वर्तन जोडावे, clients अवलंबून असलेल्या रुंद interface मार्गे नव्हे.

🧬 फुगीर base interface

अनेक methods असलेला component interface प्रत्येक decorator ला त्या सर्वांना पुढे पाठवण्यास भाग पाडतो. interface लहान ठेवा म्हणजे wrappers पातळ राहतात, नाहीतर delegation boilerplate ताबा घेते.

🆔 identity आणि equals सापळे

गुंडाळलेला ऑब्जेक्ट त्याच्या wrapper ला == नसतो, आणि equals किंवा hashing थरांमध्ये अनपेक्षितपणे वागू शकते. decorator साखळीतून ऑब्जेक्ट identity वर अवलंबून राहू नका.

🎭 Strategy बसते तिथे तो वापरणे

जर तुम्ही अनेक add-ons थरणे नव्हे तर एक algorithm बदलत असाल, तर Strategy सोपा आहे. जबाबदाऱ्या खरोखर एकावर एक रचल्या जातात तेव्हाच Decorator चमकतो.

तडजोडी

तडजोडी आणि केव्हा वापरावे

Decorator सपाट class श्रेणीबद्धतेच्या बदल्यात रनटाइम लवचिकता आणि थोडी indirection देतो. हे ताळेबंद आहे.

पैलूतपशील
फायदेप्रति ऑब्जेक्ट रनटाइममध्ये वर्तन जोडतो, मुक्तपणे रचतो, subclass स्फोट टाळतो, प्रत्येक चिंता लहान class मध्ये ठेवतो, आणि Open/Closed पाळतो.
तोटेअनेक लहान ऑब्जेक्ट आणि खोल stacks वाचनीयता आणि debugging ला त्रास देतात; क्रम संवेदनशीलता हा एक लपलेला करार आहे; interface सोबत पुढे पाठवण्याचे boilerplate वाढते.
केव्हा वापरावेजबाबदाऱ्या ऐच्छिक आणि एकत्र करता येण्यासारख्या असतात, तुम्हाला त्या रनटाइममध्ये प्रति ऑब्जेक्ट जोडाव्या किंवा काढाव्या लागतात, किंवा inheritance संयोजनात्मक class स्फोट निर्माण करेल.
केव्हा टाळावेतुम्ही एकच algorithm बदलत असाल (Strategy वापरा), एका ऑब्जेक्टचा access नियंत्रित करत असाल (Proxy वापरा), किंवा वैशिष्ट्यांचा संच निश्चित व लहान असेल (साधे inheritance ठीक आहे).
गुंतागुंतप्रति decorator कमी, पण stack खोलीसह एकूण मानसिक भार वाढतो. एक शेअर केलेला interface आणि शिस्तबद्ध delegation आवश्यक.
संबंधितProxy (तोच interface, वर्तन नव्हे access नियंत्रित करतो), Composite (तोच-interface ऑब्जेक्टचे झाड), Adapter (interface बदलतो), Strategy (algorithm बदलतो).
अंगठ्याचा नियम: जर तुम्ही स्वतःला वैशिष्ट्यांच्या संयोजनांच्या नावाच्या classes तयार करताना पकडता (BufferedCompressedEncrypted...), तर थांबा आणि Decorator कडे वळा. जर तुम्हाला एका वेळी फक्त एकच पर्याय लागत असेल, तर तुम्हाला बहुधा त्याची अजिबात गरज नाही.
06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

तुम्ही बहुधा आधीच वापरत असलेल्या कोडमध्ये Decorator पॅटर्न दिसतो अशी तीन ठिकाणे.

📄

1 · Java I/O streams

पॅटर्न: प्रमाणित Decorator श्रेणीबद्धता

java.io package हे पाठ्यपुस्तकातील उदाहरण आहे. InputStream हा component, FileInputStream हा concrete component, FilterInputStream हा base decorator, आणि उर्वरित concrete decorators आहेत.

  • new BufferedInputStream(new GZIPInputStream(new FileInputStream(f))) कच्च्या file reads वर decompression आणि त्यावर buffering थरते.
  • प्रत्येक wrapper अजूनही एक InputStream आहे, म्हणून stream वाचणारा कोणताही कोड कोणत्याही संयोजनासह काम करतो.
  • त्याशिवाय, JDK ला प्रत्येक वैशिष्ट्य संयोजनासाठी एक class लागेल, जो नेमका तोच स्फोट आहे जो Decorator प्रतिबंधित करतो.
✅ परिणाम: मूठभर stream classes शेकडो उपयुक्त pipelines मध्ये एकत्र येतात, सर्व एका InputStream interface मार्गे.
🌐

2 · HTTP middleware आणि filters

पॅटर्न: request handlers गुंडाळणे

Web frameworks एका request handler ला थरांमध्ये गुंडाळतात: logging, authentication, compression, caching. प्रत्येक थर handler interface शेअर करतो आणि पुढच्याकडे पुढे पाठवतो.

  • एक auth decorator token तपासतो, मग वैध असेल तरच गुंडाळलेल्या handler कडे delegate करतो.
  • एक gzip decorator प्रथम delegate करतो, मग आतील handler ने तयार केलेला response compress करतो.
  • टीम्स मुख्य handler ला हात न लावता, प्रति route किंवा प्रति app, middleware पुन्हा क्रमबद्ध करतात किंवा जोडतात.
✅ परिणाम: प्रत्येक handler मधील गुंतागुंतीच्या कोडऐवजी cross-cutting चिंता एकत्र करता येणारे, पुन्हा क्रमबद्ध करता येणारे wrappers बनतात.
☕

3 · UI components आणि notifiers

पॅटर्न: ऐच्छिक दृश्य किंवा channel add-ons थरणे

एक UI toolkit एका widget ला borders, scrollbars, आणि shadows ने गुंडाळते; एक notifier एका base sender ला Slack, SMS, आणि email channels ने गुंडाळतो, सर्व एका interface मार्गे.

  • एक ScrollDecorator कोणत्याही component ला गुंडाळतो आणि तो जे रेंडर करतो त्याभोवती scrollbars रंगवतो.
  • एक SlackDecorator Slack ला पाठवतो, मग delegate करतो म्हणजे गुंडाळलेला notifier देखील चालतो.
  • Users रनटाइममध्ये configuration मधून कोणत्या सजावटी किंवा channels रचायचे ते निवडतात.
✅ परिणाम: एक base ऑब्जेक्ट आणि काही decorators users मागणी करतात ते प्रत्येक संयोजन डायनॅमिकपणे निवडून कव्हर करतात.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Decorator संग्रहालयातील वस्तूपासून खूप दूर आहे. तो आधुनिक stacks मध्ये middleware, aspect-oriented चिंता, आणि language वैशिष्ट्यांचा पाया आहे.

🧵 Middleware pipelines

Express, ASP.NET, gRPC interceptors, आणि servlet filters हे सर्व Decorator आहेत: प्रत्येक थर पुढच्या handler ला गुंडाळतो आणि call च्या आजूबाजूला एक चिंता जोडतो.

🎀 Language decorators

Python आणि TypeScript decorators आणि proxies सह Java annotations तीच कल्पना लागू करतात, व्याख्या वेळी एका function किंवा class ला जोडलेल्या वर्तनाने गुंडाळून.

🧷 Functional wrapping

एक function घेऊन गुंडाळलेले परत करणारी higher-order functions, जसे memoize किंवा retry, classes शिवाय व्यक्त केलेले Decorator आहेत.

🔭 Observability

Tracing आणि metrics libraries clients आणि repositories ला तोच-interface decorators मध्ये गुंडाळतात म्हणजे instrumentation business logic बाहेर राहते.

🛡️ Resilience layers

Retry, circuit breaker, rate limit, आणि cache decorators एका service call भोवती रचतात, प्रत्येक प्रति dependency स्वतंत्रपणे toggle केलेला.

🧪 Test doubles

Spies आणि recording wrappers calls पाहण्यासाठी एका खऱ्या ऑब्जेक्टला सजवतात तरीही delegate करत राहतात, चाचण्या production वर्तनाजवळ ठेवत.

सारांश: Decorator हे असे आहे की तुम्ही एका ऑब्जेक्टला रनटाइममध्ये त्याला पुन्हा न लिहिता किंवा तुमची class श्रेणीबद्धता न फुगवता ऐच्छिक, रचता येणारे वर्तन जोडता. जेव्हाही चिंतांना मुक्तपणे एकत्र यायचे असते, तेव्हा गुंडाळणे subclassing पेक्षा सरस असते.
