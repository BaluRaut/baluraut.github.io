Single Responsibility Principle - बदलण्याचे एकच कारण

एका class ला एकच, आणि फक्त एकच, बदलण्याचे कारण असावे. जेव्हा एखादा Invoice स्वतःचे स्वरूप ठरवतो, स्वतःला ईमेल करतो आणि स्वतःला database मध्ये साठवतो, तेव्हा तीन असंबंधित शक्ती एकाच कोडवर ओढाताण करतात. SRP त्या god class ला केंद्रित collaborators मध्ये विभागते, त्यामुळे प्रत्येक भाग स्वतःच्या कारणासाठी बदलतो, आणखी कशासाठीही नाही.

कोड पहा आकृत्यांकडे जा
बदलण्याचे एकच कारण उच्च cohesion concerns चे विभाजन केंद्रित collaborators
01 - काय

Single Responsibility Principle म्हणजे काय?

SRP हे SOLID मधील "S" आहे. Robert C. Martin यांचे नेमके शब्द असे आहेत की एका module ला बदलण्याचे एकच कारण असावे, जिथे बदलण्याचे कारण एका actor किंवा stakeholder शी जुळते. जो billing Invoice totals मोजतो, PDF बनवतो, ईमेल पाठवतो आणि Postgres मध्ये लिहितो, तो चार वेगवेगळ्या actors ना उत्तरदायी असतो: finance, design, mail platform team आणि DBA. यातील कोणीही एक बदल करायला भाग पाडू शकतो, त्यामुळे तो class कधीच स्थिर नसतो.

🎯 बदलण्याचे एकच कारण

Responsibility म्हणजे एका actor च्या मालकीचा बदलाचा axis. कोड अशा प्रकारे गटबद्ध करा की एक व्यावसायिक बदल एकाच class ला स्पर्श करेल.

🧲 उच्च cohesion

एका class मधील सर्व काही एकाच उद्देशासाठी कार्य करते. Fields आणि methods एकत्र असतात कारण ते एकच काम करतात, पाच नव्हे.

🪓 concerns चे विभाजन

Formatting, transport आणि persistence हे वेगळे concerns आहेत. प्रत्येकाला स्वतःचा collaborator द्या जेणेकरून ते स्वतंत्रपणे विकसित होतील.

एका god class मध्ये लपलेल्या responsibilities

Responsibilityबदल कोण मागतो (actor)कुठे असावी
Totals आणि tax मोजणेFinance / accounting नियमInvoice domain object
PDF / HTML मध्ये render करणेDesign आणि brand teamInvoiceRenderer
ग्राहकाला पाठवणेMessaging / deliverability teamInvoiceMailer
Storage मध्ये persist करणेDBA / infrastructureInvoiceRepository
Workflow orchestrate करणेProduct / use caseBillingService
मुख्य मानसिक प्रतिमा: SRP म्हणजे "प्रत्येक class ला एकच method" किंवा "सर्व काही छोटे करा" असे नाही. ते audience बद्दल आहे. विचारा की बदल कोण मागेल आणि का. जर दोन उत्तरे दोन वेगवेगळ्या teams ची नावे घेत असतील, तर त्या दोन responsibilities आहेत आणि त्यांना दोन classes हव्या आहेत.
02 - का

SRP का महत्त्वाचे आहे

एक god class असंबंधित बदलाच्या कारणांना एकत्र जोडतो. PDF layout ला स्पर्श करा आणि tax गणित मोडण्याचा धोका येतो; mail provider बदला आणि domain पुन्हा compile करावा लागतो. SRP त्या शक्ती वेगळ्या ठेवते जेणेकरून बदल स्वस्त आणि स्थानिक राहतो.

🛡️ बदलाचे विलगीकरण

जेव्हा mail vendor SMTP वरून provider API कडे बदलतो, तेव्हा फक्त InvoiceMailer हलतो. Totals logic आणि database कोड diff मध्ये कधीच उघडत नाहीत, त्यामुळे blast radius कमी होतो.

🧪 Testability

कोणतेही I/O नसलेला शुद्ध Invoice साध्या assertions ने test केला जातो, database किंवा SMTP stub शिवाय. Persistence आणि mail त्यांच्या स्वतःच्या seams मागे fakes वापरून test केले जातात.

🔁 पुनर्वापर

तोच InvoiceRenderer ईमेल, ग्राहक portal download आणि रात्रीच्या batch export ला सेवा देतो. एका god class मध्ये बंदिस्त असते, तर ती rendering logic कधीच पुनर्वापरता आली नसती.

👥 समांतर काम

Responsibilities teams शी जुळत असल्याने, design team rendering संपादित करते तर DBA queries tune करतो, एका 900-ओळींच्या फाईलवर merge conflicts न होता.

सोप्या शब्दांत

उपमांसह SRP समजावून

तीच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ते पटकन समजेल.

🎓 विद्यार्थ्यासाठी

एक अभ्यास गट जिथे एक जण notes घेतो, एक जण खोली bookिंग करतो, एक जण handouts ची photocopy काढतो. जर copier बिघडला, तर फक्त handout वाली व्यक्ती अडकते. एकाच सदस्याला तिन्ही कामे द्या आणि प्रत्येक अडचण संपूर्ण गटाला थांबवते.

👩‍💻 developer साठी

तुमच्या Order class ने Stripe कडे socket उघडणे आणि SQL लिहिणेही करू नये. domain object शुद्ध ठेवा आणि payment व persistence त्याच्यासोबत सहकार्य करणाऱ्या PaymentGateway आणि OrderRepository मध्ये टाका.

🏢 व्यावसायिकासाठी

एका कंपनीत finance, legal आणि shipping साठी वेगवेगळे विभाग असतात. shipping clerk ने tax law पुन्हा लिहावी असे कुणालाही नको. विभाग म्हणजे responsibilities: प्रत्येक स्वतःच्या boss खाली स्वतःच्या कारणासाठी बदलतो.

🍽️ रोजच्या जीवनातील आवृत्ती

एका restaurant मध्ये chef शिजवतो, waiter वाढतो, cashier bill करतो. एका व्यक्तीने तिन्ही केले, तर menu, till आणि floor plan मधील बदल सर्व एकाच अतिकष्टी माणसावर येतात.

03 - कसे

अंतर्गत रचनेत SRP कसे लागू करावे

god class पासून सुरुवात करा, बदलण्याचे प्रत्येक कारण नाव द्या, मग प्रत्येक कारणासाठी एक केंद्रित collaborator extract करा. domain object व्यावसायिक नियम ठेवतो; formatting, mailing आणि persistence interfaces मागे हलतात ज्यांना एक पातळ service एकत्र जोडते.

🔍 बदलण्याची कारणे नाव द्या

god class वरील प्रत्येक method यादी करा आणि तिच्या actor ला label लावा: गणित (finance), layout (design), delivery (messaging), storage (DBA). प्रत्येक वेगळे label एक seam आहे जिथे class विभागावी.

🧩 केंद्रित collaborators extract करा

प्रत्येक concern त्याच्या स्वतःच्या class मध्ये एका छोट्या interface मागे हलवा. Invoice data आणि totals ठेवतो; एक BillingService renderer, mailer आणि repository एकत्र करून use case चालवतो.

// SMELL: one class, four reasons to change
class Invoice {
  constructor(
    public id: string,
    public lineItems: { amount: number; qty: number }[],
    public customerEmail: string,
  ) {}

  subtotal(): number {
    return this.lineItems.reduce((s, li) => s + li.amount * li.qty, 0);
  }
  tax(): number {
    return this.subtotal() * 0.2;
  }
  total(): number {
    return this.subtotal() + this.tax();
  }

  // Reason to change #2: the design team
  toHtml(): string {
    return `<h1>Invoice ${this.id}</h1><p>Total ${this.total()}</p>`;
  }

  // Reason to change #3: the messaging team
  email(): void {
    const smtp = new SmtpClient("mail.internal", 25);
    smtp.send(this.customerEmail, "Your invoice", this.toHtml());
  }

  // Reason to change #4: the DBA
  save(): void {
    const db = new PgConnection(process.env.DATABASE_URL!);
    db.exec("INSERT INTO invoices(id, total) VALUES($1, $2)", [
      this.id,
      this.total(),
    ]);
  }
}

class Invoice {
  constructor(
    public id: string,
    public lineItems: { amount: number; qty: number }[],
  ) {}

  subtotal(): number {
    return this.lineItems.reduce((s, li) => s + li.amount * li.qty, 0);
  }
  tax(): number { return this.subtotal() * 0.2; }
  total(): number { return this.subtotal() + this.tax(); }
}

interface InvoiceRenderer { render(inv: Invoice): string; }
interface InvoiceMailer { send(to: string, body: string): void; }
interface InvoiceRepository { save(inv: Invoice): void; }

class PdfRenderer implements InvoiceRenderer {
  render(inv: Invoice): string {
    return `Invoice ${inv.id} - total ${inv.total()}`;
  }
}
class SmtpMailer implements InvoiceMailer {
  constructor(private smtp: SmtpClient) {}
  send(to: string, body: string): void {
    this.smtp.send(to, "Your invoice", body);
  }
}
class SqlInvoiceRepository implements InvoiceRepository {
  constructor(private db: PgConnection) {}
  save(inv: Invoice): void {
    this.db.exec("INSERT INTO invoices(id, total) VALUES($1, $2)", [
      inv.id, inv.total(),
    ]);
  }
}

// The use case composes collaborators; each changes for its own reason
class BillingService {
  constructor(
    private renderer: InvoiceRenderer,
    private mailer: InvoiceMailer,
    private repo: InvoiceRepository,
  ) {}

  issue(inv: Invoice, email: string): void {
    this.repo.save(inv);
    const doc = this.renderer.render(inv);
    this.mailer.send(email, doc);
  }
}

    else contract broke
        Dev->>S: update only the wiring in the composition root
    end

फुगलेल्या Invoice god class पासून केंद्रित collaborators पर्यंत, संपूर्ण refactor क्रमाने.

निरीक्षण

god class लक्षात घ्या

Invoice एक SMTP client आणि एक database driver import करतो आणि 900 ओळी लांब आहे. ती import यादीच पहिला smell आहे: एका data object ने transport आणि storage वर अवलंबून राहू नये.

10
यादी

प्रत्येक method आणि तिचा actor यादी करा

प्रत्येक method त्या team शेजारी लिहा जी बदल मागेल: totals (finance), toHtml (design), email (messaging), save (DBA). चार actors म्हणजे बदलण्याची चार कारणे.

20
गट

बदलण्याच्या कारणानुसार गटबद्ध करा

एकच actor असलेल्या methods भोवती चौकटी काढा. उच्च cohesion म्हणजे एका चौकटीतील सर्व काही एकत्र हलते आणि बाहेरील कशासोबतही क्वचित हलते.

30
नाव

प्रत्येक cluster ला एक class नाव द्या

प्रत्येक cluster ला हेतू-प्रकट करणारे नाव द्या: InvoiceRenderer, InvoiceMailer, InvoiceRepository. नावाने एक काम वर्णन करावे, "manager" किंवा "helper" नव्हे.

40
Interface

प्रत्येक concern साठी एक seam परिभाषित करा

प्रत्येक collaborator साठी एक छोटा interface घोषित करा जेणेकरून callers एका contract वर अवलंबून राहतील, vendor वर नाही. इथे SRP dependency inversion सक्षम करायला सुरुवात करते.

Extract

rendering बाहेर हलवा

toHtml ला PdfRenderer.render(invoice) मध्ये कापून टाका. renderer invoice त्याच्या public methods द्वारे वाचतो आणि एक document परत करतो.

60
Extract

mailing बाहेर हलवा

email ला SmtpMailer.send(to, body) मध्ये कापून टाका. mailer आता फक्त एका string body वर अवलंबून असतो, invoice च्या अंतर्गत गोष्टींवर नाही.

एक use-case service आणा

यादी पुन्हा चालवा: Invoice आता फक्त billing गणितासाठी बदलतो, आणि प्रत्येक collaborator त्याच्या स्वतःच्या actor साठी. शुद्ध invoice वरील unit tests ला कोणतेही I/O लागत नाही.

सामान्य धोके

धोके आणि anti-patterns

SRP जास्त लागू करणे किंवा चुकीचे समजणे सोपे आहे. दोन्ही बाजूंच्या नेहमीच्या चुका या आहेत.

🐙 god class

एक OrderManager जो validate करतो, charge करतो, ship करतो, email करतो आणि log करतो. तो प्रत्येक table ला स्पर्श करतो आणि कधीच बदलणे थांबवत नाही कारण प्रत्येक team कडे तो संपादित करण्याचे कारण असते.

🔬 अति-विभाजन

प्रतिक्रिया म्हणून प्रत्येक method ला एक class करणे: InvoiceTotalCalculator, InvoiceSubtotalCalculator, InvoiceTaxCalculator. आता एक बदल पाच फाईलींमध्ये पसरतो. SRP actors बद्दल आहे, ओळींच्या संख्येबद्दल नाही.

🏷️ अस्पष्ट नावे

Manager, Helper, Util किंवा Processor ने संपणारे classes असंबंधित कोडसाठी चुंबक असतात कारण त्यांची responsibility कधीच परिभाषित केली नव्हती. अस्पष्ट नाव scope creep ला आमंत्रण देते.

🧵 लपलेले side effects

एक total() getter जो database मध्ये audit row देखील लिहितो. जी method वाचते तिने persist करू नये. मिश्रित हेतू एका निरागस दिसणाऱ्या call मध्ये दुसरी responsibility लपवतो.

💉 shotgun surgery

उलट smell: एक तार्किक बदल अनेक classes मध्ये संपादने भाग पाडतो कारण एक responsibility स्वच्छपणे विभागण्याऐवजी विखुरली होती. घाईघाईतील extraction दरम्यान cohesion गळून गेली.

🧊 anemic विभाजन

सर्व behavior बाहेर काढून Invoice ला getters ची पिशवी बनवणे आणि logic services मध्ये राहणे. अति केल्यास हे एका anemic domain model कडे झुकते जिथे objects data ठेवतात पण नियम नाही.

संकेत आणि Metrics

संकेत आणि मोजमाप कसे करावे

तुम्ही "responsibilities" थेट मोजू शकत नाही, पण अनेक संकेत विश्वासार्हपणे अतिभारित class उघड करतात.

संकेततो तुम्हाला काय सांगतो
बदलण्याची कारणेएक संपादन मागू शकणाऱ्या actors ना नाव द्या. एकापेक्षा जास्त वेगळ्या teams म्हणजे सहसा एकापेक्षा जास्त responsibility.
Import / dependency पसाराजो domain class एक SMTP client, एक PDF library आणि एक DB driver import करतो, तो transport, formatting आणि storage एकाच वेळी करतो.
LCOM (cohesion चा अभाव)कोणतेही fields सामायिक न करणाऱ्या methods विभक्त clusters बनवतात. उच्च LCOM म्हणजे class खरे तर एकत्र चिकटलेल्या अनेक classes आहेत.
Commit co-change churnजर असंबंधित features सतत तीच फाईल संपादित करत असतील, तर तिच्या responsibilities गुंतलेल्या आहेत. Git history हे coupling उघड करते.
Test setup चे वजनफक्त एक method test करण्यासाठी database, SMTP fake आणि PDF stub लागणे म्हणजे एका दारामागे मिश्रित concerns असल्याचा संकेत.
"and" testजर class चे वर्णन करायला "and" लागत असेल (format आणि mail आणि save), तर प्रत्येक खंड extract करण्याजोगी candidate responsibility आहे.
अंगठ्याचा नियम: जर तुम्ही एका class चे "and" शब्दाशिवाय एका वाक्यात वर्णन करू शकत नसाल, तर बहुधा त्याला बदलण्याची एकापेक्षा जास्त कारणे आहेत. actor नुसार विभागा, अनियंत्रित आकारानुसार नाही.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

तीन production-शैलीच्या systems जिथे responsibilities वेगळ्या केल्याचा फायदा झाला.

💳

1 · एका subscriptions platform मधील billing god class विभागणे

Pattern: अतिभारित domain object मधून collaborators extract करणे

एका SaaS billing service कडे एक Invoice होता जो proration मोजायचा, PDFs render करायचा, email पाठवायचा आणि Postgres मध्ये लिहायचा, त्यामुळे प्रत्येक team एकाच फाईलवरून भांडायची.

  • Proration गणित Invoice वरच राहिले; rendering PDF आणि HTML implementations असलेल्या InvoiceRenderer interface मध्ये हलले.
  • Delivery एका InvoiceMailer मागे हलली, ज्यामुळे messaging team ला finance logic ला स्पर्श न करता providers बदलता आले.
  • Persistence एका InvoiceRepository मध्ये हलली, त्यामुळे DBA ला domain पुन्हा compile न करता schema बदलता आला.
✅ परिणाम: Tax नियम बदल आणि vendor migrations एकाच pull request मध्ये टकराणे थांबले, आणि शुद्ध invoice unit test करणे अगदी सोपे झाले.
🛒

2 · एका e-commerce order flow मधील checkout सोडवणे

Pattern: एकल-उद्देश classes ना समन्वयित करणारी एक use-case service

एका OrderService ने carts validate केले, cards charge केले, inventory reserve केले आणि receipts email केले एकाच method मध्ये, त्यामुळे कोणताही बदल संपूर्ण checkout ला धोक्यात आणायचा.

  • Payment एका PaymentGateway interface मागे हलले, card-processor SDK ला order नियमांपासून विलग केले.
  • Stock बदल warehouse team च्या मालकीच्या InventoryReservation class मध्ये हलले.
  • एका पातळ PlaceOrder use case ने validate, charge, reserve, notify यांचा क्रम लावला, प्रत्येक एका केंद्रित collaborator कडे सोपवला.
✅ परिणाम: एका payment processor वरून दुसऱ्याकडे बदलणे एका-class चा बदल बनला, आणि inventory logic checkout पासून स्वतंत्रपणे विकसित झाली.
🔔

3 · एका logistics कंपनीत notification pipeline चे decoupling

Pattern: काय पाठवायचे ते कसे पाठवायचे यापासून वेगळे करा

एका shipment tracker ने email bodies बनवले, SMS format केले, तीन vendor APIs call केले आणि delivery status log केले सर्व एकाच Notifier class मध्ये.

  • Message content product च्या मालकीच्या प्रति-event NotificationTemplate classes मध्ये हलले.
  • प्रत्येक channel एका सामायिक interface मागे स्वतःचा sender बनला (EmailSender, SmsSender, PushSender).
  • एका DispatchService ने user preference नुसार channels निवडले आणि सोपवले, स्वतः कोणताही vendor कोड न ठेवता.
✅ परिणाम: WhatsApp channel जोडणे म्हणजे एक नवीन sender class लिहिणे, template आणि dispatch कोड अस्पर्शित ठेवून.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

SRP SOLID च्या लोकप्रियतेच्या आधीचे आहे पण systems services आणि functions मध्ये विघटित होत असताना ते अधिकच केंद्रस्थानी आले आहे.

🧱 Microservices सीमा

एका bounded context ची मालकी असलेली service म्हणजे deployment scale वरील SRP. classes विभागणारी तीच "बदलण्याचे एकच कारण" test service seams देखील काढते.

⚡ Serverless functions

प्रत्येक event साठी एक एकल-उद्देश function म्हणजे SRP प्रत्यक्षात आणलेले. प्रत्येक handler एका trigger साठी बदलतो, आणि असंबंधित logic स्वतःच्या deployment मध्ये राहते.

🧭 Hexagonal architecture

Ports आणि adapters SRP औपचारिक करतात: domain नियम ठेवतो, आणि प्रत्येक adapter (mail, DB, HTTP) एक single-responsibility किनार आहे जी एका port मागे plug होते.

🧪 मोठ्या प्रमाणात Testability

कोणतेही I/O नसलेले शुद्ध domain objects जलद, deterministic unit tests देतात. SRP हेच आहे जे ती शुद्धता जड mocks शिवाय शक्य करते.

🤖 AI-सहाय्यित refactors

Extract-class refactors हेच coding assistants चांगले करतात, पण actors ना नाव देण्यासाठी त्यांना अजूनही माणसाची गरज असते. SRP त्या निर्णयाला एक नियम देते.

📦 Domain-driven design

DDD मधील aggregates, repositories आणि application services या नाव दिलेल्या responsibilities आहेत. SRP ती निम्न-स्तरीय शिस्त आहे जी त्या प्रत्येकाला केंद्रित ठेवते.

सारांश: SRP एका method पासून संपूर्ण service पर्यंत scale होते. जेव्हा तुम्हाला एक गोष्ट अनेक कारणांसाठी बदलताना दिसते, तेव्हा तिला actor नुसार विभागा. केंद्रित collaborators थोडी जास्त जोडणी घेतात आणि requirements बदलल्यावर प्रत्येक वेळी त्याची परतफेड करतात.
