Structural Pattern

Flyweight लाखो ऑब्जेक्ट्स परवडणारे कसे बनवते

दहा लाख अक्षरे असलेले document किंवा दहा लाख particles असलेला गेम रेंडर करताना, प्रत्येक जर जड ऑब्जेक्ट असेल तर memory फुटून जाते. Flyweight हे दुरुस्त करते: जे भाग पुन्हा पुन्हा येतात ते (intrinsic state) सर्व instances मध्ये ते सामायिक करते आणि जे भाग बदलतात ते (extrinsic state) call च्या वेळी आत पाठवते, त्यामुळे मूठभर सामायिक ऑब्जेक्ट्स जवळजवळ अमर्याद संख्येने logical ऑब्जेक्ट्सना आधार देऊ शकतात.

01 - काय

Flyweight pattern म्हणजे काय?

Flyweight हा एक structural pattern आहे जो अनेक समान ऑब्जेक्ट्समध्ये शक्य तितका data सामायिक करून memory चा वापर कमी करतो. तो ऑब्जेक्टच्या state चे दोन भाग करून काम करतो: intrinsic state जो अनेक instances मध्ये सारखाच असतो आणि सामायिक करता येतो, आणि extrinsic state जो प्रत्येक वापरागणिक वेगळा असतो आणि caller पुरवतो. एक factory सामायिक flyweights वाटते त्यामुळे एकसारखा intrinsic state फक्त एकदाच साठवला जातो.

🧬 Intrinsic state

संदर्भरहित, सामायिक करता येण्याजोगा data जो instances मध्ये पुन्हा पुन्हा येतो (एखाद्या glyph चा font आणि outline, एखाद्या झाडाचा mesh आणि texture). flyweight च्या आत एकदाच साठवला जातो आणि कधीही बदलला जात नाही.

📍 Extrinsic state

संदर्भावर अवलंबून असलेला data जो प्रत्येक instance गणिक बदलतो (एखाद्या अक्षराचे स्क्रीनवरील स्थान, एखाद्या particle चा velocity). flyweight च्या बाहेर ठेवला जातो आणि arguments म्हणून आत पाठवला जातो.

🏭 Flyweight factory

एक pool जो key नुसार flyweights तयार करतो आणि cache करतो. आधीच अस्तित्वात असलेला मागा आणि तुम्हाला तोच सामायिक instance परत मिळतो, त्यामुळे intrinsic state कधीही डुप्लिकेट होत नाही.

02 - का

Flyweight का अस्तित्वात आहे

जेव्हा तुम्हाला बहुतांशी एकसारख्या ऑब्जेक्ट्सची अत्यंत मोठी संख्या हवी असते, तेव्हा भोळसट पद्धत तोच जड data पुन्हा पुन्हा साठवते. Flyweight सामायिक भाग एकदाच साठवून RAM चा वापर सपाट ठेवते, कितीही logical ऑब्जेक्ट्स त्याला संदर्भित करत असले तरी.

🪶 Memory चा वापर मोठ्या प्रमाणात कमी करते

दहा लाख जड ऑब्जेक्ट्सऐवजी, तुम्ही काही सामायिक flyweights आणि प्रत्येक instance गणिक छोटासा context धरता. डुप्लिकेट झालेला intrinsic state memory मध्ये एकाच copy मध्ये संकुचित होतो.

⚡ चांगले cache आणि GC वर्तन

कमी, छोट्या allocations म्हणजे garbage collector वर कमी दबाव आणि प्रचंड collections वर iterate करताना खूप चांगली CPU cache locality.

♻️ रचनेतूनच deduplication

factory याची हमी देते की तोच intrinsic key दोनदा मागितल्यास अगदी तोच ऑब्जेक्ट मिळतो, त्यामुळे समान गोष्टी फक्त logical दृष्ट्या समान नसून physical दृष्ट्या सामायिक होतात.

🎯 अशक्य ते शक्य करते

जे systems आपले ऑब्जेक्ट्स स्वतंत्रपणे कधीही धरू शकले नसते - forest renderers, particle systems, tile maps - ते पुन्हा पुन्हा येणारा जड भाग सामायिक केल्यावर व्यवहार्य बनतात.

सोप्या शब्दांत

उपमांसह Flyweight ची स्पष्टता

तीच कल्पना, चित्रित करण्याचे चार मार्ग, त्यामुळे तुम्ही कोणीही असलात तरी ती डोक्यात बसते.

🎓 विद्यार्थ्यासाठी

एका रबर stamp चा विचार करा. एकच कोरलेला stamp (सामायिक intrinsic भाग) तोच आकार हजारो वेळा उमटवतो; बदलणारी एकच गोष्ट म्हणजे तुम्ही पानावर कुठे उमटवता (extrinsic स्थान). प्रत्येक उमटवण्यासाठी तुम्ही नवीन stamp कधीच कोरत नाही.

👩‍💻 developer साठी

हे interned strings किंवा constant pool सारखे आहे. प्रत्येक "OK" literal एकाच सामायिक ऑब्जेक्टकडे निर्देश करते; ते धरणारा variable फक्त एक reference वाहतो. Flyweight संपूर्ण ऑब्जेक्ट्स intern करते आणि बदलणारा data त्यांना parameters म्हणून पुरवते.

🏢 व्यावसायिकासाठी

एका call center script ची कल्पना करा. एकच छापलेली script (सामायिक) प्रत्येक ग्राहकाला वाचून दाखवली जाते; ग्राहकाचे नाव आणि account number (प्रत्येक-call context) जागच्या जागी भरले जातात. प्रत्येक calling साठी तुम्ही script पुन्हा छापत नाही.

♟️ रोजच्या जीवनातील आवृत्ती

एका बुद्धिबळाच्या संचात प्याद्याची एकच रचना असते. board आठ पांढरे प्यादे आठ वेगळ्या प्याद्यांची रचना कोरून धरत नाही, तर तोच प्याद्याचा आकार वेगवेगळ्या घरांवर ठेवून धरते. ते घर म्हणजे extrinsic state.

03 - कसे

अंतर्गत ते कसे काम करते

Flyweight ला दोन हलणारे भाग असतात: एक factory जो सामायिक intrinsic ऑब्जेक्ट्स pool करतो, आणि एक client जो extrinsic state ठेवतो आणि call च्या वेळी तो सामायिक methods मध्ये पाठवतो.

🔑 विभाजन ओळखा

जे पुन्हा पुन्हा येते (font, outline, texture) ते जे बदलते (position, color, velocity) यापासून वेगळे करा. सर्व intrinsic flyweight च्या आत जाते आणि अपरिवर्तनीय केले जाते; सर्व extrinsic client कडे राहते.

🗄️ Pool करा आणि पुनर्वापर करा

intrinsic state वर keyed असलेला factory अस्तित्वात असल्यास cache केलेला flyweight परत देतो, किंवा नवीन तयार करून साठवतो. Clients कधीही थेट flyweights बनवत नाहीत, त्यामुळे सामायिकरण अनिवार्य होते.

Java मधील एक वास्तववादी अंमलबजावणी

import java.util.Map;
import java.util.HashMap;

// Flyweight: stores only intrinsic, shared, immutable state
final class Glyph {
    private final char symbol;   // intrinsic
    private final String font;   // intrinsic (outline lives here too)

    Glyph(char symbol, String font) {
        this.symbol = symbol;
        this.font = font;
    }

    // Extrinsic state (x, y, color) is passed in, never stored
    void draw(int x, int y, String color) {
        System.out.printf("'%c' [%s] at (%d,%d) in %s%n",
                          symbol, font, x, y, color);
    }
}

// Factory: pools flyweights so identical intrinsic state is stored once
final class GlyphFactory {
    private final Map<String, Glyph> pool = new HashMap<>();

    Glyph getGlyph(char symbol, String font) {
        String key = symbol + "@" + font;
        return pool.computeIfAbsent(key, k -> new Glyph(symbol, font));
    }

    int distinctGlyphs() { return pool.size(); }
}

// Client holds extrinsic state and reuses shared flyweights
final class Document {
    private record Placed(Glyph glyph, int x, int y, String color) {}
    private final GlyphFactory factory = new GlyphFactory();
    private final java.util.List<Placed> chars = new java.util.ArrayList<>();

    void type(String text, String font) {
        int x = 0;
        for (char c : text.toCharArray()) {
            Glyph g = factory.getGlyph(c, font); // shared, not new
            chars.add(new Placed(g, x, 0, "black"));
            x += 8;
        }
    }

    void render() {
        for (Placed p : chars) p.glyph().draw(p.x(), p.y(), p.color());
    }

    int distinctGlyphs() { return factory.distinctGlyphs(); }
}

"mississippi" टाइप केल्याने अकरा placements तयार होतात पण फक्त चार वेगळे Glyph ऑब्जेक्ट्स (m, i, s, p) तयार होतात. Glyph हे final आहे आणि त्यात फक्त final fields आहेत, त्यामुळे सामायिकरण सुरक्षित आहे: कोणताही client intrinsic state बदलून तो इतर सर्वांसाठी बिघडवू शकत नाही.

सामान्य धोके

धोके आणि anti-patterns

Flyweight चुकीच्या पद्धतीने वापरणे सोपे आहे. हे ते सापळे आहेत जे memory जिंकीचे bug स्त्रोतात रूपांतर करतात.

🧊 परिवर्तनीय सामायिक state

flyweight मध्ये परिवर्तनीय fields टाकणे हे मुख्य पाप आहे. एक client "सामायिक" ऑब्जेक्ट बदलतो आणि गुपचूप इतर प्रत्येक धारकाला बिघडवतो. intrinsic state अपरिवर्तनीय असले पाहिजे.

🎭 चुकीचे विभाजन

प्रत्येक-instance data ला intrinsic म्हणून चिन्हांकित केल्यास वेगळे ऑब्जेक्ट्स एकात संकुचित होतात; सामायिक data ला extrinsic म्हणून चिन्हांकित केल्यास बचत नष्ट होते. intrinsic/extrinsic रेषा बरोबर आखा नाहीतर pattern अपयशी होतो.

🐘 अकाली optimization

Flyweight एक factory, एक indirection, आणि मानसिक कर जोडते. जर तुमच्याकडे फक्त काहीशे ऑब्जेक्ट्स असतील, तर ती गुंतागुंत काहीही देत नाही. आधी profile करा, मग वापरा.

💧 कधीही आकुंचित न होणारा pool

अमर्याद factory cache स्वतःच memory leak बनू शकते, विशेषतः high-cardinality keys सह. ती मर्यादित करा किंवा scope करा जेणेकरून pool त्याने वाचवलेल्यापेक्षा मोठा होणार नाही.

🧵 thread safety दुर्लक्षित करणे

cache miss वर factory ला धडकणारे दोन threads डुप्लिकेट flyweights तयार करू शकतात किंवा map बिघडवू शकतात. Concurrent pools ना योग्य synchronization किंवा concurrent map लागतो.

🔁 Extrinsic खर्च बचतीला बुडवतो

जर extrinsic state इकडे-तिकडे पाठवणे त्याने वाचवलेल्यापेक्षा जास्त memory किंवा CPU खर्च करत असेल, किंवा key गणना महाग असेल, तर pattern निव्वळ तोटा ठरू शकतो. दोन्ही बाजू मोजा.

तडजोडी

तडजोडी आणि कधी वापरावे

Flyweight थोडेसे indirection आणि रचनेचे कष्ट देऊन मोठी memory बचत विकत घेते. आकडे न्याय्य ठरवतात तेव्हाच त्याकडे वळा.

पैलूतपशील
फायदेनाट्यमयरीत्या कमी memory footprint, कमी GC दबाव, चांगली cache locality, सामायिक state च्या deduplication ची हमी.
तोटेअधिक गुंतागुंतीचा code, एक अतिरिक्त factory आणि indirection, keys गणण्याचा आणि extrinsic state पाठवण्याचा CPU खर्च, अपरिवर्तनीयतेच्या मर्यादा.
कधी वापरावेतुमच्याकडे अत्यंत मोठ्या संख्येने ऑब्जेक्ट्स आहेत, ज्यांचा बहुतांश state पुन्हा पुन्हा येतो आणि थोड्याशा सामायिक मूल्यांमध्ये वेगळा करता येतो.
कधी टाळावेऑब्जेक्ट्सची संख्या माफक आहे, state फारसा पुन्हा येत नाही, किंवा intrinsic state परिवर्तनीय असला पाहिजे. गुंतागुंत स्वतःची किंमत वसूल करणार नाही.
गुंतागुंतमध्यम. pattern सोपा आहे, पण intrinsic/extrinsic रेषा बरोबर आखणे आणि सामायिक state अपरिवर्तनीय ठेवणे यासाठी काळजी लागते.
संबंधितSingleton (factory अनेकदा एकच असतो), Prototype (cloning विरुद्ध sharing), Composite (सामायिक leaves म्हणून flyweights), Proxy (दोन्ही अप्रत्यक्ष access).
अंगठ्याचा नियम: Flyweight फक्त तेव्हाच वापरा जेव्हा memory ही खरी मर्यादा असेल आणि ऑब्जेक्टचा state स्वच्छपणे एका छोट्या सामायिक गाभ्यात आणि एका बदलणाऱ्या context मध्ये विभागला जात असेल. यापैकी एक अट अपयशी झाली, तर साधा ऑब्जेक्ट किंवा object pool अधिक सोपा आहे.
06 - केस स्टडीज

प्रत्यक्ष जगातील केस स्टडीज

तीन ठिकाणे जिथे Flyweight हेच चालणे आणि memory संपणे यातील फरक आहे.

📝

1 · Text editor glyph rendering

Pattern: सामायिक character ऑब्जेक्ट्स, प्रत्येक-position context

एका document editor ला लाखो अक्षरे दाखवावी लागतात, प्रत्येकाला font, outline, आणि metrics लागतात.

  • प्रत्येक वेगळी character-आणि-font जोडी म्हणजे एकच सामायिक Glyph जो outline आणि advance width धरतो.
  • document फक्त positions आणि styles चा हलका run साठवतो, सामायिक glyphs ना संदर्भित करतो.
  • Rendering प्रत्येक glyph ला draw च्या वेळी त्याची row, column, आणि color extrinsic state म्हणून पुरवते.
✅ परिणाम: क्लासिक Gang of Four उदाहरण. पुस्तकाएवढे लांब document लाखोंऐवजी काहीशे glyph ऑब्जेक्ट्सद्वारे आधारलेले असते, ज्यामुळे editor प्रतिसाद देणारा राहतो.
🎮

2 · Game particle आणि foliage systems

Pattern: सामायिक mesh आणि texture, प्रत्येक-instance transform

एक गेम दहा लाख झाडांचे जंगल किंवा हजारो particles चा स्फोट सेकंदाला 60 frames वर रेंडर करतो.

  • जड mesh, texture, आणि material त्याच प्रजातीच्या प्रत्येक झाडात सामायिक केले जातात.
  • प्रत्येक instance फक्त त्याचे position, rotation, scale, आणि velocity साठवतो, काही डझन bytes.
  • renderer सामायिक asset ला अनेकदा instance करतो, प्रत्येक-instance transforms GPU ला पुरवतो.
✅ परिणाम: दाट जग VRAM मध्ये बसते आणि सुरळीत stream होते, कारण megabytes च्या geometry एकदाच अस्तित्वात असते, प्रत्येक ऑब्जेक्ट गणिक एकदा नाही.
☕

3 · JVM Integer आणि String interning

Pattern: language-पातळीवरील flyweight caches

एक high-throughput service प्रचंड संख्येने छोटी boxed values आणि पुन्हा येणारे string literals तयार करते.

  • Java -128 ते 127 पर्यंतच्या boxed Integer values cache करते जेणेकरून valueOf सामायिक instances परत देतो.
  • String literals एका pool मध्ये intern केले जातात, त्यामुळे codebase मधील एकसारखे literals एक ऑब्जेक्ट सामायिक करतात.
  • Application code ला memory जिंक फुकट मिळते, स्वतः कोणताही factory न लिहिता.
✅ परिणाम: सामान्य छोट्या values एकदाच allocate होतात आणि सर्वत्र पुनर्वापर होतात, संपूर्ण runtime मधील hot paths मध्ये allocation churn कमी करून.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Flyweight आधुनिक hardware च्या आधीचे आहे, पण त्याची मूळ कल्पना, पुन्हा येणारा जड भाग सामायिक करा आणि फक्त context बदला, ती scale वर आजपेक्षा कधीही अधिक प्रासंगिक आहे.

🕹️ GPU instanced rendering

आधुनिक graphics APIs Flyweight ला native बनवतात: प्रत्येक-instance transforms च्या एका buffer सह हजारो वेळा काढलेला एक mesh म्हणजे hardware मधील Flyweight.

🧊 Value types आणि records

अपरिवर्तनीय records आणि value objects सुरक्षित, सामायिक करता येण्याजोगे flyweights घोषित करणे क्षुल्लक बनवतात, कारण भाषा pattern ला लागणारी अपरिवर्तनीयता अनिवार्य करते.

🌊 Big-data columnar stores

columnar formats मधील dictionary encoding प्रत्येक वेगळे मूल्य एकदाच साठवते आणि id द्वारे संदर्भित करते, जे अब्जावधी rows वर लागू केलेले Flyweight आहे.

⚛️ UI virtualization

Virtualized lists आणि अपरिवर्तनीय component trees प्रचंड views मध्ये सामायिक node descriptions पुनर्वापर करतात, प्रत्येक item गणिक फक्त बदलणारे props ठेवतात.

🔗 String आणि object interning

Runtimes आणि caches अजूनही डुप्लिकेट values संकुचित करण्यासाठी interning वर विसंबतात, JVM strings पासून interpreters मधील symbol tables पर्यंत.

🧠 Tokenizer आणि vocab tables

ML pipelines प्रत्येक sequence मध्ये token ऑब्जेक्ट्सचा एक vocabulary सामायिक करतात, प्रत्येक-sequence data संक्षिप्त id arrays म्हणून साठवतात.

सारांश: अत्यंत मोठ्या संख्येने ऑब्जेक्ट्स परवडणारे बनवण्याचा मार्ग म्हणजे Flyweight: जे पुन्हा येते ते एकदाच साठवा, जे बदलते ते आत पाठवा, आणि सामायिक भाग अपरिवर्तनीय ठेवा. जेव्हा जेव्हा scale आणि duplication भेटतात, तेव्हा pattern आपली किंमत वसूल करते.
