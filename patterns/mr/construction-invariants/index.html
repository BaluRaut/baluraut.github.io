Construction आणि Invariants - पहिल्या ओळीपासूनच वैध असणारे objects

एखादा object अस्तित्वात येताच त्याच्यावर विश्वास ठेवता आला पाहिजे. जेव्हा constructor invariants लागू करतो - किमान एक line item असलेला Order, खरोखर पत्ता असणारा Email, कधीही ऋण न होणारा Money - तेव्हा उर्वरित system ने पुन्हा पुन्हा तपासणी करणे थांबवून तो object थेट वापरता येतो. याला पर्याय म्हणजे अर्धवट बांधलेल्या objects आणि सर्वत्र पसरणाऱ्या defensive null checks नी भरलेला codebase.

01 - काय

Construction आणि invariants म्हणजे काय?

Invariant म्हणजे असा नियम जो object च्या संपूर्ण आयुष्यभर नेहमी खरा असला पाहिजे: Order कडे नेहमी किमान एक line item असते, Money मूल्य नेहमी एक currency बाळगते, ShippingAddress कडे नेहमी रिक्त नसलेला postal code असतो. Construction हा तो क्षण आहे जिथे तुम्ही हे नियम हमी देऊ शकता. जर constructor असे काहीही बांधण्यास नकार देत असेल जे या नियमांचे उल्लंघन करेल, तर पुढील प्रत्येक method वैध object गृहीत धरू शकते आणि पुन्हा कधीही validation करावी लागत नाही.

🧱 पहिल्या ओळीपासून वैध

Constructor एकतर पूर्णपणे वैध object परत करतो किंवा throw करतो. असा कोणताही क्षण नसतो ज्यात caller कडे अर्धवट initialize झालेला, नियम मोडणारा instance असेल.

🚧 सुरुवातीलाच Guard clauses

Constructor आधी preconditions तपासतो आणि कोणतेही field नियुक्त करण्यापूर्वीच चुकीचे input तात्काळ नाकारतो. लवकर अपयशी व्हा, चुकीच्या स्रोताच्या जवळ.

🏭 Static factory methods

Order.forCustomer(...) किंवा Money.fromCents(...) सारखे नावाचे builders उद्देश स्पष्ट करतात, validation करतात, आणि cached किंवा subtype instances परत करू शकतात.

02 - का

Construction च्या वेळी invariants का लागू करावेत

चुकीचा data नाकारण्यासाठी सर्वात स्वस्त जागा म्हणजे तुमच्या object model मध्ये तो जिथे प्रवेश करतो ती सीमा. Constructor मध्ये तुम्ही लागू करणारा प्रत्येक नियम म्हणजे असा नियम जो कोणत्याही caller, service, किंवा database ला पुन्हा कधीही तपासावा लागत नाही.

🛡️ विश्वास ठेवण्याची एकच जागा

जर Order फक्त वैध line items सहच अस्तित्वात येऊ शकतो, तर checkout, invoicing, आणि shipping कोडला रिक्त order पासून कधीही रक्षण करावे लागत नाही. Invariant एकदाच, जन्माच्या वेळी सिद्ध होतो.

💥 लवकर अपयश, जवळ अपयश

Guard clause नेमक्या त्याच call site वर throw करते जिथून चुकीचे input आले, स्पष्ट संदेशासह. Bugs निर्मितीच्या वेळी समोर येतात, तीन services नंतर एका गूढ null म्हणून नव्हे.

🧹 कमी defensive गोंधळ

Invariants शिवाय, प्रत्येक method if (this.items == null) तपासण्यांनी सुरू होते. त्या एकदाच लागू करा आणि तो विखुरलेला defensive कोड फक्त नाहीसा होतो.

🔐 टिकणारे encapsulation

Public setters कोणत्याही caller ला नंतर object एका अवैध स्थितीत टाकू देतात. Invariants पुन्हा तपासणाऱ्या उद्देश-दर्शवणाऱ्या methods object ला त्याच्या संपूर्ण आयुष्यभर प्रामाणिक ठेवतात.

सोप्या शब्दांत

उपमांसह समजावलेले Construction आणि invariants

तीच कल्पना, चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती लक्षात येते.

🎓 विद्यार्थ्यासाठी

प्रत्येक आवश्यक field भरेपर्यंत submit न होणाऱ्या form सारखे हे आहे. नियम पूर्ण होईपर्यंत तुम्ही record तयारच करू शकत नाही, त्यामुळे अर्धवट-वैध submission इकडेतिकडे फिरत राहण्याचा प्रश्नच येत नाही.

👩‍💻 developer साठी

Constructor म्हणजे एक validating parser: कच्चे input आत जाते, आणि एकतर हमी-वैध object बाहेर येतो किंवा तो throw करतो. त्या ओळीनंतर, तुम्ही त्या object साठी पुन्हा कधीही if valid तपासणी लिहित नाही.

🏢 व्यावसायिकासाठी

बँक खाते उघडते तसे विचार करा. Account number जारी करण्यापूर्वी ओळख, किमान ठेव, आणि सह्या पडताळल्या जातात. तपासण्या टाळलेले कोणतेही सक्रिय खाते नसते.

🏗️ रोजच्या जीवनातील आवृत्ती

इमारतीला तपासणीत उत्तीर्ण झाल्यावरच certificate of occupancy मिळते. तुम्ही कुटुंबांना अर्धवट बांधलेल्या इमारतीत नेऊन नंतर तपासणी करत नाही, तर उघडण्यापूर्वीच नियमांवर नियंत्रण ठेवता.

03 - कसे

Construction मध्ये invariants कसे लागू करावेत

दोन कृती आहेत. पहिली, constructor ला guard clauses सह कोणतीही अवैध गोष्ट नाकारायला लावा. दुसरी, invariant पुन्हा तपासणाऱ्या उद्देश-दर्शवणाऱ्या methods उघड करून object कालांतराने वैध ठेवा, ते तोडू शकणारे कच्चे setters कधीही नको.

🚪 निर्मितीच्या वेळी नियंत्रण

Guard clauses आधी चालतात: रिक्त item lists, ऋण रकमा, चुकीचे emails नाकारा. प्रत्येक precondition उत्तीर्ण झाल्यावरच fields नियुक्त करा, जेणेकरून object कधीही अर्धवट बांधलेला नसतो.

🔁 आयुष्यभर जपणूक

बदल addItem किंवा applyDiscount सारख्या methods मधून वाहतो ज्या invariant पुन्हा प्रस्थापित करतात. कोणताही public setter शांतपणे order रिक्त किंवा total ऋण ठेवू शकत नाही.

// Money: a value object that can never be malformed
class Money {
  private constructor(
    readonly amountCents: number,
    readonly currency: string,
  ) {}

  // Static factory: validate, then build
  static fromCents(cents: number, currency: string): Money {
    if (!Number.isInteger(cents)) throw new Error("amount must be whole cents");
    if (!/^[A-Z]{3}$/.test(currency)) throw new Error("currency must be ISO 4217");
    return new Money(cents, currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("currency mismatch");
    return new Money(this.amountCents + other.amountCents, this.currency);
  }
}

class LineItem {
  constructor(
    readonly sku: string,
    readonly quantity: number,
    readonly unitPrice: Money,
  ) {
    // Guard clauses run before the object is usable
    if (!sku.trim()) throw new Error("sku is required");
    if (!Number.isInteger(quantity) || quantity < 1)
      throw new Error("quantity must be at least 1");
  }

  subtotal(): Money {
    return Money.fromCents(this.unitPrice.amountCents * this.quantity, this.unitPrice.currency);
  }
}

class Order {
  private readonly items: LineItem[];

  // Private: the ONLY way in is the validated factory below
  private constructor(readonly id: string, readonly customerId: string, items: LineItem[]) {
    if (items.length === 0) throw new Error("an order needs at least one line item");
    this.items = [...items]; // defensive copy, no shared mutable reference
  }

  static forCustomer(customerId: string, items: LineItem[]): Order {
    if (!customerId.trim()) throw new Error("customerId is required");
    return new Order(crypto.randomUUID(), customerId, items);
  }

  // Intent-revealing mutation, NOT a public setter
  addItem(item: LineItem): void {
    this.items.push(item);
  }

  removeItem(sku: string): void {
    if (this.items.length === 1 && this.items[0].sku === sku)
      throw new Error("cannot remove the last line item"); // invariant preserved
    const next = this.items.filter((i) => i.sku !== sku);
    this.items.length = 0;
    this.items.push(...next);
  }

  total(): Money {
    return this.items
      .map((i) => i.subtotal())
      .reduce((sum, s) => sum.add(s));
  }
}

// Usage: object is valid the instant it exists
const order = Order.forCustomer("cust_42", [
  new LineItem("SKU-BOOK-1", 2, Money.fromCents(1999, "USD")),
]);
order.addItem(new LineItem("SKU-PEN-9", 5, Money.fromCents(150, "USD")));
console.log(order.total().amountCents); // 4748

from __future__ import annotations
from dataclasses import dataclass
from functools import reduce
import re
import uuid


@dataclass(frozen=True)
class Money:  # value object: immutable, always well-formed
    amount_cents: int
    currency: str

    @staticmethod
    def from_cents(cents: int, currency: str) -> "Money":
        if not isinstance(cents, int):
            raise ValueError("amount must be whole cents")
        if not re.fullmatch(r"[A-Z]{3}", currency):
            raise ValueError("currency must be ISO 4217")
        return Money(cents, currency)

    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError("currency mismatch")
        return Money(self.amount_cents + other.amount_cents, self.currency)


class LineItem:
    def __init__(self, sku: str, quantity: int, unit_price: Money) -> None:
        # Guard clauses run before any field is trusted
        if not sku.strip():
            raise ValueError("sku is required")
        if not isinstance(quantity, int) or quantity < 1:
            raise ValueError("quantity must be at least 1")
        self.sku = sku
        self.quantity = quantity
        self.unit_price = unit_price

    def subtotal(self) -> Money:
        return Money.from_cents(self.unit_price.amount_cents * self.quantity,
                                self.unit_price.currency)


class Order:
    # Private constructor convention: build via for_customer()
    def __init__(self, id: str, customer_id: str, items: list[LineItem]) -> None:
        if len(items) == 0:
            raise ValueError("an order needs at least one line item")
        self._id = id
        self._customer_id = customer_id
        self._items = list(items)  # defensive copy

    @classmethod
    def for_customer(cls, customer_id: str, items: list[LineItem]) -> "Order":
        if not customer_id.strip():
            raise ValueError("customer_id is required")
        return cls(str(uuid.uuid4()), customer_id, items)

    def add_item(self, item: LineItem) -> None:  # intent-revealing, not a setter
        self._items.append(item)

    def remove_item(self, sku: str) -> None:
        if len(self._items) == 1 and self._items[0].sku == sku:
            raise ValueError("cannot remove the last line item")  # invariant held
        self._items = [i for i in self._items if i.sku != sku]

    def total(self) -> Money:
        return reduce(lambda acc, i: acc.add(i.subtotal()),
                      self._items[1:], self._items[0].subtotal())


# Usage: valid from the first line
order = Order.for_customer("cust_42", [
    LineItem("SKU-BOOK-1", 2, Money.from_cents(1999, "USD")),
])
order.add_item(LineItem("SKU-PEN-9", 5, Money.from_cents(150, "USD")))
print(order.total().amount_cents)  # 4748

require "securerandom"

# Value object: frozen and always well-formed
class Money
  attr_reader :amount_cents, :currency

  def self.from_cents(cents, currency)
    raise ArgumentError, "amount must be whole cents" unless cents.is_a?(Integer)
    raise ArgumentError, "currency must be ISO 4217" unless currency.match?(/\A[A-Z]{3}\z/)
    new(cents, currency)
  end

  def initialize(amount_cents, currency)
    @amount_cents = amount_cents
    @currency = currency
    freeze
  end

  def add(other)
    raise ArgumentError, "currency mismatch" unless other.currency == currency
    Money.new(amount_cents + other.amount_cents, currency)
  end
end

class LineItem
  attr_reader :sku, :quantity, :unit_price

  def initialize(sku, quantity, unit_price)
    # Guard clauses reject bad input at construction
    raise ArgumentError, "sku is required" if sku.to_s.strip.empty?
    raise ArgumentError, "quantity must be at least 1" unless quantity.is_a?(Integer) && quantity >= 1
    @sku = sku
    @quantity = quantity
    @unit_price = unit_price
  end

  def subtotal
    Money.from_cents(unit_price.amount_cents * quantity, unit_price.currency)
  end
end

class Order
  attr_reader :id, :customer_id

  # Prefer the factory; initialize enforces the core invariant
  def initialize(id, customer_id, items)
    raise ArgumentError, "an order needs at least one line item" if items.empty?
    @id = id
    @customer_id = customer_id
    @items = items.dup # defensive copy
  end
  private_class_method :new

  def self.for_customer(customer_id, items)
    raise ArgumentError, "customer_id is required" if customer_id.to_s.strip.empty?
    allocate.tap { |o| o.send(:initialize, SecureRandom.uuid, customer_id, items) }
  end

  def add_item(item) # intent-revealing method, not a setter
    @items.push(item)
  end

  def remove_item(sku)
    if @items.size == 1 && @items.first.sku == sku
      raise ArgumentError, "cannot remove the last line item" # invariant preserved
    end
    @items.reject! { |i| i.sku == sku }
  end

  def total
    @items.map(&:subtotal).reduce { |sum, s| sum.add(s) }
  end
end

# Usage: the object is valid the moment it is born

काय गहाळ आहे ते लक्षात घ्या: इथे setItems नाही, रिक्त order बांधण्याचा कोणताही मार्ग नाही, आणि guard clauses उत्तीर्ण होण्यापूर्वी fields नियुक्त करणारा कोणताही मार्ग नाही. Constructor private आहे आणि एकमेव public प्रवेश बिंदू, static factories, आधी validation करतात. बदल addItem आणि removeItem मधून होतो, ज्या दोन्ही "किमान एक item" नियमाचे रक्षण करतात.

// ANTI-PATTERN: anemic object with public setters
class Order {
  id = "";
  customerId = "";
  items: LineItem[] = []; // starts empty and invalid
  status = "";
}

// Half-built and rule-breaking, yet the type system is happy
const order = new Order();
order.customerId = "cust_42"; // did anyone set items? who knows
checkout(order);              // may explode on an empty order deep in the call stack

# ANTI-PATTERN: anemic object, no invariants
class Order:
    def __init__(self):
        self.id = ""
        self.customer_id = ""
        self.items = []   # empty and invalid
        self.status = ""

# Half-built object escapes into the system
order = Order()
order.customer_id = "cust_42"   # items never set
checkout(order)                 # blows up later, far from the mistake

# ANTI-PATTERN: attr_accessor exposes every field
class Order
  attr_accessor :id, :customer_id, :items, :status
end

# Nothing stops an empty, half-built order
order = Order.new
order.customer_id = "cust_42"   # items still nil
checkout(order)                 # fails somewhere downstream

        F-->>C: exception bubbles up here
    else items present
        Ctor-->>F: valid Order
    end
    Note over C,Ctor: No half-built object ever escapes the factory

Invariants नमूद करा

नेहमी खरे असले पाहिजेत असे नियम लिहून काढा: order कडे किमान एक line item असते, money कधीही ऋण नसते, email पत्त्याच्या आकाराशी जुळते. हे object चे contract बनतात.

लपवा

Constructor private करा

Validation टाळू शकतील अशा मनमानी new calls रोखा. Callers ना तुमच्या नियंत्रणातील नावाच्या प्रवेश बिंदूमधूनच जावे लागते.

उघड करा

Static factory method जोडा

Order.forCustomer(...) किंवा Email.parse(...) द्या जेणेकरून उद्देश स्पष्ट होतो आणि निर्मितीचा एकच validate केलेला मार्ग असतो.

Preconditions आधी तपासा

वरच्या guard clauses कोणतेही field नियुक्त करण्यापूर्वी रिक्त ids, रिक्त item lists, आणि चुकीची मूल्ये नाकारतात. स्पष्ट संदेशासह लवकर अपयशी व्हा.

नाकारा

उल्लंघनावर throw करा

कोणताही नियम मोडला गेला तर, चुकीचे input पुरवणाऱ्या call site वर तात्काळ throw करा, जेणेकरून bug जिथे झाला तिथेच समोर येतो, तीन थर दूर नव्हे.

Inputs ची defensive copy करा

वैध असतानाच fields सेट करा

प्रत्येक guard उत्तीर्ण झाल्यावरच तुम्ही state साठवता. Object थेट "तयार न झालेल्या" वरून "पूर्णपणे वैध" वर जातो, अर्धवट मधली स्थिती नसते.

वैध भागांतून मोठे objects बांधा

प्रत्येक value object स्वतः-validate होत असल्याने, Money च्या LineItem चा Order construction ने बरोबर असतो, अगदी वरपर्यंत.

सामान्य अडचणी

अडचणी आणि anti-patterns

बहुतेक invariant bugs objects दोन टप्प्यांत तयार केल्याने, किंवा callers ना आत पोहोचून state बदलू दिल्याने येतात. हे नेहमीचे दोषी आहेत.

🧟 Anemic objects

वर्तन नसलेल्या आणि नियम नसलेल्या public fields ची पिशवी. रिक्त order किंवा ऋण money ला काहीही रोखत नाही, त्यामुळे प्रत्येक consumer ला त्याऐवजी validation करावी लागते. Object स्वतःचे रक्षण करू शकत नाही.

🪣 रिक्त-मग-भरा हा नमुना

कोरा object तयार करून नंतर fields सेट केल्याने असा एक क्षण तयार होतो जिथे तो अवैध असतो. कोणीतरी त्या क्षणी तो वापरेल, किंवा एखादे field पूर्णपणे विसरेल.

🔓 सर्वत्र public setters

attr_accessor, auto-properties, किंवा उघड fields कोणत्याही caller ला नंतर object एका अवैध स्थितीत टाकू देतात. नियम टाळणारे setters constructor चे काम पुसून टाकतात.

🕳️ अंतर्गत collections गळणे

Caller ची list copy न करता परत करणे किंवा साठवणे बाहेरील कोडला थेट internals बदलू देते, त्यामुळे "किमान एक item" नियमाचे दुरून उल्लंघन होऊ शकते.

🤐 गप्प coercion

ऋण रक्कम शांतपणे शून्यावर आणणे किंवा चुकीच्या currency ला default देणे caller च्या चुका लपवते. Guard clauses ने नाकारावे आणि समजावावे, अवैध input झाकून टाकू नये.

🏗️ वेगळ्या टप्प्यात validation

तुम्हाला बोलावणे लक्षात ठेवावे लागणारी order.validate() method म्हणजे कोणीतरी ती बोलावण्यापूर्वी अवैध objects वापरले जाऊ शकतात आणि जातीलच. Validation construction मध्ये असावी, ऐच्छिक विचारानंतर नव्हे.

संकेत आणि मापके

संकेत आणि कसे मोजावे

Codebase मध्ये कमकुवत invariants सिद्ध करण्यापूर्वीच तुम्हाला ते जाणवू शकतात. हे संकेत तुम्हाला सांगतात की construction आपले काम करत आहे का.

संकेततो तुम्हाला काय सांगतो
प्रति method defensive तपासण्याBusiness methods मध्ये अनेक if x == null किंवा रिक्तपणाचे guards म्हणजे constructor invariants प्रस्थापित करत नाही. तपासण्या पुढे स्थलांतरित झाल्या.
Setter संख्या विरुद्ध method संख्याबहुतांश getters आणि setters असणारा वर्ग anemic आहे. निरोगी domain object कडे कमी किंवा कोणतेही setters नसतात आणि अनेक उद्देश-दर्शवणाऱ्या methods असतात.
Construction मार्गांची संख्याजर object पाच वेगवेगळ्या प्रकारे बांधता येत असेल, तर पाचही validation करतात याची हमी देणे कठीण आहे. एका factory मधून वाहून हमी घट्ट होते.
Production मधील अवैध-स्थिती bugsNull pointer आणि "रिक्त order" घटना objects अर्धवट बांधलेल्या स्थितीत निर्मितीतून सुटल्याकडे निर्देश करतात. असा प्रत्येक bug म्हणजे एक गहाळ guard clause.
Test setup ची गुंतागुंतजर test मध्ये वैध object बांधायला अनेक ओळी आणि manual field-setting लागत असेल, तर construction आपले नियम नीट encapsulate करत नाही.
कारणापासून crash पर्यंतचे अंतरज्या bugs त्यांना कारणीभूत कोडपासून दूर समोर येतात ते उशीरा validation चे संकेत देतात. Fail-fast constructors ते अंतर शून्यावर आणतात.
ठोकताळा: जर तुम्ही object वैध असल्याशिवाय तो बांधूच शकत नसाल, तर तो वैध आहे का हे तपासण्याची कधीही गरज नाही. Constructors बाहेरील runtime guards मोजा; एखादा constructor घट्ट केल्यानंतर तुम्ही जो प्रत्येक guard हटवू शकता तो पुरावा आहे की invariant आता योग्य ठिकाणी राहतो.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

तीन production-शैलीच्या systems जिथे constructor ने लागू केलेल्या invariants चे खरे महत्त्व आहे.

💳

1 · Payments: एक Money value object

नमुना: validate केलेला value object, floats नाहीत

Payments platform ला अशा रकमा हव्या असतात ज्या कधीही अचूकता गमावत नाहीत आणि कधीही currencies मिसळत नाहीत. Money हा integer cents आणि एक ISO currency code म्हणून model केला जातो.

  • Static factory non-integer cents आणि वैध ISO 4217 code नसलेली कोणतीही currency नाकारते.
  • add सारखे arithmetic दोन वेगळ्या currencies एकत्र करण्यास नकार देते, शांतपणे रूपांतर करण्याऐवजी throw करते.
  • Object immutable आहे, त्यामुळे shared Money instance कधीही अवैध रकमेत बदलता येत नाही.
✅ निकाल: rounding आणि currency-मिसळण्याच्या bugs चे संपूर्ण प्रकार अशक्य होतात, कारण अवैध Money बांधताच येत नाही.
🛒

2 · E-commerce: Order aggregate

नमुना: आयुष्यभराच्या invariant सह aggregate root

Checkout service Order ला असा aggregate मानते ज्याकडे नेहमी किमान एक line item आणि सुसंगत total असला पाहिजे.

  • Private constructor आणि Order.forCustomer(...) कोणताही order रिक्त तयार होणार नाही याची हमी देतात.
  • removeItem शेवटची line item हटवण्यास नकार देते, बदलादरम्यान invariant जपते.
  • Line items आणि money हे स्वतः validate केलेले value objects आहेत, त्यामुळे संपूर्ण aggregate construction ने बरोबर असते.
✅ निकाल: पुढील invoicing, tax, आणि fulfillment कोड आपले रिक्त-order guards सोडून देतो आणि मिळणाऱ्या प्रत्येक Order वर विश्वास ठेवतो.
📧

3 · Notifications: parse केलेला Email पत्ता

नमुना: parse करा, validate-आणि-आशा-करा नको

Notifications service email, SMS, आणि push पाठवते. Email पत्ते signup forms, imports, आणि webhooks मधून येतात, सर्व अविश्वासार्ह.

  • Email.parse(raw) सीमेवर एकदाच normalize आणि validate करते, typed Email परत करते किंवा throw करते.
  • पुढील प्रत्येक function string नव्हे तर Email घेते, त्यामुळे "हा वैध पत्ता आहे का" या प्रश्नाचे उत्तर type देते.
  • मूल्य immutable असल्याने, normalize केलेला पत्ता नंतर न पाठवता येणाऱ्या string मध्ये भ्रष्ट होऊ शकत नाही.
✅ निकाल: चुकीच्या पत्त्यांमुळे होणारे bounce rates घटतात, आणि validation logic senders मध्ये विखुरण्याऐवजी नेमक्या एकाच ठिकाणी राहते.
07 - सुसंगतता

आधुनिक सुसंगतता

Constructor ने लागू केलेले invariants ही जुनी OOP सवय नाही, आधुनिक type-driven आणि domain-driven systems कशा बरोबर राहतात याचा तो आधार आहेत.

🧩 Domain-driven design

Aggregates आणि value objects ते जे invariants रक्षतात त्यावरून परिभाषित होतात. Construction च्या वेळी नियम लागू करणे हीच ती यंत्रणा आहे जी aggregate ला खरी consistency boundary बनवते.

🔒 Parse करा, validate नको

असंरचित input ला सीमेवर typed, नेहमी-वैध मूल्यात रूपांतरित करण्याची functional-programming ची कल्पना म्हणजे नेमके एक validating constructor किंवा factory.

🧊 Immutability by default

Records, frozen dataclasses, आणि readonly fields असे objects बनवतात जे एकदाच validate होतात आणि कधीही अवैध स्थितीत बदलत नाहीत, हे मजबूत construction शी नैसर्गिकरित्या जुळते.

🏭 new पेक्षा factories

नावाचे static factories आधुनिक libraries मध्ये सर्वसामान्य आहेत कारण ते उद्देश स्पष्ट करतात, subtype निवडी लपवतात, आणि validation ला एकच घर देतात.

🛠️ Type-state आणि smart constructors

भाषा आता type system ला "हा object आपल्या तपासण्या उत्तीर्ण झाला" हे encode करू देत आहेत, त्यामुळे अवैध instance फक्त अशक्य नव्हे तर अप्रस्तुत होतो.

🌐 सुरक्षित API सीमा

JSON ला validating factories मधून समृद्ध objects मध्ये deserialize केल्याने चुकीचा बाह्य data कधीही वैध दिसणारा instance म्हणून domain मध्ये प्रवेश करत नाही.

सारांश: अवैध स्थिती अशक्य करण्याचा सर्वात विश्वासार्ह मार्ग म्हणजे त्या बांधण्यास नकार देणे. तुमचे नियम constructor आणि factory मध्ये ठेवा, objects immutable ठेवा किंवा फक्त invariant जपणाऱ्या methods मधूनच बदला, आणि उर्वरित तुमची system फुकटातच सोपी आणि सुरक्षित होते.
