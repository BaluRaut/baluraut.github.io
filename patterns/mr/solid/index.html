SOLID तत्त्वे - बदलाला टिकून राहणारे class डिझाइन करा

SOLID म्हणजे पाच डिझाइन तत्त्वे जी ऑब्जेक्ट-ओरिएंटेड code लवचिक आणि बदलण्यास सोपे ठेवतात. प्रत्येक तत्त्व class कशा प्रकारे कडक, ठिसूळ किंवा गुंतागुंतीचे बनते त्या एका विशिष्ट मार्गावर हल्ला करते. एकत्रितपणे ती तुम्हाला छोट्या जबाबदाऱ्या, स्थिर abstraction, आणि ठोस तपशिलांऐवजी interface कडे रोखलेल्या dependency यांच्याकडे ढकलतात.

संपूर्ण प्रवाह पाहा ↓ आकृत्यांकडे जा
Single responsibility Open/closed Substitutability Dependency inversion
01 - काय

SOLID म्हणजे काय?

SOLID हे Robert C. Martin यांनी लोकप्रिय केलेल्या पाच ऑब्जेक्ट-ओरिएंटेड डिझाइन तत्त्वांचे संक्षिप्त रूप आहे. ती अचूकतेचे नियम नाहीत; ती बदलण्याच्या सोयीसाठीचे मार्गदर्शक अंदाज आहेत. या तत्त्वांचे पालन करणाऱ्या code मध्ये सहसा छोटे, केंद्रित class असतात जे तुम्ही संपादित न करता वाढवू शकता, आणि असे module जे एकमेकांच्या अंतर्गत भागांऐवजी abstraction वर अवलंबून असतात.

🧩 बदलण्याचे एकच कारण

SRP आणि ISP जाड class व interface यांना सुसंगत तुकड्यांमध्ये विभागतात, त्यामुळे एका बाबीतील बदल असंबंधित code मध्ये पसरत नाही.

🔌 वाढवा, संपादित करू नका

OCP तुम्हाला अधिक if/else शाखांनी चाचणी केलेला code पुन्हा लिहिण्याऐवजी नवीन type जोडून वर्तन जोडण्यास सांगते.

🔗 abstraction वर अवलंबून राहा

LSP आणि DIP subtype ना त्यांचे करार पाळायला लावतात आणि dependency interface मार्गे नेतात, त्यामुळे तुकडे मोकळेपणाने बदलता येतात.

पाच तत्त्वे एका दृष्टिक्षेपात

तत्त्वते काय सांगतेकोणता दोष दूर करते
S - Single Responsibilityclass ला बदलण्याचे एकच कारण असावे, त्याच्या वर्तनाचा एकच मालक असावाpersistence, formatting आणि व्यवसाय नियम मिसळणारे God class
O - Open/Closedविस्तारासाठी खुले, बदलासाठी बंदप्रत्येक नवीन प्रकरणासाठी संपादित कराव्या लागणाऱ्या वाढत्या switch रचना
L - Liskov Substitutionbase type अपेक्षित असेल तिथे subtype वापरता येण्याजोगे असावेवारशाने आलेले करार तोडणारे, कमकुवत करणारे किंवा अपवाद फेकणारे subclass
I - Interface Segregationएका जाड interface पेक्षा अनेक छोट्या interface ना प्राधान्य द्याकधीच न वापरणाऱ्या method अंमलात आणण्यास भाग पडलेले client
D - Dependency Inversionठोस गोष्टींऐवजी abstraction वर अवलंबून राहाखालच्या स्तरावरील library ला जोडलेले उच्च-स्तरीय धोरण
महत्त्वाचे मानसिक मॉडेल: SOLID हे dependency च्या दिशा आणि आकाराबद्दल आहे. जबाबदाऱ्या छोट्या ठेवा, करार विश्वासार्ह बनवा, आणि बाण स्थिर abstraction कडे रोखा. असे केल्यास बदल codebase भर पसरण्याऐवजी स्थानिक राहतो.
02 - का

SOLID का अस्तित्वात आहे

Software एकदा चुकीचे लिहिले म्हणून अपयशी होत नाही; ते ऱ्हास पावते कारण प्रत्येक बदल आधीच्या पेक्षा अधिक कठीण होतो. SOLID त्या ऱ्हासावर थेट लक्ष केंद्रित करते, त्यामुळे codebase वाढत असतानाही बदलण्यास स्वस्त राहते.

🛡️ बदल स्थानिक राहतो

प्रत्येक class एकाच बाबीचा मालक असेल तेव्हा नवीन गरज एकाच ठिकाणाला स्पर्श करते. असंबंधित file मध्ये पसरणारे संपादन, ज्याला ऱ्हासाचे उत्कृष्ट लक्षण मानले जाते, बहुतांशी नाहीसे होते.

🧪 रचनेतूनच चाचणीयोग्य

abstraction वर अवलंबून राहिल्याने तुम्ही fake आणि mock inject करू शकता. प्रत्येक चाचणीत database किंवा network ओढण्याऐवजी unit वेगळ्या स्वरूपात चाचणी करता येतात.

🔧 सुरक्षित विस्तार

payment पद्धत किंवा export format जोडणे म्हणजे production मध्ये आधीच चालणाऱ्या code मधील धोकादायक संपादन नव्हे, तर तुम्ही जोडता येणारा नवीन class बनतो.

🤝 समांतर संघकार्य

छोटे interface आणि स्पष्ट करार म्हणजे संघ एका स्थिर सीमेवर काम करतात, एकमेकांच्या अंमलबजावणीत अडथळा न आणता एकत्र येतात.

सोप्या भाषेत

उपमांसह SOLID समजावून

तीच पाच कल्पना, त्यांना समजून घेण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी त्या पटकन कळतील.

🎓 विद्यार्थ्यासाठी

SOLID हे व्यवस्थित लावलेल्या रिंग बाइंडर सारखे आहे. प्रत्येक विषयाला स्वतःचा टॅब असतो (single responsibility), जुनी पाने पुन्हा न लिहिता तुम्ही नवीन पाने जोडता (open/closed), आणि तुम्ही काढलेला कोणताही टॅब त्याच रिंगमध्ये बसतो (substitution).

👩‍💻 डेव्हलपरसाठी

USB port चा विचार करा. laptop विशिष्ट device वर नव्हे तर USB कराराच्या वर अवलंबून असते (dependency inversion). कोणतेही सुसंगत device चालते (Liskov), आणि port फक्त device ला जे हवे तेवढेच उघड करते (interface segregation).

🏢 व्यावसायिकासाठी

ही एका कंपनीची संघटना रचना आहे. प्रत्येक भूमिकेला एकच स्पष्ट कार्यक्षेत्र असते (SRP), एका व्यक्तीवर अधिक भार टाकण्याऐवजी तुम्ही नवीन तज्ज्ञ नेमता (OCP), आणि व्यवस्थापक विशिष्ट व्यक्तींवर नव्हे तर पदाच्या वर्णनावर अवलंबून असतात (DIP).

🔌 रोजच्या जीवनातील आवृत्ती

घरातील भिंतीवरचे सॉकेट. सॉकेटमध्ये बसणारे प्रत्येक उपकरण फक्त चालते, wiring न बदलता किटली टोस्टरची जागा घेऊ शकते, आणि आणखी एक दिवा जोडण्यासाठी तुम्हाला कधीच इलेक्ट्रिशियन बोलवावा लागत नाही.

03 - कसे

पाच तत्त्वे एकत्र कशी काम करतात

प्रत्येक तत्त्व बदलाच्या एका अक्षाला हाताळते, पण ती एकमेकांना बळकट करतात. SRP आणि ISP सांधे कुठे असावेत हे ठरवतात; OCP आणि DIP ते सांधे कसे पार करावेत हे ठरवतात; LSP हमी देते की दोन्ही बाजूंचे तुकडे खरोखर परस्पर बदलण्याजोगे आहेत.

🧭 सांधे: SRP आणि ISP

class ला बदलण्याच्या कारणानुसार विभागा (SRP) आणि त्याच्या interface ला वापरणाऱ्या client नुसार विभागा (ISP). शेवटी तुम्हाला छोटे, सुसंगत unit आणि अरुंद करार मिळतात जे कोणी सक्तीने अंमलात आणत नाही.

🚪 दरवाजे: OCP आणि DIP

DIP सांध्यावर एक abstraction ठेवते जेणेकरून उच्च-स्तरीय धोरण कधीच ठोस तपशिलाचे नाव घेत नाही. मग OCP तुम्हाला त्या abstraction च्या मागे धोरण संपादित न करता नवीन अंमलबजावणी जोडू देते. LSP प्रत्येक अंमलबजावणी प्रामाणिक ठेवते.

dependency ची रचना

रचना - धोरण abstraction वर अवलंबून असते, तपशील ती अंमलात आणतात (DIP + OCP + LSP)

        +checkout(order)
    }

        <<interface>>
        +charge(amount) Receipt

TypeScript मधील dependency-inversion रिफॅक्टर

// BEFORE - high-level policy welded to a concrete detail (violates DIP + OCP)
class StripeGateway {
  charge(amount: number) { /* call Stripe */ }
}

class OrderService {
  private gateway = new StripeGateway();   // hard dependency
  checkout(total: number) {
    this.gateway.charge(total);            // to add PayPal, you must edit this class
  }
}

// AFTER - depend on an abstraction; add providers without touching OrderService
interface PaymentGateway {
  charge(amount: number): Receipt;
}

class StripeGateway implements PaymentGateway {
  charge(amount: number): Receipt { /* call Stripe */ return new Receipt(); }
}

class PaypalGateway implements PaymentGateway {   // new type, zero edits to policy (OCP)
  charge(amount: number): Receipt { /* call PayPal */ return new Receipt(); }
}

class OrderService {
  constructor(private readonly gateway: PaymentGateway) {}  // injected abstraction (DIP)
  checkout(total: number): Receipt {
    return this.gateway.charge(total);   // works with any conforming gateway (LSP)
  }
}

// wiring happens at the edge, not inside the policy
const service = new OrderService(new PaypalGateway());

उच्च-स्तरीय OrderService आता फक्त PaymentGateway abstraction चे नाव घेते. provider जोडणे म्हणजे नवीन class (विस्तारासाठी खुले), service कधीच बदलत नाही (बदलासाठी बंद), आणि कोणतेही gateway स्वच्छपणे बदलता येते कारण ती सर्व एकच करार पाळतात.

04 - क्रम आकृत्या

तपशीलवार क्रम आकृत्या

तीन दृष्टिकोन: abstraction मार्गे dependency inject करणे, संपादन न करता वर्तन वाढवणे, आणि Liskov उल्लंघन caller ला कसे तोडते.

00
शोधा

बदलण्याची कारणे शोधा

एका class कडे पाहा आणि ती का बदलू शकते ते यादी करा - नवीन report format, नवीन payment provider, नवीन storage. अनेक कारणे म्हणजे आत लपलेल्या अनेक जबाबदाऱ्या.

10
SRP

जबाबदारीनुसार विभागा

प्रत्येक बाब स्वतःच्या class मध्ये काढा. Persistence, formatting आणि व्यवसाय नियम प्रत्येकी एक मालक असलेले वेगळे सहकारी बनतात.

20
ISP

interface अरुंद करा

जाड interface तोडा जेणेकरून प्रत्येक client फक्त प्रत्यक्ष वापरत असलेल्या method वर अवलंबून राहील. कोणत्याही class ला कधीच न वापरणाऱ्या method काढून टाकाव्या लागत नाहीत.

30
Abstract

सांध्यावर abstraction चे नाव द्या

जिथे उच्च-स्तरीय code खालच्या स्तरावरील तपशिलाला भेटते, तिथे धोरणाला जे हवे तेवढेच पकडणारे interface व्याख्यायित करा, धोरणाच्या भाषेत मांडलेले.

40
DIP

dependency उलटवा

उच्च-स्तरीय class ला त्या interface वर अवलंबून करा आणि अंमलबजावणी injection द्वारे मिळवा, जेणेकरून ती स्वतः कधीच ठोस तपशील नव्याने तयार करत नाही.

50
अंमलात आणा

ठोस provider लिहा

प्रत्येक खालच्या स्तरावरील तपशील abstraction अंमलात आणतो. Stripe gateway, file store, CSV formatter सर्व त्यांच्या कराराच्या मागे राहतात.

60
LSP

करार पाळा

प्रत्येक अंमलबजावणी base type ची आश्वासने पाळते याची खात्री करा - समान किंवा कमकुवत precondition, समान किंवा मजबूत postcondition, कोणतेही अनपेक्षित अपवाद नाहीत.

70
OCP

संपादन न करता वाढवा

पुढील provider किंवा format abstraction अंमलात आणणारा अगदी नवीन class म्हणून जोडा. चाचणी केलेला धोरण code बदलासाठी बंद राहतो.

80
जोडा

काठावर एकत्र करा

एका composition root मध्ये ठोस type निवडा - एक main method किंवा DI container - जेणेकरून सर्व ठोस निर्णय बाहेरील सीमेवर बसतात.

90
चाचणी

fake inject करा आणि पडताळा

mock अंमलबजावणीविरुद्ध धोरणाची unit चाचणी करा. dependency abstraction असल्याने चाचण्या database किंवा network शिवाय वेगाने चालतात.

100
विकसित करा

बदल स्थानिक राहतो

नवीन गरजा नवीन छोट्या class म्हणून येतात. मुख्य धोरण स्थिर असते, डिझाइन त्याच्या सांध्यांवर वाकते, आणि प्रत्येक तत्त्व इतरांना बळकट करते.

सामान्य अडचणी

अडचणी आणि anti-pattern

चुकीच्या पद्धतीने लावलेले SOLID हे कोणतेही डिझाइन नसण्याइतकेच घातक आहे. या नेहमीच्या सापळ्या आहेत.

🌫️ केवळ abstraction साठी abstraction

ज्या class ची फक्त एकच अंमलबजावणी असणार आहे त्या प्रत्येक class ला interface मध्ये गुंडाळणे काही फायदा न देता अप्रत्यक्षता वाढवते. दुसरी अंमलबजावणी खरी असेल किंवा स्पष्टपणे येत असेल तेव्हाच सांधा आणा.

🪓 तुकड्यांपर्यंत नेलेले SRP

प्रत्येक method स्वतःचा class होईपर्यंत विभागणे सुसंगत logic डझनभर file मध्ये विखुरते. बदलण्याचे एक कारण म्हणजे एक बाब, एक ओळ नव्हे.

🧬 composition योग्य असताना inheritance

code पुन्हा वापरण्यासाठी is-a उतरंड सक्तीने लादणे Liskov उल्लंघने निर्माण करते. जेव्हा ओळख नव्हे तर वर्तन बदलते तेव्हा composition आणि छोट्या interface ना प्राधान्य द्या.

🕳️ गळणारे abstraction

SQL तुकडे किंवा HTTP तपशील उघड करणारे interface ठोस अंमलबजावणी परत धोरणात ओढते, दबक्या पावलांनी dependency inversion निष्फळ करते.

🐦 करार तोडणारे subtype

अपवाद फेकण्यासाठी, precondition कडक करण्यासाठी किंवा null परत करण्यासाठी method override करणे LSP चे उल्लंघन करते. subtype हे base type असेल तिथे कुठेही वापरता येण्याजोगे असावे.

📚 पूर्वनिर्धारित जाड interface

एक विशाल service interface प्रत्येक client आणि mock ला कधीच न वापरणाऱ्या method वर अवलंबून राहायला भाग पाडते. अंमलात आणणाऱ्यानुसार नव्हे तर वापरणाऱ्यानुसार वेगळे करा.

तडजोडी

तडजोडी आणि केव्हा वापरावे

SOLID अप्रत्यक्षतेच्या किमतीवर लवचिकता विकत घेते. जिथे बदल संभवतो तिथे ते वापरा, सवयीने सर्वत्र नव्हे.

बाबतपशील
फायदेस्थानिक बदल, वेगळी चाचणी, सुरक्षित विस्तार, समांतर संघकार्य, आणि वर्षानुवर्षे संपादनांना टिकून राहणाऱ्या स्पष्ट module सीमा.
तोटेअधिक type आणि file, अनुसरण्यासाठी अतिरिक्त अप्रत्यक्षता, आणि पहिली आवृत्ती मंदावू शकणारे आधीचे डिझाइन कष्ट.
केव्हा वापरावेcode ला अस्थिर गरजा असतील, एका संकल्पनेच्या अनेक अंमलबजावणी असतील, दीर्घ आयुष्य असेल, किंवा समांतर काम करण्यासाठी स्थिर सांधे लागणारा संघ असेल.
केव्हा टाळावेअल्पकाळ टिकणारे script, एकवेळचे prototype, किंवा एकच अंमलबजावणी असलेला स्थिर code जिथे अतिरिक्त abstraction फक्त अडथळा वाढवते.
गुंतागुंतप्रति तत्त्व कमी, पण interface आणि inject केलेल्या dependency ची संख्या वाढते. ती DI container आणि स्पष्ट नावांनी व्यवस्थापित करा.
संबंधितDesign pattern (strategy, factory), inheritance पेक्षा composition, dependency injection, आणि clean/hexagonal architecture.
अंगठ्याचा नियम: बदलण्याचे खरे दुसरे कारण किंवा खरी दुसरी अंमलबजावणी असल्याच्या क्षणीच abstraction आणा, त्याआधी नव्हे. जो code विकसित होणे भाग आहे त्याला SOLID बक्षीस देते; जो कधीच बदलणार नाही त्यावर ते कर लादते.
06 - उदाहरणे

प्रत्यक्ष जीवनातील उदाहरणे

production दबावाखाली लावलेले SOLID दाखवणारे तीन प्रातिनिधिक रिफॅक्टर.

💳

1 · payment provider चा विस्तार

तत्त्वे: DIP + OCP + LSP

एका checkout service ने एकच card processor हार्डकोड केला होता; प्रत्येक नवीन बाजारपेठेसाठी नवीन provider आणि मुख्य order प्रवाहात संपादने लागत होती.

  • order domain च्या भाषेत एक PaymentGateway interface व्याख्यायित केले गेले.
  • Stripe, PayPal, आणि एक स्थानिक wallet प्रत्येकी सुरुवातीला inject केलेली अंमलबजावणी बनली.
  • order service पूर्णपणे बदलणे थांबले; नवीन provider नवीन class म्हणून पाठवले गेले.
✅ निष्कर्ष: नवीन बाजारपेठ सुरू करणे हे लढाईत सिद्ध झालेल्या checkout code मधील धोकादायक संपादनाऐवजी plug-in काम बनले.
🧾

2 · invoice चा God class

तत्त्वे: SRP + ISP

एकाच Invoice class ने एकूण रक्कम मोजली, PDF तयार केले, आणि database मध्ये साठवले, त्यामुळे कोणताही format बदल tax गणिताला धोका पोहोचवत असे.

  • गणना, rendering, आणि persistence तीन सुसंगत सहकाऱ्यांमध्ये विभागले गेले.
  • अरुंद interface ने renderer ला फक्त त्याला हव्या असलेल्या read method वर अवलंबून ठेवले.
  • PDF मांडणी बदलणे यापुढे पैसे मोजणाऱ्या code ला स्पर्श करत नसे.
✅ निष्कर्ष: Formatting बदल आर्थिक logic ला regression धोका न देता पाठवले गेले, आणि प्रत्येक बाबीला केंद्रित unit चाचण्या मिळाल्या.
🗄️

3 · storage backend बदलणे

तत्त्वे: DIP + LSP

व्यवसाय logic थेट एका ठोस file store ला call करत होते, त्यामुळे cloud object storage कडे जाणे म्हणजे codebase भर search-and-replace बनले.

  • एका DocumentStore abstraction ने save, load, आणि delete domain च्या भाषेत पकडले.
  • local disk आणि cloud अंमलबजावणींनी अगदी तोच करार पाळला.
  • चाचण्या in-memory store विरुद्ध चालल्या, ज्यामुळे suite चा वेळ लक्षणीयरीत्या कमी झाला.
✅ निष्कर्ष: backend स्थलांतर एका ओळीचा wiring बदल बनले, आणि storage cloud कडे गेले हे धोरण code ला कधीच कळले नाही.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

SOLID हे microservice आणि functional झुकाव असलेल्या codebase च्या आधीचे आहे, तरीही त्याची मूळ कल्पना, तुमच्या dependency स्थिर abstraction कडे रोखा, अधिकच महत्त्वाची झाली.

🧱 Clean आणि hexagonal architecture

Ports-and-adapters म्हणजे system च्या पातळीवर dependency inversion: domain port वर अवलंबून असते, infrastructure ती काठावर अंमलात आणते.

🧪 सर्वत्र चाचणीयोग्यता

Inject केलेली abstraction वेगवान, वेगळ्या चाचण्यांचा सर्वांत सोपा मार्ग राहते, म्हणूनच DIP प्रत्येक आधुनिक framework च्या DI container मध्ये अंतर्भूत आहे.

🔀 Functional मिलाफ

function पास करणे म्हणजे नामांकित interface शिवाय dependency inversion; higher-order function कमी औपचारिकतेने OCP आणि DIP देतात.

🌐 microservice करार

service सीमा म्हणजे मोठ्या प्रमाणावरील interface segregation - अरुंद, आवृत्तीबद्ध API जे संघांना स्थिर करारांमागे स्वतंत्रपणे deploy करू देतात.

🤖 AI-सहाय्यित रिफॅक्टरिंग

साधने आता SRP आणि DIP उल्लंघने दाखवतात आणि extraction सुचवतात, पण योग्य abstraction चे नाव देणे अजूनही बदलाबद्दलच्या मानवी विवेकावर अवलंबून आहे.

📦 plugin परिसंस्था

editor पासून CI पर्यंत प्रत्येक विस्तारयोग्य platform रचनेतूनच open/closed आहे: तिसरे पक्ष एका निश्चित extension कराराद्वारे वर्तन जोडतात.

सारांश: SOLID म्हणजे पाळायचे पाच नियम नव्हेत तर तयार करायची एक अंतःप्रेरणा - जबाबदाऱ्या छोट्या ठेवा आणि प्रत्येक dependency स्थिर abstraction कडे रोखा. असे केल्यास तुमचा code नवीन गरजांखाली तुटण्याऐवजी त्यांच्यासह वाकतो.
