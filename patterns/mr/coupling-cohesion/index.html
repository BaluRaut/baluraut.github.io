Coupling आणि Cohesion - कोड किती सहज बदलतो हे ठरवणारी दोन बले

Coupling म्हणजे एखादा module दुसऱ्याच्या अंतर्गत रचनेवर किती अवलंबून असतो; cohesion म्हणजे एकाच module मधील जबाबदाऱ्या एकमेकांशी किती घट्टपणे संबंधित असतात. चांगला design coupling कमी करतो आणि cohesion वाढवतो, त्यामुळे एखादा बदल संपूर्ण codebase भर पसरण्याऐवजी स्थानिक राहतो. हा तोल चुकला की, जो checkout flow बदलायला एक तास लागायला हवा तो एक आठवडा घेतो.

01 - काय

Coupling आणि cohesion म्हणजे काय?

Coupling हे module दरम्यानच्या जोडणीची ताकद मोजते: एका class ला आपले काम करण्यासाठी दुसऱ्या class बद्दल किती माहिती असावी लागते. Cohesion हे एकाच module ची अंतर्गत एकाग्रता मोजते: त्याच्या सर्व methods आणि fields एकाच स्पष्ट जबाबदारीला सेवा देतात का. पारंपरिक उद्दिष्ट म्हणजे loose coupling, high cohesion. जो CheckoutService एखाद्या PaymentGateway च्या खासगी fields मध्ये हात घालतो तो tightly coupled असल्याने ठिसूळ असतो; जो एका छोट्या PaymentProcessor interface शी बोलतो तो नसतो.

🔗 Coupling (module दरम्यान)

एक module दुसऱ्याच्या तपशिलांवर किती अवलंबून आहे. एखाद्या स्थिर interface वर अवलंबून राहणे ठीक आहे; खासगी state, क्रम किंवा global variables वर अवलंबून राहणे धोकादायक आहे.

🧲 Cohesion (module च्या आत)

एका module चे भाग एकमेकांशी किती चांगले संबंधित आहेत. एक cohesive Invoice फक्त invoice चे गणित हाताळतो आणि दुसरे काहीही नाही; एक incohesive तो email ही पाठवतो, log ही करतो आणि HTML ही तयार करतो.

⚖️ तडजोड

Cohesion साठी गोष्टी विभागल्यास, निष्काळजीपणे केल्यास, coupling वाढू शकते. सीमारेषा अशा प्रकारे आखणे ही कला आहे की प्रत्येक बाजू cohesive राहील आणि त्यांच्यामधील जोड पातळ व स्थिर राहील.

02 - का

हे का महत्त्वाचे आहे

Software चा खर्च पहिल्या लेखनाने नव्हे तर बदलाने ठरतो. तो बदल किती महाग असेल याचे coupling आणि cohesion हे सर्वात प्रबळ भाकीत करणारे घटक आहेत, आणि ते प्रत्येक code review, bug आणि अंदाजात दिसून येतात.

🎯 स्थानिक बदल

Loosely coupled, highly cohesive design मध्ये एक नवीन payment method जोडणे एका class ला स्पर्श करते. गुंतागुंतीच्या design मध्ये ते cart, order, receipt आणि तुम्हाला अपेक्षित नसलेल्या तीन tests ना स्पर्श करते.

🧪 स्वतंत्रपणे testable

छोट्या interface वर अवलंबून असलेला class एका fake सह मिलिसेकंदांत test करता येतो. live gateway आणि global session शी जोडलेला class संथ, अस्थिर, end-to-end tests भाग पाडतो.

🔁 सुरक्षितपणे बदलण्याजोगे

Checkout पुन्हा न लिहिता Stripe च्या जागी Adyen आणा, कारण checkout एका PaymentProcessor abstraction वर अवलंबून आहे, प्रत्येक layer मधून झिरपणाऱ्या Stripe च्या SDK प्रकारांवर नाही.

👥 समांतर संघ

पातळ, स्थिर जोड एका संघाला inventory आणि दुसऱ्याला billing स्वतःचे मानू देतात, एकमेकांच्या पायात न येता. जास्त coupling सतत समन्वय आणि merge ची डोकेदुखी भाग पाडते.

सोप्या भाषेत

Coupling आणि Cohesion उपमांसह समजावून

एकच कल्पना, ती चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

Cohesion म्हणजे एक व्यवस्थित लावलेली फाइल जिथे प्रत्येक टॅबमध्ये एकच विषय असतो; coupling म्हणजे एक असाइनमेंट पूर्ण करण्यासाठी तुम्हाला किती इतर फाइली उघडाव्या लागतात. प्रत्येक टॅब स्वयंपूर्ण असावा आणि आडवे संदर्भ कमी असावेत.

👩‍💻 डेव्हलपरसाठी

Loose coupling म्हणजे interface ला programming करणे: तुमचा CheckoutService एका ठोस Stripe client ऐवजी PaymentProcessor धरतो. High cohesion म्हणजे असा class ज्याची प्रत्येक method एकाच core state ला स्पर्श करते.

🏢 व्यावसायिकासाठी

एका कंपनीतील विभागांचा विचार करा. Cohesive विभाग एक काम आद्यंत स्वतःचे मानतो; loose coupling म्हणजे ते स्पष्ट करारांतून समन्वय साधतात, एकमेकांच्या टेबलांची उलथापालथ करून नव्हे.

🔌 रोजच्या जीवनातील

भिंतीवरील सॉकेट loosely coupled असतात: योग्य plug असलेले कोणतेही उपकरण चालते, आणि दिवा बदलण्यासाठी तुम्ही घराचे wiring कधीच बदलत नाही. Hardwired उपकरण tightly coupled असते, ते बदलायचे म्हणजे electrician बोलवावा लागतो.

03 - कसे

Coupling कसे कमी करावे आणि cohesion कशी वाढवावी

हालचाल जवळजवळ नेहमी सारखीच असते: ठोस अवलंबित्व शोधा, ते caller च्या स्वतःच्या एका छोट्या interface मागे लपवा, आणि callee ला खरोखर गरजेचा असलेला फक्त data पाठवा. खाली, एक checkout flow tightly coupled वरून loosely coupled कडे जातो.

🧱 Abstractions वर अवलंबून राहा

CheckoutService ला new StripeClient() ऐवजी एक PaymentProcessor interface धरू द्या. ठोस gateway inject केला जातो, त्यामुळे checkout आता Stripe चे SDK अजिबात import करत नाही.

✂️ जबाबदारीनुसार विभागा

Pricing, payment आणि receipts ना cohesive classes मध्ये वेगळे काढा. प्रत्येक एक काम स्वतःचे मानतो, त्यामुळे tax-rule चा बदल फक्त PricingService मध्ये होतो आणि payment code ला कधीच स्पर्श करत नाही.

आधी: tightly coupled checkout

// Tightly coupled: checkout builds its own Stripe client (content + control coupling)
class StripeClient {
  chargeCard(cents: number, token: string, live: boolean) {
    // reaches a real gateway; the `live` flag selects a branch (control coupling)
    return { id: "ch_1", ok: true, mode: live ? "live" : "test" };
  }
}

class CheckoutService {
  private stripe = new StripeClient(); // hard dependency on a concrete class

  checkout(cart: { items: { priceCents: number }[] }, token: string) {
    const total = cart.items.reduce((s, i) => s + i.priceCents, 0);
    // passes a boolean flag that steers the callee's logic (control coupling)
    const charge = this.stripe.chargeCard(total, token, true);
    if (!charge.ok) throw new Error("payment failed");
    return { paid: total, chargeId: charge.id };
  }
}

const receipt = new CheckoutService().checkout(
  { items: [{ priceCents: 1999 }, { priceCents: 500 }] },
  "tok_visa",
);
console.log(receipt); // { paid: 2499, chargeId: "ch_1" }

नंतर: inject केलेल्या processor सह loosely coupled

// Loosely coupled: depend on a narrow interface, pass only the data needed (data coupling)
interface PaymentProcessor {
  charge(amountCents: number, token: string): { id: string; ok: boolean };
}

class StripeProcessor implements PaymentProcessor {
  charge(amountCents: number, token: string) {
    return { id: "ch_1", ok: amountCents > 0 };
  }
}

// Highly cohesive: this class only prices a cart, nothing else
class PricingService {
  totalCents(items: { priceCents: number }[]): number {
    return items.reduce((sum, i) => sum + i.priceCents, 0);
  }
}

class CheckoutService {
  constructor(
    private readonly processor: PaymentProcessor, // injected abstraction
    private readonly pricing: PricingService,
  ) {}

  checkout(items: { priceCents: number }[], token: string) {
    const total = this.pricing.totalCents(items);
    const charge = this.processor.charge(total, token); // no flags, no globals
    if (!charge.ok) throw new Error("payment failed");
    return { paid: total, chargeId: charge.id };
  }
}

// wiring happens once, at the edge
const service = new CheckoutService(new StripeProcessor(), new PricingService());
const receipt = service.checkout([{ priceCents: 1999 }, { priceCents: 500 }], "tok_visa");
console.log(receipt); // { paid: 2499, chargeId: "ch_1" }
# Loosely coupled: depend on a narrow interface, pass only the data needed (data coupling)
from typing import Protocol


class PaymentProcessor(Protocol):
    def charge(self, amount_cents: int, token: str) -> dict: ...


class StripeProcessor:
    def charge(self, amount_cents: int, token: str) -> dict:
        return {"id": "ch_1", "ok": amount_cents > 0}


# Highly cohesive: this class only prices a cart, nothing else
class PricingService:
    def total_cents(self, items) -> int:
        return sum(item["price_cents"] for item in items)


class CheckoutService:
    def __init__(self, processor: PaymentProcessor, pricing: PricingService):
        self._processor = processor  # injected abstraction
        self._pricing = pricing

    def checkout(self, items, token):
        total = self._pricing.total_cents(items)
        charge = self._processor.charge(total, token)  # no flags, no globals
        if not charge["ok"]:
            raise RuntimeError("payment failed")
        return {"paid": total, "charge_id": charge["id"]}


# wiring happens once, at the edge
service = CheckoutService(StripeProcessor(), PricingService())
receipt = service.checkout([{"price_cents": 1999}, {"price_cents": 500}], "tok_visa")
print(receipt)  # {'paid': 2499, 'charge_id': 'ch_1'}
# Loosely coupled: depend on a narrow interface (duck type), pass only the data needed
class StripeProcessor
  # honors the informal PaymentProcessor contract: charge(amount_cents, token)
  def charge(amount_cents, token)
    { id: "ch_1", ok: amount_cents > 0 }
  end
end

# Highly cohesive: this class only prices a cart, nothing else
class PricingService
  def total_cents(items)
    items.sum { |item| item[:price_cents] }
  end
end

class CheckoutService
  def initialize(processor:, pricing:)
    @processor = processor # injected abstraction
    @pricing = pricing
  end

  def checkout(items, token)
    total = @pricing.total_cents(items)
    charge = @processor.charge(total, token) # no flags, no globals
    raise "payment failed" unless charge[:ok]

    { paid: total, charge_id: charge[:id] }
  end
end

# wiring happens once, at the edge
service = CheckoutService.new(processor: StripeProcessor.new, pricing: PricingService.new)
receipt = service.checkout([{ price_cents: 1999 }, { price_cents: 500 }], "tok_visa")
puts receipt.inspect # {:paid=>2499, :charge_id=>"ch_1"}

दोन्ही आवृत्त्या एकसारखेच वागतात, पण दुसरी एक PaymentProcessor inject करते आणि pricing ला त्याच्या स्वतःच्या cohesive class मध्ये काढते. आता नवीन gateway म्हणजे नवीन implementation, tax बदल एकाच जागी राहतो, आणि प्रत्येक सहकारी एका fake इतक्या अंतरावर असल्याने वेगवान unit test करता येतो. हेच coupling आणि cohesion एकत्रितपणे बदलण्याजोगता विकत घेणे.

प्रत्येक edge ला टॅग करा: content, common, control, stamp किंवा data. data coupling पेक्षा वाईट असलेले काहीही दुरुस्त करण्याचे उमेदवार आहे.

30
मापन

आकडे मोजा

प्रत्येक module साठी afferent (Ca) आणि efferent (Ce) coupling आणि प्रत्येक class साठी LCOM काढा, म्हणजे refactor ने मदत केली हे तुम्ही सिद्ध करू शकाल.

40
काढणे

प्रत्येक कामाला घर द्या

Pricing, payment आणि receipts वेगवेगळ्या classes मध्ये काढा. प्रत्येक cohesive होतो: त्याच्या methods एकच state वाटून घेतात.

50
Abstract

एक interface आणा

CheckoutService च्या मालकीचा PaymentProcessor परिभाषित करा, म्हणजे checkout gateway चे SDK import करणे थांबवते.

60
Invert

Dependency inject करा

Checkout च्या आत ठोस processor new करण्याऐवजी तो composition root वर constructor मध्ये पाठवा.

70
सपाट करा

Control flags नष्ट करा

वर्तन निवडणाऱ्या boolean parameters ना वेगळ्या methods किंवा वेगळ्या implementations ने बदला, control coupling काढून टाका.

80
पातळ करा

फक्त वापरले जाणारेच पाठवा

जिथे दोन fields साठी संपूर्ण cart record सोपवला होता, तिथे तेवढी fields पाठवा. Stamp coupling चे data coupling होते.

90
Test

जोड fake करा

प्रत्येक interface च्या fakes विरुद्ध वेगवान unit tests लिहा. fake करण्याची सुलभता म्हणजे coupling कमी झाल्याचा थेट पुरावा.

100
पडताळणी

पुन्हा मोजा आणि कायम करा

LCOM आणि Ce पुन्हा मोजा; ते खाली यायला हवेत. एक fitness function जोडा म्हणजे आकडे मुकाट्याने पुन्हा वर सरकू शकणार नाहीत.

सामान्य धोके

धोके आणि anti-patterns

बहुतांश coupling नुकसान हे मापनाशिवाय लागू केलेल्या चांगल्या हेतूंमुळे स्वतःच ओढवलेले असते. हे नेहमीचे सापळे आहेत.

🕳️ अंतर्गत रचनेत हात घालणे

Content coupling: checkout हा gateway._session वाचतो किंवा दुसऱ्या object च्या खासगी fields बदलतो. callee मध्ये एक rename केला की caller फुटतो. फक्त public methods मधून बोला.

🌍 Shared global state

Common coupling: एक global currentCart किंवा singleton config जे अनेक module वाचतात व लिहितात. execution चा क्रम भार-वाहक बनतो आणि bugs भयानक व अस्थानिक होतात.

🚩 Flag arguments

Control coupling: charge(amount, token, isRefund) जिथे flag एक branch निवडतो. आता caller callee च्या control flow वर अवलंबून असतो. charge आणि refund मध्ये विभागा.

📦 संपूर्ण record पाठवणे

Stamp coupling: फक्त total आणि currency हवे असलेल्या function ला संपूर्ण Order सोपवणे. ते तुम्हाला record च्या आकाराशी जोडते आणि खरे inputs लपवते.

🧺 God class

Low cohesion: एक CheckoutService जो pricing करतो, charge करतो, email करतो, log करतो आणि HTML render करतो. त्याचे LCOM गगनाला भिडलेले असते कारण कोणत्याही दोन methods एकच state वाटून घेत नाहीत. जबाबदारीनुसार विभागा.

🎭 झिरपणारे interfaces

एका vendor च्या SDK ची एकास-एक प्रतिबिंब असलेली abstraction म्हणजे बनावट decoupling. जर interface Stripe-विशिष्ट प्रकार उघड करत असेल, तर providers बदलल्यावरही checkout पुन्हा लिहावे लागते.

संकेत आणि मापके

संकेत आणि कसे मोजायचे

तुम्ही जे मोजत नाही ते तुम्ही व्यवस्थापित करू शकत नाही. हे संकेत "हे गुंतागुंतीचे वाटते" चे रूपांतर तुम्ही कालांतराने मागोवा घेऊ शकाल अशा आकड्यांत करतात.

संकेततो तुम्हाला काय सांगतो
Afferent coupling (Ca)किती इतर module या एकावर अवलंबून आहेत. जास्त Ca म्हणजे तो एक स्थिर गाभा आहे, त्यामुळे तो बदलणे धोकादायक व महाग आहे.
Efferent coupling (Ce)हा module किती module वर अवलंबून आहे. जास्त Ce म्हणजे तो ठिसूळ आहे, त्याचे अनेक सहकारी बदलल्यावर सहज मोडतो.
Instability (I = Ce / (Ca + Ce))1 च्या जवळ म्हणजे चंचल व अवलंबून; 0 च्या जवळ म्हणजे ज्यावर अवलंबून राहतात असा व स्थिर. तपशील अस्थिर असावेत, abstractions स्थिर.
LCOM (lack of cohesion of methods)एका class च्या methods किती कमी fields वाटून घेतात. जास्त LCOM म्हणजे तो class अनेक असंबंधित कामे करत आहे जी विभागली पाहिजेत.
प्रत्येक method चे Fan-in / fan-outcall स्तरावरील स्थानिक coupling. दहा वेगवेगळ्या objects ना call करणारी method ही समन्वयाचा hotspot आणि बदलाचा चुंबक असते.
Change coupling (git history मधून)commits मध्ये सतत एकत्र बदलणाऱ्या files प्रत्यक्षात coupled असतात, जरी कोड स्वतंत्र दिसत असला तरी. ते लपलेले जोड उघड करते.
अंगठ्याचा नियम: तुम्ही सर्वात जास्त बदलणाऱ्या classes वर कमी efferent coupling आणि कमी LCOM साठी प्रयत्न करा. जर एखाद्या class ला जास्त Ca (अनेक त्यावर अवलंबून) आणि जास्त instability दोन्ही असतील, तर ती संपूर्ण प्रणाली वारसाहक्काने घेणारी अडचण बनण्याआधी तिला interface मागे स्थिर करा.
06 - उदाहरणे

प्रत्यक्ष जगातील उदाहरणे

तीन production-सदृश परिस्थिती जिथे coupling आणि cohesion ने निकाल ठरवला.

💳

1 · एकाच payment provider पेक्षा मोठा झालेला checkout

Pattern: inject केलेली PaymentProcessor abstraction

एका commerce संघाने संपूर्ण checkout मध्ये Stripe hardcode केले, मग नवीन बाजारपेठेसाठी एक प्रादेशिक gateway जोडावा लागला आणि डझनभर files ना स्पर्श केल्याशिवाय ते शक्य झाले नाही.

  • प्रत्येक layer Stripe चे प्रकार import करत होते, त्यामुळे gateway pricing, orders आणि receipts मध्ये content-coupled होते.
  • त्यांनी checkout च्या मालकीचा एक PaymentProcessor interface आणला आणि ठोस client edge वर inject केला.
  • प्रादेशिक gateway checkout logic किंवा त्याच्या tests मध्ये कोणताही बदल न करता एक नवीन implementation म्हणून पाठवला गेला.
✅ निकाल: Provider जोडणे हे अनेक-आठवड्यांच्या आडव्या बदलावरून एका नवीन class पर्यंत आले, आणि payment code fake सह unit-testable झाले.
📦

2 · shared state द्वारे inventory शी गुंतलेला order service

Pattern: common coupling काढून टाकणे

एक order pipeline आणि एक inventory job दोन्ही एका shared in-memory stock map ला वाचत व लिहीत होते, त्यामुळे reservations execution च्या क्रमावर अवलंबून होत्या आणि oversells निर्माण करत होत्या.

  • Global map वरील common coupling मुळे bugs अस्थानिक आणि विश्वासार्हपणे पुन्हा निर्माण करणे अशक्य होते.
  • त्यांनी shared map च्या जागी reserve आणि release methods उघड करणारा एक InventoryLedger आणला.
  • Order आणि fulfillment आता shared memory बदलण्याऐवजी स्पष्ट calls द्वारे समन्वय साधतात.
✅ निकाल: Oversell दोष नाहीसे झाले, आणि प्रत्येक service स्वतंत्रपणे समजून घेता व test करता आली, कारण जोड हा एक स्पष्ट करार होता.
📣

3 · cohesion साठी विभागलेला notification god class

Pattern: cohesion वाढवणे, LCOM कमी करणे

एकच Notifier emails format करत होता, SMS पाठवत होता, push payloads लिहीत होता आणि log करत होता, त्यामुळे कोणत्याही channel बदलाने इतरांना मोडण्याचा धोका होता.

  • Static analysis ने खूप जास्त LCOM दाखवले: कोणत्याही दोन methods समान fields वाटून घेत नव्हत्या.
  • त्यांनी तो एका छोट्या Channel interface मागे EmailChannel, SmsChannel आणि PushChannel मध्ये विभागला.
  • एक पातळ NotificationService आता एक channel निवडतो आणि सोपवतो, cohesive व लहान राहतो.
✅ निकाल: प्रत्येक channel स्वतंत्रपणे विकसित झाला, LCOM झपाट्याने घसरले, आणि WhatsApp support जोडणे म्हणजे monolith भर बदल करण्याऐवजी एक नवीन cohesive class.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Coupling आणि cohesion हे object orientation पेक्षाही जुने आहेत, तरीही प्रत्येक आधुनिक architecture ही खरे तर पातळ, cohesive जोड कुठे आखायचे यावरचा एक जुगार आहे.

🧩 Microservice सीमारेषा

Service सीमारेषा म्हणजे network प्रमाणावरील coupling निर्णयच. दोन services मधील जास्त change-coupling हा त्या एकच असाव्यात याचा सर्वात स्पष्ट संकेत आहे.

🛡️ Modular monoliths

संघ monolith ठेवतात पण स्पष्ट interfaces सह cohesive modules लागू करतात, distributed-systems ची डोकेदुखी न घेता loose coupling मिळवतात.

📐 Fitness functions

Architecture tests एक निषिद्ध dependency दिसताच build अयशस्वी करतात, efferent coupling आणि LCOM ला कालांतराने भरकटण्यापासून रोखतात.

🤖 AI-सहाय्यित refactoring

Repository मधून थेट LCOM आणि change-coupling वाचून tools आता extract-class आणि dependency-injection हालचाली सुचवतात.

🔍 बदलाची observability

एकत्र बदलणाऱ्या files साठी git history खणल्याने static analysis एकट्याने चुकवणारे लपलेले coupling समोर येते.

🧪 Contract testing

Consumer-driven contracts loosely coupled services ना स्वतंत्रपणे विकसित होऊ देतात, त्यांच्यामधील पातळ जोड अजूनही टिकतो हे सिद्ध करत.

सारांश: loose coupling आणि high cohesion हे बदलण्याजोगतेचे कालातीत लीव्हर आहेत. stack किंवा प्रमाण कोणतेही असो, जिंकणारी चाल सारखीच असते: अंतर्गत रचना अरुंद interfaces मागे लपवा, प्रत्येक module ला एक काम द्या, आणि जोड पातळ राहावेत म्हणून ते मोजा.
