Polymorphism - एक कॉल, अनेक वर्तने

Polymorphism मुळे एकच call site अनेक प्रकारच्या ऑब्जेक्ट्ससोबत काम करू शकते, आणि प्रत्येक ऑब्जेक्ट आपापल्या पद्धतीने प्रतिसाद देतो. एखादी checkout service charge() एकदाच कॉल करते; एक card gateway, एक wallet, आणि एक bank transfer प्रत्येकजण स्वतःचे logic चालवतो. कॉल करणाऱ्याला concrete type कोणता आहे हे माहीत नसते, आणि runtime dynamic dispatch द्वारे योग्य method निवडतो.

01 - काय

Polymorphism म्हणजे काय?

Polymorphism म्हणजे "अनेक रूपे": एक interface, अनेक implementations. तुम्ही एका abstract contract विरुद्ध प्रोग्रामिंग करता, उदाहरणार्थ charge() method असलेला PaymentMethod, आणि runtime ला त्या contract चे पालन करणारा कोणताही concrete method त्याच्या जागी वापरता येतो. कॉल करणारा एक message पाठवतो; प्राप्त करणारा ऑब्जेक्ट कसा प्रतिसाद द्यायचा हे ठरवतो. हीच ती यंत्रणा आहे जिच्यामुळे payments सुरू करणारा कोड न बदलता तुम्ही नवीन payment provider जोडू शकता.

🧬 Subtype polymorphism

एक StripeCard हा एक PaymentMethod आहे (is-a). जिथे जिथे base type अपेक्षित असतो तिथे कोणताही subtype चालतो. हा classic OO प्रकार आहे, जो dynamic dispatch द्वारे ठरवला जातो.

🔀 Ad-hoc (overloading)

एकच operation चे नाव वेगवेगळ्या argument types ना वेगवेगळ्या कोडने हाताळते, जसे format(amount) विरुद्ध format(amount, currency). प्रत्येक signature नुसार ठरवले जाते.

📦 Parametric (generics)

एकच implementation कोणत्याही type साठी चालते, जसे Repository<T> किंवा generic Cache. Type-agnostic कोड, type नुसार कोणतेही branching नाही.

02 - का

Polymorphism का महत्त्वाचे आहे

प्रणाली नवीन cases जोडून वाढतात: नवीन payment provider, नवीन export format, नवीन notification channel. Polymorphism शिवाय, प्रत्येक नवीन case आधीपासून असलेल्या प्रत्येक conditional मध्ये बदल करते. त्याच्यासह, नवीन वर्तन एका नवीन class च्या रूपात येते जो जुना कोड कधीच पाहत नाही.

➕ जोडणीने विस्तारता येते

एक ApplePayMethod class जोडा आणि तो register करा. Checkout service, invoices, आणि receipts स्पर्श न करता चालू राहतात. नवीन वर्तन म्हणजे नवीन branches नव्हेत.

🧹 Conditional पसारा नष्ट करते

संपूर्ण codebase मध्ये पसरलेले प्रचंड if method == "card" ... elif method == "wallet" एका method.charge() मध्ये संकुचित होते. Type च निर्णय वाहून नेतो.

🧪 सहजपणे testable

कॉल करणारे एका interface वर अवलंबून असल्याने, tests एक बनावट PaymentMethod inject करतात जो कॉल्स नोंदवतो. Network नाही, खरा gateway नाही, monkey-patched globals नाहीत.

🔗 Decoupled स्तर

Order service ला contract माहीत असतो, vendor नाही. त्याच interface मागे Stripe बदलून Adyen आणा आणि वरच्या बाजूला काहीही बदलत नाही. Dependencies abstractions कडे निर्देश करतात.

सोप्या भाषेत

उपमांसह समजावलेले Polymorphism

एकच कल्पना, ती चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती पटते.

🎓 विद्यार्थ्यासाठी

हा एक universal remote आहे. तुम्ही "power" एकदाच दाबता; TV, soundbar, आणि projector प्रत्येकजण त्याच signal चा आपापल्या पद्धतीने अर्थ लावतो. एक बटण, अनेक उपकरणे, सर्वत्र योग्य वर्तन.

👩‍💻 developer साठी

तुम्ही एका interface विरुद्ध paymentMethod.charge(amount) कॉल करता. Runtime ला inject केलेला concrete ऑब्जेक्ट ठरवतो की त्याचा अर्थ card authorization, wallet debit, की bank transfer आहे. Call site कधीच type नुसार branch करत नाही.

🏢 व्यावसायिकासाठी

PDF, HTML, किंवा CSV मध्ये render होणाऱ्या invoice चा विचार करा. Accounting invoice ला "render" करायला सांगते; format ऑब्जेक्ट तपशील हाताळतो. नवीन format जोडा आणि billing screen बदलत नाही.

🔌 रोजच्या जीवनातील आवृत्ती

एक wall socket plug मध्ये बसणारे कोणतेही उपकरण स्वीकारते. Socket ला ते lamp ला वीज देते की laptop charger ला याची पर्वा नसते; ते फक्त वीज पुरवते, आणि प्रत्येक उपकरण आपले काम करते.

03 - कसे

अंतर्गत यंत्रणा कशी चालते

Polymorphism दोन गोष्टींवर आधारित आहे: एक सामायिक contract (method घोषित करणारा interface किंवा base class), आणि dynamic dispatch, म्हणजे runtime lookup जे एका कॉलला base आवृत्तीऐवजी concrete ऑब्जेक्टच्या स्वतःच्या override कडे वळवते.

📜 Contract

एक abstract PaymentMethod charge(amount): Receipt घोषित करतो. तो काय ते सांगतो, कसे ते कधीच नाही. प्रत्येक concrete method ते पूर्ण करण्याचे वचन देतो, त्यामुळे कॉल करणारे सुरक्षितपणे base type धरून ठेवू शकतात.

🎯 Dynamic dispatch

जेव्हा तुम्ही m.charge(amount) कॉल करता, तेव्हा runtime m मागील प्रत्यक्ष ऑब्जेक्ट तपासतो आणि त्या class च्या charge कडे उडी मारतो. हे late binding च overriding ला अंमलात आणते.

एक कॉल, तीन वर्तने - तीन भाषांमध्ये

// Shared contract: every payment method honors charge()
interface Receipt { method: string; amount: number; reference: string; }

abstract class PaymentMethod {
  abstract charge(amount: number): Receipt;
  abstract label(): string;
}

class CardGateway extends PaymentMethod {
  constructor(private last4: string) { super(); }
  charge(amount: number): Receipt {
    // authorize + capture against the card network
    return { method: this.label(), amount, reference: `auth_${this.last4}` };
  }
  label() { return `Card ****${this.last4}`; }
}

class DigitalWallet extends PaymentMethod {
  constructor(private walletId: string) { super(); }
  charge(amount: number): Receipt {
    // debit the stored wallet balance
    return { method: this.label(), amount, reference: `wlt_${this.walletId}` };
  }
  label() { return `Wallet ${this.walletId}`; }
}

class BankTransfer extends PaymentMethod {
  constructor(private iban: string) { super(); }
  charge(amount: number): Receipt {
    // initiate an ACH / SEPA pull
    return { method: this.label(), amount, reference: `sepa_${this.iban.slice(-4)}` };
  }
  label() { return `Bank ${this.iban.slice(-4)}`; }
}

// The caller branches on nothing. Dynamic dispatch does the routing.
class CheckoutService {
  settle(method: PaymentMethod, amount: number): Receipt {
    const receipt = method.charge(amount);
    console.log(`Settled ${amount} via ${receipt.method} -> ${receipt.reference}`);
    return receipt;
  }
}

const methods: PaymentMethod[] = [
  new CardGateway("4242"),
  new DigitalWallet("acct_9f2"),
  new BankTransfer("DE89370400440532013000"),
];
for (const m of methods) checkout.settle(m, 4999);

from dataclasses import dataclass

@dataclass
class Receipt:
    method: str
    amount: int
    reference: str

class PaymentMethod(ABC):

    @abstractmethod
    def label(self) -> str: ...

Binding शैलीतील फरक लक्षात घ्या: TypeScript आणि Python स्पष्ट base contract घोषित करतात, तर Ruby duck typing वर अवलंबून असते - settle charge ला प्रतिसाद देणारा कोणताही ऑब्जेक्ट स्वीकारते, सामायिक पूर्वज आवश्यक नाही. प्रत्येक बाबतीत कॉल करणाऱ्याकडे payment type नुसार शून्य branches असतात.

आधी आणि नंतर - dispatch conditional ची जागा घेते

// BEFORE: the caller owns every case. Each new method edits this switch.
function settle(kind: string, amount: number) {
  if (kind === "card") {
    return authorizeCard(amount);
  } else if (kind === "wallet") {
    return debitWallet(amount);
  } else if (kind === "bank") {
    return initiateTransfer(amount);
  }
  throw new Error(`Unknown method ${kind}`);
}

// AFTER: the object owns its case. New method = new class, caller untouched.
function settle(method: PaymentMethod, amount: number) {
  return method.charge(amount);
}
# BEFORE: the caller owns every case. Each new method edits this branch.
def settle(kind: str, amount: int):
    if kind == "card":
        return authorize_card(amount)
    elif kind == "wallet":
        return debit_wallet(amount)
    elif kind == "bank":
        return initiate_transfer(amount)
    raise ValueError(f"Unknown method {kind}")

# AFTER: the object owns its case. New method = new class, caller untouched.
def settle(method: PaymentMethod, amount: int):
    return method.charge(amount)
# BEFORE: the caller owns every case. Each new method edits this case.
def settle(kind, amount)
  case kind
  when "card"   then authorize_card(amount)
  when "wallet" then debit_wallet(amount)
  when "bank"   then initiate_transfer(amount)
  else raise "Unknown method #{kind}"
  end
end

# AFTER: the object owns its case. New method = new class, caller untouched.
def settle(method, amount)
  method.charge(amount)
end

हाच तो फायदा. Conditional नाहीसा झाला नाही; तो हलला. प्रत्येक concrete class जुन्या switch ची नेमकी एक branch धरून ठेवते, आणि runtime चे dispatch table तुम्ही पूर्वी हाताने लिहीत असलेल्या manual dispatch ची जागा घेते.

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

Hardcoded conditional पासून स्वच्छ polymorphic dispatch पर्यंत, आणि caller ला स्पर्श न करता अगदी नवीन payment method जोडणे.

00
वास

वाढणारा switch ओळखा

Payments एका पसरलेल्या if kind == "card" ... elif "wallet" मधून जातात. प्रत्येक provider जोडणे म्हणजे हा block तसेच receipt आणि refund मार्ग संपादित करणे.

10
Contract

सामायिक वर्तनाला नाव द्या

सर्व methods ना काय करावे लागते ते नोंदवा: charge(amount) आणि label(). ते एक abstract base class किंवा interface म्हणून घोषित करा, म्हणजे PaymentMethod contract.

20
Model

प्रत्येक case ला एक class द्या

CardGateway, DigitalWallet, आणि BankTransfer तयार करा, प्रत्येकजण contract अंमलात आणतो. जुन्या switch ची एक branch प्रत्येक class मध्ये हलते.

30
Override

प्रत्येक class मध्ये charge() अंमलात आणा

प्रत्येक subtype charge() ला स्वतःच्या logic ने override करतो: card authorize करा, wallet debit करा, transfer pull करा. तेच signature, वेगळ्या bodies.

40
Depend

Caller ला base वर type करा

CheckoutService.settle आता string नव्हे तर PaymentMethod स्वीकारते. ते abstraction वर अवलंबून असते, कधीच concrete provider वर नाही.

50
Dispatch

Switch ची जागा एका कॉलने घ्या

Conditional हटवा. Body method.charge(amount) बनते. Dynamic dispatch runtime ला योग्य override कडे वळवते.

60
Construct

Type किनाऱ्यावर निवडा

कोणीतरी अजूनही concrete class निवडलीच पाहिजे, सहसा checkout request वाचणारा एक factory. ती निवड एका सीमेवर राहते, सर्वत्र विखुरलेली नाही.

70
Iterate

मिश्र collections एकसमानपणे हाताळा

विविध PaymentMethod ऑब्जेक्ट्सची एक यादी एका call site मधून loop होते. Retries, split payments, आणि receipts त्यांना एकसारखे वागवतात.

80
Extend

वरच्या बाजूला शून्य बदल करून ApplePay जोडा

Contract अंमलात आणणारा ApplePayMethod लिहा आणि तो factory मध्ये register करा. Checkout, refunds, आणि reporting न बदलता compile आणि चालतात.

Tests amount नोंदवणारा एक stub PaymentMethod पास करतात. Polymorphic seam मुळे कोणत्याही खऱ्या gateway शिवाय service testable होते.

सामान्य धोके

धोके आणि anti-patterns

निष्काळजीपणे केलेले polymorphism तेच coupling पुन्हा निर्माण करते जे काढून टाकण्यासाठी ते होते. या गोष्टींकडे लक्ष द्या.

🔎 Abstraction चे type-checking

Caller मध्ये if (method instanceof CardGateway) लिहिणे मुख्य हेतूलाच हरवते. जर तुम्हाला एखाद्या ऑब्जेक्टला त्याचा concrete type विचारावाच लागत असेल, तर ते वर्तन ऑब्जेक्टवर आणखी एका method म्हणून असले पाहिजे.

⚠️ Liskov substitution चे उल्लंघन

जिथे base ने receipt चे वचन दिले तिथे throw करणारे BankTransfer.charge() contract वर विश्वास ठेवणाऱ्या callers ना तोडते. Subtypes ने base च्या हमी पाळल्या पाहिजेत, त्या कमकुवत करू नयेत.

🧩 Fat interfaces

charge, refund, tokenize, आणि threeDSecure असलेला contract प्रत्येक method ला जे करता येत नाही ते stub करण्यास भाग पाडतो. त्याऐवजी केंद्रित roles मध्ये विभागा.

🪜 खोल inheritance साखळ्या

कोड सामायिक करण्यासाठी PaymentMethod subclasses चे पाच स्तर overrides चा माग काढणे अशक्य करतात. उंच hierarchies पेक्षा composition आणि लहान mixins ला प्राधान्य द्या.

🕳️ मूक default cases

जे हाताळत नाही त्या case साठी शांतपणे null किंवा रिकामे receipt परत करणारे overridden method bugs लपवते. मोठ्याने अपयशी व्हा किंवा गहाळ वर्तन type मध्ये स्पष्ट करा.

🎭 तपासणीशिवाय duck typing

Dynamic भाषांमध्ये, charge नसलेला ऑब्जेक्ट पास केल्यास तो सीमेवर नव्हे तर production मध्ये खोलवर अपयशी होतो. आवश्यक methods किनाऱ्यावरच validate करा, किंवा protocols वापरा.

संकेत आणि मोजमापे

संकेत आणि कसे मोजावे

तुम्ही polymorphism dashboard वर टाकू शकत नाही, पण हे कोड संकेत तुम्हाला सांगतात की ते मदत करत आहे की गहाळ आहे.

संकेततो तुम्हाला काय सांगतो
Type-switch मोजणीत्याच kinds च्या संचावर पुनरावृत्त switch किंवा instanceof गहाळ polymorphic hierarchy दर्शवतो. प्रत्येक duplicate ही अशी जागा आहे जिथे नवीन case विसरला जाईल.
प्रत्येक feature मागे shotgun surgeryजर एक payment method जोडणे अनेक files ना स्पर्श करत असेल, तर dispatch अजूनही manual आहे. चांगले polymorphism ते एकच नवीन class बनवते.
Callers ची cyclomatic complexityService स्तरात जास्त branching बहुधा असे logic दर्शवते जे ऑब्जेक्ट्सवर असले पाहिजे. Dispatch ने हे आकडे सपाट करावेत.
Override सुसंगततासर्व subtypes तेच inputs स्वीकारतात आणि तोच आकार परत करतात का? भिन्न signatures leaky contract आणि Liskov धोक्याचा इशारा देतात.
Test double ची सुलभताजर एखादे dependency बनावट करण्यासाठी implementation पास करण्याऐवजी internals patch करावे लागत असतील, तर तुमचे seams पुरेसे polymorphic नाहीत.
Open-closed पालननवीन वर्तन जोडलेल्या classes च्या रूपात येते की अस्तित्वात असलेल्या files मधील बदललेल्या conditionals च्या रूपात ते मागोवा घ्या. पहिले हे निरोगी pattern आहे.
ठोकताळा: जर तुम्ही स्वतःला त्याच types च्या संचावर तोच if-ladder दोनपेक्षा जास्त ठिकाणी लिहिताना आढळलात, तर type system एका polymorphic method ची मागणी करत आहे. Branch ऑब्जेक्टवर हलवा.
06 - उदाहरणे

वास्तविक जगातील उदाहरणे

तीन production-शैलीच्या प्रणाली जिथे polymorphism भार वाहतो.

💳

1 · providers मधील payment orchestration

Pattern: एक charge() कॉल, अनेक gateways

एक marketplace buyer च्या प्रदेश आणि method नुसार Stripe, Adyen, आणि स्थानिक bank rails मार्गे payments वळवते.

  • प्रत्येक provider एक सामायिक PaymentMethod.charge() अंमलात आणतो, त्यामुळे checkout flow provider-agnostic असतो.
  • Request सीमेवरील एक factory concrete gateway निवडतो; downstream काहीही त्यावर branch करत नाही.
  • नवीन प्रादेशिक provider जोडणे म्हणजे एक class अधिक एक factory नोंद, आणि refunds आणि receipts अस्पर्शित राहतात.
✅ निकाल: नवीन बाजारपेठा classes जोडून सुरू होतात, आणि मुख्य settlement मार्ग स्थिर आणि जोरदार tested राहतो.
📣

2 · Multi-channel notification service

Pattern: email, SMS, push वर एक send()

एक platform एकाच dispatch loop मधून email, SMS, push, आणि in-app channels वर transactional alerts पाठवते.

  • प्रत्येक channel हा एक Notifier आहे जो send(message, recipient) ला स्वतःच्या transport ने override करतो.
  • User preferences channel ऑब्जेक्ट्सची यादी देतात; dispatcher iterate करतो आणि send एकसमानपणे कॉल करतो.
  • एक नवीन WhatsApp channel त्याच contract अंमलात आणणारा एक class म्हणून समाविष्ट होतो, dispatcher मध्ये बदल नाही.
✅ निकाल: Channels स्वतंत्रपणे विकसित होतात आणि fan-out engine कधीच नवीन if branch शिकत नाही.
🧾

3 · Report आणि invoice export pipeline

Pattern: PDF, HTML, CSV साठी एक render()

एक billing system तीच invoice ग्राहकांसाठी PDF, web view साठी HTML, आणि accounting imports साठी CSV मध्ये export करते.

  • प्रत्येक format हा एक Renderer आहे जो render(invoice) override करतो; invoice डेटा धरून ठेवते, renderer रूप.
  • Export endpoint विनंती केलेला format एका renderer ऑब्जेक्टवर सोडवते आणि एक method कॉल करते.
  • एक नवीन XLSX export invoice model किंवा endpoint चा dispatch कोड न बदलता जोडले जाते.
✅ निकाल: Output formats मुक्तपणे वाढतात तर invoice domain model स्वच्छ आणि एकल-उद्देशीय राहते.
07 - प्रासंगिकता

आधुनिक प्रासंगिकता

Polymorphism हा classic OO चा अवशेष नाही; आधुनिक typed आणि dynamic भाषा वर्तन कसे रचतात याचा तो पाया आहे.

🧱 Protocols आणि traits

Swift protocols, Rust traits, आणि Go interfaces हे inheritance शिवाय polymorphism आहेत: वर्तन क्षमतेनुसार बांधले जाते, जे compile time ला structural आणि duck typing चे प्रतिध्वनी आहे.

🔤 Structural typing

TypeScript नावांशी नव्हे तर आकारांशी जुळते. योग्य methods असलेली कोणतीही गोष्ट एका interface चे समाधान करते, जे static सुरक्षितता आणि duck-typed लवचिकता यांचे मिश्रण आहे.

🧬 Bounded generics

Constraints सह parametric polymorphism, जसे <T extends PaymentMethod>, हमी टिकवून ठेवत अनेक types साठी चालणारी एक implementation देते.

🧩 Sum types आणि pattern match

Functional भाषा आणि आधुनिक Rust व Scala बंद sum types ला exhaustive matching सोबत जोडतात, जो खुल्या subtype dispatch चा एक हेतुपुरस्सर पर्याय आहे.

🔌 Plugin architectures

Extensions, adapters, आणि drivers सर्वजण एका सामायिक interface वर अवलंबून असतात जेणेकरून तिसरे पक्ष core फोर्क न करता वर्तन जोडतात, तोच open-closed फायदा.

🌐 Polyglot service contracts

gRPC आणि OpenAPI एक contract परिभाषित करतात ज्याचे अनेक भाषा implementations समाधान करतात, म्हणजे process आणि network सीमांपलीकडे ताणलेले subtype substitution.

सारांश: Polymorphism हा तो मार्ग आहे ज्याने तुम्ही कोड नवीन cases साठी खुला आणि बदलासाठी बंद बनवता. Class, interface, protocol, किंवा generic द्वारे असो, उद्दिष्ट कायम असते: एका गोष्टीला कॉल करा, type ला वर्तन ठरवू द्या, आणि संपादन करण्याऐवजी जोडून वाढा.
