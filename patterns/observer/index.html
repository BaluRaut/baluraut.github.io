Behavioral Pattern

The Observer pattern - one change, many reactions

Observer defines a one-to-many dependency between objects: when one object (the subject) changes state, all its dependents (the observers) are notified and updated automatically. It is the backbone of event systems, UI data binding, and reactive streams. You get loose coupling between the thing that changes and the many things that care.

01 - What

What is the Observer pattern?

Observer lets an object publish changes without knowing who is listening. A subject keeps a list of observers and, whenever its state changes, walks that list calling an update method on each one. Observers can subscribe and unsubscribe at runtime, so the set of listeners is completely dynamic and the subject stays ignorant of concrete observer types.

📣 Subject (publisher)

Holds the state that matters and a registry of observers. Exposes subscribe, unsubscribe, and notify. It never knows the concrete observer classes.

👂 Observer (subscriber)

Implements a common interface, usually one update method. It reacts to a change however it likes, independent of the other observers.

🔔 Notification

When state changes, the subject iterates its list and calls update on each observer. Data is either pushed in the call or pulled back from the subject.

Key mental model: the subject does not call specific objects, it broadcasts. Observer inverts the direction of knowledge, the many depend on the one, and the one depends on nothing but an interface.
02 - Why

Why Observer exists

Without it, the object that changes has to hardcode calls to every object that reacts. Add a new consumer and you edit the producer. Observer breaks that dependency so producers and consumers evolve separately.

🔗 Loose coupling

The subject depends only on an observer interface, not on concrete listeners. You can add, remove, or swap reactions without touching the code that changes state.

📡 Broadcast communication

One state change fans out to many interested parties in a single step. New consumers just subscribe; the producer never learns their names.

⏱️ Runtime flexibility

Observers register and deregister while the program runs. The set of reactions is data, not a fixed call graph baked in at compile time.

🎯 Separation of concerns

The thing that owns state stays focused on its own job. Logging, UI refresh, caching, and analytics each live in their own observer.

In Plain Terms

Observer explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is a class group chat. When the teacher posts the exam date, everyone subscribed gets the message at once. The teacher does not text each student individually, and students can leave the group anytime.

👩‍💻 For a developer

It is addEventListener. A button holds a list of callbacks; on click it calls them all. The button knows nothing about your handlers, and you can remove a listener when the component unmounts.

🏢 For a professional

Think of a company mailing list. Publish one announcement and every subscriber receives it. People opt in and out freely, and the sender never maintains a per-person address book.

📰 Everyday version

A newspaper subscription. The paper prints once and delivers to every current subscriber. Cancel and the deliveries stop; the publisher does not need to know who you are.

03 - How

How it works under the hood

Two moving parts: a subject that maintains a list of observers and fires notifications, and observers that implement a shared interface and react. The only real design choice is how data reaches the observer.

📤 Push model

The subject sends the changed data inside the notification, for example update(temperature). Simple and self-contained, but the subject must guess what every observer needs.

📥 Pull model

The subject only signals that something changed; each observer calls back to read exactly the state it wants. More flexible, at the cost of extra round trips and tighter access to the subject.

A realistic implementation

type Listener<T> = (event: T) => void;

class Subject<T> {
  private listeners = new Set<Listener<T>>();

  // subscribe returns an unsubscribe handle, the modern idiom
  subscribe(fn: Listener<T>): () => void {
    this.listeners.add(fn);
    return () => this.listeners.delete(fn);
  }

  // push model: the changed data travels with the notification
  notify(event: T): void {
    // copy first so an observer unsubscribing mid-notify is safe
    for (const fn of [...this.listeners]) fn(event);
  }
}

// --- usage: a weather station broadcasting readings ---
interface Weather { tempC: number; humidity: number }
const station = new Subject<Weather>();

const off = station.subscribe(w => console.log(`Phone: ${w.tempC}C`));
station.subscribe(w => console.log(`Log: humidity ${w.humidity}%`));

station.notify({ tempC: 21, humidity: 55 }); // both observers fire
off();                                        // phone stops listening
station.notify({ tempC: 22, humidity: 50 }); // only the log fires

from dataclasses import dataclass
from typing import Callable

@dataclass
class Weather:
    temp_c: int
    humidity: int

class Subject:
    def __init__(self) -> None:
        self._listeners: list[Callable[[Weather], None]] = []

    # subscribe returns an unsubscribe handle, the modern idiom
    def subscribe(self, fn: Callable[[Weather], None]) -> Callable[[], None]:
        self._listeners.append(fn)
        return lambda: self._listeners.remove(fn)

    # push model: the changed data travels with the notification
    def notify(self, event: Weather) -> None:
        # copy first so an observer unsubscribing mid-notify is safe
        for fn in list(self._listeners):
            fn(event)

# --- usage: a weather station broadcasting readings ---
station = Subject()

off = station.subscribe(lambda w: print(f"Phone: {w.temp_c}C"))
station.subscribe(lambda w: print(f"Log: humidity {w.humidity}%"))

station.notify(Weather(21, 55))  # both observers fire
off()                            # phone stops listening
station.notify(Weather(22, 50))  # only the log fires

Weather = Struct.new(:temp_c, :humidity)

class Subject
  def initialize
    @listeners = []
  end

  # subscribe returns an unsubscribe handle, the modern idiom
  def subscribe(&fn)
    @listeners << fn
    -> { @listeners.delete(fn) }
  end

  # push model: the changed data travels with the notification
  def notify(event)
    # dup first so an observer unsubscribing mid-notify is safe
    @listeners.dup.each { |fn| fn.call(event) }
  end
end

# --- usage: a weather station broadcasting readings ---
station = Subject.new

off = station.subscribe { |w| puts "Phone: #{w.temp_c}C" }
station.subscribe { |w| puts "Log: humidity #{w.humidity}%" }

station.notify(Weather.new(21, 55)) # both observers fire
off.call                            # phone stops listening
station.notify(Weather.new(22, 50)) # only the log fires

Returning an unsubscribe function from subscribe is the pattern's most important ergonomic upgrade. It gives every subscriber a matching teardown, which is exactly what prevents the lapsed-listener leak described below.

05 - Step by Step

The 0 → 100 flow

From defining the contract to a clean teardown - implementing and using Observer in order.

00
Contract

Define the observer interface

Decide the method the subject will call, for example update(event). This one contract is the only thing the subject ever depends on.

10
Subject

Build the subject registry

Give the subject a collection of observers plus subscribe, unsubscribe, and notify. A set avoids duplicate registrations.

20
Model

Choose push or pull

Push sends the changed data in the call; pull sends only a signal and lets observers read what they need. Pick based on how varied the observers are.

30
Observer

Implement concrete observers

Write classes or callbacks that satisfy the interface. Each reacts independently: refresh a view, write a log, invalidate a cache.

40
Register

Subscribe observers at runtime

Observers call subscribe and keep the returned unsubscribe handle. The subject now knows to include them in future notifications.

50
Change

Mutate the subject state

Some caller updates the subject. The subject detects the change and prepares to broadcast it to everyone listening.

60
Notify

Broadcast to all observers

The subject iterates its list, calling update on each observer. Iterate over a copy so a mid-notify unsubscribe cannot corrupt the loop.

70
React

Observers handle the event

Each observer runs its own logic. Failures should be isolated so one throwing observer does not block the rest of the broadcast.

80
Order

Consider ordering and reentrancy

If an observer changes the subject during notify, you can trigger a cascade. Guard against reentrancy and do not assume any notification order.

90
Unsubscribe

Detach when done

When an observer is no longer needed, call its unsubscribe handle. This removes the reference and is the single most important step for memory health.

100
Verify

Confirm no leaks remain

Check that destroyed observers are gone from the registry. In long-lived subjects, weak references or explicit teardown keep the listener list from growing forever.

Common Pitfalls

Pitfalls & anti-patterns

Observer is easy to add and easy to abuse. These are the failures that show up in real systems.

🕳️ Lapsed-listener leak

The classic bug: an observer is discarded but never unsubscribed, so the subject keeps a strong reference to it forever. It cannot be garbage collected and its update still runs. Always pair subscribe with unsubscribe, or use weak references.

🔁 Notification cascades

An observer that mutates the subject during notify can trigger another notify, and another. Uncontrolled reentrancy leads to redundant work, stale intermediate states, or infinite loops.

🧨 One observer breaks the broadcast

If notify calls observers without isolating errors, a single thrown exception aborts the loop and later observers never fire. Catch per observer or the change silently half-applies.

❓ Unpredictable order

Code that secretly depends on observers firing in a particular order is fragile. Registration order is an implementation detail, not a contract you should lean on.

🌀 Update storms

Fine-grained changes each firing a notification can flood observers - hundreds of updates for one logical operation. Batch or debounce, or coalesce changes before broadcasting.

🔗 Hidden coupling via the event

Overloading events with subject internals recreates the tight coupling you were escaping. Keep payloads small and stable so observers do not reach into subject internals.

Trade-offs

Trade-offs & when to use

Observer buys decoupling and dynamic reactions, but it trades away directness and can obscure control flow.

AspectDetail
ProsLoose coupling, runtime subscribe/unsubscribe, one-to-many broadcast, open for new observers without editing the subject.
ConsIndirect control flow that is hard to trace, risk of memory leaks, cascades, and undefined notification order.
Use whenMany objects must react to a state change, the set of listeners varies at runtime, and the producer should not know its consumers.
Avoid whenThere is exactly one, fixed consumer, or when the reactive indirection makes a simple direct call needlessly hard to follow.
ComplexityLow to add, moderate to operate safely - lifecycle management and reentrancy are the real cost, not the initial code.
RelatedPublish/subscribe (decoupled via a broker), Mediator (centralizes interaction), Reactive streams (observers with backpressure and operators).
Rule of thumb: reach for Observer when one changing thing has many, changing listeners. If communication is many-to-many and needs coordination rules, reach for Mediator instead.
06 - Case Studies

Real-world case studies

Three places the Observer pattern quietly runs the show.

🖱️

1 · Browser DOM events

Pattern: push-model observers via addEventListener

Every UI framework and vanilla page relies on DOM elements broadcasting events to registered handlers.

  • An element is the subject; addEventListener subscribes a callback observer.
  • On an interaction the element pushes an Event object to every handler.
  • removeEventListener unsubscribes; forgetting it on a removed node leaks the handler.
✅ Outcome: Any number of independent handlers respond to the same click, with the element knowing nothing about them.
🌊

2 · Reactive streams (RxJS, Reactor)

Pattern: observers with operators and backpressure

Reactive libraries generalize Observer into composable streams of events over time.

  • An Observable is the subject; subscribe attaches an observer and returns a Subscription.
  • Operators like map, filter, and debounce transform the notification stream.
  • Unsubscribing tears down the chain, and backpressure controls fast producers.
✅ Outcome: Complex async event pipelines are built declaratively on the same subscribe-and-notify core.
🗂️

3 · State stores and data binding

Pattern: UI observers of a central store

Redux, MobX, Vue, and signals all notify subscribed views when application state changes.

  • The store is the subject; components subscribe to slices of state they care about.
  • A dispatched change notifies subscribers, which re-render with the new value.
  • Frameworks auto-unsubscribe on unmount to prevent the lapsed-listener leak.
✅ Outcome: The UI stays in sync with state automatically, with no manual wiring between the store and each view.
07 - Relevance

Modern relevance

Observer is more central now than when the Gang of Four named it, hidden inside the tools we use every day.

⚡ Signals and fine-grained reactivity

Signals in Solid, Angular, Vue, and Preact are Observer at the value level - reading a signal subscribes, writing it notifies, with automatic dependency tracking.

🌊 Reactive programming everywhere

RxJS, Reactor, and Combine turn the pattern into full stream algebras with operators, scheduling, and backpressure for async event flows.

📨 Event-driven architectures

Kafka, message brokers, and pub/sub systems scale the same publish-and-subscribe idea across services and machines.

🧹 Lifecycle-safe subscriptions

Framework hooks, AbortController, and effect cleanup make unsubscribe automatic, retiring the lapsed-listener leak by default.

🪶 Weak references

WeakRef and weak listener collections let subjects hold observers without preventing garbage collection, a built-in guard against leaks.

🔌 WebSockets and live data

Real-time dashboards, collaborative editors, and live feeds are observers reacting to a server that pushes changes as they happen.

Bottom line: Observer is how software reacts to change without hardwiring who reacts to what. From a button click to a distributed event bus, the same subscribe-and-notify core underpins nearly every interactive and reactive system you touch.
