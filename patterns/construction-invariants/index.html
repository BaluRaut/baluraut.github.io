Construction & Invariants - objects that are valid from the first line

An object should be trustworthy the instant it exists. When a constructor enforces the invariants - an Order with at least one line item, an Email that is actually an address, Money that never goes negative - the rest of the system can stop re-checking and just use it. The alternative is a codebase full of half-built objects and defensive null checks that leak everywhere.

01 - What

What is construction & invariants?

An invariant is a rule that must always hold true for an object over its entire lifetime: an Order always has at least one line item, a Money value always carries a currency, a ShippingAddress always has a non-empty postal code. Construction is the moment you get to guarantee those rules. If the constructor refuses to build anything that would violate them, then every method downstream can assume a valid object and never re-validate.

🧱 Valid from line one

The constructor either returns a fully valid object or throws. There is no window in which a caller holds a partially initialized, rule-breaking instance.

🚧 Guard clauses up front

The constructor checks preconditions first and rejects bad input immediately, before assigning any field. Fail fast, close to the source of the mistake.

🏭 Static factory methods

Named builders like Order.forCustomer(...) or Money.fromCents(...) express intent, validate, and can return cached or subtype instances.

The core building blocks

Key mental model: a constructor is a gatekeeper, not a data-loader. Its job is not to copy arguments into fields, it is to refuse to create an object that could ever be invalid. Push validation to the moment of creation and the whole system stops writing defensive checks.
02 - Why

Why enforce invariants at construction

The cheapest place to reject bad data is the boundary where it enters your object model. Every rule you enforce in a constructor is a rule no caller, service, or database ever has to re-check.

🛡️ One place to trust

If Order can only exist with valid line items, checkout, invoicing, and shipping code never need to guard against an empty order. The invariant is proven once, at birth.

💥 Fail fast, fail near

A guard clause throws at the exact call site that passed bad input, with a clear message. Bugs surface at creation, not three services later as a mysterious null.

🧹 Less defensive noise

Without invariants, every method starts with if (this.items == null) checks. Enforce them once and that scattered defensive code simply disappears.

🔐 Encapsulation that holds

Public setters let any caller drop an object into an illegal state after the fact. Intent-revealing methods that re-check invariants keep the object honest for its whole life.

In Plain Terms

Construction & invariants explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is like a form that will not submit until every required field is filled. You cannot even create the record until the rules are satisfied, so there is no such thing as a half-valid submission floating around.

👩‍💻 For a developer

The constructor is a validating parser: raw input goes in, and either a guaranteed-valid object comes out or it throws. After that line, you never write another if valid check for that object.

🏢 For a professional

Think of a bank opening an account. Identity, minimum deposit, and signatures are verified before the account number is issued. There is no active account that skipped the checks.

🏗️ Everyday version

A building only gets a certificate of occupancy once it passes inspection. You do not move families into a half-built structure and inspect it later, you gate on the rules before it opens.

03 - How

How to enforce invariants in construction

There are two moves. First, make the constructor reject anything invalid with guard clauses. Second, keep the object valid over time by exposing intent-revealing methods that re-check the invariant, never raw setters that can break it.

🚪 Gate at creation

Guard clauses run first: reject empty item lists, negative amounts, malformed emails. Assign fields only after every precondition passes, so the object is never partially built.

🔁 Preserve over the lifetime

Mutation flows through methods like addItem or applyDiscount that re-assert the invariant. No public setter can quietly leave the order empty or the total negative.

A real class enforcing its invariants

// Money: a value object that can never be malformed
class Money {
  private constructor(
    readonly amountCents: number,
    readonly currency: string,
  ) {}

  // Static factory: validate, then build
  static fromCents(cents: number, currency: string): Money {
    if (!Number.isInteger(cents)) throw new Error("amount must be whole cents");
    if (!/^[A-Z]{3}$/.test(currency)) throw new Error("currency must be ISO 4217");
    return new Money(cents, currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("currency mismatch");
    return new Money(this.amountCents + other.amountCents, this.currency);
  }
}

class LineItem {
  constructor(
    readonly sku: string,
    readonly quantity: number,
    readonly unitPrice: Money,
  ) {
    // Guard clauses run before the object is usable
    if (!sku.trim()) throw new Error("sku is required");
    if (!Number.isInteger(quantity) || quantity < 1)
      throw new Error("quantity must be at least 1");
  }

  subtotal(): Money {
    return Money.fromCents(this.unitPrice.amountCents * this.quantity, this.unitPrice.currency);
  }
}

class Order {
  private readonly items: LineItem[];

  // Private: the ONLY way in is the validated factory below
  private constructor(readonly id: string, readonly customerId: string, items: LineItem[]) {
    if (items.length === 0) throw new Error("an order needs at least one line item");
    this.items = [...items]; // defensive copy, no shared mutable reference
  }

  static forCustomer(customerId: string, items: LineItem[]): Order {
    if (!customerId.trim()) throw new Error("customerId is required");
    return new Order(crypto.randomUUID(), customerId, items);
  }

  // Intent-revealing mutation, NOT a public setter
  addItem(item: LineItem): void {
    this.items.push(item);
  }

  removeItem(sku: string): void {
    if (this.items.length === 1 && this.items[0].sku === sku)
      throw new Error("cannot remove the last line item"); // invariant preserved
    const next = this.items.filter((i) => i.sku !== sku);
    this.items.length = 0;
    this.items.push(...next);
  }

  total(): Money {
    return this.items
      .map((i) => i.subtotal())
      .reduce((sum, s) => sum.add(s));
  }
}

// Usage: object is valid the instant it exists
const order = Order.forCustomer("cust_42", [
  new LineItem("SKU-BOOK-1", 2, Money.fromCents(1999, "USD")),
]);
order.addItem(new LineItem("SKU-PEN-9", 5, Money.fromCents(150, "USD")));
console.log(order.total().amountCents); // 4748

from __future__ import annotations
from dataclasses import dataclass
from functools import reduce
import re
import uuid


@dataclass(frozen=True)
class Money:  # value object: immutable, always well-formed
    amount_cents: int
    currency: str

    @staticmethod
    def from_cents(cents: int, currency: str) -> "Money":
        if not isinstance(cents, int):
            raise ValueError("amount must be whole cents")
        if not re.fullmatch(r"[A-Z]{3}", currency):
            raise ValueError("currency must be ISO 4217")
        return Money(cents, currency)

    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError("currency mismatch")
        return Money(self.amount_cents + other.amount_cents, self.currency)


class LineItem:
    def __init__(self, sku: str, quantity: int, unit_price: Money) -> None:
        # Guard clauses run before any field is trusted
        if not sku.strip():
            raise ValueError("sku is required")
        if not isinstance(quantity, int) or quantity < 1:
            raise ValueError("quantity must be at least 1")
        self.sku = sku
        self.quantity = quantity
        self.unit_price = unit_price

    def subtotal(self) -> Money:
        return Money.from_cents(self.unit_price.amount_cents * self.quantity,
                                self.unit_price.currency)


class Order:
    # Private constructor convention: build via for_customer()
    def __init__(self, id: str, customer_id: str, items: list[LineItem]) -> None:
        if len(items) == 0:
            raise ValueError("an order needs at least one line item")
        self._id = id
        self._customer_id = customer_id
        self._items = list(items)  # defensive copy

    @classmethod
    def for_customer(cls, customer_id: str, items: list[LineItem]) -> "Order":
        if not customer_id.strip():
            raise ValueError("customer_id is required")
        return cls(str(uuid.uuid4()), customer_id, items)

    def add_item(self, item: LineItem) -> None:  # intent-revealing, not a setter
        self._items.append(item)

    def remove_item(self, sku: str) -> None:
        if len(self._items) == 1 and self._items[0].sku == sku:
            raise ValueError("cannot remove the last line item")  # invariant held
        self._items = [i for i in self._items if i.sku != sku]

    def total(self) -> Money:
        return reduce(lambda acc, i: acc.add(i.subtotal()),
                      self._items[1:], self._items[0].subtotal())


# Usage: valid from the first line
order = Order.for_customer("cust_42", [
    LineItem("SKU-BOOK-1", 2, Money.from_cents(1999, "USD")),
])
order.add_item(LineItem("SKU-PEN-9", 5, Money.from_cents(150, "USD")))
print(order.total().amount_cents)  # 4748

require "securerandom"

# Value object: frozen and always well-formed
class Money
  attr_reader :amount_cents, :currency

  def self.from_cents(cents, currency)
    raise ArgumentError, "amount must be whole cents" unless cents.is_a?(Integer)
    raise ArgumentError, "currency must be ISO 4217" unless currency.match?(/\A[A-Z]{3}\z/)
    new(cents, currency)
  end

  def initialize(amount_cents, currency)
    @amount_cents = amount_cents
    @currency = currency
    freeze
  end

  def add(other)
    raise ArgumentError, "currency mismatch" unless other.currency == currency
    Money.new(amount_cents + other.amount_cents, currency)
  end
end

class LineItem
  attr_reader :sku, :quantity, :unit_price

  def initialize(sku, quantity, unit_price)
    # Guard clauses reject bad input at construction
    raise ArgumentError, "sku is required" if sku.to_s.strip.empty?
    raise ArgumentError, "quantity must be at least 1" unless quantity.is_a?(Integer) && quantity >= 1
    @sku = sku
    @quantity = quantity
    @unit_price = unit_price
  end

  def subtotal
    Money.from_cents(unit_price.amount_cents * quantity, unit_price.currency)
  end
end

class Order
  attr_reader :id, :customer_id

  # Prefer the factory; initialize enforces the core invariant
  def initialize(id, customer_id, items)
    raise ArgumentError, "an order needs at least one line item" if items.empty?
    @id = id
    @customer_id = customer_id
    @items = items.dup # defensive copy
  end
  private_class_method :new

  def self.for_customer(customer_id, items)
    raise ArgumentError, "customer_id is required" if customer_id.to_s.strip.empty?
    allocate.tap { |o| o.send(:initialize, SecureRandom.uuid, customer_id, items) }
  end

  def add_item(item) # intent-revealing method, not a setter
    @items.push(item)
  end

  def remove_item(sku)
    if @items.size == 1 && @items.first.sku == sku
      raise ArgumentError, "cannot remove the last line item" # invariant preserved
    end
    @items.reject! { |i| i.sku == sku }
  end

  def total
    @items.map(&:subtotal).reduce { |sum, s| sum.add(s) }
  end
end

# Usage: the object is valid the moment it is born
order = Order.for_customer("cust_42", [
  LineItem.new("SKU-BOOK-1", 2, Money.from_cents(1999, "USD")),
])
order.add_item(LineItem.new("SKU-PEN-9", 5, Money.from_cents(150, "USD")))
puts order.total.amount_cents # 4748

Notice what is missing: there is no setItems, no way to construct an empty order, and no path that assigns fields before the guard clauses pass. The constructor is private and the only public entry points, the static factories, validate first. Mutation happens through addItem and removeItem, both of which protect the "at least one item" rule.

Before and after: the leaky version

// ANTI-PATTERN: anemic object with public setters
class Order {
  id = "";
  customerId = "";
  items: LineItem[] = []; // starts empty and invalid
  status = "";
}

// Half-built and rule-breaking, yet the type system is happy
const order = new Order();
order.customerId = "cust_42"; // did anyone set items? who knows
checkout(order);              // may explode on an empty order deep in the call stack

# ANTI-PATTERN: anemic object, no invariants
class Order:
    def __init__(self):
        self.id = ""
        self.customer_id = ""
        self.items = []   # empty and invalid
        self.status = ""

# Half-built object escapes into the system
order = Order()
order.customer_id = "cust_42"   # items never set
checkout(order)                 # blows up later, far from the mistake

# ANTI-PATTERN: attr_accessor exposes every field
class Order
  attr_accessor :id, :customer_id, :items, :status
end

# Nothing stops an empty, half-built order
order = Order.new
order.customer_id = "cust_42"   # items still nil
checkout(order)                 # fails somewhere downstream

05 - Step by Step

The 0 → 100 flow

From raw input to a guaranteed-valid object that stays valid, the whole journey in order.

00
Define

State the invariants

Write down the rules that must always hold: an order has at least one line item, money is never negative, an email matches an address shape. These become the object's contract.

10
Hide

Make the constructor private

Prevent arbitrary new calls that could skip validation. Callers must go through a named entry point you control.

20
Expose

Add a static factory method

Provide Order.forCustomer(...) or Email.parse(...) so intent is clear and there is a single validated path to creation.

30
Guard

Check preconditions first

Guard clauses at the top reject blank ids, empty item lists, and malformed values before any field is assigned. Fail fast with a clear message.

40
Reject

Throw on violation

If any rule is broken, throw immediately at the call site that supplied bad input, so the bug surfaces where it was made, not three layers away.

50
Copy

Defensively copy inputs

Clone incoming collections so a caller cannot mutate the internal list later and quietly break the invariant from the outside.

60
Assign

Set fields only when valid

Only after every guard passes do you store state. The object transitions straight from "not created" to "fully valid," with no half-built middle.

70
Return

Hand back a trustworthy object

The factory returns an instance every method can rely on. Downstream code carries no defensive null or emptiness checks.

80
Encapsulate

Expose intent-revealing methods

Instead of setters, offer addItem, applyDiscount, cancel. Each expresses a real operation and re-checks the invariant.

90
Preserve

Re-assert rules on mutation

A method that would leave the order empty or the balance negative refuses. The invariant holds not just at birth but for the object's whole life.

100
Compose

Build bigger objects from valid parts

Because each value object is self-validating, an Order of LineItems of Money is correct by construction, all the way up.

Common Pitfalls

Pitfalls & anti-patterns

Most invariant bugs come from creating objects in two steps, or from letting callers reach in and change state. These are the usual culprits.

🧟 Anemic objects

A bag of public fields with no behavior and no rules. Nothing stops an empty order or negative money, so every consumer has to validate instead. The object cannot protect itself.

🪣 The empty-then-fill pattern

Constructing a blank object and setting fields afterward creates a window where it is invalid. Someone will use it during that window, or forget a field entirely.

🔓 Public setters everywhere

attr_accessor, auto-properties, or exposed fields let any caller drop the object into an illegal state after the fact. Setters that bypass the rules undo the constructor's work.

🕳️ Leaking internal collections

Returning or storing the caller's list without copying lets outside code mutate internals directly, so the "at least one item" rule can be violated from a distance.

🤐 Silent coercion

Quietly clamping a negative amount to zero or defaulting a bad currency hides caller mistakes. Guard clauses should reject and explain, not paper over invalid input.

🏗️ Validation in a separate step

An order.validate() method you must remember to call means invalid objects can and will be used before anyone calls it. Validation belongs in construction, not in an optional afterthought.

Signals & Metrics

Signals & how to measure

You can feel weak invariants in a codebase before you can prove them. These signals tell you whether construction is doing its job.

SignalWhat it tells you
Defensive checks per methodMany if x == null or emptiness guards inside business methods mean the constructor is not establishing invariants. The checks migrated downstream.
Setter count vs. method countA class that is mostly getters and setters is anemic. A healthy domain object has few or no setters and several intent-revealing methods.
Number of construction pathsIf an object can be built five different ways, it is hard to guarantee all five validate. Funneling through one factory tightens the guarantee.
Invalid-state bugs in productionNull pointer and "empty order" incidents point to objects escaping creation half-built. Each such bug is a missing guard clause.
Test setup complexityIf building a valid object in a test takes many lines and manual field-setting, construction is not encapsulating its rules well.
Distance from cause to crashBugs that surface far from the code that caused them signal late validation. Fail-fast constructors shrink that distance to zero.
Rule of thumb: if you cannot construct the object without it being valid, you never have to check that it is valid. Count the runtime guards outside constructors; every one you can delete after tightening a constructor is proof the invariant now lives in the right place.
06 - Case Studies

Real-world case studies

Three production-style systems where constructor-enforced invariants carry real weight.

💳

1 · Payments: a Money value object

Pattern: validated value object, no floats

A payments platform needs amounts that never lose precision and never mix currencies. Money is modeled as integer cents plus an ISO currency code.

  • The static factory rejects non-integer cents and any currency that is not a valid ISO 4217 code.
  • Arithmetic like add refuses to combine two different currencies, throwing instead of silently converting.
  • The object is immutable, so a shared Money instance can never be mutated into an illegal amount.
✅ Outcome: whole categories of rounding and currency-mixing bugs become impossible, because an invalid Money simply cannot be constructed.
🛒

2 · E-commerce: Order aggregate

Pattern: aggregate root with a lifetime invariant

A checkout service treats Order as an aggregate that must always hold at least one line item and a consistent total.

  • A private constructor plus Order.forCustomer(...) guarantees no order is created empty.
  • removeItem refuses to delete the final line item, preserving the invariant through mutation.
  • Line items and money are themselves validated value objects, so the whole aggregate is correct by construction.
✅ Outcome: downstream invoicing, tax, and fulfillment code drops its empty-order guards and trusts every Order it receives.
📧

3 · Notifications: a parsed Email address

Pattern: parse, don't validate-and-hope

A notifications service sends email, SMS, and push. Email addresses enter from signup forms, imports, and webhooks, all untrusted.

  • Email.parse(raw) normalizes and validates once at the boundary, returning a typed Email or throwing.
  • Every function downstream takes an Email, not a string, so "is this a valid address" is answered by the type.
  • Because the value is immutable, a normalized address cannot later be corrupted into an unsendable string.
✅ Outcome: bounce rates from malformed addresses drop, and the validation logic lives in exactly one place instead of scattered across senders.
07 - Relevance

Modern relevance

Constructor-enforced invariants are not a legacy OOP habit, they underpin how modern type-driven and domain-driven systems stay correct.

🧩 Domain-driven design

Aggregates and value objects are defined by the invariants they protect. Enforcing rules at construction is the mechanism that makes an aggregate a real consistency boundary.

🔒 Parse, don't validate

The functional-programming idea of turning unstructured input into a typed, always-valid value at the boundary is exactly a validating constructor or factory.

🧊 Immutability by default

Records, frozen dataclasses, and readonly fields make objects that are validated once and never mutated into an illegal state, pairing naturally with strong construction.

🏭 Factories over new

Named static factories are the norm in modern libraries because they express intent, hide subtype choices, and give validation a single home.

🛠️ Type-state and smart constructors

Languages increasingly let the type system encode "this object passed its checks," so an invalid instance is unrepresentable, not just unlikely.

🌐 Safer API boundaries

Deserializing JSON into rich objects through validating factories stops malformed external data from ever entering the domain as a valid-looking instance.

Bottom line: the most reliable way to make invalid states impossible is to refuse to build them. Put your rules in the constructor and factory, keep objects immutable or mutated only through invariant-preserving methods, and the rest of your system gets simpler and safer for free.
