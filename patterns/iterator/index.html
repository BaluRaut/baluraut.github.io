Behavioral Pattern

How the Iterator pattern actually works

Collections come in many shapes: arrays, linked lists, trees, hash tables. The Iterator pattern gives you one uniform way to walk them all, exposing elements one at a time without ever revealing how the collection stores them. The traversal logic lives in a separate cursor object, so the collection stays simple and clients stay decoupled from its internals.

01 - What

What is the Iterator pattern?

Iterator is a behavioral design pattern that provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation. The traversal state, where you are in the collection, moves out of the collection and into a small dedicated cursor object. That single indirection lets one client loop over a list, a tree, or a stream with identical code.

🎯 Uniform traversal

Clients ask for a next() element through the same interface no matter what the collection is: array, set, tree, or database cursor.

🔒 Encapsulated internals

The collection never leaks its buckets, nodes, or index math. Callers see elements, not the data structure that holds them.

🧭 Externalized state

Each iterator holds its own position, so several traversals of the same collection can run at once without stepping on each other.

Key mental model: the collection is the book, the iterator is the bookmark. The bookmark remembers your page and knows how to turn to the next one, and you can keep several bookmarks in the same book at once.
02 - Why

Why the Iterator pattern exists

Without it, every collection would need to expose its guts, indexes, node pointers, hash buckets, and every client would hardcode a different loop. Iterator moves traversal behind one interface so structures can change freely and clients stay untouched.

🧩 Single traversal interface

Write one loop that works over any collection. Swap an ArrayList for a TreeSet and the calling code does not change at all.

🛡️ Protects encapsulation

Callers never touch internal indices or nodes, so the collection can rebalance a tree or resize an array without breaking anyone.

🔀 Multiple concurrent walks

Because each iterator carries its own position, you can run nested loops or parallel scans over one collection independently.

🌊 Lazy and infinite sequences

An iterator can compute elements on demand, so you can model streams, paginated APIs, or infinite ranges without materializing them.

Iterator explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

03 - How

How it works under the hood

The collection exposes a factory method that returns a fresh cursor. The cursor holds a position, answers "is there more?", and hands back the current element while stepping forward. The client only ever talks to that cursor interface.

🚶 External iterator

The client drives the loop: it calls hasNext() and next() itself. Maximum control, so you can pause, peek, or interleave two iterators. This is Java's Iterator and JavaScript's iterator protocol.

🔁 Internal iterator

The collection drives the loop and calls a function you pass in for each element, as in forEach or Stream.map. Less boilerplate, but you cannot easily stop early or run two walks in lockstep.

A custom iterator in Java

import java.util.Iterator;
import java.util.NoSuchElementException;

// Concrete Aggregate: exposes iterators without revealing the array
public class NameRepository implements Iterable<String> {
    private final String[] names = { "Ada", "Alan", "Grace", "Linus" };

    @Override
    public Iterator<String> iterator() {
        return new NameIterator();       // factory method
    }

    // Concrete Iterator: an inner class holding the traversal state
    private class NameIterator implements Iterator<String> {
        private int index = 0;           // externalized cursor position

        @Override
        public boolean hasNext() {
            return index < names.length;
        }

        @Override
        public String next() {
            if (!hasNext()) throw new NoSuchElementException();
            return names[index++];       // read, then advance
        }
    }
}

// Client: uses the interface, never the array
class Demo {
    public static void main(String[] args) {
        NameRepository repo = new NameRepository();
        for (String name : repo) {       // for-each calls iterator() + next()
            System.out.println(name);
        }
    }
}

Because NameRepository implements Iterable, the enhanced for loop works automatically: the compiler expands it into calls to iterator(), hasNext(), and next(). The index lives in the iterator, not the repository, so two loops over the same repo never collide.

05 - Step by Step

The 0 → 100 flow

From an aggregate object to a fully consumed, decoupled traversal, the whole journey in order.

Have a collection to traverse

You start with some aggregate: an array, a linked list, a tree, or a stream of pages from an API that a client needs to walk element by element.

10
Interface

Define the iterator contract

Declare the traversal methods, typically hasNext() and next(), so every walker looks the same to callers regardless of structure.

20

Add a factory method

Make the collection implement Iterable with an iterator() method that produces a fresh cursor on demand.

30

Write the concrete iterator

Implement a small class that holds the current position and knows how to advance through this specific structure.

40
State

Externalize the position

Store the index or node pointer inside the iterator, not the collection, so multiple iterators can coexist without interference.

50
Create

Client requests an iterator

The client calls iterator(). It receives a cursor positioned before the first element and knows nothing about the internals.

60
Check

Ask hasNext

Before each read the client calls hasNext(). The iterator reports whether any elements remain to be visited.

70
Advance

Call next

The client calls next(), which returns the current element and moves the cursor forward by one position.

80
Guard

Detect concurrent modification

A fail-fast iterator compares a modification counter; if the collection changed during the loop, it throws instead of returning corrupt data.

90
Exhaust

Reach the end

hasNext() finally returns false. The loop terminates cleanly and the client stops calling next().

100
Reuse

Swap collections freely

Because the client only touched the iterator interface, you can replace the underlying structure with any other Iterable and the loop still works.

Common Pitfalls

Pitfalls & anti-patterns

Iteration looks trivial until state, mutation, and laziness collide. These are the usual culprits.

💥 Mutating while iterating

Adding or removing elements through the collection during a loop corrupts the cursor. Use the iterator's own remove() or collect changes and apply them afterward.

♻️ Reusing an exhausted iterator

Most iterators are single-pass. Once hasNext() is false it stays false. Call iterator() again for a fresh walk instead of reusing the spent one.

🕳️ Leaking internals anyway

Returning the backing array or a live node from next() defeats the point. Hand back values or defensive copies, not references into your structure.

🔁 Reinventing built-ins

Hand-rolling a cursor when the language already offers Iterable, generators, or streams adds bugs. Implement the standard protocol so for-each just works.

🧵 Sharing one iterator across threads

Iterators carry mutable position state and are not thread-safe. Give each thread its own, or use a concurrent collection designed for shared traversal.

⏳ Forgetting laziness has side effects

With generators and streams nothing runs until you pull. If a walk never completes, deferred work never fires and infinite sequences hang without a stop condition.

Trade-offs

Trade-offs & when to use

Iterator is one of the most quietly ubiquitous patterns. Here is where it pays off and where it adds noise.

AspectDetail
ProsUniform traversal, hides internals, supports multiple simultaneous walks, and enables lazy or infinite sequences.
ConsExtra objects and indirection, single-pass semantics can surprise, and a custom iterator is overkill for a plain array loop.
Use whenYou have a nontrivial or custom structure, need to hide its layout, want lazy evaluation, or must offer several traversal orders.
Avoid whenA simple indexed loop over an array or list is clearer, or the collection is tiny and its structure is not going to change.
ComplexityLow. Two methods and a position field. The subtlety is in fail-fast checks, laziness, and thread-safety, not the core loop.
RelatedComposite (iterate a tree uniformly), Visitor (apply an operation per element), Observer (push vs pull consumption).
Rule of thumb: if a client needs to walk a collection but should not know how it is stored, expose an iterator. If it is just a flat array you fully control, a plain loop is fine, do not add ceremony you will not use.
06 - Case Studies

Real-world case studies

Three representative places the Iterator pattern shows up in production code.

📦

1 · The Java Collections Framework

Pattern: fail-fast external iterators over every collection

Every ArrayList, HashSet, and TreeMap exposes iterators so client code loops identically over all of them.

  • Iterable.iterator() is the factory method the enhanced for loop calls behind the scenes.
  • Iterators keep a modCount check and throw ConcurrentModificationException on unexpected structural change.
  • ListIterator extends the idea with backward traversal and safe in-place edits.
✅ Outcome: one traversal idiom works across dozens of data structures, and accidental mutation during a loop fails loudly instead of corrupting silently.
🌿

2 · Paginated API and database cursors

Pattern: lazy iterator over a remote, unbounded source

A client needs to process millions of records from a REST endpoint or SQL cursor without loading them all into memory.

  • Each next() fetches the following page or row only when the consumer asks for it.
  • The iterator hides paging tokens and network retries behind a plain hasNext() loop.
  • Back-pressure is natural: the source is only pulled as fast as the client consumes.
✅ Outcome: the client streams huge result sets with constant memory, unaware whether data comes from cache, disk, or a paged HTTP API.
🧬

3 · Tree and graph traversal in compilers

Pattern: multiple iteration orders over one structure

A compiler walks its abstract syntax tree in different orders for different phases: pre-order, post-order, and breadth-first.

  • Distinct iterator classes encode each traversal strategy over the same node type.
  • Optimization passes pick the order they need without the tree exposing its child pointers.
  • New traversal orders are added as new iterators, leaving existing passes untouched.
✅ Outcome: the same AST supports several traversal strategies cleanly, and each compiler phase reads elements in exactly the order it requires.
07 - Relevance

Modern relevance

Far from dated, Iterator is baked into the syntax of nearly every modern language. Today it usually arrives as a built-in protocol rather than hand-written classes.

🔤 Language-level protocols

Java's Iterable, JavaScript's Symbol.iterator, Python's __iter__, and C#'s IEnumerable all standardize the pattern into for-each syntax.

⚙️ Generators as easy iterators

A JavaScript function* or Python yield builds a lazy iterator in a few lines, with position state managed by the runtime for you.

🌊 Streams and pipelines

Java Streams and LINQ layer map, filter, and reduce on top of iteration, turning internal iterators into composable data pipelines.

⏩ Async iteration

AsyncIterator and for await...of extend the protocol to data that arrives over time, like sockets, event streams, and paged fetches.

🦀 Zero-cost abstractions

Languages like Rust compile iterator chains down to tight loops with no runtime overhead, proving the pattern need not cost performance.

🧠 Reactive and pull vs push

Reactive streams generalize iteration to pushed events, and understanding the pull-based iterator clarifies where that boundary lies.

Bottom line: the Iterator pattern won so thoroughly that it disappeared into the language. Every time you write for (const x of items) you are using it, and knowing what happens underneath lets you build custom, lazy, and async traversals with confidence.
