Equality & Identity - when are two objects "the same"?

Two Money objects holding 5 USD should count as equal, but two User records for different people never should, even if every visible field matches. Getting this wrong corrupts sets, breaks deduplication, and lets stale copies masquerade as the real thing. This is the line between identity (same object) and equality (same value).

01 - What

What is equality vs identity?

Identity asks "are these the exact same object in memory?" Equality asks "do these two objects represent the same value?" A payment ledger cares that two Money amounts of 5 USD are interchangeable; an auth system cares that two User handles point at the same account, not merely at people who happen to share a name. Every language gives you a default, and the default is almost always identity, which is rarely what your domain wants for value objects.

🧷 Reference identity

Two variables are identical when they point at the same instance. Default for === on objects in TS, is in Python, equal? in Ruby.

⚖️ Value equality

Two instances are equal when their meaningful fields match. You opt into this by implementing an equals method, __eq__, or ==.

🔑 Hashing

If equal objects must be usable as set members or map keys, they need matching hash codes. Equality and hashing travel together.

Key mental model: identity is a property of the reference; equality is a property of the value. Value objects want equality by content; entities want identity by a stable key (an id), never by content, because an entity keeps its identity even as every attribute changes.
02 - Why

Why equality & identity matter

Collections, caches, and deduplication all silently depend on your equality definition. Leave it as the default and a shopping cart will hold two "identical" line items it thinks are different, or a set of authorized users will accept duplicates.

🧺 Collections behave correctly

Sets, maps, and includes checks rely on equality. A Money value object with proper equality lets a discount engine ask "is this amount already in the applied set?" and get a truthful answer.

🧭 Entities stay themselves

A User who changes email, name, and avatar is still the same user. Identity keyed on a stable id survives every edit, so audit logs and permissions stay attached to the right account.

🔁 Deduplication actually works

Merging orders from two systems needs a defined notion of "same order line." Value equality on the meaningful fields lets you fold duplicates instead of double-charging.

🧱 The contract prevents corruption

Honoring the equals/hashCode contract keeps hash-based structures consistent. Break it and objects vanish from sets, or two "equal" keys both live in the same map.

In Plain Terms

Equality & identity explained with analogies

Same distinction, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Two ten-dollar bills are equal in value, you would trade one for the other without a thought. But your student ID card is identity: a reprinted card with a new photo is still your record, and no other student's card is interchangeable with it.

👩‍💻 For a developer

Reference identity is comparing two pointers; value equality is comparing what they point at. The default === checks the pointer, so you override equality when your domain cares about the contents, not the address.

🏢 For a professional

Two invoices for the same amount are equal amounts but different invoices. The finance system keys each invoice by its number (identity) while comparing the money figures by value.

🚚 Everyday version

Two identical courier boxes off the same shelf are equal. Once one has your tracking number on it, it becomes that parcel: swap in another box and the delivery is wrong, even though the boxes look the same.

03 - How

How to implement equality correctly

Model value objects (like Money) with equality by content and a matching hash; model entities (like User) with equality by a stable id. Never mix the two: an entity that compares by its mutable fields will "change identity" the moment someone edits it.

💵 Value object: Money

Immutable, no id. Two amounts are equal when currency and minor units match. Equality and hash both derive from those two fields, so Money works as a map key and set member.

🧑 Entity: User

Has a lifecycle and a stable id. Equality compares ids only. Email, name, and role can all change without affecting whether two references mean the same account.

Implementing value equality on Money

// Money is a value object: two amounts are equal by content, not by reference.
class Money {
  private constructor(
    readonly amountMinor: number, // cents, avoids float drift
    readonly currency: string,
  ) {}

  static of(amountMinor: number, currency: string): Money {
    return new Money(amountMinor, currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) {
      throw new Error(`Currency mismatch: ${this.currency} vs ${other.currency}`);
    }
    return new Money(this.amountMinor + other.amountMinor, this.currency);
  }

  // Value equality: same currency AND same amount.
  equals(other: unknown): boolean {
    return (
      other instanceof Money &&
      other.amountMinor === this.amountMinor &&
      other.currency === this.currency
    );
  }

  // Stable string key for use in a Map/Set that lacks value hashing.
  hashKey(): string {
    return `${this.currency}:${this.amountMinor}`;
  }
}

const a = Money.of(500, "USD");
const b = Money.of(500, "USD");

console.log(a === b);        // false -> different references (identity)
console.log(a.equals(b));    // true  -> same value (equality)

// Dedup by value using the hash key, since === would keep both.
const seen = new Map<string, Money>();
for (const m of [a, b, Money.of(750, "USD")]) seen.set(m.hashKey(), m);
console.log(seen.size);      // 2 -> the two 5.00 USD amounts collapsed

    # dataclass generates __eq__ (compares fields) and __hash__ (from the tuple
    # of fields) for us, so equal Money objects share a hash automatically.

# Money is a value object: == for equality, eql? + hash for hashing.
class Money
  attr_reader :amount_minor, :currency

  def initialize(amount_minor, currency)
    @amount_minor = amount_minor # cents, avoids float drift
    @currency = currency
    freeze                       # immutable value object
  end

  def add(other)
    unless other.currency == currency
      raise ArgumentError, "Currency mismatch: #{currency} vs #{other.currency}"
    end
    Money.new(amount_minor + other.amount_minor, currency)
  end

  # Value equality: same class, same fields.
  def ==(other)
    other.is_a?(Money) &&
      other.amount_minor == amount_minor &&
      other.currency == currency
  end

  # Hash-key equality for Set / Hash keys. eql? and hash must agree with ==.
  alias eql? ==

  def hash
    [amount_minor, currency].hash
  end
end

a = Money.new(500, "USD")
b = Money.new(500, "USD")

puts a.equal?(b)  # false -> different objects (identity)
puts a == b       # true  -> same value (equality)

# eql? + hash agree, so a Set deduplicates by value.
seen = [a, b, Money.new(750, "USD")].to_set
puts seen.size    # 2 -> the two 5.00 USD amounts collapsed

Notice the same object created twice fails the identity check (=== / is / equal?) but passes value equality. And because hashing is defined consistently with equality, a set folds the duplicates instead of storing both.

Contrast: an entity keyed by id

// User is an entity: equality is its identity (id), never its mutable fields.
class User {
  constructor(
    readonly id: string,
    private email: string,
    private displayName: string,
  ) {}

  changeEmail(email: string): void {
    this.email = email; // identity is unaffected by attribute changes
  }

  equals(other: unknown): boolean {
    return other instanceof User && other.id === this.id;
  }

  hashKey(): string {
    return `user:${this.id}`;
  }
}

const u1 = new User("u-42", "ada@corp.io", "Ada");
const u2 = new User("u-42", "ada.new@corp.io", "Ada L.");

console.log(u1.equals(u2)); // true -> same account despite different email/name

u1.changeEmail("ada@newco.io");
console.log(u1.equals(u2)); // still true -> identity survives edits
# User is an entity: equality is its identity (id), never its mutable fields.
class User:
    def __init__(self, user_id: str, email: str, display_name: str):
        self.id = user_id
        self.email = email
        self.display_name = display_name

    def change_email(self, email: str) -> None:
        self.email = email  # identity is unaffected by attribute changes

    def __eq__(self, other: object) -> bool:
        return isinstance(other, User) and other.id == self.id

    def __hash__(self) -> int:
        return hash(self.id)  # hash on the stable id, matching __eq__


u1 = User("u-42", "ada@corp.io", "Ada")
u2 = User("u-42", "ada.new@corp.io", "Ada L.")

print(u1 == u2)  # True -> same account despite different email/name

u1.change_email("ada@newco.io")
print(u1 == u2)  # still True -> identity survives edits
# User is an entity: equality is its identity (id), never its mutable fields.
class User
  attr_reader :id
  attr_accessor :email, :display_name

  def initialize(id, email, display_name)
    @id = id
    @email = email
    @display_name = display_name
  end

  def ==(other)
    other.is_a?(User) && other.id == id
  end
  alias eql? ==

  def hash
    id.hash # hash on the stable id, matching ==
  end
end

u1 = User.new("u-42", "ada@corp.io", "Ada")
u2 = User.new("u-42", "ada.new@corp.io", "Ada L.")

puts u1 == u2      # true -> same account despite different email/name

u1.email = "ada@newco.io"
puts u1 == u2      # still true -> identity survives edits

The entity compares only its id, so two references to account u-42 stay equal even after the email and display name diverge. This is the opposite policy from Money, and choosing the right one per type is the whole discipline.

05 - Step by Step

The 0 → 100 flow

From an undecided type to a correct, contract-honoring equality implementation, in order.

00
Classify

Value object or entity?

Ask whether the type is defined by its attributes (Money) or by a continuous identity over time (User). This one decision drives everything else.

10
Value

Pick the equality fields

For a value object, list the fields that define its value: for Money, the amount and the currency. Nothing else participates.

20
Entity

Pick the identity key

For an entity, choose a stable id assigned at creation. It must never change and must not be derived from mutable business fields.

30
Immutable

Freeze value objects

Make value objects immutable (readonly, frozen=True, freeze) so their identity-as-value can never drift after they are used as keys.

40
Equality

Implement equals / __eq__ / ==

Check the other object's type first, then compare the chosen fields (value) or the id (entity). Return false for foreign types instead of throwing.

50
Hash

Implement a matching hash

Derive the hash from exactly the same fields equality uses. Equal objects must hash the same, or sets and maps silently lose them.

60
Contract

Verify reflexive, symmetric, transitive

Confirm a.equals(a), that a.equals(b) implies b.equals(a), and that equality chains through a third object.

70
Null

Handle null and other types

Comparing to null/None/nil or an unrelated class returns false, never an exception. Guard the type before touching fields.

80
Collections

Exercise in a set and a map

Insert duplicates into a set and confirm they collapse; use the object as a map key and confirm lookups hit. This proves hash and equals agree.

90
Mutation

Test identity across edits

Change an entity's fields and confirm equality is unaffected. Confirm value objects cannot be mutated at all after construction.

100
Ship

Document the policy

State in the type's docs that Money is compared by value and User by id, so future callers never reach for the default again.

Common Pitfalls

Pitfalls & anti-patterns

Equality bugs are quiet: nothing crashes, but sets leak duplicates and lookups miss. These are the usual culprits.

🧨 equals without hashCode

Overriding value equality but leaving the default hash means two "equal" Money objects land in different buckets, so a set keeps both and a map key never resolves. Always define them together.

🌀 Mutable fields in the hash

Hashing on a field that later changes moves the object to a new bucket while it sits in a set, making it unfindable and un-removable. Hash only immutable data.

🪞 Comparing entities by content

Two different users with the same name become "equal," merging distinct accounts. Entities must compare by a stable id, never by their attributes.

💥 Throwing on foreign types

An equals that assumes the argument is the same class explodes when a collection compares it against null or another type. Guard with an instance check and return false.

🔗 Asymmetric equality

A subclass that considers itself equal to a base instance, but not vice versa, breaks the symmetry rule and corrupts any collection holding both. Keep equality symmetric.

😵 Trusting == on references

Reaching for === or is to compare two freshly loaded Money rows always returns false, because they are distinct instances. Use value equality for value objects.

Signals & Metrics

Signals & how to measure

You rarely get a stack trace for a broken equality contract. These signals expose it before it corrupts data.

SignalWhat it tells you
Duplicates in a setObjects you consider equal are hashing differently, so equals and hash disagree.
Map lookups miss with a valid keyThe key's hash changed after insertion, or hash is inconsistent with equals.
Distinct records treated as oneAn entity is comparing by content, so unrelated rows collapse into a single identity.
Equality throws in a collection opequals assumes a concrete type instead of guarding against null and foreign types.
Flaky dedup countsEquality depends on a mutable or time-based field, so results shift between runs.
Property tests fail on symmetry / transitivityThe contract is violated; some comparison direction disagrees with another.
Rule of thumb: if you override equality, override hashing in the same commit, from the same fields, and back it with a property test asserting reflexive, symmetric, and transitive behavior. Equal objects that hash differently are a data-corruption bug waiting to happen.
06 - Case Studies

Real-world case studies

Three production-style systems where the equality-vs-identity choice is load-bearing.

💳

1 · Payments ledger with a Money value object

Pattern: value equality for amounts, identity for transactions

A billing service adds line amounts, applies discounts, and reconciles totals across currencies.

  • Money is immutable and compared by currency plus minor units, so 5.00 USD equals any other 5.00 USD.
  • Transactions are entities keyed by a transaction id; two transfers of the same amount are never the same transaction.
  • A set of applied discounts uses Money's value hash to prevent applying the same amount twice.
✅ Outcome: Reconciliation math is correct across duplicated amounts, while every transfer stays uniquely auditable by its id.
🔐

2 · Auth system tracking User entities

Pattern: identity by stable id across profile edits

An identity provider manages accounts whose email, display name, and roles change constantly.

  • User equality compares only the immutable account id, so a rename or email change never forks the account.
  • Session and permission sets store users by id-based hash, so lookups survive profile updates.
  • Merging a duplicate signup is a deliberate id remap, not an accidental content match.
✅ Outcome: Audit trails and permissions stay bound to the correct account through every edit, with no accidental merges of look-alike users.
🛒

3 · Cart and catalog deduplication

Pattern: value equality on SKUs and options

An e-commerce cart must fold repeated adds of the same product-and-options into one line with a quantity.

  • A LineItemKey value object (SKU plus selected options) defines equality and hash for grouping.
  • Adding the same configured product twice increments quantity instead of creating a second row.
  • Orders are entities keyed by order id, so two carts with identical contents remain distinct orders.
✅ Outcome: The cart shows one line per distinct configuration with accurate quantities, while each placed order keeps its own identity.
07 - Relevance

Modern relevance

Language features keep making correct equality cheaper, but the value-vs-entity decision stays a human one.

🧊 Records & data classes

Python @dataclass(frozen=True) and Ruby's Data.define generate value equality and hashing for you, removing most hand-written boilerplate for value objects.

🧩 Structural typing

TypeScript's structural model shapes how you compare data, but object identity still defaults to reference, so value objects still need an explicit equals.

🛡️ Branded & opaque ids

Branded id types stop you from comparing a UserId to an OrderId by accident, making entity identity checks type-safe.

🧪 Property-based testing

Tools like fast-check and Hypothesis assert the reflexive, symmetric, and transitive laws automatically, catching contract breaks early.

🗃️ Domain-driven design

DDD's explicit split between value objects and entities is now mainstream vocabulary, giving teams a shared name for the equality policy per type.

🔀 Immutability by default

Persistent data structures and readonly-by-default styles make value objects safe as keys, since their hash can never drift underneath a collection.

Bottom line: tooling can generate equals and hashCode, but only you can decide whether a type is a value compared by content or an entity compared by id. Make that call explicitly, honor the contract, and your collections, caches, and dedup logic simply work.
