Behavioral Pattern

Template Method - fix the algorithm, vary the steps

Template Method defines the skeleton of an algorithm in a single base-class method, then defers specific steps to subclasses. The overall order is locked in one place, while subclasses fill in or override the parts that differ. The base class calls the subclass, not the other way around, which is exactly the Hollywood Principle: do not call us, we will call you.

01 - What

What is Template Method?

Template Method is a behavioral pattern where a base class defines an algorithm as a fixed sequence of steps in one method, marking some steps as abstract or overridable. Subclasses supply the varying steps without ever touching the sequence itself. The invariant structure lives in the parent; the variation lives in the children.

🧱 The template method

A concrete method in the base class that calls the steps in a fixed order. It is usually final so subclasses cannot reorder the algorithm.

🧩 Abstract steps

Operations the base declares but does not implement. Each subclass must provide them, filling the required gaps in the skeleton.

🪝 Hook methods

Optional steps with an empty or default body. Subclasses may override them to extend or tweak behavior, but are not forced to.

The core building blocks

PieceWhat it doesTypical form
Abstract classHolds the algorithm skeleton and shared logicBase class or interface with default methods
Template methodRuns the steps in a fixed orderfinal concrete method
Primitive operationA required step subclasses must implementabstract method
Hook methodAn optional step with a default no-opNon-abstract, overridable method
Concrete classSupplies the varying stepsSubclass overriding primitives and hooks
Key mental model: the parent owns when each step runs; the child owns how a step behaves. You freeze the workflow once and reuse it across every variant, changing only the pieces that actually differ.
02 - Why

Why Template Method exists

When several classes share the same overall procedure but differ in a few steps, copy-pasting the procedure into each one duplicates the control flow. Every bug fix or reorder then has to be repeated everywhere. Template Method pulls that shared skeleton into one place.

♻️ Removes duplication

The common sequence lives once in the base class. Subclasses contribute only the differences, so shared control flow is never copy-pasted across variants.

🔒 Guards the algorithm

Marking the template method final locks the order of steps. Subclasses cannot accidentally skip validation or reorder critical stages.

🎯 Focuses subclasses

A new variant only implements the abstract steps. Developers see exactly which gaps to fill instead of re-reading the whole workflow.

🔄 Inverts control

The framework drives the flow and calls into your code at defined points, so extension happens through well-defined hooks rather than rewrites.

In Plain Terms

Template Method explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is a fill-in-the-blank worksheet. The teacher fixes the questions and their order; you only write the answers in the blanks. You cannot rearrange the questions, just complete the gaps.

👩‍💻 For a developer

Think of a base test class with setUp and tearDown. The framework runs setUp, then your test, then tearDown, in that order. You override the hooks; the runner owns the sequence.

🏢 For a professional

It is a standard operating procedure. The steps and their order are fixed by policy; each department fills in the details specific to its work without changing the process.

☕ Everyday version

Making a hot drink: boil water, add the main ingredient, pour, add extras. Tea and coffee share the recipe skeleton; only the "add ingredient" and optional "add extras" steps differ.

03 - How

How it works under the hood

The base class exposes one public template method and a set of protected steps. Some steps are abstract (must implement), others are hooks (may override). At runtime, dynamic dispatch routes each step call to the concrete subclass.

🧭 The base class leads

It implements the template method and calls each step by name. Shared, invariant logic sits directly in the base so every subclass inherits it for free.

🔌 Subclasses plug in

Each concrete class overrides the abstract steps and any hooks it cares about. It never calls the template method's internals, it only supplies the pieces.

A realistic example

// A data-import pipeline: the base fixes the order, subclasses fill the steps.
abstract class DataImporter {

  // The template method: the algorithm skeleton. Not overridable by convention.
  run(path: string): void {
    const raw = this.read(path);        // abstract step
    const records = this.parse(raw);    // abstract step
    if (this.shouldValidate()) {        // hook controls an optional step
      this.validate(records);           // hook step
    }
    this.save(records);                 // shared, invariant step
    this.onComplete(records.length);    // hook, no-op by default
  }

  // Required steps: every subclass MUST provide these.
  protected abstract read(path: string): string;
  protected abstract parse(raw: string): Record[];

  // Hook methods: optional, with sensible defaults.
  protected shouldValidate(): boolean { return true; }
  protected validate(records: Record[]): void { /* default no-op */ }
  protected onComplete(count: number): void { /* subclasses may log here */ }

  // Invariant step shared by all importers.
  private save(records: Record[]): void {
    Database.bulkInsert(records);
  }
}

class CsvImporter extends DataImporter {
  protected read(path: string): string { return fs.readFileSync(path, "utf8"); }
  protected parse(raw: string): Record[] { return Csv.toRecords(raw); }
  protected onComplete(count: number): void {
    console.log(`Imported ${count} CSV rows`);
  }
}

class JsonImporter extends DataImporter {
  protected read(path: string): string { return Http.get(path); }
  protected parse(raw: string): Record[] { return JSON.parse(raw); }
  // Trusted feed, so skip validation via the hook.
  protected shouldValidate(): boolean { return false; }
}

new CsvImporter().run("customers.csv");
new JsonImporter().run("https://api.example.com/orders");
# A data-import pipeline: the base fixes the order, subclasses fill the steps.
from abc import ABC, abstractmethod

class DataImporter(ABC):

    # The template method: the algorithm skeleton. Do not override.
    def run(self, path):
        raw = self.read(path)             # abstract step
        records = self.parse(raw)         # abstract step
        if self.should_validate():        # hook controls an optional step
            self.validate(records)        # hook step
        self._save(records)               # shared, invariant step
        self.on_complete(len(records))    # hook, no-op by default

    # Required steps: every subclass MUST provide these.
    @abstractmethod
    def read(self, path): ...
    @abstractmethod
    def parse(self, raw): ...

    # Hook methods: optional, with sensible defaults.
    def should_validate(self): return True
    def validate(self, records): pass          # default no-op
    def on_complete(self, count): pass          # subclasses may log here

    # Invariant step shared by all importers.
    def _save(self, records):
        Database.bulk_insert(records)

class CsvImporter(DataImporter):
    def read(self, path):
        with open(path) as f:
            return f.read()
    def parse(self, raw):
        return Csv.to_records(raw)
    def on_complete(self, count):
        print(f"Imported {count} CSV rows")

class JsonImporter(DataImporter):
    def read(self, path): return Http.get(path)
    def parse(self, raw): return json.loads(raw)
    # Trusted feed, so skip validation via the hook.
    def should_validate(self): return False

CsvImporter().run("customers.csv")
JsonImporter().run("https://api.example.com/orders")

class DataImporter

  # The template method: the algorithm skeleton. Do not override.
  def run(path)
    raw = read(path)              # abstract step
    records = parse(raw)          # abstract step
    validate(records) if should_validate?  # hook controls an optional step
    save(records)                # shared, invariant step
    on_complete(records.size)    # hook, no-op by default
  end

  # Required steps: every subclass MUST provide these.
  def read(path)  = raise NotImplementedError
  def parse(raw)  = raise NotImplementedError

  # Hook methods: optional, with sensible defaults.
  def should_validate? = true
  def validate(records); end          # default no-op
  def on_complete(count); end         # subclasses may log here

  private

  # Invariant step shared by all importers.
  def save(records)
    Database.bulk_insert(records)
  end
end

  end
end

CsvImporter.new.run("customers.csv")
JsonImporter.new.run("https://api.example.com/orders")

Notice that run() is final: subclasses cannot change the order of read, parse, validate, save. They only override steps. The base class calls down into the subclass, never the reverse, which is the Hollywood Principle in action: do not call us, we will call you.

05 - Step by Step

The 0 → 100 flow

From spotting duplicated procedures to running a clean family of variants - the whole journey in order.

00
Spot

Notice a repeated procedure

Several classes run the same overall sequence of steps but differ in a few spots. The control flow is being copy-pasted around.

10
Outline

Write the algorithm skeleton

List the steps in the exact order they must run. This ordered list becomes the body of the template method.

20
Classify

Sort steps by variability

Mark which steps are always the same, which always differ, and which are optional. That split decides concrete, abstract, and hook.

30
Base

Create the abstract class

Put the invariant steps in as concrete methods and the shared state on the base so every subclass inherits them.

40
Template

Write the template method

Implement the one method that calls each step in order. Make it final so subclasses cannot reorder the algorithm.

50
Abstract

Declare required steps

Turn the always-different steps into abstract methods. Subclasses are now forced by the compiler to supply them.

60
Hook

Add optional hooks

Give optional steps a default or empty body. Subclasses may override to extend behavior, but nothing breaks if they do not.

70
Implement

Build a concrete subclass

Override the abstract steps for one variant. Override only the hooks it actually needs and leave the rest alone.

80
Extend

Add more variants

Each new case is another subclass supplying its steps. The skeleton stays untouched, so new variants cost only the differences.

90
Run

Call through the base type

Clients invoke the template method on a base-typed reference. Dynamic dispatch routes each step to the right subclass.

100
Maintain

Change the flow in one place

Reordering or fixing a shared step happens once in the base and applies to every variant instantly. Duplication is gone.

Common Pitfalls

Pitfalls & anti-patterns

Template Method leans on inheritance, so its failure modes are the classic inheritance traps.

🧨 Fragile base class

Editing the skeleton or a shared step can silently break every subclass. Tight coupling through inheritance means changes ripple downward in ways that are hard to see.

🪜 Too many abstract steps

If almost every step is abstract, the base offers little reuse and subclasses carry all the weight. That is a sign the shared skeleton barely exists.

🔓 Forgetting to lock the template

Leaving the template method overridable lets a subclass rewrite the algorithm order, defeating the whole point. Mark it final.

🕸️ Deep hierarchies

Chaining many levels of subclass to reuse partial behavior makes the flow impossible to follow. One level of variation is usually the sweet spot.

🎭 Hooks that leak requirements

Hooks that must be overridden together, or in a certain combination, hide implicit contracts. Subclasses break subtly when a hidden rule is missed.

🔁 Reaching for it when behavior is data

If steps vary at runtime per object, inheritance cannot help. Forcing a subclass per combination explodes the class count. Compose instead.

Trade-offs

Trade-offs & when to use

Template Method is the go-to when the algorithm is fixed and only its steps vary. Its main tension is Strategy: inheritance versus composition.

AspectDetail
ProsRemoves duplicated control flow, locks the algorithm order in one place, gives subclasses clear extension points, and enables inversion of control.
ConsRelies on inheritance, so it couples subclasses to the base, invites fragile-base-class problems, and fixes behavior at compile time.
Use whenYou have several variants of the same procedure that differ only in a few steps, and the sequence itself should never change.
Avoid whenThe varying behavior must be chosen or swapped at runtime, or you would need many subclasses to cover combinations of steps.
ComplexityLow. One abstract class plus a subclass per variant. The hard part is picking which steps are abstract versus hooks.
RelatedStrategy (composition alternative), Factory Method (often a step inside a template), and hooks resemble the Observer callback style.
Rule of thumb: reach for Template Method when the algorithm is fixed and the steps vary by type. Reach for Strategy when the whole behavior must be swapped at runtime. Template Method inherits, Strategy composes: prefer composition when the axis of change is dynamic.
06 - Case Studies

Real-world case studies

Three places the pattern shows up in code you have almost certainly used.

🧪

1 · JUnit test lifecycle

Pattern: framework-owned run order with hooks

A testing framework must run every test in a consistent lifecycle while letting each test class customize setup and teardown.

  • The runner owns the fixed sequence: setUp, run the test body, tearDown.
  • Test classes override setUp and tearDown as hooks; overriding is optional.
  • You never call the lifecycle yourself, the framework calls into your class.
✅ Outcome: every test shares a reliable, uniform lifecycle while each class customizes only the parts it needs, a textbook Hollywood Principle setup.
📥

2 · HTTP servlet request handling

Pattern: dispatch skeleton with overridable steps

A web framework needs to route every request through a common pipeline while letting handlers implement just the verb they care about.

  • service() is the template method: it inspects the HTTP verb and dispatches.
  • It calls doGet, doPost, and similar as overridable steps.
  • Your servlet implements only the methods for the verbs it supports.
✅ Outcome: shared request dispatch lives once in the base servlet, and each handler contributes only the verb-specific logic without rewriting the pipeline.
🍜

3 · Build and deployment pipelines

Pattern: fixed stages, project-specific steps

A CI base job defines the canonical stages every project runs, while individual projects plug in their own commands.

  • The base defines the order: checkout, install, build, test, package, publish.
  • Projects override abstract steps like build and test for their stack.
  • A hook like afterPublish lets some projects notify or tag releases.
✅ Outcome: a single, auditable pipeline order applies across every project, and teams change only their own steps instead of forking the whole workflow.
07 - Relevance

Modern relevance

The pattern predates most frameworks you use, yet its shape keeps reappearing, often expressed without a class hierarchy at all.

🏗️ Frameworks everywhere

Every framework that calls your lifecycle methods in a fixed order is a template method. Inversion of control is the pattern generalized to a whole system.

🧬 Default interface methods

Java default methods and TypeScript abstract classes let a template live on an interface, mixing shared flow with required steps more flexibly than before.

🧩 Functional variants

Passing step functions into a fixed pipeline function achieves the same skeleton with composition, blurring the line with Strategy.

🪝 Hooks as first-class API

Modern libraries expose lifecycle hooks (beforeCreate, mounted, onRequest) that are exactly the optional-step idea, made public and documented.

⚖️ Composition-first culture

As teams favor composition over inheritance, many template methods are refactored into Strategy or higher-order functions, but the skeleton idea survives.

🔌 Plugin architectures

Plugin systems define fixed extension points and call registered code at set moments, an inversion-of-control descendant of Template Method.

Bottom line: Template Method is how you factor out a shared algorithm and let variants fill the gaps. When the variation is per-type and the flow is fixed, inheritance fits. When the variation is per-instance and dynamic, prefer Strategy and composition. The skeleton idea outlives the mechanism.
