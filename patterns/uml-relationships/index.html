OOP Concept

UML class relationships - the lines that connect your classes

A class diagram is only as useful as the relationships drawn between its boxes. UML gives you six precise arrows - association, aggregation, composition, dependency, generalization, and realization - each with a different notation and a different meaning about ownership, lifetime, and coupling. Get them right and the diagram reads like the code; get them wrong and it lies.

01 - What

What are UML class relationships?

UML class relationships are the standardized connectors that describe how classes relate at design time. They encode three things that source code scatters across constructors, fields, and imports: structural links between instances, ownership and lifetime, and type hierarchy. Reading the arrow direction, its head shape, and its multiplicity tells you how objects find each other and who is responsible for creating and destroying whom.

🔗 Structural links

Association, aggregation, and composition describe objects that hold references to other objects, such as an Order referencing its Customer and its LineItem list.

🧬 Type hierarchy

Generalization (inheritance) and realization (implementing an interface) describe subtype relationships, such as a StripeGateway realizing a PaymentGateway contract.

⚡ Transient use

Dependency is the weakest link: one class uses another only briefly, as a method parameter or local, without storing a reference to it.

The six relationships and their notation

RelationshipUML notationMeaning
AssociationSolid line, optional open arrowA structural link; one object holds a reference to another. Order knows its Customer.
AggregationSolid line, hollow diamond at the wholeWhole-part with shared, independent lifetime. A Product can belong to many Order line items.
CompositionSolid line, filled diamond at the wholeWhole-part with owned lifetime. LineItem objects die with their Order.
DependencyDashed line, open arrowTransient use; Order uses a PaymentGateway passed to checkout().
GeneralizationSolid line, hollow triangle at the parentInheritance; a subclass is a kind of its superclass.
RealizationDashed line, hollow triangle at the interfaceA class implements an interface contract.
Key mental model: the diamond answers "who owns the lifetime?" and the line style answers "how long is the link?" A filled diamond means the part cannot outlive the whole; a dashed line means the connection is momentary, not stored.
02 - Why

Why the distinctions matter

These arrows are not decoration. Choosing composition over association changes cascade-delete rules, testability, and how tightly two modules are bound. A diagram that mislabels them will steer real engineering decisions in the wrong direction.

🗑️ Lifetime & cleanup

Composition tells you a part must be created and destroyed with its owner. That maps directly to cascade deletes, ownership of database rows, and who calls dispose(). Aggregation says the opposite: the part lives on its own.

🔌 Coupling you can see

Dependency versus association is the difference between "uses briefly" and "holds forever." Preferring dependency (a parameter) over a stored field keeps classes loosely coupled and far easier to test with a fake.

📐 Contracts before implementations

Realization lets you draw the PaymentGateway interface once and swap Stripe, PayPal, or a sandbox behind it. The diagram documents the seam where implementations plug in.

🧭 Shared vocabulary

UML is a lingua franca across teams and tools. A reviewer who sees a filled diamond knows the ownership rule instantly, without reading the constructor, so design conversations move faster.

In Plain Terms

UML class relationships explained with analogies

Same six connectors, four ways to picture the difference between "knows", "owns", and "is a kind of".

🎓 For a student

Think of a school. You are associated with your teacher (you both exist independently), your notes are composed into your notebook (shred the notebook and the notes are gone), and the library book is an aggregation (borrowed, then returned to live on without you).

👩‍💻 For a developer

A stored field is association or composition; a method parameter is a dependency. implements PaymentGateway is realization; extends BaseController is generalization. The keyword in code is the arrowhead in the diagram.

🏢 For a professional

A company owns its departments (composition - dissolve the company, dissolve the departments) but only employs contractors (aggregation - the contractor keeps existing). It uses an accountant at tax time (dependency), and every manager is a employee (generalization).

🏠 Everyday version

A house and its rooms are composition: demolish the house and the rooms vanish. The house and its furniture are aggregation: the furniture can move to a new house. The plumber you call is a dependency: used for an hour, then gone.

03 - How

How the relationships map to code

Each UML arrow corresponds to a concrete code shape. Below, an ecommerce checkout domain shows all six at once: Order, LineItem, Customer, Product, and a PaymentGateway interface with two implementations.

💎 Ownership shows up in constructors

Composition means the whole builds its parts internally: Order creates its own LineItem objects, so no outside code hands them in. Aggregation and association mean references are passed in from outside and outlive the holder.

🧾 Coupling shows up in signatures

A dependency appears as a parameter type on a single method - checkout(gateway) - not as a stored field. Realization appears as implements; generalization as extends. The narrower the link, the looser the coupling.

The same model in three languages

// PaymentGateway is an interface: StripeGateway REALIZES it.
interface PaymentGateway {
  charge(amountCents: number, token: string): Receipt;
}

interface Receipt { id: string; amountCents: number; status: string; }

class StripeGateway implements PaymentGateway {            // realization
  charge(amountCents: number, token: string): Receipt {
    return { id: `ch_${token}`, amountCents, status: "paid" };
  }
}

class Customer {
  constructor(readonly id: string, readonly email: string) {}
}

class Product {
  constructor(readonly sku: string, readonly priceCents: number) {}
}

// LineItem AGGREGATES a Product: the Product exists independently,
// it is passed in and shared across many orders.
class LineItem {
  constructor(readonly product: Product, readonly quantity: number) {}   // aggregation
  subtotalCents(): number { return this.product.priceCents * this.quantity; }
}

class Order {
  // COMPOSITION: the Order builds and owns its own LineItems.
  private readonly items: LineItem[] = [];

  // ASSOCIATION: the Order holds a Customer reference it does not own.
  constructor(readonly id: string, private readonly customer: Customer) {}

  addItem(product: Product, quantity: number): void {
    this.items.push(new LineItem(product, quantity));      // owns its parts
  }

  totalCents(): number {
    return this.items.reduce((sum, li) => sum + li.subtotalCents(), 0);
  }

  // DEPENDENCY: the gateway is used only inside this call, never stored.
  checkout(gateway: PaymentGateway, token: string): Receipt {
    return gateway.charge(this.totalCents(), token);
  }
}

const order = new Order("ord_1001", new Customer("cus_7", "amir@example.com"));
order.addItem(new Product("SKU-KB-01", 8900), 2);          // create + call method
order.addItem(new Product("SKU-MS-04", 4500), 1);
const receipt = order.checkout(new StripeGateway(), "tok_visa");
console.log(order.totalCents(), receipt.status);           // 22300 paid
from dataclasses import dataclass
from typing import Protocol


# PaymentGateway is a Protocol (interface): StripeGateway REALIZES it.
class PaymentGateway(Protocol):
    def charge(self, amount_cents: int, token: str) -> "Receipt": ...


@dataclass
class Receipt:
    id: str
    amount_cents: int
    status: str


class StripeGateway:                                        # realization
    def charge(self, amount_cents: int, token: str) -> Receipt:
        return Receipt(id=f"ch_{token}", amount_cents=amount_cents, status="paid")


@dataclass
class Customer:
    id: str
    email: str


@dataclass
class Product:
    sku: str
    price_cents: int


# LineItem AGGREGATES a Product: the Product is passed in and shared.
@dataclass
class LineItem:
    product: Product                                        # aggregation
    quantity: int

    def subtotal_cents(self) -> int:
        return self.product.price_cents * self.quantity


class Order:
    # ASSOCIATION: holds a reference to a Customer it does not own.
    def __init__(self, id: str, customer: Customer) -> None:
        self.id = id
        self.customer = customer
        self._items: list[LineItem] = []                    # composition

    # COMPOSITION: the Order builds and owns its own LineItems.
    def add_item(self, product: Product, quantity: int) -> None:
        self._items.append(LineItem(product, quantity))

    def total_cents(self) -> int:
        return sum(li.subtotal_cents() for li in self._items)

    # DEPENDENCY: the gateway is used only inside this call, never stored.
    def checkout(self, gateway: PaymentGateway, token: str) -> Receipt:
        return gateway.charge(self.total_cents(), token)


order = Order("ord_1001", Customer("cus_7", "amir@example.com"))
order.add_item(Product("SKU-KB-01", 8900), 2)               # create + call method
order.add_item(Product("SKU-MS-04", 4500), 1)
receipt = order.checkout(StripeGateway(), "tok_visa")
print(order.total_cents(), receipt.status)                  # 22300 paid
Receipt = Struct.new(:id, :amount_cents, :status)

# Ruby has no formal interface; the gateway duck-types the contract.
# StripeGateway REALIZES the PaymentGateway role by responding to #charge.
class StripeGateway                                          # realization
  def charge(amount_cents, token)
    Receipt.new("ch_#{token}", amount_cents, "paid")
  end
end

class Customer
  attr_reader :id, :email
  def initialize(id, email)
    @id = id
    @email = email
  end
end

class Product
  attr_reader :sku, :price_cents
  def initialize(sku, price_cents)
    @sku = sku
    @price_cents = price_cents
  end
end

# LineItem AGGREGATES a Product: the Product is passed in and shared.
class LineItem
  attr_reader :product, :quantity
  def initialize(product, quantity)                          # aggregation
    @product = product
    @quantity = quantity
  end

  def subtotal_cents = product.price_cents * quantity
end

class Order
  attr_reader :id, :customer

  # ASSOCIATION: holds a reference to a Customer it does not own.
  def initialize(id, customer)
    @id = id
    @customer = customer
    @items = []                                              # composition
  end

  # COMPOSITION: the Order builds and owns its own LineItems.
  def add_item(product, quantity)
    @items << LineItem.new(product, quantity)
  end

  def total_cents = @items.sum(&:subtotal_cents)

  # DEPENDENCY: the gateway is used only inside this call, never stored.
  def checkout(gateway, token)
    gateway.charge(total_cents, token)
  end
end

order = Order.new("ord_1001", Customer.new("cus_7", "amir@example.com"))
order.add_item(Product.new("SKU-KB-01", 8900), 2)           # create + call method
order.add_item(Product.new("SKU-MS-04", 4500), 1)
receipt = order.checkout(StripeGateway.new, "tok_visa")
puts "#{order.total_cents} #{receipt.status}"               # 22300 paid

Read the code against the arrows: implements (or the duck-typed charge in Ruby) is realization, the stored customer field is association, new LineItem(...) inside Order is composition, the passed-in product is aggregation, and the gateway parameter on checkout is a dependency. The same six links appear identically across all three languages.

05 - Step by Step

The 0 → 100 flow

From requirements to a correct class diagram - deciding, for every pair of classes, which of the six relationships truly applies.

00
Identify

List the classes

Pull the nouns from the domain: Order, LineItem, Customer, Product, PaymentGateway. These become the boxes on the diagram.

10
Link

Find the references

For each class, ask which other classes it holds. An Order holds a Customer and a list of LineItem objects. Every held reference is at least an association.

20
Ownership

Ask who controls lifetime

Does deleting the whole delete the part? Delete an Order and its LineItem objects should vanish. That is composition, drawn with a filled diamond.

30
Sharing

Spot the shared parts

A Product lives in the catalog and is referenced by many line items. It outlives any single order, so LineItem to Product is aggregation, a hollow diamond.

40
Plain link

Mark the plain associations

The Order to Customer link is neither owned nor a whole-part; both exist on their own. It is a plain association, a solid line.

50
Transient

Separate use from having

The PaymentGateway is only used inside checkout() and never stored. That is a dependency, a dashed arrow, not an association.

60
Abstract

Introduce interfaces

Define PaymentGateway as an interface so multiple providers can plug in. Draw it as a class with the interface stereotype.

70
Realize

Connect implementations

StripeGateway and PayPalGateway implement the contract. Draw realization: a dashed line with a hollow triangle at the interface.

80
Generalize

Factor shared subtypes

If several classes share fields and behavior, extract a superclass and connect with generalization: a solid line with a hollow triangle at the parent.

90
Multiplicity

Annotate the ends

Add multiplicities: Order "1" to LineItem "1..*", Customer "1" to Order "0..*". These bounds catch invalid states early.

100
Verify

Read the diagram back as code

Walk each arrow and confirm the constructor, field, or parameter matches. If the code stores what the diagram calls a dependency, fix one of them so they agree.

Common Pitfalls

Pitfalls & anti-patterns

Most relationship errors come from confusing "knows about" with "owns" or from reaching for inheritance when a link would do.

💠 Composition vs aggregation confusion

Marking a shared Product as composed into a LineItem implies deleting the order deletes the catalog entry. Pick the diamond by asking whether the part can outlive the whole.

🪢 Association where a dependency belongs

Storing the PaymentGateway as a field just to call it once tightens coupling and complicates tests. If it is used in one method, pass it as a parameter and draw a dashed dependency.

🧬 Inheritance for code reuse

Subclassing Order to reuse a discount method creates a fake "is a" relationship. Prefer a collaborator (composition) over generalization when you only want to share behavior.

➡️ Missing or wrong direction

Arrowless or backwards associations hide who depends on whom. Direction encodes navigability; drawing Customer pointing at Order when only the order holds the reference is simply wrong.

🔢 No multiplicity

Leaving ends unlabeled hides whether an order has one line item or many, or whether a customer is optional. Missing bounds let invalid object graphs slip through review.

🔁 Bidirectional by default

Making every association two-way creates reference cycles that leak memory and complicate serialization. Keep links one-directional unless both sides genuinely need to navigate.

Signals & Metrics

Signals & how to measure

You can sanity-check relationship choices against how the code and the object graph actually behave.

SignalWhat it tells you
Cascade-delete behaviorIf removing the whole must remove the part, the link is composition. If the part survives, it is aggregation or association.
Constructor origin of a fieldParts created with new inside the owner point to composition; references passed into the constructor point to aggregation or association.
Field vs parameterA collaborator kept as a field is an association; one that appears only in a method signature is a dependency.
Afferent / efferent couplingCounting incoming and outgoing dependencies per class flags boxes with too many arrows, a design smell worth refactoring.
Interface fan-inMany classes realizing one interface is healthy abstraction; zero realizations means the interface earns its keep only as future-proofing.
Inheritance depthDeep generalization chains (more than three levels) usually signal misused inheritance that composition would model more cleanly.
Rule of thumb: if you cannot answer "does the part die with the whole?" and "is it stored or just used?" you cannot yet pick the right arrow. Answer those two questions first, then draw.
06 - Case Studies

Real-world case studies

How relationship choices play out in production software systems.

🛒

1 · Ecommerce checkout at scale

Pattern: composition for order lines, dependency for payment

A commerce platform models orders that must be immutable snapshots once placed, while the product catalog keeps changing.

  • Order composes its LineItem objects and snapshots the price, so a later catalog change never rewrites a past order.
  • LineItem aggregates the shared Product only by reference and SKU, keeping the catalog a single source of truth.
  • PaymentGateway is a dependency injected into checkout(), letting the same order flow run against Stripe in production and a fake in tests.
✅ Outcome: Historical orders stay correct and auditable, and swapping payment providers touches one interface instead of the order model.
🏦

2 · Banking ledger and accounts

Pattern: composition for entries, realization for posting rules

A core banking system records transactions as ledger entries that must never exist without their parent transaction.

  • A Transaction composes its LedgerEntry lines; deleting or reversing the transaction cascades to the entries by design.
  • Each Account is associated with an AccountHolder that exists independently across many accounts.
  • Different products realize a common PostingPolicy interface, so savings, checking, and loan accounts share one posting seam.
✅ Outcome: Double-entry invariants are structurally enforced, and new account types plug into posting without altering the ledger core.
🚚

3 · Shipping and fulfillment

Pattern: aggregation for carriers, generalization for shipment types

A logistics service assembles shipments from warehouse packages and routes them through external carriers.

  • A Shipment composes its Package contents but aggregates a Carrier that serves thousands of shipments at once.
  • ExpressShipment and FreightShipment generalize a base Shipment, sharing tracking while overriding rate calculation.
  • A RateProvider dependency is passed into quote(), so carrier pricing APIs stay behind a single, mockable seam.
✅ Outcome: Adding a carrier or a shipment type is a local change, and the object graph mirrors real ownership so cleanup and reporting stay simple.
07 - Relevance

Modern relevance

Class relationships predate today's stacks, yet the same distinctions drive how modern systems are modeled and generated.

🗄️ ORM mappings

Composition versus aggregation maps directly to cascade rules and ownership in ORMs like Prisma, Hibernate, and ActiveRecord. The diagram decides your onDelete behavior.

🧩 Domain-driven design

Aggregates in DDD are UML composition made explicit: a root owns its parts and guards their invariants, and outside code holds only the root.

💉 Dependency injection

Preferring dependency over stored association is the whole premise of DI containers. Realization against interfaces is what lets them swap implementations.

🤖 Diagrams as code

Tools like Mermaid and PlantUML put these exact arrows in version control, so relationships live beside the code and stay in review.

🔗 API and event schemas

GraphQL types, protobuf messages, and event payloads encode the same has-a and is-a choices; getting ownership right prevents leaky, cyclic schemas.

🧠 AI-assisted modeling

When a model generates a class diagram from requirements, the hard part it still gets wrong is exactly this: composition versus aggregation, and dependency versus association.

Bottom line: the six relationships are a compact vocabulary for ownership, lifetime, and coupling. Master them and every class diagram, ORM mapping, and dependency graph you touch becomes easier to reason about and safer to change.
