OOP Foundation

UML class relationships - how objects connect

Every object model is a graph of relationships. UML gives you six precise ways to draw how classes relate: association, aggregation, composition, dependency, inheritance, and realization. Learn the arrows, the diamonds, the multiplicity, and the exact semantics, so a diagram means the same thing to every engineer who reads it.

01 - What

What are UML class relationships?

UML class relationships are the standardized lines and arrowheads that connect classes in a class diagram. Each one encodes a specific meaning about how two classes are coupled: does one use the other, hold it, own it for life, extend it, or implement its contract. The notation is a shared language, so intent survives the trip from whiteboard to code.

🔗 Structural links

Association, aggregation, and composition describe objects that reference each other and live together over time, with increasing degrees of ownership.

⚡ Usage links

Dependency is the lightest touch: one class uses another briefly, as a parameter, return type, or local, without holding a reference.

🧬 Type links

Inheritance (generalization) and realization describe is-a and implements-contract relationships between types, not between object instances.

The six relationships at a glance

RelationshipNotationMeaningStrength
DependencyDashed line, open arrow ..>Uses temporarily (param, return, local)Weakest
AssociationSolid line, open arrow -->Knows about, holds a referenceWeak
AggregationSolid line, hollow diamond o--Has-a, shared parts, independent lifecycleMedium
CompositionSolid line, filled diamond *--Owns-a, parts die with the wholeStrong
InheritanceSolid line, hollow triangle <|--Is-a, subtype extends supertypeType
RealizationDashed line, hollow triangle <|..Implements an interface contractType
Key mental model: the diamond always sits on the owner (the whole), and the triangle always points at the more general type (the parent or interface). Solid means a lasting reference, dashed means a passing use. Get those three cues right and you can read any class diagram.
02 - Why

Why the distinctions matter

These are not pedantic drawing rules. Each relationship implies different lifecycle management, coupling, and testability. Blurring them produces designs that leak memory, resist change, or break in surprising ways when one object is shared.

🗂️ Encodes ownership

Composition versus aggregation tells the reader whether one object must create and destroy another, or merely borrow a shared reference. That single decision drives your constructors, cleanup, and copying.

🔧 Reveals coupling

A dependency is cheap to break; a composition is not. Seeing the relationship type up front tells you how expensive a change will ripple through the system.

🧭 Communicates intent

An interface realization signals "swap me freely," while inheritance signals "I am a specialized kind of." Readers plan extensions differently based on which arrow they see.

🧮 Sets multiplicity contracts

Labels like 1, 0..1, and 1..* state exactly how many objects sit on each end, catching invalid states, such as an order with zero line items, before you write a single test.

In Plain Terms

UML class relationships explained with analogies

Same six ideas, four ways to picture them, so ownership and lifecycle click whoever you are.

🎓 For a student

Think of your backpack and your books. Books in the bag are aggregation: take them out and they still exist. Your heartbeat and your body are composition: remove the body and the heartbeat is gone. Borrowing a friend's calculator for one exam is a dependency.

👩‍💻 For a developer

A field that holds another object is an association. If you new that object inside the constructor and never share it, that is composition. If it arrives via a parameter and you just store it, that is aggregation. A type you implements is realization; a class you extends is inheritance.

🏢 For a professional

A company and its departments: dissolve the company and the departments vanish (composition). A project team of people borrowed from other units is aggregation; when the project ends the people remain. Hiring a consultant for one meeting is a dependency.

🏠 Everyday version

A house and its rooms are composition: demolish the house and the rooms go with it. The furniture is aggregation: it moves to the next house. "Is-a" is a cabin is a house (inheritance); "acts-as" is a house that can be rented (realization of a Rentable contract).

03 - How

How each relationship maps to code

Every UML relationship has a direct code fingerprint. The trick is learning to read a class body and name the relationship, and vice versa. The diagram below shows all six on one canvas, then the Java that produces them.

💎 Diamonds = ownership

A filled diamond (composition) means the whole creates its parts internally and they share its lifetime. A hollow diamond (aggregation) means the parts are passed in and outlive the whole.

🔺 Triangles = type

A hollow triangle on a solid line is extends (inheritance). The same triangle on a dashed line is implements (realization). Both point toward the more abstract type.

The same relationships in Java

// Realization: Employee implements the Payable contract (dashed triangle)
interface Payable {
    void pay();
}

// Inheritance / generalization: Employee IS-A Person (solid triangle)
class Person {
    protected String name;
    Person(String name) { this.name = name; }
}

class Address {                       // a value the Employee references
    final String city;
    Address(String city) { this.city = city; }
}

class TaxService {                    // used, but never stored
    double calc(Employee e) { return 0.0; }
}

class Employee extends Person implements Payable {
    private final Address address;    // association: holds a reference, 1..1

    Employee(String name, Address address) {
        super(name);
        this.address = address;       // reference passed in, not owned
    }

    @Override public void pay() { /* ... */ }

    // Dependency: TaxService is a parameter, used and discarded (dashed arrow)
    double taxes(TaxService service) {
        return service.calc(this);
    }
}

class Department {
    private final String name;
    // Aggregation: employees are passed in and outlive the department (hollow diamond)
    private final List<Employee> members = new ArrayList<>();

    Department(String name) { this.name = name; }
    void add(Employee e) { members.add(e); }   // shared, borrowed reference
}

class Company {
    // Composition: the company CREATES its departments; they die with it (filled diamond)
    private final List<Department> departments = new ArrayList<>();

    Company() {
        departments.add(new Department("Engineering")); // owned, built internally
        departments.add(new Department("Finance"));
    }
}

Read the code and the relationships fall out: extends is inheritance, implements is realization, a stored field passed in is association or aggregation, a field the class news internally and never leaks is composition, and a method parameter used once is a dependency.

05 - Step by Step

The 0 → 100 flow

From two unconnected classes to a correctly annotated, multiplicity-labeled diagram that maps cleanly to code.

00
Model

List the classes

Write down the nouns in your domain as candidate classes. Do not draw any lines yet; just get the boxes on the canvas.

10
Ask "is-a"

Find inheritance

For each pair, ask whether one is a specialized kind of the other. If yes and the substitution holds everywhere, draw a solid line with a hollow triangle toward the parent.

20
Ask "acts-as"

Find realization

Does a class promise to fulfill a contract, an interface, without being a subtype? Draw a dashed line with a hollow triangle to the interface.

30
Ask "has-a"

Find the structural links

Where one class holds another as a field, you have association, aggregation, or composition. The next steps tell them apart.

40
Ownership

Test the lifecycle

If the whole creates the part and the part cannot outlive it, it is composition (filled diamond). If the part is passed in and survives independently, it is aggregation (hollow diamond).

50
Reference

Default to association

If a class simply keeps a reference with no strong part-whole ownership claim, a plain solid line with an open arrow (association) is the honest choice.

60
Usage

Spot dependencies

Where a class only touches another as a method parameter, return type, or local variable, draw a dashed line with an open arrow. Nothing is stored.

70
Direction

Add navigability

Arrowheads show who can reach whom. If Employee knows its Address but Address never references Employee, point the arrow one way only.

80
Multiplicity

Label the ends

Annotate each end with counts: 1, 0..1, 1..*, or 0..*. A Company has 1..* Departments; a Department has 0..* Employees.

90
Verify

Cross-check against code

Walk each line back to a constructor, field, or method. If the code does not match the arrow, one of them is lying; fix the mismatch.

100
Communicate

Share the model

You now have a diagram anyone can read the same way: ownership, direction, and cardinality are all explicit and enforced by the notation.

Common Pitfalls

Pitfalls & anti-patterns

Most UML mistakes come from overstating a relationship. When in doubt, pick the weaker one.

💠 Composition when it is aggregation

Drawing a filled diamond for parts that are passed in and shared implies the whole owns their lifecycle. Readers then write cleanup code that destroys objects other classes still use.

🧬 Inheritance for code reuse

Extending a class just to borrow its methods, when no true is-a relationship exists, creates fragile hierarchies. Prefer composition; reserve inheritance for genuine substitutability.

🔢 Missing multiplicity

Leaving ends unlabeled hides invalid states. Without "1..*" nothing stops an Order from having zero line items, and the ambiguity leaks straight into buggy code.

↔️ Bidirectional by default

Adding arrowheads on both ends, or none, when navigation is really one-way inflates coupling and complicates updates. Draw navigability only where it exists.

🔗 Association masquerading as dependency

Storing an object in a field but drawing a dashed use-arrow understates the coupling. If it is a member, it is at least an association, not a passing dependency.

🎭 Realization drawn as inheritance

Using a solid triangle for an interface implementation loses the distinction between "is a kind of" and "fulfills a contract," misleading anyone planning extensions.

Trade-offs

Trade-offs & when to use

The relationships form a spectrum from loose to tight. Reach for the loosest one that still expresses the truth of your design.

AspectDetail
ProsA shared, unambiguous vocabulary; ownership and lifecycle become explicit; multiplicity catches invalid states; diagrams map directly to code.
ConsEasy to over-specify; distinctions like aggregation vs association are informal and debated; diagrams drift from code if not maintained.
Use whenDesigning or documenting a domain model, onboarding engineers, reviewing coupling, or agreeing on ownership before writing lifecycle-sensitive code.
Avoid whenA quick sketch will do, or the extra ceremony (precise diamonds and multiplicity) outweighs the value for a throwaway prototype.
ComplexityLow to draw, but the semantics are subtle. The hard part is judgment: composition vs aggregation and inheritance vs realization.
RelatedComposition-over-inheritance, coupling and cohesion, SOLID principles, and structural patterns like Composite that lean on these links.
Rule of thumb: prefer the weakest relationship that is still accurate. Dependency over association, association over aggregation, aggregation over composition, and composition over inheritance. Strength is a cost, not a feature, so pay for it only when the design truly demands it.
06 - Case Studies

Real-world case studies

Three familiar systems, each hinging on getting one relationship right.

🛒

1 · E-commerce order and line items

Pattern: composition with strict multiplicity

An order aggregates line items that make no sense on their own. Deleting the order must delete its items.

  • Order composes OrderLine with a filled diamond; the order creates and owns each line.
  • Multiplicity "1 to 1..*" enforces that an order always has at least one line item.
  • Product is referenced by association, not owned, because products exist independently of any order.
✅ Outcome: Cascading deletes and invariants fall out of the model, so no orphaned line items or empty orders slip into the database.
🎓

2 · University enrollment

Pattern: aggregation with shared parts

A course groups students, but students exist before and after the course and belong to many courses at once.

  • Course aggregates Student with a hollow diamond; students are passed in, never created by the course.
  • Multiplicity "0..* to 0..*" captures the many-to-many enrollment relationship.
  • Dropping a course leaves every student intact, exactly what the aggregation notation promises.
✅ Outcome: Lifecycle bugs disappear; ending a course never deletes a person, because the diagram made the shared ownership explicit.
💳

3 · Payment gateway abstraction

Pattern: realization for pluggable providers

A checkout service must support Stripe, PayPal, and others without changing its own code.

  • Each provider realizes a PaymentGateway interface with a dashed triangle.
  • Checkout depends on the interface, a dependency, so any provider drops in interchangeably.
  • Adding a new provider means one more realization, with zero edits to the checkout class.
✅ Outcome: New payment methods ship without touching core logic, because realization plus dependency isolated the contract from the implementations.
07 - Relevance

Modern relevance

UML as a heavyweight process faded, but its relationship vocabulary is more useful than ever in a world of quick sketches and generated diagrams.

📝 Diagrams as code

Mermaid, PlantUML, and D2 let you version class diagrams alongside source. The six relationships are first-class syntax, so the notation now lives in your repo.

🤖 AI-generated models

LLMs sketch class diagrams from a description in seconds. Knowing the semantics lets you catch when a tool draws composition where aggregation belongs.

🧩 Domain-driven design

Aggregates, entities, and value objects map directly onto composition and association. The relationships underpin how you draw bounded contexts.

🔍 Code review shorthand

Saying "that should be aggregation, not composition" is a precise, fast way to flag a lifecycle bug in review, no diagram required.

🏗️ Architecture whiteboarding

Interview and design sessions still run on boxes and arrows. Correct notation signals seniority and prevents costly ownership misunderstandings.

🔗 Foundation for patterns

Every design pattern is described in these relationships. Composite, Strategy, and Observer are all just specific arrangements of composition, realization, and dependency.

Bottom line: you may never draw a full UML spec again, but you will read and reason about these six relationships constantly. Master the diamonds, triangles, and multiplicity, and you can describe any object model precisely, in a diagram or a sentence.
