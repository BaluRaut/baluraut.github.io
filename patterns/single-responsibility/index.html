OOP Concept

The Single Responsibility Principle - one reason to change

A class should have one, and only one, reason to change. When an Invoice also formats itself, emails itself, and saves itself to the database, three unrelated forces tug on the same code. SRP splits that god class into focused collaborators, so each piece changes for its own reason and nothing else.

01 - What

What is the Single Responsibility Principle?

SRP is the "S" in SOLID. Robert C. Martin's precise wording is that a module should have one reason to change, where a reason to change maps to a single actor or stakeholder. A billing Invoice that computes totals, renders a PDF, sends email, and writes to Postgres answers to four different actors: finance, design, the mail platform team, and the DBA. Any one of them can force an edit, so the class is never stable.

🎯 One reason to change

A responsibility is an axis of change owned by one actor. Group code so that a single business change touches a single class.

🧲 High cohesion

Everything inside a class works toward the same purpose. Fields and methods belong together because they serve one job, not five.

🪓 Separation of concerns

Formatting, transport, and persistence are distinct concerns. Give each its own collaborator so they evolve independently.

Responsibilities hiding in one god class

ResponsibilityWho asks for the change (actor)Belongs in
Calculate totals & taxFinance / accounting rulesThe Invoice domain object
Render to PDF / HTMLDesign & brand teamInvoiceRenderer
Send to the customerMessaging / deliverability teamInvoiceMailer
Persist to storageDBA / infrastructureInvoiceRepository
Orchestrate the workflowProduct / use caseBillingService
Key mental model: SRP is not "one method per class" or "make everything tiny." It is about audience. Ask who would request a change and why. If two answers name two different teams, those are two responsibilities and they want two classes.
02 - Why

Why SRP matters

A god class couples unrelated reasons to change. Touch the PDF layout and you risk breaking tax math; swap the mail provider and you recompile the domain. SRP keeps those forces apart so change stays cheap and local.

🛡️ Change isolation

When the mail vendor changes from SMTP to a provider API, only InvoiceMailer moves. The totals logic and the database code never open in the diff, so the blast radius shrinks.

🧪 Testability

A pure Invoice with no I/O is tested with plain assertions, no database or SMTP stub. Persistence and mail are tested behind their own seams with fakes.

🔁 Reuse

The same InvoiceRenderer serves email, the customer portal download, and a nightly batch export. Bundled inside a god class, that rendering logic could never be reused.

👥 Parallel work

Because responsibilities map to teams, the design team edits rendering while the DBA tunes queries, with no merge conflicts on one 900-line file.

In Plain Terms

SRP explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

A study group where one person takes notes, one books the room, one photocopies handouts. If the copier breaks, only the handout person is stuck. Give one member all three jobs and every hiccup stalls the whole group.

👩‍💻 For a developer

Your Order class should not also open a socket to Stripe and write SQL. Keep the domain object pure and push payment and persistence into a PaymentGateway and an OrderRepository it collaborates with.

🏢 For a professional

A company has separate departments for finance, legal, and shipping. Nobody wants the shipping clerk rewriting tax law. Departments are responsibilities: each changes for its own reason under its own boss.

🍽️ Everyday version

In a restaurant the chef cooks, the waiter serves, the cashier bills. One person doing all three means a change to the menu, the till, and the floor plan all land on the same overworked human.

03 - How

How to apply SRP under the hood

Start from the god class, name each reason to change, then extract a focused collaborator per reason. The domain object keeps the business rules; formatting, mailing, and persistence move behind interfaces that a thin service wires together.

🔍 Name the reasons to change

List every method on the god class and label its actor: math (finance), layout (design), delivery (messaging), storage (DBA). Each distinct label is a seam where a class should split.

🧩 Extract focused collaborators

Move each concern into its own class behind a small interface. The Invoice holds data and totals; a BillingService composes the renderer, mailer, and repository to run the use case.

Before: one Invoice that does everything

// SMELL: one class, four reasons to change
class Invoice {
  constructor(
    public id: string,
    public lineItems: { amount: number; qty: number }[],
    public customerEmail: string,
  ) {}

  subtotal(): number {
    return this.lineItems.reduce((s, li) => s + li.amount * li.qty, 0);
  }
  tax(): number {
    return this.subtotal() * 0.2;
  }
  total(): number {
    return this.subtotal() + this.tax();
  }

  // Reason to change #2: the design team
  toHtml(): string {
    return `<h1>Invoice ${this.id}</h1><p>Total ${this.total()}</p>`;
  }

  // Reason to change #3: the messaging team
  email(): void {
    const smtp = new SmtpClient("mail.internal", 25);
    smtp.send(this.customerEmail, "Your invoice", this.toHtml());
  }

  // Reason to change #4: the DBA
  save(): void {
    const db = new PgConnection(process.env.DATABASE_URL!);
    db.exec("INSERT INTO invoices(id, total) VALUES($1, $2)", [
      this.id,
      this.total(),
    ]);
  }
}

// Invoice now has ONE reason to change: billing math
class Invoice {
  constructor(
    public id: string,
    public lineItems: { amount: number; qty: number }[],
  ) {}

  subtotal(): number {
    return this.lineItems.reduce((s, li) => s + li.amount * li.qty, 0);
  }
  tax(): number { return this.subtotal() * 0.2; }
  total(): number { return this.subtotal() + this.tax(); }
}

interface InvoiceRenderer { render(inv: Invoice): string; }
interface InvoiceMailer { send(to: string, body: string): void; }
interface InvoiceRepository { save(inv: Invoice): void; }

class PdfRenderer implements InvoiceRenderer {
  render(inv: Invoice): string {
    return `Invoice ${inv.id} - total ${inv.total()}`;
  }
}
class SmtpMailer implements InvoiceMailer {
  constructor(private smtp: SmtpClient) {}
  send(to: string, body: string): void {
    this.smtp.send(to, "Your invoice", body);
  }
}
class SqlInvoiceRepository implements InvoiceRepository {
  constructor(private db: PgConnection) {}
  save(inv: Invoice): void {
    this.db.exec("INSERT INTO invoices(id, total) VALUES($1, $2)", [
      inv.id, inv.total(),
    ]);
  }
}

// The use case composes collaborators; each changes for its own reason
class BillingService {
  constructor(
    private renderer: InvoiceRenderer,
    private mailer: InvoiceMailer,
    private repo: InvoiceRepository,
  ) {}

  issue(inv: Invoice, email: string): void {
    this.repo.save(inv);
    const doc = this.renderer.render(inv);
    this.mailer.send(email, doc);
  }
}

const billing = new BillingService(
  new PdfRenderer(),
  new SmtpMailer(new SmtpClient("mail.internal", 25)),
  new SqlInvoiceRepository(new PgConnection(process.env.DATABASE_URL!)),
);
billing.issue(new Invoice("INV-1024", [{ amount: 50, qty: 2 }]), "buyer@acme.com");

05 - Step by Step

The 0 → 100 flow

From a bloated Invoice god class to focused collaborators, the whole refactor in order.

00
Observe

Notice the god class

The Invoice imports an SMTP client and a database driver and is 900 lines long. That import list is the first smell: a data object should not depend on transport and storage.

10
Inventory

List every method and its actor

Write each method beside the team that would request a change: totals (finance), toHtml (design), email (messaging), save (DBA). Four actors means four reasons to change.

20
Group

Cluster by reason to change

Draw boxes around methods that share an actor. High cohesion means everything in a box moves together and rarely with anything outside it.

30
Name

Name a class per cluster

Give each cluster an intention-revealing name: InvoiceRenderer, InvoiceMailer, InvoiceRepository. The name should describe one job, not "manager" or "helper."

40
Interface

Define a seam for each concern

Declare a small interface per collaborator so callers depend on a contract, not a vendor. This is where SRP starts enabling dependency inversion.

50
Extract

Move rendering out

Cut toHtml into PdfRenderer.render(invoice). The renderer reads the invoice through its public methods and returns a document.

60
Extract

Move mailing out

Cut email into SmtpMailer.send(to, body). The mailer now depends only on a string body, not on invoice internals.

70
Extract

Move persistence out

Cut save into SqlInvoiceRepository.save(invoice). All SQL and connection handling leaves the domain object for good.

80
Compose

Introduce a use-case service

Create BillingService.issue(invoice, email) that takes the three collaborators as constructor arguments and sequences save, render, send.

90
Wire

Assemble at the composition root

In main or a factory, build the concrete renderer, mailer, and repository and hand them to the service. Nothing else knows the vendors.

100
Verify

Confirm one reason each

Re-run the inventory: Invoice now changes only for billing math, and each collaborator for its own actor. Unit tests on the pure invoice need no I/O.

Common Pitfalls

Pitfalls & anti-patterns

SRP is easy to over-apply or misread. These are the usual mistakes on both sides.

🐙 The god class

An OrderManager that validates, charges, ships, emails, and logs. It touches every table and never stops changing because every team has a reason to edit it.

🔬 Over-splitting

Reacting by making one class per method: InvoiceTotalCalculator, InvoiceSubtotalCalculator, InvoiceTaxCalculator. Now a single change fans out across five files. SRP is about actors, not line counts.

🏷️ Vague names

Classes ending in Manager, Helper, Util, or Processor are magnets for unrelated code because their responsibility was never defined. The vague name invites scope creep.

🧵 Hidden side effects

A total() getter that also writes an audit row to the database. A method that reads should not persist. Mixed intent hides a second responsibility inside an innocent-looking call.

💉 Shotgun surgery

The opposite smell: one logical change forces edits across many classes because a responsibility was scattered rather than split cleanly. Cohesion leaked out during a rushed extraction.

🧊 Anemic split

Pulling all behavior out so Invoice becomes a bag of getters with logic living in services. Taken too far this drifts into an anemic domain model where objects hold data but no rules.

Signals & Metrics

Signals & how to measure

You cannot count "responsibilities" directly, but several signals reliably expose an overloaded class.

SignalWhat it tells you
Reasons to changeName the actors that could request an edit. More than one distinct team usually means more than one responsibility.
Import / dependency spreadA domain class that imports an SMTP client, a PDF library, and a DB driver is doing transport, formatting, and storage at once.
LCOM (lack of cohesion)Methods that share no fields form disjoint clusters. High LCOM means the class is really several classes stuck together.
Commit co-change churnIf unrelated features keep editing the same file, its responsibilities are entangled. Git history exposes the coupling.
Test setup weightNeeding a database, an SMTP fake, and a PDF stub just to test one method signals mixed concerns behind one door.
The "and" testIf describing the class needs "and" (formats and mails and saves), each clause is a candidate responsibility to extract.
Rule of thumb: if you cannot describe a class in one sentence without the word "and," it probably has more than one reason to change. Split by actor, not by arbitrary size.
06 - Case Studies

Real-world case studies

Three production-style systems where separating responsibilities paid off.

💳

1 · Splitting a billing god class in a subscriptions platform

Pattern: extract collaborators from an overloaded domain object

A SaaS billing service had an Invoice that computed proration, rendered PDFs, sent email, and wrote to Postgres, so every team fought over one file.

  • Proration math stayed on Invoice; rendering moved to an InvoiceRenderer interface with PDF and HTML implementations.
  • Delivery moved behind an InvoiceMailer, letting the messaging team swap providers without touching finance logic.
  • Persistence moved to an InvoiceRepository, so the DBA could change the schema without recompiling the domain.
✅ Outcome: Tax rule changes and vendor migrations stopped colliding in the same pull request, and the pure invoice became trivial to unit test.
🛒

2 · Untangling checkout in an e-commerce order flow

Pattern: one use-case service coordinating single-purpose classes

An OrderService validated carts, charged cards, reserved inventory, and emailed receipts inside one method, so any change risked the whole checkout.

  • Payment moved behind a PaymentGateway interface, isolating the card-processor SDK from order rules.
  • Stock changes moved to an InventoryReservation class owned by the warehouse team.
  • A thin PlaceOrder use case sequenced validate, charge, reserve, notify, each delegated to a focused collaborator.
✅ Outcome: Switching from one payment processor to another became a one-class change, and inventory logic evolved independently of checkout.
🔔

3 · Decoupling a notification pipeline at a logistics company

Pattern: separate what to send from how to send it

A shipment tracker built email bodies, formatted SMS, called three vendor APIs, and logged delivery status all in one Notifier class.

  • Message content moved to per-event NotificationTemplate classes owned by product.
  • Each channel became its own sender (EmailSender, SmsSender, PushSender) behind a shared interface.
  • A DispatchService chose channels by user preference and delegated, holding no vendor code itself.
✅ Outcome: Adding a WhatsApp channel meant writing one new sender class, with template and dispatch code untouched.
07 - Relevance

Modern relevance

SRP predates SOLID's popularity but has only grown more central as systems decompose into services and functions.

🧱 Microservices boundaries

A service that owns one bounded context is SRP at the deployment scale. The same "one reason to change" test that splits classes also draws service seams.

⚡ Serverless functions

A single-purpose function per event is SRP made physical. Each handler changes for one trigger, and unrelated logic lives in its own deployment.

🧭 Hexagonal architecture

Ports and adapters formalize SRP: the domain holds rules, and each adapter (mail, DB, HTTP) is a single-responsibility edge that plugs in behind a port.

🧪 Testability at scale

Pure domain objects with no I/O give fast, deterministic unit tests. SRP is what makes that purity possible without heavyweight mocks.

🤖 AI-assisted refactors

Extract-class refactors are exactly what coding assistants do well, but they still need a human to name the actors. SRP gives that judgment a rule.

📦 Domain-driven design

Aggregates, repositories, and application services in DDD are named responsibilities. SRP is the low-level discipline that keeps each of them focused.

Bottom line: SRP scales from a single method to a whole service. Whenever you find one thing that changes for many reasons, split it by actor. Focused collaborators cost a little more wiring and repay it every time requirements shift.
