OOP Concept

When NOT to use OOP - and what to reach for instead

Objects earn their keep when you have identity, mutable state, and behavior that travels with data. But a lot of real code is just data in, data out: an ETL transform, a pricing calculation, a one-off migration script. Wrapping those in classes adds ceremony without buying anything. This page is about recognizing when procedural, functional, or data-oriented code is the clearer choice, and how to mix paradigms without dogma.

01 - What

What "not OOP" actually means

This is not anti-OOP. It is about matching the tool to the shape of the problem. OOP bundles state and behavior behind an interface so objects can collaborate over time. When your problem has no long-lived state and no identity to protect, that bundling becomes overhead: constructors, dependency wiring, mocks, and lifecycle you do not need. The alternatives are procedural code, functional pipelines, and data-oriented design that keeps plain data and the functions over it separate.

🔁 Stateless transforms

An ETL step that takes rows in and returns rows out holds no state between calls. A pure function is the honest signature; a class with a single run() method is a function wearing a costume.

🧮 Pure calculations

Pricing, tax, discounts, and currency math are deterministic: same inputs, same output. Functions compose and test trivially. Objects add a lifecycle that pure math never asked for.

📜 Small scripts

A backfill or a CSV cleanup that runs once and exits does not need a class hierarchy. Top-to-bottom procedural code you can read in one pass is the correct amount of structure.

Where OOP fits and where it does not

Signal in the problemOOP fitsPrefer procedural / functional
Long-lived identityA ShoppingCart or Account that persists and mutatesA tax calc that lives only for one call
State + invariantsA ledger that must never go negativeA stateless map/filter over a batch of records
PolymorphismMany payment providers behind one interfaceA single fixed transform with no variants
Data shapeRich behavior tied to each entityFlat rows flowing through a pipeline
LifetimeA long-running service with sessionsA cron script that runs and exits
Key mental model: objects are for things that persist and enforce rules. If your code is a one-way street from input to output with nothing to protect between calls, a function is the clearer, cheaper, more testable unit.
02 - Why

Why forcing OOP hurts

Dogmatic OOP turns simple data flow into a graph of collaborators you must construct, inject, and mock. The ceremony obscures the actual computation and slows every future reader down.

🎭 Ceremony over substance

A three-line transform becomes a class with a constructor, a private field, and a process() method. Readers now scan boilerplate to find one map. The signal-to-noise ratio drops.

🧪 Harder testing

Pure functions need only inputs and asserted outputs. An object graph needs constructed dependencies, mocks, and stubs to test the same logic. You test wiring instead of behavior.

🕳️ Hidden mutation

Objects invite mutable fields. In a data pipeline that should be a clean sequence of immutable stages, hidden state creates order-dependent bugs that are painful to reproduce.

🧩 Anemic shells

Wrapping data-only records in classes that just get and set fields produces the anemic domain model: all the ceremony of objects with none of the behavior that justifies them.

In Plain Terms

When NOT to use OOP explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

You do not build a filing cabinet to add two numbers on a scrap of paper. A pricing formula is the scrap of paper. Objects are the cabinet: worth it when you are storing and managing many things over time, wasteful for a single sum.

👩‍💻 For a developer

An ETL stage is a Unix pipe: read | clean | enrich | write. Each stage takes a stream and returns one. You would not turn grep into a stateful object with a lifecycle just to filter lines.

🏢 For a professional

Filling in a tax form is a procedure: fixed inputs, fixed rules, one number out. You do not hire a standing department to compute one return. Reserve the org chart (objects and roles) for the ongoing business, not the one-off calculation.

🍳 Everyday version

To make toast you follow steps, you do not appoint a Toast Manager who owns a Bread repository. Simple linear tasks want a recipe, not an organization with departments and hand-offs.

03 - How

How to recognize and refactor the over-objected case

The tell is a class with no meaningful state, one public method, and a name that ends in -er or -Manager. It is a function that grew a constructor. The fix is to collapse it into a pure function or a small pipeline of them.

🔎 Spot the smell

Look for classes whose only field is injected config and whose only method is run, process, or calculate. That is a stateless computation. It wants to be a function, optionally curried with its config.

🧵 Compose stages

Model an ETL flow as a sequence of small pure functions passing immutable data. Each stage is independently testable, reorderable, and reusable, with no shared mutable object holding the batch.

Over-objected design vs a simpler functional pipeline

// OVER-OBJECTED: four classes to compute one price.
class TaxService {
  apply(cents: number, region: string): number {
    const rate = region === "EU" ? 0.20 : 0.0725;
    return Math.round(cents * (1 + rate));
  }
}
class DiscountEngine {
  apply(cents: number, coupon?: string): number {
    return coupon === "SAVE10" ? Math.round(cents * 0.9) : cents;
  }
}
class PriceCalculator {
  constructor(private tax: TaxService, private discounts: DiscountEngine) {}
  calculate(order: { subtotalCents: number; region: string; coupon?: string }): number {
    const discounted = this.discounts.apply(order.subtotalCents, order.coupon);
    return this.tax.apply(discounted, order.region);
  }
}
const calc = new PriceCalculator(new TaxService(), new DiscountEngine());
calc.calculate({ subtotalCents: 5000, region: "EU", coupon: "SAVE10" }); // 5400

// SIMPLER: pure functions that compose. No wiring, no mocks to test.
type Order = { subtotalCents: number; region: string; coupon?: string };

const applyDiscount = (cents: number, coupon?: string): number =>
  coupon === "SAVE10" ? Math.round(cents * 0.9) : cents;

const applyTax = (cents: number, region: string): number => {
  const rate = region === "EU" ? 0.20 : 0.0725;
  return Math.round(cents * (1 + rate));
};

const priceOrder = (o: Order): number =>
  applyTax(applyDiscount(o.subtotalCents, o.coupon), o.region);

priceOrder({ subtotalCents: 5000, region: "EU", coupon: "SAVE10" }); // 5400

  coupon == "SAVE10" ? (cents * 0.9).round : cents
end

def apply_tax(cents, region)
  rate = region == "EU" ? 0.20 : 0.0725

Both versions compute the same 5400 cents. The functional version drops the constructors, the injected fields, and the mocks you would need to test the object graph. What is left is exactly the math, expressed as composition. This is data-oriented design: plain data flows through pure functions, and nothing hides state between calls.

An ETL pipeline as composed stages, not a stateful engine

// A transform pipeline: each stage is data-in, data-out. No engine object.
type Row = { email: string; amount: string; region: string };
type Clean = { email: string; cents: number; region: string };

const parse = (rows: Row[]): Clean[] =>
  rows.map(r => ({
    email: r.email.trim().toLowerCase(),
    cents: Math.round(parseFloat(r.amount) * 100),
    region: r.region.toUpperCase(),
  }));

const dropInvalid = (rows: Clean[]): Clean[] =>
  rows.filter(r => r.email.includes("@") && r.cents > 0);

const totalsByRegion = (rows: Clean[]): Record<string, number> =>
  rows.reduce((acc, r) => ({ ...acc, [r.region]: (acc[r.region] ?? 0) + r.cents }), {} as Record<string, number>);

// Compose the whole pipeline as a single expression.
const run = (rows: Row[]) => totalsByRegion(dropInvalid(parse(rows)));

from functools import reduce

def parse(rows):
    return [
        {
            "email": r["email"].strip().lower(),
            "cents": round(float(r["amount"]) * 100),
            "region": r["region"].upper(),
        }
        for r in rows
    ]

def drop_invalid(rows):
    return [r for r in rows if "@" in r["email"] and r["cents"] > 0]

def totals_by_region(rows):
    acc = {}
    for r in rows:
        acc[r["region"]] = acc.get(r["region"], 0) + r["cents"]
    return acc

# Compose the whole pipeline as a single expression.
def run(rows):
    return totals_by_region(drop_invalid(parse(rows)))
# A transform pipeline: each stage is data-in, data-out. No engine object.
def parse(rows)
  rows.map do |r|
    {
      email: r[:email].strip.downcase,
      cents: (r[:amount].to_f * 100).round,
      region: r[:region].upcase,
    }
  end
end

def drop_invalid(rows)
  rows.select { |r| r[:email].include?("@") && r[:cents] > 0 }
end

def totals_by_region(rows)
  rows.each_with_object(Hash.new(0)) { |r, acc| acc[r[:region]] += r[:cents] }
end

# Compose the whole pipeline with method chaining.
def run(rows)
  totals_by_region(drop_invalid(parse(rows)))
end

Nothing here is an object with a lifecycle. Each stage is a pure transformation you can unit-test in isolation, reorder, or reuse in another pipeline. Adding a stage means adding a function, not editing a stateful engine and re-checking its invariants.

05 - Step by Step

The 0 → 100 flow

A decision procedure for choosing paradigm per unit of code, from first look to a maintainable result.

00
Frame

Describe the unit in one sentence

Say what it does out loud: "computes a total from an order", "cleans a CSV". A pure input-to-output sentence is a strong hint toward a function.

10
State

Ask: is there long-lived state?

Does anything need to persist and mutate between calls? A cart, an account, a connection pool. If nothing persists, you likely do not need an object.

20
Identity

Ask: is there identity to protect?

Two carts with the same items are still different carts. If instances have identity and invariants, objects fit. If your data is just values, prefer records and functions.

30
Variants

Ask: do you need polymorphism?

Many interchangeable providers behind one interface justify classes. One fixed calculation with no variants does not; a function is enough.

40
Lifetime

Weigh the script vs the service

A one-off backfill that runs and exits wants top-to-bottom procedural code. A long-running service with sessions is where object lifecycles pay off.

50
Shape data

Model plain data first

Define the records that flow through: rows, orders, line items. Keep them as simple immutable values before deciding what behavior, if any, needs to attach.

60
Write functions

Express the core as pure functions

Turn each transform into a function with no side effects. Deterministic math and reshaping belong here, isolated from I/O.

70
Compose

Chain stages into a pipeline

Compose the functions into one flow. Each stage is testable alone and the whole reads as a sequence, not a graph of collaborators.

80
Boundary

Push objects to the edges

Where you truly need state, a repository, a session, a stateful client, keep it at the boundary and let it call into the pure core.

90
Test

Assert inputs and outputs directly

Pure functions test without mocks: pass data, assert results. Reserve heavier integration tests for the thin stateful edges.

100
Review

Delete the ceremony

If a class has one method and no real state, collapse it into a function. Keep objects only where identity, state, or polymorphism earned them.

Common Pitfalls

Pitfalls & anti-patterns

The failure modes cut both ways: forcing objects where functions fit, and swinging so hard the other way you lose the structure objects rightly provide.

🏭 The -er class

A Manager, Processor, or Handler with no state and one method is a function in disguise. It multiplies constructors and mocks without encapsulating anything.

💉 Injection theater

Wiring stateless helpers through a DI container so you can mock pure math. If a dependency has no side effects, you can just call it; the container is pure overhead.

🩻 Anemic domain model

Classes that are only getters and setters over data. You paid the object tax and got none of the behavior. Either add real invariants or use a plain record.

🌀 Stateful pipeline engine

An ETL "engine" object that accumulates the batch in mutable fields creates order-dependent bugs. Immutable data through pure stages avoids the whole class of defect.

🔨 Overcorrecting to spaghetti

Rejecting objects everywhere yields a pile of free functions sharing global state. Functional does not mean unstructured; group by module and keep data immutable.

🧬 Deep hierarchies for calculation

Subclassing to vary a formula bakes a taxonomy into inheritance. A function taking a strategy or a lookup table flexes without the fragile base class.

Signals & Metrics

Signals & how to measure

You rarely need a formal metric to feel this, but these signals make the call concrete and reviewable.

SignalWhat it tells you
Fields per classZero real state (only injected config) means the class is a stateless computation dressed as an object. Collapse it to a function.
Public methods per classExactly one public method named run or calculate is a strong "this is a function" signal.
Mocks per unit testNeeding many mocks to test simple logic means you are testing wiring, not behavior. Pure functions need none.
Mutation in transformsIn-place mutation inside a data pipeline predicts order-dependent bugs. Immutable data through pure stages is safer.
Constructor-to-logic ratioMore lines wiring dependencies than doing work signals ceremony that a function would erase.
Instance lifetimeObjects created and discarded within a single call have no lifecycle to justify them. A function has the same lifetime honestly.
Rule of thumb: if a class has no meaningful state, one public method, and needs mocks to test its own logic, it should be a function. Keep objects for identity, invariants, and polymorphism; use functions for stateless transforms and pure math.
06 - Case Studies

Real-world case studies

Three production-style situations where dropping or limiting OOP made the system clearer and safer.

🧾

1 · Billing engine rebuilt as pure functions

Domain: subscriptions & invoicing

A subscriptions team had proration, tax, and discount logic spread across a graph of service objects that were hard to test and reason about.

  • Extracted the math into pure functions over immutable invoice data, keeping I/O in a thin repository at the edge.
  • Replaced dozens of mock-heavy tests with plain input-output assertions covering edge cases like leap-year proration.
  • Kept the Subscription aggregate as an object because it has real state and lifecycle rules worth protecting.
✅ Outcome: The pricing core became deterministic and trivially testable, while objects stayed exactly where identity and invariants justified them.
🔀

2 · ETL pipeline as composed stages

Domain: data ingestion & reporting

A reporting pipeline used a stateful "processor" object that accumulated rows in mutable fields, producing intermittent, order-dependent totals.

  • Rewrote each step, parse, validate, enrich, aggregate, as a pure function passing immutable batches forward.
  • Composed the stages into one flow so a new enrichment was an added function, not an edit to shared mutable state.
  • Ran stages in isolation for tests and reused two of them unchanged in a second pipeline.
✅ Outcome: The order-dependent bugs disappeared, and adding or reordering stages became a low-risk, local change.
📜

3 · One-off data migration script

Domain: schema migration & backfill

An engineer started building a class hierarchy, readers, mappers, writers, for a migration that would run once and be deleted.

  • Replaced the hierarchy with a top-to-bottom procedural script that reads, maps, and writes in clear phases.
  • Guarded correctness with a dry-run flag and idempotent upserts instead of an abstraction layer.
  • Left the script readable in a single pass so reviewers could verify the backfill without tracing indirection.
✅ Outcome: The migration shipped in a fraction of the time, was easy to review, and was safely deleted after it ran, with no framework to maintain.
07 - Relevance

Modern relevance

Mainstream languages have grown functional and data-oriented features, making "not everything is an object" the pragmatic default rather than a fringe stance.

🧊 Records & value types

Immutable records in modern TypeScript, Python dataclasses, and Ruby Data give you plain data without the ceremony of full classes, exactly the shape pipelines want.

🧵 Pattern matching

Structural matching in Python, Ruby, and TS-adjacent tools lets you branch on data shape without a polymorphic class hierarchy for every variant.

🚿 Data-oriented design

Separating plain data from the functions over it improves cache behavior and clarity, a principle now common far beyond game engines.

⚙️ Functional cores

The "functional core, imperative shell" style is a mainstream architecture: pure logic inside, side effects at the boundary.

🔗 Composable pipelines

Stream and iterator abstractions make composed stateless stages idiomatic, so ETL and transforms rarely need a bespoke engine object.

🤝 Pragmatic polyglot code

Teams mix paradigms per module without apology: objects for stateful aggregates, functions for math and transforms, chosen by fit.

Bottom line: OOP is one tool, not the default wrapper for all code. Reach for objects when you have identity, state, and invariants to protect; reach for functions and data-oriented design for stateless transforms, pure calculations, and small scripts. The senior move is mixing paradigms deliberately, not enforcing one everywhere.
