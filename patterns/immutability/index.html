OOP Concept

Immutability - objects that never change after construction

An immutable object is fully built by its constructor and never mutated again. Every field is set once and validated up front, so the object is always in a valid state. When you need a variant, you don't edit it - you compute a new object and leave the original untouched.

01 - What

What is immutability?

An immutable object exposes no operation that changes its observable state. Money, a date range, or an application config is created once, checked once, and from then on it is read-only. Callers that want a different value ask a method for a fresh object; the receiver is never rewritten in place. That single rule removes a whole class of bugs and unlocks safe sharing.

🧱 Set once, at construction

All fields are assigned in the constructor and validated there. A Money with a negative minor-unit amount or mismatched currency simply cannot exist.

🔒 No mutators

There are no setters and no methods that reassign fields. The public surface is queries and pure transformations that return new instances.

➕ Functional updates

Operations like add or withCurrency return a brand-new object. The original stays exactly as it was, so old references never see surprise changes.

The core building blocks

Key mental model: an immutable object is a value, not a slot. You never change what 5 means, and you never change what a given Money(499, "USD") means either. To get a different value you compute one; the original is permanent and safe to share.
02 - Why

Why immutability exists

Mutable shared state is the root of most concurrency bugs and aliasing surprises. When an object can change under you, every reference to it becomes a liability. Immutability trades a little copying for a large amount of certainty.

🧵 Thread safety for free

If no thread can change an object, no thread needs a lock to read it. Immutable Money and Config can be shared across a request pool with zero synchronization.

🔗 Safe sharing & caching

You can hand the same instance to many callers, cache it, and use it as a hash-map key without fear that someone downstream mutates it and corrupts everyone else's copy.

🐛 No aliasing bugs

Two variables pointing at the same object can never diverge unexpectedly, because the object never changes. Passing it to a function cannot surprise the caller.

🧭 Easy to reason about

State only ever appears in constructors, so you audit correctness in one place. Undo, retries, and time-travel debugging become trivial when old values still exist.

In Plain Terms

Immutability explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It's like an exam answer written in pen. Once it's down you don't erase it; if you change your mind you write a fresh, corrected copy. The old sheet stays exactly as it was.

👩‍💻 For a developer

Think of a string in most languages. "hello".toUpperCase() doesn't change the original; it returns a new string. Immutable domain objects behave the same way.

🏢 For a professional

Like a signed contract. You never scribble on the executed document; you issue an amendment as a new versioned document. The original remains the record of what was agreed.

🧾 Everyday version

A printed receipt. To fix a charge the shop doesn't rewrite your receipt; it prints a new one. Both slips exist, and history stays honest.

03 - How

How it works under the hood

Immutability is two disciplines working together: lock the fields so nothing can reassign them, and replace whole objects instead of editing them. The language gives you the lock; you supply the functional-update methods.

🔐 Lock the fields

Mark every field read-only at the type level. TypeScript uses readonly, Python uses a frozen=True dataclass, and Ruby calls freeze in the constructor. Any attempt to reassign is a compile error or runtime error.

🔁 Return new objects

Every "change" is a method that reads the current fields, computes the next values, and constructs a fresh instance. The caller rebinds their variable; the old object is untouched and still valid.

The same immutable class in three languages

// Money as an immutable value object. Amount is in minor units (cents).
class Money {
  constructor(
    public readonly amount: number,
    public readonly currency: string,
  ) {
    if (!Number.isInteger(amount)) throw new Error("amount must be integer minor units");
    if (currency.length !== 3) throw new Error("currency must be an ISO code");
    Object.freeze(this); // lock the instance at runtime too
  }

  // Functional update: returns a NEW Money, never mutates `this`.
  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("currency mismatch");
    return new Money(this.amount + other.amount, this.currency);
  }

  scale(factor: number): Money {
    return new Money(Math.round(this.amount * factor), this.currency);
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }

  format(): string {
    return `${(this.amount / 100).toFixed(2)} ${this.currency}`;
  }
}

const price = new Money(1999, "USD");
const shipping = new Money(500, "USD");
const total = price.add(shipping);   // -> new Money(2499, "USD")
console.log(price.format());         // "19.99 USD" (unchanged)
console.log(total.format());         // "24.99 USD"
# Money as an immutable value object using a frozen dataclass.
from dataclasses import dataclass, replace

@dataclass(frozen=True)          # frozen -> fields cannot be reassigned
class Money:
    amount: int                  # minor units (cents)
    currency: str

    def __post_init__(self):
        if not isinstance(self.amount, int):
            raise ValueError("amount must be integer minor units")
        if len(self.currency) != 3:
            raise ValueError("currency must be an ISO code")

    # Functional update: returns a NEW Money, never mutates self.
    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError("currency mismatch")
        return replace(self, amount=self.amount + other.amount)

    def scale(self, factor: float) -> "Money":
        return replace(self, amount=round(self.amount * factor))

    def format(self) -> str:
        return f"{self.amount / 100:.2f} {self.currency}"

price = Money(1999, "USD")
shipping = Money(500, "USD")
total = price.add(shipping)      # -> Money(amount=2499, currency='USD')
print(price.format())            # "19.99 USD" (unchanged)
print(total.format())            # "24.99 USD"

# Money as an immutable value object. freeze locks the instance.
class Money
  attr_reader :amount, :currency   # readers only, no writers

  def initialize(amount, currency)
    raise ArgumentError, "amount must be integer minor units" unless amount.is_a?(Integer)
    raise ArgumentError, "currency must be an ISO code" unless currency.length == 3
    @amount = amount
    @currency = currency.freeze
    freeze                          # no ivar can be reassigned after this
  end

  # Functional update: returns a NEW Money, never mutates self.
  def add(other)
    raise ArgumentError, "currency mismatch" unless other.currency == @currency
    Money.new(@amount + other.amount, @currency)
  end

  def scale(factor)
    Money.new((@amount * factor).round, @currency)
  end

  def ==(other)
    other.is_a?(Money) && amount == other.amount && currency == other.currency
  end

  def format
    format_amount = (@amount / 100.0)
    "%.2f %s" % [format_amount, @currency]
  end
end

price = Money.new(1999, "USD")
shipping = Money.new(500, "USD")
total = price.add(shipping)       # -> new Money(2499, "USD")
puts price.format                 # "19.99 USD" (unchanged)
puts total.format                 # "24.99 USD"
# price.instance_variable_set(:@amount, 0)  # FrozenError

In all three, add reads the receiver, computes the next amount, and hands back a new Money. The original price still formats as 19.99 after the addition. The frozen or readonly declaration is what makes that guarantee enforceable rather than a convention.

05 - Step by Step

The 0 → 100 flow

From designing a value to safely sharing it across a live system - the whole journey in order.

00
Model

Identify a value

Spot a concept defined entirely by its data, like Money, a DateRange, or an app Config. These are candidates for immutability because identity does not matter, only the fields do.

10
Fields

Declare read-only fields

List the minimal fields and mark them read-only: TS readonly, a Python frozen dataclass, or Ruby instance variables you will freeze.

20
Validate

Guard in the constructor

Reject bad input up front - non-integer amounts, unknown currency, a range whose end precedes its start. A constructed object is always valid.

30
Freeze

Lock the instance

Finalize immutability: Object.freeze(this), the frozen dataclass machinery, or freeze as the last line of the constructor.

40
Query

Expose read-only methods

Add pure queries like format(), contains(date), or isEnabled(flag) that compute from fields without changing anything.

50
Update

Add functional updates

Write add, withCurrency, or extendTo(date) that build and return a new instance instead of mutating the receiver.

60
Equality

Compare by value

Implement field-by-field equality and a matching hash so two equal values are interchangeable and usable as map keys.

70
Nesting

Guard collections

Ensure nested arrays or maps are also frozen or defensively copied, so a shared inner list cannot leak mutability.

80
Share

Pass freely, no locks

Hand the same instance to many callers and threads. Because it never changes, no synchronization is required to read it.

90
Cache

Cache and key safely

Memoize results and use the value as a cache key. Nothing downstream can corrupt a cached entry by mutating it.

100
Evolve

Version through new objects

When requirements change, produce new instances for new states. Old values persist, powering undo, audit trails, and easy reasoning.

Common Pitfalls

Pitfalls & anti-patterns

Immutability is easy to declare and easy to accidentally break. These are the usual leaks.

🕳️ Shallow freeze

Marking the object read-only but leaving a nested array or map mutable. Callers edit the inner collection and the "immutable" object silently changes. Freeze or copy the nested state too.

🚪 Leaking internal references

Returning the actual internal list from a getter lets callers mutate it directly. Return a copy, a frozen view, or an iterator instead of the live reference.

🔧 Hidden setters

Adding a convenience method that reassigns a field "just this once" destroys every guarantee. If any code path mutates state, it is not immutable. Keep the surface query-only.

🐢 Copy churn in hot loops

Building a new object per iteration when summing thousands of values can allocate heavily. Use a builder or accumulate primitives, then construct one final immutable result.

🎭 Equality by identity

Forgetting value equality means two equal Money instances look different, breaking sets, cache keys, and deduplication. Immutable values need field-based equals and hash.

🧨 Mutable default arguments

Sharing a mutable default like a list across instances in Python leaks state between objects. Use immutable defaults or a factory so each instance is independent.

Signals & Metrics

Signals & how to measure

You can tell whether immutability is real or aspirational by watching a few signals in the codebase and at runtime.

SignalWhat it tells you
Setter count on value typesZero setters or field reassignments means the object is genuinely immutable, not just labeled so.
Freeze / readonly coverageHow many value classes actually declare frozen or readonly fields versus relying on convention.
Defensive-copy auditWhether getters return copies or frozen views; leaked live references reveal hidden mutability.
Locks around shared stateFewer locks needed as more shared objects become immutable - a direct concurrency-simplification signal.
Aliasing bug rateDrop in "value changed unexpectedly" defects after converting a type to immutable.
Allocation profileObject churn from functional updates in hot paths, telling you where a builder or batching is worth it.
Rule of thumb: if you can find a single line of code that reassigns a field on a value object after construction, it is not immutable yet. Grep for setters and field writes before trusting the label.
06 - Case Studies

Real-world case studies

Three production-style systems where immutability is load-bearing.

💳

1 · Money in a payments ledger

Pattern: immutable value object for amounts

A payments platform represents every amount as an immutable Money in integer minor units, shared across pricing, tax, and settlement.

  • Amounts never mutate: a discount produces a new Money, so the original line price is preserved for audit.
  • Currency mismatch is impossible to add together, caught at the operation instead of in a downstream report.
  • Ledger entries are safe to cache and reconcile because no code path can rewrite a posted amount.
✅ Outcome: Fewer rounding and currency defects, and a clean audit trail because historical amounts are permanent by construction.
📅

2 · DateRange in a bookings engine

Pattern: immutable interval with functional updates

A reservations service models availability windows as an immutable DateRange validated so the end never precedes the start.

  • Extending a stay returns a new DateRange, leaving the original booking window intact for the change log.
  • Overlap and contains checks are pure queries, safe to run concurrently across many availability workers.
  • Ranges are used as cache keys for pricing, which only works because they compare by value and never change.
✅ Outcome: Concurrency-safe availability checks and a trustworthy history of how each reservation window evolved.
🎛️

3 · Immutable app Config at startup

Pattern: frozen configuration shared everywhere

A backend service loads its configuration once into an immutable Config object read by every request handler and thread.

  • Config is validated and frozen at boot, so no request can accidentally flip a flag mid-flight.
  • A config reload builds a whole new Config and swaps the reference atomically, never editing the live one.
  • Because it never mutates, thousands of concurrent reads need no locks and no defensive copying.
✅ Outcome: Deterministic behavior per deploy, safe hot reloads via reference swap, and no lock contention on the hottest read path.
07 - Relevance

Modern relevance

Immutability is not a relic of functional programming; it is central to how modern concurrent and reactive systems stay correct.

⚛️ Reactive UI state

Frameworks like React rely on immutable state so change detection is a cheap reference comparison. New state means a new object, never an in-place edit.

🧵 Concurrency without locks

As core counts rise, sharing immutable data beats guarding mutable data with locks. Value objects pass safely between threads and actors.

🗃️ Event sourcing

Immutable events are the source of truth; state is a fold over history. Nothing is overwritten, so audit and replay are built in.

📦 Persistent data structures

Structural sharing gives immutable maps and lists near-mutable performance, so functional updates stay cheap at scale.

🧊 Language support

Records in Java, data classes in Kotlin, frozen dataclasses in Python, and readonly in TypeScript make immutability a first-class, low-ceremony default.

🔎 Caching and CDNs

Immutable, content-addressed values are trivially cacheable, the same property that makes hashed asset URLs safe to keep forever.

Bottom line: immutability turns shared state from a hazard into an asset. Build objects that never change, replace instead of mutate, and whole categories of concurrency and aliasing bugs simply stop happening.
