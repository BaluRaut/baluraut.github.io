Structural Pattern

The Adapter pattern - making incompatible interfaces work together

Your client expects one interface, but the class you have speaks another. The Adapter sits in between and translates: it wraps the existing object and exposes the interface the client wants, converting calls and data on the way through. It is how you plug legacy code, third-party libraries, and mismatched APIs into a codebase without rewriting either side.

01 - What

What is the Adapter pattern?

Adapter is a structural pattern that converts the interface of a class into another interface that a client expects. The client codes against a Target interface; the Adaptee is the existing class with a useful implementation but the wrong signature. The Adapter implements the Target and holds or extends the Adaptee, forwarding each call and reshaping arguments and results so the two sides fit.

🎯 Target

The interface the client already depends on. The client never changes; it only ever sees this contract.

🔌 Adaptee

The existing or third-party class with the capability you want, but the wrong method names, shapes, or units.

🔄 Adapter

Implements Target, delegates to Adaptee, and translates between them. The only class that knows both worlds.

Key mental model: an Adapter changes an interface without changing behavior. It is a translator, not a new feature. If you are adding responsibilities, you want Decorator; if you are simplifying a subsystem, you want Facade.
02 - Why

Why the Adapter exists

Real systems are assembled from parts written by different people at different times. You rarely control both sides of an integration, and rewriting a stable library or a vendor SDK to match your interface is expensive and risky. Adapter lets both sides stay as they are.

🧱 Reuse without rewriting

You keep a proven Adaptee exactly as it is and reuse it through a clean Target, instead of editing code you do not own or trust.

🔗 Decouple from vendors

The client depends on your Target, not on a third-party API. Swap Stripe for Adyen by writing a new adapter; the client never notices.

🧪 Testable seams

Because the client talks to an interface, you can substitute a fake adapter in tests and drive edge cases without hitting the real system.

🕰️ Tame legacy code

Wrap an old module behind a modern interface so new code stays clean while the legacy internals are migrated or retired on their own schedule.

In Plain Terms

Adapter explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is a translator in a conversation. You speak English, the other person speaks Japanese; the translator does not change what either of you means, it just converts the words so you understand each other.

👩‍💻 For a developer

It is a wrapper class that implements your interface and forwards calls to a library with a different signature, mapping its return types and errors into the shapes your code already handles.

🏢 For a professional

Think of a currency exchange desk. Your wallet holds euros, the shop wants yen; the desk converts one to the other at a known rate so the purchase goes through without either side changing.

🔌 Everyday version

A travel power adapter. The wall socket and your laptop plug are both fine; the adapter just reshapes the connection so a device built for one standard works with the other.

03 - How

How it works under the hood

There are two classic forms. An object adapter holds the Adaptee as a field and delegates to it (composition). A class adapter inherits from both the Target and the Adaptee (inheritance). Object adapters are the default in languages without multiple inheritance; class adapters can override Adaptee behavior but couple you to its class.

🧩 Object adapter (composition)

The adapter has-a Adaptee. It can wrap any subclass of the Adaptee and adapt multiple adaptees at once. Flexible and the recommended default.

🧬 Class adapter (inheritance)

The adapter is-a Adaptee and is-a Target. No delegation object, and it can override protected members, but it binds to one concrete Adaptee and needs multiple inheritance.

An object adapter in code

// Target: the interface our application already speaks
interface PaymentGateway {
  charge(amount: Money, customerId: string): Receipt;
}

// Adaptee: a third-party SDK we do not control
class StripeClient {
  createCharge(cents: number, currency: string, customer: string): StripeResult {
    // ... real HTTP call to Stripe ...
    return { id: "ch_123", status: "succeeded" };
  }
}

// Adapter: implements Target, holds the Adaptee (composition), translates both ways
class StripePaymentAdapter implements PaymentGateway {
  constructor(private readonly stripe: StripeClient) {} // has-a Adaptee

  charge(amount: Money, customerId: string): Receipt {
    const cents = amount.toMinorUnits();                 // reshape input
    const r = this.stripe.createCharge(cents, amount.currencyCode(), customerId);
    if (r.status !== "succeeded") {                      // translate errors
      throw new PaymentFailedError(r.id);
    }
    return new Receipt(r.id, amount);                    // reshape output
  }
}

// Client stays blissfully unaware of Stripe
const gateway: PaymentGateway = new StripePaymentAdapter(new StripeClient());
const receipt = gateway.charge(Money.usd(49.99), "cus_42");
# Target: the interface our application already speaks
class PaymentGateway(Protocol):
    def charge(self, amount: Money, customer_id: str) -> Receipt: ...

# Adaptee: a third-party SDK we do not control
class StripeClient:
    def create_charge(self, cents: int, currency: str, customer: str) -> StripeResult:
        # ... real HTTP call to Stripe ...
        return StripeResult(id="ch_123", status="succeeded")

# Adapter: implements Target, holds the Adaptee (composition), translates both ways
class StripePaymentAdapter:
    def __init__(self, stripe: StripeClient) -> None:
        self._stripe = stripe                            # has-a Adaptee

    def charge(self, amount: Money, customer_id: str) -> Receipt:
        cents = amount.to_minor_units()                  # reshape input
        r = self._stripe.create_charge(cents, amount.currency_code(), customer_id)
        if r.status != "succeeded":                      # translate errors
            raise PaymentFailedError(r.id)
        return Receipt(r.id, amount)                      # reshape output

# Client stays blissfully unaware of Stripe
gateway: PaymentGateway = StripePaymentAdapter(StripeClient())
receipt = gateway.charge(Money.usd(49.99), "cus_42")
# Target: the interface our application already speaks (duck-typed)
# every gateway responds to #charge(amount, customer_id) -> Receipt

# Adaptee: a third-party SDK we do not control
class StripeClient
  def create_charge(cents, currency, customer)
    # ... real HTTP call to Stripe ...
    StripeResult.new(id: "ch_123", status: "succeeded")
  end
end

# Adapter: exposes #charge, holds the Adaptee (composition), translates both ways
class StripePaymentAdapter
  def initialize(stripe)
    @stripe = stripe                                     # has-a Adaptee
  end

  def charge(amount, customer_id)
    cents = amount.to_minor_units                        # reshape input
    r = @stripe.create_charge(cents, amount.currency_code, customer_id)
    raise PaymentFailedError, r.id unless r.status == "succeeded" # translate errors
    Receipt.new(r.id, amount)                            # reshape output
  end
end

# Client stays blissfully unaware of Stripe
gateway = StripePaymentAdapter.new(StripeClient.new)
receipt = gateway.charge(Money.usd(49.99), "cus_42")

The client only ever sees PaymentGateway. All the mismatch - dollars to cents, the vendor result shape, the vendor error convention - is absorbed inside the adapter, so swapping providers means writing a new adapter, not touching the client.

05 - Step by Step

The 0 → 100 flow

From an interface mismatch to a clean, swappable integration - the whole journey in order.

00
Spot

Notice the mismatch

You have a class that does what you need but its interface does not match what your client code expects to call.

10
Define

Write the Target interface

Describe the interface your client wants in domain terms - the methods, types, and errors that feel natural to your code.

20
Identify

Pin down the Adaptee

Name the existing or third-party class whose behavior you will reuse, and list exactly how its signature differs from the Target.

30
Choose

Object or class adapter

Prefer composition: hold the Adaptee as a field. Reach for inheritance only if you must override protected Adaptee behavior.

40
Implement

Make the adapter implement Target

Create the adapter class, declare it as implementing the Target, and give it a reference to the Adaptee.

50
Map input

Translate arguments

Inside each method, convert the client's arguments into the shape, units, and order the Adaptee requires.

60
Delegate

Call the Adaptee

Forward the translated call to the Adaptee and capture its result. This is the one place the two worlds meet.

70
Map output

Translate results and errors

Reshape the Adaptee's return value into the Target type and convert its exceptions into your domain errors.

80
Wire

Inject the adapter

Construct the adapter with a real Adaptee and hand it to the client as the Target, ideally through dependency injection.

90
Test

Cover the translation

Unit-test the mapping in both directions and the error paths. Substitute a fake Target when testing the client itself.

100
Swap

Reap the payoff

When a new vendor or version appears, write another adapter behind the same Target. The client code never changes.

Common Pitfalls

Pitfalls & anti-patterns

Adapters are simple, which is exactly why they get abused. Watch for these.

🧠 Logic creep

An adapter should translate, not decide. When business rules, caching, or retries pile up inside it, you have hidden a service behind an adapter and lost the seam.

🪆 Adapter stacking

Adapting an adapter that adapts an adapter usually signals the wrong Target. Redesign the interface instead of chaining translators.

💧 Leaky abstraction

If the Adaptee's exceptions, types, or quirks leak through the Target, the client is still coupled to the vendor and the adapter bought you nothing.

🎭 Confusing it with Facade

Building a whole simplified subsystem entry point and calling it an adapter blurs intent. Adapter matches an existing interface; Facade invents a simpler one.

🧬 Overusing class adapters

Inheriting from the Adaptee binds you to one concrete class and its internals. Composition adapts more targets with far less coupling.

🔕 Swallowing errors

Catching the Adaptee's failures and returning a bland default hides real problems. Translate errors faithfully into meaningful domain exceptions.

Trade-offs

Trade-offs & when to use

Adapter is cheap and low-risk, but it is a translation layer, not a cure for a bad interface. Weigh it honestly.

AspectDetail
ProsReuses existing code as-is, decouples the client from vendors, creates a testable seam, and isolates change to one small class.
ConsAdds an indirection layer, can leak the Adaptee's quirks if the Target is poorly chosen, and tempts logic creep.
Use whenYou need to fit an existing or third-party class to an interface you cannot or do not want to change on either side.
Avoid whenYou control both interfaces and can just align them, or the real need is new behavior (Decorator) or a simpler entry point (Facade).
ComplexityLow. Usually one small class per integration, with the object (composition) form as the safe default over class inheritance.
RelatedBridge separates abstraction from implementation up front; Decorator adds behavior; Facade simplifies a subsystem; Proxy controls access.
Rule of thumb: reach for Adapter when the shapes are right but the signatures are wrong. If you find yourself adding responsibilities rather than translating them, you have outgrown the pattern.
06 - Case Studies

Real-world case studies

Three representative uses showing the Adapter in production-style code.

💳

1 · Payment provider abstraction

Pattern: vendor-agnostic Target with per-provider adapters

A checkout service must support several payment vendors without rewriting order logic for each one.

  • The domain defines one PaymentGateway Target with a clean charge and refund.
  • Each vendor SDK gets its own adapter that maps money, currency, and result types.
  • Adding a new provider is a new adapter class registered in the factory, nothing else.
✅ Outcome: the order flow depends only on the Target, so vendors can be added, swapped, or A/B tested without touching business code.
🕰️

2 · Wrapping a legacy module

Pattern: modern interface over old internals

A decade-old reporting library works fine but exposes an awkward, stateful API the new codebase should not depend on.

  • A modern ReportSource interface describes what new code actually needs.
  • An adapter wraps the legacy library, hiding its setup calls and global state behind clean methods.
  • The legacy code is migrated behind the adapter over time with zero client changes.
✅ Outcome: new features build against a clean interface while the old library is refactored or retired quietly behind the seam.
📚

3 · The java.util adapter (Arrays.asList)

Pattern: adapting arrays to the Collections interface

Java arrays and the Collections framework are different worlds; code written for List cannot take a raw array.

  • Arrays.asList(arr) returns a List view that adapts the array to the Collections API.
  • Iterators, streams, and any List-consuming method now work over the underlying array.
  • The adapter forwards reads to the array without copying the elements.
✅ Outcome: a plain array flows through the entire Collections ecosystem, a standard-library Adapter used by millions of programs.
07 - Relevance

Modern relevance

Adapter is one of the most quietly ubiquitous patterns. As systems get more distributed and more dependent on external services, translation layers only get more common.

🔌 Hexagonal architecture

Ports and adapters is Adapter promoted to an architectural style: the domain defines ports, and adapters connect it to databases, queues, and APIs.

🌐 Anti-corruption layers

In domain-driven design, an adapter is the anti-corruption layer that keeps another system's model from leaking into your bounded context.

🤖 LLM tool and API bridging

Agent frameworks wrap heterogeneous APIs behind a uniform tool interface, an adapter per integration so the model calls one consistent shape.

🧱 Framework binding

ORMs, loggers, and HTTP clients ship adapters so one interface (SLF4J, JPA) fronts many concrete backends chosen at deploy time.

🧪 Test doubles

Because clients depend on the Target, fake adapters make integration seams trivial to stub, driving fast and deterministic tests.

🔁 Incremental migration

Strangler-fig migrations lean on adapters to route between old and new implementations while a system is replaced piece by piece.

Bottom line: Adapter is the joint that lets independently built parts fit together. Any time you integrate code you did not write, or shield your core from a shape you do not control, you are reaching for it, often without naming it.
