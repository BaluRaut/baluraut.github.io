Behavioral Pattern

The Mediator pattern - one hub instead of a tangle of wires

When a set of objects all talk directly to each other, every new participant multiplies the connections and the codebase turns into spaghetti. The Mediator pattern moves that conversation into a single object: colleagues stop referencing one another and instead notify a mediator, which decides who reacts and how. Many-to-many coupling collapses into many-to-one.

01 - What

What is the Mediator pattern?

Mediator is a behavioral design pattern that defines an object which encapsulates how a set of objects interact. Instead of each object holding direct references to its peers and calling them, the objects (called colleagues) know only the mediator. When something happens, a colleague tells the mediator, and the mediator coordinates the rest. This turns a dense web of connections into a hub-and-spoke shape.

🧑‍🤝‍🧑 Colleagues

The individual components (form fields, chat users, UI widgets). They raise events and respond to instructions but never call each other directly.

🎛️ Mediator

The central coordinator. It holds references to the colleagues and contains the interaction logic that used to be scattered across them.

🔌 The interface

A shared contract (often a single notify(sender, event) method) so colleagues signal the mediator without knowing its concrete type.

Key mental model: Mediator does not remove the interactions, it relocates them. The logic that says "if this field changes, enable that button" lives in one place you can read top to bottom, instead of being smeared across every widget.
02 - Why

Why the Mediator pattern exists

Direct object-to-object references feel natural at first, but they scale badly. With n objects talking freely you can have on the order of n squared connections, and every one of them is a place a change can ripple. Mediator trades that quadratic tangle for a linear set of spokes.

🕸️ Kills many-to-many coupling

Each colleague depends only on the mediator, not on every other colleague. Adding or removing a participant touches one class instead of rewiring a dozen.

🧭 Centralizes control flow

The rules of "what talks to what, and when" live in a single readable place, so the interaction logic stops hiding inside unrelated components.

♻️ Makes colleagues reusable

Because a button or field no longer hardcodes its neighbors, you can drop the same component into a different dialog with a different mediator.

🧪 Easier to test and change

You can unit-test a colleague with a mock mediator, and change coordination behavior by swapping the mediator without editing any colleague.

In Plain Terms

Mediator explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Think of a teacher running a group discussion. Students do not shout across each other; they raise a hand and the teacher decides who speaks next. Twenty students need one teacher, not two hundred side conversations.

👩‍💻 For a developer

It is a chat-room server. Clients never open sockets to each other; they send a message to the room and the room broadcasts it. Add a new user and you register one connection, not one per existing user.

🏢 For a professional

Picture an air traffic controller. Pilots do not negotiate runways directly with one another; they talk to the tower, and the tower sequences everyone. One authority replaces a chaos of peer-to-peer radio calls.

📞 Everyday version

An old telephone switchboard operator. Callers do not string their own wires; they ask the operator, who connects the right lines. The complexity of "who reaches whom" sits with the operator.

03 - How

How it works under the hood

A colleague never imports its peers. It holds one field: a reference to the mediator. When state changes, it calls mediator.notify(this, event), and the concrete mediator runs the coordination logic and pushes updates back to whichever colleagues need them.

📨 Colleague to mediator

A colleague reports an event upward: "I changed" or "I was clicked." It passes itself as the sender so the mediator knows the source, and it waits for instructions.

🎚️ Mediator to colleagues

The mediator inspects the event, applies the rules (validation, enabling, broadcasting), and calls methods on the specific colleagues that must react.

A dialog form in Java

// The contract every colleague uses to talk to the hub
interface Mediator {
    void notify(Component sender, String event);
}

// Colleagues know only the mediator, never each other
abstract class Component {
    protected Mediator mediator;
    Component(Mediator mediator) { this.mediator = mediator; }
}

class TextBox extends Component {
    private String text = "";
    TextBox(Mediator m) { super(m); }
    void type(String value) {
        this.text = value;
        mediator.notify(this, "changed");   // report upward
    }
    String getText() { return text; }
}

class Button extends Component {
    private boolean enabled = false;
    Button(Mediator m) { super(m); }
    void setEnabled(boolean e) { this.enabled = e; }
    boolean isEnabled() { return enabled; }
}

// The concrete mediator holds the interaction rules in ONE place
class LoginDialog implements Mediator {
    private final TextBox username = new TextBox(this);
    private final TextBox password = new TextBox(this);
    private final Button submit = new Button(this);

    public void notify(Component sender, String event) {
        if (event.equals("changed")) {
            boolean ready = !username.getText().isBlank()
                         && password.getText().length() >= 8;
            submit.setEnabled(ready);       // coordinate the peers
        }
    }

    public TextBox username() { return username; }
    public TextBox password() { return password; }
    public Button submit()    { return submit; }
}

// Usage
LoginDialog dialog = new LoginDialog();
dialog.username().type("ada");
dialog.password().type("hunter2secret");
// submit is now enabled - the fields never touched each other

Notice that TextBox and Button contain no cross-references. The rule "enable submit when both fields are valid" exists only inside LoginDialog.notify, so changing that rule is a one-file edit.

05 - Step by Step

The 0 → 100 flow

From a tangled set of components to a clean hub-and-spoke design, the whole journey in order.

00
Smell

Spot the tangle

Notice components holding direct references to many peers, with interaction logic duplicated across them. Every new widget forces edits everywhere.

10
Scope

Identify the colleagues

List the objects that currently talk to each other - form fields, buttons, chat users - and the events that pass between them.

20
Contract

Define the mediator interface

Declare a small contract, usually a single notify(sender, event) method, that colleagues will use to signal the hub.

30
Base

Give colleagues a mediator field

Add a base component that stores one reference to the mediator and remove all direct peer references from the colleagues.

40
Report

Replace direct calls with notify

Wherever a colleague used to call a peer, have it call mediator.notify(this, event) instead, passing itself as the sender.

50
Concrete

Build the concrete mediator

Create the mediator that holds references to all colleagues and will contain the coordination logic in one place.

60
Move

Relocate interaction logic

Move the scattered "if this then that" rules into the mediator's notify method, branching on sender and event.

70
Wire

Register the colleagues

In the client or mediator constructor, instantiate the colleagues and connect each one to the mediator so the graph is complete.

80
Run

Trigger and coordinate

A colleague raises an event; the mediator inspects it, applies rules, and calls back into the specific colleagues that must react.

90
Guard

Watch the god object

As logic accumulates, split large mediators by concern or extract sub-mediators so the hub does not swell into an unmaintainable monster.

100
Extend

Add participants cheaply

New colleagues plug into the same interface. You touch the mediator, not every peer, and the interaction stays readable in one file.

Common Pitfalls

Pitfalls & anti-patterns

Mediator is easy to overreach with. These are the failure modes that turn a clean hub back into a mess.

👑 The god object

The biggest risk. All the logic you removed from colleagues piles into the mediator until it knows everything and does everything. Split it by feature or extract sub-mediators before it becomes untouchable.

🔗 Hidden coupling to concretes

If the mediator calls very specific methods on very specific colleague types, colleagues and mediator become tightly bound. Keep the mediator programming to interfaces where you can.

🌀 Overuse on simple cases

Two objects that talk cleanly do not need a hub. Introducing a mediator for a trivial one-to-one relationship just adds indirection and a class to maintain.

🧵 Event soup

A single stringly-typed notify with a giant if-else on event names becomes hard to follow. Use typed events or a dispatch map once the branching grows.

🔁 Notification loops

A colleague notifies the mediator, which updates another colleague, which notifies back, ad infinitum. Guard against re-entrant updates and infinite echo.

🕳️ Lost traceability

Because interactions are indirect, following a single user action through the mediator can be harder than a direct call. Name events well and log the flow.

Trade-offs

Trade-offs & when to use

Mediator is a coupling trade: you centralize complexity to decentralize dependencies. Know what you are buying.

AspectDetail
ProsCuts many-to-many coupling to many-to-one, centralizes interaction logic, makes colleagues reusable and testable, and makes adding participants cheap.
ConsThe mediator can grow into a god object, control flow becomes indirect and harder to trace, and it adds a class plus a layer of indirection.
Use whenA group of objects communicate in complex, tangled ways; you want to reuse components independently; or the interaction rules change often and should live in one place.
Avoid whenThe relationships are simple or one-to-one, the coordination logic is trivial, or centralizing would just create a bottleneck class nobody wants to own.
ComplexityLow to moderate to introduce. The ongoing cost is managing the mediator's growth so it stays cohesive rather than becoming a dumping ground.
RelatedObserver (notification mechanism), Facade (simplified access), Command (encapsulated requests), Colleague and coupling reduction principles.
Rule of thumb: reach for Mediator when the connections between objects are the problem, not the objects themselves. If you can draw the dependency graph and it looks like a mess of crossing lines, a hub will straighten it out. If it is already a clean tree, leave it alone.
06 - Case Studies

Real-world case studies

Three representative places the Mediator pattern earns its keep.

🖥️

1 · GUI dialogs and forms

Pattern: components coordinated by a dialog controller

A settings dialog has checkboxes that enable date pickers, fields that gate a save button, and radio groups that swap panels.

  • Each widget reports changes to a dialog mediator instead of poking its neighbors.
  • The mediator holds all enable, disable, and validation rules in one method.
  • The same widgets get reused in other dialogs with a different mediator.
✅ Outcome: Interaction rules are readable in one class, and adding a new field means editing the mediator, not every existing widget.
💬

2 · Chat rooms and messaging

Pattern: a room brokers all participant messages

Users in a group chat must reach everyone else without opening a connection to each individual peer.

  • Each user sends to the room; the room decides delivery, ordering, and filtering.
  • New users register once with the room, not once per existing user.
  • Features like mute, history, and moderation live in the room, not in clients.
✅ Outcome: Adding a user is O(1) wiring, and cross-cutting features slot into the mediator instead of every client.
✈️

3 · Air traffic and dispatch control

Pattern: a controller sequences independent actors

Aircraft (or ride-share drivers, or warehouse robots) must not coordinate movement peer to peer under contention.

  • Each actor reports position and intent to a central controller.
  • The controller resolves conflicts and issues instructions back to each actor.
  • Actors stay simple and interchangeable; the coordination policy is one place.
✅ Outcome: Safe, auditable sequencing where the hard logic is centralized and testable, and actors carry no knowledge of each other.
07 - Relevance

Modern relevance

The Mediator idea is everywhere in modern software, often under different names, because loose coupling never went out of style.

🧩 Front-end state stores

Redux-style stores and event buses are mediators: components dispatch actions to a central store rather than mutating each other directly.

📮 Message brokers

Kafka, RabbitMQ, and service buses are distributed mediators, decoupling producers from consumers so neither knows the other exists.

🎯 The MediatR library

In the .NET world, in-process mediators route requests to handlers, keeping controllers thin and coordination centralized.

🕹️ Orchestration in microservices

Orchestrators coordinate multi-service workflows so individual services stay unaware of the wider choreography.

🤖 Multi-agent systems

An orchestrator agent that routes tasks to specialist agents is a mediator, keeping the agents decoupled from one another.

⚠️ The eternal caveat

At every scale the same warning applies: centralize interaction, but do not let the hub swell into a god object or a single point of failure.

Bottom line: Mediator is how you tame a mess of interacting objects by giving their conversation a single home. Used with discipline it turns quadratic coupling into linear, readable coordination; used carelessly it just moves the mess into one giant class.
