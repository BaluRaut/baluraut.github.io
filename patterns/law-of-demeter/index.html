OOP Concept

The Law of Demeter - only talk to your immediate collaborators

The Law of Demeter says an object should only call methods on itself, its own fields, its arguments, and objects it creates. It bans reaching through one object to poke at another, so you stop writing train wrecks like order.getCustomer().getAddress().getCity(). Instead you add a method that hides the walk, which is the same instinct behind Tell Don't Ask.

01 - What

What is the Law of Demeter?

The Law of Demeter (LoD), also called the principle of least knowledge, is a design guideline for reducing coupling between objects. A method should only send messages to a small set of nearby objects: itself, its own fields, the arguments it was handed, and objects it creates locally. It should not reach across a chain of getters to command a stranger it was never introduced to.

🤝 Talk to friends

Call methods on your own fields and your arguments. These are the collaborators you were explicitly given, so depending on them is fair.

🚫 Not to strangers

Do not call methods on the objects returned by your friends. The city inside a customer's address is a stranger you were never handed.

🧱 Hide the walk

When you need something deep in the graph, add a method on the near object that fetches it for you, so the navigation lives in one place.

Key mental model: count the dots that cross object boundaries, not the dots on your own object. this.a.b.c() forces you to know that a has a b and that b has a c. The Law of Demeter says: ask a for the end result and let it keep its own shape private.
02 - Why

Why the Law of Demeter exists

Every dot that crosses an object boundary is a fact your code now depends on. A train-wreck chain hardwires the entire shape of the object graph into a caller that should not care, so a small refactor in one class breaks callers three classes away.

🔗 Cuts coupling

A caller that only touches its direct collaborators does not depend on the internal structure of Customer or Address. You can restructure those without hunting down every chain that walked through them.

🛡️ Localizes change

When shipping rules move from Address to a new Region object, only the method that hid the navigation changes. The dozens of call sites that used it stay untouched.

🔒 Protects encapsulation

Exposing getters that return live internal objects invites callers to command your private parts. Hiding navigation keeps each object in charge of its own data and invariants.

🧪 Eases testing

A method with two direct collaborators needs two stubs. A train wreck needs you to build the whole graph - customer, address, region - just to exercise one branch.

In Plain Terms

Law of Demeter explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is the only talk to your friends rule. You can ask your friend a question; you should not reach into your friend's backpack, pull out their phone, and start texting their contacts. Ask your friend, and let them handle their own things.

👩‍💻 For a developer

Count the dots crossing object boundaries. a.b().c().d() means your code knows three layers of someone else's structure. Add one method on a that returns what you actually need, and the chain collapses to a.thing().

🏢 For a professional

Think of a chain of command. You brief your direct report and they brief theirs. You do not walk past three managers to give an order to a junior you have never met; that skips accountability and breaks when the org chart changes.

🐶 Everyday version

To walk the dog you tell the dog to walk; you do not reach in and move each of its legs. You command the nearest responsible thing and trust it to coordinate what is inside.

03 - How

How it works under the hood

The fix is almost always the same shape: a caller was walking a chain of getters, so you push a method down to the object that owns the start of the chain. The caller asks for the end result and never learns the intermediate structure.

🚂 Spot the train wreck

Look for chains of getters that cross objects: order.getCustomer().getAddress().getCity(). Each getter returns a stranger, and the next call talks to it. That is three dependencies smuggled into one line.

🔧 Hide the navigation

Add order.shippingCity() that walks the chain internally, or better, tell the order to do the work with order.ship(courier). The caller now depends only on Order.

Train wreck, then the fix

// TRAIN WRECK: the caller walks the whole object graph.
// It must know Order has a Customer, Customer has an Address,
// and Address has a city. Three couplings in one line.
function labelForShipping(order: Order): string {
  const city = order.getCustomer().getAddress().getCity();
  const zip  = order.getCustomer().getAddress().getPostcode();
  return `${city} ${zip}`;
}

// FIX: push a method down to Order. The caller only knows Order now.
class Address {
  constructor(private readonly city: string,
              private readonly postcode: string) {}
  shippingLabel(): string {
    return `${this.city} ${this.postcode}`;
  }
}

class Customer {
  constructor(private readonly address: Address) {}
  shippingLabel(): string {
    return this.address.shippingLabel();   // talks to its own field
  }
}

class Order {
  constructor(private readonly customer: Customer) {}
  shippingLabel(): string {
    return this.customer.shippingLabel();  // talks to its own field
  }
}

// One dot across the boundary. Order's internals stay private.
function labelForShippingFixed(order: Order): string {
  return order.shippingLabel();
}

Each object only delegates to a field it already owns, so no method ever calls through a returned stranger. The chain of knowledge is broken into a chain of small, local delegations, and the caller depends on exactly one type.

Better still: Tell, do not Ask

Hiding a getter chain behind shippingLabel() removes the coupling, but you are still pulling data out to act on it elsewhere. The stronger move is to tell the object to do the whole job, so behavior lives with the data it needs.

// ASKING: pull data across boundaries, then decide outside.
const city = order.getCustomer().getAddress().getCity();
const fee  = rateTable.lookup(city);
courier.dispatch(order, fee);

// TELLING: hand the order a courier and let it coordinate.
class Order {
  constructor(private readonly customer: Customer,
              private readonly items: LineItem[]) {}

  ship(courier: Courier, rates: RateTable): Shipment {
    const fee = this.customer.shippingFee(rates); // Customer knows its address
    return courier.dispatch(this, fee);           // courier is an argument
  }
}

// Caller: one message, no navigation, no leaked internals.
order.ship(courier, rates);
# ASKING: pull data across boundaries, then decide outside.
city = order.get_customer().get_address().get_city()
fee = rate_table.lookup(city)
courier.dispatch(order, fee)

# TELLING: hand the order a courier and let it coordinate.
class Order:
    def __init__(self, customer, items):
        self._customer = customer
        self._items = items

    def ship(self, courier, rates):
        fee = self._customer.shipping_fee(rates)  # Customer knows its address
        return courier.dispatch(self, fee)        # courier is an argument


# Caller: one message, no navigation, no leaked internals.

    @customer = customer
    @items = items
  end

    fee = @customer.shipping_fee(rates)  # Customer knows its address
    courier.dispatch(self, fee)          # courier is an argument
  end
end

# Caller: one message, no navigation, no leaked internals.
order.ship(courier, rates)

The Law of Demeter and Tell Don't Ask push the same way: keep behavior next to the data it touches. Demeter forbids the walk; Tell Don't Ask removes the reason you wanted to walk in the first place.

05 - Step by Step

The 0 → 100 flow

From spotting a getter chain to a caller that depends on exactly one collaborator - the whole refactor in order.

00
Notice

See the getter chain

You read order.getCustomer().getAddress().getCity() in a service and pause. Multiple getters strung together are the classic Demeter smell.

10
Count

Count the boundary crossings

Each getter that returns a different object is one crossing. Three crossings means the caller silently depends on three classes it should not know.

20
Classify

Identify friends vs strangers

The order is a friend (it was passed in). The customer and address are strangers reached through return values. Only the friend is fair to call.

30
Name

Name what you actually want

You do not want the city; you want a shipping label, a fee, or a dispatched shipment. Name the real intent, not the field you were digging for.

40
Push down

Add a method on the near object

Give Order a shippingLabel() that returns the finished value. The navigation now lives inside the object that owns the chain.

50
Delegate

Delegate one hop at a time

Order asks its customer; Customer asks its address. Each object touches only a field it owns, so no stranger is ever called.

60
Replace

Swap the chain at the call site

Replace the train wreck with order.shippingLabel(). The caller's dependency list shrinks from three classes to one.

70
Strengthen

Prefer Tell over Ask

If the caller only pulled the value to act on it, move the action inside too: order.ship(courier). Now no data leaks out at all.

80
Guard

Watch for fake delegation

Do not add a getter for every internal field. A wall of pass-through getters recreates the coupling with extra steps. Expose intent, not structure.

90
Verify

Check the seams move freely

Change Address into a Region plus a Postcode. Only the delegating methods should change; every caller should keep compiling.

100
Done

Low-knowledge collaborators

Each object knows only its direct neighbors. Structure is private, behavior sits with its data, and refactors stay local.

Common Pitfalls

Pitfalls & anti-patterns

The Law of Demeter is easy to state and easy to over-apply. These are the traps on both sides.

🚂 Train-wreck chains

The classic smell: invoice.getAccount().getOwner().getEmail().send(). Every dot binds the caller to another layer of structure, so any of four classes can break it.

🕳️ Getter explosion

Obeying the letter of the law by adding getCustomerAddressCity(), getCustomerAddressZip(), and so on just relocates the coupling and bloats the near object with someone else's data.

📤 Leaking internals

Returning a live Address from getAddress() lets callers mutate an order's guts. The chain is a symptom; the exposed internal object is the disease.

🧩 Middle-man objects

Over-applying Demeter can create classes that do nothing but forward calls. If an object only delegates and adds no behavior, it may not deserve to exist.

🔍 Miscounting fluent APIs

query.where(...).order(...).limit(10) chains on the same builder, returning this. That is not a Demeter violation; only chains across different objects count.

📦 Data structures caught by the rule

Walking a plain DTO or a parsed JSON tree is fine; there is no behavior or invariant to protect. Applying LoD to dumb data bags adds ceremony for no gain.

Signals & Metrics

Signals & how to measure

You cannot put a single number on coupling, but these signals tell you whether Demeter is being honored across a codebase.

SignalWhat it tells you
Getter chains per methodChains of two or more cross-object getters flag likely violations; a linter or grep for get followed by ().get surfaces them quickly.
Types imported per fileA caller that must import Order, Customer, and Address to do one job is coupled to the whole graph, not just its collaborator.
Blast radius of a renameRename a deep field and count how many files break. High counts mean structure has leaked through chains into distant callers.
Objects built in a testIf exercising one method needs a full graph of stubs, the method is reaching through objects it should not touch.
Ratio of tell to askMany methods that pull data out and decide elsewhere signal Ask-heavy code; behavior belongs closer to the data.
Pass-through getter countA spike in getters that only forward to an inner object hints you traded a chain for a pile of thin accessors.
Rule of thumb: if a single line forces a reader to learn the internal shape of two or more other classes, it is a Demeter violation worth hiding, even if it technically compiles and runs.
06 - Case Studies

Real-world case studies

Three representative situations where honoring the Law of Demeter changed how a system held up to change.

🛒

1 · Checkout service in an e-commerce platform

Pattern: hide the order-to-address navigation

A checkout service computed shipping by walking order.getCustomer().getAddress().getCountry() in dozens of places to pick a tax and rate table.

  • Splitting billing and shipping addresses meant the customer no longer had a single address, and every chain broke at once.
  • The fix added order.shippingDestination() and order.shippingFee(rates), moving the walk into the order.
  • The country now comes from a Destination value object the order assembles internally, invisible to callers.
✅ Outcome: the address split touched three methods on Order instead of forty call sites, and checkout code depends only on Order.
💳

2 · Payments module in a subscriptions product

Pattern: tell the account to charge, do not ask for its card

A billing job read subscription.getAccount().getDefaultCard().getToken() and passed the token to a gateway, spreading card knowledge everywhere.

  • Reaching in for the raw token leaked PCI-sensitive detail into unrelated billing code.
  • The team replaced the chain with account.charge(amount, gateway), so the account picks its own payment method.
  • Retry logic and card fallback moved inside the account, where the data to make those decisions already lived.
✅ Outcome: card details stopped traveling through the codebase, and adding a backup-card fallback was a one-class change.
📦

3 · Warehouse fulfillment in a logistics system

Pattern: fix a train wreck through inventory and bins

A picker screen called shipment.getWarehouse().getZone().getBin().getQuantity() to show stock, coupling the UI to the storage hierarchy.

  • When zones were replaced by dynamic pick paths, the entire picking UI stopped compiling.
  • The refactor exposed shipment.availableStock(sku), letting the shipment resolve location internally.
  • The storage layout became a private detail the fulfillment domain could restructure at will.
✅ Outcome: swapping zones for pick paths was invisible to the UI, and stock lookups went through one stable method.
07 - Relevance

Modern relevance

The Law of Demeter predates most of today's stacks, yet the least-knowledge idea shows up everywhere modern systems try to stay loosely coupled.

🧭 Domain-driven design

Aggregates enforce Demeter at scale: outside code talks to the aggregate root, never to entities buried inside it. The root hides its own navigation.

🔌 Microservice boundaries

The same instinct at the network level: a service exposes an intent-shaped endpoint rather than letting callers traverse its internal data model over the wire.

🧱 Hexagonal architecture

Ports expose behavior, not internal objects, so adapters stay ignorant of the domain's shape. That is Demeter applied to whole layers.

⚛️ Component props in UIs

Passing a whole model deep into a component tree recreates train wrecks in the view. Passing the specific values or callbacks a component needs keeps it decoupled.

🧪 Test doubles & mocks

"Don't mock what you don't own," and the pain of deep stub chains, both push designs toward direct collaborators and thin surfaces.

🤖 GraphQL & API design

Even where clients traverse a graph, well-designed resolvers expose intent-level fields so consumers do not hardwire the storage shape.

Bottom line: the Law of Demeter is not about counting dots for its own sake. It is a reminder that behavior should live with its data, and every boundary you reach across is a coupling you will pay for when the design changes.
