Behavioral Pattern

The Visitor pattern - operations that travel to your objects

You have a stable tree of objects (an AST, a document, a shape hierarchy) and a growing list of things you want to do with it. Visitor lets you add new operations without touching the element classes. It moves each operation into its own visitor object and uses double dispatch so the right code runs for the right element type.

01 - What

What is the Visitor pattern?

Visitor represents an operation to be performed on the elements of an object structure. It lets you define a new operation without changing the classes of the elements on which it operates. Instead of scattering a method across every node type, you gather that operation into one visitor class and let each element hand itself back to the visitor through an accept call.

🧩 Element

Each node type in the structure exposes one method, accept(visitor), whose only job is to call the matching visit method back on the visitor.

🧳 Visitor

An interface with one visit method per concrete element type. Each concrete visitor is one whole operation: a printer, a type checker, an evaluator.

🌳 Object structure

The collection or tree of elements that can enumerate its nodes and pass a visitor to each one, often via a recursive traversal.

Key mental model: Visitor turns a method that would live on every node into a standalone object. The element still picks which visit to run (that is its type talking), but the behavior lives entirely in the visitor. Add an operation by writing a new visitor, not by editing every class.
02 - Why

Why the Visitor pattern exists

When a class hierarchy is stable but the operations over it keep multiplying, putting every operation as a method on every node makes the classes bloat and forces edits across the whole hierarchy for each new feature. Visitor flips the axis: it groups one operation in one place.

➕ Open to new operations

Add a serializer, a validator, or an optimizer by writing one new visitor class. The element hierarchy is never touched, so a stable set of node types stays closed to edits.

📚 Cohesion by operation

All the logic for pretty-printing an AST lives in one PrintVisitor, not smeared across Add, Sub, Number, and Call. Related code sits together, which is easier to read and test.

🎯 Double dispatch, not type checks

The right code runs based on both the element type and the visitor type, without long instanceof or switch (node.kind) ladders that the compiler cannot exhaustively check.

🧮 Accumulate across a structure

A visitor carries state as it walks the tree, so it can total a bill, collect free variables, or build a symbol table in a single traversal.

In Plain Terms

Visitor explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Think of a substitute teacher who visits every classroom. Each room (element) opens its door and says "come in" (accept); the teacher does the same lesson tailored per grade. Send a new teacher for a new lesson; the classrooms never change.

👩‍💻 For a developer

It is an externalized method with two-step dispatch. The node calls visitor.visitAdd(this), so both the node type and the operation type pick the code. Adding ToJsonVisitor needs zero changes to the node classes.

🏢 For a professional

Like a compliance auditor touring departments. Each department presents its records (accept); the auditor applies one checklist everywhere. Next quarter a different auditor runs a different checklist over the exact same departments.

🏨 Everyday version

A hotel housekeeping cart that stops at each room type. A standard room and a suite each let the cart in and get the service that suits them. Swap the cart (cleaning to restocking) without rebuilding the rooms.

03 - How

How it works under the hood

The trick is double dispatch. A single virtual call in most languages dispatches on one type (the receiver). Visitor chains two virtual calls so the running method depends on both the element type and the visitor type.

1️⃣ First dispatch (element)

You call element.accept(visitor). Virtual dispatch picks the concrete element's accept, so the runtime type of the node is now known inside that method.

2️⃣ Second dispatch (visitor)

Inside accept, the element calls visitor.visitAdd(this). Overload resolution and virtual dispatch now pick the code for that exact element and that exact visitor.

A realistic AST visitor in Java

// Element hierarchy: a tiny expression AST
interface Expr {
    <R> R accept(Visitor<R> v);
}

record Number(double value) implements Expr {
    public <R> R accept(Visitor<R> v) { return v.visitNumber(this); }
}

record Add(Expr left, Expr right) implements Expr {
    public <R> R accept(Visitor<R> v) { return v.visitAdd(this); }
}

record Mul(Expr left, Expr right) implements Expr {
    public <R> R accept(Visitor<R> v) { return v.visitMul(this); }
}

// Visitor interface: one method per concrete element
interface Visitor<R> {
    R visitNumber(Number n);
    R visitAdd(Add a);
    R visitMul(Mul m);
}

// One whole operation = one visitor. Evaluate the tree to a double.
class EvalVisitor implements Visitor<Double> {
    public Double visitNumber(Number n) { return n.value(); }
    public Double visitAdd(Add a) {
        return a.left().accept(this) + a.right().accept(this);
    }
    public Double visitMul(Mul m) {
        return m.left().accept(this) * m.right().accept(this);
    }
}

// A second operation added with ZERO changes to Expr classes.
class PrintVisitor implements Visitor<String> {
    public String visitNumber(Number n) { return String.valueOf(n.value()); }
    public String visitAdd(Add a) {
        return "(" + a.left().accept(this) + " + " + a.right().accept(this) + ")";
    }
    public String visitMul(Mul m) {
        return "(" + m.left().accept(this) + " * " + m.right().accept(this) + ")";
    }
}

// Usage: (1 + 2) * 3
Expr ast = new Mul(new Add(new Number(1), new Number(2)), new Number(3));
double result = ast.accept(new EvalVisitor());   // 9.0
String pretty = ast.accept(new PrintVisitor());  // ((1.0 + 2.0) * 3.0)

Notice that EvalVisitor and PrintVisitor are entirely separate operations, yet neither required editing Number, Add, or Mul. The recursion lives in the visitor via child.accept(this), so each visitor controls its own traversal and return type.

05 - Step by Step

The 0 → 100 flow

From a bare element hierarchy to a running visitor operation, then to a second operation added for free.

00
Model

Identify the object structure

Pin down the node types you will operate on, such as AST expressions or document nodes. Visitor pays off when this set is stable and the operations grow.

10
Element API

Add accept to the element interface

Declare accept(visitor) on the base element type so every concrete node promises to hand itself to a visitor.

20
Visitor API

Declare the Visitor interface

Write one visit method per concrete element: visitNumber, visitAdd, and so on. This interface is the contract every operation implements.

30
Wire up

Implement accept on each node

In every concrete element, accept calls the matching method: return v.visitAdd(this). This one line per class enables double dispatch.

40
Operation

Write the first concrete visitor

Build, for example, EvalVisitor that implements every visit method. All the evaluation logic lives here, in one cohesive class.

50
Traverse

Recurse into children

Inside composite visits, call child.accept(this) to descend. The visitor drives the walk and decides order, depth, and short-circuiting.

60
State

Carry accumulating state

Let the visitor hold fields (a total, a symbol table, a StringBuilder) so a single pass gathers results across the whole structure.

70
Run

Kick off from the root

Call root.accept(new EvalVisitor()). The first dispatch resolves the node, the second resolves the operation, and the traversal unrolls.

80
Extend

Add a new operation for free

Need pretty-printing or JSON export? Write PrintVisitor. The element classes stay untouched, which is the whole point of the pattern.

90
Compose

Combine or chain visitors

Run a validating visitor, then an optimizing visitor, then a codegen visitor over the same tree. Each is independent and testable in isolation.

100
Maintain

Manage element changes deliberately

Adding a node type means updating every visitor. Accept that cost knowingly; it is the trade you made to keep operations open and cohesive.

Common Pitfalls

Pitfalls & anti-patterns

Visitor is powerful but easy to misapply. These are the usual traps.

🔁 Unstable element set

If node types change often, every new type forces edits to every visitor. Visitor is the wrong choice when the hierarchy is volatile and operations are few.

🕳️ Breaking encapsulation

Visitors need access to element internals, so nodes end up exposing getters or public fields. This can leak implementation details the class would rather hide.

🧨 Default catch-all visits

A base visitor with a no-op default silently swallows new element types instead of failing loudly. You lose the compiler's help in finding unhandled cases.

🌀 Hidden traversal order

Mixing traversal logic into each visit method makes order implicit and inconsistent between visitors. Consider a separate traversal strategy or a base walker.

🧱 Overkill for simple cases

Two node types and one operation do not need accept, a visitor interface, and double dispatch. A plain method or a switch is clearer and shorter.

🔗 Cyclic dependencies

Elements import the visitor interface and visitors import every element, creating a tight two-way coupling that resists splitting the code into modules.

Trade-offs

Trade-offs & when to use

Visitor makes one axis of change cheap and the other expensive. Know which axis your system actually moves along.

AspectDetail
ProsNew operations without editing elements; related logic gathered per operation; double dispatch replaces type-switch ladders; a visitor can accumulate results across a whole traversal.
ConsAdding an element type touches every visitor; often breaks element encapsulation; a lot of boilerplate; two-way coupling between elements and visitors.
Use whenThe element hierarchy is stable but operations keep growing; you have an AST, parse tree, document model, or shape hierarchy walked in many ways.
Avoid whenNode types change often, the operations are few, or a language feature (pattern matching, sealed types) already gives you exhaustive, cheap dispatch.
ComplexityModerate. The mechanism is small but indirection and the accept/visit ceremony add cognitive load and files.
RelatedComposite (the tree Visitor walks), Iterator (an alternative traversal), Interpreter (Visitor often evaluates its grammar), Strategy (each visitor is a swappable operation).
Rule of thumb: reach for Visitor when you expect many new operations over a fixed set of types. If you instead expect many new types over a fixed set of operations, keep the methods on the classes; Visitor would fight you on every new node.
06 - Case Studies

Real-world case studies

Three places Visitor earns its keep in production systems.

🛠️

1 · Compiler and interpreter ASTs

Pattern: many passes over one node set

A language front end parses source into an AST, then runs pass after pass over the same nodes.

  • Separate visitors implement type checking, constant folding, and bytecode generation.
  • The node classes (literals, calls, loops) stay closed while new passes are added freely.
  • Each visitor carries its own state, such as a scope stack or an emitted-instruction buffer.
✅ Outcome: New analyses ship as new visitor classes without destabilizing the grammar or the node hierarchy, which is exactly the change pattern a compiler needs.
📄

2 · Document trees and rendering

Pattern: one model, many output formats

A rich-text or Markdown editor holds documents as a tree of headings, paragraphs, lists, and images.

  • An HtmlVisitor renders to HTML, a LatexVisitor to LaTeX, a WordCountVisitor to a stat.
  • New export formats are new visitors; the node types never learn about output.
  • Visitors reuse a shared traversal so structure and formatting stay decoupled.
✅ Outcome: Adding a PDF or plain-text exporter is one self-contained class, so the document model remains a single source of truth across every format.
🧾

3 · Static analysis and linters

Pattern: rules over a syntax tree

A linter walks a code AST to flag issues, and rule sets grow constantly.

  • Each rule is a visitor that inspects specific node types and reports findings.
  • Rules run independently over the same parsed tree, so failures are isolated.
  • The parser and node model are shared and rarely change once the language is fixed.
✅ Outcome: Teams add and toggle lint rules without ever editing the parser, keeping a large rule catalog maintainable and easy to test rule by rule.
07 - Relevance

Modern relevance

Language features have reshaped when Visitor is the right tool, but the underlying problem it solves is very much alive.

🧵 Pattern matching rivals it

Sealed types plus exhaustive switch in Java, Kotlin, and TypeScript-style unions give cheap, compiler-checked dispatch, often replacing hand-written visitors for simple cases.

🌲 Still king for big ASTs

Compilers, transpilers, and query engines keep using Visitor because passes multiply while the grammar stays fixed, the exact shape Visitor was built for.

⚙️ Generated visitors

Tools like ANTLR emit visitor and listener base classes from a grammar, so you subclass rather than write the boilerplate by hand.

🔀 Listener variants

Event-style listeners (enter/exit callbacks) separate traversal from action, a common evolution of Visitor in parsing frameworks and tree walkers.

🧬 Functional fold

In FP, a fold or catamorphism over an algebraic data type expresses the same idea; Visitor is the object-oriented spelling of that recursion scheme.

🧰 Expression-tree tooling

ORMs and rule engines walk expression trees with visitors to translate queries, rewrite predicates, and optimize plans at runtime.

Bottom line: Visitor remains the go-to when operations grow over a stable type hierarchy. Where languages offer exhaustive pattern matching, prefer it for small cases; where you have a real AST or document tree traversed many ways, Visitor still pays for its ceremony.
