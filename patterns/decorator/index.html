Structural Pattern

The Decorator pattern - add behavior by wrapping, not subclassing

Decorator lets you attach new responsibilities to an object at runtime by wrapping it in another object that shares its interface. Because the wrapper implements the same type it wraps, you can stack decorators in any order and each one adds one slice of behavior. It is how java.io turns a raw stream into a buffered, compressed, data-typed stream without a single new subclass per combination.

01 - What

What is the Decorator pattern?

Decorator is a structural pattern that lets you attach responsibilities to an individual object dynamically. You wrap the target object inside a decorator object that implements the same interface, forwards calls to the wrapped object, and adds behavior before, after, or around each forwarded call. Because wrapper and wrapped share a type, client code cannot tell the difference and decorators can be layered.

🧩 Same interface

The decorator implements the exact interface of the object it wraps, so it is a drop-in substitute anywhere the base type is expected.

🎁 Wraps a component

It holds a reference to a wrapped component and delegates to it, adding its own behavior around the delegated call.

🥞 Stacks in layers

A decorator can wrap another decorator, so responsibilities compose like layers of an onion, each added independently.

The four roles

RoleWhat it doesJava I/O example

Key mental model: Decorator is "wrapping instead of subclassing." Inheritance fixes behavior at compile time for a whole class; a decorator adds behavior to one object at runtime, and you can peel layers on and off by choosing which wrappers to apply.
02 - Why

Why Decorator exists

The problem it kills is subclass explosion. If you try to model every combination of optional features with inheritance, the number of classes grows combinatorially. Decorator makes each feature one small wrapper you mix freely at runtime.

💥 Kills subclass explosion

Three features via inheritance means a class for each combination: Buffered, Compressed, BufferedCompressed, and so on. With decorators you write three wrappers and compose them, so N features cost N classes, not 2 to the N.

🔓 Honors Open/Closed

You add capabilities without touching the base class or existing decorators. New behavior arrives as a new wrapper, so tested code stays closed to modification but open to extension.

🎚️ Per-object, at runtime

Two instances of the same class can have different decorators. You decide the stack based on configuration, user input, or request context, not at compile time.

🎯 Single responsibility

Each decorator does one thing: buffer, compress, encrypt, log. Small focused classes are easier to test and reason about than one class juggling every optional concern.

In Plain Terms

Decorator explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Think of layers of clothing. A person is still a person whether they add a sweater, then a coat, then a scarf. Each layer adds warmth without changing what a person is, and you add or remove layers as needed.

👩‍💻 For a developer

It is new BufferedInputStream(new FileInputStream(f)). Each constructor takes the same interface it returns, so wrapping is just nesting, and every layer still answers to InputStream.

🏢 For a professional

Like a document going through approval stamps. The document is unchanged, but each desk wraps it with a stamp, a cover note, or a redaction. Downstream still handles a "document," now with extra handling applied.

☕ Everyday version

03 - How

How it works under the hood

A decorator holds a reference to a component of the same interface, delegates the core call to it, and adds behavior around that delegation. Stacking works because a decorator's wrapped field can itself be another decorator.

🔁 Delegate then add

Each method typically calls wrapped.method() and adds work before or after. The wrapped reference is the same type, so the call chain is uniform all the way down.

🥞 Order matters

Wrapping compress-then-buffer behaves differently from buffer-then-compress. The outermost decorator runs its "before" work first and its "after" work last, like a stack unwinding.

A realistic example in Java

// Component: the shared interface
interface DataSource {
    void writeData(String data);
    String readData();
}

// Concrete Component: does the real work
class FileDataSource implements DataSource {
    private final String path;
    FileDataSource(String path) { this.path = path; }
    public void writeData(String data) { /* write raw bytes to file */ }
    public String readData()          { /* read raw bytes from file */ return "..."; }
}

// Base Decorator: implements the interface, forwards to the wrappee
abstract class DataSourceDecorator implements DataSource {
    protected final DataSource wrappee;
    DataSourceDecorator(DataSource source) { this.wrappee = source; }
    public void writeData(String data) { wrappee.writeData(data); }
    public String readData()           { return wrappee.readData(); }
}

// Concrete Decorator: adds behavior around the forwarded call
class CompressionDecorator extends DataSourceDecorator {
    CompressionDecorator(DataSource source) { super(source); }
    public void writeData(String data) { wrappee.writeData(compress(data)); }
    public String readData()           { return decompress(wrappee.readData()); }
    private String compress(String s)   { /* deflate */ return s; }
    private String decompress(String s) { /* inflate */ return s; }
}

class EncryptionDecorator extends DataSourceDecorator {
    EncryptionDecorator(DataSource source) { super(source); }
    public void writeData(String data) { wrappee.writeData(encrypt(data)); }
    public String readData()           { return decrypt(wrappee.readData()); }
    private String encrypt(String s) { /* cipher */ return s; }
    private String decrypt(String s) { /* decipher */ return s; }
}

// Client: composes the stack at runtime, then uses the base interface
DataSource source = new EncryptionDecorator(
                        new CompressionDecorator(
                            new FileDataSource("out.dat")));
source.writeData("salary report");   // compresses, then encrypts, then writes
String plain = source.readData();     // reads, decrypts, then decompresses

The client only ever sees DataSource. Writing runs the stack outer to inner (encrypt wraps compress wraps file); reading unwinds it inner to outer. Add a new concern, say a LoggingDecorator, without editing any existing class.

05 - Step by Step

The 0 to 100 flow

From defining the interface to running a stacked chain in production - the whole journey in order.

00
Interface

Define the Component

Declare the shared interface that both the real object and every decorator will implement, for example DataSource with read and write.

10
Base

Build the Concrete Component

Write the class that does the real work, such as FileDataSource. This is what sits at the center and gets wrapped.

20
Wrapper

Create the Base Decorator

Make an abstract decorator that implements the interface, holds a wrappee field of the same type, and forwards every call to it unchanged.

30
Behavior

Add a Concrete Decorator

Subclass the base decorator and override a method to add work before or after delegating, like compressing on write and decompressing on read.

40
Behavior

Add more decorators

Write independent wrappers for other concerns: encryption, logging, buffering. Each stays small and knows nothing about the others.

50
Compose

Wrap at runtime

The client nests constructors to build a stack, for example encryption around compression around the file source, choosing the order deliberately.

60
Call

Invoke through the interface

The client calls the outermost object using only the DataSource type, unaware of how many layers sit underneath.

70
Descend

Delegate down the stack

Each decorator applies its "before" work and forwards to its wrappee, so the call travels outer to inner until it reaches the concrete component.

80
Ascend

Unwind the results

The concrete component returns, and each decorator applies its "after" work on the way back up, in reverse order of wrapping.

90
Extend

Add features without edits

A new requirement becomes a new decorator inserted into the stack. Existing classes are never modified, honoring Open/Closed.

100
Ship

Configure stacks per context

Different requests or configs assemble different chains from the same building blocks, so behavior varies per object without new classes.

Common Pitfalls

Pitfalls & anti-patterns

Decorator is powerful but easy to overuse. These are the usual traps.

🧅 Too many tiny layers

A stack ten wrappers deep is hard to read and debug. A stack trace becomes a wall of forwarding calls. Reach for Decorator when combinations really vary, not for every option.

🔀 Order-sensitivity ignored

Compress-then-encrypt and encrypt-then-compress give different results, and one may not even work. Treat the order of wrapping as part of the contract, not an accident.

🪪 Leaking the concrete type

If clients downcast to reach a decorator's extra method, substitutability breaks. Decorators should add behavior through the shared interface, not a wider one clients depend on.

🧬 Fat base interface

A component interface with many methods forces every decorator to forward all of them. Keep the interface small so wrappers stay thin, or delegation boilerplate takes over.

🆔 Identity and equals traps

A wrapped object is not == to its wrapper, and equals or hashing may behave unexpectedly across layers. Do not rely on object identity through a decorator chain.

🎭 Using it where Strategy fits

If you are swapping one algorithm rather than layering several add-ons, Strategy is simpler. Decorator shines only when responsibilities genuinely stack.

Trade-offs

Trade-offs & when to use

Decorator trades a flat class hierarchy for runtime flexibility and a bit of indirection. Here is the balance sheet.

AspectDetail
ProsAdds behavior at runtime per object, composes freely, avoids subclass explosion, keeps each concern in a small class, and honors Open/Closed.
ConsMany small objects and deep stacks hurt readability and debugging; order sensitivity is a hidden contract; forwarding boilerplate grows with the interface.
Use whenResponsibilities are optional and combinable, you need to add or remove them per object at runtime, or inheritance would produce a combinatorial class blowup.
Avoid whenYou are swapping a single algorithm (use Strategy), controlling access to one object (use Proxy), or the set of features is fixed and small (plain inheritance is fine).
ComplexityLow per decorator, but overall cognitive load rises with stack depth. Requires a shared interface and disciplined delegation.
RelatedProxy (same interface, controls access not behavior), Composite (tree of same-interface objects), Adapter (changes interface), Strategy (swaps algorithm).
Rule of thumb: if you catch yourself creating classes named for combinations of features (BufferedCompressedEncrypted...), stop and reach for Decorator. If you only ever need one option at a time, you probably do not need it at all.
06 - Case Studies

Real-world case studies

Three places the Decorator pattern shows up in code you likely already use.

📄

1 · Java I/O streams

Pattern: the canonical Decorator hierarchy

The java.io package is the textbook example. InputStream is the component, FileInputStream the concrete component, FilterInputStream the base decorator, and the rest are concrete decorators.

  • new BufferedInputStream(new GZIPInputStream(new FileInputStream(f))) layers buffering over decompression over raw file reads.
  • Each wrapper is still an InputStream, so any code reading a stream works with any combination.
  • Without it, the JDK would need a class per feature combination, which is exactly the explosion Decorator prevents.
✅ Outcome: A handful of stream classes compose into hundreds of useful pipelines, all through one InputStream interface.
🌐

2 · HTTP middleware & filters

Pattern: wrapping request handlers

Web frameworks wrap a request handler in layers: logging, authentication, compression, caching. Each layer shares the handler interface and forwards to the next.

  • An auth decorator checks a token, then delegates to the wrapped handler only if valid.
  • A gzip decorator delegates first, then compresses the response the inner handler produced.
  • Teams reorder or add middleware without touching the core handler, per route or per app.
✅ Outcome: Cross-cutting concerns become composable, reorderable wrappers instead of tangled code inside every handler.
☕

3 · UI components & notifiers

Pattern: layering optional visual or channel add-ons

A UI toolkit wraps a widget with borders, scrollbars, and shadows; a notifier wraps a base sender with Slack, SMS, and email channels, all through one interface.

  • A ScrollDecorator wraps any component and paints scrollbars around whatever it renders.
  • A SlackDecorator sends to Slack, then delegates so the wrapped notifier also fires.
  • Users pick which decorations or channels to stack at runtime from configuration.
✅ Outcome: One base object plus a few decorators covers every combination users ask for, chosen dynamically.
07 - Relevance

Modern relevance

Decorator is far from a museum piece. It underpins middleware, aspect-oriented concerns, and language features across modern stacks.

🧵 Middleware pipelines

Express, ASP.NET, gRPC interceptors, and servlet filters are all Decorator: each layer wraps the next handler and adds one concern around the call.

🎀 Language decorators

Python and TypeScript decorators and Java annotations with proxies apply the same idea, wrapping a function or class with added behavior at definition time.

🧷 Functional wrapping

Higher-order functions that take a function and return a wrapped one, like memoize or retry, are Decorator expressed without classes.

🔭 Observability

Tracing and metrics libraries wrap clients and repositories in same-interface decorators so instrumentation stays out of business logic.

🛡️ Resilience layers

Retry, circuit breaker, rate limit, and cache decorators stack around a service call, each toggled independently per dependency.

🧪 Test doubles

Spies and recording wrappers decorate a real object to observe calls while still delegating, keeping tests close to production behavior.

Bottom line: Decorator is how you add optional, stackable behavior to one object at runtime without rewriting it or exploding your class hierarchy. Whenever concerns need to combine freely, wrapping beats subclassing.
