Behavioral Pattern

The State pattern - behavior that changes with the object

Some objects behave completely differently depending on what mode they are in: a draft order is not a shipped order, a paused player is not a playing one. The State pattern lets an object alter its behavior when its internal state changes by delegating to interchangeable state objects. Instead of one class riddled with if and switch blocks, each state becomes its own class that knows how to act and when to hand control to the next state.

01 - What

What is the State pattern?

State is a behavioral design pattern that lets an object change its behavior when its internal state changes, so that it appears to change its class. The object, called the context, holds a reference to a state object and delegates all state-dependent work to it. Each concrete state is a separate class implementing a shared interface, and a state may switch the context to a different state, driving the transitions of a finite state machine.

📦 Context

The object whose behavior varies. It keeps a current-state reference and forwards requests to it, never branching on the state itself.

🔌 State interface

A common contract listing the state-dependent operations. Every concrete state implements it, so the context can treat them uniformly.

🎭 Concrete states

One class per mode. Each encapsulates the behavior for that mode and decides which state comes next after an event.

The core roles

Key mental model: the State pattern turns a finite state machine into objects. The states are the nodes, the methods on each state are the labeled edges, and the context is just the token that sits on whichever node is current.
02 - Why

Why the State pattern exists

Objects that pass through a lifecycle tend to grow a tangle of flags and conditionals. Every method sprouts a switch (status), and adding one new state means editing every method. The State pattern replaces that with localized, single-responsibility state classes.

🧹 Kills the giant switch

Behavior for each mode lives in its own class instead of being smeared across dozens of conditionals in every method. Reading one state tells you everything it does.

➕ Open to new states

Adding a state means writing one new class, not editing every method of the context. This respects the open-closed principle and keeps changes local.

🚦 Makes transitions explicit

Each state names exactly which states it can move to, so the machine's topology is visible in code rather than hidden inside boolean flags.

🛡️ Prevents illegal actions

An operation that is invalid in a mode simply does nothing or throws in that state class, so you cannot ship an order that was never paid.

In Plain Terms

State explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Think of the states of water. Ice, liquid, and steam are the same H2O, but they behave differently. Add heat and each one transitions to the next. The water is the context; ice, liquid, and steam are the state objects.

👩‍💻 For a developer

It is a lookup table of behavior turned into polymorphism. Instead of switch (status) in every method, you call state.handle() and let the current object decide. Adding a status never touches existing code.

🏢 For a professional

Like a document approval workflow: Draft, In Review, Approved, Rejected. Which buttons you can press depends on the stage, and pressing one moves the document to the next stage. Each stage is a state.

🚦 Everyday version

A traffic light. Green, yellow, and red each know what they show and what comes next. The light does not check "am I green?" everywhere; each color simply behaves and then hands off to the following one.

03 - How

How it works under the hood

You extract every state-dependent method into a state interface, write one concrete state class per mode, and have the context delegate to whichever state is current. States trigger transitions by asking the context to swap its current state.

🧭 Delegation, not branching

The context never inspects its own status. It forwards each call to the current state object, which supplies the right behavior for that mode.

🔁 States own transitions

A concrete state decides what happens next. After handling an event it calls back into the context to set the new current state, encoding one edge of the machine.

A finite state machine in Java: a media player

// State interface: the state-dependent operations
interface PlayerState {
    void play(Player p);
    void pause(Player p);
    void stop(Player p);
}

// Context: delegates every request to the current state
class Player {
    private PlayerState state = new Stopped();

    void setState(PlayerState next) { this.state = next; }

    void play()  { state.play(this); }
    void pause() { state.pause(this); }
    void stop()  { state.stop(this); }
}

// Concrete state: nothing is playing yet
class Stopped implements PlayerState {
    public void play(Player p) {
        System.out.println("Starting playback");
        p.setState(new Playing());        // transition
    }
    public void pause(Player p) { /* no-op: cannot pause when stopped */ }
    public void stop(Player p)  { /* already stopped */ }
}

// Concrete state: audio is running
class Playing implements PlayerState {
    public void play(Player p)  { /* already playing */ }
    public void pause(Player p) {
        System.out.println("Pausing");
        p.setState(new Paused());         // transition
    }
    public void stop(Player p) {
        System.out.println("Stopping");
        p.setState(new Stopped());        // transition
    }
}

// Concrete state: playback is suspended
class Paused implements PlayerState {
    public void play(Player p) {
        System.out.println("Resuming");
        p.setState(new Playing());        // transition
    }
    public void pause(Player p) { /* already paused */ }
    public void stop(Player p) {
        System.out.println("Stopping");
        p.setState(new Stopped());        // transition
    }
}

Notice that Player has no if or switch anywhere. Each state answers the same three methods but behaves differently, and each one decides which state the player becomes next. Calling pause() while Stopped is simply a legal no-op, so illegal transitions are handled by construction rather than by scattered guards.

05 - Step by Step

The 0 → 100 flow

From a class full of conditionals to a clean finite state machine of objects - the whole journey in order.

00
Spot

Notice the state smell

You see the same switch (status) or chain of booleans repeated across many methods, and every new mode forces you to touch all of them.

10
Enumerate

List the states

Write down every distinct mode the object can be in, for example Stopped, Playing, Paused, or New, Paid, Shipped, Cancelled.

20
Map

Draw the transitions

For each state, note which events are valid and which state each event leads to. This diagram is the finite state machine you are about to encode.

30
Extract

Define the state interface

Collect the state-dependent methods into one interface, each taking the context so a state can request a transition.

40
Split

Create one class per state

Move the branch body for each mode into its own concrete state class implementing the interface. One state, one file, one responsibility.

50
Wire

Give the context a current state

Add a state field plus a setState method, and have every public method delegate to the current state instead of branching.

60
Transition

Let states set the next state

Inside each state's methods, call context.setState(next) to encode each valid edge of the machine.

70
Guard

Handle illegal events

For events invalid in a state, make the method a no-op or throw a clear error, so bad transitions are impossible rather than merely discouraged.

80
Initialize

Set the starting state

Construct the context in its initial state (for example Stopped or New) so it is valid the moment it exists.

90
Test

Cover every edge

Test each event from each state, asserting both the resulting state and that illegal events are rejected. The map from step 20 is your checklist.

100
Ship

Extend without fear

Need a new mode like Refunded? Add one class and the edges into and out of it. Existing states stay untouched, and the giant switch never returns.

Common Pitfalls

Pitfalls & anti-patterns

The State pattern is powerful but easy to over-apply or wire together badly. Watch for these.

🪆 Using it for two states

A single boolean flag does not need a class hierarchy. Reach for State when there are several modes and behavior genuinely diverges, not for on and off.

🕸️ Transition logic everywhere

Scattering setState calls across states with no map makes the machine unreadable. Keep an explicit diagram or table so the topology stays clear.

🔓 Leaking context internals

Giving states raw access to every field couples them tightly. Expose a focused API on the context so states change only what they should.

💾 Losing state on transition

Creating a fresh state object each time is fine for behavior, but if data must survive the switch, store it on the context, not on the state.

🐘 God states

One state that handles many special cases with internal branching just moves the switch inside a class. Split it into distinct states instead.

🎭 Confusing it with Strategy

If the caller picks the behavior once and it never self-changes, that is Strategy. Using State there adds transition machinery you do not need.

Trade-offs

Trade-offs & when to use

State trades a handful of small classes for the removal of sprawling conditionals. Here is the honest ledger, including how it differs from Strategy.

AspectDetail
ProsRemoves large conditional and switch blocks, localizes each mode's behavior, makes transitions explicit, and follows the open-closed and single-responsibility principles.
ConsMore classes and indirection, transition logic spread across states, and overkill when there are only one or two simple modes.
Use whenAn object has several distinct modes, behavior differs sharply per mode, and transitions between modes follow rules, that is, a finite state machine.
Avoid whenThere are just a couple of states with trivial differences, or the mode never changes at runtime, where a flag or a Strategy is simpler.
ComplexityLow per state, moderate overall. Each state is tiny, but you must keep the transition map coherent across the whole set.
RelatedStrategy shares the same structure but the client chooses the behavior and states never switch themselves. State objects trigger their own transitions. Both descend structurally from the same delegation idea.
Rule of thumb: reach for State when your object is really a finite state machine and its methods keep asking "what mode am I in?". If instead the caller just plugs in one interchangeable algorithm that never changes on its own, that is Strategy, not State.
06 - Case Studies

Real-world case studies

Three representative uses showing the State pattern where lifecycles and modes dominate the design.

🛒

1 · E-commerce order lifecycle

Pattern: lifecycle as a finite state machine

An order moves through New, Paid, Shipped, Delivered, and Cancelled, and each stage allows different actions.

  • Each status is a state class that permits only its valid actions, so ship() is impossible before payment.
  • Transitions live in the state classes, giving a single, auditable map of the order lifecycle.
  • Adding a Refunded state is one new class plus its edges, with no edits to existing statuses.
✅ Outcome: Illegal transitions become compile-safe by construction, and the sprawling status switch that once lived in the order service disappears.
🎬

2 · Media player controls

Pattern: mode-dependent UI behavior

A player is Stopped, Playing, or Paused, and the same buttons must do different things in each mode.

  • Each state defines how play, pause, and stop behave, so the play button resumes when paused but starts when stopped.
  • The UI simply forwards clicks to the current state and never inspects a status flag.
  • Buffering or an Error state slots in as another class without touching the existing controls.
✅ Outcome: Control logic stays tiny and correct per mode, and new playback states extend the player instead of complicating it.
🔌

3 · TCP connection protocol

Pattern: protocol states from a classic reference

A TCP connection is Established, Listening, or Closed, a textbook example from the original design patterns literature.

  • Operations like open, close, and acknowledge behave differently depending on the connection state.
  • Each protocol state encapsulates its response and the state it transitions to on each event.
  • The connection object delegates to the current state, keeping protocol handling out of one monster method.
✅ Outcome: The protocol's rules read directly as a set of state classes, matching the spec closely and easing verification.
07 - Relevance

Modern relevance

Finite state machines are everywhere in modern software, and the State pattern remains the clean object-oriented way to express them.

⚛️ UI state machines

Front-end tools model components as explicit states and transitions, the same discipline State encodes, taming complex interactive flows.

🔄 Workflow engines

Order, approval, and onboarding workflows are finite state machines at heart, where each step maps naturally to a state class.

🧩 Enum-backed states

Modern languages let a state carry data and behavior together, so the pattern can be expressed with sealed types or enums with methods.

🕹️ Game and agent logic

Characters and agents switch between idle, patrol, chase, and attack modes, a canonical State pattern use in game development.

☁️ Distributed sagas

Long-running distributed transactions track their progress as states, with compensating transitions when a step fails.

🔬 Testable transitions

Because each edge is explicit, state machines are easy to model-check and property-test, raising confidence in critical flows.

Bottom line: whenever an object's behavior depends on a mode that changes over time under rules, you have a finite state machine. The State pattern is how you make that machine explicit, testable, and easy to extend, instead of letting it hide inside ever-growing conditionals.
