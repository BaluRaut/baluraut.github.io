OOP Concept

The Anemic Domain Model - objects with data but no behavior

An anemic domain model is a codebase where your entities are bags of getters and setters and every rule lives in a separate service layer. It looks object-oriented, but it is procedural code wearing a class costume. The rich alternative puts the behavior next to the data it protects, so an Order enforces its own invariants instead of trusting an OrderService to remember.

01 - What

What is the Anemic Domain Model?

An anemic domain model is a design where domain objects carry state but almost no logic. The Order, Cart, and Invoice classes expose public fields (or getters and setters for every field) and nothing else. All the actual behavior - validating a transition, calculating a total, applying a discount - is pushed into stateless service classes that reach into those objects, read the data, mutate it, and write it back. The objects are anemic because the blood, the behavior, has been drained out of them.

🩸 Data-only entities

Classes like Order hold fields and accessors. They have no methods that mean anything in the business language, only getStatus() and setStatus().

🏭 Fat service layer

An OrderService owns every rule. It decides when an order may ship, how totals are computed, and which transitions are legal - reading and writing the entity from outside.

🔓 Invariants left open

Because any caller can set any field, nothing guarantees the object is ever in a valid state. The rules live somewhere else, and only if the caller remembered to route through the service.

Anemic versus rich, side by side

Key mental model: the test is not "do I have classes" but "do my classes have behavior." If deleting every method except getters and setters would not break your entities, they are anemic and the object-orientation is an illusion. Martin Fowler named this an anti-pattern precisely because it pays the cost of a domain model (mapping, hydration) while forfeiting its benefit (encapsulated behavior).
02 - Why

Why it matters

The anemic style is seductive because it is easy to start and mirrors database rows one-to-one. The cost arrives later, when the same rule has to be re-checked in three services and one of them forgets.

🛡️ Encapsulation is forfeited

Public setters mean any code anywhere can put an Order into an impossible state - shipped before paid, negative quantity. The object cannot defend itself, so the guarantee has to be repeated everywhere.

🧭 Logic loses its home

When behavior does not live with data, the same total-calculation or state-check reappears in OrderService, CheckoutService, and ReportService. Duplication drifts and the copies quietly disagree.

🔍 The domain becomes unreadable

To learn what an order can do, you cannot read the Order class - you must grep across a service layer. The ubiquitous language of the business never shows up as methods.

🧪 Testing gets awkward

Rules trapped in stateless services usually need mocks for a repository, a gateway, and a clock just to assert "you cannot ship an unpaid order," a fact that is really about one object.

In Plain Terms

Anemic Domain Model explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

An anemic object is a fill-in-the-blank worksheet with no answer key. Anyone can write anything in the boxes; the rules for what counts as correct live in the teacher's head, in another room. A rich object is a worksheet that refuses invalid answers as you write them.

👩‍💻 For a developer

It is a struct with a manager function. You have a data record and a pile of free functions that operate on it. That is fine in C, but in an object language you have paid for classes and thrown away the one feature - behavior next to state - that justifies them.

🏢 For a professional

Imagine a bank account whose balance anyone can overwrite, where the rule "never go below zero" lives only in the teller's manual. If a teller forgets to open the manual, the account goes negative. A rich model bakes the rule into the account itself.

🚗 Everyday version

A car with the engine, brakes, and steering ripped out and left in the garage, next to a note saying "the mechanic will operate these for you." It has all the parts of a car and none of the ability to drive. The behavior was separated from the thing that needs it.

03 - How

How to recognize it and fix it

The refactor from anemic to rich is mechanical: find a rule inside a service, find the object whose data it reads, and move the rule onto that object as a named method. Then make the fields private so nobody can bypass it.

🩸 The anemic shape

An Order with public status, items, and paidAt, plus an OrderService.markPaid, OrderService.ship, and OrderService.total that read and mutate those fields from the outside.

💪 The rich shape

The same Order with private state and methods pay(), ship(), and total(). Each method checks the invariant first, so an unpaid order simply cannot ship, no matter who calls it.

Contrast in three languages: anemic vs rich

// ANEMIC: Order is a data bag, OrderService does everything.
class Order {
  status: "pending" | "paid" | "shipped" = "pending";
  items: { quantity: number; unitPriceCents: number }[] = [];
  paidAt: Date | null = null;
}

class OrderService {
  markPaid(order: Order, clock: () => Date): void {
    // The rule lives out here, and nothing forces callers through it.
    order.status = "paid";
    order.paidAt = clock();
  }
  ship(order: Order): void {
    if (order.status !== "paid") throw new Error("Order not paid");
    order.status = "shipped";
  }
  totalCents(order: Order): number {
    return order.items.reduce((s, i) => s + i.quantity * i.unitPriceCents, 0);
  }
}

// A caller can bypass every rule; the object cannot defend itself.
const bad = new Order();
bad.status = "shipped"; // shipped without ever being paid. Nothing stops it.

// RICH: behavior and invariants live on the Order itself.
class RichOrder {
  private status: "pending" | "paid" | "shipped" = "pending";
  private paidAt: Date | null = null;
  constructor(private readonly items: LineItem[]) {
    if (items.length === 0) throw new Error("Order needs at least one line item");
  }
  pay(clock: () => Date): void {
    if (this.status !== "pending") throw new Error("Only a pending order can be paid");
    this.status = "paid";
    this.paidAt = clock();
  }
  ship(): void {
    if (this.status !== "paid") throw new Error("Cannot ship an unpaid order");
    this.status = "shipped";
  }
  total(): Money {
    return this.items.reduce((sum, i) => sum.add(i.subtotal()), Money.zero());
  }
}

const order = new RichOrder([new LineItem(2, Money.cents(1999))]);
order.pay(() => new Date());
order.ship();                 // legal: it was paid first
console.log(order.total().format());  // behavior lives where the data lives

from dataclasses import dataclass, field
from datetime import datetime

@dataclass
class Order:
    status: str = "pending"
    items: list = field(default_factory=list)
    paid_at: datetime | None = None

class OrderService:
    def mark_paid(self, order: Order, now: datetime) -> None:
        # The rule lives out here; nothing forces callers through it.
        order.status = "paid"
        order.paid_at = now

    def ship(self, order: Order) -> None:
        if order.status != "paid":
            raise ValueError("Order not paid")
        order.status = "shipped"

    def total_cents(self, order: Order) -> int:
        return sum(i["quantity"] * i["unit_price_cents"] for i in order.items)

# A caller can bypass every rule; the object cannot defend itself.
bad = Order()
bad.status = "shipped"  # shipped without ever being paid. Nothing stops it.

# RICH: behavior and invariants live on the Order itself.
class RichOrder:
    def __init__(self, items: list["LineItem"]):
        if not items:
            raise ValueError("Order needs at least one line item")
        self._items = items
        self._status = "pending"
        self._paid_at: datetime | None = None

    def pay(self, now: datetime) -> None:
        if self._status != "pending":
            raise ValueError("Only a pending order can be paid")
        self._status = "paid"
        self._paid_at = now

    def ship(self) -> None:
        if self._status != "paid":
            raise ValueError("Cannot ship an unpaid order")
        self._status = "shipped"

    def total(self) -> "Money":
        return sum((i.subtotal() for i in self._items), Money.zero())

order.pay(datetime.now())
order.ship()                       # legal: it was paid first
print(order.total().format())      # behavior lives where the data lives

  attr_accessor :status, :items, :paid_at
  def initialize

    @items = []
    @paid_at = nil
  end
end

class OrderService
  def mark_paid(order, now)
    # The rule lives out here; nothing forces callers through it.
    order.status = "paid"
    order.paid_at = now
  end

  def ship(order)
    raise "Order not paid" unless order.status == "paid"
    order.status = "shipped"
  end

  def total_cents(order)
    order.items.sum { |i| i[:quantity] * i[:unit_price_cents] }
  end
end

# A caller can bypass every rule; the object cannot defend itself.
bad = Order.new
bad.status = "shipped"  # shipped without ever being paid. Nothing stops it.

# RICH: behavior and invariants live on the Order itself.
class RichOrder
  def initialize(items)
    raise "Order needs at least one line item" if items.empty?
    @items = items
    @status = "pending"
    @paid_at = nil
  end

  def pay(now)
    raise "Only a pending order can be paid" unless @status == "pending"
    @status = "paid"
    @paid_at = now
  end

  def ship
    raise "Cannot ship an unpaid order" unless @status == "paid"
    @status = "shipped"
  end

  def total
    @items.reduce(Money.zero) { |sum, i| sum.add(i.subtotal) }
  end
end

order = RichOrder.new([LineItem.new(2, Money.cents(1999))])
order.pay(Time.now)
order.ship                       # legal: it was paid first
puts order.total.format          # behavior lives where the data lives

Notice what moved. In the anemic version any line of code can set status = "shipped" and skip payment entirely. In the rich version the field is private and the only door in is ship(), which refuses unless the order was paid. The rule went from a convention you hope everyone follows to a guarantee the object enforces.

When anemic is the right call

// DTOs and API payloads SHOULD be anemic. They carry data across a
// boundary and have no invariants of their own to protect.
interface CreateOrderRequest {
  customerId: string;
  lines: { sku: string; quantity: number }[];
  couponCode?: string;
}

// The wire type is a plain record. Behavior belongs on the domain object
// you build FROM it, not on the transport shape itself.
function toDomain(req: CreateOrderRequest): RichOrder {
  const items = req.lines.map(l => LineItem.fromSku(l.sku, l.quantity));
  return new RichOrder(items); // the RichOrder enforces the rules
}
# DTOs and API payloads SHOULD be anemic. They carry data across a
# boundary and have no invariants of their own to protect.
from dataclasses import dataclass

@dataclass(frozen=True)
class CreateOrderRequest:
    customer_id: str
    lines: list[dict]           # {"sku": str, "quantity": int}
    coupon_code: str | None = None

# The wire type is a plain record. Behavior belongs on the domain object
# you build FROM it, not on the transport shape itself.
def to_domain(req: CreateOrderRequest) -> "RichOrder":
    items = [LineItem.from_sku(l["sku"], l["quantity"]) for l in req.lines]
    return RichOrder(items)     # the RichOrder enforces the rules
# DTOs and API payloads SHOULD be anemic. They carry data across a
# boundary and have no invariants of their own to protect.
CreateOrderRequest = Struct.new(:customer_id, :lines, :coupon_code, keyword_init: true)
# lines: [{ sku: "ABC", quantity: 2 }]

# The wire type is a plain record. Behavior belongs on the domain object
# you build FROM it, not on the transport shape itself.
def to_domain(req)
  items = req.lines.map { |l| LineItem.from_sku(l[:sku], l[:quantity]) }
  RichOrder.new(items)          # the RichOrder enforces the rules
end

Anemic is not always wrong. Data transfer objects, API request and response bodies, event payloads, and read-model projections have no behavior to protect, so giving them methods would be noise. The anti-pattern is specifically about domain entities with real business rules being reduced to records while the rules leak into services.

05 - Step by Step

The 0 → 100 flow

From spotting an anemic model to a healthy rich one, the whole refactor in order.

00
Spot

Notice the smell

Your entities are nothing but getters and setters, and a growing set of ...Service classes hold every rule. That combination is the anemic signature.

10
Locate

Find the real rules

Search the service layer for the business logic: state transitions, total calculations, discount conditions. These are behaviors that belong on an object.

20
Map

Match each rule to its data

For every rule, identify which entity owns the fields it reads and writes. "Cannot ship unless paid" reads status on Order, so it belongs on Order.

30
Name

Choose intention-revealing methods

Replace setStatus("shipped") with a domain verb like ship(). The method name should read like the business event, not the field mutation.

40
Move

Relocate the logic onto the entity

Cut the rule out of the service and paste it into the new method on the entity, checking the invariant before it mutates state.

50
Guard

Validate in the constructor

Ensure an object cannot even be created in an invalid state. An Order with zero line items should throw, not exist.

60
Close

Make the fields private

Remove the public setters. Now the only way to change state is through the methods that enforce the rules. Encapsulation is restored.

70
Thin

Shrink the service to a coordinator

The service now loads the entity, calls one method, and saves. It orchestrates persistence and transactions, not business rules.

80
Extract

Pull out value objects

Concepts like Money, Quantity, or Email become small types with their own rules, draining even more scattered validation into place.

90
Test

Test behavior without mocks

Because rules now live on plain objects, you construct an Order and assert ship() throws. No repository or gateway mock required.

100
Keep

Keep DTOs anemic on purpose

Leave request bodies, event payloads, and read models as plain records. You have moved behavior to where it belongs, not everywhere.

Common Pitfalls

Pitfalls & anti-patterns

The anemic model rarely arrives on purpose. It grows from framework defaults and a few reasonable-looking shortcuts.

⚙️ Getter and setter reflex

Auto-generating a getter and setter for every field is the fastest route to anemia. Expose behavior first, and only the accessors the outside world genuinely needs.

🏭 Service that never shrinks

An OrderService that grows a new method for every rule is a sign the rules have no home. If a method's body is mostly reading and writing one entity's fields, it belongs on that entity.

🧬 ORM entities as the domain

Letting the persistence framework's row-mapped class be your business model pushes you toward public fields and no behavior. Consider mapping to a separate rich model.

🔁 Duplicated invariants

The same "cannot go negative" check copied into three services will drift. Move it onto the object once so there is a single source of truth.

🦴 Over-correcting to a god entity

Fixing anemia by cramming unrelated logic and external calls into one entity is the opposite mistake. Keep behavior that belongs to the object; coordination and I/O stay in services.

🧾 Confusing DTOs with entities

Adding rules to a transport object, or treating a rich entity like a transport object, blurs the boundary. Keep DTOs data-only and entities behavior-rich, and map between them.

Signals & Metrics

Signals & how to measure

Anemia is measurable. These signals tell you whether behavior lives with data or has leaked into a service layer.

SignalWhat it tells you
Method-to-accessor ratio on entitiesIf entities are almost all getters and setters with no domain methods, the model is anemic.
Public setter countMany public setters mean invariants cannot be protected; any caller can reach in and break state.
Service lines per entityA service class far larger than the entity it operates on shows where the behavior actually lives.
Duplicated rule occurrencesThe same validation appearing in several services signals a rule that has no single home.
Mocks needed to test a ruleIf asserting a pure business rule requires repository and gateway mocks, the rule is trapped in a service.
Invalid states reachable in codeCount the ways an object can be constructed or mutated into a state the business forbids.
Rule of thumb: if you can describe a class's entire job as "holds fields and lets a service change them," it is anemic. A healthy entity has at least one method whose name a domain expert would recognize, and no public setter that could break an invariant.
06 - Case Studies

Real-world case studies

Three representative systems where anemic versus rich modeling had real consequences.

🛒

1 · E-commerce checkout with a fat OrderService

Pattern: state transitions pulled back onto the entity

A retail platform had an Order class of pure accessors and an OrderService of several thousand lines holding every transition rule.

  • A bug let orders ship before payment settled, because one code path set status directly and skipped the service check.
  • The team moved transition rules onto Order as pay(), ship(), and cancel(), each guarding its precondition.
  • Public setters were removed, so the invalid path stopped compiling and could not recur.
✅ Outcome: A whole class of "impossible" state bugs became unrepresentable, and the service shrank to a thin coordinator around one method call.
🏦

2 · Banking ledger with money math in services

Pattern: value objects absorb scattered validation

A payments team kept balances as raw integers on an Account record, with rounding and currency checks copied across transfer, fee, and refund services.

  • The copies disagreed on rounding, producing off-by-one-cent discrepancies during reconciliation.
  • They introduced a Money value object owning currency, rounding, and non-negativity, and a rich Account.withdraw() that enforced sufficient funds.
  • Services stopped touching integers directly and simply asked the account to move money.
✅ Outcome: Reconciliation discrepancies disappeared once one type owned the money rules, and overdraft checks could no longer be forgotten.
📅

3 · Booking system that kept its API anemic on purpose

Pattern: rich entities, anemic transport at the edge

A reservations platform had rich Reservation entities that enforced overlap and capacity rules, and deliberately anemic request and response objects at the HTTP boundary.

  • Incoming CreateBookingRequest objects were plain records with no behavior, mapped into rich entities by a thin translator.
  • All availability and cancellation-window rules lived on Reservation, tested with no infrastructure mocks.
  • The wire format could evolve independently without touching a single business rule.
✅ Outcome: The team got both benefits: a defensible domain core and a flexible API surface, because they chose anemic and rich each where it fit.
07 - Relevance

Modern relevance

Frameworks, functional styles, and typed languages have changed the conversation, but the core tension between data and behavior is as alive as ever.

🧱 Domain-driven design revival

DDD's aggregates are the mainstream answer to anemia: an entity that guards its own consistency boundary is the rich model made concrete.

🧮 Functional core, imperative shell

Functional codebases split pure logic from I/O. The pure core carries the behavior, so anemia is avoided by keeping rules and data in the same module, not the same class.

🔒 Types that make states unrepresentable

Sum types and branded types let you encode "a shipped order was paid" in the type system, pushing invariants even earlier than a runtime check.

🧬 ORMs still nudge toward anemia

Many persistence frameworks default to public-field entities. Separating a rich domain model from the persistence model remains a live design choice.

📨 Events and CQRS embrace anemia at edges

Event payloads and read models are intentionally anemic, while the write-side aggregate stays rich. The pattern clarifies where each style belongs.

🤖 Generated code amplifies both

Scaffolding and AI-assisted code emit getter-and-setter entities fast, so the discipline of moving behavior onto objects matters more, not less.

Bottom line: the anemic domain model is not "classes without methods are always wrong." It is a reminder that domain entities earn their keep by owning behavior and defending their invariants. Keep the rules on the objects that hold the data, and keep your transport shapes plain - choose each deliberately.
