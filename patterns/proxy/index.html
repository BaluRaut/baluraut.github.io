Structural Pattern

The Proxy pattern - a stand-in that controls access

A Proxy is a surrogate that implements the same interface as a real object and sits in front of it. Callers think they are talking to the real thing, but the proxy quietly decides when and whether to forward the call - deferring expensive work, enforcing permissions, caching results, or reaching across a network. Same interface, extra control.

01 - What

What is the Proxy pattern?

Proxy provides a placeholder for another object to control access to it. The proxy and the real object (the subject) share one interface, so the proxy is a drop-in substitute. Clients hold a reference to the interface and never learn whether they are wired to the real subject or a stand-in - the proxy intercepts every call and adds behavior before, after, or instead of delegating to the real object.

🎭 Same interface

Proxy and real subject implement the identical type. The client codes to the interface, so the proxy substitutes transparently with zero client changes.

🛡️ Controls access

The proxy sits on the path to the subject and gates it: it can defer creation, check permissions, cache, log, or forward across a boundary.

🔗 Holds the real object

The proxy keeps a reference to the real subject (or the means to create it) and delegates the actual work once it decides the call should proceed.

The main kinds of proxy

KindWhat it controlsTypical use
Virtual / lazyWhen the real object is createdDefer building an expensive object until first real use
RemoteWhere the real object livesLocal stand-in for an object in another process or machine
ProtectionWho may call which methodsCheck roles or permissions before forwarding
CachingWhether the call repeats workReturn a stored result instead of recomputing or refetching
Smart referenceSide effects of using the objectReference counting, lazy locking, logging, load-on-access
Key mental model: a proxy does not change what the operation means - only whether, when, and under what conditions it reaches the real object. If you are changing the result's behavior, you probably want Decorator; if you are changing the interface, you want Adapter.
02 - Why

Why the Proxy pattern exists

Sometimes you cannot or should not let a client touch a real object directly. Creation might be costly, the object might live on another machine, access might need guarding, or repeated calls might be wasteful. A proxy inserts a control point without the client ever knowing.

⏳ Defer expensive work

A virtual proxy postpones building heavy objects (large images, DB connections, parsed models) until the moment they are actually used, so startup stays fast and unused resources are never created.

🌐 Hide remoteness

A remote proxy lets local code call an object in another process or across the network as if it were in memory, encapsulating serialization, transport, and retries behind the same interface.

🔐 Enforce access rules

A protection proxy checks credentials or roles before delegating, centralizing authorization so the real subject stays focused on its core job.

⚡ Avoid repeated work

A caching proxy stores results and serves them on repeat calls, cutting latency and load without the client managing any cache itself.

Proxy explained with analogies

🎓 For a student

A proxy is a teaching assistant who answers routine questions and only passes the hard ones to the professor. To you it feels like asking the professor, but the TA is filtering and forwarding on their behalf.

👩‍💻 For a developer

03 - How

How it works under the hood

A proxy implements the Subject interface that the real object also implements. It holds a reference to the real object, and each method either delegates straight through or wraps the delegation with control logic: create-on-demand, permission checks, cache lookups, or remote calls.

🧩 Shared interface

Client depends only on Subject. Both RealSubject and Proxy implement it, so the proxy is interchangeable with the real object at any call site.

🎚️ Intercept then delegate

The proxy runs its control logic first, then forwards to the real subject if the call should proceed - possibly creating that subject lazily on the first call.

A virtual (lazy-loading) proxy in Java

// Shared interface: both real object and proxy implement it
interface Image {
    void render();
}

// RealSubject: construction is expensive (reads bytes from disk)
class HighResImage implements Image {
    private final String path;
    private byte[] pixels;

    HighResImage(String path) {
        this.path = path;
        loadFromDisk(); // heavy work happens in the constructor
    }

    private void loadFromDisk() {
        System.out.println("Loading " + path + " from disk...");
        this.pixels = new byte[10_000_000]; // pretend this is costly
    }

    public void render() {
        System.out.println("Rendering " + path);
    }
}

// Virtual Proxy: same interface, defers creation until first render()
class LazyImage implements Image {
    private final String path;
    private HighResImage real; // created on demand

    LazyImage(String path) {
        this.path = path; // cheap: no disk I/O yet
    }

    public void render() {
        if (real == null) {            // lazy load on first use
            real = new HighResImage(path);
        }
        real.render();                 // delegate to the real subject
    }
}

// Client codes to the interface and never knows it holds a proxy
class Gallery {
    public static void main(String[] args) {
        Image img = new LazyImage("photo.raw"); // instant, nothing loaded
        System.out.println("Gallery ready.");
        img.render(); // NOW the real image loads, then renders
        img.render(); // already loaded: just renders
    }
}

Notice the proxy adds no new methods - it exposes exactly Image. All it changes is when the heavy HighResImage is built. Swap LazyImage for a ProtectedImage that checks permissions, or a CachedImage that memoizes, and the client stays untouched.

05 - Step by Step

The 0 → 100 flow

From spotting the need to a working, transparent stand-in - implementing and using a proxy in order.

00
Spot

Notice the access problem

Creation is costly, the object is remote, calls need guarding, or results repeat. You need a control point without changing every caller.

10
Interface

Define the shared Subject

Extract the interface the real object exposes. Both the real subject and the proxy will implement exactly this type.

20
Real

Implement the RealSubject

Write the concrete class that does the actual work, unaware that a proxy will ever sit in front of it.

30
Proxy

Create the Proxy class

Make a class that also implements Subject and holds a reference (or the means to create) the real object.

40
Choose

Pick the proxy kind

Decide virtual, remote, protection, caching, or smart reference. That choice defines what control logic the proxy adds.

50
Intercept

Add the control logic

In each method, run the guard first: lazy-create, check permission, look up the cache, or open the remote channel.

60
Delegate

Forward to the real object

When the call should proceed, delegate to the real subject and pass its result back, keeping semantics identical.

70
Wire

Hand the proxy to clients

Return the proxy where clients expect a Subject - often from a factory or DI container - so callers never see the concrete type.

80
Verify

Confirm transparency

Check clients behave the same with the proxy as with the real object, aside from the intended control effect.

90
Harden

Handle edges

Guard concurrent lazy creation, invalidate stale caches, and translate remote failures so the proxy stays reliable under load.

100
Ship

Run in production

The client enjoys fast startup, guarded access, or cached speed, with no idea a surrogate is doing the controlling.

Common Pitfalls

Pitfalls & anti-patterns

Proxies are easy to misuse. These are the usual traps that turn a clean surrogate into a liability.

🎭 Confusing it with Decorator

If your wrapper adds new behavior to the result rather than controlling access, it is a Decorator. Naming a Decorator a proxy hides its real intent from readers.

🧵 Unsafe lazy creation

A virtual proxy that lazy-loads without synchronization can build the real object twice under concurrent calls. Guard the creation or use a thread-safe holder.

🕰️ Stale caches

A caching proxy that never invalidates serves outdated data forever. Without a TTL or invalidation hook, the speed win becomes a correctness bug.

🫥 Hidden latency

A remote proxy makes a network call look like a local method. Callers assume it is cheap and hammer it in loops, unaware of the round trips and failure modes.

🪆 Over-proxying

Stacking proxies for every concern adds indirection that is hard to trace and debug. Each layer must earn its place; needless surrogates just obscure the real object.

🧬 Interface drift

When the real subject gains methods the proxy forgets to forward, the surrogate silently diverges. Keep the proxy in lockstep with the Subject interface.

Trade-offs

Trade-offs & when to use

Proxy buys you a control point at the cost of an extra layer. Weigh it before reaching for it.

AspectDetail
ProsAdds access control, laziness, caching, or remoting transparently; the client and real subject stay untouched and unaware.
ConsExtra indirection and a class to maintain; can hide cost or latency and complicate debugging and stack traces.
Use whenYou need to defer creation, guard access, cache, or represent a remote object behind the same interface as the real one.
Avoid whenYou want to add behavior (use Decorator) or change the interface (use Adapter), or the control adds no real value.
ComplexityLow to moderate. The pattern is simple; the difficulty lives in thread safety, invalidation, and remote error handling.
RelatedDecorator (adds behavior), Adapter (changes interface), Facade (simplifies a subsystem), Flyweight (shares fine-grained objects).
Rule of thumb: reach for Proxy when the wrapper's job is to decide whether, when, or where a call reaches the real object. If the wrapper's job is to change what the call does or how it is shaped, you want Decorator or Adapter instead.
06 - Case Studies

Real-world case studies

Three representative uses of Proxy in production-grade systems.

🌱

1 · Hibernate lazy-loading proxies

Kind: virtual / lazy proxy

An ORM must not load an entire object graph every time you fetch one row, or a single query would drag in the whole database.

  • Hibernate returns a runtime-generated proxy for lazy associations instead of the real entity.
  • The real object and its related rows load from the database only when a method is first called.
  • The proxy implements the entity's type, so application code treats it exactly like the real entity.
✅ Outcome: Queries stay lean, memory is saved, and developers get natural object access without hand-writing fetch logic.
🛰️

2 · gRPC and RMI client stubs

Kind: remote proxy

A service needs to call an object that lives in another process or datacenter, but wants the call to look like an ordinary method invocation.

  • The generated client stub implements the same service interface as the remote server.
  • Calling a method serializes arguments, sends them over the wire, and deserializes the reply.
  • Transport, retries, and connection handling stay hidden behind that local-looking interface.
✅ Outcome: Teams call remote services with clean, typed method calls while networking details stay encapsulated in the stub.
🛡️

3 · Spring AOP and security proxies

Kind: protection / smart-reference proxy

An enterprise app must enforce permissions, transactions, and logging without cluttering business logic with cross-cutting concerns.

  • Spring wraps beans in dynamic proxies that implement the bean's interface.
  • The proxy checks roles, starts transactions, or records metrics before delegating to the real bean.
  • Business methods stay clean; the surrogate applies the policy on every guarded call.
✅ Outcome: Security and transaction rules are enforced consistently and centrally, while the real objects remain focused on their core work.
07 - Relevance

Modern relevance

Far from dated, the Proxy pattern underpins much of today's infrastructure, from language runtimes to service meshes.

🕸️ Service mesh sidecars

Sidecar proxies like Envoy sit beside each service, controlling access, retries, and observability transparently - the remote proxy idea at platform scale.

🧠 JS runtime Proxy object

JavaScript's built-in Proxy intercepts property access and calls at runtime, powering reactive frameworks and validation with the classic surrogate model.

⚙️ Dynamic proxies

Java's java.lang.reflect.Proxy and CGLIB generate proxies at runtime, the backbone of AOP, mocking libraries, and ORM lazy loading.

🚪 API gateways

Gateways are protection and caching proxies for whole systems, enforcing auth, rate limits, and response caching in front of backend services.

🔒 Lazy and safe initialization

Virtual proxies remain the clean way to defer costly construction and manage resource lifecycles in memory-conscious and startup-sensitive apps.

🧪 Test doubles

Mocking frameworks build proxies that stand in for real collaborators, letting tests control and observe interactions through the same interface.

Bottom line: Proxy stays central because the need to control access to an object - to defer, guard, cache, or reach it remotely - never goes away. Whenever a stand-in must be indistinguishable from the real thing, you are looking at a proxy.
