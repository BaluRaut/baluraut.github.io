OOP Concept

Interface Segregation - keep clients off methods they never call

The Interface Segregation Principle says no client should be forced to depend on methods it does not use. When one fat interface bundles reading, writing, refunds, and exports together, every consumer is chained to code it never touches. ISP splits that giant contract into small, focused role interfaces so each caller depends only on the slice it actually needs.

01 - What

What is the Interface Segregation Principle?

Interface Segregation is the "I" in SOLID. It states that a class should never be made to implement, and a caller never made to depend on, a bloated interface whose methods it will not use. Instead of one all-knowing contract, you define several small role interfaces - one per distinct way a client interacts with the object - and let types implement exactly the roles they support.

🧩 Role interfaces

Break a fat contract into focused slices like OrderReader and OrderWriter. Each names a single responsibility a client might depend on.

🔌 Client-specific contracts

A read-only reporting service asks for OrderReader and never sees save or delete. The interface is shaped by the consumer, not the implementer.

🧱 Compose, do not bloat

A concrete class can implement many role interfaces at once. Callers still see only the narrow role they were handed, so coupling stays minimal.

Fat interface vs. segregated roles

AspectOne fat interfaceSegregated role interfaces
Client dependencyEvery caller depends on all methodsEach caller depends only on its role
Forced implementationsClasses stub methods they cannot supportClasses implement only relevant roles
Recompile / redeploy blast radiusA change ripples to unrelated clientsChange is isolated to the affected role
TestingMocks must fake dozens of methodsMock the tiny role under test
ReadabilityIntent buried in a huge surfaceThe type name states what it does
Key mental model: ISP is about the consumer's view, not the implementer's. Ask "what does this caller actually invoke?" and give it a contract that promises exactly that - nothing more.
02 - Why

Why Interface Segregation exists

Fat interfaces spread false coupling. A payment gateway that lumps charge, refund, and payout into one interface forces a checkout screen that only ever charges to recompile when the payout API changes. ISP cuts those phantom dependencies.

🎯 Depend on less

A client that only reads inventory should not break, recompile, or re-test when the write path evolves. Narrow contracts shrink the surface a consumer is bound to.

🧪 Test in isolation

Mocking a five-method role is trivial; mocking a forty-method god interface is a chore that pushes teams toward brittle, over-broad fakes.

🚫 No throw-not-supported stubs

When a read replica cannot write, a fat interface forces a save() that throws at runtime. Split roles let it simply not implement the writer contract.

🔭 Intent by name

Handing a service an OrderReader documents that it will not mutate anything. The type itself is a guardrail and a design statement.

In Plain Terms

Interface Segregation explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Imagine a library card that also legally obliges you to shelve books, manage payroll, and fix the boiler. You only want to borrow. ISP hands you a card that does just borrowing, and gives the janitor a different card.

👩‍💻 For a developer

Instead of one Repository with twenty methods, you expose Reader and Writer. A query handler takes Reader; it literally cannot call delete, and it never rebuilds when the write side changes.

🏢 For a professional

A vendor contract scoped to "refunds only" means you are not liable for their payout obligations. Narrow the contract to the exact service used and the legal blast radius shrinks with it.

🔧 Everyday version

A power outlet gives you two slots, not the whole breaker panel. You plug in what you need; you are not handed every switch in the building just to charge a phone.

03 - How

How it works under the hood

Start from a fat contract, identify the distinct roles its clients play, and carve one interface per role. A concrete class implements every role it truly supports; each caller asks only for the role it needs.

🔎 Find the client roles

List every consumer of the interface and the methods each actually calls. Clusters of methods used together reveal the natural role boundaries - reader, writer, refunder, payout.

✂️ Split, then compose

Extract each cluster into its own interface. The concrete gateway implements all of them; the checkout flow depends on Charger, the ops tool on Refunder.

Splitting a fat interface into role interfaces

// Role interfaces, not one fat PaymentGateway
interface Charger {
  charge(amountCents: number, cardToken: string): Receipt;
}
interface Refunder {
  refund(chargeId: string, amountCents: number): Receipt;
}
interface Payout {
  payout(accountId: string, amountCents: number): Transfer;
}

// One concrete implementation can play many roles
class StripeGateway implements Charger, Refunder, Payout {
  charge(amountCents: number, cardToken: string): Receipt {
    return { id: "ch_1", amountCents, status: "captured" };
  }
  refund(chargeId: string, amountCents: number): Receipt {
    return { id: "re_1", amountCents, status: "refunded" };
  }
  payout(accountId: string, amountCents: number): Transfer {
    return { id: "po_1", accountId, amountCents };
  }
}

// Checkout depends ONLY on Charger - it cannot refund or pay out
class CheckoutService {
  constructor(private readonly gateway: Charger) {}
  placeOrder(cart: Cart): Receipt {
    return this.gateway.charge(cart.totalCents, cart.cardToken);
  }
}

const stripe = new StripeGateway();
const checkout = new CheckoutService(stripe); // passes as a Charger
const receipt = checkout.placeOrder({ totalCents: 4999, cardToken: "tok_visa" });
console.log(receipt.status); // "captured"
from typing import Protocol

# Role interfaces expressed as structural Protocols
class Charger(Protocol):
    def charge(self, amount_cents: int, card_token: str) -> Receipt: ...

class Refunder(Protocol):
    def refund(self, charge_id: str, amount_cents: int) -> Receipt: ...

class Payout(Protocol):
    def payout(self, account_id: str, amount_cents: int) -> Transfer: ...

# One concrete gateway satisfies all three roles
class StripeGateway:
    def charge(self, amount_cents: int, card_token: str) -> Receipt:
        return Receipt(id="ch_1", amount_cents=amount_cents, status="captured")

    def refund(self, charge_id: str, amount_cents: int) -> Receipt:
        return Receipt(id="re_1", amount_cents=amount_cents, status="refunded")

    def payout(self, account_id: str, amount_cents: int) -> Transfer:
        return Transfer(id="po_1", account_id=account_id, amount_cents=amount_cents)

# Checkout depends ONLY on Charger
class CheckoutService:
    def __init__(self, gateway: Charger) -> None:
        self._gateway = gateway

    def place_order(self, cart: Cart) -> Receipt:
        return self._gateway.charge(cart.total_cents, cart.card_token)

stripe = StripeGateway()
checkout = CheckoutService(stripe)  # accepted as a Charger
receipt = checkout.place_order(Cart(total_cents=4999, card_token="tok_visa"))
print(receipt.status)  # "captured"
# Role modules keep each contract focused
module Charger
  def charge(amount_cents, card_token)
    raise NotImplementedError
  end
end

module Refunder
  def refund(charge_id, amount_cents)
    raise NotImplementedError
  end
end

module Payout
  def payout(account_id, amount_cents)
    raise NotImplementedError
  end
end

# One concrete gateway mixes in every role it supports
class StripeGateway
  include Charger, Refunder, Payout

  def charge(amount_cents, card_token)
    Receipt.new(id: "ch_1", amount_cents: amount_cents, status: "captured")
  end

  def refund(charge_id, amount_cents)
    Receipt.new(id: "re_1", amount_cents: amount_cents, status: "refunded")
  end

  def payout(account_id, amount_cents)
    Transfer.new(id: "po_1", account_id: account_id, amount_cents: amount_cents)
  end
end

# Checkout only ever calls the charging role
class CheckoutService
  def initialize(gateway)
    @gateway = gateway
  end

  def place_order(cart)
    @gateway.charge(cart.total_cents, cart.card_token)
  end
end

stripe = StripeGateway.new
checkout = CheckoutService.new(stripe)
receipt = checkout.place_order(Cart.new(total_cents: 4999, card_token: "tok_visa"))
puts receipt.status # "captured"

Notice that CheckoutService only ever receives a Charger. It has no compile-time knowledge of refunds or payouts, so evolving those roles cannot break it - that is ISP turning a broad dependency into a precise one.

Before and after: a fat repository split into Reader and Writer

// BEFORE - one fat interface every client must depend on
interface OrderRepository {
  findById(id: string): Order | null;
  search(query: OrderQuery): Order[];
  save(order: Order): void;
  delete(id: string): void;
}

// AFTER - segregated roles
interface OrderReader {
  findById(id: string): Order | null;
  search(query: OrderQuery): Order[];
}
interface OrderWriter {
  save(order: Order): void;
  delete(id: string): void;
}

class SqlOrderRepo implements OrderReader, OrderWriter {
  findById(id: string): Order | null { return null; }
  search(_: OrderQuery): Order[] { return []; }
  save(_: Order): void {}
  delete(_: string): void {}
}

// A reporting job asks for the Reader role only
class RevenueReport {
  constructor(private readonly orders: OrderReader) {}
  monthlyTotal(q: OrderQuery): number {
    return this.orders.search(q).reduce((s, o) => s + o.totalCents, 0);
  }
}

const repo = new SqlOrderRepo();
const report = new RevenueReport(repo); // narrowed to OrderReader
console.log(report.monthlyTotal({ month: "2026-07" }));
from typing import Optional, Protocol

# BEFORE - one fat interface
class OrderRepository(Protocol):
    def find_by_id(self, id: str) -> Optional[Order]: ...
    def search(self, query: OrderQuery) -> list[Order]: ...
    def save(self, order: Order) -> None: ...
    def delete(self, id: str) -> None: ...

# AFTER - segregated roles
class OrderReader(Protocol):
    def find_by_id(self, id: str) -> Optional[Order]: ...
    def search(self, query: OrderQuery) -> list[Order]: ...

class OrderWriter(Protocol):
    def save(self, order: Order) -> None: ...
    def delete(self, id: str) -> None: ...

class SqlOrderRepo:
    def find_by_id(self, id: str) -> Optional[Order]: return None
    def search(self, query: OrderQuery) -> list[Order]: return []
    def save(self, order: Order) -> None: ...
    def delete(self, id: str) -> None: ...

# Reporting job depends on the Reader role only
class RevenueReport:
    def __init__(self, orders: OrderReader) -> None:
        self._orders = orders

    def monthly_total(self, q: OrderQuery) -> int:
        return sum(o.total_cents for o in self._orders.search(q))

repo = SqlOrderRepo()
report = RevenueReport(repo)  # narrowed to OrderReader
print(report.monthly_total(OrderQuery(month="2026-07")))
# BEFORE - one fat module every client mixed in
module OrderRepository
  def find_by_id(id); end
  def search(query); end
  def save(order); end
  def delete(id); end
end

# AFTER - segregated roles
module OrderReader
  def find_by_id(id); raise NotImplementedError; end
  def search(query); raise NotImplementedError; end
end

module OrderWriter
  def save(order); raise NotImplementedError; end
  def delete(id); raise NotImplementedError; end
end

class SqlOrderRepo
  include OrderReader, OrderWriter
  def find_by_id(id) = nil
  def search(query) = []
  def save(order) = nil
  def delete(id) = nil
end

# Reporting job accepts anything that plays the reader role
class RevenueReport
  def initialize(orders)
    @orders = orders
  end

  def monthly_total(query)
    @orders.search(query).sum(&:total_cents)
  end
end

repo = SqlOrderRepo.new
report = RevenueReport.new(repo) # uses only OrderReader methods
puts report.monthly_total(OrderQuery.new(month: "2026-07"))

The concrete SqlOrderRepo still does everything, but consumers no longer see everything. A read replica could implement OrderReader alone and honestly advertise that it cannot write, instead of throwing from a save it never supported.

05 - Step by Step

The 0 → 100 flow

From one bloated interface to clean, client-specific role contracts - the whole refactor in order.

00
Spot

Notice the fat interface

A single PaymentGateway or Repository keeps growing methods, and unrelated clients recompile whenever any of them changes.

10
Map

List the real clients

Enumerate every consumer: checkout, support console, payouts job, reporting. Record which methods each one actually calls.

20
Cluster

Group methods by role

Methods that clients use together form a cohesive role: charge, refund, payout, reader, writer. These clusters become your interfaces.

30
Extract

Define one interface per role

Create Charger, Refunder, Payout (or OrderReader, OrderWriter), each promising only its cluster.

40
Implement

Let the concrete class play many roles

The real StripeGateway implements every role it supports at once, so behavior is unchanged and centralized.

50
Narrow

Retype each client to its role

Change constructor and parameter types: checkout takes Charger, reporting takes OrderReader. Depend on the slice, not the whole.

60
Inject

Wire the concrete once

At composition root, pass the single StripeGateway into each client. Each sees only the role its parameter declares.

70
Enforce

Let the compiler forbid misuse

Checkout can no longer call refund - it is not on the Charger type. Illegal calls fail at build, not in production.

80
Test

Mock the tiny role

Unit tests fake a two-method Charger instead of a twenty-method gateway. Fixtures shrink and intent sharpens.

90
Delete

Remove the fat interface

Once all clients depend on roles, delete the original god interface and any no-op stubs it forced classes to fake.

100
Evolve

Change one role safely

Adding a method to Payout now touches only payout clients. The blast radius matches the change - ISP achieved.

Common Pitfalls

Pitfalls & anti-patterns

ISP violations are easy to smell once you know the shapes they take.

🗑️ The god interface

A Repository with findById, search, save, delete, export, and audit forces every client to depend on all of it. The type name stops meaning anything.

💥 throw new NotSupported

When a read replica implements a fat writer interface, save() throws at runtime. That thrown stub is proof the interface was too wide for the class.

📎 Coupling by proximity

Bundling charge and payout in one interface makes checkout recompile when payouts change, even though checkout never pays anyone out.

🪆 Over-segregation

Splitting into one interface per method produces a swarm of single-method contracts that obscure real roles. Segregate by client need, not by method count.

🎭 Fat mocks in tests

If a unit test must stub fifteen methods to exercise one, the interface the code depends on is too big. The test pain is the design smell.

🧟 Leaky role naming

Calling a role interface IManager or IService hides its purpose. Name it for the capability - Refunder, OrderReader - so callers see what they get.

Signals & Metrics

Signals & how to measure

You can spot fat interfaces before they hurt by watching a few concrete signals.

SignalWhat it tells you
Methods per interfaceA steadily growing method count on one contract hints it is absorbing multiple roles that should be split.
Unused method ratio per clientIf most clients call only a few of an interface's methods, the interface is wider than any consumer needs.
NotImplemented / throw stubsEvery method that throws "not supported" marks a client that was forced to depend on something it cannot do.
Recompile blast radiusCount how many modules rebuild when the interface changes. A wide radius on an unrelated change signals false coupling.
Mock size in testsLarge hand-written mocks or many stubbed methods per test reveal that consumers depend on more than they use.
Fan-in vs. method usageHigh fan-in on an interface whose methods are used by disjoint client groups is the textbook case for segregation.
Rule of thumb: if the union of methods any single client calls is much smaller than the interface, split it. The right-sized contract is the one where every method is reachable by every client that depends on it.
06 - Case Studies

Real-world case studies

Three production-shaped systems where segregating a fat interface paid off.

💳

1 · Payments gateway split into Charge, Refund, Payout

Pattern: role interfaces per consumer

A marketplace ran checkout, a support console, and a seller-payouts job against a single PaymentGateway interface. Any change to payouts forced checkout to redeploy.

  • The fat interface was split into Charger, Refunder, and Payout role interfaces.
  • The concrete provider client kept implementing all three; each service was retyped to its single role.
  • Checkout could no longer accidentally call payout, and payout changes stopped rippling into checkout builds.
✅ Outcome: Independent deploys per capability and a compiler that blocks a checkout path from ever issuing a payout.
🗄️

2 · CQRS repository split into Reader and Writer

Pattern: read/write segregation

An orders service backed reads with a replica and writes with the primary, but a single OrderRepository interface meant every query handler carried save and delete.

  • The interface was segregated into OrderReader and OrderWriter.
  • Read handlers depended on OrderReader, backed by the replica, which honestly does not implement the writer.
  • Command handlers depended on OrderWriter, routed to the primary database.
✅ Outcome: Read paths physically cannot mutate data, and read-only replicas stopped needing thrown save stubs.
📨

3 · Notification provider split by channel capability

Pattern: capability role interfaces

A notifications platform had one NotificationChannel interface with send, schedule, template render, and delivery-receipt methods. SMS providers could not render rich templates, so they threw.

  • The contract was split into Sender, Schedulable, and TemplateRenderer roles.
  • Each provider implemented only the roles it truly supported; SMS skipped template rendering entirely.
  • Callers requested channels by capability, so a rich-template flow never selected an SMS-only provider.
✅ Outcome: Runtime "not supported" errors disappeared because capability was expressed in the type system, not discovered on send.
07 - Relevance

Modern relevance

ISP is not a relic of classic OOP; it underpins how modern typed and structural languages keep large systems decoupled.

🦫 Small interfaces in Go

Go culture ("accept interfaces, return structs") is ISP by default: tiny interfaces like io.Reader and io.Writer that a client asks for exactly when needed.

🧬 Structural & duck typing

Python Protocols and TypeScript structural types let you declare a narrow role a client depends on without the implementer even knowing the interface exists.

🧭 CQRS and ports

Command/query separation and hexagonal ports are ISP applied to whole subsystems: read ports and write ports as distinct, minimal contracts.

🔒 Capability-based security

Handing a component only the narrow capability it needs, and nothing broader, is ISP as a security boundary, not just a design nicety.

🧩 API and RPC design

gRPC and GraphQL schemas benefit from focused service definitions so clients bind to the methods they call, not a monolithic service surface.

🤖 Tool interfaces for agents

Exposing an agent or plugin only the exact tools a task requires mirrors ISP: give each caller the smallest capable contract.

Bottom line: ISP is the discipline of shaping contracts around consumers. Give each client the smallest interface that lets it do its job, and coupling, test size, and deploy blast radius all shrink together.
