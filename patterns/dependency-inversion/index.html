OOP Concept

Dependency Inversion Principle - point your code at abstractions, not vendors

The Dependency Inversion Principle says high-level policy should not depend on low-level detail; both depend on an abstraction. An OrderService that charges customers should talk to a PaymentGateway interface, never to the Stripe SDK directly. Invert the arrow and your business rules stop caring which vendor is behind them.

01 - What

What is the Dependency Inversion Principle?

DIP is the "D" in SOLID. It has two clauses: high-level modules should not depend on low-level modules, and both should depend on abstractions; and abstractions should not depend on details, details should depend on abstractions. In practice that means your policy code (what to do) defines an interface, and your mechanism code (how to do it, the Stripe SDK, an SMTP client, a Postgres driver) implements that interface. The dependency arrow that normally points from policy down to detail is inverted so both now point at the abstraction.

🏛️ High-level module

Business policy, like OrderService.checkout(). It owns the rules and declares what it needs as an interface. It must not import a vendor SDK.

🔌 Abstraction

The PaymentGateway interface: charge(amount, token). Stable, vendor-neutral, owned alongside the policy that uses it.

⚙️ Low-level module

A concrete adapter like StripeGateway that wraps the Stripe SDK and satisfies the interface. It depends on the abstraction, not the other way around.

The core building blocks

PieceWhat it isIn the checkout example
High-level moduleOwns business policy and rulesOrderService, CheckoutHandler

Adapter (low-level)Concrete class implementing the portStripeGateway, AdyenGateway

Key mental model: DIP is about who owns the interface. The high-level policy defines the contract; the low-level detail conforms to it. Ownership pointing "upward" toward policy is what inverts the dependency.
02 - Why

Why DIP exists

Without inversion, your business rules import concrete vendors, so swapping Stripe for Adyen, or Stripe for a test stub, means editing the code that holds your money logic. DIP keeps volatile details at the edges and your stable policy at the core.

🔄 Swap vendors without touching policy

Add an AdyenGateway that implements PaymentGateway and rewire the composition root. OrderService never changes because it only ever knew the interface.

🧪 Test policy in isolation

Pass a fake gateway that records calls and returns a canned result. You can unit-test refunds and partial captures with no network, no Stripe keys, and no flaky sandbox.

🛡️ Protect the core from churn

SDKs change signatures, deprecate methods, and rename fields. The blast radius stops at the adapter, so your domain layer stays stable while vendors move underneath it.

🧭 Enforce clean architecture boundaries

The rule "domain code may not import infrastructure" becomes checkable. Dependencies all point inward toward abstractions, which keeps layering honest as the system grows.

In Plain Terms

Dependency Inversion explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

You write your essay to the assignment rubric, not to one specific teacher. Any grader who follows the rubric can mark it. The rubric is the abstraction both you and the grader agree on.

👩‍💻 For a developer

Your OrderService declares interface PaymentGateway { charge(...) } and depends only on that. StripeGateway is a plug that fits the socket. You can unplug it and plug in a fake without rewiring the service.

🏢 For a professional

A company hires against a job description, not a named person. Whoever meets the spec can fill the role. The role definition is stable even as the individuals filling it change.

🔌 Everyday version

A wall socket is a standard port. Your laptop charger, a lamp, a kettle - all conform to it. The wall does not depend on your specific device; both depend on the socket standard.

03 - How

How it works under the hood

Define the port next to the policy that needs it, implement adapters at the edge, and choose the concrete adapter once at the composition root. The policy is compiled and tested against the interface alone.

🏛️ Policy owns the port

OrderService declares and imports PaymentGateway. It calls gateway.charge(...) and reasons about the domain result, never about HTTP status codes or Stripe error shapes.

⚙️ Adapter satisfies the port

StripeGateway imports the Stripe SDK, translates a domain charge into an SDK call, and maps the vendor response back into the domain ChargeResult.

The same checkout in three languages

// PORT: the abstraction the policy depends on
interface ChargeResult { ok: boolean; chargeId: string; }

interface PaymentGateway {
  charge(amountCents: number, token: string): ChargeResult;
}

// HIGH-LEVEL MODULE: knows only the port, never Stripe
class OrderService {
  constructor(private readonly gateway: PaymentGateway) {}

  checkout(order: { id: string; totalCents: number; cardToken: string }): string {
    const result = this.gateway.charge(order.totalCents, order.cardToken);
    if (!result.ok) throw new Error(`Payment failed for order ${order.id}`);
    return `Order ${order.id} paid, charge ${result.chargeId}`;
  }
}

// LOW-LEVEL MODULE: adapter that wraps the vendor SDK
class StripeGateway implements PaymentGateway {
  constructor(private readonly sdk: StripeClient) {}

  charge(amountCents: number, token: string): ChargeResult {
    const c = this.sdk.charges.create({ amount: amountCents, source: token });
    return { ok: c.status === "succeeded", chargeId: c.id };
  }
}

// COMPOSITION ROOT: pick the concrete adapter once, inject it
const service = new OrderService(new StripeGateway(new StripeClient(process.env.STRIPE_KEY!)));
console.log(service.checkout({ id: "A-1007", totalCents: 4999, cardToken: "tok_visa" }));

from abc import ABC, abstractmethod
from dataclasses import dataclass

# PORT: the abstraction the policy depends on
@dataclass
class ChargeResult:
    ok: bool
    charge_id: str

class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount_cents: int, token: str) -> ChargeResult: ...

# HIGH-LEVEL MODULE: knows only the port, never Stripe
class OrderService:
    def __init__(self, gateway: PaymentGateway) -> None:
        self._gateway = gateway

    def checkout(self, order: dict) -> str:
        result = self._gateway.charge(order["total_cents"], order["card_token"])
        if not result.ok:
            raise RuntimeError(f"Payment failed for order {order['id']}")
        return f"Order {order['id']} paid, charge {result.charge_id}"

# LOW-LEVEL MODULE: adapter that wraps the vendor SDK
class StripeGateway(PaymentGateway):
    def __init__(self, sdk) -> None:
        self._sdk = sdk

    def charge(self, amount_cents: int, token: str) -> ChargeResult:
        c = self._sdk.charges.create(amount=amount_cents, source=token)
        return ChargeResult(ok=c.status == "succeeded", charge_id=c.id)

# COMPOSITION ROOT: pick the concrete adapter once, inject it
service = OrderService(StripeGateway(StripeClient(os.environ["STRIPE_KEY"])))
print(service.checkout({"id": "A-1007", "total_cents": 4999, "card_token": "tok_visa"}))

ChargeResult = Struct.new(:ok, :charge_id)

# PORT: the abstraction the policy depends on (a duck-typed contract)
module PaymentGateway
  def charge(amount_cents, token)
    raise NotImplementedError
  end
end

# HIGH-LEVEL MODULE: knows only the port, never Stripe
class OrderService
  def initialize(gateway)
    @gateway = gateway
  end

  def checkout(order)
    result = @gateway.charge(order[:total_cents], order[:card_token])
    raise "Payment failed for order #{order[:id]}" unless result.ok
    "Order #{order[:id]} paid, charge #{result.charge_id}"
  end
end

# LOW-LEVEL MODULE: adapter that wraps the vendor SDK
class StripeGateway
  include PaymentGateway

  def initialize(sdk)
    @sdk = sdk
  end

  def charge(amount_cents, token)
    c = @sdk.charges.create(amount: amount_cents, source: token)
    ChargeResult.new(c.status == "succeeded", c.id)
  end
end

# COMPOSITION ROOT: pick the concrete adapter once, inject it
service = OrderService.new(StripeGateway.new(StripeClient.new(ENV.fetch("STRIPE_KEY"))))
puts service.checkout(id: "A-1007", total_cents: 4999, card_token: "tok_visa")

In all three, OrderService never mentions Stripe. It receives a PaymentGateway and sends it the charge message. The Stripe knowledge lives entirely in the adapter, so a test can pass a fake gateway and a production switch to Adyen is one line at the composition root.

Before and after inverting the arrow

// BEFORE: policy depends directly on the vendor detail (arrow points down)
class OrderService {
  private stripe = new StripeClient(process.env.STRIPE_KEY!); // hard-wired vendor
  checkout(order: Order): string {
    const c = this.stripe.charges.create({ amount: order.totalCents, source: order.cardToken });
    return c.id; // cannot test without real Stripe; cannot swap vendors
  }
}

// AFTER: policy depends on an abstraction it owns (arrow inverted)
class OrderService {
  constructor(private readonly gateway: PaymentGateway) {}
  checkout(order: Order): string {
    return this.gateway.charge(order.totalCents, order.cardToken).chargeId;
  }
}

# BEFORE: policy depends directly on the vendor detail (arrow points down)

    def __init__(self, gateway: PaymentGateway) -> None:

  def initialize
    @stripe = StripeClient.new(ENV.fetch("STRIPE_KEY")) # hard-wired vendor
  end

  def checkout(order)
    c = @stripe.charges.create(amount: order[:total_cents], source: order[:card_token])
    c.id # cannot test without real Stripe; cannot swap vendors
  end
end

# AFTER: policy depends on an abstraction it owns (arrow inverted)
class OrderService
  def initialize(gateway)
    @gateway = gateway
  end

  def checkout(order)
    @gateway.charge(order[:total_cents], order[:card_token]).charge_id
  end
end

The "after" class is shorter, has no secrets, and does one thing: apply order policy. That is the payoff of inverting the dependency, the vendor detail is no longer welded to the rule.

05 - Step by Step

The 0 → 100 flow

From a vendor-coupled service to inverted, testable policy - the whole refactor in order.

00
Spot

Find the direct vendor import

OrderService constructs a StripeClient and calls charges.create inline. Policy and mechanism are welded together.

10
Name

Name the capability, not the vendor

The service needs "the ability to charge a card," not "Stripe." Name the concept: a payment gateway with a charge operation.

20
Define

Declare the port

Create interface PaymentGateway { charge(amountCents, token): ChargeResult }, owned next to the policy that consumes it.

30
Shape

Design a domain result type

Return a neutral ChargeResult, not a raw Stripe object, so the vendor's shape never leaks into policy code.

40
Adapt

Build the Stripe adapter

Write StripeGateway implements PaymentGateway. It holds the SDK, translates the call, and maps the response to ChargeResult.

50
Invert

Depend on the abstraction

Change OrderService to accept a PaymentGateway in its constructor and delete every mention of Stripe from it.

60
Wire

Inject at the composition root

In main(), build a StripeGateway and pass it into OrderService. This is the one place that knows the concrete choice.

70
Verify

Run the real path end to end

Confirm the object graph works: caller invokes checkout, the message reaches Stripe, a real charge id comes back.

80
Fake

Add a test double

Write FakeGateway implementing the same port. Inject it in tests to drive success and failure branches without a network.

90
Extend

Add a second vendor

Implement AdyenGateway against the same port. Policy stays byte-for-byte identical, proving the arrow really is inverted.

100
Guard

Enforce the boundary

Add a lint or architecture rule so the domain layer can never import a vendor SDK again. The inversion is now structural, not just tidy.

Common Pitfalls

Pitfalls & anti-patterns

DIP is easy to misapply. These are the smells that mean you inverted the label but not the dependency.

🎭 Leaky abstraction

A PaymentGateway whose method returns a raw Stripe.Charge or throws Stripe.CardError. The vendor still bleeds into policy, so nothing was really inverted.

🪆 Interface owned by the wrong side

Putting the port in the infrastructure package so the domain must import infrastructure to see it. The abstraction has to live with the policy that depends on it.

🧱 One interface per class, reflexively

Wrapping every class in an interface with a single implementer that will never change adds ceremony with no seam. Invert dependencies on volatile details, not on stable ones.

🏗️ New-ing inside the policy

OrderService that does new StripeGateway() in its constructor has an abstract type but a concrete dependency. It still cannot be tested or swapped.

🌊 Interface that mirrors the SDK

A port with createPaymentIntent, confirmIntent, capture - the exact Stripe surface. That is Stripe with extra steps; design the port around your domain needs.

📦 God abstraction

One giant PaymentSystem port with twenty methods forces every adapter to implement operations it does not support. Keep ports small and role-focused.

Signals & Metrics

Signals & how to measure

You cannot put DIP on a dashboard, but these observable signals tell you whether your dependencies really point at abstractions.

SignalWhat it tells you
Vendor imports in the domain layerGrep the domain package for stripe, adyen, SDK names. Any hit means the arrow still points down to detail.
Unit tests need real credentialsIf testing checkout requires a live Stripe key or sandbox, the policy is not decoupled from the mechanism.
Number of adapters per portTwo or more real implementations (Stripe, Adyen, a fake) proves the seam is genuine, not decorative.
Blast radius of an SDK upgradeA vendor version bump should change only the adapter file. Diffs that reach domain classes signal a leak.
Where new StripeGateway appearsConcrete construction should occur only at the composition root. Scattered instantiation means hidden coupling.
Cyclomatic churn in policy classesIf OrderService keeps changing whenever a vendor changes, the abstraction is not absorbing the volatility it should.
Rule of thumb: if you can write a fast unit test for your business rule by passing in a fake, and swapping the vendor touches exactly one file, the dependency is genuinely inverted. If either is false, you have an abstraction in name only.
06 - Case Studies

Real-world case studies

Three production-style systems where inverting the dependency paid off.

💳

1 · Checkout switching payment providers

Pattern: policy depends on a PaymentGateway port

A marketplace ran entirely on Stripe, then needed Adyen for European settlement and lower fees in some regions.

  • OrderService already depended on a PaymentGateway port, so the domain code needed zero changes.
  • A new AdyenGateway adapter was written and selected per-region at the composition root.
  • A FakeGateway let the team keep unit tests fast and offline throughout the migration.
✅ Outcome: The provider swap shipped by adding one adapter and one wiring rule, with the money-handling policy untouched and fully tested.
📣

2 · Notifications across email, SMS, and push

Pattern: a Notifier port with many adapters

A booking platform sent confirmations only by email through SendGrid, then needed SMS via Twilio and mobile push.

  • The ReservationService was refactored to depend on a Notifier port with a single send(message) operation.
  • SendGridNotifier, TwilioNotifier, and PushNotifier each implemented the port at the edge.
  • A composite adapter fanned one domain event out to all channels without the service knowing how many existed.
✅ Outcome: New channels became new adapters. The reservation policy never learned what a Twilio message id or an APNs token is.
🗄️

3 · Repository ports in a hexagonal service

Pattern: domain owns the persistence abstraction

An inventory service was tightly bound to an ORM, making the warehouse logic slow to test and hard to move off the ORM.

  • The domain defined an InventoryRepository port with intent-revealing methods like reserve(sku, qty).
  • A PostgresInventoryRepository adapter implemented it, keeping SQL and the driver out of the domain.
  • An in-memory repository gave the team millisecond unit tests over the reservation and backorder rules.
✅ Outcome: Domain tests ran without a database, and a later storage change stayed contained inside the adapter behind the port.
07 - Relevance

Modern relevance

DIP is decades old, but it underpins how modern services stay testable, portable, and honest about their boundaries.

🛠️ Hexagonal & clean architecture

Ports-and-adapters is DIP made into a whole-application layout: the domain in the center defines ports, and every framework, database, and vendor sits at the edge as an adapter.

🧩 Ports for AI and vendor SDKs

Wrapping an LLM provider behind a CompletionClient port keeps your app free to switch or A/B providers without rewriting prompt-orchestration policy.

☁️ Cloud portability

A BlobStorage port with S3, GCS, and Azure adapters keeps deploy targets swappable and lets local dev run against a filesystem stub.

🧪 Contract testing

Because adapters share a port, one shared test suite can verify every implementation satisfies the same contract, catching drift between vendors.

🔬 Fast, deterministic tests

Inverted dependencies mean the bulk of the suite runs against fakes in memory, so business rules get tested in milliseconds, not over the network.

🧱 Modular monoliths & microservices

Ports become the seams along which a monolith can later split. What was an in-process adapter becomes a network adapter with no change to policy.

Bottom line: DIP is the discipline of pointing your stable business rules at abstractions you own, and letting volatile vendors and frameworks conform to them. Get the arrow right and everything downstream - testing, swapping, scaling - gets cheaper.
