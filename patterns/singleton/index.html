Creational Pattern

The Singleton pattern - one instance, one global door

Singleton guarantees that a class has exactly one instance and provides a single, global access point to it. It is the simplest creational pattern to describe and the easiest to misuse: get the initialization and threading right, and it is a clean way to model a truly unique resource; reach for it by reflex, and it becomes hidden global state that quietly wrecks your tests.

01 - What

What is Singleton?

Singleton is a creational design pattern that restricts a class to a single instance and exposes that instance through a global access point, typically a static getInstance() method. The constructor is made private so no other code can call new, and the class itself owns the one and only object it ever hands out.

🔒 Private constructor

The constructor is hidden so callers cannot create their own copies. The class alone decides when and whether the instance is built.

📦 Static holder

A private static field stores the single instance. It is the class-level slot that all callers ultimately share.

🚪 Global access point

A public static getInstance() returns the shared instance, creating it on first use if needed.

Key mental model: a Singleton is two responsibilities glued together - the object's real job, and the guarantee that there is only one of it. That second responsibility is a global variable in disguise, which is exactly what makes the pattern both convenient and dangerous.
02 - Why

Why Singleton exists

Some resources are genuinely unique: a single connection pool, one in-memory cache, a single hardware device handle. Creating several would be wrong or wasteful, and passing one around everywhere by hand is tedious. Singleton centralizes that "there is exactly one" rule in the class itself.

🎯 Enforces uniqueness

When more than one instance would corrupt state or duplicate a scarce resource, the private constructor makes a second copy impossible rather than merely discouraged.

🌍 One well-known access point

Any code can reach the shared object without threading it through constructors and method parameters, which is convenient for cross-cutting concerns like logging.

💤 Controlled, lazy creation

The instance can be built on first use rather than at startup, so expensive setup happens only if and when the object is actually needed.

📉 Shared, coordinated state

Caches, configuration, and counters that everyone must agree on live in one place, so there is a single source of truth instead of drifting copies.

In Plain Terms

Singleton explained with analogies

Singleton is the one student ID card the registrar issues you. There is exactly one, everyone refers to the same number, and you cannot print yourself a second official copy.

👩‍💻 For a developer

It is a module-level constant object behind a factory method. The first call builds it, every later call gets the very same reference, and new is off the table.

🏢 For a professional

Think of a company's single official seal. Any department can stamp a document, but there is one authoritative seal, kept in one place, that everyone shares.

🏛️ Everyday version

A country has one president at a time. People refer to "the president" without naming anyone, and the office guarantees there is never two of them at once.

03 - How

How it works under the hood

A Singleton hides its constructor and exposes a static accessor. The interesting decisions are when the instance is created (eager vs lazy) and how creation stays correct when many threads call the accessor at once.

🌅 Eager initialization

The instance is built when the class loads, in a static field. It is inherently thread-safe because the class loader guarantees one-time init, but the object is created even if never used.

🌙 Lazy initialization

The instance is built on the first getInstance() call. It saves work when unused, but the check-then-create step is a race under concurrency and needs care to stay safe.

Thread-safe lazy Singleton in Java

public final class Config {

    // volatile so the half-built instance is never seen by another thread
    private static volatile Config instance;

    private final Map<String, String> settings;

    private Config() {
        settings = loadFromDisk();      // expensive, do it once
    }

    public static Config getInstance() {
        Config result = instance;        // read the volatile field once
        if (result == null) {            // first check (no lock, fast path)
            synchronized (Config.class) {
                result = instance;
                if (result == null) {    // second check (inside the lock)
                    instance = result = new Config();
                }
            }
        }
        return result;
    }

    public String get(String key) {
        return settings.get(key);
    }
}

This is double-checked locking. The first null check skips the lock once the instance exists, so the common path stays fast; the volatile keyword is what makes it correct, because without it another thread could observe a partially constructed object.

05 - Step by Step

The 0 to 100 flow

From deciding you need one instance to using it safely and testing around it - the whole journey in order.

00
Decide

Confirm a single instance is required

Ask whether more than one object would actually be wrong. If two copies are merely inconvenient, a normal object plus injection is a better fit than a Singleton.

10
Seal

Make the constructor private

Hide the constructor so no external code can call new. This is the mechanism that turns "please only make one" into an enforced guarantee.

20
Store

Add a static instance field

Declare a private static field to hold the one object. For lazy creation mark it volatile so concurrent reads stay correct.

30
Expose

Write the static accessor

Add a public static getInstance() that returns the shared field. This is the single global door every caller uses.

40
Choose

Pick eager or lazy init

Build eagerly at class load if the object is cheap and always needed; go lazy if construction is expensive or may never happen.

50
Protect

Make creation thread-safe

Guard lazy creation with double-checked locking, or sidestep locks entirely with the holder idiom or an enum. Never leave a bare check-then-create in concurrent code.

60
Harden

Close the back doors

Guard against reflection, serialization, and multiple class loaders that can each forge a second instance. An enum Singleton handles all three for free.

70
Use

Call getInstance where needed

Consumers ask the class for the instance and invoke its behavior. The first call constructs it; every later call reuses the cached object.

80
Smell-check

Watch for hidden coupling

Every direct getInstance() call is an invisible dependency. Count them; a class littered with Singleton lookups is hard to reason about and reuse.

90
Refactor

Prefer injecting the instance

Keep "only one" as a container scope or a single wiring in main, but pass it in through constructors so collaborators depend on an interface, not a static call.

100
Test

Swap it in tests

Because the dependency is injected, tests hand in a fake or mock instead of the real Singleton. No global state to reset between tests, no order-dependent flakiness.

Common Pitfalls

Pitfalls & anti-patterns

Singleton is the pattern most likely to be labeled an anti-pattern, and usually for good reason. These are the traps.

🕳️ Hidden global state

A Singleton is a global variable wearing a class costume. Any method can mutate its state from anywhere, so bugs become non-local and behavior depends on invisible call history.

🧪 Untestable code

Classes that call getInstance() internally cannot be tested in isolation. You cannot substitute a fake, and shared state leaks between test cases causing order-dependent flakiness.

🧵 Broken lazy init

A naive lazy Singleton with a plain null check races under threads and can create two instances, or hand out a partially constructed object if volatile is missing.

🔗 Tight coupling

Direct static calls hard-wire callers to a concrete class. Dependencies are no longer visible in the constructor signature, so you cannot see what a class truly needs.

🪞 Reflection & serialization leaks

Reflection can call a private constructor and deserialization can rebuild an object, both forging a second instance unless you defend against them explicitly.

🧲 Singleton overuse

Turning every manager, helper, and service into a Singleton "for convenience" creates a web of global objects with unclear lifetimes and startup ordering nightmares.

Trade-offs

Trade-offs & when to use

Singleton buys guaranteed uniqueness and easy access at the cost of testability and hidden coupling. Weigh both sides before reaching for it.

AspectDetail
ProsGuarantees one instance, gives a single access point, supports lazy expensive setup, and centralizes shared state in one authoritative place.
ConsIntroduces hidden global state, hurts testability and isolation, tightens coupling to a concrete class, and hides real dependencies from constructors.
Use whenA resource is truly unique (a device handle, one connection pool) and the alternative genuinely cannot be a normal injected object.
Avoid whenYou only want convenient access, or the object holds mutable business state. Prefer dependency injection with a single-instance scope instead.
ComplexityLow to state, but subtle to get thread-safe and reflection-safe. The enum and holder idiom hide most of that complexity.
RelatedFactory Method and Abstract Factory (often singleton-scoped), Prototype (cloning vs sharing), Facade (a single entry point without enforced uniqueness).
Rule of thumb: if you want "only one," use a DI container's singleton scope and inject it. Reserve the classic static Singleton for the rare cases where uniqueness must be enforced by the language itself, and reach for the enum Singleton when you do.
06 - Case Studies

Real-world case studies

Three representative patterns showing Singleton, and its safer variants, in real systems.

🗄️

1 · Database connection pool

Pattern: one shared, expensive resource

An application must share a single pool of database connections so it never exhausts the database's connection limit.

  • The pool is costly to build, so it is created lazily on first use behind a thread-safe accessor.
  • Every request borrows and returns connections from the one pool, keeping total connections bounded.
  • In modern stacks the pool is registered as a container singleton and injected, not fetched statically.
✅ Outcome: connections stay within limits and setup happens once, while injection keeps the pool swappable for an in-memory test double.
🪵

2 · Application logger

Pattern: cross-cutting access point

Code across every layer needs to write to the same logging backend with consistent configuration and buffering.

  • A single logger instance owns the output sinks, formatters, and async buffer.
  • Classic implementations expose it statically, which is convenient but couples every class to the logger.
  • Frameworks now inject a logger per class, preserving one backend while restoring testable, explicit dependencies.
✅ Outcome: consistent, buffered logging everywhere, with injection giving each class a named logger you can capture and assert in tests.
⚙️

3 · Runtime configuration & enum registry

Pattern: enum Singleton for safe uniqueness

A service needs one authoritative, immutable configuration object that resists reflection and serialization attacks.

  • Configuration is modeled as a single-value enum, which the JVM guarantees to instantiate exactly once.
  • The enum form is immune to reflection and deserialization forging a second instance, unlike a plain class.
  • Values are loaded once at class-load time and exposed as read-only accessors.
✅ Outcome: a truly unique, tamper-resistant config object with zero locking code, courtesy of the language guaranteeing one instance.
07 - Relevance

Modern relevance

The need for "exactly one" never went away, but how we achieve it has shifted from static accessors toward container-managed lifetimes.

💉 DI containers won

Spring, Guice, and .NET register services in singleton scope and inject them. You get one instance without the static call, and it is trivially replaceable in tests.

🏅 Enum Singleton is the gold standard

When you truly need a static Singleton in Java, the single-value enum is the recommended form because it is concise and safe against reflection and serialization.

🪟 Holder idiom for lazy without locks

The initialization-on-demand holder idiom uses a nested static class so the JVM's class-loading guarantees give you lazy, thread-safe init with no synchronization.

📦 Module singletons in JS/TS

An ES module is evaluated once, so exporting an instance gives a natural singleton without a class or static method - the runtime does the caching.

🧊 Immutability defuses the risk

Much of the harm comes from mutable global state. A stateless or immutable Singleton (pure config, constants) keeps the convenience with far fewer downsides.

🧭 Taught as a cautionary tale

Singleton remains the canonical example of a pattern that is easy to reach for and hard to live with, so it is now taught alongside its own anti-pattern critique.

Bottom line: keep the goal, drop the reflex. When you need one instance, express it as a single wiring in your composition root or a container scope and inject it. Reserve the classic static Singleton, ideally the enum form, for the rare case where the language itself must enforce uniqueness.
