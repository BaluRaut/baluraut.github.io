OOP Concept

Tell, Don't Ask - let objects act on their own data

Instead of pulling an object's state out, making a decision, and pushing a mutation back in, you tell the object what you want and let it decide how. The behavior lives next to the data it needs. That is what keeps encapsulation real rather than a comment on a public getter.

01 - What

What is Tell, Don't Ask?

Tell, Don't Ask is a design guideline: rather than asking an object for its internal state and then making decisions on its behalf, you should tell the object what to do and let it apply its own rules. A caller that reads account.getBalance(), checks it, and then sets a new balance has taken responsibility that belongs inside Account. The fix is a single command, account.withdraw(amount), that enforces the rule where the data lives.

📤 Send a command

Call a method that expresses intent, like cart.applyDiscount(code), instead of fetching fields and computing the result outside the object.

🧲 Behavior next to data

The logic that needs a field should live in the class that owns the field. Decisions move to where the state already is, not the other way around.

🛡️ Encapsulation, enforced

When callers cannot reach in and mutate state, the object controls every transition. Invariants hold because there is only one door in.

Ask-then-act versus tell

AspectAsk-then-act (avoid)Tell (prefer)
Who decidesThe caller reads state and branchesThe object applies its own rule
Where logic livesScattered across callersInside the class that owns the data
State accessGetters and setters exposedState stays private; intent is public
InvariantsDuplicated and easy to skipEnforced in one place, every time
Change costEdit every call siteEdit one method
Key mental model: Tell, Don't Ask is not a ban on questions. It is a rule about decisions. Reading state to display a report is fine. Reading state to decide what the object should do to itself is the smell.
02 - Why

Why Tell, Don't Ask exists

When callers make decisions from an object's exposed state, the object becomes a bag of data and the real logic leaks into services and controllers. Telling keeps each rule in one place, so the system stays coherent as it grows.

🔒 Protects invariants

An account can refuse an overdraft in withdraw. If every caller instead reads the balance and subtracts, one forgotten check overdraws the account.

🧹 Removes duplication

A discount rule enforced by the cart appears once. The same rule copied across checkout, admin, and API endpoints drifts out of sync fast.

🧭 Localizes change

When the withdrawal policy changes, you edit one method. Ask-then-act forces you to hunt down and update every branch that touched the balance.

🧠 Reveals intent

order.markShipped() reads like a business action. A sequence of getters and setters reads like plumbing and hides what the code is trying to do.

In Plain Terms

Tell, Don't Ask explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

You tell the librarian "check out this book for me." You do not ask for the shelf status, the loan rules, and the stamp so you can update the ledger yourself. The librarian owns those rules.

👩‍💻 For a developer

Prefer account.withdraw(amount) over if (account.balance >= amount) account.balance -= amount. The second version scatters the overdraft rule across every call site and breaks encapsulation.

🏢 For a professional

You delegate to a specialist: you tell finance to process a refund. You do not demand their spreadsheet, apply the policy yourself, and hand back edited numbers. They own the decision that touches their data.

🍽️ Everyday version

At a restaurant you order the dish; you do not walk into the kitchen, read the pantry, and cook it yourself. You state intent and the kitchen, which owns the ingredients, decides how.

03 - How

How it works under the hood

The move is mechanical: find a place where a caller reads an object's state, decides, then writes state back. Push the whole decision into a method on that object and expose only the intent.

🔎 Spot the ask-then-act

Look for a getter, a branch on its result, and a setter or field mutation that follows. That trio is a decision that belongs inside the object.

🚚 Move the decision in

Add a command method that takes the intent as arguments, runs the rule against private state, and either succeeds or raises. Delete the getters that only fed the decision.

Ask-then-act versus tell, three languages

// ASK-THEN-ACT: the caller reads state and decides. The overdraft
// rule now lives outside Account and must be repeated everywhere.
if (account.getBalance() >= amount) {
  account.setBalance(account.getBalance() - amount);
} else {
  throw new Error("Insufficient funds");
}

// TELL: send a command; Account owns balance and the rule.
class Account {
  constructor(
    private balance: number,
    private readonly overdraftLimit = 0,
  ) {}

  withdraw(amount: number): void {
    if (amount <= 0) throw new Error("Amount must be positive");
    if (this.balance - amount < -this.overdraftLimit) {
      throw new Error("Insufficient funds");
    }
    this.balance -= amount;
  }

  deposit(amount: number): void {
    if (amount <= 0) throw new Error("Amount must be positive");
    this.balance += amount;
  }

  // A legitimate ASK: a read-only query for reporting, not a decision.
  get available(): number {
    return this.balance + this.overdraftLimit;
  }
}

const account = new Account(100);
account.withdraw(30);   // tell it what to do
account.deposit(50);
console.log(account.available); // 120 - asking is fine for a report

    raise "Insufficient funds" if @balance - amount < -@overdraft_limit
    @balance -= amount
  end

  def deposit(amount)
    raise ArgumentError, "Amount must be positive" if amount <= 0
    @balance += amount
  end

  # A legitimate ASK: a read-only query for reporting, not a decision.
  def available
    @balance + @overdraft_limit
  end
end

account.deposit(50)
puts account.available  # 120 - asking is fine for a report

Notice the withdrawal rule appears exactly once, inside withdraw, and callers never touch the balance directly. The available query is still allowed because it only reports; it does not decide what the account should do to itself.

A second case: a cart that applies its own discount

// TELL: the cart owns its lines and the discount policy.
class Cart {
  private lines: { price: number; qty: number }[] = [];
  private discountPct = 0;

  add(price: number, qty: number): void {
    this.lines.push({ price, qty });
  }

  applyCoupon(code: string): void {
    // The cart decides whether the coupon is valid for its contents.
    if (code === "SAVE10" && this.subtotal() >= 50) {
      this.discountPct = 10;
    } else {
      throw new Error("Coupon not applicable");
    }
  }

  total(): number {
    return this.subtotal() * (1 - this.discountPct / 100);
  }

  private subtotal(): number {
    return this.lines.reduce((s, l) => s + l.price * l.qty, 0);
  }
}

const cart = new Cart();
cart.add(30, 2);          // tell it to hold items
cart.applyCoupon("SAVE10"); // tell it to apply the coupon
console.log(cart.total());  // 54
# TELL: the cart owns its lines and the discount policy.
class Cart:

        self._discount_pct = 0

    def add(self, price: float, qty: int) -> None:
        self._lines.append((price, qty))

    def apply_coupon(self, code: str) -> None:

        if code == "SAVE10" and self._subtotal() >= 50:
            self._discount_pct = 10
        else:
            raise ValueError("Coupon not applicable")

    def total(self) -> float:
        return self._subtotal() * (1 - self._discount_pct / 100)

    def _subtotal(self) -> float:
        return sum(price * qty for price, qty in self._lines)

# TELL: the cart owns its lines and the discount policy.
class Cart
  def initialize
    @lines = []
    @discount_pct = 0
  end

  def add(price, qty)
    @lines << [price, qty]
  end

  def apply_coupon(code)
    # The cart decides whether the coupon is valid for its contents.
    if code == "SAVE10" && subtotal >= 50
      @discount_pct = 10
    else
      raise "Coupon not applicable"
    end
  end

  def total
    subtotal * (1 - @discount_pct / 100.0)
  end

  private

  def subtotal
    @lines.sum { |price, qty| price * qty }
  end
end

cart = Cart.new
cart.add(30, 2)            # tell it to hold items
cart.apply_coupon("SAVE10") # tell it to apply the coupon
puts cart.total           # 54

The caller never reads the line items to compute eligibility. It tells the cart to apply a coupon, and the cart, which owns both the items and the policy, decides. Move the rule and no call site changes.

05 - Step by Step

The 0 → 100 flow

From an ask-then-act tangle to a clean command, the whole refactor in order.

00
Find

Locate a decision on foreign state

Scan for a caller that reads an object's field, branches on it, and writes a field back. That trio is behavior stranded away from its data.

10
Name

Name the intent

Ask what the caller is really trying to do, not how. "Withdraw," "apply coupon," "mark shipped." The verb becomes the new method.

20
Add

Add a command method

Create a method on the owning class that takes the intent as arguments and returns nothing meaningful, or raises on violation.

30
Move

Move the rule inside

Copy the branch condition and the mutation into the method, now reading and writing private state directly instead of through getters.

40
Guard

Enforce the invariant

Validate inputs and reject illegal transitions at the top of the method, so the object can never be left in a bad state.

50
Replace

Swap call sites

Change each caller from read-decide-write to a single call to the new command. The branching disappears from the caller.

60
Prune

Remove needless getters and setters

Delete accessors that only existed to feed the old decision. State becomes private again and the surface area shrinks.

70
Keep

Keep legitimate queries

Retain reads that only report, like a balance shown on a statement. These ask without deciding, and that is allowed.

80
Test

Test the command directly

Unit test the method for both success and rejection. Because the rule is in one place, one test suite covers every caller.

90
Coordinate

Let services tell, not decide

Where a workflow spans objects, have the service send commands and handle failures, without re-implementing any object's rules.

100
Done

Behavior sits with its data

Every decision now lives in the object that owns the state. Changing a rule touches one method, and encapsulation holds by construction.

Common Pitfalls

Pitfalls & anti-patterns

Applying Tell, Don't Ask carelessly creates its own messes. These are the usual traps.

🩸 Anemic domain model

Classes that are only getters and setters, with all logic in services, are the ask-then-act smell at scale. The data has no behavior, so callers must decide for it.

🎣 Getter, branch, setter

The classic trio: if (x.getState() == READY) x.setState(DONE). The state machine belongs in the object as a complete() command.

🚂 Train-wreck chains

order.getCustomer().getAddress().getCity() asks through several objects. It couples you to their internals and pairs badly with the Law of Demeter.

🕳️ Fake encapsulation

A getter that returns the internal list by reference lets callers mutate private state anyway. Telling means no back door, so return copies or expose commands.

🔨 Dogmatic no-queries

Forbidding all reads breaks reporting, serialization, and UIs. Tell, Don't Ask targets decisions, not honest queries. Do not contort code to avoid every getter.

🧨 Over-command

Cramming unrelated logic into an object to avoid asking bloats it and violates single responsibility. If the behavior does not need the object's private state, it may belong elsewhere.

Signals & Metrics

Signals & how to measure

You cannot put a single number on this, but these signals tell you whether behavior sits with its data.

SignalWhat it tells you
Getter-then-setter pairs per classMany read-decide-write sequences on the same object mean decisions have leaked out of it.
Ratio of commands to accessorsA class that is mostly getters and setters is anemic; intent-revealing methods should dominate the public surface.
Duplicated business rulesThe same condition appearing in several callers shows a rule that should live once, inside the owning object.
Call-site changes per rule changeIf tweaking one policy forces edits across many files, the policy was never encapsulated.
Method-chain depthDeep a.getB().getC() chains signal asking through objects and coupling to their internals.
Test setup complexityIf testing a behavior means stubbing many getters on an object, the behavior probably belongs inside that object.
Rule of thumb: before you read an object's state to make a decision, ask whether the object could make that decision itself. If yes, add a command and delete the getter. If you only need the value to show or record it, asking is fine.
06 - Case Studies

Real-world case studies

Three production-style systems where telling objects, instead of asking them, kept the rules coherent.

🏦

1 · Ledger and account balances in a payments system

Pattern: commands enforce financial invariants

A payments platform needed to guarantee that no account could be overdrawn beyond its arranged limit, across dozens of entry points.

  • Callers were rewritten from reading the balance and subtracting to a single account.withdraw(amount) command.
  • The overdraft rule and currency checks moved inside the account, so every path enforced the same invariant.
  • Read-only statement queries stayed as plain accessors because they report, they do not decide.
✅ Outcome: A whole class of overdraft bugs disappeared, because the rule could no longer be skipped by any caller.
🛒

2 · Checkout carts applying their own discounts

Pattern: pricing policy lives with the cart

An e-commerce team had coupon logic copied across the web checkout, the mobile API, and an internal admin tool, and the three drifted apart.

  • Eligibility checks that read line items in each client moved into cart.applyCoupon(code).
  • The cart became the single owner of totals, discounts, and validity rules for its contents.
  • Clients now tell the cart to apply a coupon and render whatever it returns, deciding nothing.
✅ Outcome: Coupon behavior became consistent everywhere, and new promotions shipped by editing one class.
📦

3 · Order state machine in a fulfillment service

Pattern: transitions as commands, not setters

An order fulfillment service was littered with if (order.getStatus() == PAID) order.setStatus(SHIPPED) checks that let illegal transitions slip through.

  • Status setters were replaced with intent commands like order.markShipped() and order.cancel().
  • Each command validated the current state and rejected illegal transitions from inside the order.
  • The status field became private, so no caller could force an invalid jump.
✅ Outcome: Invalid state transitions became impossible by construction, and the order's lifecycle read as business verbs.
07 - Relevance

Modern relevance

Tell, Don't Ask predates most of today's frameworks, but the pressure it relieves only grows as systems get more distributed.

🧩 Domain-driven design

Rich aggregates that guard their own invariants are Tell, Don't Ask by another name. DDD explicitly fights the anemic model this concept warns against.

📨 CQRS and commands

Command-query separation formalizes the split: commands tell and change state; queries ask and only report. The two are treated as different citizens.

🌐 Distributed services

Sending a message to a service to do something, rather than fetching its data to decide, keeps behavior and state together across process boundaries too.

🧵 Concurrency safety

When an object mutates only through its own commands, it can guard those transitions with a lock in one place. Externalized read-decide-write races.

🎭 Actors and messages

The actor model is Tell, Don't Ask at the runtime level: you send an actor a message and it acts on its private state; you cannot reach in.

🧪 Testable design

Behavior colocated with its data is easy to unit test in isolation, without elaborate stubbing of getters, which keeps test suites fast and honest.

Bottom line: Tell, Don't Ask is how you keep decisions next to the data they depend on, so encapsulation is real and rules live in one place. Ask freely when you only need to report; tell when the object should act on itself.
