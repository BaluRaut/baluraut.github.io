Structural Pattern

How Flyweight makes millions of objects affordable

Rendering a document with a million characters, or a game with a million particles, blows up memory if each one is a fat object. Flyweight fixes that: it shares the parts that repeat (intrinsic state) across all instances and passes in the parts that vary (extrinsic state) at call time, so a handful of shared objects can back an almost unlimited number of logical ones.

01 - What

What is the Flyweight pattern?

Flyweight is a structural pattern that minimizes memory use by sharing as much data as possible between many similar objects. It works by splitting an object's state into two parts: the intrinsic state that is identical across many instances and can be shared, and the extrinsic state that differs per use and is supplied by the caller. A factory hands out shared flyweights so identical intrinsic state is stored exactly once.

🧬 Intrinsic state

The context-free, shareable data that repeats across instances (a glyph's font and outline, a tree's mesh and texture). Stored once inside the flyweight and never changed.

📍 Extrinsic state

The context-dependent data that varies per instance (a character's screen position, a particle's velocity). Kept outside the flyweight and passed in as arguments.

🏭 Flyweight factory

A pool that creates and caches flyweights by key. Ask for one that already exists and you get the same shared instance back, so intrinsic state is never duplicated.

Key mental model: Flyweight does not reduce the number of logical objects, it reduces the number of physical ones. A million characters on screen are backed by maybe a hundred shared glyphs plus a cheap array of positions.
02 - Why

Why Flyweight exists

When you need very large numbers of objects that are mostly identical, the naive approach stores the same heavy data over and over. Flyweight keeps the RAM footprint flat by storing the shared part once, no matter how many logical objects reference it.

🪶 Slashes memory use

Instead of a million fat objects, you hold a few shared flyweights plus tiny per-instance context. Duplicated intrinsic state collapses to a single copy in memory.

⚡ Better cache and GC behavior

Fewer, smaller allocations mean less pressure on the garbage collector and far better CPU cache locality when iterating over huge collections.

♻️ Deduplication by construction

The factory guarantees that asking for the same intrinsic key twice yields the exact same object, so equal things are physically shared, not just logically equal.

🎯 Makes the impossible feasible

Systems that could never hold their objects individually - forest renderers, particle systems, tile maps - become tractable once the repeated bulk is shared.

In Plain Terms

Flyweight explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Think of a rubber stamp. One carved stamp (the shared intrinsic part) presses the same shape thousands of times; the only thing that changes is where on the page you press it (the extrinsic position). You never carve a new stamp per press.

👩‍💻 For a developer

It is like interned strings or a constant pool. Every "OK" literal points to one shared object; the variable holding it just carries a reference. Flyweight interns whole objects and feeds them the varying data as parameters.

🏢 For a professional

Picture a call center script. One printed script (shared) is read to every customer; the customer's name and account number (per-call context) are filled in on the fly. You do not reprint the script for each caller.

♟️ Everyday version

A chess set has one design for a pawn. The board holds eight white pawns not by carving eight unique pawns' worth of design, but by placing the same pawn shape at different squares. The square is the extrinsic state.

03 - How

How it works under the hood

Flyweight has two moving parts: a factory that pools shared intrinsic objects, and a client that keeps the extrinsic state and passes it into shared methods at call time.

🔑 Identify the split

Separate what repeats (font, outline, texture) from what varies (position, color, velocity). Everything intrinsic goes inside the flyweight and is made immutable; everything extrinsic stays with the client.

🗄️ Pool and reuse

A factory keyed on the intrinsic state returns a cached flyweight if one exists, or builds and stores a new one. Clients never construct flyweights directly, so sharing is enforced.

A realistic implementation in Java

import java.util.Map;
import java.util.HashMap;

// Flyweight: stores only intrinsic, shared, immutable state
final class Glyph {
    private final char symbol;   // intrinsic
    private final String font;   // intrinsic (outline lives here too)

    Glyph(char symbol, String font) {
        this.symbol = symbol;
        this.font = font;
    }

    // Extrinsic state (x, y, color) is passed in, never stored
    void draw(int x, int y, String color) {
        System.out.printf("'%c' [%s] at (%d,%d) in %s%n",
                          symbol, font, x, y, color);
    }
}

// Factory: pools flyweights so identical intrinsic state is stored once
final class GlyphFactory {
    private final Map<String, Glyph> pool = new HashMap<>();

    Glyph getGlyph(char symbol, String font) {
        String key = symbol + "@" + font;
        return pool.computeIfAbsent(key, k -> new Glyph(symbol, font));
    }

    int distinctGlyphs() { return pool.size(); }
}

// Client holds extrinsic state and reuses shared flyweights
final class Document {
    private record Placed(Glyph glyph, int x, int y, String color) {}
    private final GlyphFactory factory = new GlyphFactory();
    private final java.util.List<Placed> chars = new java.util.ArrayList<>();

    void type(String text, String font) {
        int x = 0;
        for (char c : text.toCharArray()) {
            Glyph g = factory.getGlyph(c, font); // shared, not new
            chars.add(new Placed(g, x, 0, "black"));
            x += 8;
        }
    }

    void render() {
        for (Placed p : chars) p.glyph().draw(p.x(), p.y(), p.color());
    }

    int distinctGlyphs() { return factory.distinctGlyphs(); }
}

Typing "mississippi" creates eleven placements but only four distinct Glyph objects (m, i, s, p). The Glyph is final with only final fields, so sharing is safe: no client can mutate the intrinsic state and corrupt it for everyone else.

05 - Step by Step

The 0 → 100 flow

From a memory-heavy design to a shared, scalable one - the whole journey in order.

00
Spot

Notice the scale problem

You need thousands or millions of similar objects and profiling shows memory dominated by duplicated data. That is the signal Flyweight is worth it.

10
Analyze

List every field

Enumerate the fields of the heavy object. For each, ask: does this repeat across most instances, or does it vary per instance?

20
Split

Divide intrinsic vs extrinsic

Repeating, context-free fields become intrinsic (stay in the flyweight). Varying, context-dependent fields become extrinsic (move out to the client).

30
Model

Design the flyweight class

Create a class holding only intrinsic state. Its methods accept extrinsic state as parameters rather than reading it from fields.

40
Freeze

Make intrinsic state immutable

Mark the fields final/readonly and expose no setters. Shared objects must be immutable so one client cannot corrupt them for all the others.

50
Pool

Build the factory

Write a factory keyed on the intrinsic state. On request it returns the cached flyweight or creates, stores, and returns a new one.

60
Gate

Route all creation through it

Make the flyweight constructor private or package-scoped so clients cannot bypass the pool. Sharing is only guaranteed if the factory is the single door.

70
Store

Hold extrinsic state in the client

The client keeps a compact record per logical object: a reference to the shared flyweight plus its own position, color, or other varying data.

80
Invoke

Pass context at call time

When acting, the client calls the flyweight method and passes the extrinsic state in, so one shared object behaves differently per context.

90
Measure

Verify the savings

Count distinct flyweights versus logical objects and re-profile memory. Confirm the pool size is small and the footprint dropped as expected.

100
Tune

Manage the pool lifecycle

Decide when flyweights are evicted or kept for the process lifetime, and whether the factory must be thread-safe under concurrent access.

Common Pitfalls

Pitfalls & anti-patterns

Flyweight is easy to misapply. These are the traps that turn a memory win into a bug source.

🧊 Mutable shared state

Putting mutable fields in the flyweight is the cardinal sin. One client changes the "shared" object and silently breaks every other holder. Intrinsic state must be immutable.

🎭 Wrong split

Marking per-instance data as intrinsic collapses distinct objects into one; marking shared data as extrinsic destroys the savings. Get the intrinsic/extrinsic line right or the pattern fails.

🐘 Premature optimization

Flyweight adds a factory, an indirection, and a mental tax. If you only have a few hundred objects, the complexity buys nothing. Profile first, then apply.

💧 Pool that never shrinks

An unbounded factory cache can itself become a memory leak, especially with high-cardinality keys. Bound it or scope it so the pool does not outgrow what it saved.

🧵 Ignoring thread safety

Two threads hitting the factory on a cache miss can create duplicate flyweights or corrupt the map. Concurrent pools need proper synchronization or a concurrent map.

🔁 Extrinsic overhead swamps savings

If passing extrinsic state around costs more memory or CPU than it saved, or key computation is expensive, the pattern can be a net loss. Measure both sides.

Trade-offs

Trade-offs & when to use

Flyweight trades a little indirection and design effort for large memory savings. Reach for it only when the numbers justify it.

AspectDetail
ProsDramatically lower memory footprint, less GC pressure, better cache locality, guaranteed deduplication of shared state.
ConsMore complex code, an extra factory and indirection, CPU cost to compute keys and pass extrinsic state, immutability constraints.
Use whenYou have very large numbers of objects, most of whose state repeats and can be separated into a small set of shared values.
Avoid whenObject counts are modest, state barely repeats, or intrinsic state must be mutable. The complexity would not pay for itself.
ComplexityModerate. The pattern is simple, but drawing the intrinsic/extrinsic line correctly and keeping shared state immutable takes care.
RelatedSingleton (factory is often one), Prototype (cloning vs sharing), Composite (flyweights as shared leaves), Proxy (both indirect access).
Rule of thumb: Use Flyweight only when memory is a real constraint and the object's state cleanly splits into a small shared core and a variable context. If either condition fails, a plain object or an object pool is simpler.
06 - Case Studies

Real-world case studies

Three places where Flyweight is the difference between running and running out of memory.

📝

1 · Text editor glyph rendering

Pattern: shared character objects, per-position context

A document editor must display hundreds of thousands of characters, each needing a font, outline, and metrics.

  • Each distinct character-and-font pair is a single shared Glyph holding the outline and advance width.
  • The document stores only a lightweight run of positions and styles, referencing shared glyphs.
  • Rendering passes each glyph its row, column, and color as extrinsic state at draw time.
✅ Outcome: The classic Gang of Four example. A book-length document is backed by a few hundred glyph objects instead of millions, keeping the editor responsive.
🎮

2 · Game particle and foliage systems

Pattern: shared mesh and texture, per-instance transform

A game renders a forest of a million trees or a burst of tens of thousands of particles at 60 frames per second.

  • The heavy mesh, texture, and material are shared across every tree of the same species.
  • Each instance stores only its position, rotation, scale, and velocity, a few dozen bytes.
  • The renderer instances the shared asset many times, feeding the per-instance transforms to the GPU.
✅ Outcome: Dense worlds fit in VRAM and stream smoothly, because the megabytes of geometry exist once, not once per object.
☕

3 · JVM Integer and String interning

Pattern: language-level flyweight caches

A high-throughput service creates enormous numbers of small boxed values and repeated string literals.

  • Java caches boxed Integer values from -128 to 127 so valueOf returns shared instances.
  • String literals are interned in a pool, so identical literals across the codebase share one object.
  • Application code gets the memory win for free, without writing any factory itself.
✅ Outcome: Common small values are allocated once and reused everywhere, cutting allocation churn in hot paths across the entire runtime.
07 - Relevance

Modern relevance

Flyweight predates modern hardware, but its core idea, share the repeated bulk and vary only the context, is more relevant than ever at scale.

🕹️ GPU instanced rendering

Modern graphics APIs make Flyweight native: one mesh drawn thousands of times with a buffer of per-instance transforms is Flyweight in hardware.

🧊 Value types and records

Immutable records and value objects make safe, shareable flyweights trivial to declare, since the language enforces the immutability the pattern requires.

🌊 Big-data columnar stores

Dictionary encoding in columnar formats stores each distinct value once and references it by id, which is Flyweight applied to billions of rows.

⚛️ UI virtualization

Virtualized lists and immutable component trees reuse shared node descriptions across huge views, keeping only the varying props per item.

🔗 String and object interning

Runtimes and caches still lean on interning to collapse duplicate values, from JVM strings to symbol tables in interpreters.

🧠 Tokenizer and vocab tables

ML pipelines share one vocabulary of token objects across every sequence, storing per-sequence data as compact id arrays.

Bottom line: Flyweight is how you make very large numbers of objects affordable: store what repeats once, pass in what varies, and keep the shared part immutable. Whenever scale meets duplication, the pattern earns its keep.
