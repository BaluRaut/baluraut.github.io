Behavioral Pattern

How the Memento pattern captures and restores state

Sometimes you need to rewind an object to an earlier moment: undo an edit, roll back a failed transaction, restore a saved game. Memento lets you snapshot an object's internal state and later restore it, all without exposing the object's private fields to the outside world. The object that owns the state stays in control of what gets saved and how.

01 - What

What is the Memento pattern?

Memento is a behavioral pattern that captures an object's internal state into a separate object, so that the state can be restored later, without violating the original object's encapsulation. The saved snapshot is opaque to everyone except the object that created it, which means private fields never leak into client code just to support save and restore.

🧑‍🎨 Originator

The object whose state matters. It creates a memento capturing its current state and later uses a memento to restore itself.

📦 Memento

A value object holding a snapshot of the originator's state. Opaque to outsiders; only the originator can read its full contents.

🗂️ Caretaker

Keeps mementos in a history (often a stack) and asks for save or restore, but never inspects or edits what is inside a memento.

Key mental model: the memento is a sealed envelope. The originator writes the letter and later reads it back; the caretaker only files the envelope by date and hands it back on request. Nobody else opens it, so encapsulation stays intact.
02 - Why

Why the Memento pattern exists

The naive way to add undo is to make every field public so a manager class can copy and reset them. That shatters encapsulation and couples the manager to internal layout. Memento gives you rewind without that leak.

🔒 Preserves encapsulation

State is captured and restored by the originator itself. Private fields never become public just to support saving, so internal structure stays hidden and free to change.

↩️ Enables clean undo and redo

A stack of mementos gives you multi-level undo almost for free. Push before each change, pop to revert, and keep a redo stack for the other direction.

🧩 Separates concerns

The originator focuses on its behavior; the caretaker focuses on history management. Neither needs to know the other's internals.

🕰️ Supports checkpoints and rollback

Take a snapshot before a risky operation, then restore it if the operation fails. This gives transactional, all-or-nothing behavior to plain objects.

In Plain Terms

Memento explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is the save point in a video game. Before a hard boss you save; if you lose, you reload that exact save and try again. The game world writes and reads the save file; you just choose when to save and load.

👩‍💻 For a developer

Think of Ctrl+Z in your editor. Each keystroke pushes a snapshot of the buffer onto an undo stack. Undo pops the last snapshot and the document restores itself; your history manager never parses the document format.

🏢 For a professional

It is a document version history. Every save records a full version. To roll back, you pick a version and the document reloads it. The archive stores versions but does not edit their contents.

📸 Everyday version

A Polaroid photo of a room. Later you rearrange the furniture back to match the picture. The photo froze one moment; the room can be restored to it without the photo knowing how furniture moves.

03 - How

How it works under the hood

The originator exposes two operations: save, which returns a memento holding its current state, and restore, which reads a memento back into itself. The caretaker keeps those mementos in order and decides when to save or roll back.

💾 Save

The originator copies its relevant fields into a new, immutable memento and hands it out through a narrow interface. The caretaker pushes it onto the history stack.

♻️ Restore

On undo, the caretaker pops a memento and passes it back to the originator, which copies the stored fields back into itself, returning to that exact past state.

A working example

// Memento: opaque snapshot. Only the Originator reads its full state.
class EditorMemento {
  constructor(
    private readonly content: string,
    private readonly cursor: number,
  ) {}

  // Wide interface, used by the Originator only.
  getContent(): string { return this.content; }
  getCursor(): number { return this.cursor; }
}

// Originator: owns the state, creates and restores snapshots.
class Editor {
  private content = "";
  private cursor = 0;

  type(text: string): void {
    this.content =
      this.content.slice(0, this.cursor) + text + this.content.slice(this.cursor);
    this.cursor += text.length;
  }

  save(): EditorMemento {
    return new EditorMemento(this.content, this.cursor);
  }

  restore(m: EditorMemento): void {
    this.content = m.getContent();
    this.cursor = m.getCursor();
  }

  toString(): string { return this.content; }
}

// Caretaker: keeps history, never inspects a memento.
class History {
  private readonly stack: EditorMemento[] = [];

  backup(editor: Editor): void {
    this.stack.push(editor.save());
  }

  undo(editor: Editor): void {
    const m = this.stack.pop();
    if (m) editor.restore(m);
  }
}

const editor = new Editor();
const history = new History();

history.backup(editor);
editor.type("Hello");
history.backup(editor);
editor.type(", world");
console.log(editor.toString()); // Hello, world

history.undo(editor);
console.log(editor.toString()); // Hello
history.undo(editor);
console.log(editor.toString()); // (empty)

# Memento: opaque snapshot. Only the Originator reads its full state.
class EditorMemento:
    def __init__(self, content: str, cursor: int) -> None:
        # Underscore-prefixed: treated as private to the Originator.
        self._content = content
        self._cursor = cursor

    # Wide interface, used by the Originator only.
    def get_content(self) -> str:
        return self._content

    def get_cursor(self) -> int:
        return self._cursor


# Originator: owns the state, creates and restores snapshots.
class Editor:
    def __init__(self) -> None:
        self._content = ""
        self._cursor = 0

    def type(self, text: str) -> None:
        self._content = (
            self._content[: self._cursor] + text + self._content[self._cursor :]
        )
        self._cursor += len(text)

    def save(self) -> EditorMemento:
        return EditorMemento(self._content, self._cursor)

    def restore(self, m: EditorMemento) -> None:
        self._content = m.get_content()
        self._cursor = m.get_cursor()

    def __str__(self) -> str:
        return self._content


# Caretaker: keeps history, never inspects a memento.
class History:
    def __init__(self) -> None:
        self._stack: list[EditorMemento] = []

    def backup(self, editor: Editor) -> None:
        self._stack.append(editor.save())

    def undo(self, editor: Editor) -> None:
        if self._stack:
            editor.restore(self._stack.pop())

history = History()

history.backup(editor)
editor.type("Hello")
history.backup(editor)
editor.type(", world")
print(editor)  # Hello, world

history.undo(editor)
print(editor)  # Hello
history.undo(editor)
print(editor)  # (empty)

# Memento: opaque snapshot. Only the Originator reads its full state.
class EditorMemento
  # Wide interface, used by the Originator only.
  attr_reader :content, :cursor

  def initialize(content, cursor)
    @content = content
    @cursor = cursor
  end
end

# Originator: owns the state, creates and restores snapshots.
class Editor
  def initialize
    @content = ""
    @cursor = 0
  end

  def type(text)
    @content = @content[0...@cursor] + text + @content[@cursor..]
    @cursor += text.length
  end

  def save
    EditorMemento.new(@content, @cursor)
  end

  def restore(m)
    @content = m.content
    @cursor = m.cursor
  end

  def to_s
    @content
  end
end

# Caretaker: keeps history, never inspects a memento.
class History
  def initialize
    @stack = []
  end

  def backup(editor)
    @stack.push(editor.save)
  end

  def undo(editor)
    m = @stack.pop
    editor.restore(m) if m
  end
end

editor = Editor.new
history = History.new

history.backup(editor)
editor.type("Hello")
history.backup(editor)
editor.type(", world")
puts editor # Hello, world

history.undo(editor)
puts editor # Hello
history.undo(editor)
puts editor # (empty)

Notice the caretaker never reads getContent() or getCursor(). It stores and returns mementos blindly, so the editor is free to change how it represents content without breaking the history.

05 - Step by Step

The 0 → 100 flow

From identifying the state to a working multi-level undo, the whole journey in order.

00
Identify

Find the state to protect

Pick the object whose internal state must be captured and restored. Decide exactly which fields define a meaningful snapshot.

10
Design

Define the Memento type

Create an immutable value object that holds a copy of those fields. Give it a wide interface for the originator and a narrow one for everyone else.

20
Originator

Add a save method

Implement save() on the originator so it copies its current state into a fresh memento and returns it.

30
Originator

Add a restore method

Implement restore(memento) so the originator copies the stored fields back into itself, returning to that exact state.

40
Copy

Snapshot by value, not reference

Deep-copy mutable fields into the memento so later edits to the originator cannot alter a saved snapshot.

50
Caretaker

Build the history store

Add a caretaker holding a stack of mementos. It calls save before each change and keeps the returned memento.

60
Backup

Save before mutating

Wire the caretaker so every user action first pushes a memento, then applies the change. Now the previous state is always recoverable.

70
Undo

Pop and restore

Implement undo: pop the last memento and pass it to the originator's restore. The object jumps back one step.

80
Redo

Add a redo stack

When you undo, push the popped state onto a redo stack so the user can move forward again. Clear it on any new edit.

90
Bound

Cap the history size

Limit how many mementos you keep so memory stays bounded. Drop the oldest, or snapshot less often, to control cost.

100
Ship

Undo, redo, and rollback in place

The originator supports full undo and redo with encapsulation intact, plus checkpoint and rollback for risky operations.

Common Pitfalls

Pitfalls & anti-patterns

Memento is simple to state and easy to get subtly wrong. These are the usual traps.

💥 Memory blowup

Every snapshot is a full copy of state. Save on every keystroke over a large document and memory grows without bound. Cap the history and snapshot at coarse boundaries.

🔗 Shallow copies

Storing references instead of deep copies means later mutations quietly corrupt old mementos. A restore then returns the wrong state. Copy mutable data by value.

🔓 Leaky interface

Exposing the memento's full state to the caretaker recreates the encapsulation break you were trying to avoid. Keep the wide interface private to the originator.

🧨 Caretaker editing mementos

If the caretaker mutates or interprets what is inside a memento, it couples to the originator's internals. The caretaker must treat mementos as opaque tokens.

🐌 Snapshotting huge state

Full snapshots of large objects are slow and heavy. For big state, prefer incremental or command-based undo that stores diffs instead of whole copies.

🌐 External resources in state

Sockets, file handles, or threads cannot be meaningfully snapshotted and restored. Capture only serializable, value-like state, not live resources.

Trade-offs

Trade-offs & when to use

Memento buys clean, encapsulated rollback at the price of memory and copy cost. Weigh both before reaching for it.

AspectDetail
ProsPreserves encapsulation, gives clean undo and rollback, and keeps history logic out of the originator.
ConsFull snapshots cost memory and copy time; frequent saves of large state can dominate resource use.
Use whenYou need undo, redo, checkpoints, or transactional rollback and must not expose the object's internals.
Avoid whenState is very large or changes constantly; prefer command-based diffs or event sourcing to storing full copies.
ComplexityLow structurally, but correctness hinges on deep copying and on keeping the memento opaque to the caretaker.
RelatedCommand stores the actions to reverse; Prototype clones state; State models the modes you snapshot; Iterator can walk history.
Rule of thumb: reach for Memento when a snapshot of state is cheap and self-contained. When state is large or edits are frequent, store what changed (Command) rather than the whole object.
06 - Case Studies

Real-world case studies

Three representative patterns showing Memento in production-style use.

📝

1 · Undo history in a text editor

Pattern: multi-level undo and redo

A code editor needs unlimited undo across edits, selections, and cursor moves without exposing the buffer's internals.

  • Each edit asks the document originator for a memento of its buffer and cursor.
  • A caretaker keeps undo and redo stacks, popping between them as the user rewinds.
  • History is capped and snapshots are coalesced so rapid typing does not exhaust memory.
✅ Outcome: Reliable undo and redo with the buffer's representation fully hidden, so the editor can change its internal model without touching history code.
🎮

2 · Save and load in a game

Pattern: checkpoints and restore

A game must let players save progress at checkpoints and reload the exact world state after a defeat.

  • The game state object creates a memento of player position, inventory, and world flags.
  • A save manager stores mementos as named slots and serializes them to disk.
  • Loading passes the chosen memento back to the state object to restore the moment exactly.
✅ Outcome: Players resume from any checkpoint with the full world intact, while the save system stays decoupled from how game state is structured.
🔁

3 · Transactional rollback in a form wizard

Pattern: all-or-nothing state change

A multi-step wizard applies changes as the user advances but must roll everything back if final submission fails.

  • Before the risky commit, the model snapshots its whole state into a checkpoint memento.
  • If the server rejects the submission, the model restores the checkpoint atomically.
  • On success the checkpoint is discarded, leaving the new state committed.
✅ Outcome: Users never see a half-applied state; a failed submit cleanly reverts to the last good snapshot with no manual undo logic.
07 - Relevance

Modern relevance

Memento is old, but its idea of capturing and restoring state runs through much of today's software.

🧠 State management libraries

Redux time-travel debugging is Memento at scale: each dispatched action snapshots the store so you can step backward through state.

📼 Event sourcing contrast

Event sourcing rebuilds state from a log of changes rather than full snapshots, but often uses periodic snapshots as Memento-style checkpoints to speed replay.

🗄️ Database savepoints

Transactional savepoints and rollbacks mirror the checkpoint use of Memento, letting a unit of work revert to a known good point.

📸 Immutable snapshots

Persistent, immutable data structures make Memento cheap: sharing unchanged parts means each snapshot stores only the difference.

🧩 Command plus Memento

Undo systems often combine the two: Command records the action while Memento captures any state the action cannot recompute.

☁️ Serverless and workflows

Durable workflow engines checkpoint execution state so a paused or crashed run can resume exactly where it left off.

Bottom line: Memento is how you give an object a rewind button without prying it open. Whenever you need undo, checkpoints, or rollback with encapsulation intact, the snapshot-and-restore idea is the right tool, balanced against its memory cost.
