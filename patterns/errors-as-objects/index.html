OOP Concept

Errors as Objects - modeling failure in the type system

A failed payment is not a string and not a stray -1. It is a thing with a name, a cause, and context: which card, how much, why the bank said no. When you make errors first-class objects instead of magic values, failure becomes something the compiler and your handlers can reason about, route, and recover from.

01 - What

What does "errors as objects" mean?

In object-oriented languages an exception is not a special primitive: it is an ordinary object of a class you can subclass, extend, and enrich. "Errors as objects" is the discipline of naming each distinct failure as its own type, giving it fields that carry the facts of what went wrong, and letting callers match on the type rather than parsing a message or checking a numeric code.

🏷️ A named type

PaymentDeclined is a class, not a string. Handlers catch it by name, so "declined" and "network timeout" take different branches without string matching.

🎒 Carries context

The object holds the amount, currency, card fingerprint, and decline code. The catch site gets structured data, not a sentence it has to reverse-engineer.

🌳 Part of a hierarchy

InsufficientFunds extends PaymentDeclined extends a base PaymentError. Catch the base to handle a whole family, or a leaf for one precise case.

Ways a failure can be represented

RepresentationHow the caller reactsCost
Boolean / null returnGuesses why from thin airLoses the reason entirely
Numeric error codeLooks up a constant, hopes it is currentUntyped, easy to ignore
String messageParses prose, breaks on rewordingFragile, not machine-safe
Exception objectCatches by class, reads fieldsControl flow leaves the happy path
Result / Either valueMust inspect before using the valueFailure is visible in the signature
Key mental model: an error object answers three questions at once - what kind of failure (its class), the specifics (its fields), and where it fits (its place in the hierarchy). A string answers none of them reliably.
02 - Why

Why model errors as objects

Failure is not an afterthought in real systems - a payments service spends most of its edge cases handling the ways money does not move. Making those cases explicit types turns "hope nothing throws" into a checklist the code enforces.

🎯 Precise handling

Catching InsufficientFunds can prompt "add funds," while CardExpired prompts "update card." A single generic catch cannot tell these apart, so it does the wrong thing for both.

📦 Context travels with the failure

The decline code, retry-ability, and gateway reference ride inside the object all the way up the stack. No global lookup, no re-deriving facts the origin already knew.

🧭 The type system documents failure

A Result<Receipt, PaymentError> return type tells every caller, at compile time, that this call can fail and exactly how. Failure stops being a surprise at 3am.

🧱 Extends without breaking callers

Add FraudSuspected under PaymentDeclined and old handlers that catch the base still work. New handlers opt into the finer case when ready.

In Plain Terms

Errors as objects explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

A graded exam that just says "wrong" teaches you nothing. One that says "wrong: you divided instead of multiplied on question 4" tells you exactly what to fix. An error object is the second kind of feedback.

👩‍💻 For a developer

It is the difference between a function returning false and returning a typed failure value. One forces you to guess; the other hands you a class you can catch by name and read fields off.

🏢 For a professional

A declined transaction slip lists the reason code, amount, and merchant, not just "no." The bank encodes the failure as a structured record so downstream systems act correctly. That slip is an error object.

📮 Everyday version

A returned letter stamped "no such address" versus one stamped "moved, forwarding expired." Both are undelivered, but the reason on the envelope decides your next move. The stamp is a typed error.

03 - How

How to build it

You do two things: define a hierarchy of error classes rooted in one domain base, and decide per operation whether to raise them (for truly exceptional, non-local failures) or return them as a Result (for expected, business-level outcomes callers must handle inline).

🌳 Design the hierarchy

One base PaymentError so any handler can catch the whole domain. Leaf classes like InsufficientFunds and CardExpired add fields specific to their case. Depth pays for itself the first time you route on it.

🔀 Raise vs. return

Raise when the caller usually cannot recover here and wants it to bubble (a gateway outage). Return a Result when the failure is an ordinary business outcome the immediate caller must branch on (a declined card).

Define the error class, raise it, and handle it

// A domain error is a real class: named, typed, context-carrying.
class PaymentError extends Error {
  constructor(
    message: string,
    readonly amount: number,
    readonly currency: string,
  ) {
    super(message);
    this.name = new.target.name; // keeps the leaf class name
  }
}

class InsufficientFunds extends PaymentError {
  constructor(amount: number, currency: string, readonly shortfall: number) {
    super(`Short by ${shortfall} ${currency}`, amount, currency);
  }
}

class CardExpired extends PaymentError {
  constructor(amount: number, currency: string, readonly expiry: string) {
    super(`Card expired ${expiry}`, amount, currency);
  }
}

class PaymentGateway {
  charge(cardBalance: number, expiry: string, amount: number): string {
    if (expiry < "2026-07") throw new CardExpired(amount, "USD", expiry);
    if (cardBalance < amount)
      throw new InsufficientFunds(amount, "USD", amount - cardBalance);
    return `receipt_${Date.now()}`; // charge succeeded
  }
}

// Handle by TYPE, not by parsing a message.
const gateway = new PaymentGateway();
try {
  const receipt = gateway.charge(40, "2027-01", 99.5);
  console.log("Charged:", receipt);
} catch (err) {
  if (err instanceof InsufficientFunds) {
    console.log(`Ask for ${err.shortfall} ${err.currency} more`);
  } else if (err instanceof CardExpired) {
    console.log(`Prompt to update card (was ${err.expiry})`);
  } else if (err instanceof PaymentError) {
    console.log("Generic payment failure:", err.message);
  } else {
    throw err; // not ours - let it bubble
  }
}

class PaymentError(Exception):
    def __init__(self, message: str, amount: float, currency: str):
        super().__init__(message)
        self.amount = amount
        self.currency = currency


class InsufficientFunds(PaymentError):
    def __init__(self, amount: float, currency: str, shortfall: float):
        super().__init__(f"Short by {shortfall} {currency}", amount, currency)
        self.shortfall = shortfall


class CardExpired(PaymentError):
    def __init__(self, amount: float, currency: str, expiry: str):
        super().__init__(f"Card expired {expiry}", amount, currency)
        self.expiry = expiry

# A domain error is a real class: named, typed, context-carrying.
class PaymentError < StandardError
  attr_reader :amount, :currency

  def initialize(message, amount:, currency:)
    super(message)
    @amount = amount
    @currency = currency
  end
end

class InsufficientFunds < PaymentError
  attr_reader :shortfall

  def initialize(amount:, currency:, shortfall:)
    super("Short by #{shortfall} #{currency}", amount: amount, currency: currency)
    @shortfall = shortfall
  end
end

class CardExpired < PaymentError
  attr_reader :expiry

  def initialize(amount:, currency:, expiry:)
    super("Card expired #{expiry}", amount: amount, currency: currency)
    @expiry = expiry
  end
end

class PaymentGateway
  def charge(card_balance:, expiry:, amount:)
    raise CardExpired.new(amount: amount, currency: "USD", expiry: expiry) if expiry < "2026-07"
    if card_balance < amount
      raise InsufficientFunds.new(amount: amount, currency: "USD", shortfall: amount - card_balance)
    end
    "receipt_#{amount}" # charge succeeded
  end
end

# Handle by TYPE, not by parsing a message.
gateway = PaymentGateway.new
begin
  receipt = gateway.charge(card_balance: 40, expiry: "2027-01", amount: 99.5)
  puts "Charged: #{receipt}"
rescue InsufficientFunds => err
  puts "Ask for #{err.shortfall} #{err.currency} more"
rescue CardExpired => err
  puts "Prompt to update card (was #{err.expiry})"
rescue PaymentError => err
  puts "Generic payment failure: #{err.message}"
end

Notice each rescue / catch branch matches a class and then reads fields. The base PaymentError branch is a safety net for future leaf types you have not written yet, and re-raising anything foreign keeps unrelated bugs loud.

When failure is routine: return a Result instead of raising

// Result makes the failure visible in the signature - callers cannot forget it.
type Ok<T> = { ok: true; value: T };
type Err<E> = { ok: false; error: E };
type Result<T, E> = Ok<T> | Err<E>;

function authorize(balance: number, amount: number): Result<string, PaymentError> {
  if (balance < amount)
    return { ok: false, error: new InsufficientFunds(amount, "USD", amount - balance) };
  return { ok: true, value: `auth_${amount}` };
}

const res = authorize(40, 99.5);
if (res.ok) {
  console.log("Authorized:", res.value);
} else {
  console.log("Declined:", res.error.message); // typed error, no throw
}
# Result makes the failure visible in the signature - callers cannot forget it.
from dataclasses import dataclass
from typing import Generic, TypeVar, Union

T = TypeVar("T")
E = TypeVar("E")


@dataclass
class Ok(Generic[T]):
    value: T


@dataclass
class Err(Generic[E]):
    error: E


Result = Union[Ok[T], Err[E]]


def authorize(balance: float, amount: float) -> Result[str, PaymentError]:
    if balance < amount:
        return Err(InsufficientFunds(amount, "USD", amount - balance))
    return Ok(f"auth_{amount}")


res = authorize(40, 99.5)
if isinstance(res, Ok):
    print("Authorized:", res.value)
else:
    print("Declined:", res.error)  # typed error, no raise
# Result makes the failure visible in the return value - callers must branch on it.
Ok  = Struct.new(:value)
Err = Struct.new(:error)

def authorize(balance:, amount:)
  if balance < amount
    return Err.new(InsufficientFunds.new(amount: amount, currency: "USD", shortfall: amount - balance))
  end
  Ok.new("auth_#{amount}")
end

res = authorize(balance: 40, amount: 99.5)
case res
when Ok  then puts "Authorized: #{res.value}"
when Err then puts "Declined: #{res.error.message}" # typed error, no raise
end

Same error classes, different delivery. Raising suits failures that should abort a deep call chain; returning a Result suits expected outcomes the immediate caller must confront before touching the value. The error object is identical either way - only its transport changes.

05 - Step by Step

The 0 → 100 flow

From a boolean-returning function to a fully typed error model routed at the edge - the whole journey in order.

00
Smell

Spot the stringly-typed failure

The charge function returns false or throws a bare string. Callers guess the reason, and every new decline case adds another fragile if message.includes(...).

10
Base

Create one domain base class

Define PaymentError extending the language's exception type. Every payment failure will descend from it so a single handler can catch the whole family.

20
Fields

Give the base shared context

Add amount, currency, and a retryable flag to the base so context that every payment failure shares lives in exactly one place.

30
Leaves

Name each distinct failure

Subclass into InsufficientFunds, CardExpired, GatewayUnavailable. Each carries the fields specific to its case, like shortfall or statusCode.

40
Raise

Throw the specific type at the origin

The gateway constructs and raises the precise leaf class the moment it detects the condition, capturing the facts it already has on hand.

50
Propagate

Let it bubble unchanged

Intermediate layers do not swallow or rewrap it. The object travels up with its type and context intact until a layer that can decide catches it.

60
Catch

Handle by class, not by message

The boundary matches on InsufficientFunds vs CardExpired and reads their fields, giving each a tailored user response.

70
Net

Keep a base-class safety branch

A final catch PaymentError handles any leaf you have not special-cased yet, so new error types degrade gracefully instead of leaking raw.

80
Choose

Decide raise vs. Result per call

For expected business outcomes callers must confront, return a Result<Receipt, PaymentError> so the failure shows up in the signature.

90
Log

Serialize the object, not a sentence

A toLog() method emits structured fields (code, amount, gatewayRef) so dashboards can group and alert on failure types precisely.

100
Evolve

Add new failures without breaking callers

Introduce FraudSuspected under PaymentDeclined. Old base-class handlers still work; new handlers opt into the finer case when they are ready.

Common Pitfalls

Pitfalls & anti-patterns

Modeling errors well is easy to get subtly wrong. These are the recurring mistakes.

🕳️ Catch-all swallowing

A bare catch (e) {} or rescue => e that logs and moves on hides InsufficientFunds next to a real NullPointer. Catch the narrowest type you can actually handle.

🧵 Stringly-typed reasons

Branching on if err.message.includes("declined") shatters the moment someone rewords the message or localizes it. Match on the class, never the prose.

🥞 One giant error class

A single AppError with a type string field is just an enum in disguise. You lose instanceof routing and per-case fields. Prefer real subclasses.

📭 Context stripped on rethrow

Catching a rich error and rethrowing new Error("payment failed") deletes the decline code and cause. Wrap with a cause, never flatten to a string.

🚦 Exceptions for control flow

Throwing to signal an ordinary, expected outcome (an empty cart) abuses the stack-unwinding machinery. Reserve raising for the genuinely exceptional; return a Result otherwise.

🌊 Over-deep hierarchies

Ten levels of abstract error classes nobody ever catches individually is ceremony, not clarity. Add a subclass only when some handler will branch on it.

Signals & Metrics

Signals & how to measure

Whether your error model is pulling its weight shows up in the code and in production telemetry.

SignalWhat it tells you
Ratio of typed catches to bare catchesHigh typed ratio means handlers act on specific failures; many bare catches mean failure detail is being thrown away.
String matching on error messagesAny message.includes(...) in control flow is a signal the failure should have been a distinct type instead.
Error types present in log dashboardsIf you can group incidents by class name and field, your errors carry enough structure. If everything is "Error," they do not.
Rethrows that lose the causeWrapping without preserving cause breaks stack traces and hides root causes during on-call debugging.
New failure added without touching callersIf a new leaf type slots under an existing base and old handlers still compile and behave, your hierarchy is well factored.
Result types in fallible signaturesFallible operations whose signatures admit failure force callers to handle it; hidden throws let callers forget.
Rule of thumb: if a human reading a catch block cannot tell what failed without opening the function that threw, the error needed to be a richer object. Name the failure, carry its context, and route on its type.
06 - Case Studies

Real-world case studies

Three production systems where errors-as-objects is load-bearing.

💳

1 · Stripe-style payment API error taxonomy

Pattern: typed decline codes carrying context

A payments platform must tell integrators exactly why a charge failed so their apps react correctly, not just "it did not work."

  • A CardError base splits into card_declined, expired_card, insufficient_funds, each with a machine-readable decline_code.
  • Every error object carries the request id, the amount, and whether a retry could plausibly succeed.
  • SDKs in each language surface the same taxonomy as native exception classes callers catch by type.
✅ Outcome: Integrators write precise recovery flows (retry vs. prompt vs. abandon) because the failure arrives as structured, typed data instead of an opaque status.
✅

2 · Form validation returning many typed errors

Pattern: aggregate error objects over throwing

A signup service must report every invalid field at once, not fail fast on the first bad input.

  • Each rule yields a ValidationError subclass (Required, TooShort, NotUnique) with the offending field and a stable code.
  • The validator returns a Result holding a list of error objects, so nothing is raised for ordinary bad input.
  • The API layer serializes each error's field and code into a JSON response the front end maps to inline messages.
✅ Outcome: Users see all their mistakes in one pass, and the front end renders messages from stable codes rather than parsing English sentences.
🦀

3 · Rust and Go steering the whole industry to Result

Pattern: failure encoded in the return type

Two mainstream languages deliberately made fallibility part of the signature rather than a hidden side channel.

  • Rust's Result<T, E> and Go's explicit error return force every caller to confront failure at the call site.
  • Custom error enums and types carry context and let callers match on the specific variant.
  • The pattern pushed TypeScript, Kotlin, and Swift ecosystems toward typed-result libraries for expected failures.
✅ Outcome: Fewer forgotten failure paths and clearer APIs, because "this can fail, and here is how" is written into the type, not left to documentation or luck.
07 - Relevance

Modern relevance

Treating failure as first-class data is only getting more central as type systems and distributed systems mature.

🧬 Typed results going mainstream

TypeScript, Kotlin, and Swift ship or popularize Result-style types, making expected failure a visible part of signatures rather than a hidden throw.

🔗 Errors with a cause chain

Native cause support (JavaScript, Python's raise from) lets an error object wrap the one beneath it, preserving the full story from origin to boundary.

🌐 Structured errors across services

gRPC status details and Problem Details for HTTP (RFC 9457) carry typed, field-rich errors across the network, extending the object model past one process.

🔭 Observability keyed on error types

Tracing tools group and alert on error class and attributes. Rich error objects turn incident triage into a query instead of log grepping.

🛡️ Exhaustiveness checking

Union-typed errors let the compiler prove you handled every case, so adding a new failure variant surfaces every place that must adapt.

🤖 Machine-actionable failures

Agents and automated retries need failures they can branch on programmatically. A retryable flag on a typed object beats reading a message.

Bottom line: failure is a normal part of every real system, so model it like one. Give each distinct failure a name, let it carry the facts, place it in a hierarchy, and choose deliberately whether to raise it or return it. Errors as objects turn "something broke" into something your code, and your team, can actually reason about.
