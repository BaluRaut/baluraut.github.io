OOP Concept

Encapsulating collections - guard the list, don't hand it out

A class that owns a list of order line items, playlist tracks, or team members owns the rules about that list too. The moment you return the raw collection from a getter, any caller can add, remove, or clear it behind your back and your invariants quietly die. Encapsulating collections means exposing behavior, not the container: return copies or read-only views for reading, and mutate only through methods that enforce the rules.

01 - What

What is encapsulating collections?

Encapsulating a collection means the internal list, set, or map is a private implementation detail that the outside world never touches directly. Callers ask the object to do things - add a line item, remove a track, count members - and the object mutates its own collection while enforcing rules like uniqueness, totals, limits, and ordering. Reads hand back a copy or an unmodifiable view, never the live reference.

🔒 Hide the container

The field holding the list or map is private. There is no getter that returns it and no setter that swaps it. Callers cannot reach in.

👁️ Expose safe reads

Reading returns an immutable view or a fresh copy. Iterating or counting is fine; mutating the returned value must not touch the owner's state.

🛠️ Mutate through methods

addItem and removeItem are the only doors in. Each one validates input and re-checks invariants before the change sticks.

The moving parts

PieceWhat it doesTypical shape
Private backing fieldHolds the real collection, never sharedprivate items: LineItem[]

Key mental model: a getter that returns the internal collection is a public setter in disguise. If a caller can hold the reference, it can call .push(), .clear(), or reassign an element, and your object's rules never get a say.
02 - Why

Why encapsulate the collection

A collection is not just data; it is data plus the rules that keep it valid. Leaking the container splits the rules from the data and invites corruption from anywhere in the codebase.

🛡️ Invariants stay true

An order total that must equal the sum of its line items can only be trusted if every add and remove goes through the order. One direct push from outside and the cached total is a lie.

🧭 One place to change rules

Need a limit of 500 tracks per playlist, or to block duplicate SKUs? You add the check in one method instead of auditing every caller that ever touched the list.

🔎 Bugs have a short trail

When state can only change through named methods, a corrupt collection has a handful of suspects, not the whole application. You set breakpoints on the doors, not the walls.

🔀 Freedom to swap internals

Because nobody depends on it being an array, you can switch to a set for uniqueness or a map for fast lookup without breaking a single caller.

03 - How

How it works in code

Take an Order that owns its line items. The list is private. Reads return a read-only view. Adds and removes go through methods that validate and keep the total honest.

📥 Guard the writes

addItem validates quantity, merges duplicate SKUs, and enforces a max-item cap before the change is committed. Nothing bypasses it.

📤 Neuter the reads

lineItems returns a frozen or read-only sequence. Callers can loop and sum, but a stray push or clear either fails or hits a throwaway copy.

A class that guards its collection

class LineItem {
  constructor(
    readonly sku: string,
    readonly name: string,
    readonly unitPriceCents: number,
    readonly quantity: number,
  ) {}
  subtotalCents(): number {
    return this.unitPriceCents * this.quantity;
  }
}

class Order {
  // Private backing collection: no getter returns it, no setter replaces it.
  private readonly items: LineItem[] = [];

  constructor(private readonly maxItems = 100) {}

  addItem(sku: string, name: string, unitPriceCents: number, qty: number): void {
    if (qty <= 0) throw new Error("quantity must be positive");
    if (unitPriceCents < 0) throw new Error("price cannot be negative");

    const existing = this.items.find((i) => i.sku === sku);
    if (existing) {
      this.replace(sku, new LineItem(sku, name, unitPriceCents, existing.quantity + qty));
      return;
    }
    if (this.items.length >= this.maxItems) throw new Error("order is full");
    this.items.push(new LineItem(sku, name, unitPriceCents, qty));
  }

  removeItem(sku: string): void {
    const idx = this.items.findIndex((i) => i.sku === sku);
    if (idx === -1) throw new Error(`no line item for ${sku}`);
    this.items.splice(idx, 1);
  }

  changeQuantity(sku: string, qty: number): void {
    if (qty <= 0) { this.removeItem(sku); return; }
    const cur = this.items.find((i) => i.sku === sku);
    if (!cur) throw new Error(`no line item for ${sku}`);
    this.replace(sku, new LineItem(sku, cur.name, cur.unitPriceCents, qty));
  }

  // Read-only view: callers can iterate but cannot mutate our state.
  get lineItems(): readonly LineItem[] {
    return this.items as readonly LineItem[];
  }

  totalCents(): number {
    return this.items.reduce((sum, i) => sum + i.subtotalCents(), 0);
  }

  count(): number {
    return this.items.length;
  }

  private replace(sku: string, next: LineItem): void {
    const idx = this.items.findIndex((i) => i.sku === sku);
    this.items[idx] = next;
  }
}

from dataclasses import dataclass
from typing import Sequence


@dataclass(frozen=True)
class LineItem:
    sku: str
    name: str
    unit_price_cents: int
    quantity: int

    def subtotal_cents(self) -> int:
        return self.unit_price_cents * self.quantity


class Order:
    def __init__(self, max_items: int = 100) -> None:
        # Name-mangled backing list: no accessor returns it directly.
        self.__items: list[LineItem] = []
        self.__max_items = max_items

    def add_item(self, sku: str, name: str, unit_price_cents: int, qty: int) -> None:
        if qty <= 0:
            raise ValueError("quantity must be positive")
        if unit_price_cents < 0:
            raise ValueError("price cannot be negative")

        existing = self.__find(sku)
        if existing is not None:
            self.__replace(sku, LineItem(sku, name, unit_price_cents,
                                         existing.quantity + qty))
            return
        if len(self.__items) >= self.__max_items:
            raise ValueError("order is full")
        self.__items.append(LineItem(sku, name, unit_price_cents, qty))

    def remove_item(self, sku: str) -> None:
        item = self.__find(sku)
        if item is None:
            raise KeyError(f"no line item for {sku}")
        self.__items.remove(item)

    def change_quantity(self, sku: str, qty: int) -> None:
        if qty <= 0:
            self.remove_item(sku)
            return
        cur = self.__find(sku)
        if cur is None:
            raise KeyError(f"no line item for {sku}")
        self.__replace(sku, LineItem(sku, cur.name, cur.unit_price_cents, qty))

    @property
    def line_items(self) -> Sequence[LineItem]:
        # Read-only copy: mutating the tuple cannot touch our list.
        return tuple(self.__items)

    def total_cents(self) -> int:
        return sum(i.subtotal_cents() for i in self.__items)

    def count(self) -> int:
        return len(self.__items)

    def __find(self, sku: str) -> LineItem | None:
        return next((i for i in self.__items if i.sku == sku), None)

    def __replace(self, sku: str, nxt: LineItem) -> None:
        idx = next(i for i, it in enumerate(self.__items) if it.sku == sku)
        self.__items[idx] = nxt

LineItem = Struct.new(:sku, :name, :unit_price_cents, :quantity) do
  def subtotal_cents
    unit_price_cents * quantity
  end
end

class Order
  def initialize(max_items: 100)
    # Private backing array; no attr_accessor exposes it.
    @items = []
    @max_items = max_items
  end

  def add_item(sku, name, unit_price_cents, qty)
    raise ArgumentError, "quantity must be positive" if qty <= 0
    raise ArgumentError, "price cannot be negative"  if unit_price_cents < 0

    existing = find(sku)
    if existing
      replace(sku, LineItem.new(sku, name, unit_price_cents,
                                existing.quantity + qty))
      return
    end
    raise "order is full" if @items.size >= @max_items
    @items << LineItem.new(sku, name, unit_price_cents, qty)
  end

  def remove_item(sku)
    item = find(sku) or raise KeyError, "no line item for #{sku}"
    @items.delete(item)
  end

  def change_quantity(sku, qty)
    return remove_item(sku) if qty <= 0
    cur = find(sku) or raise KeyError, "no line item for #{sku}"
    replace(sku, LineItem.new(sku, cur.name, cur.unit_price_cents, qty))
  end

  # Frozen copy: callers iterate, but cannot mutate our state.
  def line_items
    @items.map(&:dup).freeze
  end

  def total_cents
    @items.sum(&:subtotal_cents)
  end

  def count
    @items.size
  end

  private

  def find(sku)
    @items.find { |i| i.sku == sku }
  end

  def replace(sku, nxt)
    idx = @items.index { |i| i.sku == sku }
    @items[idx] = nxt
  end
end

order.add_item("SKU-APT-12", "Aeropress filter", 899, 2)
order.add_item("SKU-APT-12", "Aeropress filter", 899, 1) # merges to qty 3
order.change_quantity("SKU-APT-12", 4)
puts "#{order.count} #{order.total_cents}" # 1 3596

# The leak that raises: pushing onto a frozen array is refused.
# order.line_items << something  # FrozenError

All three define Order, create one, and drive it only through methods. Adding the same SKU twice merges quantities instead of duplicating a row, and the total is always derived from the live items, never cached and left to rot. The read accessor hands back something the caller cannot use to corrupt the order: a readonly type in TypeScript, a tuple in Python, a frozen copy in Ruby.

05 - Step by Step

The 0 → 100 flow

From a naive exposed list to a fully guarded collection - the whole refactor in order.

00
Spot

Find the leaky getter

Search for accessors that return the raw array, list, or map. A get items() returning the field is the smell that starts it all.

10
Privatize

Make the field private

Mark the backing collection private and remove any setter that replaces the whole thing. Nobody outside gets the reference anymore.

20
Inventory

List how callers use it

Grep every call site. Group them into reads (iterate, count, sum) and writes (add, remove, clear, reorder). This becomes your method surface.

30
Reads

Add a read-only accessor

Return a readonly type, a tuple, or a frozen copy. Callers keep iterating; they just cannot mutate what they get back.

40
Queries

Push derived questions inward

Replace order.items.length and manual sums with order.count() and order.total(). Callers ask, they do not compute.

50
Writes

Add command methods

Create addItem and removeItem. Move every external mutation into them, one call site at a time.

60
Invariants

Enforce the rules inside

Validate quantity, block duplicates or merge them, cap the size. The checks that were scattered now live in one place.

70
Migrate

Rewrite each caller

Swap direct push/splice calls for the new methods. The compiler and failing tests point you at the stragglers.

80
Seal

Delete the raw getter

Remove the accessor that returned the live collection. Now the only paths in and out are the ones you control.

90
Prove

Test the guards

Write tests that try to break invariants: negative quantity, over the cap, duplicate SKU, and mutating the returned view. All should be rejected or harmless.

100
Evolve

Swap internals freely

With nobody depending on the shape, change the array to a set or map for uniqueness or fast lookup. Callers never notice.

Common Pitfalls

Pitfalls & anti-patterns

Encapsulating collections is easy to half-do. These are the leaks that slip through review.

🔓 Returning the live reference

A getter that returns the field itself, not a copy, hands callers a private setter. They can push, splice, or clear your state with zero validation.

🪟 Shallow copy, mutable elements

You copy the list but the elements are still shared mutable objects. A caller edits item.quantity in place and your total silently drifts. Copy deeply or make elements immutable.

🏗️ Leaking through the constructor

Storing the exact array a caller passed in means they still hold it and can mutate it later. Copy incoming collections on the way in, not just on the way out.

📊 Cached total that rots

Keeping a total field updated by hand only works if every mutation goes through you. One direct edit and the cache lies. Derive it, or update it only inside the guarded methods.

🧵 Iterator invalidation

Handing out a live iterator or view and then mutating the collection can throw or skip elements mid-loop. Snapshot before you expose, or forbid mutation during iteration.

🕳️ Anemic wrapper

Wrapping the list but adding getItems() that returns it anyway. The encapsulation is theater; the behavior still lives in the callers, not the object.

Signals & Metrics

Signals & how to measure

You cannot unit-test taste, but you can watch for the fingerprints of a leaked collection.

SignalWhat it tells you
Getter returns the fieldThe collection is leaked; any caller can mutate it. This is the primary smell to grep for.
Callers call .push/.add on a getter resultMutation logic lives outside the owner, so invariants are not enforced consistently.
Duplicated validation across call sitesThe same "reject empty / cap at N" check is copy-pasted; it belongs in one command method.
Bugs where state is wrong but no method looks guiltySomething mutated the collection behind the object's back through a leaked reference.
Cached aggregate disagrees with the itemsA total or count is maintained by hand while mutations bypass it. Strong sign of a leak.
Hard to change the data structureCallers depend on it being an array; a set or map swap breaks them. Encapsulation would have hidden the shape.
Rule of thumb: if you can point at a line outside the owning class that mutates its collection, the collection is not encapsulated. Reads leave the class as copies or read-only views; writes enter only through named methods.
06 - Case Studies

Real-world case studies

Three systems where guarding a collection is the difference between correct and corrupt.

🛒

1 · Checkout: Order and its line items

Pattern: totals derived from a guarded collection

An e-commerce order must keep its total, tax, and discounts consistent with its line items at all times.

  • Order exposes addItem, removeItem, and changeQuantity; the list is private.
  • Adding an existing SKU merges quantities so no duplicate rows appear on the receipt.
  • The total is derived from the items, so it can never disagree with what the customer sees.
✅ Outcome: pricing bugs where the shown total drifts from the charged amount disappear, because every mutation re-derives from the same source of truth.
🎵

2 · Music app: Playlist and its tracks

Pattern: ordering and limits as invariants

A streaming playlist must respect a maximum length, preserve order, and forbid the same track twice in a row.

  • Playlist.addTrack checks the cap and the no-adjacent-duplicate rule before inserting.
  • tracks returns a read-only view so the UI can render without being able to reorder state directly.
  • Reordering is a method that moves an index, keeping positions valid rather than trusting callers.
✅ Outcome: the client and server agree on track order and length limits, because only the playlist can change its own sequence.
👥

3 · Collaboration tool: Team and its members

Pattern: uniqueness and role invariants

A workspace team must always have at least one owner and never list the same user twice.

  • Team.addMember rejects duplicates and validates the role against allowed values.
  • removeMember refuses to remove the last owner, protecting the "always one owner" invariant.
  • members returns copies, so the permissions UI can iterate without demoting anyone by accident.
✅ Outcome: no orphaned teams and no duplicate seats on the bill, because membership rules are enforced in one guarded place.
07 - Relevance

Modern relevance

Guarding collections is not a legacy nicety; it underpins how modern systems stay correct under concurrency, immutability, and rich domain models.

🧱 Domain-driven aggregates

An aggregate root owns its child collection and is the only gateway for changing it. Encapsulating collections is exactly how aggregates protect their consistency boundary.

🧊 Immutability by default

Records, frozen dataclasses, and readonly types make elements safe to hand out. The trend is toward reads that literally cannot be mutated.

🔁 Concurrency safety

A leaked collection mutated from two threads is a data race. Keeping mutation inside guarded methods gives you one place to add locking or copy-on-write.

🧪 Testability

When state only changes through named methods, you assert on behavior, not on private fields. Guards become small, targeted unit tests.

🌐 API and DTO boundaries

Serializing an entity should project a copy, not expose the live model. The same discipline that guards the collection guards the wire format.

♻️ Event sourcing

State is rebuilt by applying events through methods, never by poking the collection. Encapsulation is a prerequisite for a trustworthy event log.

Bottom line: a collection is behavior wearing the costume of data. Hide the container, hand out copies or read-only views, and let every change pass through a method that keeps the rules. Do that and your invariants hold no matter who calls you.
