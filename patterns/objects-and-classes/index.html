OOP Concept

Objects & Classes - blueprints and the instances they stamp out

A class is a blueprint: it declares what data an object holds and what it can do. An object is a live instance built from that blueprint, with its own state and its own identity. Master this split and the rest of OOP - encapsulation, inheritance, polymorphism - all falls into place.

01 - What

What are objects and classes?

A class defines a type: the fields every instance will carry and the methods every instance can run. An object is one concrete instance of that type, created at runtime. Think of a shopping Cart class describing "a cart has line items and can add or total them," versus the actual cart Ada is filling right now with three items in it.

📐 Class = blueprint

A template written once. It names the fields and methods but holds no live data itself. class Cart { ... } is a plan, not a purchase.

🛒 Object = instance

A concrete thing built from the blueprint with new. Two carts made from the same class are two separate objects with independent contents.

🆔 Identity

Each object has its own reference. Two carts holding the same items are still distinct objects; equality of contents is not the same as being the same object.

The three things an object bundles

AspectWhat it meansCart example
State (fields)The data an instance holds right nowitems, currency, customerId

Key mental model: a class is a cookie cutter and objects are the cookies. The cutter defines the shape once; each cookie is its own physical thing with its own sprinkles. Changing one cookie never changes the cutter or the other cookies.
02 - Why

Why classes and objects exist

Bundling related data with the operations that act on it keeps a system understandable as it grows. Instead of loose dictionaries passed everywhere, you get named types that guard their own rules.

🧱 Modeling the domain

Classes let code mirror the business: an Account, a Cart, an Invoice. Readers map concepts to types instantly instead of decoding raw maps and tuples.

🔒 Invariants in one place

A balance can never go negative if only the Account's methods can touch it. The class becomes the single guardian of its own rules rather than scattering checks across the codebase.

♻️ Reuse without copy-paste

Define the blueprint once and stamp out thousands of instances. Every cart shares the same tested behavior; you fix a bug in one place, not per copy.

🧩 A vocabulary to build on

Objects and classes are the foundation the other pillars stand on: encapsulation hides fields, inheritance shares blueprints, polymorphism swaps instances behind a shared type.

In Plain Terms

Objects & Classes explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

A class is the syllabus; an object is your enrolled section. The syllabus lists what the course covers; your section has real students, a real room, and its own attendance. Many sections, one syllabus.

👩‍💻 For a developer

A class is a struct plus the functions that operate on it, glued together. The constructor is the factory function that returns an initialized value; methods are functions whose first hidden argument is the instance itself.

🏢 For a professional

A class is a job description; an object is the person hired into that role. The description defines responsibilities and data (title, salary band); each hire is a distinct individual doing the job.

🏦 Everyday version

A bank's account-opening form is the class: it dictates which fields exist and what you can do. Your actual account, with its own number and balance, is the object stamped from that form.

03 - How

How it works under the hood

Defining a class registers a type. Calling the constructor allocates a fresh object, runs the initializer to set its fields, and hands back a reference. Method calls then dispatch through that reference using this or self to reach the instance's own state.

🏗️ Instance members

Fields and methods that belong to each object. this.balance is per-instance; every Account has its own. Methods read and mutate the state of the specific object they were called on.

📌 Static / class members

Data and behavior owned by the class itself, shared across all instances: constants like Account.MIN_BALANCE, counters, or factory methods like Account.open() that build and return new objects.

A real class, an object, and its methods in three languages

// A bank Account: state, behavior, identity, and a static factory.
class Account {
  // static/class member: shared by every instance
  static readonly MIN_BALANCE = 0;
  private static nextId = 1;

  // instance state (fields)
  readonly id: number;
  private balance: number;

  // constructor: initializes a fresh instance
  constructor(private readonly owner: string, opening: number) {
    if (opening < Account.MIN_BALANCE) {
      throw new Error("Opening balance cannot be negative");
    }
    this.id = Account.nextId++;   // identity, assigned once
    this.balance = opening;
  }

  // behavior: methods act on this instance's state via `this`
  deposit(amount: number): void {
    this.balance += amount;
  }

  withdraw(amount: number): void {
    if (amount > this.balance) throw new Error("Insufficient funds");
    this.balance -= amount;
  }

  getBalance(): number {
    return this.balance;
  }

  // static factory method: builds and returns a new object
  static open(owner: string): Account {
    return new Account(owner, 0);
  }
}

// create objects (instances) from the blueprint
const ada = new Account("Ada Lovelace", 100);
const liam = Account.open("Liam Reyes");

// call methods on each independent object
ada.deposit(50);
ada.withdraw(30);

console.log(ada.id, ada.getBalance());   // 1 120
console.log(liam.id, liam.getBalance()); // 2 0
console.log(ada === liam);               // false: distinct identities

# A bank Account: state, behavior, identity, and a static factory.
class Account:
    # class member: shared by every instance
    MIN_BALANCE = 0
    _next_id = 1

    # constructor: initializes a fresh instance
    def __init__(self, owner: str, opening: float):
        if opening < Account.MIN_BALANCE:
            raise ValueError("Opening balance cannot be negative")
        self.id = Account._next_id      # identity, assigned once
        Account._next_id += 1
        self._owner = owner
        self._balance = opening         # instance state (fields)

    # behavior: methods act on this instance via `self`
    def deposit(self, amount: float) -> None:
        self._balance += amount

    def withdraw(self, amount: float) -> None:
        if amount > self._balance:
            raise ValueError("Insufficient funds")
        self._balance -= amount

    def get_balance(self) -> float:
        return self._balance

    # classmethod factory: builds and returns a new object
    @classmethod
    def open(cls, owner: str) -> "Account":
        return cls(owner, 0)

# A bank Account: state, behavior, identity, and a static factory.
class Account
  MIN_BALANCE = 0            # class-level constant, shared by all
  @next_id = 1              # class-level state

  class << self
    attr_accessor :next_id   # class member accessors
  end

  attr_reader :id            # expose identity, keep balance private

  # constructor: initializes a fresh instance
  def initialize(owner, opening)
    raise ArgumentError, "Opening balance cannot be negative" if opening < MIN_BALANCE

    @id = self.class.next_id           # identity, assigned once
    self.class.next_id += 1
    @owner = owner
    @balance = opening                 # instance state (fields)
  end

  # behavior: methods act on this instance via `self`/@ivars
  def deposit(amount)
    @balance += amount
  end

  def withdraw(amount)
    raise "Insufficient funds" if amount > @balance

    @balance -= amount
  end

  def balance
    @balance
  end

  # class method factory: builds and returns a new object
  def self.open(owner)
    new(owner, 0)
  end
end

# create objects (instances) from the blueprint
ada  = Account.new("Ada Lovelace", 100)
liam = Account.open("Liam Reyes")

# call methods on each independent object
ada.deposit(50)
ada.withdraw(30)

puts "#{ada.id} #{ada.balance}"    # 1 120
puts "#{liam.id} #{liam.balance}"  # 2 0
puts ada.equal?(liam)              # false: distinct identities

All three define the same blueprint, stamp out two independent objects, and mutate each one's private balance through its own methods. Notice how this (TypeScript), self (Python), and instance variables (Ruby) all point at the specific object a method runs on, while MIN_BALANCE and the open factory live on the class, shared by every instance.

05 - Step by Step

The 0 → 100 flow

From naming a concept to holding a live, working object that guards its own rules - the whole journey in order.

00
Model

Spot a concept worth a type

You notice "a cart" or "an account" keeps recurring in the domain. That recurring noun, with its data and its rules, is a candidate class.

10
Fields

Decide the state

List what each instance must remember: a cart's items and currency, an account's owner and balance. These become the instance fields.

20
Behavior

Decide the methods

List what the object can do to its own state: addItem, total, deposit, withdraw. Behavior lives with the data it touches.

30
Invariants

Name the rules

Write down what must always hold: balance never negative, quantity always positive. The class will enforce these so no caller can break them.

40
Blueprint

Declare the class

Write class Account { ... } with its fields and method signatures. Nothing runs yet; you have only defined the type.

50
Constructor

Write the initializer

Define how a fresh instance sets itself up: validate inputs, assign an identity, seed the starting state. This is the one entry point to a valid object.

60
Instantiate

Create an object

Call new Account("Ada", 100). Memory is allocated, the constructor runs, and you get back a reference to a live instance.

70
Identity

The object is its own thing

Each instance carries a distinct reference. A second account with the same balance is still a separate object; equality of data is not sameness of identity.

80
Invoke

Call its methods

Send messages: ada.deposit(50). Inside, this/self refers to this object, so only ada's balance changes.

90
Static

Reach for class-level members

Use shared constants and factories: Account.MIN_BALANCE, Account.open(...). These belong to the class, not any single instance.

100
Compose

Objects collaborate

Instances hold and call other instances - a cart holds line items, an order references an account. From these blueprints you build the whole system.

Common Pitfalls

Pitfalls & anti-patterns

Most trouble with objects and classes comes from blurring the blueprint/instance line or leaking state that the class should guard.

🩹 Anemic classes

A class that is only public fields with no behavior is just a struct in disguise. Logic then leaks into every caller, and invariants go unguarded. Put the methods where the data lives.

🌐 Global mutable statics

Stashing per-request data in static fields makes all instances share it, causing cross-talk between users. Statics are for constants and factories, not for holding instance state.

🪢 Misusing this/self

Passing a method as a bare callback in TypeScript loses its this binding; the instance vanishes at call time. Bind it or use arrow methods so behavior keeps its object.

🧨 Constructors that do too much

A constructor firing network calls or heavy work makes objects hard to build and test. Keep it to validating inputs and setting state; move side effects to a factory or an explicit method.

🎭 Confusing equality with identity

Comparing objects with == when you meant "same instance," or reference-comparing when you meant "same value," causes subtle bugs. Decide which you need and implement it deliberately.

🏰 God objects

One class that models the whole domain - a Cart that also does payments, shipping, and email - becomes unchangeable. Split responsibilities across focused, collaborating classes.

Signals & Metrics

Signals & how to measure

You rarely score "objects" directly, but these signals tell you whether your classes are pulling their weight.

SignalWhat it tells you
Methods per class vs public fieldsLots of exposed fields and few methods suggests anemic, behavior-less classes leaking logic to callers.
Invariant violations reaching productionIf invalid objects (negative balances, empty required fields) exist at runtime, construction or methods are not guarding state.
Places that mutate an object's fields directlyMany external writers to a field mean encapsulation is broken and the class no longer owns its own state.
Constructor complexity / side effectsHeavy or effectful constructors show objects are hard to create and test in isolation.
Static state that changes at runtimeMutable statics beyond constants signal hidden shared state and likely concurrency bugs.
Class size and responsibilitiesGrowing line count and many unrelated methods hint at a god object that should be split.
Rule of thumb: a healthy class can only be created in a valid state and can only be changed through its own methods. If callers can build a broken instance or poke its fields directly, the blueprint is not doing its job.
06 - Case Studies

Real-world case studies

Three production-style systems where the class/object split does real work.

🛒

1 · Checkout carts in an e-commerce backend

Pattern: one class, millions of independent instances

A retail platform models each shopper's cart as an instance of a single Cart class serving traffic concurrently.

  • Every active session holds its own Cart object with private line items and totals; instances never share state.
  • addItem and applyCoupon enforce quantity and stock invariants inside the class, not in controllers.
  • A static Cart.fromSavedOrder factory rebuilds a cart from a stored order, keeping construction rules in one place.
✅ Outcome: Thousands of concurrent carts stay isolated and consistent, because each is a distinct object guarding its own contents.
🏦

2 · Ledger accounts in a banking core

Pattern: identity and invariants as first-class concerns

A payments system represents each customer balance as an Account object with a stable identity across the ledger.

  • Each account has an immutable id assigned at construction; transfers reference accounts by identity, never by matching balances.
  • debit and credit are the only paths that change the balance, so the "never overdraw" rule holds everywhere.
  • Class-level constants (minimum balance, currency precision) live as static members shared by every account.
✅ Outcome: Money movements stay auditable and correct because identity and invariants are enforced by the object itself.
🔔

3 · Notification messages in a delivery service

Pattern: value-carrying objects created by factories

A notifications platform builds a Notification object per outbound message across email, SMS, and push.

  • Each message is an instance with its own recipient, channel, and payload; the class validates required fields in its constructor.
  • Static factories like Notification.forPasswordReset assemble correctly shaped instances for common events.
  • Behavior such as render and markSent operates only on that instance's state via this.
✅ Outcome: Millions of independent message objects flow through the pipeline, each self-contained and impossible to construct half-formed.
07 - Relevance

Modern relevance

Even amid functional and data-oriented styles, the class/object distinction remains a core way to structure state and behavior.

🧊 Immutable objects & records

Modern languages favor objects you construct valid and never mutate. The blueprint idea stays; you swap in-place edits for producing new instances.

🧬 Data classes & case classes

Concise class syntax in Python, Kotlin, and Scala keeps the type and its data but cuts boilerplate, making small value objects cheap to define.

🧭 Domain-driven design

Entities (identity matters) versus value objects (only the data matters) is exactly the class/object/identity split applied to real domains.

⚙️ Objects at service boundaries

Even functional cores wrap I/O and connections - clients, sessions, repositories - as objects, because they carry state and behavior naturally.

🧰 Composition over deep hierarchies

Teams now build objects by combining small collaborators rather than long inheritance chains, but the unit of composition is still the class.

🔎 Type systems reward good classes

Rich types and pattern matching make well-defined classes safer and more expressive, catching invalid instances at compile time.

Bottom line: classes and objects are the alphabet of OOP. Get the blueprint-versus-instance distinction, the state/behavior/identity trio, and the instance-versus-static split right, and every higher pattern becomes a natural sentence built from them.
