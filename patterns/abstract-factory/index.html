Creational Pattern

Abstract Factory - families of objects that belong together

Some objects only make sense together: a Windows button with a Windows checkbox, a dark-theme card with a dark-theme scrollbar. Abstract Factory hands you one factory per family so you can create whole sets of related products without naming a single concrete class, and it guarantees that everything you build comes from the same family.

01 - What

What is Abstract Factory?

Abstract Factory provides an interface for creating families of related or dependent objects without specifying their concrete classes. Client code talks only to abstract product interfaces (Button, Checkbox) and one abstract factory interface (GUIFactory). At runtime you plug in a single concrete factory (WindowsFactory or MacFactory), and every product it produces is guaranteed to belong to the same family.

🏭 The abstract factory

An interface with one create method per product kind: createButton(), createCheckbox(). It names what can be built, never the concrete type.

👪 Product families

Each concrete factory produces one coherent set. A MacFactory only ever returns Mac widgets, so a Mac button never sits next to a Windows checkbox.

🔌 Client stays blind

The client is handed a factory and abstract products. It never sees new WindowsButton(), so it works with any family you inject.

The core roles

RoleWhat it doesExample
Abstract FactoryDeclares creation methods for each abstract productGUIFactory
Concrete FactoryImplements those methods for one familyWindowsFactory, MacFactory
Abstract ProductInterface the client depends onButton, Checkbox
Concrete ProductA family-specific implementationWindowsButton, MacCheckbox
ClientUses factory + products through interfaces onlyApplication
Key mental model: Factory Method makes one product through inheritance. Abstract Factory makes a set of related products through composition. You inject one factory and get a matched suite, never a mismatched pair.
02 - Why

Why Abstract Factory exists

The moment your code scatters new ConcreteThing() calls across many files, swapping the whole family becomes a search-and-replace nightmare, and nothing stops you from mixing incompatible parts. Abstract Factory centralizes the choice of family into one object.

🧩 Guarantees compatibility

Because one factory builds the whole set, products always match. You cannot accidentally pair a dark-theme scrollbar with a light-theme panel - the type system won't let a factory return mixed parts.

🔀 Swap families in one line

Choosing Windows vs Mac, or MySQL vs Postgres, becomes a single decision at startup: pick the concrete factory. The rest of the app never changes.

🚪 Decouples client from concretes

Client code depends only on interfaces, honoring the Dependency Inversion Principle. Adding a new family does not touch existing client code.

🎯 Single Responsibility

Object creation lives in factories, not smeared through business logic. Construction rules for a family sit in one place, easy to find and test.

In Plain Terms

Abstract Factory explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It's like a themed stationery set. Pick the "space" set and you get a space notebook, space pen, and space folder that all match. Pick "ocean" and everything switches together. You never end up with an ocean pen in a space folder.

👩‍💻 For a developer

It's a toolbox interface with interchangeable brands. Your code calls toolbox.getWrench() and toolbox.getDrill(). Hand it the DeWalt toolbox or the Makita toolbox at startup; the calling code is identical either way.

🏢 For a professional

Think of a furniture catalog by collection. A hotel orders the "Modern" collection and gets a matching chair, sofa, and table. Switching to "Victorian" reorders the whole coordinated set from one supplier, guaranteeing they look right together.

🍔 Everyday version

A fast-food combo meal. Order "combo 2" and the kitchen assembles a specific burger, side, and drink that go together. You choose the combo, not each item, and the crew guarantees the set is consistent.

03 - How

How it works under the hood

You define abstract interfaces for the factory and for each product. Concrete factories implement the factory interface, returning concrete products of a single family. The client receives one factory and builds everything through it.

🧱 Define the contracts

Write a Button and Checkbox interface, then a GUIFactory interface with a create method for each. These are the only types the client will ever import.

🎚️ Wire the family at the edge

At startup, detect the OS or config and instantiate the matching concrete factory once. Inject it into the client so the choice of family is made in exactly one spot.

A realistic implementation

// Abstract products - the client depends only on these
interface Button   { render(): void; }
interface Checkbox { toggle(): void; }

// Abstract factory - one create method per product kind
interface GUIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

// Family 1: Windows
class WindowsButton   implements Button   { render() { console.log("[ Win Button ]"); } }
class WindowsCheckbox implements Checkbox { toggle() { console.log("Win check toggled"); } }
class WindowsFactory  implements GUIFactory {
  createButton(): Button     { return new WindowsButton(); }
  createCheckbox(): Checkbox { return new WindowsCheckbox(); }
}

// Family 2: macOS
class MacButton   implements Button   { render() { console.log("( Mac Button )"); } }
class MacCheckbox implements Checkbox { toggle() { console.log("Mac check toggled"); } }
class MacFactory  implements GUIFactory {
  createButton(): Button     { return new MacButton(); }
  createCheckbox(): Checkbox { return new MacCheckbox(); }
}

// Client - never mentions a concrete product
class Application {
  private button: Button;
  private checkbox: Checkbox;
  constructor(factory: GUIFactory) {      // family injected once
    this.button   = factory.createButton();
    this.checkbox = factory.createCheckbox();
  }
  paint() { this.button.render(); this.checkbox.toggle(); }
}

const factory: GUIFactory =
  process.platform === "darwin" ? new MacFactory() : new WindowsFactory();
new Application(factory).paint();          // matched family, guaranteed
from abc import ABC, abstractmethod
import sys

# Abstract products - the client depends only on these
class Button(ABC):
    @abstractmethod
    def render(self) -> None: ...

class Checkbox(ABC):
    @abstractmethod
    def toggle(self) -> None: ...

# Abstract factory - one create method per product kind
class GUIFactory(ABC):
    @abstractmethod
    def create_button(self) -> Button: ...
    @abstractmethod
    def create_checkbox(self) -> Checkbox: ...

# Family 1: Windows
class WindowsButton(Button):
    def render(self): print("[ Win Button ]")
class WindowsCheckbox(Checkbox):
    def toggle(self): print("Win check toggled")
class WindowsFactory(GUIFactory):
    def create_button(self) -> Button:     return WindowsButton()
    def create_checkbox(self) -> Checkbox: return WindowsCheckbox()

# Family 2: macOS
class MacButton(Button):
    def render(self): print("( Mac Button )")
class MacCheckbox(Checkbox):
    def toggle(self): print("Mac check toggled")
class MacFactory(GUIFactory):
    def create_button(self) -> Button:     return MacButton()
    def create_checkbox(self) -> Checkbox: return MacCheckbox()

# Client - never mentions a concrete product
class Application:
    def __init__(self, factory: GUIFactory):   # family injected once
        self.button   = factory.create_button()
        self.checkbox = factory.create_checkbox()
    def paint(self):
        self.button.render()
        self.checkbox.toggle()

factory = MacFactory() if sys.platform == "darwin" else WindowsFactory()
Application(factory).paint()               # matched family, guaranteed
# Abstract products - duck-typed, the client relies only on these methods
module Button;   def render; raise NotImplementedError; end; end
module Checkbox; def toggle; raise NotImplementedError; end; end

# Family 1: Windows
class WindowsButton;   include Button;   def render; puts "[ Win Button ]"; end; end
class WindowsCheckbox; include Checkbox; def toggle; puts "Win check toggled"; end; end
class WindowsFactory
  def create_button   = WindowsButton.new
  def create_checkbox = WindowsCheckbox.new
end

# Family 2: macOS
class MacButton;   include Button;   def render; puts "( Mac Button )"; end; end
class MacCheckbox; include Checkbox; def toggle; puts "Mac check toggled"; end; end
class MacFactory
  def create_button   = MacButton.new
  def create_checkbox = MacCheckbox.new
end

# Client - never mentions a concrete product
class Application
  def initialize(factory)                  # family injected once
    @button   = factory.create_button
    @checkbox = factory.create_checkbox
  end
  def paint
    @button.render
    @checkbox.toggle
  end
end

factory = RUBY_PLATFORM.include?("darwin") ? MacFactory.new : WindowsFactory.new
Application.new(factory).paint             # matched family, guaranteed

Notice that Application never writes new WindowsButton(). It receives a GUIFactory and gets a coherent set. Choosing the family happens once, in main, so the widgets can never be mismatched.

05 - Step by Step

The 0 → 100 flow

From a tangle of hardcoded constructors to a clean, swappable family of products - the whole journey in order.

00
Spot

Notice related objects

You see a group of objects that must vary together: button, checkbox, and menu that all need to match one platform or theme.

10
Group

Map the product families

List the product kinds down one axis (Button, Checkbox) and the families across the other (Windows, Mac). The grid defines what you must build.

20
Abstract

Declare product interfaces

Write one interface per product kind - Button, Checkbox - capturing only the behavior clients rely on.

30
Contract

Declare the factory interface

Create GUIFactory with a create method returning each abstract product. This is the single seam the client depends on.

40
Implement

Build concrete products

Implement each product for every family: WindowsButton, MacButton, and so on. Each is family-specific but honors the shared interface.

50
Assemble

Build one factory per family

Write WindowsFactory and MacFactory. Each returns only its own family's concrete products, guaranteeing internal consistency.

60
Inject

Pass the factory to the client

Refactor the client to accept a GUIFactory in its constructor instead of calling new directly. Now it is family-agnostic.

70
Select

Choose the family at the edge

At startup, read the OS, config, or feature flag and instantiate the one matching concrete factory. This is the only place the concrete type appears.

80
Create

Client builds a matched set

The client calls createButton() and createCheckbox(). Every returned object comes from the same family, so nothing clashes.

90
Extend

Add a whole new family

Need a Linux look? Add LinuxFactory plus its products. No existing client or factory changes - the open/closed principle in action.

100
Ship

Swap families freely

Switching platform or theme is now a one-line change to which factory you construct. The app runs identically, always with a coherent set.

Common Pitfalls

Pitfalls & anti-patterns

Abstract Factory pays off with stable families and multiple platforms. Reach for it too early and you drown in ceremony.

🥱 Premature abstraction

If you only ever have one family, the extra interfaces are pure overhead. A plain constructor is clearer until a second family actually appears.

➕ New product = touch everything

Adding a product kind means changing the factory interface and every concrete factory. Families are easy to add; products are expensive. Design the product axis carefully up front.

🔎 Leaking concrete types

If client code downcasts to WindowsButton or checks instanceof, the abstraction is broken and the consistency guarantee is gone.

🧨 Class explosion

With M product kinds and N families you get M x N concrete classes plus N factories. On large grids this balloons fast and gets hard to navigate.

🔀 Confusing it with Factory Method

Using inheritance and a subclass per product when you actually need a family of products, or vice versa, leads to awkward, forced hierarchies.

🌍 Global factory singleton

Reaching for a hidden global factory instead of injecting it hides the dependency, hurts testability, and makes swapping families at runtime awkward.

Trade-offs

Trade-offs & when to use

Abstract Factory buys consistency and swappability at the cost of upfront structure. Weigh it against how many families you truly need.

AspectDetail
ProsGuarantees products from one family are used together; decouples client from concrete classes; isolates construction; adding a new family is trivial and closed to existing code.
ConsMany interfaces and classes even for small grids; adding a new product kind ripples through the factory interface and every concrete factory; can feel like heavy ceremony.
Use whenYour system must work with several families of related products (cross-platform UI, multiple DB backends, themes) and you want to enforce that a family is never mixed.
Avoid whenThere is only one family, or products are unrelated and vary independently. A simple factory or plain constructor is lighter and clearer.
ComplexityModerate. More moving parts than Factory Method, but each part is small. Cost scales with product kinds (hard to add) more than families (easy to add).
RelatedFactory Method (one product via inheritance), Builder (step-by-step assembly), Prototype (clone instead of construct), Bridge (separate abstraction from implementation).
Rule of thumb: Choose Abstract Factory when the set of product kinds is stable but the number of families will grow. If instead you keep adding new product kinds, the pattern fights you - reconsider the design.
06 - Case Studies

Real-world case studies

Three representative places where families of related objects must stay consistent.

🖥️

1 · Cross-platform UI toolkit

Pattern: one widget family per operating system

A desktop app must look native on Windows, macOS, and Linux without branching UI code everywhere.

  • A GUIFactory exposes createButton, createCheckbox, and createMenu.
  • One concrete factory per OS returns natively styled widgets from that platform.
  • The app detects the OS at startup and injects the matching factory once.
✅ Outcome: Every screen renders a consistent native look, and adding a new platform means writing one factory plus its widgets, with zero changes to existing screens.
🗄️

2 · Pluggable database backends

Pattern: a family of DB objects per vendor

An ORM must support MySQL and PostgreSQL, each needing its own connection, command, and dialect objects that must match.

  • A DbFactory creates Connection, Command, and QueryBuilder objects.
  • MySqlFactory and PostgresFactory return only their vendor's implementations.
  • Config picks the factory, so a Postgres command can never run on a MySQL connection.
✅ Outcome: Switching database vendors is a config change, and the type system prevents vendor-mismatched objects from ever being combined.
🎨

3 · Theming a design system

Pattern: coherent light and dark component sets

A web component library needs light and dark themes where every element - card, input, tooltip - matches the active theme.

  • A ThemeFactory produces styled cards, inputs, and tooltips.
  • LightThemeFactory and DarkThemeFactory each yield a fully coordinated set.
  • A single toggle swaps the factory, re-rendering the whole UI in one theme.
✅ Outcome: Themes stay internally consistent with no half-styled screens, and new themes drop in as additional factories without touching component logic.
07 - Relevance

Modern relevance

Abstract Factory is decades old, but the problem it solves - swapping coherent families behind a stable interface - is more common than ever.

💉 Dependency injection

Modern DI containers are Abstract Factory at scale: you bind an interface to an implementation set once, and the container wires a consistent family throughout the app.

☁️ Cloud provider abstraction

Libraries that target AWS, Azure, and GCP expose one factory per cloud so storage, queue, and secrets clients always come from the same provider.

🧪 Test doubles

Injecting a fake factory lets tests supply a whole family of stub products at once, keeping unit tests isolated from real platform code.

🔧 Feature-flagged rollouts

Swapping a factory behind a flag ships a new coherent implementation set to some users while everyone else keeps the old family.

🌐 Multi-tenant systems

Per-tenant factories deliver tenant-specific but internally consistent objects - billing, storage, and policy - selected by tenant at request time.

🧱 Functional variants

In languages with first-class functions, the factory can shrink to a record of constructor functions, but the family-consistency idea is identical.

Bottom line: Whenever you must swap a matched set of implementations behind one stable seam and guarantee they are never mixed, you are reaching for Abstract Factory - whether you call it that or a DI binding.
