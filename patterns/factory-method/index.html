Creational Pattern

Factory Method - let subclasses decide what to build

A class often knows when it needs to create an object but not which concrete class to instantiate. Factory Method defines an interface for creating an object and defers the choice of concrete type to subclasses. The caller works only against abstractions, so new product types slot in without touching the code that uses them.

01 - What

What is the Factory Method?

Factory Method is a creational pattern that defines a method for creating an object but lets subclasses override that method to decide which concrete class to instantiate. The parent class contains the workflow and calls the factory method as a placeholder; each subclass supplies a different product. The result is a class that operates on products without ever naming a concrete product type.

🏭 Creator

The class that declares the factory method. It contains core logic that uses the product but leaves the actual instantiation to a subclass.

📦 Product

The interface the created objects share. The Creator only ever depends on this abstraction, never on the concrete implementations.

🔧 Concrete Creator

A subclass that overrides the factory method to return a specific concrete product, wiring one variant into the shared workflow.

The four participants

RoleResponsibilityExample
ProductDeclares the interface of the objects the factory createsTransport
Concrete ProductA specific implementation of the product interfaceTruck, Ship
CreatorDeclares the factory method and uses its result in shared logicLogistics

Key mental model: Factory Method is a virtual constructor. The parent class writes an algorithm around "make a product here," and each subclass answers the "which product" question by overriding a single method. The rest of the code never changes.
02 - Why

Why the Factory Method exists

Scattering new ConcreteThing() across a codebase hard-wires it to specific classes. Every new variant then means hunting down and editing every construction site. Factory Method pulls that decision into one overridable place so the workflow stays stable while the products vary.

🔌 Decouples use from creation

Client code depends on the product interface, not concrete classes. You can add a new product by writing a new subclass, without editing existing callers.

🧩 Open for extension

New variants arrive as new Concrete Creators. Existing code is closed to modification, satisfying the open-closed principle in a natural way.

♻️ Reuses the surrounding workflow

The Creator holds shared logic - logging, validation, orchestration - once. Subclasses only override which object gets built, not the whole flow.

🧪 Easier to test

Override the factory method in a test subclass to inject a fake or stub product, so the surrounding algorithm can be exercised in isolation.

In Plain Terms

Factory Method explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Think of a fill-in-the-blank essay template. The teacher writes the structure and leaves a blank labeled "insert your example here." Every student keeps the same structure but fills the blank with a different, specific example.

👩‍💻 For a developer

It is an overridable constructor hook. The base class calls create() inside its algorithm; a subclass overrides create() to return whichever concrete type it needs, and the algorithm keeps working unchanged.

🏢 For a professional

Like a hiring process with role-specific interviewers. HR runs the same pipeline for every req, but each department decides who conducts the technical round. The pipeline is fixed; the specialist plugged in varies.

🍕 Everyday version

A pizza chain with regional kitchens. Head office defines "take order, make pizza, box it." Each franchise overrides "make pizza" to produce its own style, while the order and boxing steps stay identical.

03 - How

How it works under the hood

The Creator defines an abstract factory method and calls it from within concrete business logic. Subclasses override the factory method to return a specific product. The two hierarchies, Creator and Product, evolve in parallel.

🏭 The Creator side

An abstract Creator declares createProduct() and provides a real method, like plan(), that calls it. Concrete Creators override only createProduct().

📦 The Product side

A Product interface declares the operations the Creator relies on. Each Concrete Product implements them, and typically one Concrete Product pairs with one Concrete Creator.

A realistic example

// Product hierarchy
interface Transport {
  deliver(cargo: string): string;
}

class Truck implements Transport {
  deliver(cargo: string): string {
    return `Delivering ${cargo} by road in a box.`;
  }
}

class Ship implements Transport {
  deliver(cargo: string): string {
    return `Delivering ${cargo} by sea in a container.`;
  }
}

// Creator hierarchy
abstract class Logistics {
  // The factory method - subclasses decide the concrete Transport.
  protected abstract createTransport(): Transport;

  // Shared workflow that depends only on the Transport interface.
  planDelivery(cargo: string): string {
    const t = this.createTransport();
    return `Planning route... ${t.deliver(cargo)}`;
  }
}

class RoadLogistics extends Logistics {
  protected createTransport(): Transport {
    return new Truck();
  }
}

class SeaLogistics extends Logistics {
  protected createTransport(): Transport {
    return new Ship();
  }
}

// Usage: pick the Creator, the workflow stays identical.
const logistics: Logistics = new SeaLogistics();
console.log(logistics.planDelivery("electronics"));
// -> "Planning route... Delivering electronics by sea in a container."
from abc import ABC, abstractmethod

# Product hierarchy
class Transport(ABC):
    @abstractmethod
    def deliver(self, cargo: str) -> str:
        ...

class Truck(Transport):
    def deliver(self, cargo: str) -> str:
        return f"Delivering {cargo} by road in a box."

class Ship(Transport):
    def deliver(self, cargo: str) -> str:
        return f"Delivering {cargo} by sea in a container."

# Creator hierarchy
class Logistics(ABC):
    # The factory method - subclasses decide the concrete Transport.
    @abstractmethod
    def create_transport(self) -> Transport:
        ...

    # Shared workflow that depends only on the Transport interface.
    def plan_delivery(self, cargo: str) -> str:
        t = self.create_transport()
        return f"Planning route... {t.deliver(cargo)}"

class RoadLogistics(Logistics):
    def create_transport(self) -> Transport:
        return Truck()

class SeaLogistics(Logistics):
    def create_transport(self) -> Transport:
        return Ship()

# Usage: pick the Creator, the workflow stays identical.
logistics: Logistics = SeaLogistics()
print(logistics.plan_delivery("electronics"))
# -> "Planning route... Delivering electronics by sea in a container."

class Truck < Transport

  end
end

class Ship < Transport
  def deliver(cargo)
    "Delivering #{cargo} by sea in a container."
  end
end

class Logistics
  # The factory method - subclasses decide the concrete Transport.
  def create_transport
    raise NotImplementedError
  end

  # Shared workflow that depends only on the Transport interface.
  def plan_delivery(cargo)
    t = create_transport
    "Planning route... #{t.deliver(cargo)}"
  end
end

class RoadLogistics < Logistics
  def create_transport
    Truck.new
  end
end

class SeaLogistics < Logistics
  def create_transport
    Ship.new
  end
end

# Usage: pick the Creator, the workflow stays identical.
logistics = SeaLogistics.new
puts logistics.plan_delivery("electronics")
# -> "Planning route... Delivering electronics by sea in a container."

Notice that planDelivery never names Truck or Ship. Adding air freight is a new AirLogistics plus a Plane class, with zero edits to the existing workflow. That is the whole payoff.

05 - Step by Step

The 0 → 100 flow

From a tangle of scattered constructors to a clean, extensible pair of hierarchies - the whole journey in order.

00
Smell

Spot the branching construction

You find a method littered with new X() or a switch that picks a concrete class. Every new type forces you to edit it.

10
Abstract

Define the Product interface

Extract the operations the caller actually needs into a single interface. This becomes the contract the workflow depends on.

20
Implement

Create the Concrete Products

Move each concrete variant behind the interface. Truck, Ship, Plane each implement deliver() in their own way.

30
Creator

Declare the abstract Creator

Make a base class that holds the shared workflow and declares an abstract createProduct() factory method returning the product interface.

40
Rewire

Call the factory method in the workflow

Replace direct new calls inside the workflow with a call to createProduct(). The workflow now speaks only to the abstraction.

50
Subclass

Write the Concrete Creators

For each variant, add a subclass that overrides createProduct() to return the matching Concrete Product. One Creator per Product.

60
Select

Choose the Creator at the edge

Configuration, DI, or a small lookup at startup picks which Concrete Creator to use. The decision lives in one place at the boundary.

70
Run

Invoke the shared workflow

The client calls the workflow on the chosen Creator. Polymorphism dispatches to the right factory method and the correct product is built.

80
Extend

Add a new variant safely

A new requirement means a new Product plus a new Creator. Existing classes stay closed to modification. Nothing else changes.

90
Test

Override for test doubles

A test subclass overrides the factory method to return a fake product, letting you verify the workflow without real dependencies.

100
Maintain

Evolve hierarchies in parallel

Creator and Product grow side by side. Each pairing is isolated, so the system scales to many variants without central rewrites.

Common Pitfalls

Pitfalls & anti-patterns

Factory Method earns its keep with real variation. Reach for it too early or too broadly and you pay in ceremony.

🪆 Subclass explosion

Using it when there is only ever one product forces a whole Creator hierarchy for nothing. If the type never varies, just call the constructor directly.

🔀 Confusing it with Abstract Factory

Factory Method makes one product via inheritance. Abstract Factory makes families of related products via composition. Mixing the two blurs both.

🧨 Logic creeping into the factory

The factory method should only construct and return. Piling validation, side effects, or branching into it turns a clean hook into a hidden god-method.

🕳️ Leaking concrete types

If the workflow casts the product back to a concrete class, the decoupling is gone. Depend strictly on the product interface.

🥶 Rigid one-to-one binding

Hard-coding one product per Creator can feel restrictive when a Creator needs to pick among several at runtime. Then a parameterized factory or Strategy fits better.

🌀 Static "factory" mislabeled

Calling a static method with a switch a "factory method" invites the wrong expectations. It is a simple factory idiom and is not extensible by subclassing.

Trade-offs

Trade-offs & when to use

Factory Method buys extensibility with an extra layer of classes. Weigh the flexibility you gain against the indirection you add.

AspectDetail
ProsDecouples callers from concrete classes, honors open-closed, centralizes construction, and makes the surrounding workflow reusable and testable.
ConsIntroduces a parallel class hierarchy and more indirection. Overkill when only one product type exists or types never change.
Use whenA class cannot anticipate the concrete type it must create, or you want subclasses to specify it, and you expect new variants over time.
Avoid whenThe product set is fixed and tiny, or a plain constructor or simple static factory already reads clearly.
ComplexityLow to moderate. One interface plus a Creator base class, then a Creator and Product pair per variant.
RelatedAbstract Factory (families of products), Builder (step-wise construction), Prototype (clone instead of subclass), Template Method (the workflow that calls the hook).
Rule of thumb: Use Factory Method when the surrounding algorithm is stable but the object it creates should vary by subclass. If instead you need whole families of related objects, graduate to Abstract Factory. If the type never varies, skip the pattern entirely.
06 - Case Studies

Real-world case studies

Three places the Factory Method shows up in production frameworks and systems.

☕

1 · JDK collection iterators

Pattern: virtual constructor via iterator()

Java's Collection.iterator() is a textbook factory method: each collection returns its own Iterator without exposing the concrete iterator class.

  • Iterable declares iterator() as the factory method returning the Iterator product.
  • ArrayList, LinkedList, and HashSet each return a private concrete iterator tuned to their structure.
  • The for-each loop and stream code depend only on Iterator, so any collection works uniformly.
✅ Outcome: A single traversal API spans every collection type, and new collections add their own iterator without changing client loops.
🖼️

2 · Cross-platform UI toolkits

Pattern: parallel Creator and Product hierarchies

A dialog framework needs the same interaction flow across operating systems while rendering native controls on each.

  • An abstract Dialog Creator defines render() and an abstract createButton() factory method.
  • WindowsDialog returns a WindowsButton, WebDialog returns an HtmlButton, one Creator per platform.
  • The render() workflow wires up the button's click handler through the shared Button interface.
✅ Outcome: The dialog logic is written once, while each platform plugs in native widgets through matching Creator and Product subclasses.
🔌

3 · Pluggable document parsers

Pattern: subclass decides the concrete parser

An import service ingests many file formats but wants one stable ingestion pipeline around them.

  • An abstract Importer declares createParser() and a concrete import() that validates and stores results.
  • CsvImporter, JsonImporter, and XmlImporter each override createParser() for their format.
  • Adding a new format is a new Importer plus a new Parser, with no change to validation or storage.
✅ Outcome: The ingestion pipeline stays stable and well-tested while the supported format list grows purely by extension.
07 - Relevance

Modern relevance

Factory Method predates modern dependency injection, but the core idea, deferring the choice of concrete type, is as central as ever.

💉 DI containers absorb it

Frameworks like Spring resolve concrete types through configuration, a generalized, container-driven form of the same decoupling Factory Method provides.

🧵 Functional factories

In languages with first-class functions, a supplier or lambda often replaces a Creator subclass, keeping the "defer the choice" spirit with less ceremony.

🧬 Generics sharpen the contract

Typed factory methods returning <T extends Product> give compile-time safety that the 1994 pattern lacked.

🔍 Reflection and registries

Plugin systems register Creators by key and resolve them at runtime, scaling Factory Method to open sets of products.

🧪 Testability endures

Overriding a factory method to inject a fake remains one of the simplest ways to test a workflow in isolation.

🏗️ Still taught first

It stays the entry point to creational patterns because it isolates one idea: separate what varies (the product) from what stays (the workflow).

Bottom line: Even where a container or a lambda does the wiring, you are applying Factory Method's principle - depend on an abstraction and let something else decide the concrete type. Learn it once and you see it everywhere.
