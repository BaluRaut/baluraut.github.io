Behavioral Pattern

Chain of Responsibility - passing a request until someone handles it

Some requests do not belong to a single, known object. Chain of Responsibility lets you string handlers together and pass a request down the line until one of them handles it. The sender never learns which handler responded, and you can add, reorder, or remove links without touching the caller.

01 - What

What is Chain of Responsibility?

Chain of Responsibility is a behavioral pattern that turns a request into a standalone object and sends it along a chain of potential handlers. Each handler decides one of two things: handle the request itself, or pass it to the next handler in the chain. The client that fires the request does not know or care which handler will deal with it.

🧩 Handler interface

A common contract every link implements, typically a handle(request) method and a reference to the next handler.

🔗 The chain

Concrete handlers linked in order. Each either serves the request or delegates to its successor until the end is reached.

📨 The client

Builds the chain once, then sends requests to the first link. It stays blind to who ultimately responds.

The core building blocks

Key mental model: the pattern is a conveyor belt of handlers. Each station looks at the package and either processes it or lets it slide to the next station. The belt operator (the client) just drops the package on and walks away.
02 - Why

Why Chain of Responsibility exists

Without it, request handling collapses into one giant conditional: a sprawling if / else if that knows every possible handler, in a fixed order, welded to the caller. That block is hard to extend, impossible to reorder cleanly, and violates the open/closed principle every time a new case appears.

🔓 Decouples sender from receiver

The caller fires a request without naming a handler. Handlers can change, multiply, or disappear and the caller never notices.

🧱 Open for extension

Add a new concern by inserting a link. Existing handlers and the client stay untouched, so you extend behavior without editing tested code.

🔄 Order becomes configuration

Because links are wired at runtime, you reorder or swap steps by changing how you build the chain, not by rewriting branching logic.

🎯 Single responsibility per link

Each handler does exactly one thing and knows only its own rule plus its successor, which keeps every class small and testable.

In Plain Terms

Chain of Responsibility explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is like escalating a question. You ask the tutor; if they cannot answer, they send you to the lecturer; if they cannot, it goes to the professor. You just ask once, and whoever can answer, answers.

👩‍💻 For a developer

It is a middleware pipeline. A request enters, each middleware either responds or calls next(), and control flows down the line until something writes a response or the request is served.

🏢 For a professional

Think of an expense approval flow. A manager approves up to a limit; above it the request rises to a director, then to finance. The person filing the claim does not need to know who signs off.

🎧 Everyday version

A support hotline. Tier 1 tries first; if the issue is beyond them they route you to tier 2, then to a specialist. You dial one number and the call finds the right person.

03 - How

How it works under the hood

Every handler implements a shared interface and holds a reference to the next handler. When a request arrives, a handler decides to serve it or delegate. Wiring the links together builds the chain; sending a request to the head kicks it off.

🔗 Linking the handlers

Each concrete handler stores a next reference. A helper like setNext() returns that next handler so you can wire the chain in a fluent, readable order.

🚦 Handle or forward

Inside handle(), a handler checks a condition. If it matches, it acts and may stop the chain; otherwise it calls the successor, or does nothing if it is the last link.

A realistic implementation in TypeScript

interface Request {
  user?: string;
  role?: string;
  body: string;
}

abstract class Handler {
  private next?: Handler;

  setNext(handler: Handler): Handler {
    this.next = handler;
    return handler; // enables fluent wiring
  }

  // Default: pass the request along the chain.
  handle(req: Request): void {
    if (this.next) this.next.handle(req);
  }
}

class AuthHandler extends Handler {
  handle(req: Request): void {
    if (!req.user) throw new Error("401 Unauthorized");
    super.handle(req); // authenticated, keep going
  }
}

class RoleHandler extends Handler {
  handle(req: Request): void {
    if (req.role !== "admin") throw new Error("403 Forbidden");
    super.handle(req);
  }
}

class ValidationHandler extends Handler {
  handle(req: Request): void {
    if (req.body.trim() === "") throw new Error("400 Empty body");
    super.handle(req); // reached the end, request is served
  }
}

// Wire the chain once, then just fire requests at the head.
const chain = new AuthHandler();
chain.setNext(new RoleHandler()).setNext(new ValidationHandler());

chain.handle({ user: "ada", role: "admin", body: "ship it" });

Notice that AuthHandler knows nothing about validation, and the caller knows nothing about either. Each link owns one rule and either advances the request or stops it, which is exactly what keeps the chain flexible.

05 - Step by Step

The 0 → 100 flow

From a tangled conditional to a clean, ordered chain and a request that finds its handler, the whole journey in order.

00
Spot the smell

Find the giant conditional

You notice a growing if / else if block that routes a request to different handling logic, and it changes every time a new case appears.

10
Model the request

Turn the request into an object

Capture what each handler needs to decide, user, role, amount, or payload, into a single request or context object passed down the chain.

20
Define contract

Declare the Handler interface

Create a shared interface with a handle(request) method and a way to set the next handler, so every link is interchangeable.

30
Base link

Add a base handler

Provide an abstract base that stores the successor and forwards by default, so concrete handlers only write the logic unique to them.

40
Extract

Split each case into a handler

Pull every branch of the old conditional into its own concrete handler, each owning exactly one responsibility.

50
Decide policy

Handle, or handle and stop

Choose per handler whether serving the request ends the chain or the request keeps flowing so later links can also act.

60
Wire

Link the handlers in order

Use setNext() to connect the concretes into a chain. Order is now configuration you can change without touching the handlers.

70
Send

Fire the request at the head

The client hands the request to the first link and stays blind to which handler will ultimately respond.

80
Traverse

Each link handles or forwards

A handler checks its condition, acts if it matches, otherwise calls its successor. The request walks the chain link by link.

90
Fall-through

Decide what happens at the end

If no handler serves the request, choose a policy: return a default, throw, or log. A must-handle chain treats fall-through as a bug.

100
Evolve

Insert or reorder without fear

New concern? Add a link. Different priority? Rewire. The client and existing handlers never change, so the design keeps paying off.

Common Pitfalls

Pitfalls & anti-patterns

The pattern is simple, but it fails in predictable ways when the chain is built or reasoned about carelessly.

🕳️ Silent fall-through

A request that no handler serves slips off the end and vanishes. If the request must be handled, an unhandled request is a defect, so make the tail throw or log.

🔁 Broken forwarding

A handler forgets to call its successor, so links after it never run. One missing super.handle() quietly kills half the chain.

🧭 Order dependence hidden

Handlers that secretly depend on running before or after another link make the chain fragile. Reordering then breaks behavior in non-obvious ways.

🌀 Debugging by tracing

Because the caller does not know the receiver, following a request through many links is hard. Long, dynamic chains become tricky to reason about.

🧨 Over-engineering

For a fixed set of two or three cases that never change, a chain adds ceremony a simple switch would handle more clearly.

🪢 Fat handlers

Stuffing several unrelated rules into one link defeats the point. Each handler should own a single decision, or the chain stops being flexible.

Trade-offs

Trade-offs & when to use

Chain of Responsibility trades a little indirection for a lot of flexibility. Reach for it when the set of handlers, or their order, is expected to change.

AspectDetail
ProsDecouples sender from receiver, one responsibility per link, add or reorder handlers without editing the client or other handlers.
ConsA request can go unhandled, control flow is harder to trace, and long dynamic chains can hurt performance and readability.
Use whenMultiple objects may handle a request, the handler is not known up front, or the set and order of handlers should be configurable at runtime.
Avoid whenExactly one known object always handles the request, or the cases are few and fixed, where a simple conditional is clearer.
ComplexityLow structural cost, one interface plus small handlers, but added runtime indirection you must be able to trace.
RelatedCommand (requests as objects), Decorator (also a wrapping chain), Mediator (centralizes instead of chaining), Observer (broadcasts to all).
Rule of thumb: if the answer to "who handles this?" is "it depends, and the list keeps changing," use a chain. If it is "always this one object," do not, just call it directly. And always decide explicitly whether a request may fall through or must be handled.
06 - Case Studies

Real-world case studies

Three representative uses showing the pattern doing real work in production systems.

🌐

1 · HTTP middleware pipeline

Pattern: request must be processed, response wraps back

Web frameworks like Express, ASP.NET Core, and Java servlet filters model the request lifecycle as a chain of middleware.

  • Each middleware, logging, CORS, auth, compression, either responds or calls next() to advance.
  • Order is configuration: authentication runs before the route handler, compression wraps the response after.
  • A middleware can short-circuit, returning 401 immediately so downstream links never run.
✅ Outcome: cross-cutting concerns live in small, reorderable, independently testable links instead of being tangled into every route.
🪵

2 · Logging framework levels

Pattern: request may fall through, best match wins

Loggers in java.util.logging and log4j walk a chain of parent loggers and handlers by severity level.

  • A log record is offered to each logger up the hierarchy until one is configured to emit it.
  • Level thresholds decide whether a link handles the record or passes it toward the root.
  • A record below every threshold simply falls through and is dropped, which is intended behavior here.
✅ Outcome: teams tune verbosity per component by reconfiguring the chain, with no code changes to the call sites.
💳

3 · Approval and validation workflows

Pattern: escalate until an authority can decide

Expense approvals, purchase orders, and multi-stage input validation escalate a request through tiers of authority.

  • A manager approves up to a limit; larger amounts pass to a director, then to finance.
  • Each validator checks one rule, format, range, business constraint, then forwards on success.
  • The submitter fires one request and never needs to know which tier signs off.
✅ Outcome: approval limits and validation rules change by editing the chain, keeping business policy out of the caller.
07 - Relevance

Modern relevance

Far from dated, Chain of Responsibility is one of the most widely deployed patterns in modern software, usually hiding under the name "pipeline" or "middleware."

🧅 Middleware everywhere

Express, Koa, ASP.NET Core, Django, and gRPC interceptors are all chains. If you have written a next() call, you have used the pattern.

🛡️ API gateways

Gateways and service meshes run requests through ordered filters, auth, rate limiting, routing, that you compose declaratively.

⚙️ Functional composition

In modern codebases a chain is often just composed functions, each taking the next handler, which is the same idea with less ceremony.

🤖 LLM and agent pipelines

Guardrail and tool-routing stacks pass a request through validators and handlers until one accepts it, a textbook chain.

🧪 Event and stream processing

Interceptor chains in Kafka, message brokers, and ETL stages let each stage transform, drop, or forward a record.

🔌 Plugin architectures

Extensible tools let third parties insert handlers into a request chain without the core knowing they exist.

Bottom line: whenever a request should flow through an ordered, changeable set of processors, and you want the sender to stay ignorant of who responds, Chain of Responsibility is the pattern. Decide up front whether requests must be handled or may fall through, and the rest follows.
