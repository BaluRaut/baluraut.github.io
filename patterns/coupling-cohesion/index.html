OOP Concept

Coupling & Cohesion - the two forces that decide how easily code changes

Coupling is how much one module depends on the internals of another; cohesion is how tightly the responsibilities inside a single module belong together. Good design pushes coupling down and cohesion up, so a change stays local instead of rippling across the whole codebase. Get the balance wrong and a checkout flow that should take an hour to change takes a week.

01 - What

What are coupling and cohesion?

Coupling measures the strength of the connections between modules: how much a class needs to know about another class to do its job. Cohesion measures how focused a single module is internally: whether its methods and fields all serve one clear responsibility. The classic target is loose coupling, high cohesion. A tightly coupled CheckoutService that reaches into a PaymentGateway's private fields is fragile; one that talks to a small PaymentProcessor interface is not.

🔗 Coupling (between modules)

How dependent one module is on the details of another. Depending on a stable interface is fine; depending on private state, ordering, or global variables is dangerous.

🧲 Cohesion (inside a module)

How well the parts of one module belong together. A cohesive Invoice handles invoice math and nothing else; an incohesive one also emails, logs, and formats HTML.

⚖️ The trade-off

Splitting things for cohesion can add coupling if done carelessly. The art is drawing boundaries so each side is cohesive and the seam between them is thin and stable.

The types of coupling, weakest connection last

TypeWhat connects the modulesHow bad
Content couplingOne module reaches into another's internals, private fields, or implementation directly.Worst
Common couplingModules share global mutable state, so a change in one silently affects the others.Very high
Control couplingOne module passes a flag that tells another which branch to run, exposing its logic.High
Stamp couplingA whole record is passed when the callee needs only a couple of its fields.Moderate
Data couplingOnly the primitive data actually needed is passed as parameters.Best (aim here)
Key mental model: coupling and cohesion are two ends of the same lever. You reduce coupling by hiding a module's internals behind a narrow interface, and that same act usually raises the module's cohesion because it now owns one job completely. Together they decide your changeability: how far a single edit spreads.
02 - Why

Why it matters

Software cost is dominated by change, not by the first write. Coupling and cohesion are the strongest predictors of how expensive that change will be, and they show up in every code review, bug, and estimate.

🎯 Localized change

In a loosely coupled, highly cohesive design, adding a new payment method touches one class. In a tangled one, it touches the cart, the order, the receipt, and three tests you did not expect.

🧪 Testable in isolation

A class that depends on a small interface can be tested with a fake in milliseconds. A class wired to a live gateway and a global session forces slow, flaky, end-to-end tests.

🔁 Safe to replace

Swap Stripe for Adyen without rewriting checkout, because checkout depends on a PaymentProcessor abstraction, not on Stripe's SDK types leaking through every layer.

👥 Parallel teams

Thin, stable seams let one team own inventory and another own billing without stepping on each other. High coupling forces constant coordination and merge pain.

In Plain Terms

Coupling & Cohesion explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Cohesion is a well-organized binder where each tab holds one subject; coupling is how many other binders you must open to finish one assignment. You want each tab self-contained and few cross-references.

👩‍💻 For a developer

Loose coupling is programming to an interface: your CheckoutService holds a PaymentProcessor, not a concrete Stripe client. High cohesion is a class whose every method touches the same core state.

🏢 For a professional

Think of departments in a company. A cohesive department owns one function end to end; loose coupling means they coordinate through clear contracts, not by rummaging through each other's desks.

🔌 Everyday version

Wall sockets are loosely coupled: any appliance with the right plug works, and you never rewire the house to swap a lamp. A hardwired appliance is tightly coupled, replacing it means an electrician.

03 - How

How to reduce coupling and raise cohesion

The move is almost always the same: find the concrete dependency, hide it behind a small interface the caller owns, and pass in only the data the callee truly needs. Below, a checkout flow goes from tightly coupled to loosely coupled.

🧱 Depend on abstractions

Have CheckoutService hold a PaymentProcessor interface instead of new StripeClient(). The concrete gateway is injected, so checkout no longer imports Stripe's SDK at all.

✂️ Split by responsibility

Pull pricing, payment, and receipts into cohesive classes. Each owns one job, so a tax-rule change lands in PricingService alone and never touches payment code.

Before: tightly coupled checkout

// Tightly coupled: checkout builds its own Stripe client (content + control coupling)
class StripeClient {
  chargeCard(cents: number, token: string, live: boolean) {
    // reaches a real gateway; the `live` flag selects a branch (control coupling)
    return { id: "ch_1", ok: true, mode: live ? "live" : "test" };
  }
}

class CheckoutService {
  private stripe = new StripeClient(); // hard dependency on a concrete class

  checkout(cart: { items: { priceCents: number }[] }, token: string) {
    const total = cart.items.reduce((s, i) => s + i.priceCents, 0);
    // passes a boolean flag that steers the callee's logic (control coupling)
    const charge = this.stripe.chargeCard(total, token, true);
    if (!charge.ok) throw new Error("payment failed");
    return { paid: total, chargeId: charge.id };
  }
}

const receipt = new CheckoutService().checkout(
  { items: [{ priceCents: 1999 }, { priceCents: 500 }] },
  "tok_visa",
);
console.log(receipt); // { paid: 2499, chargeId: "ch_1" }

  end
end

  "tok_visa"
)
puts receipt.inspect # {:paid=>2499, :charge_id=>"ch_1"}

After: loosely coupled with an injected processor

// Loosely coupled: depend on a narrow interface, pass only the data needed (data coupling)
interface PaymentProcessor {
  charge(amountCents: number, token: string): { id: string; ok: boolean };
}

class StripeProcessor implements PaymentProcessor {
  charge(amountCents: number, token: string) {
    return { id: "ch_1", ok: amountCents > 0 };
  }
}

// Highly cohesive: this class only prices a cart, nothing else
class PricingService {
  totalCents(items: { priceCents: number }[]): number {
    return items.reduce((sum, i) => sum + i.priceCents, 0);
  }
}

class CheckoutService {
  constructor(
    private readonly processor: PaymentProcessor, // injected abstraction
    private readonly pricing: PricingService,
  ) {}

  checkout(items: { priceCents: number }[], token: string) {
    const total = this.pricing.totalCents(items);
    const charge = this.processor.charge(total, token); // no flags, no globals
    if (!charge.ok) throw new Error("payment failed");
    return { paid: total, chargeId: charge.id };
  }
}

// wiring happens once, at the edge
const service = new CheckoutService(new StripeProcessor(), new PricingService());
const receipt = service.checkout([{ priceCents: 1999 }, { priceCents: 500 }], "tok_visa");
console.log(receipt); // { paid: 2499, chargeId: "ch_1" }
# Loosely coupled: depend on a narrow interface, pass only the data needed (data coupling)
from typing import Protocol


class PaymentProcessor(Protocol):
    def charge(self, amount_cents: int, token: str) -> dict: ...


class StripeProcessor:
    def charge(self, amount_cents: int, token: str) -> dict:
        return {"id": "ch_1", "ok": amount_cents > 0}


# Highly cohesive: this class only prices a cart, nothing else
class PricingService:
    def total_cents(self, items) -> int:
        return sum(item["price_cents"] for item in items)


class CheckoutService:
    def __init__(self, processor: PaymentProcessor, pricing: PricingService):
        self._processor = processor  # injected abstraction
        self._pricing = pricing

    def checkout(self, items, token):
        total = self._pricing.total_cents(items)
        charge = self._processor.charge(total, token)  # no flags, no globals
        if not charge["ok"]:
            raise RuntimeError("payment failed")
        return {"paid": total, "charge_id": charge["id"]}


# wiring happens once, at the edge
service = CheckoutService(StripeProcessor(), PricingService())
receipt = service.checkout([{"price_cents": 1999}, {"price_cents": 500}], "tok_visa")
print(receipt)  # {'paid': 2499, 'charge_id': 'ch_1'}
# Loosely coupled: depend on a narrow interface (duck type), pass only the data needed
class StripeProcessor
  # honors the informal PaymentProcessor contract: charge(amount_cents, token)
  def charge(amount_cents, token)
    { id: "ch_1", ok: amount_cents > 0 }
  end
end

# Highly cohesive: this class only prices a cart, nothing else
class PricingService
  def total_cents(items)
    items.sum { |item| item[:price_cents] }
  end
end

class CheckoutService
  def initialize(processor:, pricing:)
    @processor = processor # injected abstraction
    @pricing = pricing
  end

  def checkout(items, token)
    total = @pricing.total_cents(items)
    charge = @processor.charge(total, token) # no flags, no globals
    raise "payment failed" unless charge[:ok]

    { paid: total, charge_id: charge[:id] }
  end
end

# wiring happens once, at the edge
service = CheckoutService.new(processor: StripeProcessor.new, pricing: PricingService.new)
receipt = service.checkout([{ price_cents: 1999 }, { price_cents: 500 }], "tok_visa")
puts receipt.inspect # {:paid=>2499, :charge_id=>"ch_1"}

The two versions behave identically, but the second injects a PaymentProcessor and pulls pricing into its own cohesive class. Now a new gateway is a new implementation, a tax change lives in one place, and every collaborator is a fake away from a fast unit test. That is coupling and cohesion working together to buy changeability.

05 - Step by Step

The 0 → 100 flow

From a tangled checkout to a loosely coupled, highly cohesive one, and how to measure the improvement along the way.

00
Smell

Feel the pain

A one-line pricing change breaks payment tests. That ripple is the signal that coupling is high and cohesion is low.

10
Map

Draw the dependencies

List who calls whom. Note every new ConcreteClass(), shared global, and boolean flag passed between modules.

20
Classify

Name the coupling

Tag each edge: content, common, control, stamp, or data. Anything worse than data coupling is a candidate to fix.

30
Measure

Baseline the numbers

Compute afferent (Ca) and efferent (Ce) coupling per module and LCOM per class so you can prove the refactor helped.

40
Extract

Give each job a home

Pull pricing, payment, and receipts into separate classes. Each ends up cohesive: its methods share the same state.

50
Abstract

Introduce an interface

Define PaymentProcessor that CheckoutService owns, so checkout stops importing the gateway SDK.

60
Invert

Inject the dependency

Pass the concrete processor into the constructor at the composition root instead of newing it up inside checkout.

70
Flatten

Kill the control flags

Replace boolean parameters that select behavior with distinct methods or separate implementations, removing control coupling.

80
Slim

Pass only what is used

Where a whole cart record was handed over for two fields, pass those fields. Stamp coupling becomes data coupling.

90
Test

Fake the seams

Write fast unit tests against fakes of each interface. The ease of faking is direct evidence coupling dropped.

100
Verify

Re-measure and lock it in

Recompute LCOM and Ce; they should fall. Add a fitness function so the numbers cannot silently creep back up.

Common Pitfalls

Pitfalls & anti-patterns

Most coupling damage is self-inflicted by good intentions applied without measurement. These are the usual traps.

🕳️ Reaching into internals

Content coupling: checkout reads gateway._session or mutates another object's private fields. One rename in the callee and the caller explodes. Talk through public methods only.

🌍 Shared global state

Common coupling: a global currentCart or singleton config that many modules read and write. Order of execution becomes load-bearing and bugs turn spooky and non-local.

🚩 Flag arguments

Control coupling: charge(amount, token, isRefund) where the flag picks a branch. The caller now depends on the callee's control flow. Split into charge and refund.

📦 Passing the whole record

Stamp coupling: handing an entire Order to a function that needs only total and currency. It couples you to the record's shape and hides the real inputs.

🧺 The god class

Low cohesion: a CheckoutService that prices, charges, emails, logs, and renders HTML. Its LCOM is sky-high because no two methods share the same state. Split by responsibility.

🎭 Interfaces that leak

An abstraction that mirrors one vendor's SDK one-to-one is fake decoupling. If the interface exposes Stripe-specific types, swapping providers still rewrites checkout.

Signals & Metrics

Signals & how to measure

You cannot manage what you do not measure. These signals turn "this feels tangled" into numbers you can track over time.

SignalWhat it tells you
Afferent coupling (Ca)How many other modules depend on this one. High Ca means it is a stable core, so changing it is risky and expensive.
Efferent coupling (Ce)How many modules this one depends on. High Ce means it is fragile, easily broken when its many collaborators change.
Instability (I = Ce / (Ca + Ce))Near 1 means volatile and dependent; near 0 means depended-upon and stable. Details should be unstable, abstractions stable.
LCOM (lack of cohesion of methods)How little the methods of a class share fields. A high LCOM flags a class doing several unrelated jobs that should be split.
Fan-in / fan-out per methodLocal coupling at the call level. A method that calls ten different objects is a coordination hotspot and a change magnet.
Change coupling (from git history)Files that keep changing together in commits are coupled in practice even if the code looks independent. It reveals hidden seams.
Rule of thumb: aim for low efferent coupling and low LCOM on the classes you change most. If a class has both high Ca (many depend on it) and high instability, stabilize it behind an interface before it becomes a bottleneck the whole system inherits.
06 - Case Studies

Real-world case studies

Three production-shaped situations where coupling and cohesion decided the outcome.

💳

1 · Checkout that outgrew a single payment provider

Pattern: injected PaymentProcessor abstraction

A commerce team hardcoded Stripe throughout checkout, then had to add a regional gateway for a new market and could not without touching dozens of files.

  • Every layer imported Stripe types, so the gateway was content-coupled into pricing, orders, and receipts.
  • They introduced a PaymentProcessor interface owned by checkout and injected the concrete client at the edge.
  • The regional gateway shipped as a new implementation with no change to checkout logic or its tests.
✅ Outcome: Adding a provider went from a multi-week cross-cutting change to a single new class, and payment code became unit-testable with a fake.
📦

2 · Order service tangled with inventory via shared state

Pattern: removing common coupling

An order pipeline and an inventory job both read and wrote a shared in-memory stock map, so reservations depended on execution order and produced oversells.

  • Common coupling on the global map made bugs non-local and impossible to reproduce reliably.
  • They replaced the shared map with an InventoryLedger exposing reserve and release methods.
  • Order and fulfillment now coordinate through explicit calls, not by mutating shared memory.
✅ Outcome: Oversell defects disappeared, and each service could be reasoned about and tested on its own, since the seam was an explicit contract.
📣

3 · A notification god class split for cohesion

Pattern: raising cohesion, lowering LCOM

A single Notifier formatted emails, sent SMS, wrote push payloads, and logged, so any channel change risked breaking the others.

  • Static analysis showed a very high LCOM: no two methods shared the same fields.
  • They split it into EmailChannel, SmsChannel, and PushChannel behind a small Channel interface.
  • A thin NotificationService now selects a channel and delegates, staying cohesive and small.
✅ Outcome: Each channel evolved independently, LCOM dropped sharply, and adding WhatsApp support meant one new cohesive class rather than edits across a monolith.
07 - Relevance

Modern relevance

Coupling and cohesion are older than object orientation, yet every modern architecture is really a bet on where to draw thin, cohesive seams.

🧩 Microservice boundaries

A service boundary is just a coupling decision at network scale. High change-coupling between two services is the clearest sign they should be one.

🛡️ Modular monoliths

Teams keep the monolith but enforce cohesive modules with explicit interfaces, getting loose coupling without distributed-systems pain.

📐 Fitness functions

Architecture tests fail the build when a forbidden dependency appears, keeping efferent coupling and LCOM from drifting over time.

🤖 AI-assisted refactoring

Tools now suggest extract-class and dependency-injection moves by reading LCOM and change-coupling straight from the repository.

🔍 Observability of change

Mining git history for files that change together surfaces hidden coupling that static analysis alone misses.

🧪 Contract testing

Consumer-driven contracts let loosely coupled services evolve independently while proving the thin seam between them still holds.

Bottom line: loose coupling and high cohesion are the timeless levers of changeability. Whatever the stack or scale, the winning move is the same: hide internals behind narrow interfaces, give each module one job, and measure the seams so they stay thin.
