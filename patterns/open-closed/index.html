OOP Concept

The Open/Closed Principle - add behavior without editing what already works

Software entities should be open to extension but closed to modification. When a new discount rule, shipping carrier, or payment method arrives, you add a new class, you do not reopen a stable file and bolt another branch onto a growing switch. Polymorphism is the mechanism that makes this possible.

01 - What

What is the Open/Closed Principle?

The Open/Closed Principle (the O in SOLID) says a module's behavior should be extendable without editing its source. You achieve it by depending on an abstraction, a stable interface, and letting new behavior arrive as new implementations of that abstraction. The code that orchestrates the work never needs to know how many implementations exist.

🔓 Open to extension

New requirements are met by adding new classes that satisfy an existing contract, so the system grows at its edges.

🔒 Closed to modification

Tested, shipped code stays untouched. You do not risk regressions in the checkout calculator to add one more carrier.

🧩 Bound by a contract

An interface or abstract base defines the seam. Callers program to that seam, never to a concrete type.

Key mental model: OCP does not mean code never changes. It means the change for a new variant lands as new code, not as a surgical edit to logic that already works and is already tested.
02 - Why

Why OCP matters

Every time you reopen a working file to add a branch, you risk breaking the branches already there. OCP moves that risk out of the hot path and into isolated, additive units.

🛡️ Fewer regressions

Adding the tenth discount rule cannot break the other nine when each rule is its own class with its own tests. The stable core is never touched.

🔀 Smaller merge conflicts

Two teams adding two payment methods edit two different files instead of fighting over the same growing switch statement.

🧪 Testable in isolation

Each strategy is a small object you can unit test directly, without spinning up the whole checkout to reach one branch.

🔌 Plugin-friendly

Carriers, gateways, and formats can be discovered at runtime through a registry, so extensions ship without a redeploy of the core.

In Plain Terms

Open/Closed explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

It is like a multiple-choice answer sheet. Adding another possible answer means printing one more bubble, not re-typing the whole question and every existing choice.

👩‍💻 For a developer

Think of a plugin architecture. The host defines the interface once and stays frozen; each plugin adds capability by implementing that interface, and the host never learns their names.

🏢 For a professional

A well-run approvals workflow: adding a new approver role is filling out a form the system already understands, not rewriting the routing engine.

🔌 Everyday version

A power strip. To power a new device you plug into an existing socket. You do not rewire the wall every time you buy an appliance.

03 - How

How you actually achieve it

Find the axis of change, name it as an interface, and let the orchestrator depend only on that interface. New behavior is then a new class the orchestrator never has to know about by name.

🎯 Name the abstraction

Define the seam where variants differ. For checkout that seam is PaymentMethod.charge(amount). Callers hold the interface, not a concrete gateway.

➕ Extend by adding classes

A new method, PayPal, Klarna, or a gift card, is a new class implementing the same contract. The processor loops over methods polymorphically and never branches on type.

Extension without modification, in three languages

// The stable contract. The processor depends only on this.
interface PaymentMethod {
  name(): string;
  charge(amountCents: number): Receipt;
}
interface Receipt { method: string; amountCents: number; ref: string; }

// The orchestrator is CLOSED: it never changes when methods are added.
class CheckoutProcessor {
  pay(order: { totalCents: number }, method: PaymentMethod): Receipt {
    if (order.totalCents <= 0) throw new Error("empty order");
    return method.charge(order.totalCents);
  }
}

// Shipped, tested, frozen.
class CardPayment implements PaymentMethod {
  constructor(private last4: string) {}
  name() { return `card ****${this.last4}`; }
  charge(amountCents: number): Receipt {
    return { method: this.name(), amountCents, ref: `ch_${Date.now()}` };
  }
}

// NEW requirement -> NEW class. Nothing above is edited.
class GiftCardPayment implements PaymentMethod {
  constructor(private code: string) {}
  name() { return `gift ${this.code.slice(0, 4)}`; }
  charge(amountCents: number): Receipt {
    return { method: this.name(), amountCents, ref: `gc_${this.code}` };
  }
}

const order = { totalCents: 4999 };
console.log(processor.pay(order, new CardPayment("4242")));
console.log(processor.pay(order, new GiftCardPayment("HOLIDAY25")));
from abc import ABC, abstractmethod
from dataclasses import dataclass
from time import time

@dataclass
class Receipt:
    method: str
    amount_cents: int
    ref: str

# The stable contract.
class PaymentMethod(ABC):
    @abstractmethod
    def name(self) -> str: ...
    @abstractmethod
    def charge(self, amount_cents: int) -> Receipt: ...

# The orchestrator is CLOSED: unchanged as methods are added.
class CheckoutProcessor:
    def pay(self, order, method: PaymentMethod) -> Receipt:
        if order["total_cents"] <= 0:
            raise ValueError("empty order")
        return method.charge(order["total_cents"])

# Shipped, tested, frozen.
class CardPayment(PaymentMethod):
    def __init__(self, last4: str):
        self.last4 = last4
    def name(self) -> str:
        return f"card ****{self.last4}"
    def charge(self, amount_cents: int) -> Receipt:
        return Receipt(self.name(), amount_cents, f"ch_{int(time())}")

# NEW requirement -> NEW class. Nothing above is edited.
class GiftCardPayment(PaymentMethod):
    def __init__(self, code: str):
        self.code = code
    def name(self) -> str:
        return f"gift {self.code[:4]}"
    def charge(self, amount_cents: int) -> Receipt:
        return Receipt(self.name(), amount_cents, f"gc_{self.code}")

The CheckoutProcessor is the closed part: it was written once and never edited to support gift cards. GiftCardPayment is the open part: a brand-new type that slots into the same contract. That asymmetry, one file frozen while the system still grows, is the whole point.

05 - Step by Step

The 0 → 100 flow

From a growing switch statement to a closed core that still accepts new behavior, the whole refactor in order.

00
Smell

Spot the growing switch

A method branches on a type tag, and every new requirement means one more case. That file is edited on every feature.

10
Axis

Name the axis of change

Identify what varies: the payment method, the carrier, the discount rule. That variation is your future abstraction.

20
Contract

Define the interface

Write the seam once: charge(amount), price(weight, zone). Keep it minimal and behavior-focused.

30
Extract

Move each branch into a class

Every case body becomes a small class implementing the contract. Behavior is preserved, just relocated.

40
Invert

Depend on the abstraction

The orchestrator now accepts the interface as a parameter and calls one polymorphic method. The switch is deleted.

50
Test

Unit test each strategy

Each class gets focused tests. You no longer need the whole pipeline to exercise one branch.

60
Register

Wire selection at the edge

A registry or factory maps input to the right class in one place, so runtime selection is data, not control flow.

70
Freeze

Close the core

The orchestrator is done. It will not be edited when variant number eleven arrives. This is the "closed" half.

80
Extend

Add the next variant

A new carrier is a new class plus a registry entry. No existing file is opened. This is the "open" half.

90
Guard

Watch for over-abstraction

Do not add interfaces for axes that never vary. Two stable cases rarely justify a plugin framework.

100
Ship

Grow at the edges

Features now arrive as additive classes. The blast radius per change is one new file, and the tested core stays green.

Common Pitfalls

Pitfalls & anti-patterns

OCP is easy to overshoot and easy to fake. These are the usual failures.

🔮 Speculative abstraction

Building a plugin system for one payment method "in case we add more." Premature interfaces add indirection with no payoff and are the most common OCP mistake.

🕵️ Hidden switch-on-type

Replacing the switch with if isinstance(m, CardPayment) inside the processor. You moved the branch, you did not remove it. The core is still not closed.

🧱 Leaky interface

An abstraction that exposes concrete details, like a getStripeToken() on the payment contract, forces callers to special-case and defeats the seam.

💥 Fat base class

Piling shared logic into an abstract base until subclasses must override half of it. That coupling means new variants still edit shared code.

🚪 Modification through the back door

Adding a boolean flag to an existing class to fork behavior. That is modification, not extension, and it grows combinatorially.

🗺️ Registry that must be edited

If every new class requires hand-editing a central map, the map becomes the new switch. Prefer auto-registration or dependency injection.

Signals & Metrics

Signals & how to measure

You cannot put a single number on OCP, but these signals tell you whether a module is truly closed to modification.

SignalWhat it tells you
Files touched per new variantIf adding a carrier edits the calculator, the core is not closed. Ideally it is one new file plus a wiring line.
Churn on the orchestratorHigh commit frequency on a dispatch file that "should be stable" points to a switch that keeps growing.
Cyclomatic complexity of dispatchA rising branch count in one method is the switch-on-type smell in numeric form.
Type checks in the coreCount instanceof / isinstance / is_a? in orchestration code. More than zero usually means the abstraction leaks.
Test blast radiusIf a new variant forces edits to existing tests, behavior was not really isolated.
Interfaces with one implementationMany single-use abstractions signal over-engineering: you paid for extension points nobody uses.
Rule of thumb: apply OCP on the second or third time an axis actually changes, not the first. Duplication is cheaper than the wrong abstraction; add the seam when the variation is proven, not predicted.
06 - Case Studies

Real-world case studies

Three production-style systems where extension without modification is the load-bearing design.

💳

1 · Checkout with pluggable payment methods

Pattern: strategy behind a stable processor

A marketplace supports cards, wallets, buy-now-pay-later, and store credit, and adds new methods often.

  • Each method implements a PaymentMethod contract with charge and refund.
  • The checkout processor and order state machine are frozen; they only speak the interface.
  • Adding Klarna is a new class plus a registry entry, shipped without touching checkout.
✅ Outcome: New payment methods reach production as isolated, tested classes, and the core checkout has not been reopened for a regression in months.
🚚

2 · Shipping-cost calculator across carriers

Pattern: rate strategy per carrier

A logistics platform quotes rates from many carriers, each with its own weight, zone, and surcharge rules.

  • A ShippingRate interface exposes price(weight, zone); each carrier is one implementation.
  • The quoting engine iterates over registered rates and picks the cheapest, with no per-carrier branches.
  • A regional courier is onboarded by dropping in a class the engine discovers at startup.
✅ Outcome: Carrier integrations became parallelizable across teams, since each one is an additive strategy rather than an edit to a shared calculator.
🏷️

3 · Pluggable discount and promotion rules

Pattern: composable rule pipeline

A retail platform runs stacking promotions: loyalty tiers, coupons, bundle deals, and flash sales.

  • Each promotion is a DiscountRule applied in sequence over the running subtotal.
  • Marketing configures which rules are active as data; the pricing core never changes.
  • A seasonal rule is added as a class and enabled by config, then removed cleanly after the campaign.
✅ Outcome: Campaigns ship at marketing speed without engineering edits to pricing logic, and expired promotions are deleted without scar tissue in a switch.
07 - Relevance

Modern relevance

OCP predates most of today's stacks, but its shape shows up everywhere extensibility is a feature.

🔌 Plugin ecosystems

Editors, CI runners, and payment SDKs expose an interface and let third parties extend behavior without forking the host.

🎛️ Feature flags & strategies

Swapping algorithms behind a flag is OCP in practice: the caller is closed, the strategies are open to addition.

🧩 Dependency injection

Frameworks wire implementations into a stable core at runtime, so extension is configuration, not code surgery.

☁️ Serverless handlers

A new event type is a new handler registered against a stable router, not an edit to a central dispatch function.

🤖 Tool-using agents

Giving an agent a new capability is registering another tool against a fixed calling protocol, a direct OCP shape.

⚖️ The YAGNI counterweight

Modern practice pairs OCP with "you are not gonna need it": add the seam when variation is real, not on a hunch.

Bottom line: OCP is not a rule to apply everywhere; it is a tool for the axes that genuinely change. Used there, it lets a system grow for years without reopening its tested core. Used everywhere, it drowns you in interfaces nobody needs.
