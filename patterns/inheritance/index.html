OOP Concept

Inheritance - modeling is-a and reusing behavior safely

Inheritance lets one class extend another so a subtype reuses and specializes a base type's data and behavior. Used well, it captures a real is-a relationship, like an email notification is a notification. Used carelessly, it welds classes together and creates the fragile base class trap.

01 - What

What is inheritance?

Inheritance is a mechanism where a subclass derives from a base class and automatically gains its fields and methods. The subclass can add new behavior, reuse what it inherited, or override methods to specialize them. The design test is the is-a question: an SMS notification is a notification, a salaried employee is an employee. If that sentence sounds wrong, inheritance is the wrong tool.

🧬 Base class

Holds the shared contract and state, like a Notification with a recipient, retry policy, and a delivery routine common to every channel.

📨 Subclass

Extends the base and specializes it, like EmailNotification adding subject and HTML body while reusing the retry and logging logic.

🔁 Override + super

A subclass replaces a base method with its own version, and can call super to run the base implementation as part of it.

The core building blocks

Base classDefines shared state and default behaviorNotification with send() and retry logic

Key mental model: inheritance is not code sharing for its own sake, it is subtyping. A subclass is a promise that instances can stand in anywhere the base is expected. If a subtype breaks that promise, you have coupling without the safety, which is the seed of the fragile base class problem.
02 - Why

Why inheritance exists

Inheritance earns its place when a family of types genuinely shares a contract and a large chunk of behavior. It removes duplication, expresses hierarchy directly, and gives you one place to change common logic.

♻️ Reuse without copy-paste

Retry, logging, and validation live once in the base. Every channel subtype inherits them instead of duplicating fragile boilerplate across email, SMS, and push senders.

🗂️ Models a real hierarchy

When the domain truly has an is-a tree, like employee types in payroll, the class graph mirrors the business language and reads clearly to newcomers.

🎯 Enables polymorphism

Code that accepts the base type works with any subclass. A dispatcher loops over notifications and calls send() without knowing the concrete channel.

🧩 One place to extend

Adding a new channel means one new subclass, not edits scattered across a switch statement. The base contract tells you exactly what to implement.

In Plain Terms

Inheritance explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

Inheritance is a base recipe with variations. The master dough is written once; the sourdough and focaccia versions inherit the steps and only change what makes them different.

👩‍💻 For a developer

It is extends plus override. A PaymentGateway base defines charge(); StripeGateway reuses the retry loop and overrides only the provider-specific call, invoking super for the shared parts.

🏢 For a professional

Think of a company policy with department addenda. Every team inherits the corporate handbook; each department overrides a few clauses. The base rules still apply unless explicitly specialized.

🏛️ Everyday version

Legal precedent: a general law covers everyone, and a specific ruling refines it for one case. The specific still relies on the general beneath it.

03 - How

How inheritance works under the hood

A subclass declares that it extends a base, gets the base members, and can override methods. At call time the runtime uses the object's real type to pick the method, and super lets an override reuse the base version.

🧬 Subclassing and constructors

The subclass constructor first calls the base constructor (super(...)) to initialize inherited state, then sets up its own fields. Skip that call and inherited invariants never get established.

🔒 Protected members

Fields marked protected are reachable by subclasses but hidden from outside callers, so subtypes can build on internal state without exposing it as public API.

Define a class, create an object, call its methods

// Base class: shared delivery contract for every channel
abstract class Notification {
  protected retries = 3;

  constructor(protected recipient: string) {}

  // Subclasses MUST specialize how the body is rendered
  abstract formatBody(): string;

  protected log(msg: string): void {
    console.log(`[notify] ${msg}`);
  }

  // Template behavior reused by all subtypes
  send(): boolean {
    const body = this.formatBody();
    for (let attempt = 1; attempt <= this.retries; attempt++) {
      this.log(`attempt ${attempt} -> ${this.recipient}`);
      if (this.transmit(body)) return true;
    }
    return false;
  }

  protected transmit(_body: string): boolean {
    return true; // pretend the carrier accepted it
  }
}

class EmailNotification extends Notification {
  constructor(recipient: string, private subject: string) {
    super(recipient); // initialize inherited state first
  }

  formatBody(): string {
    return `Subject: ${this.subject}\n<html>Hello</html>`;
  }
}

class SmsNotification extends Notification {
  constructor(recipient: string, private senderId: string) {
    super(recipient);
    this.retries = 2; // SMS carriers are stricter, override default
  }

  formatBody(): string {
    return `From ${this.senderId}: your code is 4821`;
  }

  // Override that reuses the base via super
  send(): boolean {
    this.log("checking SMS opt-in");
    return super.send();
  }
}

const outbox: Notification[] = [
  new EmailNotification("ana@shop.io", "Order shipped"),
  new SmsNotification("+15550100", "SHOPIO"),
];

for (const n of outbox) {
  n.send(); // dynamic dispatch picks the right formatBody + send
}
from abc import ABC, abstractmethod

class Notification(ABC):
    """Base class: shared delivery contract for every channel."""

    def __init__(self, recipient: str) -> None:
        self._recipient = recipient   # protected by convention
        self._retries = 3

    @abstractmethod
    def format_body(self) -> str:
        ...

    def _log(self, msg: str) -> None:
        print(f"[notify] {msg}")

    def _transmit(self, body: str) -> bool:
        return True  # pretend the carrier accepted it

    def send(self) -> bool:
        body = self.format_body()
        for attempt in range(1, self._retries + 1):
            self._log(f"attempt {attempt} -> {self._recipient}")
            if self._transmit(body):
                return True
        return False


class EmailNotification(Notification):
    def __init__(self, recipient: str, subject: str) -> None:
        super().__init__(recipient)   # initialize inherited state
        self._subject = subject

    def format_body(self) -> str:
        return f"Subject: {self._subject}\n<html>Hello</html>"


class SmsNotification(Notification):
    def __init__(self, recipient: str, sender_id: str) -> None:
        super().__init__(recipient)
        self._sender_id = sender_id
        self._retries = 2             # override the default

    def format_body(self) -> str:
        return f"From {self._sender_id}: your code is 4821"

    def send(self) -> bool:           # override that reuses super
        self._log("checking SMS opt-in")
        return super().send()


outbox = [
    EmailNotification("ana@shop.io", "Order shipped"),
    SmsNotification("+15550100", "SHOPIO"),
]

for n in outbox:
    n.send()  # dynamic dispatch picks the right format_body + send
# Base class: shared delivery contract for every channel
class Notification
  def initialize(recipient)
    @recipient = recipient   # instance vars are protected by design
    @retries = 3
  end

  # Subclasses must specialize this
  def format_body
    raise NotImplementedError, "subclass must implement format_body"
  end

  def send
    body = format_body
    (1..@retries).each do |attempt|
      log("attempt #{attempt} -> #{@recipient}")
      return true if transmit(body)
    end
    false
  end

  protected

  def log(msg)
    puts "[notify] #{msg}"
  end

  def transmit(_body)
    true # pretend the carrier accepted it
  end
end

class EmailNotification < Notification
  def initialize(recipient, subject)
    super(recipient)   # initialize inherited state first
    @subject = subject
  end

  def format_body
    "Subject: #{@subject}\n<html>Hello</html>"
  end
end

class SmsNotification < Notification
  def initialize(recipient, sender_id)
    super(recipient)
    @sender_id = sender_id
    @retries = 2       # override the default
  end

  def format_body
    "From #{@sender_id}: your code is 4821"
  end

  def send             # override that reuses super
    log("checking SMS opt-in")
    super
  end
end

outbox = [
  EmailNotification.new("ana@shop.io", "Order shipped"),
  SmsNotification.new("+15550100", "SHOPIO")
]

outbox.each(&:send) # dynamic dispatch picks the right format_body + send

All three snippets define one base contract, add two subclasses, and create real objects that go through a shared send routine. Notice how SmsNotification overrides send but still calls super, so it adds an opt-in check without reimplementing the retry loop.

05 - Step by Step

The 0 → 100 flow

From spotting a shared contract to shipping a safe hierarchy, the whole journey in order.

00
Spot

Find repeated behavior

Email, SMS, and push senders all retry, log, and validate the same way. Duplication across a real type family is the signal to consider a base class.

10
Test

Ask the is-a question

Say it out loud: an SMS notification is a notification. If the sentence is true and stable, inheritance fits. If it feels forced, prefer composition.

20
Extract

Define the base class

Pull the shared state and the common routine into Notification. Mark the parts every subtype must supply as abstract.

30
Subclass

Declare extends

Create EmailNotification and SmsNotification that extend the base and inherit its members automatically.

40
Chain

Call super in constructors

Each subclass constructor calls super(...) first so inherited fields and invariants are set before subtype-specific setup runs.

50
Override

Specialize methods

Override formatBody() per channel. Where you only need to add behavior, override and call super to reuse the base version.

60
Protect

Scope shared state

Mark fields protected so subclasses can use them while outside callers cannot, keeping the public surface small.

70
Dispatch

Program to the base type

The dispatcher holds a list of Notification and calls send(). Dynamic dispatch selects the right override at runtime.

80
Guard

Respect the base contract

Every override must honor the base promise: no throwing where the base returns, no strengthening preconditions. This keeps substitution safe.

90
Watch

Limit depth and coupling

Keep the tree shallow. A base change should not silently break subclasses. Deep hierarchies are where the fragile base class problem bites.

100
Ship

Extend by adding subclasses

A new channel is one new subclass implementing the contract, with no edits to existing senders. That is the payoff of a clean hierarchy.

Common Pitfalls

Pitfalls & anti-patterns

Inheritance fails loudest when it is used for reuse rather than for a true subtype relationship. These are the usual culprits.

🏚️ Fragile base class

A harmless-looking change to the base, like reordering internal calls, silently breaks subclasses that depended on the old flow. The deeper the tree, the wider the blast radius.

🧱 Inheriting for reuse only

Subclassing ArrayList just to borrow methods, when your type is not really a list, drags along an API you cannot honor. If it is not an is-a, use composition.

🚫 Breaking substitution

An override that throws where the base returns, or narrows accepted inputs, violates the base contract. Callers holding a base reference get surprised at runtime.

🕳️ Deep hierarchies

Five levels of extends means behavior is smeared across the chain. Understanding one method requires reading the whole ancestry, and every change ripples down.

🔓 Leaky protected state

Exposing too many protected fields turns internals into an unofficial API. Subclasses lock onto them, and you can no longer refactor the base freely.

🧨 Calling overridable methods in constructors

The base constructor calls an overridden method before the subclass has initialized its fields, so the override runs against half-built state and misbehaves.

Signals & Metrics

Signals & how to measure

Healthy inheritance stays shallow, honors its contracts, and rarely forces base edits. Watch these signals to catch decay early.

SignalWhat it tells you
Hierarchy depthChains deeper than two or three levels usually mean behavior is hard to trace and a candidate for flattening or composition.
Base change rippleHow many subclasses break when the base changes. High ripple is the fragile base class problem in numbers.
Override obligationThe count of abstract methods a subclass must implement. Too many means the base is doing too little to justify the coupling.
Liskov violationsTests that pass on the base but fail on a subclass signal that a subtype is not truly substitutable.
Protected surface sizeA large protected member set means subclasses depend on internals, shrinking your freedom to refactor.
super-call ratioOverrides that never call super may be replacing rather than extending, hinting the base abstraction is off.
Rule of thumb: if a change to the base class regularly forces edits or breaks tests in subclasses, the hierarchy is fragile. Favor shallow trees, small protected surfaces, and composition when the relationship is has-a rather than is-a.
06 - Case Studies

Real-world case studies

Three representative systems where inheritance models a genuine type hierarchy.

💳

1 · Payment gateway adapters

Pattern: base charge flow, provider-specific overrides

A checkout service integrates several payment providers that share a lifecycle but differ in the actual API call.

  • A PaymentGateway base owns validation, idempotency keys, and the retry loop.
  • StripeGateway and AdyenGateway override only the provider request, calling super for shared handling.
  • The order service programs to the base type, so adding a provider is one new subclass.
✅ Outcome: New processors ship without touching checkout, and shared safety logic lives in exactly one place.
🧾

2 · Payroll employee types

Pattern: is-a hierarchy for pay calculation

A payroll engine computes pay for salaried, hourly, and commission employees that share identity and tax handling.

  • An Employee base holds tax withholding and pay-stub formatting.
  • SalariedEmployee, HourlyEmployee, and CommissionEmployee override calculateGrossPay().
  • The run loop treats every worker as an Employee and never branches on type.
✅ Outcome: Adding a new worker classification means one subclass and the pay run stays untouched and correct.
🖼️

3 · UI component frameworks

Pattern: base widget, specialized controls

A component toolkit models controls as a hierarchy where every widget shares layout and event plumbing.

  • A base View or Component handles measure, layout, and the render lifecycle.
  • Buttons, text fields, and lists extend it and override render and event hooks.
  • The framework walks a tree of base references and drives everything through the shared lifecycle.
✅ Outcome: Widget authors reuse the entire lifecycle and only implement what is truly specific to their control.
07 - Relevance

Modern relevance

Inheritance is no longer the default hammer it was in early OOP, but it remains the right tool for genuine is-a hierarchies and disciplined framework design.

🧩 Composition first

Modern guidance favors composition for reuse and reserves inheritance for true subtyping. Both belong in a healthy codebase, used for different jobs.

🧭 Interfaces over deep trees

Teams lean on interfaces and small traits to share contracts without dragging state, keeping hierarchies shallow and flexible.

🏛️ Frameworks still rely on it

UI toolkits, ORMs, and test frameworks expose base classes you extend. Inheritance remains the ergonomic extension point for lifecycles.

🔐 sealed and final

Languages add sealed and final so authors can cap hierarchies, taming the fragile base class problem by controlling who may extend.

📐 Liskov as a guardrail

The substitution principle is the litmus test for whether a subclass is honest. It keeps inheritance safe rather than merely convenient.

🧬 Mixins and traits

Ruby modules and similar mechanisms offer targeted behavior sharing without single-inheritance limits, blending reuse with clean contracts.

Bottom line: reach for inheritance only when a subtype truly is-a base type and shares its contract. Keep trees shallow, honor substitution, and prefer composition for plain reuse. Done that way, inheritance stays a precise modeling tool instead of a coupling trap.
