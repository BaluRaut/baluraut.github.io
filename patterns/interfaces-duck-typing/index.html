Interfaces & duck typing - coding to a contract, not a class

An interface is a contract: a set of methods a caller can rely on without knowing the concrete type behind them. Whether the language checks that contract by name (nominal) or by shape (structural), the payoff is the same - your checkout code talks to a PaymentGateway, and Stripe or PayPal can be swapped in without a single line of the caller changing.

01 - What

What are interfaces and duck typing?

An interface (or protocol) names a set of methods and their signatures without saying how they work. Any object that provides those methods satisfies the contract. Duck typing takes this to its logical end: if an object walks like a duck and quacks like a duck, the runtime treats it as a duck, no declared interface required. Both let calling code depend on what an object can do, not on which class it is.

📜 Contract

An interface lists the methods a collaborator must expose, like charge(amount, token) and refund(chargeId). The caller trusts the shape, not the source.

🏷️ Nominal typing

A type conforms only if it explicitly declares that it does, by name. Java and C# work this way: a class must say implements PaymentGateway.

🦆 Structural / duck typing

A type conforms if it has the right shape, no declaration needed. TypeScript checks structure at compile time; Ruby and Python check it at call time.

The core building blocks

PieceWhat it doesExample
Interface / ProtocolDeclares the required method signaturesPaymentGateway with charge, refund
ImplementationA concrete class that fulfills the contractStripeGateway, PayPalGateway
ConsumerCode that depends on the interface, not the classA CheckoutService taking any gateway
Conformance checkHow the language verifies the contract holdsCompile-time (TS) or runtime (Ruby, Python)
SubstitutabilitySwapping one implementation for another safelyStripe in prod, a fake gateway in tests
Key mental model: an interface is a promise about behavior. Nominal typing verifies the promise by a signed declaration; duck typing verifies it by watching the object actually keep it. Either way, the consumer never needs to know the concrete class.
02 - Why

Why interfaces exist

Concrete classes couple code to specifics. Interfaces let you name only the behavior you need, so implementations become interchangeable, testable, and safe to evolve.

🔌 Swappable implementations

A CheckoutService that accepts any PaymentGateway can move from Stripe to PayPal, or run both, without touching its own logic. The contract is the seam.

🧪 Testable in isolation

Because the consumer depends on an interface, tests inject a fake gateway that records calls instead of hitting a real payment API. Fast, deterministic, no network.

🧱 Decoupled modules

Teams agree on the contract, then build both sides independently. The billing team and the checkout team never share concrete types, only the interface.

🔭 Clear expectations

An interface documents exactly what a collaborator must provide. New engineers read the contract and know what to implement, without reverse-engineering a class.

In Plain Terms

Interfaces & duck typing explained with analogies

Same idea, four ways to picture it, so it clicks whoever you are.

🎓 For a student

An interface is the question sheet on an exam. It says which questions must be answered; it does not say your exact words. Any student whose answers cover every question passes, regardless of how they phrase them.

👩‍💻 For a developer

It is a type of plug socket. Your checkout code exposes a socket shaped PaymentGateway; Stripe and PayPal are appliances with matching plugs. The wall does not care which brand you plug in.

🏢 For a professional

Think of a job description. It lists the duties a role must perform. Whether you hire an internal team or an agency, anyone who can do the listed duties fills the role. The org chart depends on the role, not the person.

🎫 Everyday version

A theme park accepts anything that scans as a valid ticket. Paper stub, phone barcode, or wristband - the turnstile checks the behavior (it scans), not the material. That is duck typing at the gate.

03 - How

How it works under the hood

You define a PaymentGateway contract, write two concrete implementations, and let a consumer depend only on the contract. The language decides how conformance is checked: by declaration, by structure, or by behavior at call time.

🧾 Define the contract

Name the methods the consumer needs: charge(amountCents, token) returns a result, refund(chargeId) reverses one. Nothing about HTTP, keys, or vendors leaks in.

🔁 Program to the interface

The CheckoutService holds a PaymentGateway reference. At runtime it is a StripeGateway or PayPalGateway, chosen by configuration, and the service never asks which.

The same contract in three languages

// TypeScript: a nominal-looking interface checked structurally at compile time.
interface ChargeResult { id: string; ok: boolean; }

interface PaymentGateway {
  charge(amountCents: number, token: string): ChargeResult;
  refund(chargeId: string): boolean;
}

class StripeGateway implements PaymentGateway {
  constructor(private apiKey: string) {}
  charge(amountCents: number, token: string): ChargeResult {
    // POST https://api.stripe.com/v1/charges
    return { id: `ch_${token.slice(0, 6)}`, ok: amountCents > 0 };
  }
  refund(chargeId: string): boolean {
    return chargeId.startsWith("ch_");
  }
}

class PayPalGateway implements PaymentGateway {
  charge(amountCents: number, token: string): ChargeResult {
    return { id: `PAYID-${token.slice(0, 6)}`, ok: amountCents > 0 };
  }
  refund(chargeId: string): boolean {
    return chargeId.startsWith("PAYID");
  }
}

// CheckoutService is programmed to the interface, not a concrete gateway.
class CheckoutService {
  constructor(private gateway: PaymentGateway) {}
  pay(amountCents: number, token: string): ChargeResult {
    const result = this.gateway.charge(amountCents, token);
    if (!result.ok) throw new Error("Payment declined");
    return result;
  }
}

const checkout = new CheckoutService(new StripeGateway("sk_live_123"));
console.log(checkout.pay(4999, "tok_visa")); // { id: "ch_tok_vi", ok: true }

# Python: a Protocol gives structural typing; conformance is by shape, no inheritance.
from dataclasses import dataclass
from typing import Protocol

@dataclass
class ChargeResult:
    id: str
    ok: bool

class PaymentGateway(Protocol):
    def charge(self, amount_cents: int, token: str) -> ChargeResult: ...
    def refund(self, charge_id: str) -> bool: ...

class StripeGateway:  # note: no explicit base class needed
    def __init__(self, api_key: str) -> None:
        self.api_key = api_key
    def charge(self, amount_cents: int, token: str) -> ChargeResult:
        return ChargeResult(id=f"ch_{token[:6]}", ok=amount_cents > 0)
    def refund(self, charge_id: str) -> bool:
        return charge_id.startswith("ch_")

class PayPalGateway:
    def charge(self, amount_cents: int, token: str) -> ChargeResult:
        return ChargeResult(id=f"PAYID-{token[:6]}", ok=amount_cents > 0)
    def refund(self, charge_id: str) -> bool:
        return charge_id.startswith("PAYID")

class CheckoutService:
    def __init__(self, gateway: PaymentGateway) -> None:
        self.gateway = gateway  # any object matching the Protocol shape
    def pay(self, amount_cents: int, token: str) -> ChargeResult:
        result = self.gateway.charge(amount_cents, token)
        if not result.ok:
            raise RuntimeError("Payment declined")
        return result

checkout = CheckoutService(StripeGateway("sk_live_123"))
print(checkout.pay(4999, "tok_visa"))  # ChargeResult(id='ch_tok_vi', ok=True)

# Ruby: pure duck typing. No interface declaration; the object just responds to the methods.
ChargeResult = Struct.new(:id, :ok)

class StripeGateway
  def initialize(api_key)
    @api_key = api_key
  end
  def charge(amount_cents, token)
    ChargeResult.new("ch_#{token[0, 6]}", amount_cents > 0)
  end
  def refund(charge_id)
    charge_id.start_with?("ch_")
  end
end

class PayPalGateway
  def charge(amount_cents, token)
    ChargeResult.new("PAYID-#{token[0, 6]}", amount_cents > 0)
  end
  def refund(charge_id)
    charge_id.start_with?("PAYID")
  end
end

# CheckoutService accepts any object that quacks like a payment gateway.
class CheckoutService
  def initialize(gateway)
    @gateway = gateway
  end
  def pay(amount_cents, token)
    result = @gateway.charge(amount_cents, token)
    raise "Payment declined" unless result.ok
    result
  end
end

checkout = CheckoutService.new(StripeGateway.new("sk_live_123"))
puts checkout.pay(4999, "tok_visa").inspect # #<struct ChargeResult id="ch_tok_vi", ok=true>

The three snippets are behaviorally identical, but the contract lives in different places. TypeScript writes it as an explicit interface checked at compile time. Python states it as a Protocol that classes satisfy structurally, no base class needed. Ruby writes no contract at all - the gateway simply responds to charge and refund, and any object that does can stand in.

Nominal vs structural: the same class, two checks

// Structural: a plain object with the right shape is accepted, even without `implements`.
const sandboxGateway = {
  charge(amountCents: number, token: string) {
    return { id: `test_${token}`, ok: true };
  },
  refund(chargeId: string) { return true; },
};

// No class, no `implements PaymentGateway`, yet it type-checks as one:
const testCheckout = new CheckoutService(sandboxGateway);
console.log(testCheckout.pay(100, "tok_test")); // accepted by structure alone

# Structural: a bare object satisfies the Protocol if it has the methods.
class SandboxGateway:
    def charge(self, amount_cents: int, token: str) -> ChargeResult:
        return ChargeResult(id=f"test_{token}", ok=True)
    def refund(self, charge_id: str) -> bool:
        return True

# CheckoutService never asked for a base class, only the shape:
test_checkout = CheckoutService(SandboxGateway())
print(test_checkout.pay(100, "tok_test"))  # accepted by structure

# Duck typing: conformance is decided at the moment charge is actually called.
sandbox_gateway = Object.new
def sandbox_gateway.charge(amount_cents, token)
  ChargeResult.new("test_#{token}", true)
end
def sandbox_gateway.refund(charge_id)
  true
end

test_checkout = CheckoutService.new(sandbox_gateway)
puts test_checkout.pay(100, "tok_test").inspect # works: it responds to charge

This is the difference in one screen. TypeScript and Python accept the sandbox object because its structure matches the contract, checked before the program runs. Ruby accepts it because, when pay calls charge, the object happens to respond, checked as it runs. A nominal language like Java would reject all three unless they said implements PaymentGateway.

05 - Step by Step

The 0 → 100 flow

From naming a contract to swapping vendors in production - the whole journey in order.

00
Need

Spot the varying collaborator

Checkout must take payments, but the vendor is a detail that changes. That variation is the signal to define a contract instead of hardcoding Stripe.

10

Define the interface

Write PaymentGateway with charge and refund. Capture only what the consumer needs, no keys or transport in the signature.

20

Program the consumer to it

CheckoutService accepts a PaymentGateway in its constructor and calls only the contract methods, never a concrete type.

30

Write StripeGateway

The first concrete class fulfills the contract by wrapping the Stripe API. It maps charge to a real HTTP call and returns a ChargeResult.

40
Verify

Confirm conformance

In TypeScript the compiler checks the shape; in Python a type checker validates the Protocol; in Ruby you rely on tests to exercise the methods.

50

Wire it at composition time

The app root constructs a StripeGateway and passes it into CheckoutService. The service stays ignorant of the choice.

60

Take a real payment

A customer checks out, pay calls charge through the interface, Stripe processes it, and the order is marked paid.

70

Swap in a fake

Unit tests inject a FakeGateway that satisfies the same contract and records calls, so checkout logic is tested with no network.

80

Add PayPalGateway

A second vendor arrives. Write a new class against the existing contract; not one line of CheckoutService changes.

90

Select at runtime

A factory picks Stripe or PayPal per region or per customer. The consumer holds a PaymentGateway and cannot tell which it received.

100
Evolve

Change vendors safely

Migrate traffic between gateways, deprecate one, or add a third. The contract absorbs the churn while the rest of the system stays stable.

Common Pitfalls

Pitfalls & anti-patterns

Interfaces are simple to declare and easy to misuse. These are the recurring mistakes.

🧿 Leaky abstractions

Putting stripeCustomerId or an HTTP status on the PaymentGateway interface drags vendor detail into the contract, so PayPal cannot implement it cleanly and the abstraction breaks.

🗑️ Fat interfaces

A gateway with twenty methods forces every implementation to stub ones it does not support. Keep contracts narrow so implementers only provide what consumers actually call.

🔎 isinstance checks everywhere

If CheckoutService asks if gateway is StripeGateway and branches, you have thrown away the interface. Behavior belongs in the implementation, not in type sniffing.

💥 Silent duck-typing gaps

In Ruby or Python, a missing refund is not caught until it is called in production. Without tests exercising each method, structural mismatches hide until the worst moment.

🎯 Contradicting the contract

An implementation that returns ok=true on a declined card technically matches the shape but violates the promise. Conforming to signatures is not the same as honoring behavior.

🏗️ Interface for a single impl

Extracting a PaymentGateway when only Stripe will ever exist adds indirection with no payoff. Introduce the contract when a second implementation or a test double is real.

Signals & Metrics

Signals & how to measure

You cannot unit-test "good design," but these observable signals tell you whether your interfaces are earning their keep.

SignalWhat it tells you
Implementations per interfaceTwo or more (including test doubles) means the contract is a real seam; exactly one forever suggests premature abstraction.
Consumer imports of concrete typesIf CheckoutService imports StripeGateway, the interface is not actually decoupling anything. Aim for zero.
Type-narrowing branchesCounting isinstance / is_a? checks against implementations shows where polymorphism leaked back into the caller.
Methods per interfaceSmall, cohesive interfaces (2-5 methods) are easy to implement; ballooning method counts signal a fat contract to split.
Test double effortIf faking the interface in a test is trivial, the contract is clean; if it drags in databases or HTTP, the abstraction is leaky.
Runtime NoMethodError rateIn duck-typed code, method-missing errors in production reveal structural gaps a compiler would have caught.
Rule of thumb: a healthy interface has few methods, at least two implementations, and zero concrete imports in its consumers. If a consumer ever inspects which class it received, the abstraction has already failed.
06 - Case Studies

Real-world case studies

Three production systems built around programming to an interface.

💳

1 · Marketplace payments over multiple gateways

Pattern: one PaymentGateway contract, many vendors

A marketplace needs Stripe in the US, PayPal in Europe, and a local processor in Brazil, without rewriting checkout per region.

  • Checkout depends only on PaymentGateway.charge and refund, never on a vendor SDK.
  • A factory selects the concrete gateway per buyer region at request time.
  • Adding the Brazilian processor is one new class implementing the existing contract.
✅ Outcome: new payment vendors ship as isolated classes, and checkout logic stays untouched and fully covered by tests using a fake gateway.
📣

2 · Notification delivery across channels

Pattern: a Notifier protocol for email, SMS, and push

A product sends order updates over email, SMS, and push, and wants to add Slack later without disturbing the sending code.

  • A Notifier protocol declares one method, send(recipient, message).
  • EmailNotifier, SmsNotifier, and PushNotifier each satisfy it structurally.
  • The dispatcher iterates over a list of notifiers, calling the contract, blind to the channel.
✅ Outcome: a Slack channel is added by writing one class that responds to send, with no change to the dispatcher.
🗄️

3 · Pluggable file storage in a Ruby app

Pattern: duck-typed Storage across local disk and S3

A Rails app stores user uploads on local disk in development and on S3 in production, decided by config.

  • Upload code calls store.put(key, io) and store.url(key) on whatever object it is given.
  • DiskStorage and S3Storage respond to the same methods; neither declares an interface.
  • Tests inject an in-memory storage double that quacks the same way, so no disk or network is touched.
✅ Outcome: the storage backend is a config switch, and duck typing keeps the upload path identical across disk, S3, and the test double.
07 - Relevance

Modern relevance

Interfaces and structural typing are quietly at the center of how modern languages and tools evolve.

🧩 Structural typing goes mainstream

TypeScript made structural typing familiar to millions; Go's implicit interfaces did the same on the backend. Conforming by shape, not declaration, is now a default expectation.

🐍 Gradual typing in dynamic languages

Python's Protocol and Ruby's RBS and Sorbet bring optional static contracts to duck-typed code, catching structural gaps before runtime without giving up flexibility.

🔗 Contracts at service boundaries

The same instinct scales up: OpenAPI and gRPC schemas are interfaces between services, letting teams build against a contract instead of a concrete server.

🧪 Test doubles by default

Programming to an interface is what makes fast, isolated tests possible. As suites grow, injecting fakes against a contract is standard practice, not a luxury.

🧱 Ports and adapters

Hexagonal architecture is interfaces all the way down: the domain defines ports, and adapters like a PaymentGateway plug in at the edges, keeping business logic vendor-free.

🤖 Tool contracts for agents

Even LLM tool-calling relies on a declared schema, an interface an agent programs against, so any tool matching the shape can be invoked without special-casing.

Bottom line: whether the language checks by name, by shape, or at call time, coding to a contract is how software stays swappable, testable, and free to evolve. Interfaces and duck typing are two answers to the same enduring question - depend on behavior, not on concrete types.
