Evals आणि LLM-as-Judge

LLM app खरोखर कसे मोजायचे - evals आणि judge

LLM आउटपुट non-deterministic असतात आणि क्वचितच एकच बरोबर उत्तर असते, त्यामुळे तुम्ही ते जुन्या पद्धतीने unit-test करू शकत नाही. Evals अंदाजांच्या जागी पुरावा आणतात: काळजीपूर्वक निवडलेले datasets, deterministic आणि semantic scorers, आणि एक LLM-as-judge जो मुक्त-स्वरूप मजकुराला rubric विरुद्ध गुण देतो - माणसांविरुद्ध calibrate केलेला आणि CI मध्ये जोडलेला जेणेकरून गुणवत्ता कधीही गुपचूप घसरणार नाही.

01 - काय

LLM evals म्हणजे काय?

एक eval म्हणजे LLM system एखादे काम किती चांगल्या प्रकारे करते याचे पुनरावर्ती मापन: ते एका निश्चित dataset वर चालवा, प्रत्येक आउटपुटला एक किंवा अधिक graders नी गुण द्या, आणि तुम्ही कालांतराने मागोवा घेऊ शकाल अशा metrics मध्ये एकत्रित करा. आउटपुट खुल्या स्वरूपाचे असल्याने, गुण देताना अनेकदा deterministic checks (exact match, JSON validity) यांचे semantic आणि LLM-as-judge grading सोबत मिश्रण केले जाते. उद्दिष्ट कोणत्याही test suite प्रमाणेच आहे - regressions पकडणे आणि सुधारणा सिद्ध करणे - पण ज्या मजकुराला एकच बरोबर string नाही त्याला अनुकूल केलेले.

🗂️ Dataset (प्रश्न)

काळजीपूर्वक निवडलेले inputs सोबत ऐच्छिक references किंवा अपेक्षित वर्तन - golden examples, नमुना घेतलेली real traffic, आणि हाताने तयार केलेली edge cases.

📏 Scorers (graders)

आउटपुटला गुणात रूपांतरित करणारी functions: deterministic नियम, semantic similarity, task-specific metrics, किंवा rubric असलेला LLM judge.

📊 Report (निकाल)

प्रत्येक slice नुसार एकत्रित केलेले metrics, baseline शी तुलना केलेले, जेणेकरून तुम्ही pass rate, faithfulness, आणि गुणवत्ता कुठे वर किंवा खाली गेली हे पाहू शकता.

मूलभूत घटक

घटकते काय करतेसामान्य पर्याय

02 - का

Evals का अस्तित्वात आहेत

जे तुम्ही मोजू शकत नाही ते तुम्ही ship करू शकत नाही. LLM वर्तन प्रत्येक prompt बदलासोबत, model upgrade सोबत, किंवा retrieval बदलासोबत बदलते - आणि ते गुपचूप बदलते. Evals "बरे वाटते" चे रूपांतर एका आकड्यात करतात, आणि कालच्या fix ला उद्याच्या regression होण्यापासून थांबवतात.

🎲 Non-determinism हाताळा

तोच prompt प्रत्येक वेळी वेगळा मजकूर देतो. Evals एका dataset वर सरासरी काढतात जेणेकरून तुम्ही distribution मोजता, एकच नशीबवान (किंवा दुर्दैवी) नमुना नाही.

🌫️ एकच बरोबर उत्तर नाही

अनेक कामांना अनेक स्वीकार्य आउटपुट असतात. Rubric-आधारित judging एकच अचूक string मागण्याऐवजी गुणवत्ता आणि correctness properties ला गुण देते.

🛡️ Regressions लवकर पकडा

एका case ला मदत करणारा prompt बदल दहा इतरांना बिघडवू शकतो. CI मध्ये evals चालवल्याने regression users पर्यंत पोहोचण्याआधीच अडवली जाते.

🚀 आत्मविश्वासाने ship करा

एकाच dataset वर candidate आवृत्त्यांची तुलना केल्याने एक prompt, model, किंवा retriever ला दुसऱ्यापेक्षा पुढे नेण्याचे बचावयोग्य कारण मिळते.

सोप्या भाषेत

उपमांसह evals समजून घेणे

एकच कल्पना, ती चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ते पटकन समजेल.

🎓 विद्यार्थ्यासाठी

एक eval म्हणजे answer key आणि rubric सह गुण दिलेली परीक्षा. तुम्ही एका निबंधाचा न्याय अंतःप्रेरणेने करत नाही; तुम्ही प्रत्येक विद्यार्थ्याला त्याच प्रश्नांविरुद्ध चालवता आणि पूर्ण, प्रामाणिक गुणांसाठी प्रत्येकाला स्पष्ट निकषांविरुद्ध तपासता.

👩‍💻 डेव्हलपरसाठी

हे गद्यासाठी test suite आहे. Deterministic checks म्हणजे तुमची assertions; LLM-as-judge म्हणजे ज्या मजकुराला एकच बरोबर string नाही त्यासाठी fuzzy matcher. ते CI मध्ये जोडा आणि कोणत्याही तुटलेल्या test प्रमाणे regression build अपयशी करते.

🏢 व्यावसायिकासाठी

scorecard असलेल्या QA reviewer चा विचार करा. काही calls केवळ भावनेने तपासण्याऐवजी, reviewer प्रातिनिधिक संच नमुना घेतो आणि प्रत्येकाला त्याच गुणवत्ता मानकाविरुद्ध गुण देतो, जेणेकरून निर्णय पुराव्यावर आधारित असतात, किस्स्यांवर नाही.

👨‍🍳 रोजच्या जीवनातील आवृत्ती

rubric card असलेल्या पाककला स्पर्धेच्या परीक्षकासारखे: चव, सादरीकरण, तंत्र. Rubric प्रत्येक पदार्थाला त्याच पद्धतीने गुण देत राहते, त्यामुळे विजेता फक्त शेवटी plate केलेला किंवा सर्वात मोठा भाग वाढणारा नसतो.

03 - कसे

Evals आतून कसे काम करतात

Evals दोन परिस्थितींमध्ये चालतात: offline काळजीपूर्वक निवडलेल्या dataset विरुद्ध (ship करण्याआधी), आणि online नमुना घेतलेल्या production traffic विरुद्ध (ship केल्यानंतर). दोन्ही त्याच scorers ला feed करतात; फक्त inputs चा स्रोत वेगळा असतो.

🧪 Offline eval harness

एक निश्चित dataset घ्या, प्रत्येक row वर तपासाधीन system चालवा, प्रत्येक आउटपुटला गुण द्या, आणि एकत्रित metrics ची साठवलेल्या baseline शी तुलना करा. Deterministic, पुनरुत्पादनीय, CI मध्ये gate करण्यायोग्य.

📡 Online (production) eval

Live traffic नमुना घ्या, real outputs वर reference-free judges आणि heuristics चालवा, आणि dashboards वर metrics चा मागोवा घ्या. तुमच्या dataset ने कधीही अपेक्षा न केलेली drift आणि edge cases पकडते.

Harness ची रचना एका दृष्टीक्षेपात

रचना - एक dataset तपासाधीन system मधून scorers आणि report मध्ये वाहते

Judge rubric prompt (reference-free scoring)

You are a strict grader. Score the ANSWER on each criterion
from 1-5. Judge only what is written. Do NOT reward length.
Return JSON only.

Criteria:
  - faithfulness:  every claim is supported by CONTEXT (no invented facts)
  - relevance:     the answer addresses the QUESTION directly
  - completeness:  no essential part of the question is ignored

CONTEXT:  {{context}}
QUESTION: {{question}}
ANSWER:   {{answer}}

Respond exactly as:
{"faithfulness": n, "relevance": n, "completeness": n,
 "rationale": "one sentence"}

guardrails लक्षात घ्या: एक निश्चित scale, verbosity bias शी लढण्यासाठी "do not reward length", deterministic parsing साठी JSON-only output, आणि scores auditable असावेत यासाठी एक अनिवार्य rationale. एखादा judge तेव्हाच विश्वासार्ह असतो जेव्हा त्याचे scores human labels विरुद्ध calibrated असतात.

"चांगले" म्हणजे काय ते ठरवा

काम आणि महत्त्वाच्या गुणांची नोंद करा - correctness, faithfulness, tone, safety. अस्पष्ट उद्दिष्टे निरुपयोगी evals निर्माण करतात.

10
Dataset

Golden set तयार करा

अपेक्षित उत्तरे किंवा वर्तनांसह प्रातिनिधिक inputs काळजीपूर्वक निवडा. लहानपासून सुरुवात करा (30–100 हाताने-तपासलेली cases) पण ती महत्त्वाची असू द्या.

20
समृद्ध करा

Real traffic आणि edge cases जोडा

वास्तववादी distribution साठी production logs नमुना घ्या, नंतर golden set चुकवते अशा adversarial आणि दुर्मिळ cases हाताने तयार करा.

30
Scorers

प्रत्येक case साठी metrics निवडा

जिथे exact/JSON उत्तर आहे तिथे deterministic checks वापरा; paraphrase साठी semantic similarity; खुल्या-स्वरूप गुणवत्तेसाठी judge.

40
Rubric

Judge rubric लिहा

स्पष्ट निकष आणि scoring scale ठरवा, length rewards ला मनाई करा, आणि auditability साठी JSON सोबत rationale ची मागणी करा.

50
Calibrate

Judge ला माणसांशी जुळवा

माणसांना एक slice label करू द्या, नंतर judge–human agreement मोजा. ते correlate होईपर्यंत rubric tune करा; अन्यथा judge खोटे बोलतो.

60
Debias

ज्ञात biases निष्प्रभ करा

Position bias टाळण्यासाठी A/B क्रम बदला, length cap करा किंवा normalize करा, आणि वेगळ्या model family ने judge करून self-preference टाळा.

70
Baseline

सध्याची system चालवा आणि नोंदवा

प्रत्येक slice साठी baseline metrics मिळवण्यासाठी संपूर्ण suite चालवा. हा गोठवलेला snapshot म्हणजे प्रत्येक भावी बदल ज्याविरुद्ध मोजला जातो तो.

80
Gate

Evals ला CI मध्ये जोडा

प्रत्येक PR वर suite चालवा आणि जेव्हा मुख्य metrics baseline threshold खाली येतात तेव्हा build अपयशी करा - एक कठोर regression gate.

90
Monitor

Online production evals जोडा

Live outputs नमुना घ्या, reference-free judges आणि heuristics चालवा, आणि offline set पकडू शकत नाही अशी drift पकडण्यासाठी trends dashboard करा.

100
पुनरावृत्ती

अपयशे परत feed करा

खरी अपयशे dataset मध्ये पुढे न्या, rubrics परिष्कृत करा, आणि पुन्हा baseline करा. Eval suite चे मूल्य प्रत्येक चक्रासोबत वाढत जाते.

सामान्य धोके

धोके आणि anti-patterns

बहुतेक eval अपयशे dataset आणि judge मुळे येतात, तपासाधीन मॉडेलमुळे नाही. हे नेहमीचे दोषी आहेत.

🔬 लहान, अप्रातिनिधिक संच

निवडक दहा cases real traffic ला व्यापत नाहीत. खेळण्यातल्या संचावरील उच्च pass rate काहीच सिद्ध करत नाही; तुम्ही कधीही नमुना न घेतलेली अपयशे तीच users पर्यंत पोहोचतात.

🎭 Judge bias

Judges गुपचूप पहिल्या पर्यायाला (position), लांब उत्तराला (verbosity), आणि त्यांच्या स्वतःच्या model family च्या outputs ला (self-preference) पसंती देतात. न बदललेले, न normalize केलेले judging ते biases थेट तुमच्या scores मध्ये भाजून टाकते.

🎚️ Uncalibrated judge

माणसांविरुद्ध कोणीही न तपासलेला judge म्हणजे rationale असलेला random number generator. मोजलेल्या judge-human agreement शिवाय, "4/5" चा काही अर्थ आहे की नाही हे तुम्हाला कळत नाही.

🎯 एकाच metric ला गेम करणे

एका एकत्रित आकड्याला optimize केल्याने Goodhart's law ला आमंत्रण मिळते: system खरी गुणवत्ता घसरत असतानाही metric जिंकायला शिकते. एक score तो ज्या प्रत्येक slice वर सरासरी काढतो त्यातील regressions लपवतो.

💧 Data leakage

जेव्हा eval cases prompt, few-shot examples, किंवा fine-tuning data मध्ये गळतात, तेव्हा system ला तिने आधीच पाहिलेल्या उत्तरांवर गुण दिले जातात. Scores गगनाला भिडतात आणि generalization हा एक भ्रम असतो.

🕰️ गोठवलेला eval set

जो eval कधीही नवीन failure modes शोषून घेत नाही तो हळूहळू वास्तव मोजणे थांबवतो. जर production आश्चर्ये dataset मध्ये परत वाहत नसतील, तर suite कालच्या bugs चे रक्षण करते आणि आजचे चुकवते.

कसे मोजायचे

Eval गुणवत्ता कशी मोजायची

तुमची eval suite स्वतःच एक अशी system आहे जिला मोजण्याची गरज आहे. हे संकेत तुम्हाला सांगतात की तिच्या निकालांवर विश्वास ठेवायचा की नाही.

Metricते तुम्हाला काय सांगतेचांगले चिन्ह
Judge-human agreementJudge किती जवळून human labels चा मागोवा घेतो (correlation / kappa)उच्च: judge scores वर विश्वास ठेवता येतो
Failure-mode coverageज्ञात failure प्रकारांपैकी किती वाटा dataset प्रत्यक्ष तपासतोउच्च: थोडे blind spots शिल्लक
Pass rate / score distributionनिकालांचा आकार, फक्त सरासरी नाही, slices वरनिरोगी पसरण, कोणतेही लपलेले cliffs नाहीत
Variance across runsतोच input चा score runs दरम्यान किती हलतोकमी: निकाल स्थिर आणि पुनरुत्पादनीय
Regression catch rateRelease आधी suite अडवते अशा खऱ्या regressions चे प्रमाणउच्च: gate खरोखर users चे रक्षण करते
Eval cost आणि runtimeसंपूर्ण suite चालवण्यासाठी token खर्च आणि wall-clock वेळप्रत्येक PR वर चालवण्याइतके स्वस्त आणि जलद
ढोबळ नियम: कोणत्याही score वर विश्वास ठेवण्याआधी judge calibrate करा. जर judge-human agreement कमी असेल, तर आधी rubric दुरुस्त करा; uncalibrated judge वर बांधलेली suite कितीही cases चालवली तरी noise मोजते.
06 - Case Studies

प्रत्यक्ष जगातील उदाहरणे

Production-शैलीच्या वापरात evals आणि LLM-as-judge दाखवणारे तीन प्रातिनिधिक नमुने.

🔗

1 · RAG faithfulness आणि groundedness मूल्यांकन

Pattern: retrieved context वर reference-free judge

एक टीम RAG assistant ship करते आणि उत्तरे तथ्ये शोधून काढण्याऐवजी retrieved passages मध्ये grounded राहतात याचा पुरावा हवा असतो.

  • प्रत्येक उत्तरासाठी, judge प्रत्येक दाव्याची retrieved context विरुद्ध तपासणी करतो आणि faithfulness सोबत answer-relevance ला गुण देतो.
  • Context recall वेगळे मोजले जाते जेणेकरून hallucination ला retrieval miss समजले जाऊ नये.
  • Judge चे scores releases gate करण्याआधी तो human groundedness labels विरुद्ध calibrate केला जातो.
✅ निकाल: Ungrounded उत्तरे आपोआप पकडली जातात, आणि टीम अपयशांचे कारण अंदाज लावण्याऐवजी retrieval किंवा generation ला देऊ शकते.
💬

2 · Chatbot गुणवत्ता regression suite

Pattern: CI gate म्हणून offline suite

एक support chatbot सतत संपादित केला जातो - नवीन prompts, नवीन tools, नवीन model आवृत्त्या - आणि प्रत्येक बदल आधीचे वर्तन गुपचूप बिघडवण्याचा धोका निर्माण करतो.

  • भूतकाळातील संभाषणांचा golden set सोबत खणून काढलेली अपयशे प्रत्येक pull request वर चालतात.
  • Deterministic checks रचना आणि refusals पडताळतात; rubric judge helpfulness आणि tone ला गुण देतो.
  • जर कोणतेही मुख्य metric त्याच्या baseline threshold खाली आले तर CI job merge अपयशी करते.
✅ निकाल: Regressions merge आधीच अडवली जातात, त्यामुळे एका intent साठी केलेला fix आता production मध्ये दहा इतरांना गुपचूप बिघडवू शकत नाही.
⚔️

3 · दोन prompt आवृत्त्यांचे pairwise judge ranking

Pattern: bias controls सह A/B तुलना

एका engineer कडे दोन candidate system prompts आहेत आणि "यापैकी कोणता खरोखर चांगला आहे?" याचे बचावयोग्य उत्तर हवे आहे.

  • दोन्ही prompts एकाच dataset वर चालतात; judge प्रत्येक case साठी pairwise चांगले आउटपुट निवडतो.
  • Position bias रद्द करण्यासाठी प्रत्येक जोडी क्रम बदलून दोनदा judge केली जाते, आणि length normalize केली जाते.
  • Confidence intervals सह win rate promotion ठरवते - मूठभर निवडक chats नाही.
✅ निकाल: विजेता prompt सांख्यिकीयदृष्ट्या प्रामाणिक win rate वर निवडला जातो, आणि debiasing पावले judge ला लांब किंवा पहिल्या उत्तराला पसंती देण्यापासून थांबवतात.
07 - भविष्य

Evals कुठे जात आहेत

Evals अधूनमधूनच्या spreadsheets पासून सतत, स्वयंचलित infrastructure कडे सरकत आहेत जी प्रत्येक LLM product च्या केंद्रस्थानी बसते.

🤖 Agentic आणि trajectory evals

फक्त अंतिम उत्तरे नव्हे तर संपूर्ण tool-using trajectory ला गुण देणे - agent ने योग्य पावले उचलली का, योग्य tools call केले का, आणि चुकांतून सावरले का?

🎚️ Auto-calibrated judges

Judges जे स्वतःला सतत ताज्या human labels शी जुळवतात, स्वतःचे agreement नोंदवतात जेणेकरून त्यांच्यावर किती विश्वास ठेवायचा हे तुम्हाला नेमके कळते.

🧬 Synthetic dataset generation

असे मॉडेल जे coverage वाढवण्यासाठी लक्ष्यित edge cases आणि adversarial inputs निर्माण करतात, माणसे हाताने जमवू शकतात त्यापेक्षा खूप पुढे.

⚖️ Bias-aware judging by default

Position, verbosity, आणि self-preference controls judge frameworks मध्ये भाजून टाकलेले - बदललेले orders, length normalization, cross-family graders.

📡 Observability म्हणून online evals

Live traffic वर reference-free scoring हे मानक telemetry बनते, drift पुढच्या release ऐवजी ती दिसताच पकडते.

🛡️ Safety आणि policy evals

Jailbreaks, toxicity, PII leakage, आणि policy compliance साठी समर्पित suites गुणवत्ता metrics सोबत release आवश्यकता म्हणून ship होतात.

सारांश: evals हे LLM युगाचे test suite आहे. Calibrated, debiased scorers सोबत जोडलेला काळजीपूर्वक निवडलेला dataset - CI मध्ये आणि production मध्ये चालवलेला - हेच अप्रत्याशित मॉडेलचे रूपांतर तुम्ही आत्मविश्वासाने ship आणि सुधारू शकता अशा product मध्ये करते.
