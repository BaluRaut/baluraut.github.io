Tool / Function-Calling रचना

Tool calling प्रत्यक्षात कसे चालते - संपूर्ण चित्र

एखादे language model स्वतःहून विमानाचे तिकीट बुक करू शकत नाही, query चालवू शकत नाही, किंवा आजची किंमत वाचू शकत नाही - ते फक्त मजकूर तयार करते. Tool calling ही दरी भरून काढते: तुम्ही तुमची functions typed schemas म्हणून वर्णन करता, गरज पडल्यावर model एक structured call तयार करते, तुमचे host ते चालवते, आणि निकाल परत संभाषणात येतो. हे loop पुन्हा पुन्हा चालवा आणि एक chat model असे agent बनते जे कृती करू शकते.

01 - काय

Tool calling म्हणजे काय?

Tool calling (याला function calling असेही म्हणतात) एखाद्या language model ला तुमच्या नियंत्रणातील code बोलावण्याची मुभा देते. तुम्ही model ला tool definitions ची यादी देता - प्रत्येकाला एक नाव, एक वर्णन, आणि त्याच्या arguments साठी एक JSON-Schema. जेव्हा model ठरवते की एखादे tool उपयोगी ठरेल, तेव्हा ते स्वतः काहीही चालवत नाही; ते tool आणि त्याचे arguments नमूद करणारी एक structured विनंती तयार करते. तुमचे application ते function चालवते आणि निकाल परत सोपवते, आणि model त्या नव्या माहितीसह पुढे चालू ठेवते.

📋 परिभाषित करा (तुम्ही)

Tools ला नाव + वर्णन + typed parameter schema म्हणून घोषित करा. हा तो करार आहे जो model काय करू शकते हे ठरवण्यासाठी वाचते.

🛠️ ठरवा (model)

संभाषण आणि tools पाहून, model arguments सह एक structured tool_use block तयार करते - किंवा tool ची गरज नसल्यास थेट उत्तर देते.

↩️ चालवा आणि परत करा (तुम्ही)

तुमचे host args तपासते, function चालवते, आणि एक tool_result परत पाठवते जेणेकरून model उत्तर पूर्ण करू शकेल.

02 - का

Tool calling का अस्तित्वात आहे

स्वतःच एक model म्हणजे एक बंद पेटी आहे: कोणताही live data नाही, कोणतेही side effects नाहीत, विश्वास ठेवता येईल असे कोणतेही गणित नाही. Tool calling ते एका controller मध्ये बदलते जो कोणती कृती करायची याबद्दल विचार करते, तर तुमचा code प्रत्यक्ष कृती करतो - विश्वासार्हपणे, पडताळणीयोग्य पद्धतीने आणि तुमच्या नियमांच्या आत.

🌐 Real-time आणि खाजगी data

आजचा साठा, ग्राहकाची नोंद, किंवा live किंमत आणा. Model विचार करते; तुमचे tool त्याने कधीही लक्षात न ठेवलेले ठोस सत्य पुरवते.

🎬 खऱ्या कृती करा

ईमेल पाठवा, तिकीट उघडा, deployment चालवा. Tools एका model ला गोष्टी फक्त वर्णन करण्याऐवजी त्या प्रत्यक्ष करण्याची मुभा देतात - chat ला agent मध्ये बदलतात.

📐 Structured, विश्वासार्ह outputs

एक JSON-Schema arguments ना typed, तपासलेल्या आकारांत बसवते, त्यामुळे तुम्हाला अंदाज बांधावा लागणाऱ्या free-text ऐवजी parse करता येण्याजोगी रचना मिळते.

🔒 नियंत्रण आणि लेखापरीक्षणक्षमता

प्रत्येक कृती तुमच्या executor मधून जाते, जिथे तुम्ही permissions लागू करता, calls ची नोंद ठेवता, आणि कोणतीही धोकादायक गोष्ट पुष्टीकरणामागे बंद करता.

सोप्या शब्दांत

उपमांसह tool calling समजावून सांगितले

तीच कल्पना, कल्पना करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

Tool calling म्हणजे घरी सोडवायच्या परीक्षेसारखे आहे जिथे तुम्ही calculator वापरू शकता. विचार तुम्हीच करता, पण गणितासाठी तुम्ही calculator वर नेमके आकडे भरता, बटण दाबता, आणि निकाल तुमच्या उत्तरात परत उतरवता.

👩‍💻 developer साठी

हे म्हणजे model एक typed API बोलावते. तुम्ही function signatures JSON-Schema म्हणून प्रसिद्ध करता; model एक structured argument object परत करते; तुमचा code खरे function चालवतो आणि मूल्य परत करतो, अगदी एखाद्या RPC सारखे जिथे model हा caller असतो.

🏢 व्यावसायिकासाठी

एका manager चा विचार करा जो योग्य विनंती फॉर्म भरून काम सोपवतो. Manager काय करायचे ते ठरवतो आणि तपशील निश्चित करतो, पण एक तज्ज्ञ प्रत्यक्ष ते पार पाडतो आणि निकाल परत कळवतो.

🍽️ रोजच्या जीवनातील आवृत्ती

एक waiter जो structured order स्वयंपाकघरात नेतो. Waiter स्वयंपाक करत नाही; तुम्हाला जे हवे ते नेमके स्वयंपाकघराला समजेल अशा फॉर्ममध्ये लिहितो, तो सोपवतो, आणि तयार पदार्थ परत आणतो.

03 - कसे

ते आतून कसे चालते

Tool calling हे एका विनंतीऐवजी एक multi-turn loop आहे. Host tools अधिक संभाषण पाठवते; model एका उत्तराने किंवा एक किंवा अधिक tool_use blocks ने प्रत्युत्तर देते; host ते चालवते आणि tool_result blocks जोडते; model पूर्ण होईपर्यंत loop पुन्हा चालते.

🧩 करार

प्रत्येक tool म्हणजे name + description + parameters चा JSON-Schema (types, enums, आवश्यक fields). Model हे documentation सारखे वाचते जेणेकरून tool निवडावे आणि त्याचे arguments आकारावेत.

🔁 loop

Model एका call ची विनंती करते → host ते तपासते आणि चालवते → host निकाल परत करते → model तो वाचते आणि पुन्हा call करते किंवा उत्तर देते. Parallel calls पसरतात आणि model पुढे जाण्यापूर्वी पुन्हा एकत्र येतात.

एक tool schema आणि call loop

// 1) You declare the tool (name + description + JSON-Schema)
{
  "name": "get_weather",
  "description": "Get the current weather for a city. Use when the user asks about weather.",
  "input_schema": {
    "type": "object",
    "properties": {
      "city":  { "type": "string", "description": "City name, e.g. 'Paris'" },
      "units": { "type": "string", "enum": ["celsius", "fahrenheit"], "default": "celsius" }
    },
    "required": ["city"]
  }
}

// 2) The loop the host runs
messages = [ user("What's the weather in Paris?") ]
while True:
    reply = model.generate(messages, tools=[get_weather, ...])
    if reply.stop_reason != "tool_use":
        return reply.text                      # model is done
    for call in reply.tool_calls:              # may be several (parallel)
        args   = validate(call.input, schema)  # reject bad args early
        result = registry[call.name](**args)   # actually run it
        messages.append(tool_result(call.id, result))
    messages.append(reply)                      # keep the tool_use turn too

प्रत्येक tool_result ला त्याच्या उगमस्थानी असलेल्या tool_use शी जोडणारा id लक्षात घ्या, आणि host - model कधीही नाही - हीच अशी गोष्ट आहे जी arguments तपासते आणि code चालवते. ती सीमा म्हणजे जिथे सुरक्षितता राहते.

पोहोचवा

कृतींवर आधारित उत्तर

वापरकर्त्याला खऱ्या data आणि खऱ्या परिणामांतून बांधलेले प्रत्युत्तर मिळते. प्रत्येक call च्या नोंदी काळानुरूप evals आणि guardrail tuning ला पुरवतात.

सामान्य धोके

धोके आणि anti-patterns

बहुतांश tool-calling अपयश tool च्या रचनेतून येतात, model मधून नाही. हे नेहमीचे गुन्हेगार आहेत.

🧰 खूप जास्त, परस्परव्यापी tools

Model ला डझनभर tools देणे, ज्यांतील अनेक जवळपास सारखीच कामे करतात, निवडीची अचूकता बिघडवते. ते चुकीचे निवडते किंवा घुटमळते. कामापुरता एक लहान, वेगळा संच उघड करा.

🏷️ अस्पष्ट नावे आणि वर्णने

do_thing सारखी नावे आणि एका ओळीची वर्णने model ला कधी आणि कसे call करायचे याचा अंदाज लावायला लावतात. वर्णन हे prompt आहे, ते tool नेमके काय करते आणि कधी वापरायचे हे सांगण्यासाठी लिहा.

🚫 न तपासलेली arguments

Model ने तयार केलेल्या arguments वर विश्वास ठेवून त्या थेट API ला देणे चुकीच्या तारखा, injection, आणि मर्यादेबाहेरील मूल्यांना आमंत्रण देते. चालवण्यापूर्वी schema विरुद्ध types, enums, आणि ranges तपासा.

💥 Non-idempotent side effects

पुष्टीकरण किंवा idempotency key नसलेल्या write कृती retry वर दुहेरी शुल्क, दुहेरी बुकिंग, किंवा दुहेरी पाठवणी करतात. विध्वंसक कृती मंजुरीमागे बंद करा आणि त्यांना key द्या जेणेकरून replays सुरक्षित असतील.

♻️ error handling नाही / अनंत retry

कच्चे stack traces परत करणे, किंवा त्याच अपयशी call वर सदैव loop करणे, tokens जाळते आणि agent अडवते. एक स्पष्ट is_error संदेश परत करा आणि retries ला मर्यादा घाला जेणेकरून model जुळवून घेईल किंवा थांबेल.

📜 अवाढव्य JSON schemas

खोल nesting, डझनभर वैकल्पिक fields, आणि वर्णने नसलेली विस्तृत schemas model ला गोंधळवतात आणि prompt फुगवतात. Parameter आकार सपाट, किमान, आणि स्पष्टपणे documented ठेवा.

कसे मोजावे

Tool calling कसे मोजावे

Selection आणि execution वेगवेगळे मोजा, जेणेकरून tool संच दुरुस्त करायचा की tools स्वतः हे तुम्हाला कळेल.

06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

उत्पादन-शैलीच्या वापरात tool calling दाखवणारे तीन प्रातिनिधिक नमुने.

✈️

1 · प्रवास आणि बुकिंग सहाय्यक

नमुना: संरक्षित कृतींसह multi-step tool orchestration

एक प्रवास सहाय्यक सुरुवातीपासून शेवटपर्यंत सहलींची योजना करते - विमाने शोधणे, हॉटेल तपासणे, नंतर बुकिंग - read-only lookups ला खऱ्या, side-effecting खरेदींशी मिसळते.

  • Read tools (search_flights, get_hotel_availability) मुक्तपणे चालतात आणि पर्यायांची त्वरित तुलना करण्यासाठी अनेकदा parallel मध्ये.
  • Write tool book_flight संरक्षित आहे: त्याला स्पष्ट वापरकर्ता पुष्टीकरण लागते आणि एक idempotency key धारण करते जेणेकरून retry कधीही दुहेरी बुकिंग करत नाही.
  • Typed, मर्यादित params (IATA codes, ISO dates, प्रवासी संख्या) कोणत्याही provider call आधी तपासली जातात, आणि त्रुटी model ला पुन्हा विचारल्या जातात.
✅ निष्कर्ष: सहाय्यक गुंतागुंतीच्या सहलींची योजना करते आणि बुक करते, तर एक कडक host सीमा खरेदी सुरक्षित, पुष्ट, आणि कधीही अपघाताने पुनरावृत्त न होणारी ठेवते.
📊

2 · query tool असलेला data विश्लेषक

नमुना: natural language पासून structured, read-only queries

एक analytics सहाय्यक warehouse वरील एका एकल, घट्ट-मर्यादित query tool द्वारे व्यावसायिक प्रश्नांना SQL मध्ये बदलून उत्तरे देते.

  • run_sql tool एक query string स्वीकारते पण row limits आणि statement timeout असलेल्या read-only replica विरुद्ध चालते.
  • Structured निकाल typed rows म्हणून परत येतात ज्यांचा model सारांश करू शकते, chart करू शकते, किंवा follow-up call ने खोलात जाऊ शकते.
  • सदोष किंवा असुरक्षित queries validation द्वारे नाकारल्या जातात आणि त्रुटी म्हणून परत केल्या जातात, ज्यामुळे model परिष्कृत करून पुन्हा प्रयत्न करते.
✅ निष्कर्ष: तांत्रिक नसलेल्या वापरकर्त्यांना अचूक, data-आधारित उत्तरे मिळतात, तर एक मर्यादित tool warehouse ला बेलगाम किंवा विध्वंसक queries पासून सुरक्षित ठेवते.
🔧

3 · संरक्षित कृती करणारा DevOps agent

नमुना: idempotency आणि मंजुरीसह side-effecting operations

एक on-call सहाय्यक घटनांची छाननी करते - logs आणि metrics वाचणे, नंतर service scale करणे किंवा deploy परत आणणे यासारखे उपाय अंमलात आणणे.

  • Diagnostic tools (get_logs, get_metrics) read-only आणि जलद तपासासाठी अनिर्बंध आहेत.
  • Action tools (scale_service, rollback) ना एक मंजुरी टप्पा लागतो आणि ते idempotency keys सह चालतात जेणेकरून replays सुरक्षित असतात.
  • प्रत्येक call actor, arguments, आणि निकालासह पूर्ण audit trail साठी नोंदवले जाते, आणि विध्वंसक कृती आधी dry-run mode ला support करतात.
✅ निष्कर्ष: Agent पुराव्यावर कृती करून time-to-recovery कमी करते, तर मंजुरी, idempotency, आणि audit logs प्रत्येक कृती उलट करण्याजोगी आणि जबाबदार ठेवतात.
07 - भविष्य

Tool calling कोणत्या दिशेने चालले आहे

Tool calling एका एकल function invocation पासून agentic systems च्या कण्यात विकसित होत आहे - प्रमाणित, composable, आणि रचनेनेच अधिक सुरक्षित.

🔌 MCP आणि standard tool protocols

Model Context Protocol सारखे open standards कोणत्याही model ला कोणत्याही tool server शी जोडू देतात, त्यामुळे integrations वैयक्तिक ऐवजी plug-and-play बनतात.

🤝 Multi-agent tool सामायिकरण

विशेष agents त्यांची कौशल्ये एकमेकांना tools म्हणून उघड करतात, अशा systems मध्ये रचना करतात जिथे प्रत्येक agent subtask साठी योग्य साथीदाराला बोलावते.

🛡️ बारीक permissions

Capability scopes, per-tool policies, आणि human-in-the-loop gates side-effecting कृती लेखापरीक्षणयोग्य आणि रचनेनेच सुरक्षित बनवतात.

⚡ अधिक हुशार parallelism

Models वाढत्या प्रमाणात एकाच वेळी स्वतंत्र calls ची योजना आणि पाठवणी करतात, अनेक systems ना स्पर्श करणाऱ्या कामांची latency कमी करतात.

🎯 Tool-use evals first-class म्हणून

Selection अचूकता, argument validity, आणि त्रुटींतून सावरणे मोजणे हा agent विश्वासार्हतेवर नियंत्रण ठेवणारा मापदंड बनतो.

🧠 स्वतः दुरुस्त करणारे agents

Agents जे tool त्रुटी वाचतात, विचार करतात, आणि दुरुस्त केलेल्या arguments सह पुन्हा प्रयत्न करतात - ठिसूळ calls ना मजबूत, लवचिक workflows मध्ये बदलतात.

सारांश: tool calling हा तो मार्ग आहे ज्याद्वारे एक केवळ-मजकूर model अशी system बनते जी live data पाहू शकते आणि खरी कृती करू शकते - तुमच्या validation, permissions, आणि audit च्या अंतर्गत. जसे protocols प्रमाणित होतात आणि agents रचना करतात, तसे उत्तम-रचित tools कोणत्याही AI उत्पादनाचा सर्वात टिकाऊ भाग बनतात.
