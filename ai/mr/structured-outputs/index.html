Structured Outputs

structured outputs मजकुराचे विश्वसनीय डेटामध्ये रूपांतर कसे करतात

LLMs गद्यात बोलतात, पण सॉफ्टवेअरला डेटा हवा असतो. Structured outputs मॉडेलकडून मशीन-वाचनीय JSON परत मिळवतात जे तुम्ही ठरवलेल्या schema नुसार असते, त्यामुळे त्याची उत्तरे थेट तुमच्या कोड, APIs आणि databases मध्ये उतरतात, ठिसूळ string parsing किंवा नशिबावर सोडलेल्या regex शिवाय.

01 - काय

structured outputs म्हणजे काय?

Structured outputs ही मॉडेलची अशी उत्तरे आहेत जी मुक्त गद्याऐवजी तुम्ही आधीच ठरवलेल्या मशीन-वाचनीय आकाराचे अनुसरण करतात - सहसा schema शी जुळणारे JSON. तुम्ही मॉडेलला एक करार देता ("या fields आणि या types असलेला object परत करा"), आणि उत्तर डेटा म्हणून परत येते जे तुमचा प्रोग्राम थेट parse, validate आणि वापरू शकतो.

📐 आकार ठरवा

तुम्ही उद्दिष्ट JSON Schema किंवा typed model (Pydantic, zod) म्हणून वर्णन करता. हाच तो करार आहे जो output ने पूर्ण केला पाहिजे.

🔒 generation मर्यादित करा

मॉडेलला असे मार्गदर्शन केले जाते की तो फक्त तेच tokens देतो जे output ला schema नुसार वैध ठेवतात, त्यामुळे तो गद्याकडे भरकटू शकत नाही.

✅ Parse & validate

निकाल typed object मध्ये parse आणि validate केला जातो. जे काही निसटते ते तुमच्या कोडपर्यंत पोहोचण्याआधीच पकडले जाते.

पद्धतींचा वर्णपट

पद्धतती काय करतेहमी

02 - का

structured outputs का अस्तित्वात आहेत

गद्य माणसांसाठी उत्तम आणि मशीनसाठी भयंकर आहे. ज्या क्षणी एखादे LLM output दुसऱ्या यंत्रणेला दिले जाते - database, API call, UI component - तेव्हा तुम्हाला एक अपेक्षित आकार हवा असतो, ज्याचे उलगडून विश्लेषण करावे लागेल असा परिच्छेद नाही.

🔌 मुळातच मशीन-वाचनीय

पुढील यंत्रणा वाक्ये नव्हे तर fields वापरतात. हमी दिलेले schema म्हणजे तुम्ही ठिसूळ मजकूर काढणीशिवाय output index, store आणि route करू शकता.

🧱 कमी parsing अपयश

"साधारण JSON सारख्या" मजकुरावर आता regex नको. Constrained decoding "मॉडेलने कंसाआधी एक गोड वाक्य जोडले" या संपूर्ण प्रकारच्या bugs काढून टाकते.

🧩 विश्वसनीय tool & API calls

Function आणि tool calling हे मुळात structured output आहे - arguments ने tool च्या parameter schema शी अगदी तंतोतंत जुळावे लागते नाहीतर call अपयशी होते.

🤝 components मधील करार

Schema म्हणजे typed interface. Producers आणि consumers त्यावर सहमत होतात, त्यामुळे संघ प्रत्येक बाजू स्वतंत्रपणे विकसित करू शकतात आणि लवकर विचलन पकडू शकतात.

सोप्या शब्दांत

उपमांसह structured outputs समजावले

एकच कल्पना, चित्रित करण्याचे चार मार्ग, म्हणजे तुम्ही कोणीही असाल तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

हे निबंधाऐवजी बहुपर्यायी उत्तरपत्रिका आहे. तुम्ही समासात खरडू शकत नाही; तुम्ही अचूक चौकटी भरता, म्हणजे तपासणी यंत्र तुमची उत्तरे तत्काळ वाचू शकते.

👩‍💻 डेव्हलपरसाठी

हे कच्च्या string ऐवजी typed return value आहे. Function signature एका आकाराचे वचन देते, आणि type checker तुमच्या logic पर्यंत पोहोचण्याआधीच न जुळणारे काहीही नाकारतो.

🏢 व्यावसायिकासाठी

एका प्रमाणित नोंदणी अर्जाचा विचार करा. प्रत्येक अर्जदार नाव, तारीख आणि रक्कम त्याच जागी देतो, त्यामुळे प्रक्रिया एकसमान राहते आणि काहीही चुकीच्या ठिकाणी दाखल होत नाही.

📝 रोजची आवृत्ती

लेबल केलेल्या चौकटी असलेला काटेकोर कागदी अर्ज भरण्यासारखे: प्रत्येक चौरसात एक अक्षर, तारीख DD/MM/YYYY मध्ये. चौकटी आकार लादतात, त्यामुळे नंतर वाचणाऱ्याला कधीही अंदाज लावावा लागत नाही.

03 - कसे

हे आतून कसे कार्य करते

Structured output चे दोन हलणारे भाग आहेत: generation दरम्यान constraint, जो मॉडेल काय देऊ शकतो त्याला आकार देतो, आणि generation नंतर validation, जे निकाल पडताळून तुमचा कोड विश्वास ठेवू शकेल अशा typed object मध्ये coerce करते.

🔒 Constrained decoding

प्रत्येक टप्प्यावर decoder ठरवतो कोणते tokens output ला schema नुसार वैध ठेवतील, बाकीचे शून्य संभाव्यतेवर लपवतो, आणि फक्त उरलेल्यातूनच sample घेतो. अवैध JSON तयार करणे अशक्य होते.

✅ आधी validate मग coerce

कच्चा मजकूर parse केला जातो आणि typed model विरुद्ध तपासला जातो. गहाळ fields, चुकीचे types, किंवा जादा keys नाकारल्या जातात, आणि अपयशी तपासणी crash ऐवजी आपोआप reask सुरू करू शकते.

Python मधील एक वास्तविक structured call

from pydantic import BaseModel, Field
from openai import OpenAI

class Invoice(BaseModel):
    vendor: str
    invoice_number: str
    total_amount: float = Field(ge=0)
    currency: str = Field(pattern=r"^[A-Z]{3}$")
    due_date: str  # ISO 8601

client = OpenAI()

# The SDK sends Invoice's JSON Schema and constrains decoding to it.
resp = client.chat.completions.parse(
    model="gpt-model",
    messages=[
        {"role": "system", "content": "Extract invoice fields from the text."},
        {"role": "user", "content": document_text},
    ],
    response_format=Invoice,   # schema-constrained output
)

invoice: Invoice = resp.choices[0].message.parsed
save_to_ledger(invoice)        # already a validated, typed object

response_format हीच संपूर्ण युक्ती आहे: Invoice पासून मिळवलेले schema generation ला मार्गदर्शन करते आणि निकाल validate करते, त्यामुळे parsed हा खरा typed object असतो, तुम्हाला अजूनही विश्वास ठेवावा लागणारा string नाही.

04 - Sequence Diagrams

सविस्तर sequence diagrams

तीन दृश्ये: token-by-token constrained decoding, validate-then-reask loop, आणि schema पासून पुढील बाजूला दिलेल्या typed object पर्यंतचा संपूर्ण मार्ग.

आकृती 1 - Constrained decoding: schema ची token by token अंमलबजावणी
sequenceDiagram
    autonumber
    participant App as 🖥️ App
    participant Dec as ⛓️ Decoder
    participant SM as 📐 Schema mask
    participant LM as 🧠 Language model

    App->>Dec: generate(prompt, schema)
    Dec->>SM: compile schema to token constraints
    SM-->>Dec: valid next-token set
    loop for each token
        Dec->>LM: next-token logits
        LM-->>Dec: raw probabilities
        Dec->>SM: which tokens keep JSON valid
        SM-->>Dec: allowed token mask
        Dec->>Dec: mask illegal tokens then sample
    end
    Dec-->>App: guaranteed schema-valid JSON
आकृती 2 - output schema मध्ये अपयशी झाल्यावर validate मग reask
sequenceDiagram
    autonumber
    participant App as 🖥️ App
    participant LLM as 🧠 LLM
    participant Val as 🔍 Validator

    App->>LLM: prompt + schema
    LLM-->>App: candidate JSON
    App->>Val: validate(candidate, schema)
    alt valid
        Val-->>App: typed object
        App-->>App: proceed
    else invalid
        Val-->>App: errors (wrong type, missing field)
        loop until valid or max retries
            App->>LLM: reask with errors + prior output
            LLM-->>App: corrected JSON
            App->>Val: validate again
        end
        Note over App,Val: give up gracefully after max retries
    end
आकृती 3 - Schema पासून prompt पासून generate पासून पुढील service साठी typed object पर्यंत
sequenceDiagram
    autonumber
    participant Dev as 👩‍💻 Schema author
    participant App as 🖥️ App
    participant LLM as 🧠 LLM
    participant Svc as 🚀 Downstream service

    Dev->>App: define typed model (Pydantic / zod)
    App->>App: derive JSON Schema from model

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

असंरचित विनंतीपासून तुमच्या यंत्रणांमध्ये वाहणाऱ्या validate केलेल्या, typed object पर्यंत - संपूर्ण प्रवास क्रमाने.

00
Model

उद्दिष्ट आकार ठरवा

इच्छित output typed model किंवा JSON Schema म्हणून लिहा: fields, types, enums, आवश्यक keys, आणि ranges व patterns सारख्या मर्यादा.

10
Derive

schema तयार करा

Typed model (Pydantic, zod) provider समजू शकेल अशा JSON Schema मध्ये रूपांतरित करा. हाच तो करार आहे ज्यावर दोन्ही बाजू सहमत असतात.

20
Prompt

विनंती जुळवा

तुमच्या सूचना schema सोबत एकत्र करा. प्रत्येक field चा अर्थ वर्णन करा म्हणजे मॉडेल केवळ योग्य type नव्हे तर योग्य मूल्य भरेल.

30
Constrain

output format जोडा

Schema response format म्हणून द्या म्हणजे provider मुक्त मजकुराऐवजी schema-constrained decoding चालू करतो.

40
Compile

token mask बनवा

Decoder schema ला अशा state machine मध्ये compile करतो जी प्रत्येक स्थानावर कोणते tokens JSON वैध ठेवतात हे जाणते.

50
Decode

constraint खाली generate करा

प्रत्येक टप्प्यावर मॉडेलचे logits परवानगी असलेल्या संचापुरते mask केले जातात, त्यामुळे तो फक्त वैध document पुढे नेणारे tokens देऊ शकतो.

60
Stream

आंशिक रचना द्या

पर्यायाने tokens येताच stream करा, वाढणारे JSON parse करा म्हणजे fields पूर्ण होताच UI ती render करू शकते.

70
Parse

मजकुराचे object मध्ये रूपांतर करा

पूर्ण झाल्यावर JSON parse करा आणि typed model मध्ये लोड करा, schema परवानगी देईल तिथे मूल्ये coerce करा.

80
Validate

business नियम तपासा

schema व्यक्त करू शकत नाही असे semantic validation चालवा - cross-field logic, संदर्भ तपासण्या, वाजवी ranges - केवळ type शुद्धतेच्या पलीकडे.

90
Reask

अपयशावर पुन्हा प्रयत्न करा

Validation अपयशी झाल्यास, errors आणि आधीचे output दुरुस्तीसाठी परत पाठवा, सुरळीत fallback आधी retry मर्यादेपर्यंत loop करा.

100
Deliver

typed object सुपूर्द करा

Validate केलेला object API, database, किंवा UI ला द्या. अपयश आणि reasks च्या logs evals ना पुरवतात ज्या कालांतराने schema घट्ट करतात.

सामान्य अडचणी

अडचणी & anti-patterns

वैध JSON आणि योग्य डेटा एकच नाहीत. production मध्ये चावा घेणारे हे अपयशाचे प्रकार आहेत.

✂️ Truncation

object च्या मध्येच token मर्यादा गाठल्यास असे JSON मिळते जे वैध सुरू होते आणि अचानक संपते. उदार max ठेवा, अपूर्ण output ओळखा, आणि अर्धी नोंद पाठवण्याऐवजी reask करा.

🔢 चुकीचे types

constraint शिवाय मॉडेल number साठी "42" किंवा boolean साठी "true" परत करतो. coercion सह typed validation हे पुढील गणित बिघडवण्याआधी पकडते आणि दुरुस्त करते.

👻 काल्पनिक fields

मॉडेल तुम्ही कधीही न ठरवलेल्या keys शोधून काढतो किंवा आवश्यक fields आत्मविश्वासाने केलेल्या अंदाजांनी भरतो. जादा properties मनाई करा आणि "unknown" ला प्रथम श्रेणीचे परवानगी असलेले मूल्य माना.

📦 अति-nested schemas

खोलवर nested, पसरलेली schemas error rates आणि latency वाढवतात. शक्य तिथे सपाट करा आणि मोठ्या extractions ना लहान, केंद्रित calls मध्ये विभाजित करा.

🎭 वैध पण चुकीचे

schema आकाराची हमी देते, सत्याची नाही. अगदी अचूक typed invoice अजूनही चुकीची total वाहून नेऊ शकते. रचनात्मक तपासण्या semantic evals आणि spot audits सोबत जोडा.

🔁 अनंत reask loops

अशक्य constraint वर कायम पुन्हा प्रयत्न केल्याने tokens जळतात आणि विनंत्या थांबतात. नेहमी retries मर्यादित करा आणि खऱ्या अपयशांसाठी स्वच्छ fallback ठरवा.

structured outputs कसे मोजावे

रचनात्मक वैधता आणि semantic शुद्धता वेगवेगळी नोंदवा, म्हणजे schema दुरुस्त करायचे की prompt हे तुम्हाला कळेल.

ढोबळ नियम: जर वैधता उच्च पण field accuracy कमी असेल, तर prompt आणि field descriptions दुरुस्त करा; जर वैधताच कमी असेल, तर आधी schema घट्ट करा किंवा अधिक बळकट constrained decoding चालू करा. मॉडेलला दोष देण्याआधी दोन्ही मोजा.
06 - Case Studies

वास्तविक जगातील case studies

production सारख्या वापरात structured outputs दाखवणारे तीन प्रातिनिधिक patterns.

📄

1 · कागदपत्रांमधून fields काढणे

Pattern: असंरचित मजकुरापासून typed records पर्यंत

एका finance संघाला हजारो PDF invoices मधून vendor, रक्कम, currency, आणि due date त्यांच्या ledger मध्ये काढायचे आहे.

  • एक Pydantic model प्रत्येक field types, patterns, आणि ranges सह extraction करार म्हणून ठरवते.
  • Schema-constrained decoding प्रत्येक उत्तर त्या model मध्ये स्वच्छपणे parse होण्याची हमी देते.
  • Cross-field validation (totals line-item बेरजांशी समान) आकडे जुळत नसतील तेव्हा reask सुरू करते.
✅ निष्कर्ष: Invoices validate केलेले objects म्हणून थेट ledger मध्ये वाहतात, प्रत्येक कागदपत्राऐवजी फक्त खरे संदिग्ध प्रकरणच माणसाकडे पाठवले जातात.
🔧

2 · tool आणि API call arguments तयार करणे

Pattern: function calling म्हणून structured output

एका assistant ला नैसर्गिक-भाषेतील विनंत्यांचे अंतर्गत APIs विरुद्ध अचूक calls मध्ये भाषांतर करावे लागते - search, booking, refunds.

  • प्रत्येक tool चे parameter schema मॉडेलला परवानगी असलेले arguments मर्यादित करते.
  • Enums आणि आवश्यक fields हे सुनिश्चित करतात की मॉडेल पूर्ण inputs सह खऱ्या operations निवडतो.
  • अवैध argument संच कोणतेही API स्पर्श होण्याआधी नाकारले जातात आणि reask केले जातात.
✅ निष्कर्ष: assistant सुव्यवस्थित arguments सह खरे endpoints कॉल करतो, त्यामुळे विकृत विनंत्या कधीही production यंत्रणांपर्यंत पोहोचत नाहीत आणि error handling साधे राहते.
🗂️

3 · Form आणि data-entry automation

Pattern: संभाषणापासून पूर्ण झालेल्या form पर्यंत

एक onboarding प्रवाह मुक्त-स्वरूपाच्या chat मधून अर्जदाराचे तपशील गोळा करतो आणि एक काटेकोर backend form भरावा लागतो.

  • एक zod schema form च्या अचूक fields, formats, आणि आवश्यक चौकटींचे प्रतिबिंब करते.
  • आंशिक structured output UI मध्ये stream होते, मॉडेल सोडवताच चौकटी थेट भरत जाते.
  • गहाळ किंवा विकृत नोंदी मूक अपयशाऐवजी लक्ष्यित पाठपुरावा प्रश्न विचारतात.
✅ निष्कर्ष: संभाषणे स्वच्छ, validate केलेल्या form सादरीकरणांमध्ये बदलतात, backend चा काटेकोर करार अबाधित ठेवत मॅन्युअल पुनर्टंकन कमी करतात.
07 - भविष्य

structured outputs कुठे चालले आहेत

Structured outputs एका जोडलेल्या parsing युक्तीपासून मॉडेल runtime च्या प्रथम श्रेणीच्या, हमी दिलेल्या क्षमतेकडे वाटचाल करत आहेत.

⛓️ Native constrained decoding

Grammar आणि schema अंमलबजावणी serving stack मध्येच बांधलेली, त्यामुळे retries भोवतीच्या SDK wrapper ऐवजी वैध output हा default असतो.

🌊 Streaming typed objects

प्रमाणित आंशिक parsing जे typed, टप्प्याटप्प्याने पूर्ण होणारे objects देते, त्यामुळे fields सुटताच UIs ती render करतात.

🧩 समृद्ध schema समर्थन

अधिक पूर्ण JSON Schema व्याप्ती - recursion, unions, conditionals, formats - तुम्ही काय व्यक्त करू शकता आणि decoding काय अंमलात आणू शकते यातील अंतर कमी करत.

🔗 Structured सोबत tools सोबत RAG

Typed outputs हे agents चे जोडणारे ऊतक: retrieval fields भरते, tools ती वापरतात, आणि प्रत्येक टप्पा मशीन-तपासण्याजोगा राहतो.

🧪 Semantic validation स्तर

Model-graded आणि नियम-आधारित तपासण्या ज्या केवळ आकार नव्हे तर अर्थ पडताळतात, schemas चुकवणारे "वैध पण चुकीचे" outputs पकडत.

⚡ कमी-भार अंमलबजावणी

वेगवान constraint compilation आणि token masking, latency खर्च कमी करत, त्यामुळे structured output सर्वत्र चालू करणे मुक्त होते.

सारांश: structured outputs हाच मार्ग आहे ज्याने तुम्ही probabilistic मॉडेलला विश्वासार्ह software component सारखे वागायला लावता - typed, validate केलेले, आणि खऱ्या यंत्रणांशी जोडण्यास सुरक्षित. जसजशी अंमलबजावणी runtime मध्ये सरकते, तसतसे "फक्त मला वैध डेटा द्या" ही आशा राहत नाही आणि हमी बनते.
