Tracing आणि Observability

तुमच्या LLM अ‍ॅपच्या आत पाहा - traces, spans आणि observability

LLM chains आणि agents हे non-deterministic ब्लॅक बॉक्स असतात: एकच request retrieval, model calls आणि tools मध्ये विखुरली जाते. Tracing ती संपूर्ण अंमलबजावणी nested spans च्या झाडासारखी नोंदवते - inputs, outputs, tokens, latency आणि cost सह - त्यामुळे LangSmith आणि Langfuse सारखी tools तुम्हाला तुमच्या अ‍ॅपने प्रत्यक्षात काय केले हे debug करू, मोजू आणि त्यावर विश्वास ठेवू देतात.

01 - काय

LLM tracing म्हणजे काय?

Tracing एका LLM request ची संपूर्ण अंमलबजावणी एक trace म्हणून नोंदवते - nested spans चे झाड. प्रत्येक span म्हणजे कामाचे एक एकक (एक retrieval, एक LLM call, एक tool invocation, एक chain step) ज्याचे स्वतःचे inputs, outputs, timing आणि metadata असते. Observability म्हणजे तुम्ही त्यावर जे बांधता ते: dashboards, evals आणि alerts जे त्या traces ला correctness, latency आणि cost विषयीच्या अंतर्दृष्टीत रूपांतरित करतात.

🌳 Trace

संपूर्ण request, मुळापासून पानापर्यंत - एक वापरकर्ता प्रश्न एक span झाड तयार करतो. तो एक trace ID वाहतो जो प्रत्येक step एकत्र बांधतो.

📏 Span

trace मधील एकच क्रिया - एक retrieval, generation किंवा tool call - सुरुवात/शेवट वेळ, inputs, outputs आणि parent link सह.

🏷️ Metadata

Model आणि version, prompt template, token counts, cost, user/session IDs, tags आणि errors जे नंतर विभागणीसाठी spans ला जोडलेले असतात.

एका span ने काय नोंदवायला हवे

क्षेत्रका महत्त्वाचेउदाहरण

मुख्य मानसिक प्रतिमान: एक trace म्हणजे probabilistic सॉफ्टवेअरसाठीचा stack trace. Logs तुम्हाला सांगतात की एक request घडली; एक trace प्रश्नाचे उत्तर तयार करणाऱ्या steps, prompts आणि निर्णयांचे नेमके झाड दाखवतो - जो non-deterministic chain debug करण्याचा एकमेव मार्ग आहे.
02 - का

Observability का अनिवार्य आहे

एकच input वेगवेगळे outputs तयार करू शकते, chains एका response मागे अनेक steps लपवतात आणि agents runtime ला स्वतःचा मार्ग ठरवतात. Traces शिवाय तुम्ही अंदाज लावत असता. Observability "ते कधीकधी वाईट उत्तरे देते" याला तुम्ही तपासू आणि दुरुस्त करू शकता अशा विशिष्ट span मध्ये बदलते.

🔬 Non-deterministic chains debug करा

एका वाईट उत्तराची नेमकी trace पुन्हा चालवून ते पुनरुत्पादित करा - retrieved context, rendered prompt आणि model कुठे चुकले ते पाहा.

🕹️ Agent वर्तन समजून घ्या

Agents स्वतःहून loop करतात, फांद्या फोडतात आणि tools call करतात. Span झाड त्यांचा तर्काचा मार्ग दृश्यमान करते जेणेकरून ते का loop झाले किंवा वाईट tool का निवडले ते तुम्ही पाहू शकता.

💸 Tokens आणि cost नियंत्रित करा

प्रत्येक span tokens आणि cost नोंदवते, त्यामुळे तुम्ही प्रति feature, user किंवा model खर्च आरोपित करू शकता आणि बिल येण्यापूर्वीच अनियंत्रित prompts पकडू शकता.

⏱️ Latency आणि regressions शोधा

प्रति-span timing मंद step उघड करते; model आणि prompt versions निश्चित केल्याने एखाद्या बदलाने गुणवत्ता किंवा latency खराब केली तेव्हा तुम्हाला ते पकडता येते.

सोप्या शब्दांत

उपमांसह LLM tracing समजावले

एकच कल्पना, ती चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती स्पष्ट होते.

🎓 विद्यार्थ्यासाठी

एक trace म्हणजे सोडवलेले उत्तर, केवळ अंतिम उत्तर नाही. फक्त गुण पाहण्याऐवजी, तुम्ही model ने घेतलेला प्रत्येक step पाहता, त्यामुळे तर्क नेमका कुठे चुकला ते तुम्ही ओळखू शकता.

👩‍💻 डेव्हलपरसाठी

हा probabilistic code साठीचा stack trace आहे. प्रत्येक span म्हणजे स्वतःचे inputs, outputs आणि timing असलेली एक frame, त्याच्या parent खाली nested, जेणेकरून प्रत्यक्षात तुटलेल्या call मध्ये तुम्ही खोलवर जाऊ शकता.

🏢 व्यावसायिकासाठी

प्रत्येक request साठीचा audit trail असा विचार करा: कोणी काय विचारले, कोणते sources खेचले गेले, प्रत्येक step ला किती खर्च आला आणि किती वेळ लागला, हे सर्व नंतर पुनर्रचित करता येते.

🛫 रोजच्या भाषेत

एक trace म्हणजे flight recorder, विमानातील ब्लॅक बॉक्स. जेव्हा काहीतरी बिघडते, तेव्हा मध्येच काय झाले याचा अंदाज लावण्याऐवजी तुम्ही रेकॉर्डिंग step by step पुन्हा चालवता.

03 - कसे

Tracing पडद्यामागे कसे कार्य करते

तुमचे अ‍ॅप असे instrumented केलेले असते की प्रत्येक step एक span उघडते, त्याचा डेटा नोंदवते आणि तो बंद करते. Spans batch केले जातात आणि asynchronously एका tracing backend कडे (LangSmith, Langfuse किंवा कोणताही OpenTelemetry collector) पाठवले जातात, जो त्यांना एका trace झाडात पुन्हा जोडतो आणि dashboards, evals आणि alerts चालवतो.

🪝 Instrumentation

Functions ला एका decorator किंवा callback ने गुंडाळा, किंवा SDK auto-instrument करा. प्रत्येक गुंडाळलेली call parent link सह एक span उत्सर्जित करते, त्यामुळे nesting आपोआप नोंदवली जाते.

🚚 Export आणि ingest

Hot path वेगवान ठेवण्यासाठी spans पार्श्वभूमीत buffer आणि flush केले जातात. Backend त्यांना साठवते, trace ID नुसार जोडते आणि tags, cost आणि latency नुसार index करते.

Pseudocode मध्ये एक chain instrument करणे

@trace(name="rag_request")          # opens the root span
def answer(question, user):
    with span("retrieval") as s:    # child span
        chunks = vector_db.search(question, filter=user.acl)
        s.log(inputs=question, outputs=chunks, latency_ms=s.dt)

    with span("llm") as s:          # sibling child span
        out = llm.generate(prompt(question, chunks))
        s.log(model="claude-sonnet-4-5",
              prompt_tokens=out.usage.input,
              completion_tokens=out.usage.output,
              cost=price(out.usage))
    return out.text
# → backend reconstructs: rag_request → [retrieval, llm]

प्रत्येक with span(...) सक्रिय parent खाली nest होते, त्यामुळे backend नेमके झाड पुन्हा बांधते. उच्च-volume systems मध्ये तुम्ही sample करता - 100% errors आणि उर्वरितांचा एक टक्का ठेवा - storage मर्यादित करण्यासाठी तरीही समस्या पकडत.

एका uninstrumented अ‍ॅपपासून पूर्णपणे observable अ‍ॅपपर्यंत - traces dashboards, evals आणि alerts ला अनुक्रमे पुरवत.

Instrument

Entry point गुंडाळा

तुमच्या अ‍ॅपमध्ये एक tracer जोडा आणि top-level handler ला decorate करा जेणेकरून प्रत्येक request एका अनन्य trace ID सह root span उघडते.

10
Nest

प्रत्येक step span करा

Retrieval, LLM calls आणि tool calls गुंडाळा जेणेकरून प्रत्येक त्याच्या parent ला जोडलेला child span बनतो, ज्यातून trace झाड तयार होते.

20
Capture

Inputs आणि outputs नोंदवा

प्रत्येक span वर rendered prompt, retrieved context आणि completion log करा - प्रत्येक नंतरच्या निदानासाठीचा कच्चा माल.

30
Measure

Tokens, latency आणि cost जोडा

Token counts, प्रति-span कालावधी, model आणि version आणि काढलेला cost जोडा जेणेकरून spans केवळ वर्णनात्मक नव्हे तर परिमाणात्मक होतात.

40
Tag

Metadata जोडा

User, session, tenant आणि feature tags सोबत environment जोडा, जेणेकरून traces नंतर विभागता आणि filter करता येतात.

50
Export

Spans asynchronously पाठवा

Request मंद न करता spans पार्श्वभूमीत buffer आणि flush करून LangSmith, Langfuse किंवा एका OpenTelemetry collector कडे पाठवा.

60
Sample

मोठ्या प्रमाणात volume मर्यादित करा

100% errors आणि निरोगी वाहतुकीचा एक टक्का ठेवा जेणेकरून समस्या तरीही समोर येत असताना storage आणि cost मर्यादित राहतात.

70
Reassemble

Trace झाडात जोडा

Backend spans ला trace ID नुसार एका navigable झाडात जोडते आणि त्यांना tag, cost, latency आणि error नुसार index करते.

80

Traces ला evals आणि datasets शी जोडा

वास्तविक traces evaluation datasets मध्ये चढवा आणि outputs गुणांकित करा - production वर्तनाला offline गुणवत्ता तपासण्यांशी जोडत.

90

Dashboards आणि alerts

p95 latency, cost आणि error rate चार्ट करा; असे thresholds सेट करा जे एखादा मापदंड त्याचे अंदाजपत्रक ओलांडतो तेव्हा on-call ला page करतात.

100
Improve

Debug करा, दुरुस्त करा, पुन्हा करा

दोषी trace उघडा, root-cause span शोधा, एक fix पाठवा आणि मापदंड सुधारताना पाहा - एक बंद observability loop.

सामान्य धोके

धोके आणि anti-patterns

Tracing चुकीच्या पद्धतीने जोडणे सोपे आहे. या त्या चुका आहेत ज्या traces ला गळक्या, महाग किंवा निरुपयोगी बनवतात.

🔓 Traces मध्ये PII log करणे

कच्चे prompts आणि outputs टाकल्याने नावे, ईमेल आणि secrets plaintext मध्ये नोंदवले जातात. संवेदनशील fields capture च्या वेळी redact किंवा hash करा आणि पाठवण्यापूर्वी retention नियम सेट करा.

💥 मोठ्या प्रमाणात sampling नसणे

100% वाहतूक साठवणे dev मध्ये ठीक दिसते आणि production मध्ये storage आणि cost फुगवते. मर्यादित राहण्यासाठी प्रत्येक error आणि निरोगी वाहतुकीचा एक sampled अंश ठेवा.

📃 Spans ऐवजी flat logs

असंरचित log ओळी उत्सर्जित केल्याने parent-child झाड फेकून दिले जाते. Nested spans शिवाय कोणत्या step ने कोणत्या step ला call केले, किंवा वेळ प्रत्यक्षात कुठे खर्च झाला हे तुम्ही पाहू शकत नाही.

🏷️ Token आणि cost metadata गहाळ

Token counts, model किंवा cost नसलेले spans observability ला अशा सुंदर timelines मध्ये बदलतात ज्यांच्या विरुद्ध तुम्ही अंदाजपत्रक करू शकत नाही. प्रत्येक model span ला usage जोडा.

🚨 केवळ errors trace करणे

फक्त काहीतरी throw होते तेव्हा spans नोंदवल्याने मंद-पण-यशस्वी आणि आत्मविश्वासाने-चुकीचे लपले जाते. केवळ exceptions नव्हे, संपूर्ण context trace करा.

🔗 Traces evals शी जोडलेले नाहीत

जे traces कधीच datasets किंवा scorers ला पुरवत नाहीत ते एक debugging खेळणे राहतात. वास्तविक traces evals मध्ये चढवा जेणेकरून production वर्तन offline गुणवत्ता तपासण्या चालवते.

06 - केस स्टडीज

वास्तविक जगातील केस स्टडीज

Production-शैलीच्या वापरात tracing आणि observability दाखवणारे तीन प्रातिनिधिक patterns.

🤖

1 · गैरवर्तन करणारा agent debug करणे

Pattern: span झाडातून root-cause

एक agent कधीकधी अनंत काळ loop करतो किंवा चुकीच्या tool मधून उत्तर देतो, आणि logs फक्त अंतिम अपयश दाखवतात.

  • Trace झाड प्रत्येक reason-act step, निवडलेले tool आणि प्रत्येक वळणावर पाठवलेले args उघड करते.
  • Spans तपासल्याने उघड होते की model ने database call करायला हवी होती तेव्हा एक search tool निवडले.
  • तो fix - एक धारदार tool वर्णन आणि एक step मर्यादा - trace पुन्हा चालवून पडताळला जातो.
✅ परिणाम: एक अस्पष्ट "agent अविश्वसनीय आहे" एका विशिष्ट span वरील विशिष्ट वाईट निर्णयात बदलतो, अंदाज लावण्याऐवजी दुरुस्त आणि पुष्ट केला जातो.
💸

2 · एका product ओलांडून cost आणि token देखरेख

Pattern: spans पासून खर्च आरोपण

एका LLM feature चे बिल चढत आहे आणि कोणता flow किंवा user ते चालवत आहे हे कोणालाच माहीत नाही.

  • प्रत्येक span tokens आणि cost नोंदवते, feature, tenant आणि model नुसार tagged.
  • एक dashboard खर्च गटबद्ध करते जेणेकरून एक बडबडा prompt template सर्वात मोठा cost चालक म्हणून वेगळा दिसतो.
  • तो prompt छाटणे आणि एक step स्वस्त model वर बदलणे गुणवत्ता न गमावता cost कमी करते.
✅ परिणाम: Cost नेमक्या feature आणि prompt ला आरोपित होतो, त्यामुळे optimization सरसकट rate limits ऐवजी खऱ्या चालकावर लक्ष केंद्रित करते.
⏱️

3 · मंद span शोधून latency optimization

Pattern: प्रति-span timing विश्लेषण

एक RAG endpoint मंद वाटतो, पण retrieval, reranking की generation दोषी आहे हे संघाला सांगता येत नाही.

  • प्रति-span latency दाखवते की reranking, LLM नव्हे, बहुतांश p95 अंदाजपत्रक खाते.
  • Reranker async केला जातो आणि त्याचा candidate set छाटला जातो, तो span आकुंचित करत.
  • Dashboard पुष्टी करते की p95 घसरते आणि कोणतेही error किंवा गुणवत्ता regression येत नाही.
✅ परिणाम: मंद step गृहीत न धरता मोजला जातो, त्यामुळे मेहनत प्रत्यक्षात latency आकडा हलवणाऱ्या span वर पडते.
07 - भविष्य

Observability कुठे जात आहे

LLM observability खुल्या मानकांवर एकत्र येत आहे आणि production traces आणि गुणवत्ता यांच्यातील loop घट्ट करत आहे.

📐 OpenTelemetry मानक

GenAI semantic conventions span नावे आणि attributes प्रमाणित करत आहेत, त्यामुळे traces lock-in शिवाय vendors दरम्यान हलतात.

🧪 Live traces वर online evals

LLM-as-judge आणि heuristic scorers sampled production traces वर सतत चालतात, वास्तविक वेळेत गुणवत्ता घसरण उघड करत.

🔁 Trace-ते-dataset loops

रोचक किंवा अयशस्वी traces थेट eval datasets मध्ये वाहतात, जे पाठवले आणि जे तुम्ही तपासता यातील अंतर बंद करत.

🧠 AI-सहाय्यित root cause

Models एक अयशस्वी trace सारांशित करतात आणि दोषी span आणि fix सुचवतात, गुंतागुंतीच्या agents वर time-to-diagnosis कमी करत.

🕹️ Agent-native observability

Loops, फांद्या आणि tool graphs साठी खास बनवलेली दृश्ये खोल agent traces जबरदस्त होण्याऐवजी navigable बनवतात.

🔐 गोपनीयता-जागरूक tracing

आपोआप PII redaction आणि sampling संघांना data-handling आणि retention नियमांचा आदर करत समृद्ध traces ठेवू देतात.

सारांश: tracing हा probabilistic system चालवण्यायोग्य बनवण्याचा मार्ग आहे - अदृश्य chains आणि agents ला एका debuggable, मोजता येणाऱ्या span झाडात बदलत. मानके परिपक्व होत असताना आणि evals online जात असताना, observability प्रत्येक गंभीर LLM product चा कणा बनते.
