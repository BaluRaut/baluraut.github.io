Retrieval-Augmented Generation

RAG खरोखर कसे चालते - संपूर्ण चित्र

LLMs त्यांच्या training cutoff वेळी गोठलेले असतात आणि तुमच्या खाजगी डेटाबद्दल त्यांना काहीच माहीत नसते. RAG हे दुरुस्त करते: ते query वेळी तुमच्या knowledge base मधून संबंधित chunks retrieve करते आणि त्यांच्यासह prompt augment करते, त्यामुळे मॉडेल अंदाज लावण्याऐवजी खऱ्या, ताज्या आणि उद्धृत केलेल्या स्रोतांमधून उत्तर देते.

01 - काय

RAG म्हणजे काय?

Retrieval-Augmented Generation हा एक पॅटर्न आहे जो language model ला बाहेरील knowledge store शी जोडतो. मॉडेलने training दरम्यान लक्षात ठेवलेल्या गोष्टींवरच अवलंबून राहण्याऐवजी, तुम्ही प्रश्नासाठी सर्वात संबंधित उतारे retrieve करता आणि context म्हणून prompt मध्ये टाकता. मग मॉडेल त्या retrieve केलेल्या पुराव्यावर आधारित उत्तर तयार करते.

📥 Ingestion (offline)

दस्तऐवज chunks मध्ये विभागले जातात, vectors मध्ये embed केले जातात आणि vector database मध्ये साठवले जातात. हे एकदाच, आधीच केले जाते.

🔎 Retrieval (online)

Query वेळी, प्रश्न embed केला जातो आणि semantic similarity नुसार सर्वात जवळचे chunks आणले जातात.

🧠 Generation (online)

Retrieve केलेले chunks prompt मध्ये जोडले जातात; मॉडेल त्यांचा वापर करून उत्तर देते, आदर्शतः citations सह.

मुख्य घटक

घटकते काय करतेसामान्य पर्याय
Chunkerदस्तऐवजांना retrieve करण्यायोग्य तुकड्यांमध्ये विभागतोFixed-size, recursive, semantic, by-heading

मुख्य मानसिक प्रतिमा: RAG मॉडेलला नवीन तथ्ये शिकवत नाही, ते उत्तर देण्याच्या क्षणी योग्य तथ्ये मॉडेलच्या समोर ठेवते. Retrieval ची गुणवत्ता, LLM नव्हे, हीच सहसा RAG सिस्टम यशस्वी किंवा अयशस्वी करते.
02 - का

RAG का अस्तित्वात आहे

Fine-tuning ज्ञान weights मध्ये भाजून टाकते, ते संथ, महाग असते आणि तुमचा डेटा बदलताच जुने होते. RAG ज्ञान मॉडेलच्या बाहेर ठेवते, जिथे ते अद्ययावत करणे स्वस्त आणि नियंत्रित करणे सोपे असते.

🎯 Hallucination कमी करते

उत्तरे retrieve केलेल्या मजकुरात ग्राउंड केल्याने बनवलेली तथ्ये तीव्रपणे कमी होतात आणि पडताळणीसाठी तुम्हाला स्रोत उद्धृत करता येतात.

🔄 नेहमी ताजे

Knowledge base अद्ययावत करा आणि उत्तरे लगेच बदलतात, retraining ची गरज नाही. एखादा दस्तऐवज जोडा, संपादित करा किंवा हटवा आणि पुढच्या query मध्येच ते प्रतिबिंबित होते.

🔐 खाजगी आणि access-controlled

तुमचा डेटा कधीही मॉडेलच्या weights मध्ये जात नाही. तुम्ही user permissions नुसार retrieval फिल्टर करू शकता जेणेकरून लोकांना फक्त त्यांना परवानगी असलेलेच दिसेल.

💸 Fine-tuning पेक्षा स्वस्त

कोणतेही training runs नाहीत. तुम्ही embeddings साठी एकदा पैसे देता आणि प्रत्येक query साठी थोडासा अतिरिक्त context, खर्च आणि श्रमाचा एक अंश.

सोप्या शब्दांत

उपमांसह RAG चे स्पष्टीकरण

एकच कल्पना, ती चित्रित करण्याचे चार मार्ग, जेणेकरून तुम्ही कोणीही असाल तरी ती लक्षात येईल.

🎓 विद्यार्थ्यासाठी

RAG म्हणजे एक ओपन-बुक परीक्षा. मॉडेलला सर्व काही पाठ करण्याची गरज नाही; ते आधी संबंधित पाने पाहते, मग समोर पुस्तक उघडे ठेवून उत्तर लिहिते.

👩‍💻 डेव्हलपरसाठी

हे एका function समोर search index ठेवण्यासारखे आहे. ज्ञान hardcode करण्याऐवजी, तुम्ही store ला महत्त्वाच्या rows साठी query करता, मग त्या मॉडेल कॉलला arguments म्हणून पास करता.

🏢 व्यावसायिकासाठी

एका संशोधन सहाय्यकाची कल्पना करा जो तुमच्या मीटिंगपूर्वी कॅबिनेटमधून नेमक्या फाइल्स काढतो, जेणेकरून तुमचे briefing अस्पष्ट स्मृतीऐवजी खऱ्या दस्तऐवजांचे उद्धरण देते.

🍳 दैनंदिन आवृत्ती

एक शेफ जो स्वयंपाक करण्यापूर्वी रेसिपी कार्ड पाहतो, स्मृतीतून अंदाज लावण्याऐवजी. कौशल्य तेच असते; तथ्ये कार्डवरून येतात.

03 - कसे

आतल्या बाजूने ते कसे चालते

RAG मध्ये दोन pipelines असतात: एक offline ingestion pipeline जो index तयार करतो, आणि एक online query pipeline जो प्रत्येक request साठी चालतो.

📦 Ingestion pipeline

Load → clean → chunk → embed → vector store मध्ये upsert करा. प्रत्येक chunk सोबत metadata (source, section, permissions, timestamp) जाते.

⚡ Query pipeline

प्रश्न embed करा → top-k search करा → (पर्यायाने) rerank करा → grounded prompt जमवा → generate करा → उत्तर + citations परत करा.

एका दृष्टीक्षेपात आर्किटेक्चर

आर्किटेक्चर - ingestion index तयार करते; queries त्यातून वाचतात
flowchart LR
    subgraph Ingest["📦 Offline ingestion"]
        D["📄 Documents"] --> CH["✂️ Chunk"]
        CH --> EM1["🔢 Embed"]
        EM1 --> VDB[("🗄️ Vector DB")]
    end
    subgraph Query["⚡ Online query"]
        Q["❓ User question"] --> EM2["🔢 Embed query"]
        EM2 --> SR["🔎 Similarity search"]
        VDB --> SR
        SR --> RR["📊 Rerank"]
        RR --> PR["🧩 Build prompt + context"]
        PR --> LLM["🧠 LLM"]
        LLM --> ANS["✅ Grounded answer + citations"]
    end

Pseudocode मध्ये एक किमान query

q_vec   = embed(question)
hits    = vector_db.search(q_vec, top_k=20, filter=user_acl)
top     = rerank(question, hits)[:5]
context = "\n\n".join(h.text + f"  [source: {h.source}]" for h in top)

answer = llm.generate(
    system="Answer ONLY from the context. Cite sources. Say 'I don't know' if absent.",
    user=f"Context:\n{context}\n\nQuestion: {question}"
)

लक्षात घ्या की system prompt मॉडेलला retrieve केलेल्या context पुरते मर्यादित करतो आणि माहीत नसल्यास टाळण्यास सांगतो, हेच retrieval ला विश्वासार्ह, grounded generation मध्ये बदलते.

05 - टप्प्याटप्प्याने

0 → 100 प्रवाह

रिकाम्या knowledge base पासून उद्धृत, grounded उत्तरापर्यंत, संपूर्ण प्रवास क्रमाने.

00
Ingest

स्रोत गोळा करा आणि स्वच्छ करा

दस्तऐवज गोळा करा - wikis, PDFs, tickets, databases - आणि boilerplate, headers व noise काढून टाका जेणेकरून फक्त उपयुक्त मजकूर उरेल.

10
Chunk

Retrieve करण्यायोग्य तुकड्यांमध्ये विभागा

दस्तऐवजांना retrieval साठी योग्य आकाराच्या chunks मध्ये (सहसा 200-800 tokens) थोड्या overlap सह विभागा, आणि source व section सारखे metadata जोडा.

20
Embed

Chunks ना vectors मध्ये बदला

प्रत्येक chunk embedding model मधून चालवा जेणेकरून high-dimensional space मध्ये त्याचा अर्थ पकडणारा vector मिळेल.

30
Index

Vector database मध्ये साठवा

जलद similarity search साठी ANN index असलेल्या vector store मध्ये vectors आणि त्यांचा मजकूर व metadata upsert करा.

40
Query

वापरकर्ता प्रश्न विचारतो

एक request येते. प्रश्न ingestion साठी वापरलेल्याच model ने embed केला जातो जेणेकरून vectors त्याच space मध्ये राहतील.

50
Retrieve

Top-k chunks शोधा

वापरकर्त्याच्या access permissions नुसार फिल्टर करून vector store मध्ये nearest neighbors शोधा. Hybrid search keyword matching जोडते.

60
Rerank

Relevance तीक्ष्ण करा

एक cross-encoder किंवा LLM reranker candidates ना पुन्हा गुण देतो जेणेकरून prompt मध्ये पोहोचण्यापूर्वी सर्वात योग्य उतारे वर येतील.

70
Gate

ठरवा: उत्तर द्या की टाळा

जर सर्वोत्तम score खूपच कमी असेल, तर सिस्टम hallucinate करण्याऐवजी "मला माहीत नाही" म्हणते, हे विश्वासाचे एक महत्त्वाचे पाऊल आहे.

80
Augment

Grounded prompt जमवा

निवडलेले chunks prompt मध्ये जोडा, फक्त context मधूनच उत्तर देण्याच्या आणि प्रत्येक source उद्धृत करण्याच्या सूचनांसह.

90
Generate

मॉडेल पुराव्यावरून उत्तर देते

LLM retrieve केलेल्या context चा वापर करून उत्तर तयार करते, नेमक्या स्रोतांकडे परत निर्देश करणारी citations जोडते.

100
Deliver

उत्तर + स्रोत परत करा

वापरकर्त्याला clickable citations सह एक grounded, पडताळण्यायोग्य उत्तर मिळते. Feedback आणि logs कालांतराने retrieval सुधारण्यासाठी evals ला पुरवतात.

सामान्य अडचणी

अडचणी आणि anti-patterns

बहुतेक RAG सिस्टम मॉडेलवर नव्हे तर retrieval वर अपयशी ठरतात. हे नेहमीचे दोषी आहेत.

✂️ चुकीचे chunking

खूप मोठे chunks उत्तर noise मध्ये गाडतात; खूप लहान असल्यास context गमावतात. वाक्याच्या किंवा table च्या मधोमध विभागल्याने अर्थ नष्ट होतो. आंधळ्या character count नुसार नव्हे तर रचनेनुसार chunk करा.

🔀 Embedding मध्ये विसंगती

Queries आणि documents वेगवेगळ्या models ने embed करणे, किंवा re-indexing शिवाय model बदलणे, vectors ना विसंगत spaces मध्ये टाकते आणि retrieval कोसळते.

📉 Reranking नाही

फक्त raw vector similarity वर अवलंबून राहिल्याने बरेचदा "संबंधित पण चुकीचे" chunks समोर येतात. Reranker वगळणे हे प्रशंसनीय-पण-चुकीच्या उत्तरांचे सर्वात सामान्य कारण आहे.

📚 Context मध्ये अति-भरणा

Prompt मध्ये 30 chunks कोंबल्याने खर्च वाढतो आणि "lost in the middle" ट्रिगर होते, जिथे मॉडेल लांब context च्या मधला भाग दुर्लक्षित करते. विस्तृतपणे retrieve करा, पण थोडेच पाठवा.

🎭 Abstention नाही

जर सिस्टम कधीच "मला माहीत नाही" म्हणत नसेल, तर कमी-relevance असलेल्या retrievals ला तरीही उत्तर दिले जाते आणि मॉडेल आत्मविश्वासाने hallucinate करते. नेहमी relevance threshold वर gate करा.

🕰️ जुना किंवा गळणारा index

बदललेले docs पुन्हा embed करायला विसरल्याने जुनी उत्तरे दिली जातात; access filters वगळल्याने डेटा वापरकर्त्यांमध्ये गळतो. Index ही एक जिवंत, permissioned मालमत्ता आहे.

एका SaaS कंपनीला असा सहाय्यक हवा आहे जो फीचर्स न बनवता तिच्या docs मधून ग्राहकांच्या प्रश्नांची उत्तरे देतो.

  • Help-center लेख आणि release notes heading नुसार chunk केले जातात आणि दररोज रात्री embed केले जातात.
  • प्रत्येक उत्तराने ज्या लेखातून आले तो उद्धृत करावा; कमी-confidence असलेल्या queries माणसाकडे पाठवल्या जातात.
  • Retrieval product tier नुसार फिल्टर केले जाते जेणेकरून ग्राहकांना फक्त त्यांनी विकत घेतलेल्या गोष्टीचेच docs दिसतात.
✅ निकाल: नित्याच्या tickets चे प्रमाण खूप कमी चुकीच्या उत्तरांसह कमी झाले, कारण प्रत्येक प्रतिसाद grounded असतो आणि खऱ्या doc पर्यंत मागोवा घेता येतो.
⚖️

2 · कायदेशीर आणि contract search

पॅटर्न: संवेदनशील दस्तऐवजांवर precision retrieval

एका कायदेशीर टीमला हजारो contracts वर प्रश्न विचारून paraphrases नव्हे तर नेमकी clauses मिळवायची आहेत.

  • Hybrid search (semantic + keyword) अर्थ आणि नेमक्या कायदेशीर संज्ञा दोन्ही पकडते.
  • एक cross-encoder reranker नेमकी clause प्रथम रँक होईल याची खात्री करतो.
  • कडक access controls आणि on-prem embeddings गोपनीय डेटा फर्मच्या आत ठेवतात.
✅ निकाल: वकील source contract च्या citations सह काही सेकंदांत governing clauses शोधतात, तर संवेदनशील मजकूर कधीही security boundary सोडत नाही.
🏥

3 · engineers साठी अंतर्गत knowledge base

पॅटर्न: अनेक systems वर enterprise search

एक engineering संस्था wikis, runbooks, Slack आणि code docs एकाच सहाय्यकात एकत्र करते.

  • Connectors अनेक स्रोतांमधून ingest करतात; metadata मूळ आणि ताजेपणा नोंदवते.
  • बदलावर जुने chunks पुन्हा embed केले जातात जेणेकरून उत्तरे सध्याची स्थिती प्रतिबिंबित करतात.
  • उत्तरे पडताळणीसाठी नेमक्या runbook किंवा thread कडे परत link करतात.
✅ निकाल: Engineers पाच tools मध्ये शोधणे थांबवतात; सहाय्यक citation सह योग्य runbook समोर आणतो, ज्यामुळे निराकरणाचा वेळ कमी होतो.
07 - भविष्य

RAG कुठे जात आहे

RAG एका retrieve-मग-read पायरीपासून अधिक समृद्ध, अधिक अनुकूल सिस्टममध्ये विकसित होत आहे.

🤖 Agentic RAG

असे agents जे multi-step retrieval ची योजना करतात - प्रश्न विघटित करणे, पुनरावृत्तीने शोधणे आणि पुरेसा पुरावा कधी मिळाला हे ठरवणे.

🕸️ GraphRAG

अनेक दस्तऐवजांमधील तथ्ये जोडण्याची आवश्यकता असलेल्या प्रश्नांची उत्तरे देण्यासाठी vector search ला knowledge graphs सोबत जोडणे.

📈 Retrieval evals प्रथम-श्रेणीचे

Recall, precision आणि faithfulness सतत मोजणे - retrieval गुणवत्तेला सर्वात महत्त्वाचा मापदंड मानणे.

🧩 Long-context विरुद्ध RAG

मोठे context windows RAG ला संपवणार नाहीत; ते त्याला पूरक ठरतात - RAG कोणत्याही scale वर खर्च, ताजेपणा आणि access नियंत्रित करते.

🎛️ Adaptive retrieval

अशा सिस्टम ज्या प्रश्नाच्या अडचणीवर आणि confidence वर आधारित retrieve करायचे की नाही, आणि किती, हे ठरवतात.

🖼️ Multimodal RAG

फक्त मजकुरावरच नव्हे तर images, tables, audio आणि video वर retrieve करणे - प्रत्येक डेटा प्रकारावर grounded उत्तरांसाठी.

सारांश: RAG हा असा मार्ग आहे ज्याद्वारे तुम्ही एका सामान्य मॉडेलला तुमचे विशिष्ट, ताजे, permissioned ज्ञान देता - स्वस्तपणे आणि पडताळण्यायोग्यपणे. जसजसे models आणि retrievers सुधारतात, तसतसा हा पॅटर्न खऱ्या AI उत्पादनांसाठी अधिकच केंद्रस्थानी येतो.
